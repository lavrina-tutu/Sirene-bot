# Запуск роли dev-workflow из terminal (bootstrap)

Класс задачи: штатно посадить роль (архитектор/ревизор/исполнитель) через pipeline CLI из terminal — когда готового слага нет (например, RESEARCH-анализ текста от архитектора) или нужно повторить invoke вручную.

## Bootstrap CLI

Когда владелец запрещает pipeline и велит запускать роли напрямую через codex (без emit/invoke-контура, файлы в одной общей папке in/out/evidence, полная остановка после каждой задачи) — см. `references/direct-mode.md`: полная последовательность, модели ролей, правила диспетчеризации и питфоллы прямого режима; там же пилот на штатном канбане (карточки `hermes kanban create/complete` + codex, родитель-цепочки, TEST-PILOT-метка) и сборка итога проверки шаги 19–21 (матрица H01–H08 — М0; правка реального ТЗ — архитектор астра).

Команда `pipeline` — это `python3 -m pipeline.cli`, а не системная утилита. Чтобы `ModuleNotFoundError: No module named 'pipeline'` не съел первый ход, перед ЛЮБЫМ вызовом выставить оба env:

```bash
PIPELINE_ROOT=/home/tkachenkoav/WorkVault/Registries/pipeline      # фактический каталог CLI
PYTHONPATH="$(dirname "$PIPELINE_ROOT")"                          # ~/WorkVault/Registries — иначе модуль не импортируется
export PIPELINE_ROOT PYTHONPATH
```

`tools.dev_workflow` в EcosystemConfig.yaml — единственный источник путей (`DEV_STATE_ROOT`, `TZ_ROOT`, `PIPELINE_ROOT`, `SKILL_ROOT`). Режим `orchestration.mode=workflow-only` разрешает `init` для любого слага, не только `pilot_slugs`.

## Новая задача под конкретную роль (например, RESEARCH-текст от архитектора)

1. `suggest-slug --title '<формулировка>' --kind train` → свободный слаг (поле `slug`, `collision:false`).
2. `init --case <CASE> --slug <slug> --title '<title>' --origin-chat <chat_id> --origin-thread <thread> --slug-source suggest-cli` — создать задачу по рецепту кейса.
3. **brief.md с fenced-блоком ````handoff-contract` для ПЕРВОЙ ролевой фазы любого поезда, в рецепте которого есть `TZ:compress`/`HF:compress` (CHANGE/SKILL-CHANGE/DEV) — она почти всегда компрессорная.** RESEARCH (`RS:collect`) и `DEC:inventory` тоже требуют brief (ramka/`required input missing`) — но там отсутствие даёт явный сбой; для ТЗ-поезда оно ТИХОЕ: emit проходит с rc=0 и `write_scope:[]`, роль полный проход (пишет валидный `extract.md`), и только `complete-phase` отвергает `output outside write_scope` — ход и труд потрачены. Поэтому контракт писать ДО первого emit: `write_scope`/`outputs` перечисляют фазу `TZ:compress` (workspace → `extract.md`), не только `TZ:patch`/`REV:tz`. Проверить `status` (фаза todo).
4. `emit-prompt --slug <slug> --phase <PHASE> --out /tmp/task.md` → `invoke-role`.

Первые фазы ТЗ-поезда (CHANGE/SKILL-CHANGE/DEV) оркестраторские: `SK:preflight` → `preflight --mode create` (rc=0) + `complete-phase` с evidence `path=`/`sha256=`; `TZ:stabilize` → `complete-phase` с evidence `path=<master> version=<ver> mtime=<ns>` (НЕ sha256). Стабилизацию emit `TZ:compress` требует `--master-tz` (иначе `master binding required`). Лечение `output outside write_scope` на свежей компрессорной фазе (артефакт валиден): править контракт → `recover --class rc0-no-complete` (или dead-pid) → СВЕЖИЙ emit (новая packet_id) → один фоновый invoke. Принять артефакт «вручную» нельзя (G2 требует живую роль).

## Invoke-role

```text
pipeline invoke-role --role <architect|reviewer|executor> --prompt-file /tmp/task.md --workspace <ABS> --slug <slug> --phase <PHASE>
```

Фоновый wrapper invoke-role обязан экспортировать **оба** env (PIPELINE_ROOT и PYTHONPATH) в ОДНОЙ команде И нести все три обязательных аргумента (`--workspace <ABS>` относится к обязательным: argparse падает `error: the following arguments are required: --workspace`, rc=2, ДО любого prepare). Забытый PYTHONPATH в фоновом вызове даёт тихий rc=1 `ModuleNotFoundError: No module named 'pipeline'` (модуль CLI не найден — роль вообще не стартовала); забытый `--workspace` — rc=2 с usage-сообщением. Оба легко спутать с dead-pid/empty-result. Признак `"/venv/.../python3": Error while finding module specification for 'pipeline.cli'` в выводи lookup; до любого reset/повторного invoke сперва прочитать вывод упавшего фонового процесса и увидеть, какая часть команды отсутствует — launch-баг чинится одним перезапуском с полным env/аргументами, без сброса state (в этом классе фаза уходит в WORK/awaiting и трогать её по dead-pid-регламенту нельзя). Команда, собранная с одного из двух env или без `--workspace` вручную, НЕ надёжна — держать готовую обёртку (как `export PIPELINE_ROOT=...; export PYTHONPATH=...; python3 -m pipeline.cli invoke-role ... --workspace <ABS> ...`) одной строкой и не переписывать её по частям.

Для Hermes `terminal` invoke передавать **одним** request: `background=true`, `notify=true`, `persist_on_release=true` (поля tool request, не shell-флаги). Из полученного session id вести приём результата того же запуска. Не переспрашивать `wait`/`poll` в цикле: `notify_on_complete` доставит уведомление само; цикл sleep/wait на уже-running процессе жжёт ходы и не ускоряет завершение. То же правило — в canonical invoke.md: не мониторить свой wrapper, не двойной invoke при живом. **Ошибка `notify only applies to background commands (foreground results return directly)` означает одно: `background=true` не передан на уровне TOOL-параметра (переданы только `notify`/`persist_on_release`).** Лечение — вызвать terminal с `background=true` наряду с notify в том же request, а НЕ менять аргументы команды и не передёргивать «передано ли» каждый раз — это чисто tool-поле, а не shell-флаг.

**Foreground invoke-role на роль, реально работающую >180с (компрессор, bounded/full regression с `--total-timeout 3600`, большие матрицы), гарантированно обрывается таймаутом терминала.** Если несколько первых запусков в сессии были foreground и каждый умирал по 180–420с — это не «роль не отвечает», а именно foreground-таймаут; дольше ждать в foreground нельзя (кап 600с). Особо коварно при bounded/full regression: запущенный foreground прогон умирает на середине счёта узлов, оставляя фазу в `doing` с мёртвым pid → только recover dead-pid + reopen + повторный запуск; счёт узлов потерян. Практическое правило: для TZ:compress/HF:compress, HF:test prep с bounded regression и любых ролей с крупной работой сразу `background=true`+`notify` — никогда не foreground.

**CLI-флаг `--background` у invoke-role НЕ существует — передавать фон ТОЛЬКО флагами terminal-tool (`background=true, notify=true, persist_on_release=true`), не shell-аргументом.** Проброс `python3 -m pipeline.cli invoke-role ... --background` даёт мгновенный rc=2 (`unknown mode`), роль вообще не стартует; это другая ошибка, не dead-pid и не сбой фазы — просто перезапуск через terminal-wrapper. Признак: перед любым dead-pid reset глянуть `process_manage log`/stdout упавшего вызова — увидеть `unknown mode` и понять, что нужен только правильный способ запуска, без трогания state.

**Хвостовой `&` в самой команде invoke при `background=true` НЕ добавлять — он двойной-оборачивает команду и ломает env дочернего `python3`, который падает `ModuleNotFoundError: No module named 'pipeline'` как будто PYTHONPATH не передан.** Когда terminal-tool уже бежит командой как фон (`background=true` — поле tool-request), завершающий `&` (напр. `python3 -m pipeline.cli invoke-role ... &`) заворачивает всю строку в ещё один фоновый job, `export`-переменные не доезжают до дочернего интерпретатора, и `invoke_role.py` стартует с голым env. Признак: фоновый процесс завершился `exit 1` с выводом `/venv/.../python3: Error while finding module specification for 'pipeline.cli' (ModuleNotFoundError: No module named 'pipeline')`, а PYTHONPATH в команде при этом указан. Это НЕ «PYTHONPATH забыт» и НЕ dead-pid: убрать хвостовой `&`, оставить `background=true` на уровне tool-поля — команда одна строка, без shell-фона внутри неё. Сверяться по `process_manage wait`/лог упавшего вызова: если в выводе виден лишний `&`-собранный `[1] ...` от родительской оболочки — отбросить `&`, перезапустить чистым фоновым tool-вызовом.

**РОВНО один concurrent invoke на фазу — несколько ПАРАЛЛЕЛЬНЫХ invoke поверх живого wrapper'а той же фазы плодят лишние `invoke_prepare`, ломают инвариант G2 (`accepted prepare/result receipt mismatch`) и позволяют закрыть `GATE:done` раньше реального завершения фазы.** Когда первый (живой) wrapper уже пишет артефакт, а оркестратор паникует и гонит повторные invoke «на ускорить», каждый лишний вызов делает новый `invoke_prepare`/packet; в итоге фаза остаётся `doing` со stale pid, артефакт написан, но `complete-phase` на ней вечно даёт receipt mismatch, а при попытке закрыть поезд авто-гейт успевает уйти `done` раньше времени — поезд «закрыт преждевременно», фаза в нём числится незавершённой. Лечение НЕ в ещё одном invoke: сперва РАЗ упокоить хаос одним последовательным контролем фактического состояния (`status` + `journal.md` + ps wrapper'а), затем разбирать по классу (если arтефакт и `proof.context_result`/receipt есть — штатный `complete-phase` с реальным sha; если receipt потерян из-за лишнего prepare — восстановить `proof.context_result` в точном формате `invoke_role` и обычный complete). Вывод-правило панической серии: не запускать повторный invoke, пока первый wrapper жив и пишет (не мониторить свой wrapper); единственный легитимный повод — мёртвый wrapper с НЕнаписанным артефактом после `recover dead-pid`. Отличать от одиночного второго invoke после dead-pid (допустим один corrective-повтор) — здесь вред именно от ПАРАЛЛЕЛЯТСЯ нескольких живых.**

**Foreground-таймаут роли, успевшей записать канон на диск, оставляет dead-pid НЕ с receipt-mismatch, а с «фаза → todo» после `recover --class dead-pid`.** Пример REV:plan: ревизор записал REV-plan.md (APPROVE на диске), но invoke оборвался ДО записи `proof.context_result`/receipt → state: `status=WORK, pid=мёртвый, без proof`. Штатный ремонт: `recover --slug … --class dead-pid --reason '…foreground timeout до snapshot…' --evidence 'path=<канон>'` (rc=0) — выставляет фазу в `todo` и чистит pid; ЗАТЕМ снова переоткрыть фазу штатным writer'ом (`status='WORK'; awaiting_invoke=True`, стереть реквизиты) + свежий emit-prompt (новый packet_id) + один background-invoke той же ролью. Важно: после recover канон на диске уже есть и валиден — повторная роль читает его и не переписывает с нуля; полный reset receipts при этом не нужен.

**rc=3 `provider-fatal` (stream disconnected / refused / connection reset) — временный провайдерский сбой, НЕ диагноз кода и НЕ повод для rework плана.** Признак: фоновый invoke завершился rc=3, в journal событие `invoke_fatal reason=provider-fatal: rc=0 json error: Reconnecting.../connection reset`, результата на диске нет (artefact не написан, `proof.context_result` нет), pid записан мёртвым. Лечение — техническое восстановление по регламенту SKILL.md: `recover --class dead-pid --reason 'provider-fatal ... временный сбой' --evidence path=<канон>` → repair-writer'ом reopen фазы (`WORK/awaiting_invoke=True`, стереть `pid`/`receipt`) → свежий `emit-prompt` (новая packet_id) → ОДИН повторный background-invoke той же ролью. Не менять модель/бэкенд/лимиты, не писать диагноз архитектору на первый сбой этого класса; второй подряд такой же — стоп и диагноз.

**Не append-ить диагностические блоки к emitted-промпту после emit — это ломает G2 как правка файла-источника.** Когда архитектору нужен полный контекст (доп. диагноз), писать его в ОТДЕЛЬНЫЙ файл в workspace слага (ARCH-DIAG-*.md / NOTE), на который роли ссылаются; appending к `/tmp/task_*.md` после emit меняет sha/size/mtime и заставляет пере-емитить. Если дописал — штатного пути нет, только `emit-prompt` заново (пересоздаст чистый packet с согласованным sha). Не править промпт вручную после emit ни в какую сторону.

## Питфоллы

- **CAP-гейт требует авторитетных данных маршрута — исследование делает АРХИТЕКТОР, а НЕ оркестратор (Саша: «Оркестратор не занимался исследованиями», «Отдай эту задачу исследования архитектору. Пусть он сам найдет ответы на свои вопросы»).** Оркестратор не собирает authority сам (веб-поиск, чтение конфигов/кэшей, сборка capability-JSON — это исследование, оно уходит архитектору). Штатный ход: (1) `evidence/owner-directive-<дата>.md` — директива владельца: исследование CAP делает архитектор сам; запрещено paid-прогоны, установка библиотек, изменение model/effort/window/reserves, обход канона, выдумывание authority; (2) зарегистрировать директиву в handoff-contract `inputs` (HF-plan.md) с `phase: ORCH`; (3) repair-writer'ом переоткрыть фазу-владельца (HF:plan → WORK/awaiting_invoke=True) и сбросить downstream (REV:plan, HF:backup, HF:impl, HF:test, HF:docs-handoff, ORCH:shared-state) в todo — REV обязан согласовать новую ревизию заново; (4) свежий emit-prompt → ОДИН background-invoke. Если оркестратор УЖЕ собрал submission и архитектор отверг её (13+ структурных нарушений: refs строками, пустые массивы, недоказанный tokenizer binding, неверный route) — НЕ пересобирать JSON самому: сохранить отвергнутую в `evidence/<phase>/rejected-candidates/` и вернуть исследование архитектору с директивой. После исследования архитектор возвращает requirement-revision-request (ДВА пути + рекомендация, напр. Путь 1 — согласовать client capacity policy, Путь 2 — пересмотреть модельное представление consumer) — это решение владельца: поезд → `waiting_operator` (repair-writer: `st.status='waiting_operator'; st.phase='<фаза>'; st.pid=None`, фаза `status='waiting_operator'; awaiting_invoke=False`), REV вслепую НЕ запускать (Б55.5: третий круг без новых входов = нарушение). **Владелец вправе СНЯТЬ числовую часть допуска CAP одной нормативной директивой (вопрос к токенизатору/лимитам/native) — тогда не добывать факты, а вписать распоряжение в норму через TZ:patch.** Когда на развилке по числовым фактам владелец велит «считаем что tiktoken достаточен», «публичные лимиты провайдера верны и способ 90% верен без доп проверки», «native-маршрут проводить на default-модели Hermes в лоб, другие модели кроме default запрещены» — это закрывает CAP-TOKENIZER/CAP-NATIVE-ROUTE численно, но НЕ отменяет runtime-приёмку (реальная загрузка carrier в CLI, framing, route, positive witnesses до HF:impl остаются). Директиву оформить `evidence/<phase>-rN/owner-directive-<дата>.md`, зарегистрировать в handoff-contract `inputs` под `TZ:patch` (phase: ORCH) и провести по той же TZ-цепочке. Уточняющую директиву по тому же вопросу (поправка «90% вместо 75%») — дописать в ТОТ ЖЕ файл директивы (явная поправка перекрывает старое значение в заголовке/п.1) и пере-эмитить; источник владельца не редактировать.
- **Новая владельческая нормативная дельта, пришедшая ПОСЛЕ REV:tz APPROVE, но ДО TZ:finalize, — вернуть поезд на TZ:patch и провести снова (влить в норму → заново REV:tz → finalize), а НЕ финализировать как есть.** Когда дельта 90% уже прошла TZ:patch → REV:tz APPROVE, а владелец сразу добавляет вторую директиву (tokenizer/native), — TZ:finalize зафиксирует мастер без этой правки, если успеть: возврат поезда на TZ:patch (repair-writer'ом: фаза-владелец WORK/awaiting_invoke=True, сбросить REV:tz/TZ:finalize/HF:plan/... в todo), зарегистрировать директиву в inputs под `TZ:patch`, свежий emit → один invoke архитектора → снова REV:tz → TZ:finalize. Иначе мастер пойдёт в production с неполной нормой, а правка станет отдельным CHANGE.
**После выбора владельца («делаем по рекомендации архитектора» = Путь 1) пересмотр требования Б55.5 идёт через TZ:patch, а не HF:plan:** (1) `evidence/<phase>/owner-decision-<дата>.md` — выбор владельца: какой путь, что разрешено (напр. адресно согласовать client capacity policy), что НЕ меняется (модель/effort/backend/резервы), полное распоряжение; (2) зарегистрировать решение в handoff-contract `inputs` под `TZ:patch` (phase: ORCH); (3) repair-writer'ом переоткрыть `TZ:patch` (WORK/awaiting_invoke=True, стереть proof/context_packet/pid/receipt/...) и сбросить ВСЕ нижестоящие фазы в todo — не только REV:tz/TZ:finalize, но и GATE:take-into-work, HF:plan, REV:plan и далее (план будет пересобран под новый master; старые done-фазы не переносятся); (4) свежий emit-prompt → один background-invoke архитектора. **Патчами по handoff-contract-блокам (inputs/write_scope) следить за ВЛОЖЕННОСТЬЮ: fuzzy-patch может сломать отступы элемента (key сдвинут глубже/мельче соседей) или оставить дубль, и emit молча не возьмёт вход (контракт валиден YAML, но фаза-not-scoped).** После patch inputs блока ОБЯЗАТЕЛЬНО проверить: `grep -n '<file>' HF-plan.md` — ровно один элемент на правильном фаза-уровне (`  - path: …` с двумя пробелами + `    phase:`/`    purpose:` с четырьмя), соседние элементы не съехали; дубль или сдвинутый отступ убрать/выровнять до emit. Занявшее место правило проверки packet (`'<file>' in raw`) работает, но не ловит сломанную вложенность, когда фаза уже эмитится с другим (ошибочно оторванным) элементом.
**Inputs контракта ПОФАЗНЫЕ: запись под `TZ:patch` НЕ попадает в packet последующего `HF:plan` — решение/канон финализации, нужные архитектору при пересборке плана, регистрировать отдельно под `inputs: HF:plan` (phase: ORCH/TZ:finalize) и ЗАНОВО emit-prompt. После каждого emit проверять содержимое packet ДО invoke: grep'нуть target-имя файла в `/tmp/task_*.md` (`'owner-decision' in raw` и т.п.) — отсутствие = контракт не обновлён для этой фазы, править контракт и пере-емитить; invoke по неполному packet даёт роль без критичного входа и полный проход впустую.** Архитектор вносит дельту в master (новая версия draft), пишет канон DRAFT_WRITTEN со своими verify/rollback-операциями (напр. 11 обратимых операций + обратный diff) и именованным дефектом допуска (напр. MAIN_TZ_INVENTORY.md вне write_scope — синхронизировать при TZ:finalize по Б15), затем complete-phase → next → REV:tz заново. Пока владелец не выбрал путь — поезд остаётся waiting_operator. Штатный ход: (1) дописать new goal в `brief.md` (+ пометить секцией «Дополнение …»); (2) штатным writer'ом вернуть фазу — `read_state` → `st.phase='<PHASE>'; st.status='WORK'`, целевая фаза `status='doing'; awaiting_invoke=True`, стереть `artifact_ready`/`receipt`/`context_packet`/`pid`/`started_at`/`ended_at`, затем `write_state(event={'event':'repair','actor':'sirene',...})` (JSON-write напрямую запрещён; фазу писать через `python /tmp/x.py`, не heredoc — ложный gateway-guard); (3) свежий `emit-prompt` на той же фазе (новая packet_id, контракт из `brief.md` перечитан) → проверить `write_scope` в packet до invoke — покрывает ли каталог поезда/целевой файл; (4) повторный `invoke-role` той же ролью; после неё снова идёт REV, затем GATE:done. Это дешевле и честнее форка: артефакты/журнал/AC поезда сохраняются, ревизия закрывает именно дополнение. Проверять финал журналом, а не `status` (авто-гейт GATE:done в том же поезде).
- **После TZ:patch проверять G1 на следующей фазе — `tz version drift` при бампе версии master.** Когда архитектор вносит ТЗ в master (TZ:patch), `version:` в `DevWorkflow_TZ.md` меняется (напр. 0.9.6→0.9.7), а глобальные поля `st.tz_version`/`st.tz_mtime`/`st.tz_path` остаются на старом значении → `check`/`G1 fail: tz version drift` на следующей фазе (TZ:compress, REV:tz и т.д.). Это штатно при легальном бампе, не ручной правкой JSON: скриптом через `pipeline_state.write_state` перечитать `version:` из master (regex `^version:\s*([^\n]+)`), проставить `st.tz_version`, `st.tz_mtime=str(master.stat().st_mtime_ns)`, `st.tz_path=str(master)`, затем `write_state`. JSON-write напрямую запрещён — только штатный writer. После синка `G1` уходит; останется `G2: accepted context packet required`, что нормально до invoke.
- **`--role` в invoke-role обязан совпадать с `_role(phase)` из pipeline_gates — G6 fail-fast, не изобретать имя роли.** Для TZ:patch/HF:patch/RS:* роль — `architect`, для TZ:compress/HF:compress — `compressor`, для REV:* — `reviewer`. Не выводить роль из имени фазы, а проверить `python3 -c "from pipeline import pipeline_context; print(pipeline_context._role('<PHASE>'))"` перед invoke.
- **После TZ:patch бамп master’а → следующий emit падает `G1: extract version drift`; лечится `refresh_producer`, но только при «accepted master output».** Когда в TZ:patch версия master изменилась (0.9.7→0.10.0), extract от прежней версии невалиден: emit следующей фазы (REV:tz…) падает `G1: extract version drift`, а `next` возвращает `G1: external master or compressor prompt drift; no accepted refresh basis`. refresh_producer открывает TZ:compress заново под новый master ТОЛЬКО если есть done-фаза, в `proof.context_result.outputs` которой записан ref текущего master (сравнение `result['outputs'][str(master)]==на_диске`). Этого ref нет, если контракт (handoff-contract в brief) объявил для TZ:patch только `TZ-patch.md` и НЕ объявил master как output (`kind: master`) — прецедент-прецедент uprost объявлял `- path: DevWorkflow_TZ.md kind: master`. Штатный ремонт (не JSON-write): положить `proof.context_result.outputs[str(master)]` полным `pipeline_context._ref(master)` (ключи: path, resolved_path, sha256, size_bytes, mtime_ns — неполный ref с пропущенным resolved_path НЕ проходит сравнение) через `write_state(event={'event':'repair',...})`, затем `next` вернёт `{action: WORK, phase: TZ:compress}` и свежий extract строится под новый master. `cat > /tmp/x.py <<'PYEOF' ... PYEOF` в одной terminal-команде триггерит ложный gateway-guard (`command cannot restart/stop/uninstall the gateway`) и блокируется, хотя содержимое безвредно. Ложная блокировка съедает ход. `write_file` в `/tmp/*.py` + отдельный `python /tmp/x.py` проходит и делает скрипт перезапускаемым (`&&`-цепочкой). Относится к maintenance-скриптам синхронизации/repair state, не к invoke.

Затем TZ:patch — write_scope уже включает `Registries/pipeline/` и сам master; ревизия ТЗ идёт фазой `REV:tz` (роль reviewer, output `REV-tz.md`), после синка версии master.

Презюмировать codex `gpt-6.1-terra`, не угадывать deepseek/hermes-internal. Диагностика ДО повторного invoke: `extract_production` в `proof` пуст после rc=0 codex-прогона → это кодекс-путь не публикует extract (нужно публиковать через native `publish_validated_extract`, но он требует креды); если креды не заданы — не делать слепой 3-й invoke с другой моделью, а предъявить Саше факт «компрессор требует креды native-пути» как развилку, не угадывая backend прогонами.
- **`TZ:compress`/`HF:compress` записываются в `write_scope` контракта §10 ОБЯЗАТЕЛЬНО, иначе emit-пакет уходит с пустым `boundaries.write_scope` → роль rc=4 `output outside write_scope: …/extract.md`.** Действует и при старте НОВОГО поезда (свежий init CHANGE/SKILL-CHANGE), и у refresh-producer фазы (открытой `next` под новый master после G1). Правило при написании handoff-contract в brief сразу: перечислять в `write_scope`/`outputs` ВСЕ фазы рецепта — включая первые оркестраторские и компрессорные (`TZ:stabilize` оркестратор не пишет, но `TZ:compress` пишет `extract.md`) — а не только планируемые ролевые (`TZ:patch`/`REV:tz`). Иначе первая же emit-фаза после stabilize (TZ:compress) уходит с пустым write_scope и падает rc=4 до вызова модели, хотя extract.md — required output роли. Фикс — добавить фазу в `write_scope` + `outputs` контракта (workspace поезда), штатный `recover --class dead-pid` (процесс уже умер), свежий emit, повторный invoke. Полный reset с удалением `extract_refresh` теряет basis и возвращает G1 на следующем next (для refresh-фазы); для свежего поезда reset не требуется — recover + re-emit достаточно.
- **`complete-phase` требует И `--reason`, И `--evidence`; отсутствие `--reason` даёт ТИХИЙ rc=2 без stderr.** Голый текст-причину (`auto=true verdict=accepted`) complete не принимает даже на AUTO_GATE — всегда давать путь реального артефакта (REV-tz.md, AC-list.md, TZ-finalize.md) с настоящим sha256, а `--reason` с содержательной причиной. Проверять фактический финал журналом (`tail journal.md` — есть `complete phase=`), а не пустым stdout. Тихое rc=2 без stderr чаще всего = пустой `--reason`, а не отказ приёмки: сперва дополнить оба аргумента, не убегать в reset/re-invoke.
- **Завершать pipeline CLI в пайпе на head — RC маскируется.** `$?` после пайпа — это код обрезчика вывода (всегда 0), а не CLI: failed complete-phase (`exit 1`) выглядит зелёным, и фаза остаётся в `doing`/`todo` без записи в journal. Брать код ДО пайпа (`cmd; RC=$?` без обрезки) или читать journal/состояние фаз, а не echo после pipes. Особенно коварно на `complete-phase` и `check`: их ошибки пишутся в stderr и теряются в пайпе, если не проверять состояние по-настоящему.
- **`GATE:take-into-work` — закрывать ТОЛЬКО с канонным evidence `AC-shown origin_thread=… file=AC-list.md`, а AC-list.md сделать непустым ДО закрытия.** Иначе: (1) гейт закроется с чужим evidence (напр. REV-tz.md) — нарушение мастера Б18.4 п.6 и HF:plan потом падает `required input missing: …/AC-list.md`; (2) пришлось возвращать гейт в `todo` штатным writer (`write_state(event={'event':'repair',…})` — JSON-write напрямую запрещён) и закрывать заново. Штатный ход: скопировать список `AC-COMP-01…12`/`AC-###` из диагноза/ТЗ в `dev/<slug>/AC-list.md`, показать в origin (класс S, ждать не нужно), затем близнец-гейт с evidence `AC-shown …`. Выпуклый признак правильности: emit-prompt HF:plan проходит — он требует AC-list.md вход. **`next`, вернувший `{"action": "AUTO_GATE", "phase": "GATE:…"}` — это ПРИКАЗ оркестратору самому закрыть гейт через `complete-phase` (роль гейта = sirene, invoke не нужен), а НЕ сигнал звать `next` повторно: повторный `next` вернёт тот же AUTO_GATE. `can_complete` на AUTO_GATE принимает и evidence `path=<master> version=<ver> mtime=<…>` при уже зарегистрированном в контракте AC-list.md (AC-list вход из контракта достаточен); evidence формы `AC-shown …` обязателен, когда AC-list.md ещё не в контракте.**
- **TZ:finalize: если write_scope не включает MAIN_TZ_INVENTORY.md, роль готовит inventory-proposal, а применяет патч ОРКЕСТРАТОР.** Знакомый класс №1 (fence-contract): при отсутствии inventory в write_scope архитектор не пишет реестр, а оставляет `evidence/TZ-finalize/inventory.proposed.diff` + `inventory-proposal.json` со `status=PROPOSAL_ONLY_NOT_APPLIED`, `changed_line_numbers` и `proposed_content_sha256`. Оркестратор применяет две строки (новый префикс в `updated:` + строка таблицы инструмента: версия/дата/approved/краткое Б60-описание) и **сверяет фактический sha256 файла с proposal** — совпадение подтверждает точность, расхождение = править вручную нельзя. Затем complete-phase с `inventory_sha256=` в evidence.
- **`_state.json.updated` — не дата завершения.** Это дата пачковой агрегации/последнего repair (`2026-11-03` у десятков поездов), не фактическое завершение работы. Отвечая «когда завершили X», брать даты из `journal.md` — события `complete` с timestamp на каждую фазу; `status:done` в _state.json лишь подтверждает что поезд закрыт, а не что он закрыт именно в `updated`. Искать `complete ... phase=<target>` и финальный `GATE:done` в xml-журнале поезда.
- **HF:test prep smoke: rc=4 stderr «пиши в extract.md, канон не обновлён» и rc=124 (timeout) — две РАЗНЫЕ диагностики, обе решаются вне кода роли.** (1) rc=4 с этим stderr = native child не публикует extract (fixture/process-boundary): в native.jsonl только import rows, нет worker-enter/worker-reply/sdk-constructor/send/publisher; лечится передачей проверенного candidate PYTHONPATH/HERMES_AGENT_ROOT в child, фиксацией worker-enter/reply и единственного send/publisher в offline fixture. Missing worker-enter или пустой reply — FAIL, не «empty result PASS»; negative H-ветки (pre-SDK/provider-publisher отказы) остаются FAIL-oracle, их не «позеленивать». (2) rc=124 на bounded context/full = per-node timeout харнеса (обычно 5–10 s на node): лечится явными параметрами `--per-node-timeout 60 --total-timeout 3600`, НЕ сокращением collection и НЕ ослаблением verifier; PASS только при executed==collected, duplicate==[], missing==[], remaining==[], rc=0 у каждого node, без timeout. Prep пишет PREPARED только при полном smoke+targeted+bounded PASS; при любом K2/K3 FAIL — честный FAIL, ORCH loader/P1–P5 и reader не запускаются (история: rev13→rev15 крутилась на этих двух сигналах).
- **K3 bounded: когда полный collection (сотни nodeid, напр. context 177 + full 437) НЕ влезает в один прогон даже с `--per-node-timeout 60 --total-timeout 3600` (interrupted rc=130/SIGINT на ~87 узлах, счёт теряется) — решение НЕ raise timeout до «пока влезет», а детерминированный ПАРАЛЛЕЛЬНЫЙ scheduler.** Фиксируется collect-only inventory ДО dispatch; максимум N=8 изолированных worker-процессов, каждому nodeid своя process-group и собственный временный test root; nodeid выдаётся ровно один раз в порядке collection; rows после завершения нормируются обратно в порядок collection. Запуск `--workers 8 --per-node-timeout 180 --total-timeout 3600`. Признак правильного сигнала: scheduler живёт в `run_bounded_regression` (fixture-helпер), не пишет state/journal/queue, не resume/backfill, не global mutex. PASS по-прежнему только при executed==collected, без dup/miss/remaining, active==null, rc=0 каждого node и без timeout. Scheduler сам оркестратор не пишет — executor его вносит как один адресный commit (иного слова нет). Если foreground-роль обрывается на bounded (420с терминал) — recover dead-pid + reopen + повторный ФОНОВЫЙ prep, чтобы полный пул уложился в окно.
- **Structural verifier could refuse fixture-emitted packets: legacy `emit_packet` helper writes `inputs: {}`, но verifier rev11+ требует явных ключей `inputs[<phase>]` для вызываемой фазы (`scope contract: missing inputs[RS:collect]`).** Все component-fails, выстрелившие в legacy-тестах occupancy/recovery/phase-turns, закончились в `conftest.py` fixture-контракте, где `inputs` пустой объект, а не перечислены фаза→canonical-пути. Verifier корректно отказывает (fail-closed), не коэрсит в `[]`. Фикс — не ослаблять verifier, а научить fixture писать `inputs: {<phase>: [{kind:"canonical", path:…, required:true}]}` (или контракт с правильными inputs). При диагностике 10+ детерминированных component-fails первым делом смотреть `conftest.py`/fixture-хелперы (что они кладут в `inputs`/`outputs`/`write_scope`) ДО регресса, а не гонять роль.

## Разбор «что сломалось / какой релиз вернуть» (release forensics)

Класс задач: Саша спрашивает, какая доработка после принятой базы сломала dev-workflow и на какой рабочий релиз откатиться (RESEARCH через архитектора **или** прямой разбор). Отвечать только по факту установленного кода, а не по номерам требований.

1. **Релиз — это СВЯЗКА `(скилл + pipeline)`, а не `SKILL.md`.** Рабочий pipeline лежит отдельно от git и не содержит README-версии скилла. Указание точки отката обязано назвать ОБА источника: коммит `hermes-workspace@<skill>` и hash/коммит pipeline (из `candidate/` пакета или `rollout.json`), иначе откат одного файла не вернёт рабочую базу. Расхождения разрешать по `sha256sum` сохранённого `evidence/rollout.json`, а не по доверию рабочему каталогу. [b91/0.8]
2. **Зелёный изолированный тест ≠ готовность live.** Ранняя приёмка со `stub=true`, `live_provider=false`, `production_runtime=NOT_RUN` доказывает протокол, а не реального провайдера/настройки. Дефект готовности (нет секретов провайдера, не тот backend, неполная интеграция нового пути) проявляется следущим заданием. Помечать «работает в production до X» как не подкреплённое таким smoke.
3. **Дефект, живший в принятой базе, НЕ вносится более поздним ремонтом.** Конкретную ошибку (напр. бинарный файл читается как UTF-8) прежде обвиняет последующий номер, проверить по `git log -S` / `git show` — когда этот код реально появился. Приписывать поломку «установленному релизу Б">Б58/Б59» неверно, если полные реализации живут только в `candidate/` и в runtime не переносились.
4. **Искать реальную регрессию между базами (`goto diff`), а не номер.** Частый корень — неполная интеграция нового пути: у старого адаптера была связка результат→publication, новый backend пишет файлы, но publication/identity остаётся у прежнего вызова, завершение отказывает по несовпадению identity. Сверять журнал конкретной фазы (`canonical_artifact_fail`, `invoke_prepare backend=…`) и diff принятой базы ↔ runtime.
5. **«Три дня зависаний» почти всегда наложение разных отказов** (timeout, настройки, дефект приёмки, drift плана) — каждому свой регламент; не сводить к одному номеру/модели и не обещать, что откат файлов «сам всё починит». Незавершённый результат repair откат не принимает (result/receipt не дорисовываются) — для рабочего блока нужен завершённый ремонт механизма приёмки.
6. **«До X» ≠ «просто без X»: разложить дифф на отдельные требования.** «До Б56» неявно возвращает и состояние до-Б55 — откат тянет ВСЕ изменения между базой и настоящим, а не только названную фичу/формат. Номер версии не идентифицирует наличие фичи: один и тот же номер (0.8.1) существует и до, и после установки Б56. Точку отката указывать точными коммитами скилла + pipeline, не номером версии и не «до фичи N».
7. **Проверить, существовала ли нужная способность в старой базе.** Если у старого варианта компрессор — заглушка (resolver ведёт в `hermes-internal`, функция возвращает rc=2 без вызова модели), откат убирает вызывающий путь, а не чинит его; «уже тот же native без настроек» — неверно. Ремонт отсутствующей способности, как и отсутствующего сервиса/секрета, откатом версии не делается.
8. **Прежние предпосылки пересматривать архивной уликой.** Если ранее утверждалось «дефект X уже был в базе A», а проверенные архивы A дефекта не содержат — вердикт обязан явно поправить старый тезис, а не повторять его. Сравнение баз вести по сохранённым копиям/`git show`, а не по памяти о предыдущих выводах.

- **`--evidence` sha256 — только реальный хеш артефакта, и ОДНИМ вызовом.** Никогда не вписывать в `--evidence` плейсхолдер (`sha256=____REAL____`), вручную набранный или «вспомненный» дайджест: журнал хранит evidence дословно и вручную не правится, а выдуманный хеш превращается в неразрешимую аномалию при сверке. Инжектить реальный хеш прямо в команду complete без ручного переноса значения:
  ```bash
  H=$(sha256sum /abs/RS-analyze.md | cut -d' ' -f1)
  pipeline complete-phase --slug <slug> --phase RS:analyze \
    --evidence "path=/abs/RS-analyze.md sha256=$H"
  ```

Правильное лечение по вердикту архитектора — **no-code re-entry**: исполнитель не меняет candidate source и не делает новый коммит, а заново верифицирует уже существующую работу по git-oracle (`git rev-parse HEAD` == зафиксированный candidate commit, `merge-base baseline..HEAD` == baseline, `diff --name-status baseline..HEAD` == точный allowlist, clean index, `diff --check` rc=0, SHA candidate-файлов == backup) и переписывает только канонический evidence + новый `evidence/<phase>-reconcile.json`, начинающийся с маркера `no-code-change:`.
- **Диагностировать ДО dead-pid reset: канон на диске + `context_result`/receipt уже в state = НЕ dead-pid, а `rc0-no-complete`; закрывается обычным `complete-phase`, повторный invoke запрещён (Б16.6/AC-078).** Факты (проверены read-only разбором): `invoke-role` не обязан печатать stdout — пустой stdout допустим и не равен отказу; запись `context_result`/receipt и `complete-phase` — РАЗНЫЕ, отдельные операции; `dead-pid` — только когда пригодного post-invoke результата вообще нет (нет role/canon/context_result и wrapper мёртв). Поэтому перед reset+re-invoke смотреть `_state.json` фазы: если `proof.context_result`, `receipt` и `role` присутствуют, а `complete` просто не записан — шаг только один: штатный `complete-phase` с реальным sha256 артефакта. Сброс receipts и повторный invoke в этой ситуации теряют уже принятый результат и лишний раз жгут роль.
