# План реализации и тестирования единого конвейера MPP → архив / Confluence

План реализует согласованное ТЗ без изменения требований. Порядок строго последовательный: **исправление ложного успеха → архивное ядро → batch и базовая история → идентичность и публикация → доказательное сравнение → интеграция скилла → комплексная приёмка**. Переход к следующему этапу разрешён только после выполнения gate предыдущего.

Основание: согласованное ТЗ от 16.11.2026, исходный план `/tmp/arch_plan_full.md`, master EditPlanConfluence v0.4.0, правила хранения `devops/tz-workflow` и `devops/dev-workflow/references/storage-and-archival.md`, реестры экосистемы и существующие компоненты. Исходный план прочитан целиком; при правке сверены структура, конфигурационные контракты и пересечения с §19 мастера. Код реализации, миграции и функциональная приёмка этой правкой не выполняются.

**Редакция плана: 16.11.2026.** Канонический файл: `/home/tkachenkoav/WorkVault/Hermes-Backlog/TZ/EditPlanConfluence/plans/HF-plan_EditPlanConfluence_20261116.md`. План описывает будущие изменения; перенос ТЗ в master, изменение inventory и конфигурации — работы этапа 1 и следующих этапов, а не уже выполненные факты.

## 1. Правила исполнения и обозначения

### 1.1. Обязательные правила

1. Исполнение этого пакета — вручную через Codex exec, без запуска неработающего dev-пайплайна, согласно согласованному ТЗ и текущему поручению Саши. Правила хранения, версионирования, reuse-first и коммитов dev-workflow обязательны. Это исключение не вводит альтернативный диспетчер, очередь или правила запуска других задач.
2. Следующий этап не начинается, пока предыдущий не реализован, не протестирован, не имеет долговечного отчёта с выполненным gate и завершающего коммита в `~/hermes-workspace`. Условия коммита и сохранения внешних изменений — §1.6.6.
3. Исправление обнаруженного дефекта относится к этапу, которому принадлежит нарушенный контракт. После исправления повторяются затронутые проверки и необходимые зависимые проверки.
4. Тесты используют отдельные БД, WorkVault, cache и копии входных файлов.
5. Производственные страницы A–D и AB не используются как цели приёмочной записи.
6. Gateway не изменяется и не перезапускается. Кроны, наблюдатели Inbox и расписания не создаются.
7. Существующие миграции не редактируются. Новые миграции добавляются последовательно.
8. Все изменения plan-схемы выполняются через typed writer/query API MofsIndex. SQL внутри реализации этого API допустим; обход API из скилла запрещён.
9. Ни совпадение UID, ни общая lineage, ни идентификация файла A не считаются подтверждением идентичности задач между разными MPP.
10. Успешное архивирование и подтверждённое сохранение страницы не означают `schedule:verified`.
11. Один публичный CLI — `S/scripts/cli.py`. Внутренние модули не получают самостоятельных CLI, сервисов, конфигурационных хранилищ или регистраций инструмента.
12. Новая сущность вне утверждённого расширения существующих компонентов требует маркера **[NEW-ENTITY, требует согласования Саши]** и конкретного согласования до проектирования/создания. Отсутствие ответа не является согласованием.
13. Архив, история и результаты запросов остаются в MofsIndex и существующем файловом архиве WorkVault; собственная БД скилла, дублирующий реестр проектов и новый `kind=plan` не создаются.

После failed финальной приёмки выполняются корректирующие итерации этапов — владельцев нарушенных контрактов. Первоначальные отчёты и коммиты сохраняются. Каждая итерация имеет отдельный отчёт и commit; затем выполняется новый полный прогон этапа 13.

### 1.3. Общий тестовый контур

Переиспользовать **pytest** и существующие `S/tests/conftest.py`, `S/tests/pytest.ini`, тестовые контуры MppReader/MofsIndex. Отдельные `run_acceptance.py` и `acceptance/build_report.py` не создавать. Изоляцию, фиксацию результатов и построение отчёта реализовать pytest fixtures/hooks существующего `conftest.py`; это тестовая поддержка компонента, без самостоятельного инструмента.

На этапе 1 добавить тестовые опции `--acceptance-stage`, `--test-root`, регистрацию групп `unit`, `archive_integration`, `mpp_fixtures`, `confluence_live`. Опции принадлежат pytest, не продуктовому CLI. Для каждой стадии явная карта test ID определяет обязательный набор и допустимые группы; маркер не заменяет проверку полноты набора. Старые тесты также классифицировать, чтобы они не выпали из регрессии.

Пример целевого вызова после этапа 1:

```bash
"$PY" -m pytest -c "$S/tests/pytest.ini" "$S/tests" \
  --acceptance-stage 01 --test-root "$T/stage-01" \
  -m "unit or archive_integration" \
  --junitxml="$T/stage-01/reports/junit.xml"
```

Обязательства тестового контура:

- создавать изолированные `state/index.sqlite`, `WorkVault`, `cache`, `fixtures`, `reports`;
- отклонять production-пути, включая совпадения после разрешения symlink;
- передавать продуктовым вызовам глобальные `--db`, `--workvault`, `--cache-dir` перед подкомандой;
- запускать тесты трёх компонентов отдельными последовательными процессами pytest; не собирать конфликтующие `conftest.py` в одном процессе;
- сохранять команды, exit codes, stdout/stderr, JUnit и версии окружения;
- запрещать сеть в `unit`, создание `ConfluenceClient` в архивных сценариях;
- различать обязательный непройденный тест и необязательный пропуск;
- не считать нулевое число собранных тестов успехом;
- выполнять группы последовательно; live запускать только для перечисленных тестовых страниц.

Команды в этапах показывают основной прогон S. Для перечисленных в этапе тестов R/M дополнительно выполнять самостоятельный `python -m pytest` из соответствующего корня, с отдельным JUnit и изолирующими fixtures; их команды/rc входят в тот же отчёт и gate. На этапе 13 — вся относящаяся к пакету регрессия всех трёх компонентов. Новый runner для объединения запусков не нужен.

Пути `PY` и выбранного Python с MPXJ фиксируются в отчёте. Интерпретатор MPXJ выбирается централизованно и проверяется фактическим запуском reader, а не только наличием бинарника. Изменение старых CSV/GS-потребителей не допускается.

До появления глобальных CLI-параметров на этапе 4 существующие функции тестируются через явные зависимости и изолирующие fixtures.

### 1.4. Отчёт каждого этапа

Каждый этап создаёт:

```text
T/stage-NN/reports/stage-report.json
T/stage-NN/reports/stage-report.md
T/stage-NN/reports/junit.xml
```

Отчёт содержит:

- версию исходного ТЗ и его SHA-256;
- изменённые файлы и версии кода;
- применённые миграции;
- команды и окружение;
- тесты и покрываемые требования;
- результаты, ограничения и ссылки на артефакты;
- счётчики MPXJ-read, cache hit/miss, POST/PUT;
- решение по gate: `passed` или `failed`.

Промежуточное покрытие части AC не означает окончательное прохождение всего AC. Перед закрытием этапа очищенные от секретов отчёты и необходимые evidence сохраняются в `D/stage-NN/`; cache не является их единственным хранилищем. Отчёт содержит hash проверенного дерева исходников и конфигурационного контракта. Завершающий commit связывает код и отчёт; его SHA записывается после коммита в журнал исполнения канонического плана, без попытки включить SHA коммита в него самого.

#### 1.6.6. Завершающий git-коммит каждого этапа

**Наблюдение:** `H` — git-репозиторий; `R` и `M` на момент сверки находятся вне git. Обычный `git add` в `H` не сохраняет изменения `~/USERTOOLS`. Нельзя считать их защищёнными одним коммитом скилла.

Обязательный порядок для каждого этапа:

1. Сохранить исходное состояние затрагиваемых файлов и проверить чужие незакоммиченные правки; включать в commit только пакет этапа.
2. В `H` коммитить изменённые `skills/...` (код, docs, tests, profiles, fixtures) и `D/stage-NN/` (отчёты/evidence).
3. Для каждого изменённого внешнего компонента `R`/`M` сохранить **в том же коммите** воспроизводимый комплект: `D/stage-NN/usertools/<Tool>/before/`, `after/`, `changes.patch`, `manifest.json`. Только затронутые исходники/тесты/docs; manifest содержит абсолютный целевой путь, before/after SHA-256, удаления/создания, режим файла и основание. `after/` содержит полные новые версии, поэтому сохранение не зависит от доступности прежнего файла. БД, credentials, venv, cache и runtime-архивы в комплект не включать.
4. Это версионные доказательства поставки существующих USERTOOLS, не второй исполняемый пакет и не новый deployment tool. Runtime продолжает использовать R/M; импорты из `D` запрещены. Восстановление выполняется штатными git/patch/copy с проверкой hashes, без нового скрипта. Перед gate проверить восстановление в отдельном временном дереве и совпадение `after` с рабочими файлами.
5. Обновления master/плана/inventory остаются в WorkVault; в коммите — их пути/hashes и краткий результат проверки. Несекретные изменения конфигурационных контрактов — по §1.6.3. Не выдавать наличие файла за факт завершённого ownCloud sync: если синхронизация ещё не подтверждена, указать это отдельно.
6. После успешных проверок создать commit `edit-plan-confluence: stage NN <содержание>`. Зафиксировать SHA в журнале исполнения этого плана; следующий этап разрешён только при отчёте PASS и существующем commit. Если код не менялся, коммит содержит реальные отчёты/docs, не пустую фиктивную запись.

Перенос всего USERTOOLS в git, новые репозитории/submodules и symlink-миграция не входят в пакет. Фиксация stage-комплектов обеспечивает требуемую сохранность без такой миграции. Любые дальнейшие изменения файлов после проверенного коммита требуют нового commit и относящейся к ним проверки.

6. Не использовать отправленный в PUT текст как свидетельство read-back.
7. Исправить аналогичные обходы проверки в дочерней ветке.
