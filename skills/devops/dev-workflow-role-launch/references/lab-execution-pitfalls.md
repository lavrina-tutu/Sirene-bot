# Лабораторные прогоны ролей: узкие шаги, честный negative, подписанные receipt

Применимо к точечным invoke ролей (архитектор/ревизор/исполнитель) для lab-задач поезда
DevWorkflow: реализация плагинов, proof-эксперименты (ENV-03/04/05), матрицы проб.

## Узкие шаги вместо одного широкого промпта

Codex-исполнитель на многосоставном lab-промпте (реализовать плагины + прогнать матрицу +
ordinary) склонен вернуть частичный отчёт: source-audit, setup, примитивы — а основную
работу оставить NOT_RUN. Это не разовый сбой, а воспроизводимый паттерн (повторялся трижды
за сессию: B2 дважды, ErrorBus дважды).

- Разбивать lab на узкие шаги с явной границей в каждом: «только X, НЕ гоняй Y».
- Требовать конкретные артефакты: реализованный код, таблица проб (ID → oracle → факт →
  PASS/FAIL/NOT_RUN), hashes, evidence-файлы. Описание готовности результатом не является.
- Частичный прогон с NOT_RUN не принимается как результат шага: возвращать суженным
  промптом на ту же lab-директорию, а не заново с тем же объёмом.
- Отрицательный результат по критериям проекта (negative-B2, NOT_PROVEN) — валидный гейт,
  а не незавершённость. Стоп-критерий проекта (например, недоказуемая identity на
  публичном API) останавливает дальнейшее расширение матрицы. Не заставлять исполнителя
  «дойти до конца» после стоп-критерия.

## Развилка после negative

Зафиксировать negative честно (не переименовывать в PASS), вынести развилку архитектору с
полным контекстом, владельцу — варианты с рекомендацией. Пример: negative-B2 → развилка
B3 (ручное возобновление, правка нормы) vs B1 (доработка ядра) → выбор владельца →
архитектор сам вносит адресную дельту нормы по своей же таблице → независимая REV.

## bwrap-изоляция

- Python 3.14: `os.urandom` падает EACCES на nodev-bind — добавлять
  `--dev-bind /dev/urandom /dev/urandom`; без него случайные байты недоступны и setup
  срывается. Не считать это результатом эксперимента.
- Контур: `--unshare-all --die-with-parent --ro-bind / /`, отдельный tmpfs `/tmp`,
  закрытый production `.hermes`, новый `/proc`, `env -i`, `PYTHONDONTWRITEBYTECODE=1`.
- Fake sender loopback вместо реального Telegram/:11112; журнал fake-принятия читает
  только проверяющий, не recovery adapter.

## Подписанные receipt (HMAC): защита от отката

- HMAC защищает содержимое от подмены, но НЕ отличает старую корректно подписанную версию
  от новой. Совместный откат witness на прежнюю версию + удаление поздних receipt выглядит
  как пустая история и допускает повторную отправку — это FAIL, а не «редкий край».
- Доверие к полю author бесполезно: публичный API комментариев канбана принимает
  произвольного автора. Подлинность — только через подписанный протокол и защищённый
  signer/reader, не через author.
- Для durable подтверждений нужен независимый rollback-resistant anchor: атомарная
  монотонная версия + hash head witness вне откатываемого дерева, сохраняющий состояние
  между restart. Перед send reader сверяет head и fail-closed при отсутствии/отказе/
  неоднозначном commit. HMAC-файл в том же откатываемом дереве сам по себе защиту от
  совместного отката не доказывает.
- Различать «нет ключа» / «ключ повреждён» / «ключ ок, но записи чужие»: порча доверенного
  ключа → AUTHENTICITY_NOT_PROVEN + send=0 + состояние обязательства uncertain (не «нет
  обязательства»).
- Порядок чтения переходов — по comment ID (`list_comments_after`), не по времени
  (`list_comments()` сортирует по времени).
- Дедупликация: повторное чтение внутри `write_txn()` + `add_comment` в одной транзакции;
  per-event guard; отправка после commit и освобождения dispatch lock. Один ключ = один send;
  send→crash честно даёт uncertain с пометкой duplicate_possible, не exactly-once.
