## Модуль D. Обновление проектов (✅ закрыт бриф, 2026-06-18)

### Три выходных продукта системы

Система AggregateFromMeetings + StatusSnapshot совместно производят три продукта:

| Продукт | Аудитория | Где | Отвечает | MVP | Фаза 2 |
|---|---|---|---|---|---|
| P1: PM Dashboard (Warnings) | только PM | StatusSnapshot (Obsidian) | StatusSnapshot | ✅ авто | — |
| P2: Meeting Minutes (протокол) | команда + заказчик | Snapshot → Obsidian → Confluence | StatusSnapshot → PM | ✅ PM вручную | автоматизация |
| P3: Project Status (история) | PM + начальство (1-1) | D-артефакты (Obsidian) | Модуль D | ✅ авто | автопубликация в Confluence |

**Важно:** StatusSnapshot — PM-артефакт, содержит Warnings. Публичная часть для Meeting Minutes — только выбранные секции без Warnings.

Еженедельные 1-1 с начальством: PM открывает D-артефакты в Obsidian и зачитывает статус по каждому проекту поочерёдно.

### D vs StatusSnapshot

| | Модуль D | StatusSnapshot |
|---|---|---|
| Все встречи за историю | ✅ | ❌ |
| Одна свежая встреча | ❌ | ✅ |
| decisions.md (накопленный) | ✅ | ❌ |
| action_items.md (накопленный) | ✅ | ❌ |
| risks.md / blockers.md | ✅ | ❌ |
| Подсветка изменений | ❌ | ✅ |
| PM Warnings | ❌ | ✅ |
| Сравнение с планом (card.md) | ❌ | ✅ |
| Читается PM за 30 сек | ❌ | ✅ |
| Читается машиной | ✅ | ❌ |

**Метафора:** D = база данных проекта. Snapshot = дашборд после встречи.

### Решения брифа D (2026-06-18)

| Вопрос | Решение |
|---|---|
| В1 — Граница snapshots/ | StatusSnapshot генерирует. D пишет только D-артефакты (`ai/decisions.md`, `ai/action_items.md`, `ai/timeline.md`). |
| В2 — Резолв противоречий | Новое решение добавляется строкой. Старое зачёркивается `~~текст~~` с пометкой «пересмотрено [дата]». PM опровергает через `<!-- pm: -->`. |
| В3 — Closure action_items | Система не закрывает автоматически. Сигнал «выполнено» → помечает `[?]` «похоже выполнено [дата]». PM подтверждает/опровергает через `<!-- pm: #N закрыто -->`. |
| В3а — Нумерация | **Сквозная нумерация задач по проекту `#N`** — глобальный номер, не по встрече. PM ссылается на `#N` в заметках. |
| В4 — pm_locked | **Убрано из scope MVP.** D работает append-only, конфликтов нет. Пересмотреть при реальных проблемах в Фазе 2. |
| В5 — _uncategorized/ | D складывает сигналы в `Projects/_uncategorized/action_items.md`. Модуль F отправляет разовое ежедневное TG-уведомление со списком + Obsidian-ссылками. Пересмотреть в Фазе 2/3. |
| В6 — Health/stale | Не в scope D. D пишет `last_active` в card.md — StatusSnapshot/F делают вывод сами. |

### Архитектура D

```
MeetingSignals от C
      ↓
      D (append-only)
      ├── Projects/<slug>/ai/decisions.md   (редко, зачёркивание при противоречии)
      ├── Projects/<slug>/ai/action_items.md (часто, сквозная нумерация #N)
      ├── Projects/<slug>/ai/timeline.md    (append)
      └── Projects/<slug>/card.md           (только служебные поля)
```

**Bootstrap vs Инкремент:**
- Bootstrap: обработка всех ~940 встреч. Шаг 1 (Haiku) размечает, Шаг 2 (Opus) агрегирует → D записывает.
- Инкремент: одна новая встреча. D дополняет существующие файлы, не перезаписывает.

## Ключевые принципы архитектуры

1. **MeetingPackage** — читаем файлы один раз в A, все остальные работают с объектом
2. **Заголовок — подсказка, не источник истины** — одна встреча может касаться нескольких проектов
3. **Встреча без проекта** → не мусор, это 1-1 → модуль E
4. **«Мусор на входе → мусор в Warnings»** — context.md и допущения должны быть точными и ёмкими
5. **C не пишет файлы** — только возвращает JSON. D пишет.
6. **Bootstrap vs инкремент** — при первом прогоне D и C шаг 2 почти совмещены; при инкременте нужна логика D (append-only, дедупликация)
7. **pm_locked убран из scope** — append-only архитектура D делает его избыточным
8. **Сквозная нумерация #N** — все action_items проекта нумеруются глобально; PM ссылается через `<!-- pm: #N ... -->`
9. **Три продукта (P1/P2/P3)** — система производит три разных артефакта для разных аудиторий; не путать D (P3) со StatusSnapshot (P1/P2)
