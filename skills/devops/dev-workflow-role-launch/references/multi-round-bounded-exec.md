# Многораундовый bounded-прогон большой части (direct-mode, execute roles)

Класс: крупный материальный контракт части (напр. документный перенос по-строчной таблицы source→target в N файлов), который исполнитель честно не закрывает за один инвок. Терра-исполнитель оставляет OPEN, когда не имеет текста самих span'ов и не ставит OK для непроверенного содержания — это свойство, не дефект.

## Когда НЕ повторять тот же прогон
- Исполнитель вернул честный REPORT остатком (больше файлов, чем влезает в раунд) — НЕ гнать тот же промпт с большим effort/выводом: это бесконечный цикл и сожжённый контекст на перечитывание гигантских входов задом наперёд.
- Применить правило архитектора «если часть не закрывается — пересмотреть её конкретный контракт, а не повторять общий scope» к САМОМУ запуску: резать контракт на под-батчи.

## Процедура под-батчинга
1. Разделить контракт по целевым файлам (или по общим изменяемым путям), каждый = отдельный раунд.
2. В рецепте каждого раунда указать РОВНО адресуемые ID строк/файлов + целевой раздел + где брать текст — чтобы роль не перечитывала PREP/таблицы целиком.
3. Дать роль источник текста явно (файл + диапазон строк, напр. `sed -n '73,113p' <src>`) — не только адреса span. Нет источника → роль правдиво отказывается ставить OK: input отсутствует, а не PASS желаем.
4. Устаревшее помечать SUPERSEDED со ссылкой на норму-заменитель (D1–D9/Q1/Q2), не заставляя закрывать всё как OK. Смешанный исторический span = «OK (применимое перенесено) + superseded механика» — законное закрытие.
5. Статусы сводить по ID механически (python-замена конкретной строки таблицы статусов), не требуя от роли перечитывать таблицу на N строк каждый раунд.

## Каждый раунд обязан иметь свой commit
- Отдельный документный commit, `git diff --check` чист, `git status --short` пуст после.
- Финальная сводка всей части: полная таблица статусов (OK/SUPERSEDED/REMAINING=0) + честный список того, что роль НЕ подтверждает (загрузка/интеграция/runtime/installed-paths) — не выдавать документный артефакт за работающий контур.

## Ожидание: N раундов — норма, не сбой
Документная/крупная часть в несколько bounded-раундов — НОРМАЛЬНЫЙ итог (архитекторская оценка «12 исполнительских run на 12 частей W1» это подтверждает). Каждый раунд — свой bounded-контракт и commit; не один большой повтор и не цель «закрыть всё за 1 run» любой ценой.

## Отдельный случай: часть блокируется на ОТСУТСТВУЮЩЕМ механизме, а не на объёме
Когда исполнитель честно не может закрыть обязательный nodeid (напр. acceptance-критерий P22), потому что поддерживающий штатный механизм (admission/config-set/one-task override/native board) ещё НЕ реализован в candidate этой части и появится позже (W1-03/04/05), — это НЕ «часть больше одного прогона» и НЕ повод для под-батчинга. Различай два признака:
- **Объём** → под-батчи (см. выше).
- **Отсутствующий примитив** → стоп, оркестратор не решает содержательно. Штатный ход:
  1. Не заставлять роль выдумывать сокращённый оракул ради «зелёного» nodeid и НЕ переобъявлять критерий как «изменил YAML → перечитал» сам.
  2. Дать АРХИТЕКТОРУ независимый ADVICE-вердикт по границе: что точно входит в эту часть, что переносится в какую позднюю часть и кто становится owner'ом полного критерия. Архитектор читает master/plan и фиксирует, что полный acceptance-смысл сохраняется, а его owner перераспределяется адресно.
  3. Перенос owner'а полного критерия (напр. P22 → W1-06) — это РЕШЕНИЕ ВЛАДЕЛЬЦА (Саши), не оркестратора: предъяви вилку (принять дельту / отклонить), рекомендация архитектора; без решения части остаётся честно partial, полный критерий NOT_RUN/dependency.
  4. Пока ждём решение, можно СОДЕРЖАТЕЛЬНО продвигать уже разрешённый нижний контракт этой части (config isolation A→A′, изоляция последовательных контекстов, полная reader matrix) — эта работа нужна при любом исходе дельты и не выдумывает отсутствующий механизм.

Ключевое правило: **полный acceptance-nodeid нельзя заменить локальным тестом, который наблюдает лишь часть контракта, а его owner нельзя молча переприсвоить оркестратором.** Сначала архитектор (граница), потом владелец (дельт-решение), потом исполнитель добивает разрешённое.

## Питфоллы
- Не просить роль «работать с извлечённой таблицей, не перечитывай PREP» без передачи ей самих span-текстов — она физически не может подтвердить перенос, честно оставит OPEN, раунд уйдёт на подготовку, а не на закрытие.
- Не добавлять SUPERSEDED «для галочки» без конкретной нормы-заменителя — ревизор его оспорит; каждая пометка = норме D1–D9/Q1/Q2 или явному перечислению спасённых применимых уроков.
- Пустые заголовки-разделы не создавать: раздел без реального перенесённого текста не закрывает строку, только протаскивает count-статистику мимо содержания.
- Двойную проверку итога делать оркестратору самому (readback таблицы, счётчик строк = ожидаемому числу, чтение итогового DONE.md), не полагаясь на self-report роли в JSON-usage-нотификации.
- Когда у роли задана граница `H`/`~/.hermes` read-only (класс direct-mode W1), pytest по умолчанию кладёт `pytest-of-<user>` temp root в `$TMPDIR`, а он указывает в `~/.hermes/cache/scratch` — первый же прогон тихо пишет scratch-данные под H и нарушает read-only. Поэтому КАЖДУЮ pytest/исполнительскую проверку роли запускать с `TMPDIR=/tmp` в начале команды (`TMPDIR=/tmp PYTHONPATH=... "$PY" -m pytest ...`), и в отчёте требовать подтверждение «новых файлов под H не создано»; явно упоминать этот инвариант в промпте исполнителя, иначе роль поймает нарушение на первом прогоне и потеряет раунд.
