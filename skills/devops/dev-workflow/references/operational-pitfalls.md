# Проверки объёма, повторные отказы и rollback

Читать при HF:plan/impl/test, повторном FAIL и разборе инцидента. Процесс — [SKILL.md](../SKILL.md), транспортные окна — [invoke.md](invoke.md), норма — Б18.4, Б54, Б55.3–55.8 и Б56 master-ТЗ. Этот файл не вводит нового регламента, recovery-класса или программного guard.

## До complete: план → факт → evidence

1. Зафиксировать утверждённую ревизию плана/IAC и проверяемый commit/hash. Для каждого IAC известны `path`, `verify`, `depends`, `covers`, ожидаемые файлы, сценарии и ограничения среды. LIGHT использует собственный утверждённый IAC; создавать отсутствующий HF-plan ради проверки нельзя.
2. На HF:impl сверить фактический write-set с планом и наличие **всех** обещанных тестовых узлов/сценариев. Для pytest использовать предусмотренный планом `--collect-only -q` в том же root/env/селекции, что verify; сохранить полные node IDs. Для CLI/pilot сверить идентификаторы обязательных трасс с отчётом runner. Количество собранных параметров само по себе не доказывает исполнение нужных сценариев.
3. Сравнить множества: `missing = required - actual`, отдельно дубли и неожиданные узлы. Каждый требуемый узел должен иметь собственное evidence; посторонние passed не закрывают missing. Отсутствующий обязательный узел блокирует complete HF:impl/допуск HF:test. Сохранить незавершённый impl-результат и вернуть локальную доработку исполнителю существующим rework, не отмечать фазу выполненной.
4. На отдельной HF:test исполнить каждый IAC.verify с его зависимостями. Отчёт связывает IAC/AC, команду, rc, полный лог/путь, сценарии и результаты с проверенным commit/hash. Проверить failures/errors/skips и missing; skip обязательной проверки без согласованного основания не PASS. Общий зелёный regression не заменяет матрицу и отдельный smoke.
5. Сверить вид доказательства: component/unit, offline CLI, installed smoke, live provider и production runtime отмечаются раздельно. `live_provider=false` допустим, когда утверждённый IAC требует offline smoke; это не доказательство live. `PARTIAL_DEV_ONLY`, missing trace, `required_smoke_complete=false`, no-entry и runtime FAIL нельзя переименовать в PASS. Обязательное внешнее условие недоступно — ожидание, без ослабления AC.

Строка результата: `IAC → plan revision/hash → target commit/hash → required/actual/missing → command+rc+log → verdict`. На GATE:done дополнительно обязательны G3/git-proof своего impl write-set, остальные guards, снятые operator-holds, закрытые вопросы и доставленный AC-report. Это проверки оркестратора после выхода роли, не команды внутри wrapper исполнителя.

## Когда возвращать архитектору

Локальная незавершённость при неизменном плане — работа исполнителя: например, отсутствующие 93 узла из обещанных 169. Новая улика о невыполнимом verify, конфликте scope/запретов или неверном допущении — адресный возврат архитектору с логами, объектом и затронутыми IAC. Архитектор определяет границу повторной проверки по Б55.3; содержательная смена плана требует REV.

Первый FAIL допускает адресную доработку с новым evidence. **Первый идентичный повтор** после неё (второе наблюдение того же блокера) останавливает ещё один неизменный прогон: передать архитектору диагноз «почему исправление не устранило причину». Для двух последовательных REV с тем же объектом/контрактом/сутью дефекта действует «Повтор замечания» Б55.5: архитектор с ревизором подтверждают изменившийся способ решения и проверку до третьего круга. Иной номер замечания, сессия или слово причины счёт не обнуляют.

В возврате сохраняются прежний FAIL, ссылки на попытки, новая улика, причина и ожидаемое изменение входов. Диагноз сам по себе не разрешает второй recover той же пары; техническое восстановление и пересмотр требований остаются отдельными регламентами SKILL.md. Не превращать каждый незавершённый пункт в перепланирование всего проекта.

## Owner-директива «публиковать как есть»: реальный артефакт в регрессии

Блокер, снятый владельческой директивой (publish-as-is по типу fix4/24h), обязан иметь в том же HF:impl детерминированный регрессионный тест на **точный реальный падающий артефакт** (тот же MPP/snapshot операции), а не только синтетические предикаты. Синтетика проверяет форму предиката, но не то, что реальные данные её проходят: живой resume может снова упасть на том же блокере при полностью зелёных unit-тестах. Отсутствующий тест на реальный артефакт означает NOT RUN, а не PASS, даже при 181/0 зелёных: фаза не приёмочна, AC «план публикуется как есть» не закрыт, идти в rework/диагноз архитектора с логом повторного отказа, не завершать фазу и не ослаблять live-проверки без согласованной цели.

## Откат и сопровождение скилла

Откатывать только принадлежащие изменению пути из проверенного backup/git snapshot после прекращения записи. Проверить SHA, mode и symlink target; не `git reset --hard`, не перезапись state/journal старым архивом, не reset recover_counts/turn_count. Паузы B3/B4/w3/w4 сохраняются. Restore workspace → профили выполняет ORCH:shared-state; затем подтверждаются конечные resolved paths/hash и фактическая загрузка испытанной версии. Статический diff не подтверждает runtime поведение.

По [Creating Skills](https://hermes-agent.nousresearch.com/docs/developer-guide/creating-skills/) и [Skills System](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/) общий путь остаётся в SKILL.md, подробности — в существующих references, доступных через `skill_view(name, path)`. Metadata tags/related_skills помогают обнаружению; локальный Hermes индекс показывает до 60 символов description. Скрипт `scripts/pipeline.sh` остаётся тонкой обёрткой существующего CLI. Blueprint/расписания, inline shell, новые credential/config declarations здесь не нужны: владельцем путей/моделей уже является `tools.dev_workflow`, разрешения cron не меняются.

Перед приёмкой правки скилла проверить native Hermes frontmatter/description/size, разрешение локальных ссылок и наличие требуемых решений для четырёх строк разбора. Затем проверить их поведение на предусмотренных планом безопасных сценариях с подтверждённой загрузкой версии. Не запускать из контентной роли собственную фазу повторно ради такого испытания.
