# Процедура починки код-питфоллов (hermes-feature)

## Назначение

Закрыть один или несколько питфоллов из списков в `references/*-pitfalls.md` (`srtool-v2-pitfalls.md`, `movefromloop-v042-pitfalls.md`, `movefromloop-v043-pitfalls.md` и др.) по циклу hermes-feature: от классификации до пометки «ИСПРАВЛЕНО» в reference-файле.

Факты и история багов — в `*-pitfalls.md`. Этот документ — только **процедура** (шаги 1–7).

---

## Шаг 1. Классификация питфолла

Для каждого кандидата из отчёта Pitfall Scan определить категорию:

| Категория | Описание | Действие |
|---|---|---|
| **а** | Закрывается кодом в USERTOOLS / SRTool / другом инструменте Hermes | Блоки 1А → 2 → 3 (основной путь) |
| **б** | Апстрим-фича или изменение вне нашего репозитория | Зафиксировать в отчёте, эскалация / отдельный трек; не чинить «вслепую» |
| **в** | Поведение / дисциплина (процесс, документация, ручной регламент) | Правка скилла, MEMORY, чеклиста; код — только если явно нужен guard |

Включить в отчёт Саше: **всего** питфоллов в скане, **отброшено** (категории б/в или дубликаты), **кандидатов на починку** (категория а).

---

## Шаг 2. Пофайловый план архитектора (Блок 1А)

Модель: `gpt-6-astra` через codex CLI (`invoke-role`, роль architect).

План должен содержать:
- затронутые файлы (создать / изменить);
- функции / классы / методы;
- регресс-тесты и новые тесты;
- промежуточные точки проверки с критериями;
- явное «Что НЕ трогать» (если есть).

Ждать явное **«берём в работу»** от Саши по плану.

---

## Шаг 3. Реализация (Блок 2)

Модель: `gpt-6.1-sol` через codex CLI.

- Код строго по плану архитектора.
- Мелкое отклонение (≤2 файла, без смены архитектуры) — исполнитель сам; крупное — стоп, доплан архитектора.
- Бэкап по Блоку 5 (архитектор / при изменении config).

---

## Шаг 4. Тесты (Блок 3)

Модель: `gpt-6.1-sol`.

- Прогнать регресс-тесты пакета (pytest / существующий runner инструмента).
- Добавить тесты из плана; убедиться, что питфолл воспроизводился до фикса и не воспроизводится после.
- Мелкий баг в тестах — одна попытка исправления исполнителем; иначе — hotfix-план архитектора.

---

## Шаг 5. Независимая проверка на диске

Исполнитель или координатор (без слепого доверия к отчёту агента):

- `read` / `grep` / `pytest` на ВМ Hermes по абсолютным путям из плана;
- для скиллов: `readlink -f ~/.hermes/skills/devops/<skill>/SKILL.md` → правки только в workspace (`~/hermes-workspace/skills/`);
- сырой вывод команд в отчёт (passed/failed, пути, версия скилла).

---

## Шаг 6. Пометить питфолл закрытым в references

В соответствующем `references/*-pitfalls.md`:

- добавить **✓** или пометку **ИСПРАВЛЕНО** (дата, кратко что сделано);
- не дублировать длинное описание — ссылка на коммит/ТЗ при необходимости.

После правки скилла в workspace **не** запускать `restore-all-skills.sh` (синхронизацию делает отдельный крон).

---

## Шаг 7. Ручной прогон кодов (по необходимости)

Для инструментов с cron / внешними API — по чеклисту из ТЗ или `qa-verification-checklist`:

- один контрольный прогон entry-point скрипта на тестовых данных;
- проверка stderr / exit code;
- при риске для production — только с явным ОК Саши.

Статус **«готово»** по питфоллу ставит только Саша (Блок 3 hermes-feature).
