# PFS: слаг задачи — из контекста через LLM, не из названия сущности

## When to Use

Назначаешь/правишь слаг задачи PFS (площадка «необработанных»), диагностируешь «почему у задачи
нет/другой слаг», ревьюишь ТЗ §38/§39. Триггеры: «слаг по названию встречи», «Кирилл 1-1.…»,
пересмотр слагов §38, «слаги выявлять по контексту».

Рабочий канон (патч §39, v1.34.0+) для алгоритма назначения слага задачам PFS на площадке
«необработанных» (до promote). Сокращённая памятка; полный текст норм — мастер-ТЗ
`~/WorkVault/Hermes-Backlog/TZ/ProtocolFromSummary/ProtocolFromSummary_TZ.md` §34 и §39.

## Правило

Слаг задачи выводится **из смысла ЭТОЙ задачи через LLM**: `union = assignee ∪ task.text ∪
discussion ∪ eligible MOFS bind`, проект из `closed_list` (14). Порядок: LLM-выбор → union → fail-soft.

## Запрещено как якорь слага (жесткие запреты Саши)

- `meeting_name`, `display_name` сущности встречи, общий список участников, `summary.notes`
  (majority встречи), YAML `projects:` frontmatter.
- **`route.tag_prefix` / `display_name` при `kind ∈ {one_on_one, person_1on1, unknown, sync_aid}`**
  — слаг по названию встречи (пример: «Кирилл 1-1.»). Это был §38 meeting-home; Саша отклонил
  явно: слаг берётся из контекста, а не из наименования сущности. §38 → superseded.

## Fail-soft (union после LLM) — §39: слаг ОБЯЗАТЕЛЕН, нет «без слага»

Ключевое правило Саши: **у задачи не может не быть слага** (as-is без префикса — не вариант).

- union=1 в проектной тройке → `canonical_task_slug + orig_text` без пробела после точки.
- union=1 = adm → `АДМ.`
- union=0 или ≥2, LLM пуст/невалиден/вне допустимого → **`АДМ.`** (НЕ as-is, НЕ meeting-home).
- Допустимый выбор (overlay): {ai_analitik, trisigma, parsing, adm}. Проектная тройка — только по
  уверенному контексту; иначе ADM. Имена встреч/1:1/мультисинков — never value слага.

## Lifecycle проекта (гибрид H → следующий пакет)

Семантика слагов эволюционирует дальше §39 к **гибриду H**:

- `open` / `closed_at` на `kind=project` в `entities.json` (схема 1.3, optional-поля, identity —
  НЕ числовые P(), НЕ pick_hint в реестре). Промпт строит допустимый список из реестра.
- **Закрытый проект ≠ 0** (Саша): по закрытому может прилететь вопрос (пример — закрытый стрес-тест,
  бизнес спросил об окупаемости). named hit закрытого → слаг, не ADM; антибот «давно закрыт» ≠
  «слага не существует». Область новых слагов и добавление новых проектов (open:true → подхват без
  правки кода) выводится из данных, а не из константы в коде.
- Политика выбора (ADM-always, named_only по умолчанию, frequent только исключением, шаг 4 без
  decay/априора: union 0/≥2 → только ADM) остаётся в picker-коде — это НЕ свойства карточки проекта.
- Реестр = факт мира (кто проект, жив ли, когда закрыт); picker = правило инструмента. Не смешивать.

Архитектурный урок этой сессии: **lifecycle проекта (закрытые + новые) не был предусмотрен на этапе
диагноза → дефект дошёл до ТЗ §38 и импл.** При ревью/проектировании выбора из закрытого списка
сущностей сразу проверяй: как обрабатывается закрытие сущности и добавление новой ещё на этапе BUG:diagnose,
а не разматывай поезд до ТЗ.

## Republish

Уже приклеенный 1:1-префикс («Кирилл 1-1. …») на republish **снимается со входа batch** — задача
заново идёт в LLM. Иначе строка навсегда остаётся с неверным слагом.

## Диагностика «почему у задачи нет/другой слаг»

Смотреть 4 контекстных источника (`_task_union_slugs`), а не общую тему протокола:
assignee ∩ identities(closed) · task.text ∩ identities(closed) · discussion задачи · eligible
MOFS bind. По §39 слага у задачи нет не может (если без префикса / появился «Кирилл 1-1.» на
meeting-home или «АДМ.»-клей вместо проектного) — вопрос НЕ «почему без слага», а «почему слаг
X, когда контекст говорит Y»: проверяй union по 4 источникам и допустимость выбора из overlay-четвёрки.
