# ProxyCheckLinux — Linux/Python-агент тестера прокси (linux-agent)

Мастер-ТЗ подпроекта `linux-agent` внутри Go-проекта `proxycheck` (Windows-тестер `proxycheck.exe`).
Версия 1.0.0 объединяет: исходное ТЗ подпроекта, текущее состояние кода, выводы архитектурного
анализа отказоустойчивости/токенов/расширяемости, и решение Саши по итогам теста —
**пакетный вывод в формате `.xlsx`** вместо CSV.

Доработка этого инструмента = новая секция внутри этого файла. Версию бампать по факту изменений.

## 0. Жёсткие ограничения (нарушать нельзя)

1. **Не ломать Windows-пример.** Каталоги `cmd/`, `internal/`, `go.mod`, собранный `proxycheck.exe`
   в корне проекта `proxycheck/` — **не менять** (ни флаги, ни логику, ни формат вывода). Критерий
   проверки: на Windows по-прежнему работает `.\proxycheck.exe -proxy HOST:PORT -user LOGIN -pass PASSWORD`
   и выдаёт тот же вывод, что и до правок в `linux-agent/`.
2. Всё новое — **только в `linux-agent/`**. Корень Windows-проекта Python-зависимостями не засорять.
3. Единичная проверка (`-proxy`) обязана выводить **весь исходный отчёт Go** без сокращений: таблица
   (14 колонок) + строка «Итого» + полный JSON. Это правило пакетного режима **не отменяет** —
   пакетный режим (§3.2) — отдельный, новый сценарий с собственным контрактом вывода (см. п.9 ниже).
4. Ничего не коммитить и не публиковать секреты (логин/пароль прокси). Готовые отчёты (JSON/xlsx)
   с боевыми прокси и паролями — не копировать в git, не прикреплять к TZ/скиллам. Каталог вывода
   пакетных прогонов должен быть за пределами версионируемого дерева (например, `~/.hermes/tmp/` или
   рабочая директория пользователя вне `linux-agent/`), либо явно добавлен в `.gitignore`.
5. Не переписывать Go на Python «поверх» exe — `linux-agent` дополняет, не заменяет Windows-тестер.
6. **stdlib-only — предпочтение, не абсолютный запрет.** Единственное разрешённое отступление —
   `openpyxl` для записи `.xlsx` (см. §3.2, п.9): в stdlib нет модуля для записи настоящего
   Excel-файла (`.xls`/`.xlsx`), а самодельная генерация OOXML через `zipfile` менее надёжна и не
   покрывается тестами так же хорошо, как зрелая библиотека. Других новых зависимостей не добавлять
   без отдельного решения.

## 1. Зачем этот инструмент

Автономный комплект для Linux-ВМ: распаковали → установили → AI-агент по скиллу запускает проверку
прокси (одну или пакетом) и возвращает результат. Для одиночной проверки — точный эталон Go-отчёта.
Для пакетной проверки (списки 100–5000+ прокси) — новый режим: полный JSON в файл + читаемый
человеком `.xlsx` со строгими колонками, без раздувания диалога с агентом построчным выводом.

Windows-тестер (`proxycheck.exe`) остаётся инструментом для людей на Windows-машинах, без изменений.

## 3. Формат вывода

### 3.1. Единичный режим (`-proxy`) — эталон Go, ОСТАЁТСЯ как есть

Без изменений относительно исходного ТЗ. Три слоя, всегда все три:

**Таблица** (`report.TABLE_COLUMNS`, 14 колонок):
`PROXY VERDICT TCP HTTP HTTPS TARGETS COUNTRY REGION EXIT_IP MYIP_RU IP_TYPE CONF ASN_ORG REASON`

**Итог**: `Итого: N прокси, ACCEPT=…, REJECT=…`

**JSON** — полный объект `Row` (см. `fixtures/report.schema.json`, поля перечислены там же), печатается
в stdout после таблицы и, если указан `-output`, дублируется в файл.

Правила вердикта (`verdict.decide`, без изменений): TCP обязателен (hard-gate 1); нужны и HTTP, и
HTTPS (hard-gate 2); REJECT по таргетам (hard-gate 3) только если **ни один** целевой сайт не открылся;
ASN/гео/тип IP/myip.ru на вердикт не влияют.

**Запрещено** для единичного режима: отдавать только «ЕСТЬ/НЕТ» или короткий блок без таблицы+JSON.

### 3.2. Пакетный режим (`-input`) — НОВОЕ: итоговый `.xlsx`-отчёт

Применяется, когда используется `-input <файл со списком прокси>`. Решение Саши по итогам теста:
**вывод для пользователя — `.xlsx`, не CSV.** Причина: в русской локали Excel/Google Sheets CSV с
разделителем `,` схлопывается в один столбец (локальный Excel ждёт `;`) — таблица нечитаема без
ручной донастройки при импорте. `.xlsx` (через `openpyxl`) хранит колонки и Unicode нативно —
кодировка/разделитель перестают быть проблемой.

#### 3.2.1. Источник данных

Данные для `.xlsx` берутся из полного JSON-отчёта (тех же объектов `report.Row`, что и в §3.1/§4 схемы
`fixtures/report.schema.json`) — никакой отдельной урезанной модели не заводить, `.xlsx` — это
проекция существующего JSON, а не новый источник истины.

#### 3.2.2. Схема `.xlsx` — 18 колонок (жёсткая, зафиксированная схема)

Одна строка = один прокси. Порядок и состав колонок фиксирован, менять только новой версией этого ТЗ:

| # | Колонка | Источник (поле `Row` / вычисление) | Формат |
|---|---|---|---|
| 1 | `IP` | `Proxy.host` (адрес без изменений, как задан на входе) | текст |
| 2 | `PORT` | `Proxy.port` | текст/число |
| 3 | `login` | `Proxy.user` (пусто, если без авторизации) | текст |
| 4 | `password` | `Proxy.password` (пусто, если без авторизации) | текст |
| 5 | `VERDICT` | `Row.verdict` (`ACCEPT`/`REJECT`) | текст |
| 6 | `TCP` | `Row.tcp_alive` → `OK`/`FAIL` | текст |
| 7 | `HTTP` | `Row.http_ok` → `OK`/`FAIL` | текст |
| 8 | `HTTPS` | `Row.https_ok` → `OK`/`FAIL` | текст |
| 9 | `EXIT_IP` | `Row.exit_ip` (пусто → `-`) | текст |
| 10 | `COUNTRY` | `Row.country_code` (пусто → `country_summary()`, иначе `-`) | текст |
| 11 | `REGION` | `Row.region` (пусто → `-`) | текст |
| 12 | `MYIP_RU` | `myip_ru_summary(Row)`: `match` / `MISMATCH` / `-` | текст |
| 13 | `IP_TYPE` | `Row.ip_type` (пусто → `-`) | текст |
| 14 | `ASN_ORG` | `Row.asn_org` (пусто → `-`) | текст |
| 15 | `TGT_TUTU` | статус таргета, чей `url` содержит `tutu.ru` → `OK`/`FAIL`/`-` (`-`, если таргет не проверялся, например HTTPS не прошёл) | текст |
| 16 | `TGT_YANDEX` | статус таргета, чей `url` содержит `yandex.ru` → `OK`/`FAIL`/`-` | текст |
| 17 | `REJECT_STAGE` | извлекается regex-ом из `Row.reject_reason`: `^hard-gate (\d)` → `"hard-gate 1"` / `"hard-gate 2"` / `"hard-gate 3"`; спецзначения `"PARSE_ERROR"` и `"internal error"` (см. §6); пусто при `VERDICT=ACCEPT` | текст |
| 18 | `REASON` | полный текст `Row.reject_reason` как есть (кириллица сохраняется без экранирования — xlsx хранит Unicode нативно); пусто при `ACCEPT` | текст |

Требования к записи:
- Никакого текста, объединяющего несколько логических значений в одну ячейку (запрет на паттерн
  `targets_summary()` вида `"tutu.ru:OK travel.yandex.ru:FAIL"` в одной ячейке — для xlsx это
  разносится на `TGT_TUTU`/`TGT_YANDEX` отдельно).
- `REJECT_STAGE` и `REASON` — раздельные колонки (стадия отдельно, детали отдельно), не «стадия: причина»
  одной строкой.
- Первая строка — заголовки (ровно 18 названий из таблицы выше, в этом порядке).
- Кодировка — нативная поддержка Unicode `openpyxl`, дополнительных мер не требуется.

#### 3.2.3. Расширяемость таргетов сверх 2 (открытая договорённость)

Если через `-targets` (см. §5) сконфигурировано **больше двух** таргетов (например добавлены
`ozon.ru`, `wildberries.ru`), фиксированная 18-колоночная схема `.xlsx` **не расширяется
автоматически** — `TGT_TUTU`/`TGT_YANDEX` продолжают отражать только эти два домена (по подстроке
в `url`), остальные сконфигурированные таргеты:
- участвуют в вычислении `VERDICT`/`hard-gate 3` (как обычно, через `min_ok`, см. §5);
- присутствуют в полном JSON-отчёте (файл `-output`), но не получают отдельной колонки в `.xlsx`.

Если у Саши появится потребность в xlsx-колонках для дополнительных таргетов — это отдельная секция
доработки данного ТЗ (новая версия), не тихое расширение текущей схемы.

#### 3.2.4. Что выводится в stdout при `-input`

Чтобы не тратить токены агента на построчный вывод при 5000+ строках (см. §7):
- В stdout — **только сводка**: строка «Итого: N прокси, ACCEPT=X, REJECT=Y», разбивка REJECT по
  `REJECT_STAGE` (сколько на hard-gate 1/2/3/PARSE_ERROR/internal error), и пути к файлам
  (`-output` JSON, `.xlsx`).
- Полный JSON — только в файл `-output` (в пакетном режиме обязателен, см. §4).
- Полная построчная таблица (как в §3.1) в пакетном режиме в stdout **не печатается** по умолчанию —
  это правило относится только к единичной проверке (§3.1, п.3 и §0 п.3 который сохраняет силу для
  `-proxy`). Принудительно её можно получить флагом `-verbose` (см. §4) для отладки небольших пакетов.

## 4. CLI (существующие флаги + новые)

Существующие (без изменений в поведении для единичного режима):

```
-proxy HOST:PORT | HOST:PORT:USER:PASS | scheme://user:pass@host:port
-user LOGIN            (только вместе с -proxy)
-pass PASSWORD         (только вместе с -proxy)
-input PATH            (файл со списком прокси, взаимоисключим с -proxy)
-output PATH           (путь к JSON-файлу отчёта)
-timeout DURATION      (по умолчанию 10s)
-concurrency N         (по умолчанию 20 — число прокси одновременно)
```

**Формат входного файла `-input` (доработка 27.08):**
`parse_input` принимает два формата на выбор:
- строки `host:port` / `host:port:user:pass` (как сейчас);
- **CSV** с заголовком `ip,port,login,password` (или без заголовка) — строки вида
  `pool.proxy.market,10000,login,password` автоматически распознаются и нормализуются.

Правила распознавания CSV: строка содержит запятые и не разбирается как `host:port[:user:pass]`
(нет `:` между первой и второй частью / кол-во полей не совпадает). Если поле первая строка —
заголовок (`ip,port,login,password` — регистронезависимо) — пропускается. Пустые строки и
комментарии `#` пропускаются, как и для обычного формата.

Новые флаги (только для пакетного режима, `-input`):

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `-xlsx PATH` | `<input>.report.xlsx` (если `-input` задан, а `-xlsx` — нет) | путь к итоговому `.xlsx`-отчёту (§3.2) |
| `-output PATH` | `<input>.report.json` (если `-input` задан, а `-output` — нет) | в пакетном режиме JSON-файл обязателен по факту — без явного пути используется дефолт рядом со входным файлом |
| `-verbose` | выключен | в пакетном режиме печатать в stdout ещё и полную таблицу+JSON (как в §3.1), поверх сводки — для отладки на небольших списках |
| `-dedupe` / `-no-dedupe` | `-dedupe` включён по умолчанию для `-input` | дедупликация по `host:port:user` (см. §6, D4); не действует в режиме `-proxy` |
| `-targets PATH` | не задан → встроенный дефолт (`tutu.ru`, `travel.yandex.ru`, `min_ok=1`) | путь к `targets.json` (§5) |
| `-enrichment-concurrency N` | 15 | отдельный лимит одновременных запросов обогащения (ASN/PTR/гео/myip.ru), не связан с `-concurrency` по прокси (см. §6, E6) |

`-verbose`, `-dedupe`/`-no-dedupe`, `-targets`, `-enrichment-concurrency` не действуют в режиме
`-proxy` (единичная проверка не меняется).

## 5. Расширяемость таргетов (`targets.json`, флаг `-targets`)

Сейчас `target.py:DEFAULT_TARGETS` — захардкоженный список из двух URL, конфигурации нет. По выводам
архитектурного отчёта — вынести в конфиг-файл, путь передаётся флагом `-targets`.

Формат `targets.json`:

```json
{
  "min_ok": 1,
  "targets": [
    {"url": "https://www.tutu.ru/", "enabled": true, "min_body_bytes": 3000},
    {"url": "https://travel.yandex.ru/", "enabled": true, "min_body_bytes": 3000}
  ]
}
```

Правила:
- `-targets` не указан → используется встроенный дефолт (два текущих таргета, `min_ok=1`, `min_body_bytes=3000`), поведение идентично текущему.
- `enabled: false` — выключить таргет без правки кода (не запрашивается, не участвует в вердикте).
- `min_body_bytes` — переопределение порога «похоже на страницу-заглушку» (см. `target.MIN_HTML_BODY_BYTES`) per-target.
- `min_ok` — настраиваемый порог «N из M успешных» для hard-gate 3 (сейчас в `verdict.py` жёстко «хотя бы 1»; заменить на сравнение с `min_ok`).
- Расширение состава таргетов сверх двух влияет на вердикт и на JSON, но не на 18-колоночную схему `.xlsx` (см. §3.2.3).

## 6. Защита от сбоев (приоритеты по отчёту архитектора)

Критично (блокирует безопасный прогон 5000+, делать в первую очередь):

1. **`job()` без try/except (риск E1).** Обернуть тело `job(i, p)` в `pipeline.check_all` в
   try/except: при любом необработанном исключении — записать `Row(proxy=str(p), verdict="REJECT",
   reject_reason="internal error: " + str(e))`, `REJECT_STAGE="internal error"`. Один сбойный прокси
   не должен ронять весь прогон.
2. **Инкрементальная запись (риски E2/E8).** Не хранить единственную точку записи «весь JSON одним
   `json.dumps` в конце». Писать результат по мере готовности каждого прокси (JSONL — построчно
   дозаписывать готовый `Row`), в конце (или по флагу) собрать финальный `-output` JSON-массив и
   `.xlsx` из накопленного JSONL. При падении процесса/ВМ посреди прогона частичный результат не
   теряется.

Средний приоритет:

3. **Placeholder для невалидных строк входа (риск D2/D6).** `model.parse_list` сейчас тихо теряет
   невалидные строки (только предупреждение в stderr) — из-за этого количество строк в выводе может
   не совпадать с количеством строк на входе. Добавить: для каждой строки с ошибкой парсинга —
   placeholder-строка в результате с `verdict="REJECT"`, `reject_reason="PARSE_ERROR: <ошибка>"`,
   сохранить `input_line`/`line_no`, чтобы порядок и количество строк соответствовали входу.
4. **Дедупликация (риск D4).** Флаг `-dedupe` (вкл. по умолчанию для `-input`, см. §4): ключ
   `host:port:user`. Повторные вхождения — клонировать результат первого вхождения с пометкой
   `dedup_of: <index>` в JSON (не гонять сеть повторно на идентичные прокси).
5. **Кэш enrichment по `exit_ip` (риск E5/E6).** Если несколько прокси выходят через один и тот же
   `exit_ip` (типично для пулов мобильных прокси) — не повторять ASN/PTR/гео/myip.ru запросы,
   переиспользовать результат первого попадания в рамках одного прогона.
6. **Отдельный лимит конкурентности enrichment (риск E6).** `-enrichment-concurrency` (§4) — Semaphore
   отдельно от `-concurrency` по прокси, чтобы внешние сервисы обогащения (ip-api.com, ipwho.is,
   Team Cymru, myip.ru) не захлёбывались при большом числе одновременных прокси.

Низкий приоритет:

7. **Гонка `socket.setdefaulttimeout()` (риски E4/E7).** `rdns.lookup` использует глобальный
   процессный таймаут — заменить на способ, не создающий гонку между параллельными PTR-запросами
   (например, явный таймаут через `socket.create_connection`/отдельный резолвер вместо глобальной
   настройки).

Не требует изменений (уже устойчиво по коду, зафиксировать в тестах):
- Спецсимволы `:`/`@` в логине/пароле (риск D3) — `model.py` уже обрабатывает через `split(":", 3)` и
  поиск последнего `@`; добавить unit-тесты на пароль с `@`, пароль с `://`.
- Недоступность сети/мёртвые прокси (риск E3) — `checker.py` уже ловит исключения, REJECT по hard-gate 1/2.
- Недоступность/rate-limit внешних сервисов обогащения (риск E5) — уже в try/except, деградирует без падения вердикта.

## 7. Оптимизация токенов

Два независимых режима вывода (без взаимного влияния на код единичного режима, см. §0 п.3):

1. **Единичная/малая проверка (`-proxy`)** — не трогать: полная таблица+JSON в stdout, как в §3.1.
2. **Пакетный режим (`-input`)** — stdout только сводка (§3.2.4), полный JSON только в файл
   (`-output`), итоговый читаемый артефакт — `.xlsx` (§3.2), а не CSV и не построчный текст в чат.

Дополнительно для больших пакетов (5000+):
- Полный JSON (JSONL промежуточный + финальный массив) — только в файл, никогда не ретранслируется
  агентом в чат целиком.
- Если агенту нужно проверить конкретные строки из большого прогона — читать `.xlsx`/JSONL порциями
  (например, через `openpyxl` `read_only=True` построчно, или grep/awk по JSONL), не загружать весь
  файл в контекст диалога.
- Финальный ответ агента пользователю по итогам пакетного прогона — краткая сводка (Итого, разбивка
  REJECT по `REJECT_STAGE`, топ причин) + пути к `-output`/`-xlsx`, не дамп файлов целиком.

## 8. Скилл-инструмент (`.cursor/skills/proxy-check/SKILL.md`)

Скилл должен обновиться отдельным блоком под пакетный режим, не меняя правил единичной проверки:

- **Единичная проверка (`-proxy`)** — правила скилла без изменений: полный stdout, ничего не
  урезать, пароль в чат не повторять.
- **Пакетный режим (`-input`)** — новый раздел скилла:
  - Как запускать: `python3 -m proxycheck_linux -input <файл> [-xlsx PATH] [-output PATH] [-targets PATH]`.
  - Что вернуть пользователю: сводку из stdout (§3.2.4: Итого + разбивка по REJECT_STAGE) и путь(и)
    к `.xlsx`/JSON-файлам. **Не** ретранслировать содержимое `.xlsx`/JSON целиком в чат.
  - Не публиковать логины/пароли из `.xlsx`/JSON в чат построчно (артефакты содержат учётные данные —
    это ожидаемо для локального файла, но не для текстового ответа агента).
  - Явно указать, что `.xlsx`/JSON пакетных прогонов — не коммитить, не прикреплять к TZ/скиллам
    (см. §0 п.4).

## Что НЕ трогать

- `proxy/cmd/proxycheck/` (Go, Windows CLI) — не менять флаги, логику, вывод.
- `proxy/internal/` (Go, вся логика проверки/вердикта/отчёта на стороне Windows-эталона) — не менять.
- `proxy/go.mod` — не менять.
- `proxy/proxycheck.exe` — не пересобирать, не подменять.
- Формат вывода единичного режима `-proxy` в `linux-agent` (таблица 14 колонок + Итого + полный JSON,
  §3.1) — не сокращать и не менять состав полей задним числом; это отдельный контракт от пакетного
  `.xlsx`, введённого этой версией ТЗ.
- `fixtures/report.schema.json` — эталонная схема Go-отчёта; менять только если меняется сам Go-отчёт
  (что запрещено п.0.1).

## Связи с экосистемой

`linux-agent` работает автономно на отдельной Linux-ВМ, вызывается через скилл
`.cursor/skills/proxy-check/SKILL.md`. Единственная новая внешняя зависимость — библиотека
`openpyxl` (запись `.xlsx`, см. §0 п.6) — устанавливается через `install.sh`/`pip` в рамках
самого пакета `linux-agent`, не затрагивает другие инструменты WorkVault.

### Интеграция с ErrorBus (решение архитектора A+wrap)

Инструмент остаётся **автономным standalone-CLI**: код `linux-agent` не знает про шину ошибок
Hermes, не содержит кредов ErrorBus/Telegram, не зависит от `events.db`.

Логирование **сбоев процесса/прогона целиком** (краш, необработанное исключение верхнего
уровня, OOM, `PermissionError`, синтаксическая ошибка — т.е. ненулевой exit code процесса) в
шину ошибок выполняется **снаружи**, через уже готовый мост Hermes
`~/.hermes/scripts/error_bus_wrap.sh` (Mode B, см. `ErrorBus_TZ.md` §3.4):

- Точка вызова — скилл `proxy-check`: команда запуска инструмента оборачивается в
  `error_bus_wrap.sh --tool ProxyCheckLinux --job-id proxycheck_linux -- python3 -m proxycheck_linux ...`.
- Обёртка прозрачно пробрасывает stdout/stderr/exit code. При ненулевом коде сама пишет строку
  в `events.db` (дедуп, агрегация) и шлёт в Telegram-топик Errors (`-1004300127777:11112`),
  с тротлингом и классификацией критичности — вся логика уже реализована в ErrorBus.
- Обёртка должна выполняться там, где физически доступны `~/.hermes/error_bus/` и сеть до
  Telegram (стороне с Hermes/агентом), а не на изолированной ВМ без Hermes.
- **Единичные `REJECT`/`internal error` по конкретным прокси — НЕ в шину**: это бизнес-данные
  отчёта, остаются в `.xlsx`/JSON (в т.ч. `reject_reason="internal error: ..."`, который уже
  штатно перехватывается внутри `pipeline.check_all` §6 п.1).
- Регистрация клиента: `ErrorBus_TZ.md` §11.2 — добавить строку `ProxyCheckLinux — wrap`.

Код `proxycheck_linux` и код/схема ErrorBus при этом **не меняются**.

## Критерии успеха (проверяемые)

1. `.\proxycheck.exe -proxy HOST:PORT -user LOGIN -pass PASSWORD` на Windows работает как до правок
   (регресс-тест на Windows-стороне не запускается из Linux-агента, но код `cmd/`/`internal/`/`go.mod`
   остаётся байт-в-байт без изменений — проверяется diff'ом).
2. `python3 -m proxycheck_linux -proxy HOST:PORT -user LOGIN -pass PASS` печатает все три слоя
   (таблица 14 колонок, «Итого», полный JSON) — без сокращений, как и до этой версии ТЗ.
3. `python3 -m proxycheck_linux -input list.txt` создаёт `.xlsx`-файл с ровно 18 колонками в порядке
   §3.2.2, по одной строке на каждую непустую/некомментарийную строку входного файла (включая
   `PARSE_ERROR`-плейсхолдеры, §6 п.3), и JSON-файл (`-output`) с полным отчётом.
4. При падении одного прокси (искусственно вызванное исключение внутри `check_one`) прогон списка из
   N прокси не прерывается — в результате N строк, включая одну с `reject_reason` вида
   `"internal error: ..."` (§6 п.1).
5. При прерывании процесса на середине прогона 5000 прокси частичный результат (JSONL) сохранён на
   диске и не теряется (§6 п.2).
6. Одинаковые `host:port:user` в списке входа — в результате помечены `dedup_of`, сетевой запрос
   выполнен один раз (§6 п.4), если не передан `-no-dedupe`.
7. `-targets custom.json` с изменённым составом/`min_ok` — влияет на вердикт (hard-gate 3) согласно
   конфигу, `.xlsx`-схема при этом остаётся 18 колонок (§3.2.3).
8. Пакетный прогон 5000+ без `-verbose` не печатает в stdout построчную таблицу/полный JSON — только
   сводку (§3.2.4); объём stdout не растёт линейно с числом прокси.
9. Обновлённый `SKILL.md` описывает оба режима раздельно (§8) и явно требует не ретранслировать
   `.xlsx`/JSON целиком в чат при пакетном прогоне.
