# FILL / заливка в Jira (transitions)

**Рабочий порядок:** сначала правки и утверждение текста в MD (Obsidian), затем заливка в Jira.
Jira не редактируем как основной источник блоков; доработки — снова MD → Jira.
После успешного POST `sync_md_header` (`--sync-md` в `fill-plan`) дописывает в шапку MD журнал заливки — не заменяет содержимое блоков из Jira.

## FILL (план/факт через srtool)

TG-driven, transition **61**, буллет `·` (U+00B7), переносы `\r\n`, парсер `\d+\.\t`. Детали — `SRTool_TZ.md`. **Не** `PUT` на customfield SR.

## Заливка итогов (44404–44406)

Только по явной команде («перенеси итоги»), после согласования `_draft.md` **в Obsidian** (источник правды по блокам — MD, не Jira).

1. **Только запрошенные поля.** «Только итоги» → 44404–44406, **не** 44401–44403.
2. Текст из `_draft.md` (структура `### N.`, `**Плановый результат:**` и т.д.) — plain text с переносами; при необходимости сначала дополнить draft в MD.
3. `\n` → `\r\n`.
4. **`GET /issue/{key}/transitions`** — для итогов id **`271`**, не `61`.
5. `POST /issue/{key}/transitions` с полями в `fields`.
6. GET-верификация: первые ~300 символов каждого поля; статус не должен измениться неожиданно.

## После успешного POST (обязательно; не меняет порядок MD → Jira)

1. **`sync_md_header`** / `fill-plan --sync-md`: шапка того же MD — статус Jira, дата, transition (журнал заливки; блоки 1–6 из Jira не переписывать).
2. `systemctl --user start owncloud-sync.service`
3. Не дублировать GET: достаточно stdout srtool (статус + факт заливки).
4. Согласование: если пользователь сказал «отправь / --submit` — `fill-plan --submit --yes`.
   Иначе не напоминать «сделай вручную в Jira» отдельным кругом.

## Заливка плана (44401–44403)

Transition обычно **`61`**. Только 44401–44403. Текст блоков — из MD (`--from-md`), см. `flow-plan.md`. После POST — те же шаги «После успешного POST» выше.

## Перед КАЖДОЙ заливкой

`GET /transitions` заново — статус SR может измениться вручную в Jira между репликами. При `400` или отсутствии нужной transition — сообщить текущий статус, ждать правки пользователя.

## Обработка 204 / пустого ответа

Transition POST может вернуть `204 No Content` — это успех. Верифицировать GET полей, не только HTTP-код.

## SR_BYPASS

Ручной curl только если SRTool недоступен. Строка `SR_BYPASS: …` в ответе. После — сверить GET.
