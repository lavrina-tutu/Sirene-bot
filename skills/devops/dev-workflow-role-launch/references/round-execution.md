# Адресное многораундовое исполнение и прерванные прогоны

Класс «часть требует многих прогонов»: нижний OWN-компонент ведётся точечными раундами через `invoke-role`. Операционные правила по keras этой серии.

## Исполнитель застрял — смена модели, а не перенос scope

Сигнал: несколько раундов подряд без COMMIT, отчёт «остаток вернуть владельцу». Это застревание исполнителя, а не ENV gap.

- Запросить адресный вердикт архитектора: каждая группа OWN vs DEPENDENCY с точными assertions и чек-листом адресных раундов.
- Blanket-перенос группы по аналогии с прежней дельтой архитектор не подтверждает без exact failing trace (в нашем кейсе все 6 групп остались OWN).
- По решению Саши сменить исполнителя на более сильную модель: low-reasoning `gpt-6.1-terra` → `gpt-6.1-sol`; сильный исполнитель закрывает целую группу за раунд (root+guard, occupancy+history, holds, LIGHT/verbs, events/cancel) с одним COMMIT и полным pytest evidence.
- Не гонять «ещё один общий прогон» на той же слабой роли — это слепой повтор.

## Форма адресного раунда

Один раунд = один COMMIT + команды rc + nodeid-матрица (missing/actual) + rollback-строка. WRITE-scope ТОЛЬКО согласованных файлов; прочие слои (pipeline_gates/terminal_boundary/invoke_role/pipeline_context/…) не трогать.

## Прерванный фоновый codex-раунд (exit 143 / SIGTERM)

Прерванный по таймауту/SIGTERM codex-исполнитель оставляет **незакоммиченный worktree**, чей срез может зависать: pytest не заканчивается даже с `-x`, зависший прогон → rc=124.

- Не доверять срезу и не коммитить его. Сверить `git status --short` + `git diff --stat`.
- При подозрении на зависание откатить `git checkout -- <файлы>` к стабильному HEAD и **перезапустить раунд начисто**.
- Длина введённых правок не означает готовности — только прошедший с чистого среза полный прогон.

## Диагностика зависшего pytest

Писать вывод в файл (`> log 2>&1; echo rc=$? >> log`), а не гнать через `| tail`/`| head` — pipe съедает прогресс и не показывает, где застряло. Читать файл через read_file.
