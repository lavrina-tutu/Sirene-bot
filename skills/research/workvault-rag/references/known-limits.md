## Contacts — покрытие и матчинг

**Фактическое покрытие (проверено на индексе, Фаза 0/2):** 642 встречи в mofs, из них
594 (**93%**) покрыты `meeting_slugs` (bucket='contacts'). Прежняя оценка «20-30%» была
неверной (устарела, относилась к раннему этапу до backfill) — не использовать её больше.

Оставшиеся ~7% (48 встреч) — типичные причины:
- **Формат ФИО «Имя Фамилия» не матчится.** `ContactStore.find_contacts()` ожидает
  «Фамилия Имя [Отчество]». «Никита Лысенко» → 0 результатов, «Лысенко Никита» → resolved.
  Ограничение матчера, не ошибка данных. Фикс — ТЗ `MarkObjectsFromSummary_TZ.md`
  §matcher_contacts (обратный порядок + гипокористики, v0.9.1), пока не реализован.
- **Уменьшительные формы не матчатся:** «Лёша Белов» → 0 (нет в базе как «Лёша»),
  «Саша Корнеев» → 0. Ожидаемое поведение до реализации словаря гипокористик
  (HYPOCORISTICS). Не сообщать пользователю «не нашла» по таким запросам — уточнить
  полное имя (Фамилия Имя).
- **Раздел «Блокеры» не сканируется MOFS:** одиночные слова-фамилии в разделе Блокеры
  не извлекаются — ожидаемое поведение по принципу «не угадывать».
- **`mofs rematch` не фиксит матчер:** если ФИО не матчится из-за формата — rematch
  вернёт то же самое, нужно ждать фикса в коде.
- Архив до июля 2026 без раздела «Участники» в файле — contacts пустые по построению
  (нечего извлекать), это не баг индекса.

**Практический вывод:** `search_meetings(slugs={'contacts': [...]})` покрывает
подавляющее большинство (93%) — использовать как основной путь. Grep-fallback по
секции «Участники:» — только для оставшихся 7% (участник не резолвится, «93% не
сработало») или явного запроса по редкому/уменьшительному имени.

## История: qmd (semantic search) — отказ 16.07.2026

`qmd` (semantic search MCP) исключён из системы 16.07.2026 — был ненадёжен на практике
(CPU-only эмбеддинги, частые "LLM session expired" сбои индексации, зависания по 300с
таймауту на простых запросах в рантайме) и избыточен: файловый поиск/индекс справляется
с реальными запросами быстрее и надёжнее. Полная история и rollback-инструкция —
`references/qmd-retired-2026-07-16.md`.

**Filter-farm** (copy-based фильтрация контента перед индексацией для qmd) — неактуален
без qmd: `search_files`/`read_file`/`mofs index` работают напрямую по исходным папкам.

## Архитектурное решение: связи/wiki-links, не векторный RAG (16.07.2026)

Когда встаёт вопрос «как ещё улучшить качество/скорость поиска» — ответ **structural
links (Obsidian wikilinks + Dataview + canonical `entities.json`), не переход на
векторный RAG**. Не переоткрывать вопрос с нуля без принципиально нового обстоятельства:

1. qmd уже пробовали и отключили (см. выше) — ненадёжен на практике, не гипотетически.
2. Обычный повод тянуться к RAG — «найти релевантное без точного текстового совпадения» —
   закрывается дешевле через `entities.json` (canonical aliases устраняют
   неоднозначность без эмбеддингов) и wiki-ссылки/backlinks (Obsidian graph показывает
   связи «встреча ↔ проект» нативно).
3. `MarkObjectsFromSummary` v0.2 — правильное место для project-wiki-ссылок в
   frontmatter встреч, тем же механизмом, что уже работает для контактов (v0.1). Тогда
   «эволюция постановки задачи во времени» решается через backlinks + сортировку по
   дате, а не агента, гоняющего Haiku по десяткам файлов при каждом запросе.
4. Библиотечные скиллы `langchain-rag` (требует эмбеддинги+векторную БД — тот же класс
   проблем, что и отключённый qmd) и `obsidian-vault` (grep+wikilinks без структурных
   фильтров дата/участники/тип-сущности) — разобраны и отклонены в пользу
   `entities.json` + алгоритма этого скилла.

Полное решение по стыковке `entities.json` с MOFS/AFM (naming-конфликт слугов, устав
vs протокол-страница, двойная классификация типа «Метротека = проект и инструмент»,
4 корзины при NER-прогоне архива) — см. `about_usr_skills`, секция
«EntityRegistry ↔ MarkObjectsFromSummary (MOFS) / AggregateFromMeetings (AFM)».
