# Паттерн: hermes-feature

## Overview

Единый процесс работы над фичами Hermes и USERTOOLS: от выбора варианта до кода, тестов, документации, диагностики и отката. Фиксирует кто пишет (Sonnet-5 vs Opus 4-7, провайдер из конфига), когда делать бэкап, как эскалировать, и что запрещено делать самостоятельно.

## When to Use

Триггеры:
- «разработай», «новый инструмент», «напиши ТЗ», «MoveFrom*», «ТЗ v» — Блоки 0–4
- «ошибка», «баг», «не работает», «упало», «падает», «разберись», «починить», «сломалось» — Блок 7 (hermes-debug)
- «проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если» — Блок 8 (hermes-research)
- Задача с 3+ изменениями конфига/скиллов/инструментов — Блок 6А (QA)

Не для: правок стиля общения (см. `hermes-memory-hygiene`), простой рутины без ТЗ и вариантов.

## Блок 0: ТЗ

Стартовая точка: ТЗ финализировано Opus и получено явное «берём в работу» от Саши. Если ТЗ ещё не готово — сначала создай его (Opus, cronjob), потом возвращайся сюда. Реализация без финального ТЗ и явной команды — запрещена.

## Блок 1: Анализ вариантов

- **Критерии:** токены / безопасность / консистентность / поддерживаемость + специфичные для задачи.
- **Количество:** 2-3 лучших; слабые Opus отсеивает сам.\n- **Подача:** сначала рекомендация с обоснованием → остальные кратко для справки.\n- **Нумерация вариантов — ТОЛЬКО цифры 1/2/3, никогда не A/B/C.** Прецедент 22.07.2026: Саша явно поправил «бриф значит задаем по одному вопросу за раз с вариантами под номерами 1-2-3 (не удобно ABC или abc — так неприемлемо)». Применяется ко всем брифам, опросам, вариантам — в любом контексте, не только в разработке.\n- После выбора: уточняющие вопросы **по одному** → ждать «берём в работу». Саша может прервать уточнения и перейти сразу к работе.

**Completion criterion:** Саша сказал «берём в работу» по конкретному варианту.

## Блок 1А: Планирование *(приоритет — выполнять до Блока 2)*

**Перед любой реализацией Opus составляет пофайловый план:**
- Какие файлы создать / изменить
- Какие функции / классы / методы добавить
- Какие тесты написать (по одному на кейс)
- Промежуточные точки проверки с критерием завершения каждого этапа (по ТЗ если есть, по контексту если нет)

**ТЗ-файл только для задач с Python-кодом.** Для скиллов, конфигов, memory-правок — план Opus в чате (или временный файл), ТЗ-файл не нужен.

**Sonnet проходит промежуточные точки молча** — сверяется с планом сама, без отчётов Саше после каждого этапа.

**Перед «берём в работу»** — проверить ключевые фактические утверждения плана напрямую (`which`, `read_file`): пути к бинарникам, схемы конфигов, версии ПО. Расхождение — стоп, уточнить план.

**Устойчивость к сбою:** для многошаговых планов вести `## Прогресс выполнения` с чекбоксами в файле плана, отмечать `[x]` сразу после каждого шага. Файл синкается — точка возобновления при сбое.

**Completion criterion:** Саша сказал «берём в работу» по пофайловому плану.

## Блок 2: Реализация *(изменён 06.07.2026 — Sonnet пишет код)*

### Модели
**Sonnet-5** — пишет весь код по пофайловому плану Opus. **Opus 4-7** — составляет план и fallback при архитектурном тупике. Провайдер — из дефолтного конфига Hermes, не хардкодить.

### Кто пишет
- **Sonnet-5** — пишет весь код по пофайловому плану Opus *(приоритет над всеми прежними правилами)*
- **Opus 4-7 (fallback)** — только если Sonnet не справилась: архитектурная тупиковая ситуация или повторяющиеся необъяснимые ошибки. Sonnet даёт краткий вывод о причинах → **Саша решает** запускать ли Opus.

**Мелкое отклонение от плана** (≤2 файла, не меняет архитектуру) → Sonnet решает сама.
**Крупное отклонение (архитектурное)** → Sonnet стопится, коротко сообщает причину → Opus делает доплан → Sonnet продолжает.

**Системный/инфраструктурный блокер** (недостающие OS-пакеты, sudo-права) → Sonnet стопится → **Сирень выносит вопрос напрямую Саше** → после «да» выполняет системную правку → создаёт новый cronjob для Sonnet с описанием изменений среды.

### Чеклист перед первой строкой кода
1. ТЗ согласовано (или план в чате) + явное «берём в работу».
2. **Бэкап создан** (см. Блок 5).
3. Пофайловый план Opus существует и согласован.

### Фиксация решения
Opus обновляет ТЗ-файл (если есть): добавляет выбранный вариант + дату старта.

## Блок 3: Тестирование *(изменён 06.07.2026 — Sonnet тестирует)*

**Модели:** Sonnet-5 (тестирование), Opus 4-7 (план тестирования и hotfix-план). Провайдер — из дефолтного конфига Hermes.

- **Тестирует Sonnet-5** по плану тестирования от Opus *(приоритет над прежними правилами)*
- **Мелкий баг** (≤2 файла, очевидная причина) → Sonnet чинит сама (1 попытка)
- **Крупный/архитектурный баг** → Sonnet фиксирует причину → **Саша решает** запускать ли Opus на hotfix-план → Sonnet применяет
- **Готово =** все точки проверки из плана Opus пройдены (✅/❌)
- Застрявший/интерактивный шаг — сообщить Саше что именно нужно, ждать явного «да».
- Статус «completed» на весь план ставит только Саша.

## Блок 4: Документирование

- ТЗ-файл остаётся живым в `TZ/<Tool>/<Tool>_TZ.md` **пока инструмент используется**. Архивация — только когда сам инструмент выведен из эксплуатации, по явному решению Саши.
- **Скилл:** мелкая правка → Opus сам; новый раздел → предлагает Саше.
- **MEMORY и скиллы:** см. скилл `hermes-memory-hygiene` (write-time gate, когда в скилл vs в память).

## Блок 5: Бэкапы и откат

### Когда создаётся
- Opus-задачи: всегда.
- Sonnet-задачи: только если затронут `config.yaml` или `jobs.json`.

### Состав
`config.yaml` + `jobs.json` + `skills/` + `MEMORY.md` + `USER.md` + файлы специфичные для задачи.

### Путь
Linux VM: `~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`.
Для бэкапов отдельных компонентов (unit-файлы, `rclone.conf` и т.п.) — рядом с файлом: `<file>.bak-<purpose>-YYYYMMDD-HHMMSS`.

### Хранение
2 недели, 1 бэкап в день (самый ранний). Self-check чистит автоматически.

### Откат
- **Авария** → Opus откатывает сам немедленно, сообщает Саше.
- **Плановый** → Opus предлагает какой бэкап, ждёт ОК.

## Блок 5Б: Классификация разрешающего сигнала перед side-effect-действием (обязательно)

**Триггер:** любой вызов `write_file`/`patch` на файлы вне `~/.hermes/_Archives/`, любой `cronjob(action='create'|'run')` с реальными side-effects, любой `terminal` с `curl -X POST|PUT|DELETE` к внешним API (Confluence/JIRA/Anywhere/EWS), любой `patch` на файлы в `WorkVault/Hermes-Backlog/TZ/**`.

| Категория | Определение | Разрешает действовать? |
|---|---|---|
| `direct-imperative` | В последнем сообщении Саши есть глагол-императив, ссылающийся именно на это действие: «обнови», «запусти», «делай», «фиксируй», «давай», «поставь», «удали» | ✅ Да |
| `continuation-of-approved-plan` | Действие — явный пункт из согласованного пофайлового плана Opus (Блок 1А), Саша сказал «берём в работу» по этому плану, действие соответствует одному из перечисленных шагов плана дословно | ✅ Да |
| `question-answer` | Саша задал информационный вопрос (где/как/почему/можно ли/что если), модель ответила — само действие «зафиксировать ответ в файле» Сашей не запрошено | ❌ Нет |
| `own-inference` | Модель логически вывела, что «раз X, значит нужно Y» — без явной команды от Саши | ❌ Нет |
| `conditional` | Саша дал условную команду «если X — делай Y», истинность X оценивает сама модель | ❌ Нет |

Если категория ❌ — отдельный turn БЕЗ side-effect-инструментов, текстовый вопрос Саше.

Самореференциальный запрет: факт, созданный самой моделью в этой же сессии предыдущим tool call-ом, НЕ является доказательством истинности условия для последующего действия.

## Блок 6: Эскалация

**Стоп + пишет Саше (даже ночью):**
1. Критическая поломка.
2. Неопределённость в ТЗ, которую нельзя решить самостоятельно.

**Ночью:** сохранить состояние в ТЗ-файл → «жду решения по [вопрос]» в TG → ждать утра.

**Молчит:** рутинные cron без ошибок.

## Блок 6А: QA-проверка перед «Готово» *(сужен 08.07.2026 — не дублирует Блок 1А/3)*

**Важно:** для задач, где Opus уже написал пофайловый план с тестами/точками проверки (Блок 1А), отдельный QA-чеклист через Opus **не нужен** — Sonnet тестирует по уже готовому плану (Блок 3), это и есть проверка «Готово». Дублировать её отдельным Opus-ревью после факта — лишний шаг, обнаружено 08.07.2026 на примере плана `QMD-Search_TZ.md` (план уже содержал proверочные команды и критерии).

**Когда Блок 6А всё ещё применяется:** только для изменений, сделанных **без** предварительного пофайлового плана Opus — то есть точечные правки конфига/скиллов вне обычного цикла ТЗ→план→реализация (например срочный hotfix, ручная правка вне рамок текущей задачи). Если Блок 1А/3 уже пройден — Блок 6А пропускается.

**Процесс (если применяется):**
1. Собрать чек-лист через Opus (`cronjob(repeat=1)`, не `delegate_task` — см. Блок 6Б): корректность изменений, смежный функционал, логические противоречия (особенно память vs конфиг).
2. Исправить ❌ пункты.
3. Повторить (максимум 3 попытки).
4. Все ✅ → короткий отчёт. Остались ❌ после 3 попыток → откат + доклад.

## Блок 6Б: Делегирование субагентов

### Критерий выбора модели

| Задача | Модель |
|---|---|
| Собрать факты: grep, git, конфиги, списки кронов | **Haiku 4-5** |
| Читать одно ТЗ, понять архитектуру, сформулировать рекомендацию — в рамках одного инструмента | **Sonnet-5** |
| Читать несколько ТЗ, интеграционные вопросы, связи между инструментами, новый инструмент | **Opus 4-7** |

**Короткое правило:** Haiku собирает данные → Sonnet-5 анализирует в рамках одного инструмента → Opus решает интеграционные и многоинструментальные задачи.

### Инструмент запуска

**Правило против хардкода (решение Саши 08.07.2026 — переживает переключение Anthropic↔TUTU):**
- **Sonnet-задачи — НЕ передавать `model` вообще.** Sonnet это всегда текущий основной провайдер/модель Hermes (`model.default`/`delegation.model` в `config.yaml`) — эти два поля синхронно обновляются скриптами переключения (`switch_to_sonnet5.sh`, `user_change_delegation_models1.sh`). Если не указывать `model` в `cronjob`/`delegate_task`, система сама берёт актуальное значение — не нужно править скилл при каждом переключении профиля.
- **Opus/Haiku — модель передавать явно** (они намеренно НЕ основная модель), но БЕЗ `provider` (см. Pitfall 23 — провайдер система подставит сама). Конкретные ID (`claude-opus-4-7`, `claude-haiku-4-5`) подтверждены одинаковыми на Anthropic и TUTU (см. `WorkVault/UserManuals/LLM-Migration/README.md`, таблица моделей) — переживают переключение провайдера. Переживут смену **версии** модели (когда выйдет Opus 4.8 и т.п.) — только если кто-то обновит эту таблицу вручную; проверять актуальность раз в несколько недель, не считать вечной истиной.

| Задача | Модель (параметр `model`) | Инструмент | Таймаут |
|---|---|---|---|
| Opus: ТЗ / пофайловый план | `{"model": "claude-opus-4-7"}` (без provider) | `cronjob(repeat=1)` | — |
| Opus: сложная реализация (fallback) | `{"model": "claude-opus-4-7"}` (без provider) | `cronjob(repeat=1)` | — |
| Opus: инфраструктурный анализ | `{"model": "claude-opus-4-7"}` (без provider) | `cronjob(repeat=1)` | — |
| Sonnet: реализация по плану (>5 мин или многофайловая) | **не передавать** `model` — наследует текущий default | `cronjob(repeat=1)` | — |
| Sonnet: короткая задача (<5 мин) | **не передавать** `model` — наследует `delegation.*` | `delegate_task` | 300с |
| Haiku: справочный / терминальный запрос | `{"model": "claude-haiku-4-5"}` (без provider) | `delegate_task` | 120с |

**Никогда не использовать `delegate_task` с Opus** — reasoning_effort=high держит родительский стрим → gateway-зависания ("Stream stale for 180s"). Всегда `cronjob(repeat=1)`.

### Toolsets в кронах (сокращают контекст субагента)

| Задача | enabled_toolsets |
|---|---|
| Opus: ТЗ / план (читает файлы, не запускает код) | `["file", "terminal"]` |
| Sonnet: реализация кода | `["file", "terminal"]` |
| Sonnet: тестирование | `["file", "terminal"]` |
| Исследование / аудит с web | `["file", "terminal", "web"]` |

Не добавлять `web` если не нужен — каждый лишний toolset увеличивает контекст сессии.

### Что обязательно передавать в промпт субагента

1. **Роль и среда** — «Ты Opus/Sonnet на VM hermes-agents.devel.tutu.ru»
2. **Точные абсолютные пути** — `/home/tkachenkoav/...`, не `~/...` (в кронах `~` может не резолвиться предсказуемо)
3. **Полный контент ТЗ или плана** — не ссылку на файл, а текст; субагент не должен делать дополнительные lookup'ы
4. **Граница автономности** — явное правило: «механическое (форматирование, перенос, дозаполнение) — делай сам; семантическое (удаление блока, изменение архитектуры) — СТОП, опиши причину»
5. **Формат отчёта** — «не выводить полный текст файлов, только сводку изменений»
6. **Явные запреты** для безопасности — «не удалять contacts.enc и .env», «не менять security-параметры config.yaml»

### Чего НЕ нужно передавать — и важное уточнение про память (проверено по коду 08.07.2026)

**НЕ дублировать в промпте:** SOUL.md, системный промпт Hermes. Cron-сессии всегда грузят `SOUL.md` (`load_soul_identity=True`) — идентичность агента субагент получает автоматически.

**НО: cron-сессии НЕ получают MEMORY и USER PROFILE вообще.** Проверено по коду (`cron/scheduler.py`, флаг `skip_memory=True` с комментарием «Cron system prompts would corrupt user representations») — это намеренное архитектурное решение Hermes, не баг и не то, что можно включить конфигом. Субагент через `cronjob` не видит ни одной записи из MEMORY/USER PROFILE, даже если они содержат критичный для задачи факт (например «Саша сейчас на Anthropic, не TUTU» или правило про формат имён файлов WorkVault).

**Практическое следствие:** если факт из MEMORY/USER PROFILE нужен субагенту для корректного выполнения — **передавать его явно в промпте**, не полагаться, что «он и так знает». Особенно критично для: текущего активного провайдера/модели, стабильных конвенций именования (например «латиница-only в WorkVault»), организационных фактов (кто есть кто), правил из этого самого скилла (`hermes-feature`), если задача их использует. Секции `## Контекст и уже принятые решения` в промптах установочных планов (см. пример `QMD-Search`) — это правильный паттерн именно по этой причине.

`delegate_task`-субагенты (не cron) — эта проблема не подтверждена по коду отдельно, безопаснее считать то же правило действующим по умолчанию, пока не проверено обратное.

### Бэкап перед запуском субагента

Sonnet-задачи: бэкап если затронуты `config.yaml` / `jobs.json`.
Opus-задачи: бэкап всегда (`~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`).

## Блок 6В: Диагностика перед починкой — обязательный паттерн

Когда Саша говорит «что-то не работает» / «не заполняется» / «поиск не работает»: **не чинить сразу**. Правильный порядок:

1. **Opus-крон только на диагностику** (`enabled_toolsets: ["file", "terminal"]`, явный запрет «только читай, никаких правок файлов») → собирает реальные данные командами, выявляет root cause, предлагает план П.1…П.N с приоритетами и критериями приёмки.
2. **Саша просматривает план**, при необходимости корректирует.
3. **Sonnet-крон реализует** по плану Opus — пункт за пунктом, тесты после каждого.

Opus сохраняет план в `_fix_plan_YYYYMMDD.md` рядом с инструментом → удалить после выполнения всех пунктов.

**Почему важно:** без диагностики Sonnet может починить симптом, не причину. Прецедент 22.07.2026 (MOFS contacts = []): очевидная причина — «нет раздела Участники». Opus-диагностика выявила 4 отдельные проблемы (namespace-package, plain-text заголовки, стоп-лист, хук) — каждая с отдельным фиксом, и каждая не была бы найдена без сбора данных по реальным файлам.

## Блок 7: Диагностика и отладка

**Общий метод:** см. скилл `systematic-debugging` (4 фазы: root cause → pattern → hypothesis → fix).

**Наша специфика:**
- Модель: Sonnet-5 (не Haiku, не Opus — если не нужна архитектурная правка).
- Мелкий баг (≤2 файла, очевидная причина) → Sonnet чинит сама (1 попытка).
- Крупный/архитектурный баг → Sonnet стопится → Саша решает запускать ли Opus → Sonnet применяет план.
- Системный блокер (пакеты, sudo) → Сирень выносит вопрос Саше напрямую (не Opus).
- Эскалация к Opus: root cause в архитектуре, не воспроизвелось за 2 попытки.
- Эскалация к Саше: данные могут быть повреждены, production down.

**Hermes-специфичные питфоллы отладки:**
- `routing:` в `config.yaml` — мёртвая секция, код не читает.
- `hermes skills list` не видит скилл — проверить `version` и `author` в frontmatter.
- `cronjob(action='update')` не сбрасывает `no_agent` — менять в `jobs.json` напрямую.

## Блок 7А: Двухэтапный Opus-анализ перед изменением конфигурации

Применять при: изменение systemd-юнитов, rclone-конфигов, синхронизации, инфраструктурных настроек.

**Паттерн:**
1. **Opus-крон №1** — только читает файлы, оценивает риски, **строит план реализации**, даёт рекомендации.
2. Sonnet пересказывает результат Саше, получает подтверждение.
3. **Sonnet-5-крон №2** — реализует по согласованному плану Opus.

**Почему не сразу реализовывать:** инфраструктурные изменения (systemd, rclone, cron) могут иметь неочевидные риски (race condition, `--size-only` пропускает изменения). Opus может найти питфоллы, которые меняют план.

**Формат промпта для анализа:** «оцени риски → вывод (безопасно/требует доработки/не рекомендую) → ТЗ если применимо».

## Блок 8: Исследования и анализ (hermes-research)

Применять при: нужно собрать данные, найти паттерн, оценить варианты — **без изменений кода**.
Триггеры: *«проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если»*.
**Модель — по критерию из Блока 6Б:** Haiku собирает данные (grep, конфиги, git), Sonnet-5 анализирует в рамках одного инструмента, Opus — интеграционные вопросы и несколько инструментов.

**Алгоритм:** Scope → Сбор (`session_search` 1-3 слова FTS5, параллельные запросы; файлы через grep; API только чтение) → Анализ (таблица, выводы отдельно) → Рекомендации (2-3 варианта с оценкой).

**НЕ делать:** не менять код/конфиги/скиллы, не делать выводы без данных, не запускать API без ОК Саши.

## Common Pitfalls

Компактный список. Расширенные разборы с полным текстом инцидентов — `references/pitfalls-incidents.md` (номера совпадают). Родственные подтемы — в тематических references (пометки в скобках).

1. **`hermes skills list` не видит новый скилл** — обязательные поля frontmatter: `name`, `description`, `version`, `author`, `tags`, `platforms: [windows, linux, macos]` (не `[all]` — не работает). Если не помогло — вручную добавить запись в `.usage.json` (шаблон копирует поля с другого скилла: `use_count/view_count/patch_count=0`, `state=active`, `pinned=false`), затем рестарт gateway.

2. **Бэкап обязателен до первой строки кода** — Opus создаёт бэкап в `_Archives/hermes-backup-YYYYMMDD-HHMMSS/` перед любыми изменениями Opus-уровня.

3. **Правка security-sensitive `config.yaml`** — allowlist-ключи (`telegram.*`,`delegation.*`,`fallback_providers`) через `hermes config set`; ключи вне allowlist (`personas.*`, `system_prompt`) — только `execute_code` с Python `open/replace/write` (`patch`/`write_file` блокирует). Обязательно: бэкап, `assert old in content`, `yaml.safe_load` после, diff двух связанных файлов если правится один смысловой блок в двух местах. → `references/pitfalls-incidents.md#pitfall-3`

4. **Секция `routing:` в `config.yaml` не работает** — код Hermes её не читает. Молча игнорируется. Для реальной маршрутизации — плагин/хук или правила в MEMORY.md.

5. **Рестарт gateway изнутри заблокирован** — единственный способ: `bash ~/.hermes/scripts/restart_gateway_MANUAL_ONLY.sh` из внешнего шелла. **ЗАПРЕЩЕНО** ставить no_agent cron с этим скриптом изнутри gateway — SIGTERM-петля (инцидент 26.06.2026). (config-qa.md)

6. **`cronjob(action='update')` не сбрасывает `no_agent`** — прямая правка `~/.local/share/hermes/cron/jobs.json`. (cron-and-scheduler.md)

7. **`cronjob(action='run')` разрушает one-shot джоб** — не использовать как «запустить пораньше». Для one-shot: `schedule` относительной строкой (`"4m"`,`"every 2h"`), не абсолютным ISO-таймстампом; неверное время исправлять через `update`/`remove`+`create`. `execution_success: false` в ответе `run` — ложноотрицательный, факт результата читать из `~/.hermes/cron/output/<job_id>/*.md`. → `references/pitfalls-incidents.md#pitfall-7`

8. **`cronjob(action='create')` со `script`** — только имя файла в `~/.hermes/scripts/`, без путей и `&&`, без симлинков. (cron-and-scheduler.md)

9. **`[SILENT]` guard: last-line-equals** — Variant A с 05.07.2026, `_classify_silent_marker` в `cron/scheduler.py`. Три ветки: `deliver`/`silent_clean`/`silent_dirty`. (cron-and-scheduler.md)

10. **«Слепая зона» Sonnet при ожидании крона** — читать `~/.hermes/cron/output/<job_id>/*.md` вручную, не ждать TG-доставку. (cron-and-scheduler.md)

11. **Thread ID топиков не в sessions.db** — источник правды `gateway.log`, поле `reply_to_id`. Топики Sirene Workspace (-1004300127777): General=1, Tools=3, Hermes DEV=4, WorkVault=5, Backlog=6, Monitoring=7, Personal=8. (cron-and-scheduler.md)

12. **rclone `--size-only`** пропускает изменения одного размера (правки `.md`, ре-шифрование `contacts.enc`). Убрать — по умолчанию `size+mtime` надёжнее. (movefrom-and-anywhere.md)

13. **Триггер синка после USERTOOLS** — `subprocess.run(["systemctl","--user","start","--no-block","owncloud-sync.service"], check=False, timeout=5)`. (movefrom-and-anywhere.md)

14. **AnywhereContacts PII** — `mask_contact(c)` обязателен перед любым выводом контакта; `store.read()` возвращает сырые данные намеренно. Общий lock `WorkVault/Contacts/.contacts.enc.lock`. (movefrom-and-anywhere.md)

15. **MoveFrom*/FF API отклонения** — реальный API может не совпасть с ТЗ; делать живой запрос **перед реализацией**, фиксировать отклонение в отчёте Opus (не переписывать ТЗ). Backfill, дедуп, rate-limit, reconciliation — детали в references. (movefrom-and-anywhere.md)

16. **Реальный API vs ТЗ — правило открытых вопросов** — если что-то в ТЗ неоднозначно, не «принимать решение по умолчанию»; выносить в «Открытые вопросы Саше» с рекомендацией и альтернативой. (tz-workflow.md)

17. **`anywhere_contacts.store.ContactStore` не имеет `add_alias`** — ~~метод есть только у in-memory тестового `ac_client` из `AggregateFromMeetings`~~. **ИСПРАВЛЕНО 13.07.2026:** официальный `add_alias()` добавлен в `ContactStore` (case-insensitive дедуп, `KeyError` на неизвестный login, покрыт 5 тестами `test_add_alias.py`). `OrgLookup/md_writer.py::ContactStoreAdapter` — ранее самодельная реализация поверх `update_contact` — теперь тонко делегирует в официальный метод (обратная совместимость сигнатуры сохранена). Editable-install AC в чужой venv может упасть flat-layout — читать пакет через `sys.path.insert`, не чинить чужой `pyproject.toml`. → `references/pitfalls-incidents.md#pitfall-17`

18. **EWS `resolve_names()` иногда кладёт объект-исключение прямо в список результатов** вместо raise (`ErrorNameResolutionNoResults`) — распаковка `for mailbox, contact in results` падает `TypeError`; фильтровать `isinstance(item, Exception)` перед unpacking. Переиспользовать `MeetingScheduler.exchange_client.get_account()/check_vpn()` для любого нового EWS-инструмента, не писать свою авторизацию. **ПРОВЕРЕНО 13.07.2026:** `OrgLookup/orglookup/ews_client.py::resolve_names()` уже содержал эту защиту, но не был покрыт тестом — добавлены 4 теста (`test_ews_client.py`): исключение в списке, все элементы — исключения, raise вместо list, смешанный случай None+исключение. (movefrom-and-anywhere.md)

19. **Рекомендации Opus-аудита по конфигу** — перепроверять контекст находки вручную перед действием. Пример: разные `require_mention` в разных платформенных секциях — не дубли. (config-qa.md)

20. **Апгрейд upstream hermes-agent** — использовать `~/hermes-workspace/upstream/` (pinned-version.txt, changelog.md, rollback-history.txt, `upstream_update.sh`, `upstream_rollback.sh`); обновить Windows-пути в скриптах перед первым использованием. Три ключевых урока (git status до pull, проверка что upstream не решил ту же проблему на cherry-pick конфликте, тест-триаж через baseline-diff) — в `references/upstream-cutover-procedure.md`. → `references/pitfalls-incidents.md#pitfall-20`

21. **Аудит списка кронов** — one-shot paused job'ы под уже закрытые ТЗ = забытые артефакты, предлагать Саше удалить, не удалять молча. (cron-and-scheduler.md)

22. **Форсированный пересбор summary/transcript (MoveFromFF)** — переименовать файл (`... - summary.md_old`), `reconcile_registry()` сам сбросит запись в pending; запуск `--mode manual --from-date --to-date`. Побочный эффект: writer атомарен — transcript перезапишется тоже. (movefrom-and-anywhere.md)

23. **Никогда не указывать `provider` вручную в `cronjob(model={...})`** — система сама подставит текущий активный провайдер; ручной hardcode устаревает при переключении Anthropic↔TUTU и роняет крон `Unknown provider`. **Повторилось дважды несмотря на правило** — перед вызовом `cronjob(create/update)` явно перечитать литерал `model` и убедиться что там ТОЛЬКО ключ `"model"`. Для Sonnet-задач `model` не передавать вообще (наследует из `delegation.model`). → `references/pitfalls-incidents.md#pitfall-23`

24. **Cron-субагенты НЕ получают MEMORY/USER PROFILE** (`skip_memory=True` в `cron/scheduler.py`, намеренно — «cron system prompts would corrupt user representations»). SOUL.md грузится (`load_soul_identity=True`), MEMORY/USER PROFILE — нет, ни при каких условиях. Критичные факты (провайдер, конвенции именования, кто есть кто) — передавать явно в промпт cronjob, не полагаться что субагент их «и так знает». Обнаружено 08.07.2026 при ревизии Блока 6Б.

25. **`npm install -g` пакета с native-биндингами (llama.cpp, node-llama-cpp, better-sqlite3)** может требовать сборки из исходников → нужны `cmake` + `gcc-c++` (RHEL/Alma, НЕ `g++`) или `cmake`+`g++` (Debian). Диагностика: postinstall/node-gyp упоминает `cmake`/`CMakeLists`. Это системный блокер — эскалация к Саше напрямую (Блок 2), не к Opus. → `references/pitfalls-incidents.md#pitfall-25`

26. **«N/N тестов зелёных» не гарантирует корректности write-операций во внешнюю систему, если тесты мокают именно ту функцию, где баг** — прецедент 10.07.2026 ProtocolFromSummary. После отчёта субагента о идемпотентности/republish — независимый прямой GET/`curl` к API (Confluence/JIRA) как единственное доказательство; самоотчёт о тестах доказательством не является. → `references/pitfalls-incidents.md#pitfall-26`

27. **Тройной цикл Opus(план)→Sonnet(код)→Opus(архитектурный ревью после реального бага)** — паттерн для инструментов с side-effects. При баге пилота: (1) документируем баг с пруфами; (2) Opus-cron на ревью всего ТЗ с описанием бага + поиск похожих проблем + вопросы для брифа по edge-cases; (3) бриф в pm-briefing формате; (4) второй Opus-cron дорабатывает ТЗ (не код). Реализация — отдельный третий шаг. → `references/pitfalls-incidents.md#pitfall-27`

28. **Эмпирическая проверка через `delegate_task` ДО фиксации архитектурного решения в брифе** — если вопрос зависит от непроверенного факта о поведении внешней системы (переживёт ли X сохранение через Y), не принимать рассуждение Opus как готовый ответ; запустить `delegate_task` с реальным API-тестом на безопасной сущности + обязательным откатом, потом формулировать рекомендацию. Прецедент: Confluence вырезает HTML-комментарии и `data-*` уже при PUT. → `references/pitfalls-incidents.md#pitfall-28`

29. **Открытый риск «не проверено на ручном веб-редактировании» можно закрыть по факту сессии** — если пользователь по ходу работы упомянул, что он «поправил»/«отредактировал» ранее опубликованный контент за которым числится такой риск, сразу перепроверить через GET/API-запрос, не откладывать; обновить reference с результатом, не оставлять открытым риск, который уже закрыт по факту. → `references/pitfalls-incidents.md#pitfall-29`

30. **HTML-теги (`<a href>`) не рендерятся при доставке через `no_agent` cron script + `deliver='telegram:...'`** — приходят как сырой текст. Использовать Markdown-ссылки `[текст](url)` для этого канала доставки (см. `references/cron-and-scheduler.md`). Не путать с доставкой через `hermes send`/gateway — там формат может отличаться, проверять отдельно. **ПРОВЕРЕНО 13.07.2026:** `ProtocolFromSummary/notifier.py::format_notification_markdown()` — production-путь (используется в `scripts/notify_pending.py`) уже полностью на Markdown; старая `format_notification()` (HTML) сохранена только для обратной совместимости старых тестов, не вызывается в проде. Добавлено 5 тестов на Markdown-формат (`test_format_notification_markdown_*`, `test_format_copy_notification_*`, `test_format_export_notification_*`) — раньше тестировалась только устаревшая HTML-версия.

31. **Opus во время bug-fix может незаметно добавить НОВОЕ пользовательское поведение** (визуальный индикатор, префикс, формат сообщения), которого не заказывали, и подать как часть фикса. Прецедент: префикс `♻️ (обновление)` в уведомлении о republish. При формулировании фикса отделять «устранение бага» (делать) от «дополнительный UX-элемент» (выносить отдельным пунктом «предлагаю добавить X — ок?», не в тот же патч). → `references/pitfalls-incidents.md#pitfall-31`

32. **Многораундовый бриф — пользователь может ослаблять/упрощать собственные же рекомендации Opus, и это норма.** Прецедент ProtocolFromSummary Q-1: Opus предложил компромиссный вар.3 (anchor+`role`), Саша выбрал вар.1 (anchor без `role`), обосновав доводом, не бывшим в вариантах. Зафиксировать выбор + его собственное обоснование как есть, передать следующему job явным текстом; не подгонять задним числом. → `references/pitfalls-incidents.md#pitfall-32`

33. **Полный цикл Opus(план)→Sonnet(код)→Opus(ревью-баг)→бриф→Opus(ТЗ-доработка)→Sonnet(финал)** — устойчивый паттерн для инструмента с внешними side-effects, может занять весь день с несколькими волнами. Каждая волна = явная semver ТЗ (0.1→...→1.0→1.1) + `last-section-added` в frontmatter. Не пропускать архитектурное ревью после первого реального теста — там ловятся баги, которых нет в мок-юнит-тестах (Pitfall 26). Волна брифа — 2-8 вопросов, не одним списком. → `references/pitfalls-incidents.md#pitfall-33`

34. **«Сделай чтоб ты сама могла рассказать про возможности инструмента» — правильный артефакт компаньон-скилл, не запись в MEMORY.** MEMORY — факты о пользователе/среде, не описания инструментов (раздувает лимит, не масштабируется). Паттерн: class-level skill (пример `about_usr_skills`) с режимами/механизмами инструмента + ссылка на `<Tool>_TZ.md`. Создавать после того как ТЗ = `active` (не `draft`) — иначе переписывать вслед за волнами брифа. → `references/pitfalls-incidents.md#pitfall-34`

35. **Финальный шаг доставки, отложенный на «сделаю сама после отчёта субагента», выполнить первым действием сразу по получении отчёта — не откладывать ради параллельных задач того же хода** (создание скилла, чистка памяти, уточнения). Прецедент: отправка TG-уведомлений о 3 опубликованных встречах отложена → «ты нарушила все правила». Если объективно нужна пауза (cron ещё не сработал) — сказать прямо, «готово»/«отправлено» не заявлять до подтверждения через `last_run_at`. → `references/pitfalls-incidents.md#pitfall-35`

36. **Несколько прод-багов подряд на одних внешних страницах/сущностях — фиксы последовательно, не параллельными Sonnet-джобами.** Иначе два PUT со stale-версией страницы = 409 conflict, либо один фикс перезапишет другой. Диагностика (чтение) может быть параллельной, реальные PUT — последовательно (или одним объединённым job на все баги). Если неочевидно можно ли параллельно — спросить пользователя. → `references/pitfalls-incidents.md#pitfall-36`

37. **Локальный лимит имени файла (XFS 255 байт) недостаточен, если файл синкается наружу (ownCloud/Nextcloud WebDAV)** — у внешней системы свой более строгий и нестабильный лимит, брать по МЕНЬШЕМУ порогу, эмпирически измерять на конкретном сервере (не по документации). Техника: бинарный поиск `rclone copyto` с именами нарастающей байтовой длины в `_test/`, затем `rclone purge`. Граница может «плавать» → закладывать 1.5-2× запаса. Уже созданные слишком длинные файлы найти, пометить в реестре pending, пересоздать — правка константы кода их не чинит. → `references/pitfalls-incidents.md#pitfall-37`

59. **Расширение одноразового Opus cronjob'а до его срабатывания** — если пользователь даёт уточнение к уже поставленной ТЗ/реализационной задаче, а `cronjob(action='list')` показывает `last_run_at: null` у нужного job'а, ещё есть окно: `cronjob(action='update', job_id=..., prompt=<полный переписанный промпт с добавленным требованием>)` вместо создания второго job'а. 60. **Жёсткий пользовательский приоритет между несколькими инструментами одного семейства («сначала A, потом B») — обязательный STOP-гейт в промпте субагента, не просто порядок шагов плана.** Прописывать явным пунктом: «полный regression первого инструмента (100% тестов + baseline-diff пуст) должен пройти, ПРЕЖДЕ чем субагент вообще притронется к файлам второго; если А не проходит — не начинай Б, отчитайся о поломке». Не полагаться, что порядок шагов ТЗ сам по себе это гарантирует — субагент может решить продолжить «чтобы не терять время». Прецедент 16.07.2026: EntityRegistry — ProtocolFromSummary (PFS) первым, TaskRefresh вторым.

66. **Расширение aliases в entities.json триггерит публикацию старых встреч через PFS** — добавление нового alias расширяет ROUTES PFS. Встречи из архива, ранее не матчившиеся ни на один маршрут, становятся «новыми» для реестра PFS → `process_pending` публикует их. Guard: `CUTOVER_DATE = date(2026, 7, 10)` в `pipeline.py` — `process_pending` пропускает встречи с `meeting_date < CUTOVER_DATE`. Реактивный фикс: 42 записи → `historical_no_reload: true`. Прецедент 22.07.2026: добавление aliases в рамках брифа MOFS → 42 встречи Sep 2025 – Jun 2026 опубликованы без команды. → `references/pitfalls-incidents.md`\n\n61. **Параллельные Opus/Sonnet cron-задачи, правящие один и тот же файл (SKILL.md/reference), дают `patch`-предупреждение `"_warning": "... was modified by sibling subagent ... but this agent never read it"`.** Всегда перечитывать файл целиком (`read_file`) перед повторной правкой в этом случае, не полагаться на версию контента из своего контекста. Частый исход — дублирующийся блок (обе стороны добавили похожий раздел с разных ракурсов); оставлять более полную/интегрированную версию, убирать свой дубль, не обе версии.

62. **Фикс апстрим-бага, сделанный Opus-кроном на отдельной feature-ветке форка, не работает в бою сам по себе** — это два разных шага: (1) коммит+пуш в ветку форка (готовит патч для будущего PR), (2) `git cherry-pick -x <sha>` этого коммита на нашу реальную рабочую ветку (`_test-cutover` или её аналог) — только после этого код физически меняется на диске, который читает боевой процесс. После cherry-pick — обязательно перезапустить прогон релевантных тестов ещё раз на своей ветке (не доверять «уже прогнано Opus'ом на его ветке» — контекст может отличаться), и обязательно ручной рестарт gateway (агент не может рестартить себя сам, см. Pitfall 5) — без рестарта пофикшенный код просто лежит в файле, но не выполняется. Отдельно: `gh auth` (авторизация GitHub CLI) НЕ переживает между cron-сессиями — даже если PR успешно создавался в одной интерактивной сессии с токеном, следующий cron-джоб стартует с чистым окружением и `gh auth status` даёт «not logged in»; для авто-PR из крона нужно либо явно передать токен под нестандартным именем в `.env` (см. Pitfall про `no_agent`-скрипты и провайдерские ключи в `hermes-gateway-setup`), либо заранее закладывать, что PR открывает пользователь вручную по готовой запушенной ветке. → `references/pitfalls-incidents.md#pitfall-62`

63. **`pip install -e .` с `[tool.setuptools.packages.find] include = ["pkg*"]` создаёт namespace-package** — `__init__.py` не выполняется, публичный API (`from pkg import func`) падает с `ImportError`. Симптомы: `pkg.__file__ is None`, `type(pkg.__path__).__name__ == '_NamespacePath'`. Фикс: заменить на `[tool.setuptools] packages = ["pkg"]` (явный список без find-эвристики) + `pip uninstall -y pkg && pip install -e .`. Диагноз одной командой: `python3 -c "import pkg; print(pkg.__file__)"` — если None, сломано. Прецедент: mofs_index 21.07.2026.

64. **Contacts из тела summary — три формата заголовков, все должны поддерживаться.** MoveFromFF в разных версиях генерировал три формата раздела «Участники»: `## Участники:` (markdown H2), `**Участники:**` (bold), `Участники:` (plain-text без разметки). Если contacts = [] у части встреч — диагностировать формат: `grep "Участники" summary.md`. В `text_extractor.py` должны быть три паттерна: `_SECTION_HEADER`, `_SECTION_BOLD`, `_SECTION_PLAIN`. Ограничение `_SECTION_PLAIN`: паттерн `^([А-ЯЁA-Z][А-Яа-яЁёA-Za-z ]{2,30}):\s*$` требует заглавной буквы + 2-30 символов + двоеточие без текста после — чтобы не съедать строки-исполнители вида `Скворцова Диана: задача`. Прецедент 22.07.2026: только после добавления `_SECTION_PLAIN` contacts выросли с 37/61 до 59/61.

65. **Rematch contacts по старому архиву без раздела «Участники» — regex не помогает, нужен NER.** Если 90%+ старых файлов не имеют явного раздела «Участники» (другой формат саммари: `## Bullet points`, `## Action Items`), contacts из тела не извлечь без LLM. Архитектура: S1 (regex email-header транскрипта, ~85% бесплатно) → S2 (спикер-метки транскрипта) → S3 (Haiku по телу summary, ~150 файлов, $0.5). Подкоманда к существующему CLI, не отдельный инструмент. Прецедент 22.07.2026: 494 старых встречи до июля — ТЗ `appendix_ner_archive_contacts_TZ.md`.

66. **Диагностика реальных данных обязательна перед финальным apply массового прогона.** Когда пользователь говорит «не заполняется X» — правильный порядок: (1) Opus-крон только на диагностику (запрет правок в промпте), собирает данные с диска, выявляет root cause; (2) план П.1…П.N с приоритетами; (3) Sonnet реализует по плану. Без диагностики легко починить симптом, не причину. Прецедент 22.07.2026 (MOFS contacts=[]): очевидная причина была «нет раздела Участники» — диагностика выявила 4 отдельные проблемы (namespace-package, plain-text заголовки, стоп-лист unmatched, хук). Каждая независимая, каждая требовала своего фикса.
