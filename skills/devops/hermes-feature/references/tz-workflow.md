# ТЗ workflow — детали (Блок 0)

Полный набор правил по ТЗ. Компактная выжимка — в SKILL.md.
Родственный скилл: `tz-workflow` (общее правило именования/архивации файлов ТЗ).

## Кто пишет и когда

- ТЗ пишет **Opus**, инициирует только Саша явным запросом.
- **Согласование ТЗ ≠ команда на реализацию.** Даже если ТЗ полностью готово и вопросы закрыты — миграция/кодинг/любые физические изменения стартуют только по отдельной явной команде Саши («ок, берём в работу»), не автоматически после согласования текста.
- Неопределённость в процессе: Opus **стопится**, дополняет ТЗ предложением, ждёт ОК.

## Хранение

- Один живой master-файл на инструмент → `WorkVault/Hermes-Backlog/TZ/<Tool>/<Tool>_TZ.md` (версия и дата — только в frontmatter, не в имени файла).
- Точечная доработка существующего инструмента → секция в master-файле, НЕ отдельный файл (не распыляться по документам одного инструмента).
- Независимая от инструмента задача → `TZ/_misc/TZ-<topic>-<YYYYMMDD>.md` (латиница).
- Полные правила именования/архивации → `WorkVault/Hermes-Backlog/TZ/_TZ-WORKFLOW-RULES.md`.
- Обязательные разделы ТЗ: **Цель / Контекст / Шаги / Критерии успеха / Что НЕ трогать**.

## Правило отчёта о ТЗ в чат (03.07.2026)

Саша читает файлы сам — не дублировать содержимое ТЗ в Telegram. После любой работы над ТЗ (создание/ревизия/финализация) отвечать **коротко**:

- Что именно поменялось (буллеты, не абзацы)
- Что требуется от Саши (решение / вопрос / подтверждение)
- НЕ выводить полный текст файла ТЗ в чат — он всегда может открыть файл сам

**Исключение:** если по открытому вопросу Opus дал только вывод/рекомендацию без обоснования и Саша просит «дай контекст почему» — по каждому вопросу дать мотив коротким абзацем (проблема → почему рекомендация решает её → что теряется при альтернативе). Разворачивать обоснование только когда прямо спросили, не заранее.

## Паттерн «Открытые вопросы» в ТЗ

Когда Opus сам принял решение по неоднозначному месту ТЗ (а не получил его от Саши) — выносить отдельным разделом **«Открытые вопросы Саше»** в конец файла: вопрос + своя рекомендация с обоснованием + альтернатива, НЕ выбирать самому «по умолчанию».

После того как Саша дал решения — заменить раздел на **«Решения (утверждено ДАТА)»**, зафиксировать как факты без повторения отклонённых альтернатив.

**Действует и при делегировании** (cronjob/delegate_task к Opus): в промпте никогда не писать «прими решение сам» по неоднозначному пункту; каждый открытый пункт ждёт явного ответа Саши поштучно, даже если решение кажется очевидным. Саша подтверждает пункты **поштучно** (может утвердить один и попросить контекст по другому) — не считать весь список решённым, пока по каждому не пришёл явный ответ.

## Брифование перед ТЗ (для сложных доработок)

Когда задача затрагивает безопасность, архитектуру хранения, взаимодействие с другими инструментами или пользовательский интерфейс — **перед написанием ТЗ провести бриф**:

1. Собрать все открытые вопросы по блокам (Хранение / Отображение / Фильтрация / Интеграции / Синхронизация)
2. Вывести полный список вопросов одним сообщением: «Всего N вопросов по X блокам. С какого начинаем?»
3. Идти по блокам последовательно, задавать вопросы по одному
4. Предлагать варианты (А/Б/В), а не открытые вопросы — быстрее согласовывается
5. После каждого блока — «Итог блока N: ...» с зафиксированными решениями
6. Только после завершения брифа → запускать Opus на написание ТЗ

**Триггеры для брифа:** безопасность/персданные, новый UI/TG-команды, взаимодействие 2+ инструментов, архитектурный выбор с несколькими равнозначными вариантами.

## Universal open-question protocol (05.07.2026)

Правило распространено на ВСЕ диалоги, не только брифы перед ТЗ: во всех разговорах с открытыми вопросами — сначала полный список вопросов, потом задавать по одному; каждый вопрос — краткий контекст + 1-2 лучших варианта с явной рекомендацией какой лучше; вопросы и варианты — по номерам. Зафиксировано в USER PROFILE как постоянное правило. Детали и питфоллы протокола — см. скилл `hermes-memory-hygiene` → «Universal open-question protocol».

## Хранение материалов брифа

После согласования краткое summary решений входит в ТЗ (секция «Решения брифа» или в шапку master TZ). Черновые материалы брифа — исходная переписка, дампы, research, промежуточные варианты — хранятся **в структуре инструмента** (`USERTOOLS/<Tool>/briefs/` или `WorkVault/Tools/<Tool>/briefs/`), НЕ в `TZ/<Tool>/`. `TZ/<Tool>/` содержит только сам документ ТЗ и его модули/pm-журнал. См. `_TZ-WORKFLOW-RULES.md` §«TZ vs tool runtime/working data».

## QA ТЗ перед разработкой

Промпт для Opus: «Ты senior технический аналитик. Прочитай файлы ТЗ. Ответь ТОЛЬКО: ✅ ТЗ готово к разработке [список проверенного] ИЛИ ❌ Требуются уточнения: [конкретные вопросы].»

Типичные проблемы в ТЗ: противоречия между файлами, неотражённые реальные данные API, platform-specific артефакты (`.bat` на запланированном Linux), неполный алгоритм для edge cases, несогласованные enum-значения.

## Жизненный цикл ТЗ-файла

ТЗ-файл остаётся живым в `TZ/<Tool>/<Tool>_TZ.md` **пока инструмент используется** — реализация конкретной доработки НЕ повод архивировать ТЗ, оно описывает текущее состояние инструмента и должно быть под рукой в WorkVault всегда. Архивация в `WorkVault_backup/` — только когда сам инструмент выведен из эксплуатации/удалён, и только по явному решению Саши (без автотаймера).

Реальный API может не совпасть с документацией/предположениями в ТЗ — фиксировать отклонение в **финальном отчёте Opus**, не переписывая сам ТЗ-файл. Живой запрос к API делать **перед реализацией** (блокер для ТЗ, не после). Пример: FF `extended_sections { title items text }` → реально `{ title content }`. Opus должен: (1) записать отклонение в отчёт; (2) реализовать по реальной схеме; (3) оставить опциональные поля из ТЗ для backward-compat с моками, если это разумно.

## План реализации как отдельный артефакт (pm/IMPLEMENTATION_PLAN.md)

Для инструментов с несколькими модулями (не 1 файл) — после того как ТЗ приведено к стандарту и открытые вопросы закрыты Сашей, создавать отдельный `TZ/<Tool>/pm/IMPLEMENTATION_PLAN.md` (Opus): порядок модулей с зависимостями и оценкой часов, файловая структура, milestones с проверяемым результатом на каждом, тестовый план (что мокать, конкретные fixture/кейсы), явный блок-предупреждение «не стартуем без ответов на открытые вопросы + явного „берём в работу“». Это не замена ТЗ — ТЗ описывает *что и зачем*, план — *в каком порядке и как проверить*. Пример: bk-098 ExchangeOrgLookup, 06.07.2026 — план на 7 модулей с 6 milestones и 7 test-фикстурами, реализация по нему прошла без дополнительных вопросов к исполнителю.

**Разделение труда, которое сработало:** один разовый Opus-крон и на ревизию ТЗ, и на план реализации сразу (одна задача, оба выхода) — экономит раунд по сравнению с двумя отдельными кронами, если оба шага небольшие. Разовый крон получает задачу с явными пунктами 1 (ТЗ) и 2 (план) и форматом ответа для обоих.

**Как передавать план исполнителю кода:** промпт исполнителя (Opus или Sonnet — см. Блок 2 SKILL.md про кто пишет и override) должен явно перечислить: (1) какие открытые вопросы уже закрыты и как именно (не заставлять исполнителя лезть в историю переписки — продублировать решения текстом в промпте); (2) путь к плану и ТЗ для деталей; (3) явный запрет придумывать себе разрешение на нерешённые пункты; (4) формат финального отчёта — чеклист по milestones плана, не произвольный текст.
