# Границы постановки роли и сверка write-set

Always-on, when composing a role prompt (architect/reviewer/executor) in the direct `codex exec` invoke path.

## READ-ONLY + единственный файл отчёта

- Объявлять в промпте READ-ONLY-границу и ЕДИНСТВЕННЫЙ разрешённый файл отчёта (например «править можно ТОЛЬКО out/X.md»).
- Иначе роль вязнет в противоречии «сохрани отчёт / ничего не меняй» и тратит ходы на его разрешение — снимать это однозначной фразой заранее.
- Для архитектора/ревизора: «Ничего сам не создавай/не правишь — только анализ, вердикт, варианты, план адресных правок для исполнителя».

## Write-set сверка через sha256 (не доверять self-report)

- Зафиксировать sha256 ВСЕХ файлов write-set до запуска исполнителя и после в `evidence/*-hashes.log` (одна команда до `codex exec` и одна после в той же shell-цепочке).
- Требовать от независимой REV самостоятельного пересчёта hashes против диска, а не зачитывания отчёта исполнителя.
- Правило-фильтр: изменились ровно те файлы write-set, которые заявлены; ядро и `integrations/.../__init__.py`/plugin не тронуты; `b3_control.py`-подобные «заглушки для видимости» отсутствуют.

## Честная незавершённость против заглушки

- Если роль честно сообщает, что замечание не закрыть без core-патча/новой архитектуры — принимать как незавершённость (флаг BC/блокер) и поднимать владельцу.
- НЕ подталкивать роль к созданию пустой реализации ради закрытия: фиктивная реализация хуже честного FAIL. Билд может явно сказать «ENV-03 остаётся FAIL; б3_control не реализован».

## Статическая REV как закрытие адресного замечания

- Статическую REV можно принять как закрытие адресного замечания, когда дефект установлен по коду (пропущенная операция durability и т.п.), даже без запуска pytest/live.
- Но вердикт ограничить закрытием ИМЕННО этого замечания; переаттестации всей системы (ENV-03, адмиссия, managed proof) статическая REV не даёт и не должна их подразумевать.
- Подтверждение фиксации: несколько независимых прогонов REV на одну дельту — норма; каждый возвращает автора к точному шагу, без перепроектирования.

## Recheck против повторяющегося сбоя роли

- Три подряд сбоя одной фазы/роли = стоп (запрет слепых повторов), действует и для точечных инвоков.
- Если REV второй раз возвращает REQUEST-CHANGES — это адресные правки, не перепроектирование; гнать автора на замечания, а не переписывать план.
