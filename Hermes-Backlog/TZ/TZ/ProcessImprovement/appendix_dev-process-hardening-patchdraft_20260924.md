### 3.1 devkanbanpipeline: DevKanbanPipeline_TZ.md 0.2.7 → 0.3.0

#### 3.1.1 «Уведомления графа» — канал Monitoring :7 по умолчанию

Заменить фиксированный контракт (v0.2.6), личный DM Саши → топик мониторинга (группа), без дублей в ДМ:

```bash
# БЫЛО (v0.2.6): DM Саши
hermes kanban notify-subscribe <task_id> \
  --platform telegram --chat-id 400307920 --chat-type dm \
  --delivery-mode notify+wake --notifier-profile default

# СТАЛО (v0.3.0): Monitoring :7, группа — по умолчанию, без дублей в ДМ
hermes kanban notify-subscribe <task_id> \
  --platform telegram --chat-id -1004300127777 --chat-type group \
  --delivery-mode notify+wake --notifier-profile default
```

Добавить формулировку: **«Все задачи в канбан репортят ТОЛЬКО в топик мониторинга (группа
`-1004300127777`, :7), без дублей в личный DM, по умолчанию. Отдельное явное указание Саши
может переопределить канал подписки конкретного графа, но дублирование в DM по умолчанию не выполняется.»**

Кейс 2 (DM вместо Monitoring) — закрывается заменой контракта. Ядро канбана не трогаем.

> фразы Саши. Решение Саши по багфиксу уже зафиксировано в ТЗ/плане; багфиксы по плану архитектора
> берутся в работу как уже согласованные реализации. `GATE:diagnose-review` остаётся HITL (never auto).

## 4. Вопросы к ревизору (оставшиеся противоречия)

Разобранные 24.09 противоречия (кейс 6 vs т.1; кейс 3+т.4; кейс 2+т.3) — приняты Сашей, подтверждаю
и не перепредлагаю. Три разграничения остались открытыми и требуют решения ревизора/Саши перед
фиксацией формулировок:

**Q1. Канал уведомлений при HITL-гейтах (т.3/кейс 2).**
Все уведомления уходят только в Monitoring :7 (группа), без ДМ. Но часть гейтов остаётся HITL
(`GATE:diagnose-review` never auto; `GATE:take-into-work`/`GATE:done` в пошаговом ходе) — их снимает
Саша. Если сигнал о блокированном гейте идёт только в группу мониторинга (а не лично), гарантированно
ли Саша его увидит вовремя? Подтвердить, что правило «только Monitoring, без ДМ» применяется ко всем
терминальным событиям (включая запросы HITL-действия), либо оставить узкое исключение для событий
«нужно решение Саши». Мой draft-default: **без исключений — только Monitoring :7** (решение уже
принято 24.09, задача не требует возврата в ДМ).

**Q2. Объём «мнение Hermes не предлагается» на бриф-фазе (т.2/кейс 5).**
tz-workflow (Шаг 2/процедура H) требует «задавать вопросы с вариантами и рекомендациями». Если
Сирени запрещено предлагать мнение вовсе — процедура H теряет рекомендации до передачи архитектору.
Уточнить: рекомендации по **постановке/архитектуре задач** — только архитектор (Сирень не даёт);
остаётся ли Сирени право давать **фактологические уточняющие вопросы** и бытовые рекомендации
в бриф-фазе? Мой draft-default: Сирень задаёт вопросы текстом (без собственных вариантов по
постановке) и передаёт архитектору; рекомендации по постановке — только архитектор.

**Q3. Границы авто-багфикса vs обычные задачи (т.4/кейс 3).**
Autо-проход взятия в работу после одобренного диагноза применяется к BUGFIX/BUGFIX-LIGHT. Для
DEV/CHANGE (новые фичи/доработки) сохраняется ли «берём в работу» HITL (и one-pass-режим) как было?
Подтвердить: т.1 «все задачи в план по умолчанию» = вход в план, а не автозапуск реализации всех
задач без согласования. Мой draft-default: да, авто — только для багфиксов; обычные фичи — вход в
план по умолчанию + штатный HITL «берём в работу» (или one-pass).

**Q4 (техническое, кейс 1).** Механизм «проверка активного графа по слагу перед kanban_create»:
критерий «активный» = карточки `todo|ready|running|blocked` на тот же `<slug>` (исключая `done`/`archived`);
при совпадении — reuse существующего графа, либо явная эскалация (не плодить дубль). Прошу ревизора
подтвердить критерий и поведение при коллизии (reuse vs block) — draft-default: **reuse существующего,
при неоднозначности — block с причиной** (не создавать параллельный граф).
