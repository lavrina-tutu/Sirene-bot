# Direct-mode (без pipeline) — запуск ролей вручную через codex

Оперативный режим по решению Саши: «пайплайн dev workflow мёртв», роли запускаются
только по прямому указанию владельца, прямыми вызовами `codex exec` без emit/invoke-контура.
Используется, пока владелец не вернёт штатный pipeline-путь; при возврате канона — снова
канон. Режим не отменяет содержательные решения ролей и границы прав.

## Последовательность

1. **Создать общую временную папку починки**:
   `<…>/dev/pochinka-<тема>-<ГГГГММДД>/` с подпапками `in/`, `out/`, `evidence/`.
2. **В `in/`** собрать ВСЕ материалы по теме копированием (артефакты RESEARCH, brief,
   extract, материалы triage) с абсолютными путями. Один рабочий каталог — один процесс
   ДЛЯ РОЛЕЙ, ПИШУЩИХ В ОБЩИЕ ФАЙЛЫ (replay/install/merge, общий index/worktree/каталог
   результатов). Для НЕЗАВИСИМЫХ read-only документных прогонов (разные PREP, ADVICE,
   admission-аудиты) один каталог — это нормально ПАРАЛЛЕЛЬНО, если каждый прогон пишет
   только СВОЙ disjoint файл в `out/`/`evidence/` и не модифицирует общие входы;
   запускать их отдельными background-процессами и ждать notify каждого. Эта
   параллельность — явная рекомендация для PREP-фаз декомпозиции (могут идти
   одновременно и экономят время без merge-риска), в отличие от writer-частей W1-N,
   которые по общим tests/fixtures сериализуются.
3. **Написать промпт роли** в файл (напр. `/tmp/devwf-<role>-prompt.md`): рамка задачи,
   перечень входных материалов с абсолютными путями, ключевые секции-источники,
   явный запрет реализации (роль read-only, если это анализ), куда писать результат
   (файл в `out/`, напр. `TZ-kontrakt.md`), формат результата.

   **Текст промпта держать малым; объёмные исходники роль читает САМА по путям — не
   вшивать их в промпт и не копировать контентом.** Для роли-архитектора (read-only,
   полный доступ к диску через `-C <workspace>`) укажи в промпте абсолютные пути на
   `in/*` и требование «загрузи всё, что тебе нужно, и реши» — так проходят десятки
   КБ-B мегабайтов источников без раздувания промпта и без самовольного сжатия.

   Готовый комплект входов для **SKILL-CHANGE ТЗ из RESEARCH** (собирает этот класс
   задачи): brief + extract + оба RESEARCH-поезда `collect`+`analyze` + master-ТЗ
   дорабатываемого скилла + реальный код скилла (`SKILL.md` + `scripts/`) + код
   соседних компонентов (MofsIndex/MppReader/workvault-rag). Модель роли — gpt-6-astra.

4. **Запуск роли фоном** (notify + persist_on_release), лог в `evidence/`:
   ```bash
   D=<…>/pochinka-<тема>-<ГГГГММДД>
   codex exec -C "$D" -m <модель> -c 'model_reasoning_effort="high"' \
     --skip-git-repo-check --json --sandbox danger-full-access -- "$(cat <промпт>)" \
     2>&1 | tee "$D/evidence/<role>-run.log"
   ```
5. **Остановка после каждой задачи.** По завершении роли — только передать результат
   владельцу; ничего не запускать, не продолжать, не автопереходить к следующей роли.
   Следующая роль — только по явному указанию Саши.

## Роли/модели (backends codex)

| Роль | Модель | Примечание |
|---|---|---|
| архитектор | `gpt-6-astra` | read-only по материалам; результат — документ |
| ревизор | `gpt-6-astra` | независимый вердикт по документу, отдельный run |
| исполнитель | `gpt-6.1-terra` | реализация по принятому плану |
| компрессор | `gpt-6.1-terra` | пишет extract/индекс; только по запуску Саши |
| проверка доступности | `gpt-6.1-sol`, `gpt-6.1-terra` | rc=0 «Привет!» |

`gpt-6.1-astra` не существует (HTTP 400 model_not_found); для архитектора/ревизора всегда
`gpt-6-astra` (без `.1`). Модели ролей фиксированы указанием Саши: исполнитель — терра,
архитектор и ревизор — astra (ревизора на `gpt-6.1-sol` НЕ запускать). Модели проверены
живыми вызовами.

## Цикл REQUEST-CHANGES ревизора в прямом режиме

Ревизор в прямом режиме пишет вердикт-файл `out/REV-<предмет>.md`: **Вердикт**
(APPROVE / REQUEST-CHANGES, можно раздельно по нескольким документам — напр. план
REQUEST-CHANGES + ТЗ APPROVE), резюме, матрица проверок, обязательные правки
(что/где/почему/приоритет критично-важно-желательно), подпись (роль/модель/дата).

**Любой содержательный результат роли (востребованный ревизор/архитектор вердикт,
план, расшифровка FAIL-дефектов, отчёт о proof/прогоне) предъявлять владельцу
ПО-ЧЕЛОВЕЧЕСКИ: СНАЧАЛА историей с жизненным аналогом («какой продукт, на каком
шаге что ломается, где это, с чем связано»), затем уж числами/таблицами как
доказательством.** Саша отклоняет жаргонный разбор («пример из жизни, а не четыре
поста», «это бред») и принимает рассказ-образ. Длинные артефакты (десятки КБ FAIL
отчёта) не сваливать целиком: выжимка сути историями + ссылка на файл; многообразие
разнородных дефектов (FAIL/NOT_PROVEN, разный вес каждого) сводить к трём-четырём
общим историям по корню, а не пересказывать каждый пункт отдельно.

При REQUEST-CHANGES:
1. Прочитать весь вердикт-файл, предъявить владельцу каждый блокер по-человечески
   (что замечание, почему, что ревизор считает приёмкой правки), НЕ запускать
   архитекткора автоматически и не править документ самому без выбора владельца.
2. Предложить владельцу развилку с вариантами и рекомендацией (возврат архитектору +
   повторная ревизия; закрыть одну часть вручную, вторую — ролью; править самому без
   ролей). Ждать явного выбора.
3. При возврате архитектору: в промпт-фикс включить путь к вердикту ревизора,
   точные формулировки обязательных правок (R1/R2 и т.п.) и **вербатим-команды и
   решения владельца как проверяемые источники атрибуции** — архитектор цитирует их
   в документе вместо «текущей команды». Указать, что правится ТОЛЬКО целевой
   документ, остальные (ТЗ, вердикты, контракт, черновики) не трогаются.
4. После завершения архитектора проверить артефакт на диске (число шагов/структура
   не уменьшилась, обе правки присутствуют), затем запустить ревизора повторно
   на обновлённый документ. Старый APPROVE/REQUEST-CHANGES на новую редакцию не
   переносится.

Владелец может явно распорядиться устранять замечания **сразу на исполнителе**
(терра, reasoning high), не возвращая к архитектору: «устранение замечаний — сразу
на исполнителе gpt-6.1-terra, reasoning high». Тогда цепочка после REQUEST-CHANGES
проверяющего (или ревизора) — исполнитель-фикс → проверяющий заново → ревизор, а
не архитектор-фикс. Такой порядок — это решение владельца на данную итерацию,
фиксировать его как направляющий в промпте-фиксе; содержательные пересмотры
ТЗ/плана при этом по-прежнему через архитектора.

## Разметка и вычистка тестовой информации (стоящее требование Саши)

Верификационная/проверочная работа (пилот, тестовые прогоны ролей, пробные карточки)
обязана явно размечать ВСЁ тестовое:
- каждой тестовой сущности (карточка, файл `out/TEST-*`, запись, комментарий) давать
  метку `TEST-PILOT-<дата>` и пометку о вычистке; создавать тестовые записи ТОЛЬКО
  в рамках согласованного допуска и ПОСЛЕ команды владельца на пакет;
- после завершения исследования СИРЕНЬ обязана **напомнить владельцу** о команде на
  вычистку всей размеченной тестовой информации;
- вычистку выполнять ТОЛЬКО по прямой команде Саши и ТОЛЬКО тестовых сущностей,
  не задевая боевые карточки/файлы.

## Пилот на штатном канбане: карточки + codex (проверка реализуемости)

Когда проверяется реализуемость процесса (пилот 5×6), каждая задача = канбан-карточка
на реальной доске + прямой вызов исполнителя через codex; карточки дают трассу
(created/runs/completed) и проверяют зависимости, файлы — полезный результат. Шаблон
одной задачи пилота:
1. **Тело карточки** — файл (`--body-file /tmp/<p>-body.txt`): метка TEST-PILOT-<дата>,
   AC, что разрешено записывать (только конкретные `out/`-файлы), что запрещено
   (боевое ядро/доска/state/SQLite/gateway/master-ТЗ), получатель/доставка.
2. **Создание карточки**: `hermes kanban create "<заголовок>" --body-file …
   --workspace "dir:/<абс-путь>" --parent <предыдущий-id> --json`. Родитель-цепочка
   P1→P2→…→P5 проверяет зависимость и порядок; `--json` для create РАБОТАЕТ.
3. **Вызов исполнителя** по тому же шаблону codex (промпт в `/tmp/<p>-exec-prompt.md`, лог
   в `evidence/<p>-exec.log`, фон+notify+persist). В промпт класть родительский контекст
   (результаты предыдущих задач) с явным требованием «используешь, НЕ пересобираешь». 
4. **Приёмка**: прочитать артефакт на диске, сверить sha256/неизменность прочих файлов
   (терра сама возвращает контроль SHA-256), затем `hermes kanban complete <id> --result "…"`.
5. **Протокол**: после каждой задачи дописать раздел в `out/PROTOCOL-*.md` (карточка,
   usage, результат, приёмка, статусы, остановка). Стоп по С12-режим после каждой задачи.

### Kanban CLI pitfalls (проверено на пилоте)
- `--initial-status` принимает ТОЛЬКО `blocked|running`; `ready` — НЕ валиден
  (`invalid choice`) и вообще является дефолтом — просто не передавать флаг.
- `complete` НЕ принимает `--json` — `--result "…"` без него (иначе usage-fail).
- `workspace` — только форма `dir:/<абс-путь>`, не голый путь; `--body-file` обязателен
  (файл должен существовать).
- Проверять результат: `hermes kanban show <id>` — status/run/completed/result.
- Полезный вызов — только роль по модели (исполнитель терра `gpt-6.1-terra` c
  `model_reasoning_effort="low"`); архитектор/ревизор в тестовых прогонах не вызываются.

## Финализация ТЗ после разбора противоречий по одному

Когда владелец проголосовал каждую развилку ПО ОДНОЙ («да дальше», «1 ок», «2.
уведомление в errorbus») и завершающий ответ «всё верно, запускай», следующий шаг
— НЕ новый анализ, а НАПИСАНИЕ финального ТЗ на базе решённых противоречий:
архитектор-«писатель» собирает документ, а не исследует. Вход роли:
1. **Файл принятых решений** (`out/DECISIONS-<тема>.md`) — каждый пункт дословной
   нормой с пометкой «ПРИНЯТО (<ответ владельца>)». Это ОСЬ ТЗ: архитектор обязан
   реализовать каждую норму дословно в соответствующем блоке. Свести в контрактную
   запись и дать как отдельный input, а НЕ только в чат.
2. **Каркас ТЗ** — собственный предшествующий отчёт архитектора с противоречиями и
   структурой блоков; попросить наполнить его в полный текст, согласовав с решениями.
3. **Восстановленные требования владельца** — переосмыслить в новом контексте:
   сохранить достижимые, удалить противоречащие (уже снятые решениями).
4. **Master-ТЗ** — финальный документ обязан быть cohort-совместим с ним (сохранить
   канон кейсов/ролей/гейтов), переобъявив только механизм исполнения.

Промпт «писателю»: перечислить все входы абсолютными путями, потребовать покрыть ВСЕ
блоки каркаса, реализовать решения дословно, чётко разделить «что делает штатный
канбан» и «что делает Dev Workflow», добавить раздел приёмки с матрицей `требование →
раздел ТЗ → механизм → сценарий приёмки`, в конце — перечень оставшихся развилок для
владельца. Явно запретить выдумывать факты: незафиксированное в входах помечать
«требует уточнения», а не придумывать. Результат — один целевой файл
`out/FINAL-TZ-<тема>-<механизм>.md`; больше ничего не писать. Завершение — полная
остановка: затем независимый ревизор (REV:tz) на готовый документ и только потом гейт.

Перед фоновым запуском любой тяжёлой писательской роли (может жечь миллионы
input-токенов) — ОДИН дешёвый probe алиаса модели
(`codex exec -m <model> ... "Reply with exactly: OK"`, видеть `"text":"OK"`), даже если
алиас штатный. Провал 400 `model_not_found` на пути длинного запуска = сожжённый прогон
впустую; probe стоит секунды и исключает это.

## REV:plan — план тоже проходит REQUEST-CHANGES цикл (контракты до кода)

Не только ТЗ: план реализации (HF:plan) проходит независимый REV:plan, и он может вернуть
REQUEST-CHANGES. Отличить технический rework плана от точки решения владельца — по СОБСТВЕННОЙ
классификации ревизора: если REV прямо пишет «это исправления плана, а не вопросы владельцу;
D1–D9/Q1/Q2 уже закрыты, старую машину не возвращать» — цикл возврата архитектору (адресный
фикс → повторный REV:plan на новые bytes) идёт автоматически без отдельного гейта Саши.
Новый выбор владельца нужен только если REV заявляет открытую предметную развилку.

План получает REQUEST-CHANGES по типовым причинам, которые учитывать при проектировании
плана сразу (ревизор ловит на сверке с master-ТЗ):
- **Закрытые контракты, которые master требует зафиксировать ДО кода, нельзя откладывать
  в resp. validator/код.** Б60.5-класс норм требует в плане закрытые nested JSON-структуры
  (required/null/enum/type/no-extra), полные identities, правила хеширования/связывания
  (manifest↔production↔result↔receipt), точную строковую форму receipt, допустимую единицу
  записи и способ сохранения bytes прежней редакции до замены mutable canonical. Строка
  плана «полный контракт оформить в same кодовом validator и golden fixture … до первого
  dispatch» — НЕ закрытие, это перенос проектирования в код.
- **Native и Codex-правила выбора модели/локальных отказов нельзя смешивать.** Codex —
  explicit concrete override либо `roles.<role>`, БЕЗ ENV, не-concrete → локальный rc=2;
  native — explicit → YAML, а для null/empty-селектора допустима static ENV-модель,
  static refusal → rc=3. Один общий «no ENV/fallback» на обе ветви ломает сохранённое
  различие (Б60.4/AC-COMP-*). Разносить явной таблицей ветвь × селектор × rc.
- **Oracle приёмки обязан иметь РАЗЛИЧАЮЩИЕ данные, которые неверная реализация не
  переживёт.** Общий тест «backend/argv/model/effort эквивалентны» проходит у реализации,
  всегда выбирающей одну executor-модель, при нарушенном AC-088/090 (executor_light,
  Cursor не читает Codex-ветку). Давать параметризованную fixture с заведомо разными
  значениями ролей (executor / executor_light / cursor.executor) и ожидаемым выбором по
  каждой; missing model → отказ до send.
- Предметные замечания ТЗ (M1–M3-класс) обязаны быть РАЗВЁРНУТЫ в плане адресным шагом/
  оракулом (§7.2/P30, двухдеревный workspace Б17.8, численный oracle метрик base→final),
  а не «учтены» одной строкой привязки AC.

## Сборка итога проверки (шаги 19–21)

- Шаг 19 (единая матрица H01–H08, статусы P1–P5, качество контекста, NOT_RUN-причины) —
  работа М0, выполняет Сирень без модельных вызовов; grep-проверка «нет секретов и
  денежных значений» обязательна.
- Шаг 20 (внесение доказанных поправок в реальное ТЗ переезда) — **проводит АРХИТЕКТОР
  (астра), НЕ Сирень** (указание владельца: «Проводит архитектор — астра»). Промпт
  архитектору: адресно прочитать матрицу шага 19 + текущий драфт ТЗ + §7 плана, внести
  поправки с цепочкой «наблюдение H/P → ref/version → граница/пробел → норма → владелец
  → условие повторной проверки»; разрешено писать ТОЛЬКО целевой ТЗ-файл; Git-команды
  НЕ выполнять (согласуются с Сашей отдельно).
- Каждая гипотеза без общего PASS: частично подтверждённое ≠ PASS; «не проверено» =
  NOT_RUN с причиной/влиянием/способом закрытия; честный NOT_RUN не превращать в
  новые обязательные прогоны.

## Правила диспетчеризации в прямом режиме

- Роли только по прямому указанию Саши; после каждой задачи — полная остановка,
  КРОМЕ случая, когда владелец одной директивой велит продолжать цепочку этапов
  сразу («продолжаем реализацию сразу до Э6», «делай план и шагай до точки N») —
  тогда гейт «остановка после каждой задачи» для перечисленных этапов переопределён,
  и остановки вне этого объёма нет. В маршруте заранее пресчитать фазы, гейты и
  ТОЧКИ ВОЗВРАТА К ВЛАДЕЛЬЦУ и автоматически не проходить мимо них:
  - точка тестирования (живой прогон системы на реальных задачках — владелец хочет
    «глазами» увидеть результат перед продолжением);
  - точка решения (развилка, где нужен выбор владельца).
  Всем остальным управляет директива; факты/развилки/решения в ней не достраивать.
- **Точки решения приносить с вопросом + контекстом + рекомендацией от АРХИТЕКТОРА
  (роль arch, gpt-6-astra), не от себя.** Стоящее требование владельца: рекомендацию на
  развилке готовит роль архитектора, а не оркестратор/Сирень. Для этого до точки
  решения либо запросить у архитектора рекомендацию (отдельным read-only прогоном),
  либо включить в маршрут этап, где архитектор формулирует рекомендации по вилкам.
  Свою собственную рекомендацию на развилке владельцу не давать — только вопрос,
  факты/контекст и вердикт-рекомендацию архитектора.
- Развилки/вопросы владельцу предъявлять ПО ОДНОЙ, с вариантами и рекомендацией
  (рекомендуемый вариант первым). Сначала вопрос 1; после ответа — следующий.
- Результат архитектора по ревизии требований — короткий контракт: нумерованный список
  требований, адресная матрица покрытия (предметные имена, не «вариант 1/2»), перечень
  пауз, три развилки с рекомендациями, вердикт. Помечать как «проект до ответов Саши».
- Вход/результаты — через файлы в общей папке; факты не выдумывать, недостающее
  запрашивать, а не додумывать.
- **Когда владелец согласовал [NEW-ENTITY] пакеты («делай по порядку до конца»),
  следующий гейт перед lab/реализацией — независимая REV дизайнов (ревизор gpt-6-astra,
  отдельный read-only прогон), а НЕ сразу сборка стенда.** Если архитектор прямо
  потребовал REV до исполнения, это обязательный шаг, а не формальность. Несколько
  [NEW-ENTITY] пакетов с непересекающимися файлами можно ревизовать ОДНИМ прогоном
  (ревизору передать оба проекта + норму + границы допуска, формат вердикта:
  APPROVE/условия/REQUEST-CHANGES по каждому объекту отдельно, таблица замечаний с
  типами REQUIRED/ADVISORY/OK). Только после APPROVE — сборка lab и исполнение.

## Адресная правка контракта под кандидата (норма догоняет код)

Когда кандидат уже реализует новый формат/версию контракта, а норма поезда
(HF-plan/master-ТЗ) ещё фиксирует старый, и владелец выбирает «поправить контракт»
(вариант «норма к кандидату», старые записи остаются историей):

1. **Найти ВСЕ вхождения старого формата в норме** (тип/структура, literal-строка,
   regex) — search_files по точному токену, не только по «известной строке»; править
   каждое вхождение согласованно (тип enum + строка формата + regex обязаны совпадать
   между собой и с кодом кандидата).
2. **Поднять version во frontmatter** и добавить абзац «Адресная редакция <ver>» со
   ссылкой на вердикт архитектора и решение владельца; старая редакция остаётся в
   changelog-истории, не переписывается.
3. **Синхронизировать производные таблицы допуска** (напр. PREP-01 enum-таблицы
   форматов), где тот же формат зафиксирован — иначе норма и допуск разойдутся.
4. **Проверить 0 остатков** старого формата в норме (search_files снова), затем живой
   прогон целевого тест-поднабора кандидата (напр. `-k receipt`) + `git status`
   кандидата чист — кандидат при такой правке НЕ меняется, меняется только норма.
5. Старые записи прежнего формата не мигрировать и не переписывать — они история;
   новые — только новый формат.

## Питфоллы

- **После документного прогона read-only роли, готовящей ДЕЛЬТЫ/правки (oracle, норма,
  план, вердикт), перед предъявлением результата сверять, что набор исходных файлов
  НЕ изменился: зафиксировать `sha256sum` по всем кандидатным/ядерным/нормативным
  файлам ДО запуска, повторить ту же команду ПОСЛЕ и сравнить построчно.** Дельта —
  это документ про будущую правку, а НЕ применённая правка; без сверки неизвестно,
  тронул ли прогон базу (записал себе в `out/` и заодно отредактировал исходник).
  Роль, обязанная писать только свои новые `out/`-файлы, возвращает совпадающий
  набор hash-sha — только тогда её результат честно принимается как «дельта
  готова», а не «уже применена». Сверку выполнять самому (та же команда до/после),
  не полагаться на самосообщение роли в завершающем item; при расхождении хотя бы
  одного хеша — правку откатить до запуска и выяснить, что роль тронула, прежде чем
  предъявлять результат.
- **Архитектор в прямом режиме обязан развёрнуто отвечать на фазе-развилке (что рекомендует по каждому пункту), но НЕ решать за владельца.** Даже когда в бриф ТЗ зашит явный императив «реши, один скилл или два», роль должна зафиксировать обоснованный ВЕРДИКТ в документе как рекомендацию с причинами и поместить непогашенные развилки (Q1…Qn) отдельным разделом для владельца, не ждать его решения прежде чем дописать ТЗ. Перечни развилок в ТЗ передавать владельцу ПО ОДНОЙ (с вариантом и рекомендацией), а не списком — это устоявшееся требование Саши (см. раздел «Развилки/вопросы»).
- **Проверять готовый артефакт роли на диске каноничными разделами, а не только числом строк.** Для ТЗ-документа контролировать: заголовок/вердикт, таблицу W/T, таблицу изменений компонентов, матрицу приёмки AC и раздел развилок. Прочитать эти разделы read_file'ом (grep по H2-заголовкам), а не полагаться на самосообщение роли в завершающем item — роль могла «заявить готовность», но секции не сойтись.
- **Финальный отчёт роли в прямом режиме может прийти ТОЛЬКО в JSON-потоке, не в файл и не в `agent_message`-событие лога.** Если роль в `out/`/workspace ничего не записала (а по постановке могла не писать — она read-only и выдаёт отчёт в выводе), а `codex exec ... | tee evidence/<run>.log` завершился с большим `output_tokens`, не считать результат потерянным и не перезапускать роль (2.2M input / 13.6K output = жжёт токены): полный ответ живёт в `item.text` ОДНОГО `item.completed`-объекта JSON-строки (а не в событиях типа `agent_message`, которых в логе может вообще не быть). Восстановить парс-по-строке: для каждой `line` лога `json.loads`, выбрать объект, чей `item.text` содержит УНИКАЛЬНЫЙ маркер из середины ответа (напр. «Основания:»/первый заголовок списка), сохранить `item.text` в `out/<артефакт>.md` через write_file; визировать по заголовкам/длине. Признак отчёта роли: текст начинается с выводной структуры (`# <СПИСОК ПРОТИВОРЕЧИЙ>`, `# КАРКАС ТЗ` и т.п.). Искать маркер по контенту ответа, а не по типу события потокового протокола — тип события не предсказуем между запусками.
- НЕ обобщать «пайплайн мёртв» в отрицание будущего — это текущее решение владельца,
  не запрет штатного контура навсегда. Режим применим, пока владелец его не отменит.
- НЕ продолжать цепочку ролей автоматически после завершения одной — владелец требует
  остановку и явный запуск каждой следующей. Это ядро прямого режима.
- **«Один каталог — один процесс» не запрещает параллельные независимые read-only
  прогоны в том же каталоге** (разные PREP, ADVICE, admission-аудиты): они не конкурируют
  за запись, если каждый пишет только свой disjoint `out/`/`evidence/` файл и читает
  общие входы. Сериализация обязательна для прогонов, пишущих в ОБЩИЕ файлы (общий
  index/worktree, общий `conftest.py`/`kanban_fixtures.py`, install/replay/merge).
  Различать две независимые причины сериализации — по данным (общая запись) против
  по дисциплине владельца («остановка после каждой задачи») — и обе соблюдать.
- В контракте недоказанные возможности (строгая очередь, resume после лимита, ранний
  отказ до платного вызова, локальная приёмка AC) помечать как «не доказано», а не
  «невозможно»; не превращать инженерный остаток в новые требования владельца.
- Проверять фактический результат роли на диске (`out/<артефакт>.md`, sha256 при
  необходимости), а не доверять самосообщению процесса; счётные величины из отчёта
  сверять программно, а не брать на веру.
- Перед запуском роли с входными материалами измерять их объём (`wc -c` по каждому файлу
  и суммарно); при превышении 15 000 байт сообщить Саше размеры файлов и общий объём и
  ждать его решения (компрессор запускает только Саша, либо он выбирает прямое адресное
  чтение), не запускать роль и не сжимать самовольно.
- **Когда владелец демотирует ранее установленный безопасностный блокер (напр. полный
  снег доски O1) до «проверим нюансы после запуска», обосновывая «ничем не рискуем,
  текущий процесс всё равно не работает» — принять приоритет-реордер и продвигаться
  с настройкой, но блокер НЕ закрывать и НЕ молчать о нём.** Оформить директиву
  владельца в `evidence/owner-directive-*.md` (цель в приоритете + что переопределено),
  в итоговом отчёте честно пометить блокер как «открыт, отложен в отладку после
  запуска» (полнота не подтверждена), тем самым продолжая исполнение без
  перепринятия развилки. Не объявлять снятым снег/полноту, которых по факту нет, и
  не переспрашивать уже демотированный гейт — прямая директива владельца выше
  исторического гейта.
- Роль/исполнитель, которым владелец велел «переезжай вперёд, следы/нюансы позже»,
  всё равно обязана предупреждать о побочных эффектах небезопасных операций
  (напр. экспорт, преобразующий копию; отсутствие обратимого отката) в отчёте, чтобы
  Саша принял приоритет-реордер с полным знанием риска, а не вслепую.
- При изменении назначения моделей ролей обновлять таблицы ролей во ВСЕХ ТЗ темы
  (grep по старому имени модели в `out/`), но не переписывать исторические подписи уже
  проведённых вердиктов — они фиксируют фактическую модель выполнения.
- В документе, подготовленном ролью, каждое решение, приписанное владельцу
  («Саша выбрал…», «остановка после каждой задачи»), обязано иметь проверяемое
  основание: точная ссылка/идентификатор + релевантный текст решения. Ревизор
  возвращает REQUEST-CHANGES, если решение заявлено без источника или как «текущая
  команда» — это не выдумка, но неподтверждённая атрибуция. Оркестратору давать
  архитектору вербатим-решения владельца в промпте-фикс, а не ссылаться на
  «неназванную команду».
- **Директива о модели/reasoning роли — НЕ доказательство акта принятия версии или
  завершения этапа.** Паспорт/статус, утверждающий «владелец принял ТЗ v0.6 / завершил
  Э0», не должен опираться на директиву, которая лишь фиксирует модель и reasoning
  исполнителя (оно же «обновление ТЗ выполнялось фоново») — это иной факт, не акт
  принятия. Проверяющий возвращает REQUEST-CHANGES (X0-класс), если принятие/завершение
  заявлено без отдельного проверяемого решения владельца. Лечение: отдельным фактом
  зафиксировать решение владельца «продолжаем по этой версии как неизменному основанию,
  ревизия не требуется» с датой/ref и SHA версии, либо честно пометить принятие/
  завершение как «не установлено» и убрать ссылку на директиву как доказательство.
  Не подделывать несуществующие акты ревизии; если формальная ревизия не проводилась —
  отметить это, а не выдавать принятие за ревизованное.
- **Безопасного read-only чтения штатной доски канбана НЕ существует — не выполнять
  вывод доски «просто посмотреть» вслепую.** Обычный CLI (`kanban_command`) вызывает
  `init_db()` перед handler, dashboard-API и `kanban_tools#_board` идут через
  `connect`/`init_db` (создание/инициализация/WAL); имя «чтение» не исключает запись
  при открытии. Найденная fenced-descendant ветка SQLite read-only не имеет доказанных
  контекста/авторизации/полноты охвата — вызывать без решения владельца нельзя.
  Перед любым чтением доски: перечислить все штатные интерфейсы и для каждого
  определить, тянет ли цепочка init/connect/WAL; если безопасный путь не подтверждён
  — выгрузку не делать, зависимую работу удержать, а на развилку принести владельцу
  вопрос с вариантами + рекомендацией архитектора (прямой SQLite, monkeypatch, подмена
  контекста fenced-ветки, repair, собственный exporter и правка ядра — не предлагать).
- **Рекомендации архитектора на развилки заказывать отдельным read-only прогоном с
  передачей ПОЛНЫХ фактов, затем проверять структуру результата до принесения
  владельцу.** Промпт архитектору на ADVICE: передать ему остановочный материал
  исполнителя (CANDIDATE-*.md §пробелы) и каталог развилок маршрута; требовать по
  каждой развилке блоки «Вопрос» / «Контекст» / «Рекомендация А» / «Что будет при
  выборе 1/2» и «## Резюме для владельца». Перед предъявлением владельцу прогонять
  структурную проверку выхода (assert на каждый обязательный подраздел в каждом
  блоке), затем приносить вопросы по одному. Свои рекомендации архитектору не
  навязывать.
- **Инвентаризация периметра обязана выделять каждую группу с отдельной судьбой
  отдельным объектом, а не одной общей строкой.** Если ТЗ/контракт предписывают разные
  решения группам (обвязка компрессора и старые extract/echo/inventory/CAP, карточки
  починки, тяжёлая техника: собственный диспетчер, автоблокировки, бюджетный движок,
  пересборка пакетов — неперенос, предварительное сохранение сценариев, адресная
  очистка, история 30 дней после фактической операции), паспорт/инвентарь обязан
  перечислить их адресно с источником и предписанной судьбой, явно оставив неизвестные
  пути/ID/версии/состояние «не установлено». Общий пункт «старый pipeline и поезда» не
  позволяет проверить, что группа не будет ошибочно перенесена или очищена без условий;
  проверяющий возвращает REQUEST-CHANGES (X1-класс). Документное дополнение без поиска
  и выдумывания ID; фиксировать готовность нового процесса и отдельную команду как
  условия очистки/переноса.
- Гипотеза/проверка, требующая раздельного учёта нескольких причин (напр. «учесть
  три причины повторов отдельно»), обязана содержать ИСПОЛНЯЕМЫЙ случай для КАЖДОЙ
  причины: действие, критерий, свидетельство — а не только название причины в
  матрице. Ревизор ловит «заявленную полноту шире исполняемых проверок» (H05-класс)
  и возвращает план. При отсутствии штатного учёта проверяемой причины — описать
  ограниченный процедурный вывод, без общего PASS гипотезы.
- **Один `out/DECISIONS-owner.md` с решениями владельца НЕ освобождает от встраивания
  их в нормативное тело ТЗ ДО первой REV — иначе ревизор вернёт REQUEST-CHANGES даже
  при полностью подтверждённой архитектуре/аналитике/AC-матрице.** Ревизор видит
  развилки владельца только записанными в тело ТЗ как решённые факты (конкретные
  R-…, имя/значение дословно) и §14 под заголовком «решено», а НЕ как открытые
  вопросы с рекомендациями, пусть и продублированные в отдельном файле. Оркестратор
  после каждого ответа владельца должен сразу править ТЗ (подняв version + changelog
  с «обработан вердикт/внесены решения Q…») и только затем отдавать на REV; отдельный
  файл решений — рабочий артефакт для архитектора, не основание для ревизора.
  Симптом: REQUEST-CHANGES «решения владельца не включены в тело ТЗ», хотя
  DECISIONS-owner.md существует и все пункты помечены ПРИНЯТО. Расхождение дат
  (ТЗ от 13.11, решения Q4–Q7 пришли 14.11) технически объясняет разрыв, но не
  снимает требование.
- **Роль-модель из `tools.dev_workflow` YAML (архитектор/ревизор `gpt-6-astra`, терра,
  сол) — alias бэкенда codex (`codex exec -m <alias>`), а НЕ имя для прямого
  `agent -p --model <модель>`.** Вызов `agent -p … --model gpt-6-astra` падает сразу
  с `Cannot use this model` и перечислением доступных CLI-моделей — роль не стартует,
  ход/время сожжены. Роль запускать тем бэкендом, чей набор имён содержит её модель:
  codex-контур → `codex exec -m gpt-6-astra`; агент-CLI-контур (прямой `agent -p`) →
  только реальная модель из выведенного списка (для ТЗ/ревизии подходит
  `claude-sonnet-5-thinking-medium`). Не переносить имя модели из YAML ролей в другой
  бэкенд вслепую; при сомнении — дешёвый probe модели или штатный `pipeline
  invoke-role`, который сам резолвит роль→backend из YAML.
