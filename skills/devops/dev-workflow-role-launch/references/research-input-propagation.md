# Передача аддендума владельца в поздние фазы RESEARCH (RS:analyze/REV:report)

## Проблема

В RESEARCH-поезде (init --case RESEARCH) владелец часто дополняет требование уже ПОСЛЕ `RS:collect`
(например: «промпты должны быть однозначными»). Интуитивно это аддендум пишется в `brief.md`, и
кажется, что свежий `emit-prompt` на следующей фазе его подхватит (emit читает brief заново).

Это НЕ работает для поздних фаз: дефолтная таблица контракта (`pipeline_context._inputs`) передаёт
в `RS:analyze` только `RS-collect.md` (facts), а в `REV:report` — только `RS-analyze.md` (analysis).
`brief.md` — это input только для `RS:collect` (research frame). Дописанный в brief аддендум
выпустит packet фазы, где в `handoff.inputs` нужного файла НЕТ → роль архитектора финальной фазы
требования не увидит.

## Проверка до invoke

После `emit-prompt` прочитать свежий packet JSON и смотреть ИМЕННО `handoff.inputs` (не корневой
ключ `inputs`):

```bash
PKT=$(ls -t <dev>/<slug>/context/*.json | head -1)
python3 -c "import json; p=json.load(open('$PKT'));
for i in p['handoff']['inputs']: print(i['purpose'], '->', i['ref']['path'])"
```

Нет твоего аддендума в списке → роль его не получит.

## Штатный ход (работает)

1. Вынести директиву владельца в ОТДЕЛЬНЫЙ файл: `evidence/owner-addendum-<дата>.md`.
2. Зарегистрировать его в handoff-contract (блок ```handoff-contract``` в brief.md) под ЦЕЛЕВУЮ фазу:
   ```yaml
   inputs:
     RS:analyze:
       - path: <dev>/<slug>/RS-collect.md
         phase: RS:collect
         purpose: facts
       - path: <dev>/<slug>/evidence/owner-addendum-<дата>.md
         phase: RS:analyze
         purpose: <требование владельца>   # текст обязан содержать суть директивы
   ```
3. СВЕЖИЙ `emit-prompt` на этой же фазе (новая packet_id, brief перечитан, addendum теперь в inputs).
4. Проверить: `handoff.inputs` нового packet содержит ОБА файла (facts + addendum).
5. Один background-invoke той же ролью (архитектор, если фаза RS:analyze).

## Правила-следствия

- Вход, который должна увидеть роль финальной фазы, фиксируется в contract `inputs` как отдельный
  файл ДО emit; наследования из brief нет.
- Если аддендум добавить в brief ДО emit `RS:analyze`, он всё равно не войдёт в inputs этой фазы
  (таблица контракта перечисляет только канонические входы); нужен именно отдельный файл + строка
  в `inputs`.
- Не редактировать packet/contract ПОСЛЕ emit фазы, которую уже invoked — править brief и
  пере-эмитить до инвока. Для перечисленных фаз можно пере-эмитить без reset, если роль ещё не
  запускалась (пакет принимается заново).

## Многофайловая проверка REV:report: «проверить весь комплект» требует вход на каждый файл

Когда RS:analyze велит ревизору проверить «весь exact комплект» (спецификацию, карту экосистемы,
критерии, готовые промпты, rationale, статус — напр. K-5 «единая комплексная ревизия»), а не только
канонический RS-analyze.md, то каждый обязательный новый документ комплекта надо внести ОТДЕЛЬНЫМ
входом в `inputs: REV:report` контракта (path + phase + purpose) ДО emit. Иначе packet REV:report
несёт только RS-analyze + owner-директиву, ревизор не может проверить приложения как защищённые
входы, и это фиксируется как замечание о недостаточной связанности (паттерн N-02).

Порядок: RS:analyze требует всеобъемлющую проверку комплекта → в brief у `REV:report` перечислить
каждое содержательное приложение → заново `emit-prompt` → проверить `handoff.inputs` по счёту и по
каждому имени → только затем invoke reviewer. Слово «весь комплект»/«все приложения» в требовании —
триггер: это НЕ один вход, а по строке на файл.
