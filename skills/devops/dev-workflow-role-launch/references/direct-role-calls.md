# Прямые вызовы ролей (беспайплайный режим)

Действует с 12.11.2026 по явному решению Саши («пайплайн dev workflow мертв»,
«работаем без пайплайна — только прямые вызовы ролей»). Этот режим заменяет
штатный emit-prompt → invoke-role путь для текущей работы; legacy-канон в
dev-workflow SKILL.md остаётся исторической записью процесса, не действующим
маршрутом.

## Жёсткие правила режима (нарушение ведёт к нежелательным действиям)

- **Роли запускаются только по прямому указанию Саши.** Никогда не запускать
  роль сама по себе, по завершении предыдущей, по расписанию или по своему
  разумению.
- **Остановка после каждой задачи.** Завершилась роль → доложить результат и
  СТОП. Автоматически ничего не продолжать: не вызывать следующую роль, не
  гейтить, не «продолжать путь» без явной команды.
- **Результаты и материалы — файлами в одной временной папке** с подпапками
  `in/` (вход), `out/` (выход ролей), `evidence/` (логи запусков).
- Вводные Саши по новой задаче роль получает полностью в одном промпте (его
  ответы, принятый контракт, постановка) — не узкий блокер, не без контекста.

## Команда запуска (проверена живыми вызовами)

```bash
D=<абс_путь_рабочей_папки>
codex exec -C "$D" -m <модель> -c 'model_reasoning_effort="high"' \
  --skip-git-repo-check --json --sandbox danger-full-access \
  -- "$(cat /tmp/<промпт>.md)" 2>&1 | tee "$D/evidence/<run>.log"
```

Бэкенд `codex`. Запускать фоново + `notify` + `persist_on_release`; лог — в
`evidence/`. Модели: архитектор `gpt-6-astra`, ревизор `gpt-6-astra` или
`gpt-6.1-sol`, исполнение/компрессор `gpt-6.1-terra`.

## Требования к промпту роли (архитектор особенно)

- Указать режим: «работаешь ВНЕ pipeline, прямым вызовом, по решению владельца;
  пайплайн dev workflow мертв».
- **Задача только документ/анализ** — без реализации, если иное не приказано.
- Перечислить входные материалы АБСОЛЮТНЫМИ путями; «это единственные источники
  истины, ничего не выдумывай».
- Назвать выходные файлы явно (что и куда писать). Роль не пишет в другие файлы
  и не трогает мастер/конфиги/state/журналы/доску.
- Явный запрет: правки ядра, боевого pipeline, платные прогоны сверх собственного
  вызова, выдумывание фактов/цифр; не называть документы «принятыми». В т.ч. для
  архитектора: писать в DRAFT-версии, а не в мастер-ТЗ.
- Итог роли — id/имена созданных файлов + одна строка «что это».

## Питфоллы

- **Прежде чем слать Саше ссылки — проверь, что файлы реально лежат на диске**
  (ls / wc). Роль может заявить «готово», но не создать файл или назвать другой
  путь; ссылка на отсутствующий файл — это сломанный результат.
- Не продолжай следующий шаг (корректировка ТЗ, пилот, следующая роль) без
  явной команды Саши — даже если есть готовый следующий шаг по дорожной карте.
- Если роль возвращает «готово» и объём/структура не совпали с заказом, сверь
  реальное содержимое файла, а не только сообщение роли.
- Новые сущности/процессы — только с маркером `[NEW-ENTITY, требует согласования
  Саши]` и после его согласования.
- **Большой контекст пересмотра крупного плана — сжимать промпт: компактная
  директива (суть требований списком фактов/критериев) + абсолютные пути на
  исходники, а не полные тела master-ТЗ/плана в промпте.** Роль поднимает детали
  короткими чтениями по путям (см. команду запуска с `--sandbox danger-full-access`);
  тащить весь контекст в `cat file` — риск таймаута/обрезания и лишних токенов.

## Решение владельца закрывает формальный open-loop ревизии

Когда ревизор фиксирует незавершённость («полная проверка не закрыта, live-гарантии
не подтверждены»), а Саша решением закрывает вопрос («считаем закрыто и все
проверено») — это не правка вердикта, а отдельная нормативная запись:

- **Не переписывать** исторические вердикты/протоколы и не удалять оговорку
  ревизора — она остаётся историей.
- **Дописать в конец протокола раздел** «Решение владельца …»: кто, дата, что
  считается закрытым, какие именно оговорки ревизора переопределены, что исторические
  записи сохранены как история. Это единственная правка, нужная для статуса.
- **Продолжить маршрут** только по явной команде Саши: следующим запрошенным
  артефактом (план реализации, корректировка ТЗ) через прямую роль тем же
  беспайплайным вызовом.
- **Передать решение владельца роли как вход**: в промпте следующей роли явно
  указать, что проверка закрыта решением владельца, чтобы роль не требовала
  повторного live-испытания уже закрытых пунктов и опиралась на решение как на
  факт (пометив в плане, что live-гарантии закрыты решением, а не испытанием).

## Промпт на план реализации (архитектор, документ-план)

Для плана реализации по готовому ТЗ (переезд/внедрение):

- Задача — ТОЛЬКО документ-план, реализация не выполняется.
- Входные материалы абсолютными путями (ТЗ DRAFT, протокол с решением владельца,
  финальный вердикт, контракт); «единственные источники истины, ничего не
  выдумывай».
- Структура плана: цель/границы; этапы с файлами/конфигами и критерием приёмки;
  модели/роли на этапах; валидация; откат; AC по этапам и общий; реестр открытых
  допущений/рисков; порядок ввода без потери текущей работы.
- Где в ТЗ пробел — отметить и предложить разрешение (варианты + рекомендация),
  а не замалчивать.
- В конце выходного файла — блок «## Резюме для владельца» (5–10 строк
  по-человечески, без канбан-жаргона: что за план, главные шаги, что потребует
  одобрения, рекомендуемый порядок запуска).

## Цикл ревизии документа (план/ТЗ/протокол) в прямом режиме

Архитектор → ревизор → при REQUEST-CHANGES возврат архитектору → повторная
ревизия. Каждый шаг — отдельный прямой вызов по явной команде Саши.

- **Ревизор пишет вердикт отдельным файлом** (`REV-<предмет>.md`) с обязательным
  конечным блоком `## Вердикт` и ОДНОЙ строкой `APPROVE` или `REQUEST-CHANGES`;
  детальный разбор — до блока. Входные SHA (5/5) сверяет сам в конце прогона.
- **REQUEST-CHANGES → возврат архитектору новым промптом**: перечислить полные
  замечания ревизии (M01–M03 со своими «Критериями приёмки»), указать, что
  правится ТОЛЬКО предметный файл, исторические документы (ТЗ, протокол, вердикт)
  не переписывать. Архитектор добавляет в конец предметного файла блок
  «Доработка по REV (…)» — таблицу замечание → как адресовано → проверяемое
  закрытие критерия.
- **Повторная ревизия — в НОВЫЙ файл** (`REV-<предмет>-2.md`), а не перезапись
  первой: прошлый вердикт остаётся историей, иначе теряется след цикла.
- **Роль не выдает неподтверждённое «указание владельца» за факт** (питфолл M01):
  если в ТЗ/протоколе/контракте нет решения владельца по конкретному вопросу
  (например, назначение моделей ролей) — база остаётся по ТЗ, а альтернатива
  оформляется как явно неподтверждённое проектное предложение с решением на
  конкретном этапе, а не как принятое разрешение. Решение владельца предъявляется
  как допустимый источник, а не достраивается автором по памяти.

## Пилот на канбане Hermes (карточки + прямой вызов роли)

Пилотные задачи в беспайплайном режиме заводятся на доске канбана и выполняются
ПРЯМЫМ тестовым вызовом роли (терра через codex), а не воркером канбана. Карточка
даёт трейс/приёмку; полезную работу делает отдельный явный вызов той же роли.

```bash
# карточка (модель/воркер роли НЕ запускается автоматически)
hermes kanban create "<title>" --body-file /tmp/<body>.txt \
  --workspace "dir:<абс_раб_папки>" [--parent <id_готовой_родителя>] --json
# принять результат
hermes kanban complete <id> --result "<что сделано>"
```

- **Тело карточки** (`--body-file`): метка `TEST-PILOT-<дата>`, AC (что принять),
  полезный результат и куда доставлен, `Разрешено писать:` (только свои out-файлы),
  `Запрещено:` (ядро/pipeline/конфиги/state/SQLite/журналы/master/боевые карточки,
  установка, cron, gateway, дорогие модели).
- **`--parent <id>`** — зависимость: дочерняя карточка создаётся `ready` сразу, но по
  факту выполняется после приёмки родителя; факт «стартовал после готовности родителя»
  зафиксировать в теле результата (подтверждение авто-promote/ожидания родителей в
  беспайплайном режиме).
- **CLI-грабли:** `create` принимает `--initial-status` ТОЛЬКО `blocked|running`
  (по умолчанию карточка создаётся `ready` — не передавать его, чтобы не ловить
  `invalid choice`); `--json` есть у `create`, но НЕТ у `complete`
  (`unrecognized arguments` — убрать). 
- Каждая тестовая карточка метится `TEST-PILOT-<дата>` и ПОСЛЕ завершения проверки
  вычищается только по отдельной команде Саши — напомнить ему об этом после финала.

## Экономия на проверке/пилоте (предпочтение Саши)

Для проверочных/тестовых прогонов использовать самую дешёвую допустимую модель
(для текущей тройки — `gpt-6.1-terra`) с наименьшим reasoning; не задействовать
дорогие роли на тестах. Цель проверки — осознанность маршрута (что запускаем
именно то, что задумали), а не сдача счётных значений стоимости; сами цифры
стоимости Саше как результат не нужны. Учтённые вызовы — вспомогательный контроль.
