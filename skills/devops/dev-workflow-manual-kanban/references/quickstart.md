# Памятка оператора

## Основание

Проверь согласованные требования, выбор владельцем ручного режима, область кандидата, отсутствие старого pipeline и другого Codex по поручению, а также gateway, dispatcher или daemon на выделенном хранилище. Одна роль активна за раз. Граница и остановка исключённых случаев — [в скилле](../SKILL.md#граница). Доска хранит факты, запуск каждой роли отдельный.

## Переменные одной фазы

Все пути абсолютные, каталоги приведены к одному физическому пути без различий через симлинки. Это схема, не готовые заглушки.

| Переменная | Значение |
|---|---|
| `TASK_ROOT` | Каталог поручения; DW-001: `/home/tkachenkoav/WorkVault/Hermes-Backlog/dev/dw-001` |
| `WORK_ID` | ID поручения, например `DW-001` |
| `PHASE`, `ATTEMPT`, `TITLE` | Точная фаза, положительный неиспользованный номер запуска фазы, краткая цель |
| `EXEC_ROOT` | Согласованный каталог кандидата для реализации и тестов; DW-001: `$TASK_ROOT/candidate` |
| `WORK_ROOT` | `TASK_ROOT` для HF:plan, REV:plan, REV:report и карточек решений; `EXEC_ROOT` для HF:impl и HF:test |
| `MODEL`, `SANDBOX` | План и все REV: `gpt-6-astra`, `read-only`; реализация и тесты: адресное назначение, в пилоте `gpt-6.1-terra`, `workspace-write`; effort `high`. Для решений модель не вызывается |
| `RUN_KEY` | Фаза с заменой `:` на `-` и номером попытки, например `HF-test.a2` |
| `CARD_BODY`, `PROMPT` | Подготовленные `$TASK_ROOT/in/$RUN_KEY-card.md`, `$TASK_ROOT/in/$RUN_KEY-prompt.md` |
| `CARD_KEY` | Уникальный `$WORK_ID:$PHASE:$ATTEMPT`; при неизвестном результате создания сначала искать карточку |
| `REPORT` | Новый `$TASK_ROOT/out/$RUN_KEY.md` |
| `JSONL`, `STDERR_LOG` | Новые `$TASK_ROOT/evidence/$RUN_KEY.jsonl`, `$TASK_ROOT/evidence/$RUN_KEY.stderr.log` |
| `PREVIOUS_ID`, `TASK_ID` | Реальные ID завершённого обязательного предшественника и текущей карточки; первая фаза без родителя, несколько входов — повторные `--parent` |
| `START_BASIS` | Разрешение, дата, фаза/попытка, входы с хешами, модель, рабочий каталог и область записи |
| `ROLE_RC` | Код `$?`, полученный сразу после Codex; заранее успех не подставлять |

Повторная REV сохраняет свой `TASK_ID`, получает новый `ATTEMPT` и `RUN_KEY`; номер попытки не заменяет `review_round`. Карточки решений не требуют файлов запуска и модели.

## Подготовка до claim

1. В разрешённой операторской среде создай отсутствующие `in`, `out`, `evidence` внутри `TASK_ROOT`; заранее подготовь согласованный `EXEC_ROOT` для реализации и тестов. Проверь существование `WORK_ROOT` и соответствие фазе.
2. Подготовь читаемые `CARD_BODY` и `PROMPT`: роль, SHA256 входов, цель, критерии, область записи, путь отчёта, запрет управлять доской и запускать другие роли. См. [форму карточки](records.md#карточка-фазы).
3. Убедись, что каталоги выходов доступны оператору для записи. Каждый из `REPORT`, `JSONL`, `STDERR_LOG` свободен: ни `test -e`, ни `test -L` не должны быть истинны, включая висячий симлинк. Пути различны и не совпадают с входами. При конфликте сохрани историю, выбери новые имена и обнови постановку и карточку; не удаляй предыдущие отчёты.
4. Создай карточку в `blocked` через [команду создания](commands.md#подготовка-и-карточка), сохрани ID и через `show` сверь её `--workspace "dir:$WORK_ROOT"` с будущим `codex -C "$WORK_ROOT"`. Для REV:report рабочий каталог — `TASK_ROOT`, кандидат читается по абсолютному пути. При отсутствии каталога, занятом выходе, ошибке подготовки или несовпадении каталогов `claim` не выполнять.

## Одна фаза и переход

Запиши основание, последовательно выполни `unblock → claim → show`, проверь `running`, каталог и отсутствие другого живого запуска. Перед Codex ещё раз проверь свободность трёх выходов: первая проверка их не резервирует. Команды и проверка результата — [здесь](commands.md#запуск-и-проверка). Установи завершение и rc, проверь отчёт, область, входы и критерии, запиши пути, хеши и вердикт, затем `complete`; при проблеме — факт и `block`.

Маршрут: `HF:plan → REV:plan → ДА владельца → HF:impl → HF:test → REV:report → приёмка`. Решение содержит автора, дату, источник, хеши плана и REV, точное действие; при приёмке также кандидат, тесты и итоговую REV. Новая версия кандидата после исправления требует нового отдельного HF:test и повторной REV:report; второй REQUEST-CHANGES останавливает цикл. Полные [правила исправления](commands.md#исправление-и-повторная-ревизия) и [связь версий](records.md#версия-кандидата-тесты-и-rev).

При ERROR/STOP/CANCEL — факт и блокировка; живой процесс останавливается отдельно, повтор без нового решения владельца запрещён. `ENV-03 = FAIL`; `H-OWNER = FAIL`, `H-WRITER` и `H-EGRESS = NOT_PROVEN`. Штатный Kanban не предоставляет стоп-лист «не перезапустится» и не даёт гарантий W1-09. [Остановка](commands.md#остановка-и-неизвестный-исход).
