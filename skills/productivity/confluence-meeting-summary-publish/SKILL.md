# Публикация саммари встречи на страницу Confluence

Частый сценарий: Саша даёт pageId на **уже созданную страницу** (есть title и parent, но body
пустой, version=1) + просит «собери в архиве из транскрипта саммари встречи N / зафиксируй, как
договорились считать X» и опубликуй туда. Это не создание страницы (POST) и не патч секции —
это **первый полноценный контент целиком** на предсозданной странице.

## When to Use

- Собрать из транскрипта встречи саммари и опубликовать на пустую страницу Confluence.
- Зафиксировать «как договорились считать / что решили» по конкретному показателю (KR/KAR,
  метрики) — итоги встречи живут в `- transcript.md`, а не в авто-саммари.
- Триггеры: «собери в архиве», «опубликуй на страничке …pageId», «зафиксируй итоги встречи»,
  «как договорились считать X».

## Процедура

1. **GET целевой страницы** `?expand=body.storage,version` — отличить случай от POST/PATCH:
   body length 0 + version 1 → заполняем **PUT c version.number+1 (==2)** полным body.
   POST не нужен (страница уже есть, иначе дубль), section_patch не нужен (нечего целиться).
2. **Найти встречу в архиве** — `search_meetings` из `~/USERTOOLS/MofsIndex` по дате/участнику/
   теме (скилл `workvault-rag`), проверить кратким запросом даты ±2 дня + ключевое слово
   (напр. `query="KR1", date_from=.., date_to=..`). Это надёжнее ручного поиска по `13.11.26`.
   Файлы лежат парой в `WorkVault/Meetings/NewMeetings/`: `<дата> <название> - summary.md` и
   `- transcript.md`.
3. **Читать и summary, и transcript.** Auto-summary (Fireflies/MOFS) часто тонкий и теряет
   аргументацию/нюансы решений — особенно при запросе «зафиксировать как договорились считать
   KR/KAR» сами формулировки («считать через навык мини-ресёрч», «исключить обращения Юры»,
   «запросить отчёт у Лаптевой») живут в репликах транскрипта, не в summary.
4. **Структурировать документ сам** под бриф Саши: H1 «<Проект>. Расчёт показателя X» →
   участники/дата → «Как считаем/договорились» (решения, по разделам на каждый показатель) →
   «Рассмотренные альтернативы» (не принятые как основной способ, с причиной) → «Задачи/Риски».
   Акцент строго по брифу, без канбан-жаргона. **Когда сводка собирает договорённости из НЕСКОЛЬКИХ
   встреч в один раздел («все встречи по X, по каждому KR»)** — возле каждого пункта в скобках
   указывать, из какой встречи он пришёл (дата + короткое название), это явное требование Саши.
5. **Сборка storage:** секции-хелперы (`h2`/`p`/`ul`+`li`), текст через `escape()` только на
   текстовых кусках, структурные теги литеральные (детальнее — питфолл «НЕ пропускать HTML через
   эскейпер» в `tutu-confluence-jira`). Payload PUT: `title` + `type:page` + `version.number+1` +
   полный `body` — **`space` не передавать**.
6. **Верификация (обязательный повторный GET):** version поднялась (==2); ключевые маркеры
   каждого h2-раздела и решений на месте как подстроки; `body.count('&lt;') == 0` (не протекли
   экранированные теги); счёт `h2`/`li` в ожидаемых пределах.

## Питфоллы

- **HTTP 409 на PUT — не баг, а устаревшая версия:** если тело страницы успело подняться
  (кто-то/что-то тронул страницу между твоим GET и PUT), Confluence отвечает 409 независимо от
  того, каким был `version.number`. НЕ пытайся слепо `version+1` от старого GET — повторно GET
  актуальную `?expand=body.storage,version`, возьми её текущий `version.number` и PUT с этим+1.
  При 400 — тело не принято (см. ниже), при 409 — всегда перечитать текущую версию.
- **HTTP 400 «Error parsing xhtml: Unexpected close tag … expected </strong>» = несбалансированный
  inline-тег в собранном storage.** Confluence валидирует XHTML, поэтому каждый `<strong>`/`<b>`/
  `<span>` должен быть закрыт. Перед PUT явно проверять баланс: `body.count('<strong>') ==
  body.count('</strong>')` (и по другим inline-тегам). Провал парсинга XHTML не «неудача», а явный
  резон вернуться в сборщик и закрыть тег.
- **Утечка `<function B at 0x…>` в body = вызов хелпера без скобок.** Если при f-string-сборке
  передал `f"{B}(текст)"` вместо `f"{B('текст')}"`, в body попадёт repr функции, а не её
  результат, и один `<strong>` останется незакрытым (отсюда 400). Когда видишь `<function … at
  0x»` в теле или в логе 400 — ищи вызов хелпера без `()`. Проверять `'<function' not in body`
  вместе с балансом тегов.
- **При 400/409 подменять `version.number` в payload и повторять PUT** — тело не переписывать
  заново: payload уже готов, достаточно одного инкремента и попытки.
- **Путая версия страницы:** если у тебя pageId уже заполнен (body>0), это другой сценарий
  (патч/сверка) — не перезаписывать целиком без подтверждения.
- **`get_meeting(mid)`/`get_meeting_body(mid)` может вернуть None** для свежих встреч, не
  проиндексированных в MOFS — не значит «нет файла»; идти прямо в `NewMeetings/` по имени файла.
- **Не искать файл по дате как `13.11.26`/`2026-11-13` бессмысленным файловым поиском** (даёт
  тонны `.git`). Правильный вход — `search_meetings` или glob по имени файла, который содержит
  полную дату `YYYY-MM-DD HH-MM-SS <название>`.
- **Публикация на предсозданную страницу = PUT version+1, title сохранить как есть** (даже если
  title содержит мусор/опечатки — не менять без явной просьбы, только тело).
- Требование «опубликуй» — императив, действуй без переспроса после сборки контента.
