# Архитектор-бриф по документу (релейный режим)

Когда задача — содержательный документ/фреймворк (методика, устав, описание процесса), и заказчик ведёт бриф через архитектора (codex CLI) — Сирень **чистый реле**. Роль задаётся явно: «общаемся только с архитектором, уточнения и рекомендации даёт только архитектор, не делай своих выводов».

## Роль Сирени: реле, не советник

- Передаёт **замечания заказчика** архитектору дословно, по разделам, с нумерацией по названиям пунктов — одним follow-up файлом через `--resume`.
- Возвращает **ответ архитектора** заказчику дословно, от первого лица архитектора; Сирень только канва/шапка.
- Сама **НЕ формирует** собственные выводы, варианты, рекомендации, оценки — даже если кажутся очевидными. При нарушении заказчик поправляет: «не делай своих выводов, пусть архитектор решает».
- Не фильтрует и не поддакивает при возражениях архитектора к решению заказчика — архитектор аргументирует из мировой практики сам.

## Механика итерационного цикла

```
замечания заказчика → follow-up файл → invoke-role (codex CLI) --resume <sid>
  → ответ архитектора заказчику дословно → следующий вопрос
```

- Один вызов = одна модель = одна роль (`gpt-6-astra` архитектора через codex CLI).
- Follow-up пиши **файлом**, не инлайном (gateway-guard).
- Одна сессия держится на `--resume <session_id>` до закрытия всех развилок; новую не заводи.
- Архитектор правит **тот же файл-результат**, источники не трогает (заказывать явно в каждом follow-up, если нужно).

## Брифы-развилки от архитектора

Архитектор возвращает список открытых вопросов-развилок. Отдавать заказчику **по одному за раз**: контекст (1–2 строки) → рекомендация архитектора с обоснованием из мировой практики → альтернативы «которые хуже, и почему». Ждать ответа на каждый, потом следующий. Всю пачку не вываливать.

Перед запросом следующего брифа **зафиксировать ответ заказчика** в статус-заметку/документ (какие развилки закрыты, какое решение) — решения не терять при сбое сессии.

## Архитектор ставит цифры сам — прогонять через заказчика

Архитектор часто закрывает раунд со словами «блокирующих развилок нет» и при этом сам вставляет числовые параметры «по мировой практике» (лимит параллельных задач, пороги эскалации, сроки). Это **не развилка от архитектора**, но и не согласованное заказчиком решение — **НЕ принимать молча**. Перед финализацией отдать заказчику коротким списком: что поставил сам, цифры, «устраивают?».  
Правило согласуемости: такие параметры по требованию заказчика фиксируются в документе как **согласуемые Заказчиком и Руководителем ПА, не константы** — при обкатке их можно скорректировать (не единственное место, эта формула дублируется и в разделе про согласование документа). Передать эту пометку архитектору, чтобы прогнал по всем местам, где параметр упомянут.

## Режим сбора замечаний (аудит без правок)

Во время финальной вычитки заказчик часто ведёт **режим сбора**: диктует замечания по одному и явно (или по умолчанию из первой формулировки «сейчас ничего не правим, только собираем замечания для передачи архитектору») запрещает трогать файл. Правила режима:
- **НЕ править документ и не запускать архитектора** на каждое замечание — только вести накапливающийся нумерованный список.
- Каждый пункт: номер + раздел (по названию пункта, не по номеру «вариант N») + формулировка замечания одной строкой.
- Содержательный вопрос, на который заказчик просит мнение архитектора, помечать `**[Развилка]**` прямо в пункте (развилки не решать самому).
- Подтверждать заказчику накопление коротко («принято», сверить с текущим текстом файла, если нужно) и один раз показывать полный актуальный список.
- Когда заказчик скажет «передай архитектору» — один follow-up-файл со всем списком (прямые правки вносятся сразу, развилки разбираются предложенной архитектором рекомендацией).

## Декодирование правок в редакционных раундах

Заказчик правит документ в теле файла, а не списком замечаний. Правила чтения его разметки:
- ~~зачёркнутый текст~~ — удалить / заменить (заказчик это исключает; рядом может стоять его текст-замена — тогда принять замену, а не удалять).
- `*(курсив в скобках)*` — комментарий / пожелание / вопрос, обращённый к архитектору. Каждый разбирается: мелкое — исправить сразу; содержательное (требующее решений по мировой практике) — предложить архитектору и при необходимости вынести в бриф-развилку. Зачёрк в тексте после обработки не остаётся.
- Прямые правки без разметки — просто новый текст, принять как есть.
- Мета-фразы типа «это чтобы ты исправил», «трудно запутаться» в теле — были указанием автору, в НОРМУ не попадают: переносить дословно нельзя.
- Все имена сущностей Словаря — с большой буквы и **жирным** при первом употреблении, единообразно.

## Ревизорский проход (после раунда правок, перед финализацией)

Цикл по требованию заказчика: архитектор обработал раунд → **ревизор** (claude-sonnet-5-medium, отдельная сессия) сверяет каждую правку по смыслу и возвращает недочёты → недочёты одним follow-up архитектору → финал. Полный регламент и pitfall по доставанию полного отчёта ревизора — `references/reviewer-verification-pass.md`.

**Сверять фактические правки, а не отчёт агента.** После раунда, до запуска ревизора, проверяй сам файл grep-ом по ожидаемым маркерам каждого замечания (заголовки разделов, новая терминология, что удалённое/заменённое отсутствует — например `grep -c "СтарыйТермин"` должно быть 0). Отчёт архитектора «внёс все пять правок» не заменяет проверку на диске: агент может переписать размер/числа строк или пропустить место. Расхождение «ожидаем N маркеров, нашли M» ловится до подачи ревизору.

## Pitfall: таймаут на большом рерайте документа

Большой рерайт файла целиком (>50–80 КБ, десятки секций) часто превышает таймаут роли (codex CLI) — JSON вернётся `timed out` или оборвётся. **НЕ перегенерировать задачу с нуля** (токены сгорят). Сначала проверить файл на диске: `wc -l -c <file>` + сверить mtime/размер и наличие ожидаемых заголовков. Если файл уже переписан — это успех; восстановить только потерянный блок (список брифов / квит) коротким follow-up через `--resume`: „файл уже обновлён, верни только вопросы-брифы“. Проверять на диске всегда, не только при таймауте (см. self-report правило codex CLI).

## Доставка результата заказчику

Файл-результат кладётся в `~/WorkVault/Outbox/` (см. `workvault-outbox`), синкается `systemctl --user start owncloud-sync.service`, доставка подтверждается `rclone lsjson owncloud:WorkVault/Outbox/` (exit 0 ≠ файл ушёл). Новые версии — тот же путь.
