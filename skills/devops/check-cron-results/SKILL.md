# Check Cron Results

## Когда загружать
- Когда ждёшь завершения Opus-крона
- Когда Саша спрашивает «что там по крону X», «готово?», «уже час прошёл», «проверяй»
- Когда нужно убедиться что задача выполнена

**Железное правило: статус только из живых данных.** Никогда не отвечать «ждём ещё X минут» без проверки. Даже если задача только что запустилась — сделать `cronjob(action='list')` и прочитать output. Прецедент 27.07.2026: ответ «ждём» оказался ложью — крон уже завершился.

## Инструкция

### Шаг 1 — читай журнал
```
read_file("~/.hermes/cron-journal.md", limit=60)
```
Последние строки журнала = самые свежие результаты.

### Шаг 2 — если нужны детали по конкретному крону
Из строки журнала возьми `output: <путь>` и прочитай файл:
```
read_file("<путь из журнала>")
```
Ищи секцию `## Response` — там полный отчёт агента.

### Шаг 3 — если журнал пустой или задача не нашлась
Проверь напрямую:
```bash
ls -lt ~/.hermes/cron/output/ | head -10
cat ~/.hermes/cron/output/<job_id>/<файл>.md
```

## 🔴 Известные реальные проблемы (требуют починки)

### no_agent Script с `&&` — Script not found
**Симптом:** крон падает с `Script not found: /path/script.sh && bash /path/other.sh`
**Причина:** `no_agent=True` раннер передаёт всё поле `script` как путь к файлу — `&&` и всё после него трактуется как часть имени.
**Диагностика:** `last_status: error` в `cronjob list`, в output-файле крона — `Script not found: <длинная строка с &&>`
**Починка:** обновить крон через `cronjob action=update`, вынести составную команду в отдельный `.sh`-скрипт-враппер, в поле `script` указать только путь к нему.
```bash
# Пример враппера ~/.hermes/scripts/autosync_full_with_cleanup.sh
#!/bin/bash
bash ~/.hermes/scripts/autosync_github.sh && bash ~/.hermes/scripts/cleanup_after_sync.sh
```

## [SILENT] — общее правило точного совпадения (не только для dialogbacklog)

**Механизм (проверено в `cron/scheduler.py`):** доставка результата кроны подавляется ТОЛЬКО если весь финальный ответ агента строго равен `[SILENT]` (регистронезависимо, но без единого лишнего символа до/после). Это НЕ «упомяни [SILENT] где-то в ответе» — это «ответ должен состоять ровно из этого слова».

**Симптом сбоя:** Саша получает в Telegram полный текст с `[SILENT]` где-то внутри вместо тишины — крон отработал штатно (exit code 0/1, нечего сообщать), но промпт кроны сформулирован нечётко («ответь `[SILENT]`»), и модель (особенно Haiku) добавляет вокруг маркера пояснения/префиксы → строгое совпадение не проходит → система считает ответ обычным сообщением и доставляет его целиком.

**Диагностика:** прочитать `prompt` кроны в `cronjob(action='list', job_id=...)` или в `~/.hermes/cron/jobs.json` — если там написано что-то вроде «ответь `[SILENT]`» без уточнения «и больше ничего», это кандидат на тот же баг.

**Починка — формулировка промпта кроны:**
```
Плохо: Если exit code 0 или 1 — молчи (только лог), ответь `[SILENT]`.

Хорошо: Если exit code 0 или 1 — твой финальный ответ должен состоять
РОВНО из текста [SILENT] и больше ничего — ни пояснений, ни префиксов,
ни markdown, ни новых строк до/после. Просто [SILENT] как единственное
содержимое ответа.
```
Применить через `cronjob(action='update', job_id=..., prompt=...)`.

**Проверять при любом ревью промптов кронов с фоновой/тихой доставкой** — не только dialogbacklog. Найти все такие кроны: `grep "SILENT" ~/.hermes/cron/jobs.json`.

## ⚠️ One-shot кронджоб для делегирования Opus (research-паттерн из tz-workflow A0) — доставка и поиск результата

Когда создаёшь одноразовый `cronjob` (schedule = конкретная дата/время или `action='run'` сразу после `create`) для делегирования длинной research-задачи на Opus (см. `tz-workflow` процедура A0, `about_usr_skills` "Делегирование на Opus длинных задач через cronjob"):

- **Не полагайся на дефолт `deliver`, если сессия не gateway-подключена (CLI/TUI/API-сессия без Telegram/Discord).** При `create` без явного `deliver` документация обещает автодоставку "в текущий чат", но фактически в такой сессии резолвится в `deliver: "local"` — результат сохраняется, но НЕ придёт сам в диалог. Если нужен возврат в текущий тред — **сразу указывай `deliver` явно** (например `telegram:<chat_id>:<thread_id>`), не дожидайся первого запуска чтобы это заметить.
- **`action='run'` может "сжечь" one-shot задачу даже без ошибки** — сразу после ручного запуска (`action='run'`) задача способна исчезнуть из `cronjob(action='list')` на следующем же вызове (в том числе при `execution_success: false` от быстрого промежуточного статуса). Не считай это багом/потерей результата — план был на будущее время, `run` его просто выполнил раньше срока, и одноразовая запись после выполнения из реестра убирается.
- **Если задачи нет в `list`, но она точно выполнялась — результат почти наверняка уже готов на диске.** Искать напрямую:
  ```bash
  ls -la ~/.hermes/cron/output/ | grep <job_id_prefix>
  ```
  Файл вида `<job_id>_<YYYYMMDD>_<HHMMSS>.txt` — читать через `read_file`, весь текст финального ответа агента лежит там же (не нужно ждать журнал/доставку).
- Не путать с описанным ниже правилом `[SILENT]` — это про намеренное подавление доставки; здесь же результат просто физически не долетел до чата, хотя и не был предназначен молчать.
- **`schedule` = конкретный ISO-таймстамп, который уже прошёл (или совпадает с текущим моментом) → `next_run_at: null` сразу после `create`, задача НЕ выстрелит сама.** Планировщик не запускает one-shot задачу автоматически, если целевое время уже в прошлом на момент создания — только фиксирует её как scheduled с `next_run_at: null`. Починка: сразу после `create` вызвать `action='run'` тем же `job_id` вручную — не ждать и не пересоздавать job с другим временем.
- **`execution_success: false` в ответе `action='run'` — НЕ надёжный индикатор провала.** Проверено дважды в одной сессии (Opus-план и Sonnet-билд оба вернули `execution_success: false`, при этом оба реально отработали успешно — файлы созданы, тесты прошли, боевая Confluence-страница реально изменена). Не делать выводов по одному этому полю — всегда проверять реальный результат: для агентного job (`no_agent=false`) — файл в `~/.hermes/cron/output/<job_id>/`; для `no_agent=true` script-job, доставляющего прямо в внешний канал (Telegram и т.п.) без сохранения output-файла в принципе — `search_files` по `~/.hermes/cron/output/` вернёт `0` результатов даже при полном успехе (это ожидаемо, не признак сбоя) — в этом случае нужно спросить пользователя напрямую, дошло ли сообщение, а не делать вывод по отсутствию файла.

## ⚠️ Известные ложные тревоги (не считать PROBLEM)
- `DialogBacklog` не имеет `.venv` — нормально, только stdlib
- Нет юнита `hermes-cron.service` — нормально, кроны идут через `hermes-gateway`
- Windows-пути в DEFAULT_DB / DEFAULT_FILE в старых скриптах — исправлено 03.06, не блокируют работу
- `hermes-gateway.service` запущен — это и есть основной процесс, отдельный cron-юнит не нужен

## Если Саша говорит «потерял связь с ТГ» / gateway не отвечает

Сразу проверить:
```bash
systemctl --user status hermes-gateway.service --no-pager | head -10
```
Если `failed` или `inactive` — рестартовать:
```bash
systemctl --user restart hermes-gateway.service && sleep 3 && systemctl --user status hermes-gateway.service --no-pager | head -5
```

Причину падения смотреть через лог (journalctl недоступен без прав adm/wheel):
```bash
cat ~/.hermes/logs/gateway.log | tail -60
```
Ключевые паттерны в логе:
- `SIGTERM` + `drain timed out` → systemd убил gateway, drain 180s не завершился, exit code 1
- `Restart=on-failure` должен поднять сам, но если не поднял — рестартовать вручную
- `httpx.ReadError` / `RemoteProtocolError` → сетевая ошибка ТГ, gateway восстанавливается сам (attempt N/10)

## Работа с dialog-backlog вручную

### Пакетное закрытие нескольких bk-пунктов
Когда Саша говорит «закрой bk-103, bk-104, bk-106» — не делать patch по одному. Использовать `execute_code` с циклом:
```python
from hermes_tools import patch

path = "/home/tkachenkoav/WorkVault/Hermes-Backlog/dialog-backlog.md"
changes = [
    {"old": "- [ ] ...", "new": "- [x] ...\n  - 💬 Закрыто ДД.ММ.\n  - 📅 ... · `closed:: YYYY-MM-DD`"},
    # ... остальные
]
for c in changes:
    patch(path=path, old_string=c["old"], new_string=c["new"])
```
После каждого пакета — обновить `last_scan_at` в frontmatter.

### Снятие задачи (не закрытие)
Если Саша говорит «снимаем задачу» — это НЕ просто `[x]`. Добавить контекст почему снята:
```
- [x] Текст задачи ^bk-NNN
  - 💬 Снято ДД.ММ: <причина>.
  - 📅 `created:: ...` · `updated:: YYYY-MM-DD` · `closed:: YYYY-MM-DD`
```

### `[SILENT]` от vm_dialogbacklog — норма
Если Саша вручную закрыл/снял пункты, а потом запустить крон — крон вернёт `[SILENT]`.
Причина: агент сравнивает open-пункты с `last_scan_at`, новых нет → подавляет доставку.
Это **не баг**, это ожидаемое поведение. Объяснять Саше при необходимости.
