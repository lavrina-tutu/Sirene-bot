# Адресная правка контракта (нормы) по вердикту архитектора

Класс задачи: вердикт архитектора меняет контрактный токен (формат/разделитель/версию),
кандидат уже реализует новое, оркестратор синхронизирует норму и доставляет GATE:done.

## Процедура

1. **Определить, где живёт норма** — grep по старому токену во всём `out/` поезда, не по
   названию «мастер-ТЗ». Норма поезда — его собственный план `out/HF-plan-*.md`
   («единственный изменяемый файл текущего хода»); `DevWorkflow_TZ.md` может вообще не
   содержать токена (grep даёт 0) и не быть целью правки.
2. **Патчить КАЖДОЕ вхождение токена**, не только строку, названную вердиктом: объявление
   типа (enum), строка формата, regex, таблицы допуска в `PREP-*.md`, frontmatter версии.
   Пропущенное вхождение оставляет расхождение нормы и кода в смежном документе.
3. **Бампнуть версию frontmatter** плана + строка «Адресная редакция …» с обоснованием
   (вердикт + решение владельца), чтобы редакция была трассируемой.
4. **Кандидат не трогать**, если он уже реализует новый формат (grep по `candidate/`
   подтверждает); правка docs-only.
5. **Верификация**: таргетированный поднабор тестов по теме (`pytest … -k <topic>`,
   напр. `-k receipt`) + `git status` чист / HEAD не изменился. Полный многочасовой набор
   не перегонять — он уже зелёный на зафиксированном HEAD (последний CLOSE), docs-only
   правка его не затрагивает.
6. **Зафиксировать evidence** (файл CONTRACT-PATCH-*.md в `evidence/` поезда) и отдать
   отчёт по GATE:done: что изменено, что проверено, открытые зависимости — предметно,
   без канбан-жаргона.

## Питфоллы

- Вердикт цитирует одну строку → искать токен по всему `out/`; строка из вердикта —
   указатель, не полный список мест.
- Не патчить исторические артефакты допуска как «историю»: таблицы допуска (PREP-*)
   синхронизировать с нормой, иначе admission расходится с контрактом.
- Проверять остатки старого токена после правки (search по `out/` даёт 0) до доставки.
