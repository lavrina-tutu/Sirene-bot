## Контракты экосистемы

### Источник истины
- Владелец записи: Jira (задачи типов Objective/KR в проектах OKRS/OKRAID); локальный кэш per-task MD в `WorkVault/Projects/okr-tool/<period>/`

### Входные контракты
Нет внешних входящих контрактов экосистемы (данные получаются напрямую из Jira REST API v2 и из MD-файлов SRTool в ходе брифа без формализованной контрактной схемы).

### Выходные контракты
Нет внешних исходящих контрактов экосистемы (данные передаются напрямую в Jira REST API v2 и в Google Sheets через OKRSheetsExporter без передачи другим инструментам экосистемы).

### Зависимости
- Получает от: [SRTool, Jira]
- Отдаёт: [Jira, SRTool]

### Breaking changes policy
- Версионирование формата: semver на уровне структуры per-task MD и конфига `okr_metrics_map.json`
- При breaking change: обновить структуру фронтматтера MD, применить скрипт миграции

### Границы («что НЕ трогать»)
- Не писать в Jira без финального подтверждения пользователя
- Не изменять статус задач в Jira (только чекин-поля)
- Не затирать per-task MD при сбое соединения с Jira

## 1. Философия

### Что делает OKRTool

- Работает с целями (Objective) и ключевыми результатами (KR) в Jira ТУТУ (проекты OKRS, OKRAID)
- **Читает:** выгружает иерархию Objective→KR через Jira REST API + issuelinks Contains
- **Пишет:** заполняет поля вкладки ЧЕКИН (уверенность, что сделано, риск, текущее/плановое значение метрики, % выполнения)
- **Локальное кеширование:** сохраняет per-task .md файлы в `WorkVault/Projects/okr-tool/` как источник истины по умолчанию (Правило №0 — не ходить в Jira если данные уже на диске)
- **Бриф-режим:** обсуждает заполнение каждого чекин-поля с пользователем последовательно (KR → Objective), записывает в MD, в Jira — только после финального согласования
- **Источники данных для чекина:** Self-Review (SRTool), протоколы встреч, сообщения Loop, Confluence-страницы

### Чего НЕ делает

- Не пишет в Jira без финального подтверждения пользователя
- Не меняет статус задач (только чекин-поля)
- Не создаёт новые KR/Objective без отдельного явного процесса (клонирование — отдельная фича)
- Не работает с чужими задачами (фильтр по assignee)

### Ключевой принцип: данные из SR — в чекин OKR

**Self-Review (SRTool)** — основной источник фактов для заполнения чекина.  
Пользователь пишет SR за период → Сирень сопоставляет пункты SR с OKR-задачами → предлагает заполнение чекин-полей.

## 2. Основной флоу: чекин OKR по итогам SR

### Шаги

```
1. Пользователь → TG: «актуализируй чекин по моим OKR за <период>»

2. Сирень:
   a. JQL: находит задачи пользователя в OKRS/OKRAID за указанный период
      (фильтр: assignee = текущий пользователь, fixVersion = <период>)
   b. Выгружает текущие чекин-поля из Jira
   c. Сохраняет per-task .md в WorkVault/Projects/okr-tool/<period>/
   d. Читает SR пользователя за период из WorkVault (SRTool)
   e. Сопоставляет пункты SR с OKR-задачами
   f. Готовит предложения по каждому чекин-полю

3. Бриф (поле за полем, KR → Objective):
   a. Сирень предлагает значение поля
   b. Пользователь: «ок» / правка / «посмотри в <источник>»
   c. Сирень: применяет, записывает в MD
   d. Повтор для каждого поля каждого KR
   e. Objective: обобщает согласованные KR

4. Финал: пользователь → «запиши в Jira»
   → Сирень PUT /issue/{key} для каждой задачи
   → Верификация GET + ссылки на задачи
```

### Формат per-task MD

Один файл на задачу: `<KEY>_<первые ~80 символов summary>.md`

```markdown
---
key: OKRS-3119
type: KR
status: В работе
assignee: Ткаченко Александр Владимирович
fixVersions: Q3 2026
source: https://hq.tutu.ru/browse/OKRS-3119
fetched: 2026-08-06
---

# <KEY> — <summary>

## Текущий чекин (Jira)
| Поле | Значение |
|---|---|
| Уверенность | ... |
| Что сделано | ... |
| ... | ... |

## Предложение по чекину (на основе SR <период>)
> Источник: <ссылка на SR>

| Поле | Предложение |
|---|---|
| ... | ... |
```

## 4. Закрытые решения брифа (06.08.2026)

1. **Единое место хранения per-task MD:** `WorkVault/Projects/okr-tool/<period>/` — все файлы переносятся туда. Entities не используется для OKR-данных.

2. **Автоматическое сопоставление SR→OKR:** гибридный подход. Сначала ключевые слова (название KR / ID / метрика) в тексте SR для автоматического матчинга. Неподтверждённые матчи выносятся на ручной бриф.

3. **Обобщение KR→Objective:** % выполнения = среднее арифметическое по всем KR. Поля «Что сделано» и «Риски» = текстовая агрегация (объединение) из всех KR.

4. **OKRAID vs OKRS:** единая абстракция «OKR-задача» на уровне скилла. Скрипт сам резолвит различия (типы связей, обязательные поля) по типу проекта.

5. **Клонирование KR между кварталами:** отдельный блок в ТЗ — «Клонирование KR». Копирование задачи с обновлением fixVersion и адаптацией связей.

6. **Google Sheets экспорт:** выделен в отдельный мини-инструмент OKRSheetsExporter. Ручная команда «экспортируй OKR в Sheets», не часть основного чекин-флоу.

7. **Внешние метрики (Loop, Confluence):** сервис-слой OKRMetricsResolver. По ключу OKR возвращает структурированные данные из всех источников. OKRTool вызывает резолвер, не знает про API-детали.

## 5. Новые функциональные блоки (по итогам брифа)

### 5.1 Клонирование KR

- Пользователь → «склонируй KR в Q4 2026»
- Скрипт: читает per-task MD → создаёт копию задачи в новом квартале → обновляет fixVersion → адаптирует связи (Contains для OKRS, «связано с» для OKRAID) → сохраняет MD
- Ручная проверка в брифе перед записью в Jira

### 5.2 OKRMetricsResolver

- Сервис-слой: конфиг-файл маппинга OKR→источник→параметры
- Источники: SRTool (факты из SR), MoveFromLoop (метрики команды), ConfluenceSync (план-факт)
- Интерфейс: `resolve(key)` → `{metric_name, value, source, confidence, period}`
- OKRTool вызывает `resolve(key)`, не работает с API напрямую

### 5.3 OKRSheetsExporter (отдельный мини-инструмент)

- Ручная команда: «экспортируй OKR за <период> в Sheets»
- Читает per-task MD из `Projects/okr-tool/<period>/`
- Формирует сводную таблицу: Objective, KR, %, уверенность, риски, что сделано
- Push в Google Sheets через скилл `google-workspace`

## 7. Решения при реализации v0.1.0 (06.08.2026)

### 7.1 Jira issueLinkType ID (живой прод)
- OKRS: Contains (id=11400)
- OKRAID: Link / «связано с» (id=10003)
- Источник: GET /rest/api/2/issueLinkType, зафиксировано в okrtool/okr_task.py

### 7.2 Место хранения okr_metrics_map.json
- WorkVault/Registries/okr_metrics_map.json
- По аналогии с entities.json (Registries — канонические реестры)
- ENV-override: OKR_METRICS_MAP_PATH

### 7.3 Терминологическое разграничение confidence
- resolver.confidence (high/medium/low) — уверенность в качестве/свежести резолвленных данных
- customfield_43706 (Уровень уверенности в Jira) — семантика «On Track»/риск по цели
- brief.py НЕ копирует одно в другое автоматически

### 7.4 Статус миграции per-task MD
- Скрипт: scripts/migrate_okr_md.py (dry-run + --apply)
- Откуда: Entities/okr/ → Куда: Projects/okr-tool/
- Конфликты: archive в _archived_pre_migration/
- Report/index_stub файлы: переносятся в Projects/okr-tool/_reports/
