# Оркестрация цикла доработки плана: HF:plan ↔ REV:plan

## When to Use

- REV:plan вернул REQUEST-CHANGES по плану разработки: вести rework-цикл.
- **Любая фаза-ревизор вернула REQUEST-CHANGES («Блокирующие» → «Что требуется»)
  по своему предмету — тот же цикл доработки (напр. REV:tz → rework TZ:patch).**
- Многократные REQUEST-CHANGES подряд с РАЗНЫМИ блокерами в каждом раунде.
- Проверка плана на целостность до emit: covers↔IAC-карта↔§7↔allowlist closure.

Предметная надстройка над `dev-workflow/SKILL.md` — НЕ заменяет его: читать
umbrella каноном первыми (его `references/operational-pitfalls.md` — в соседнем
скилле dev-workflow). Этот скилл фиксирует оркестраторские механики многократного
REQUEST-CHANGES-цикла и типовые классы прорех, которые ревизор ловит в плане
до кода.

## REQUEST-CHANGES с РАЗНЫМИ дефектами — нормальный путь, продолжать

Каждая ревизия плана, вернувшая REQUEST-CHANGES, вскрывает новые (не те же)
прорехи — это ожидаемая итерационная доводка, НЕ «Повтор замечания» (Б55.5).
Счётчик «два одинаковых REV» срабатывает только когда повторяется ТОТ ЖЕ объект/
контракт/суть дефекта. Разный номер замечания, разный AC-ID или разная строка
плана = разные дефекты; регламент повтора путь НЕ останавливает. Несколько
Несколько подряд идущих REQUEST-CHANGES (до 4+) при разных блокерах — норм; поезд идёт
24/7, не сообщать Саше об остановке по этой причине.

## Блок «## Вердикт» парсится буквально: контекст чужих фаз превращает APPROVE в REQUEST-CHANGES

`pipeline_gates.rev_verdict(slug, phase)` читает абзац сразу после заголовка `## Вердикт`
(до следующего `##`) и классифицирует его по **первому** совпавшему слову:
`REQUEST-CHANGES` матчится раньше `APPROVE`. Поэтому блок вердикта должен содержать только
заголовок, `**APPROVE**|**REQUEST-CHANGES**` и суть согласованного; контекстные замечания о
других фазах (например «REV-plan.md=REQUEST-CHANGES не отменяется») выносить в раздел ниже.
Написанное внутри блока такое упоминание заставляет парсер вернуть REQUEST-CHANGES при
фактическом APPROVE — `complete-phase` по фазе запрещён, поезд застревает в doing.

Оркестратору перед `complete-phase` сверять фактический `rev_verdict` по канону (python:
`pipeline_gates.rev_verdict(slug, phase)`), а не предполагать по тексту роли.

Ошибочный блок вердикта нельзя исправить ручной правкой канона или промпта: (а) адресная
правка канона после invoke ломает G2 `result output changed` (output_snapshot сверить с диском),
(б) добавление текста в уже эмитированный `/tmp/*.md` ломает G2 `packet/prompt stale`. Единственный
штатный путь — донести формулировку до роли через **input-запись в контракте фазы ДО emit**: сохранить
оригинал канона роли (`cp REV-*.md REV-*.md.orig-*`) и вернуть его на диск, создать файл-инструкцию
(что в блоке вердикта не должно быть REQUEST-CHANGES/чужих фаз), добавить его входом
`inputs.<phase>` в HF-plan.md с `purpose` (правка ДО emit — разрешённый канал оркестратора, не G2-drift),
затем emit-prompt заново и invoke роли — она сама перепишет канон. `purpose` — YAML-строка: без `##`, без незакавыченного `: ` (двоеточие-пробел) внутри, без вложенных списков, иначе emit падает «mapping values are not allowed here» и out-файл не создаётся. Значение с `: ` кавычить целиком. Перед complete снова проверить `rev_verdict`.

## Последовательность каждого REQUEST-CHANGES-цикла

1. Прочитать REV-plan.md: секция «Блокирующие» → «Что требуется». Разобрать
   каждый блокер отдельно — общий хвост их не закрывает.
2. Записать triage-карточку (idea) с полным списком блокеров этого раунда и
   требованием к новой ревизии.
3. **Развилка: чем закрывается REQUEST-CHANGES** — repair-to-HF:plan (план)
   ИЛИ повторный ТЗ-круг (норматив):
   - Если блокеры закрываются правкой самого плана → канон ниже: repair →
     REV:plan → todo + `rework_request`, HF:plan → WORK/awaiting.
   - Если блокер требует изменения НОРМЫ master-ТЗ (правка чужого/общего
     контракта, «примени дельту через TZ:patch→REV:tz→TZ:finalize», NORM-<N>) —
     это **пересмотр требований** (Б55.5), а не доработка плана. Тогда рельсу
     перематывать событием `rev_request_changes_rewind`: `TZ:patch → doing`
     (awaiting_invoke, pid/context сброшены), все фазы ПОСЛЕ TZ:patch → todo,
     фазы ДО него (BUG:diagnose, GATE:diagnose-review) остаются done — факты
     диагностики в силе, второй круг их не переделывает; `st.phase=TZ:patch`,
     `st.status=in_phase`. Затем `next` → WORK TZ:patch, `emit-prompt` с
     `--master-tz <путь>` (без него TZ:patch не собирается), invoke architect —
     он вносит дельту; дальше REV:tz → TZ:finalize → GATE:take-into-work →
     снова HF:plan под новым master.
   **НЕ вызывать `complete-phase` по REV:plan**
   при REQUEST-CHANGES — он запрещён (rc=1 «REV REQUEST-CHANGES: complete
   forbidden»); по REV-фазе complete вызовется только на APPROVE.** Полный текст
   замечаний в `rework_request` — контекст + объект + конкретное требование,
   каждый блокер целиком (многострочный), не краткое «исправить».

**`rework_request` кладётся в `phase.proof.rework_request`, а НЕ в топ-уровень
`phase.rework_request`.** Единственный читатель — `emit-prompt`, он берёт его из
`proof.rework_request` в виде `{"source": <фаза-источник>, "ref": <RefDict>}` и
только тогда собирает пакет `kind: rework` (и встраивает референс на ревью).
`ref` = `pipeline_context._ref(Path(<канон вердикта>))` (path/resolved_path/
sha256/size/mtime). Рекомендуется `source`=фаза-источник (напр. `REV:tz`) и `ref`
на фактический REV-tz.md вывода. Если это поле положено в top-level фазы,
`emit-prompt` вернёт forward-пакет без rework-маркера и архитектор получит
только краткую цель без полных блокеров. Проверять на собранном пакете
`grep '"kind"'` → `"rework"`.
4. `emit-prompt` → `/tmp/task_hfplan_revise<N>.md` (rc=0).
5. `invoke-role --role architect` ФОНОМ (background=true + notify_on_complete +
   persist_on_release). Foreground / без background=true → «notify only applies
   to background commands».
6. Прочитать новый вердикт, complete-phase HF:plan (reason+evidence path), next
   → REV:plan, emit, фоном invoke reviewer.
7. На APPROVE — complete REV:plan, next по рельсе (HF:backup→HF:impl→HF:test).

`rework_request` несёт ПОЛНЫЕ формулировки блокеров из REV-plan.md (контекст +
объект + конкретное требование), не краткое «исправить». Архитектор адресно
закрывает каждый пункт.

## APPROVE с admission-гейтом: не next вслепую, hold и вопрос владельцу

REV может дать APPROVE, но с `implementation_admission: WAITING_TZ_FORMALIZATION`
(или AGREED_WAITING_TZ / AND_FRESH_BACKUP) и `open_dependencies: [<N>-TZ]` — это
эксплицитный содержательный гейт: до HF:impl требуется нормативная формализация
в master-ТЗ через разрешённую цепочку TZ:patch → REV:tz → TZ:finalize + свежий
emit с актуальным master/packet + fresh HF:backup с preimages/чистым baseline.

Проверять шапку REV-plan.md на `implementation_admission`/`open_dependencies`
ПЕРЕД `next`. Если гейт TZ-формализации присутствует — не `next` автоматически:
repair-скриптом ставить поезд в `waiting_operator` (root + фаза) и выносить
владельцу развилку, потому что следующий шаг правит нормативный master-документ
(чужой/общий контракт), а решение по формулировке delta принимает Саша, не
оркестратор. Дефолтный `next` после APPROVE с таким гейтом увёл бы в HF:backup
без санкции на правку master — недопустимо. APPROVE «принят» ≠ admission
открыт; он лишь санкционирует саму формализацию.

Развилку на гейте формулировать ОДИН раз, кратко и по существу (варианты с
рекомендацией). Когда Саша отвечает «выполняй по плану» / «требования уже
зафиксированы в ТЗ, что указано в плане — делай» / «реализуй план разово до
конца» — это владельческая санкция снять гейт и вести рельсу целиком без новых
вопросов, а названная модель (напр. исполнитель sol 6.1) — override модели
этой итерации. Повторно не переспрашивать: после «выполняй» TZ-формализация,
fresh backup и реализация исполняются теми фазами, что описаны в плане и
вердикте; вопрос был только о праве трогать master, после санкции право дано.
Новые вопросы — только на НОВЫЙ предметный блокер, которого нет в плане.

## Рельса ПОСЛЕ APPROVE: HF:backup / HF:impl / HF:test

После снятия admission-гейта `next` ведёт на HF:backup (затем HF:impl, HF:test).
Ключевые механики, чтобы не сломать поезд на этом отрезке:

- **HF:backup — sirene-фаза, выполняется оркестратором напрямую**, без emit и без
  invoke-роли. `emit-prompt` на неё возвращает «g6: emit forbidden for sirene
  phase», `invoke-role` — неверный маршрут. Работа: собрать свежий closure
  (source/test/schema/scripts P + skill K + оба prompt source), immutable R0-копию
  (`evidence/HF-backup-runtime-v26/Registries/pipeline` — live bytes без
  `__pycache__`), preimages live targets и manifest; затем `complete-phase` с
  evidence на manifest. Она НЕ должна нести cursor-роль в state: если
  `phases.HF:backup.role` остался executor (занёсся при repair), `complete-phase`
  падает «g6: sirene phase HF:backup has cursor role». При repair фазы-sirene
  всегда `pop('role')` из её записи state.
- **Прямая правка `_state.json` ломает целостность state_sha256.** Канон
  запрещает direct JSON-write; если state повреждён или понадобилось пересобрать,
  восстанавливать только через библиотеку: прочитать raw без `state_sha256`,
  пересобрать `pipeline_state.PipelineState(...)` из всех полей и записать
  `st.to_dict()` — он пересчитает sha по canonical body. In sandbox `read_state`
  может падать на отсутствии yaml/usertools_config; пересборку/проверку state
  делать через `terminal` с рабочим venv (`export PYTHONPATH=/home/tkachenkoav/WorkVault/Registries`),
  не из execute_code.
- **`waiting_operator` без открытого HITL-hold невалидно.** Ставить поезд в
  `status=waiting_operator` repair-скриптом можно только вместе с записью
  operator_hold (иначе `pipeline_status` кидает «waiting_operator without open
  HITL holds»). После снятия развилки владельцем держать поезд в этом статусе
  не надо — вернуть `WORK`.
- **`next` до выхода wrapper запрещён.** Пока жив background-процесс invoke,
  `complete-phase`/`next` дают G6-отказ/pending; дождаться notify, проверить rc,
  потом complete с реальным sha256 артефакта, потом next.
- **`recover` принимает только `--slug` и `--class`** — передача `--phase` даёт
  `usage error` и флаг не сбрасывается. `recover --class dead-pid` сбрасывает
  фазу, УКАЗАННУЮ в самом state (текущий phase); перед повторным invoke убедиться,
  что после recover в state нужная фаза стала `todo`/`doing` (проверить `status`).
- **AUTO_GATE (не `GATE:take-into-work`-подобные АКГ) закрываются `complete-phase`
  без invoke-роли**, но `--evidence` обязан содержать `path=` или `sha256=` (и
  `reason`), иначе `rc=1 «evidence must include path=»`; пустой evidence не
  принимается даже для гейта без канона.

HF:impl — содержательная executor-фаза: emit → invoke-role executor (модель
override по распоряжению Саши), полный path-allowlist, обязательная дельта
комpressor-промптов к Б60 (если в плане REV30-01-тип правки). После HF:impl —
HF:test (R0 + lab R1), затем docs → пилот → установка → READ/RELEASE.

## TZ-дельта после APPROVE: публикация master не создаёт refresh basis сама по себе

Когда на TZ-цепи (TZ:patch → REV:tz → TZ:finalize) роль записывает новый master,
`next` на следующую фазу вызывает `refresh_producer` и может вернуть G1 «no accepted
refresh basis», даже когда запись прошла. Механизм: basis возникает только из
`context_result.outputs[str(master)] == ref(master)` фазы, записавшей master; если
emit-пакет фазы был собран по контракту ДО правки §10 (master ещё не объявлен
required output) или роль записала master как побочный эффект вне output-декларации,
accepted basis не формируется. Закрывать так:

- Исправлять контракт-проекции (master в write_scope И outputs kinds required)
  ДО emit повторной публикации, чтобы пакет declare-ил master — не
  «чинить» откатом уже опубликованной записи.
- Фактическую уже-опубликованную запись (реальна на диске, sha совпадает с
  контрактом) можно зарегистрировать как `context_result.outputs[str(master)] =
  ref` штатным repair-writer'ом — это слепок факта, не выдумка outputs; затем
  `next` корректно возьмёт producer refresh к следующим фазам. Не трогать
  содержимое master, только реестр outputs фазы.

## Компрессорные refresh-фазы (TZ:compress/HF:compress) обязаны быть в write_scope контракта

TZ:compress (и HF:compress) — штатные producer-фазы refresh extract, но emit не
наследует workspace по умолчанию: если их нет в `write_scope` контракта §10, пакет
собирается с пустым write_scope и invoke падает `rc=4 output outside write_scope`
на extract.md/артефакте. Добавлять путь (workspace поезда) в `write_scope` контракта
штатной правкой ДО emit, затем ресетить фазу (repair → todo) и пере-emit — содержимое
`extract_refresh` basis при этом сохранить, не сбрасывать.

## Бюджет фазовых ходов: длинный rework-цикл может потенциально исчерпать лимит invoke

Каждый `invoke-role` по REV:plan инкрементирует `turn_count` фазы
(`_state.json` → phases.REV:plan.turn_count). Длинная цепочка REQUEST-CHANGES
(reviewer+architect на одной фазе несколько раундов подряд) копится на этот
счётчик. Лимит по `phase_turns.py`: `LIMIT_INVOKE=20` для ревизорских/архитекторских
фаз (REV/TZ/BUG/RS/MIG/DEC), `LIMIT_HF=25` для HF. Когда `turn_count >= limit`,
`invoke-role` падает МЕХАНИЧЕСКИ с `budget_exhausted:phase-turns` в первую секунду,
до какого-либо результата роли — это НЕ вердикт, вердикта нет.

Симптомы: процесс `invoke-role` выходит с rc=1; journal фиксирует
`interrupt phase=REV:plan reason=budget_exhausted:phase-turns`; REV-plan.md не
обновлён (текст = прежний вердикт); state: `fail_class=budget_exhausted`,
`turn_count>=20`, `status=interrupted`. Замечаний ревизора нет, потому что ревизор
просто не стартовал.

Правила:
- `budget_exhausted` входит в `NON_RECOVERABLE_FAIL` — recover-флаг не легитимен.
- ВТОРОЙ сбой того же класса на фазе → по канону СТОП + диагноз, не обход
  (не сбрасывать turn_count вручную, не перезапускать invoke вслепую).
- Коррекция лимита — правка `phase_turns.py` БОЕВОГО кода (увеличить
  `LIMIT_INVOKE`/`LIMIT_HF` либо отдельный лимит под длинный цикл доводки), строго
  через разрешённую фазу/архитектора, не оркестратором напрямую.
- Перед запуском длинной серии ревью по фазе прикидывать: ~20 invoke на REV-фазу
  хватит на ~6-8 раундов REVIEW-CHANGES. Закладывать бюджет заранее для
  планов-продуктов с ожидаемой многораундной доводкой.

## Архитектор может править план in-place без новой revision-шапки

Архитектор не обязан добавлять «## Revision N» и бампать `plan_revision`:
вердикт может лечь в уже существующий раздел (пример — закрытие REQUEST-CHANGES
внутри §18.4 при `plan_revision: 18` и отсутствии «Revision 19»). Поэтому после
invoke-role НЕ полагаться на grep «Revision N» / `plan_revision`: читать
фактический контент последних правок (mtime, хвост, адресный подраздел) и
судить по наличию ответов на каждый блокер. `plan_revision=18` при живом §18.4
и prepare/result=Y в `_state.json` → вердикт ЕСТЬ; статус в state подтверждает
завершённость роли и проверяется первым чтением.

## recover-классы: один corrective-повтор на класс в фазе; второй того же класса → interrupted

`recover` допускает один corrective-повтор того же класса на фазу: `recover_counts[phase][class]`
растёт, а ВТОРОЙ recover того же класса переводит поезд в `status=interrupted` (journal:
`recover limit <phase>/<cls>`) и блокирует `next` (возвращает INTERRUPTED). Это лимит
«Технического восстановления», не место для обхода лимита.

Единственный штатный способ продолжить фазу после исчерпания одного класса — применить
ДРУГОЙ применимый класс со счётчиком 0, и ТОЛЬКО если корневая причина устранена и вход
изменился (напр. wrapper завершился rc=0, но фаза не принята → `dead-pid` правдив). Если
это второе наблюдение того же блокера — это диагноз/ожидание (канон: «Повтор замечания»
Б55.5), а не способ открыть ещё один прогон. Проверять `recover_counts` до повторного recover.

## Параллельный поезд на том же write-set: V0 NOT PASS, не разрешать руками

Если независимый dev-поезд параллельно коммитит в тот же runtime скилла (архитектор в
HF-plan фиксирует `concurrent_runtime_contract_drift`, V0 NOT PASS), НЕ разрешать конфликт
вручную: не откатывать чужой transport/upload/pipeline, не re-apply уже удалённую строку,
не маскировать новое поведение (напр. не выставлять `retry_limit=0` в тесте). Исполнитель
не должен механически restore файл из HEAD. Нужны provenance/commit параллельного владельца,
адресный разбор совместимости с контрактом и решение Саши — не молчаливое продолжение фикса
на сдвинувшемся дереве.

## Большой контекст роли (пересмотр крупного плана) умирает по 3600s subprocess-лимиту в фоне — сжимай вход

Переписывание большого плана при чтении полного master-ТЗ + текущего плана + директивы в ОДНОM промпте упрётся в 3600s кап subprocess codex в invoke_role.py — роль падает rc без артефакта (план не переписан), ещё в фоне; это НЕ зависит от фоновости терминала. Лечение:
- **Сжать вход архитектору**: компактная директива (суть требований списком фактов, каждый пункт = критерий) + абсолютные пути на файлы, где роль сама короткими чтениями тянет детали. НЕ копировать весь ТЗ+план в промпт.
- **В полном входе перечислить исходники абсолютными путями** («единственные источники истины, читать с диска») — роль поднимет их сама.
- После падения по таймауту — `recover --class dead-pid` (артефакта нет) → повторный emit сжатого пакета → invoke.
- **Сразу после таймаутной смерти первый `recover` может отказать «wrapper alive» при `pid_alive=False` — это гонка с угасающим pgrep-хвостом, не системная причина.** Проверить `pipeline_gates.occupancy_blocked(slug)`/`invoke_wrapper_alive(slug)` в python (рабочий venv, PYTHONPATH), дождаться False и повторить recover с ТЕМИ ЖЕ аргументами — проходит. Второй подряд отказ при реально живом wrapper'е — настоящая занятость фазы, recover нелегитимен.

## MIGRATION: REV:tz/REV:plan вне рецепта — ревизор-инвок вне pipeline

Кейс MIGRATION НЕ содержит REV-фаз в рецепте: `emit-prompt --phase REV:tz` (REV:plan)
падает «phase is not in recipe», `invoke-role` с REV-фазой требует `.packet.json` которого
нет. Ревизию ревизора по ТЗ/плану MIGRATION проводить ПРЯМЫМ `codex exec -m gpt-6-astra`
(роль reviewer, sandbox danger-full-access + --dangerously-bypass-approvals-and-sandbox,
промпт — аргументом, не `-f`/`--output-format`), с полным контекстом (Обязательный контекст
владельца, вердикты, hashes на диск). Вердикт писать в `evidence/REV-tz.md`/`REV-plan[-N].md`
+ корневой указатель; не трогать state/pipeline. После каждого REQUEST-CHANGES — адресная
доработка плана архитектором (тем же codex exec) по конкретным остаточным пунктам вердикта,
затем новая независимая ревизия изменённых bytes с обновлённой hash-привязкой handoff.

MIG:plan при emit требует `dev/<slug>/AC-list.md` (таблица AC из master-B34): без него
emit падает «required input missing: .../AC-list.md». При «tz version drift» после bump
архитектора синхронизировать повторным emit-prompt (emit фиксирует tz_path/tz_version).

### Длинный цикл ревью MIGRATION-плана: причина повторов — наличие полей вместо содержания

Порт навыков/инструментов на Windows требует заполнить portability-контракты
(skills-portability / usertools-portability / skill-command-contracts / skill-fixture-recipes).
Наивная доработка по REQUEST-CHANGES заполняет верхнеуровневые поля и адреса, но ревизор
дважды подряд возвращает план («проверка наличия полей подменила проверку содержания»):
каждая запись обязана быть СОДЕРЖАТЕЛЬНОЙ и СОГЛАСОВАННОЙ, а не обладать полями.
Конкретные классы остатков, которые ревизор ловит по факту содержимого JSON, а не по
`contract_complete=true`:

- **Cross-field рассинхрон:** `native_instruction`/`operational_template`/`argv`/runtime/cwd
  обязаны описывать ОДНУ принятую команду. Типичные дефекты: target-поле хранит
  `bash …`/`&&`/`done`/`$t` при PowerShell-argv; `native_instruction` = «последние 5 архивов»,
  а контракт требует 7; источник с историческими «5» оставляется только как source-evidence,
  target-текст — согласованная величина. Ревизор отклоняет любой остаток Bash/неопределённой
  переменной в target-полях и любую рассинхронизацию retention/args.
- **Подмена функции:** многострочный consumer (например `python3 -c`, читающий `*summary.md`)
  обрезается до первой строки/import и направляется на ЧУЖОЙ smoke (stats/verify другого
  инструмента). Классифицировать ВЕСЬ span: если действующий — задать input/fixture/argv,
  ожидаемый output и отрицательный случай именно этой функции; если устаревший — адресное
  обоснование исключения + актуальная замена, не «не исполняется вся строка».
- **Legacy-классификация на весь смешанный абзац:** если один и тот же абзац СНАЧАЛА
  требует действующую норму (например фиксировать `--origin-chat/--origin-thread` при init),
  а последним предложением запрещает legacy-команду, — разделить `semantic_parts`: норму
  сохранить и подтверждать её сохранение, legacy пометить отдельно. Не относить действующее
  правило к истории только из-за соседнего legacy.
- **Один владелец полного span:** несколько consumers одного блока не должны повторять
  команду; один явный owner, остальные — covered-by/non-executable continuation.

Проверку делать по фактическому содержимому JSON по адресам, не по §13-заявлению архитектора
(которое часто обещает больше, чем подтверждает содержимое). Критерий закрытия R1: исполнитель
сможет реализовать каждую согласованную проверку БЕЗ самостоятельного выбора входного сценария/
поведения. Многораундовость (5+) на одном плане при адресно разных остатках — норма, поезд
продолжается; останавливается только повтор ТОГО ЖЕ дефекта (Повтор замечания Б55.5).

## Классы прорех, которые ревизор ловит ДО кода (пресечь на шаге архитектора)

Ревизор ищет рассинхрон между секциями плана и фактами на диске. План должен
быть внутренне согласован — каждая правка одного ID тянет за собой все
упоминания (IAC-09, §5–§7, covers, evidence, reader must_read, AC-report).
Типовые классы:

- **AC/nodeids в запрещённом/отсутствующем файле.** `covers`/§7 ссылаются на
  oracles в файле, которого нет в allowlist closure (напр. `test_context_packet.py`
  вне 15-path), и функций физически нет (проверить `rg` по candidate/live).
  Новые oracles — только в разрешённых путях с полным file-qualified nodeid,
  ИЛИ расширить allowlist и пересчитать closure, иначе required-actual-missing≠∅.
- **`covers` шире активной IAC-карты.** Заявлены AC/Б55-ID, которых нет в
  активном IAC-09/§7/§5 (напр. AC-PKT-09/10/11 заявлены, активная карта — только
  04/05/06). Одна каноническая матрица: каждый заявленный ID — собственный
  nodeid/command/log/status в активной карте, либо убран из covers с обоснованием.
- **Покрытие слоя неполное.** blanket «Б55.4–Б55.11» не доказывает Б55.13 и
  его AC-RP-\*. Перечислять каждый обязательный ID отдельной строкой.
- **Evidence в write_scope, но вне полного output / вне reader must_read.**
  Состав каталога (faults/*, inputs/P*, decisions/*, wake/*, before/after)
  заявлен changed_files, но не в OutputRef/must_read — reader не получит
  обязательный слой. Дать полный фиксированный child readset или формальный
  snapshot FileRef (schema/hash/mtime/resolved target).
- **Команда неоднозначна/неисполнима.** Две разные формы одного verify (wrapper
  vs пять `--scenario-file P1..P5`) или отсутствуют обязательные аргументы
  (--pipeline-root/skill-root). Зафиксировать один исполняемый точный argv.
- **Зависимость недоступна в declared interpreter.** Oracle требует пакет
  (tiktoken), которого нет в `/home/tkachenkoav/hermes-agent/.venv` и вне
  write_scope → гарантированный NOT_RUN/FAIL. Использовать локальную метрику
  (unicode_code_points/utf8_bytes) или явно добавить разрешённый механизм
  подготовки зависимости.
- **Именование расходится между секциями.** Одна величина в разных секциях
  названа по-разному (как `unicode_code_points` vs «tokens»). Развести точные
  термины во всех секциях сразу.
- **«Reuse Б60/B<<N>>» без сверки с фактическими телами кода.** blanket
  «опираемся на существующие H/M/T traces» опровергается чтением функций:
  `invoke_role.py` run_codex/run_hermes_internal вызывают общий Codex без
  compressor confinement и publish сами до общего finalizer; существующие
  `test_case_trace[T01]...[T18]` имеют ДРУГОЙ смысл, чем master-таблица T01–T18
  (напр. T08 в коде = BUGFIX-LIGHT, в master = Python paging). Совпадение меток
  ≠ oracle coverage. Проверить literal mapping каждого заявленного Б<<N>>-ID к
  фактическому коду/сигнатуре теста; для непокрытого ID запланировать изменения
  в разрешённых owners и exact nodeid/CLI/oracle. (reuse обязан порождать
  адресную матрицу по фактическому коду, а не общую строку «master/самh».)
- **Хешируемый snapshot ссылается на собственный будущий FileRef.** Вложенный
  `transition.current`/`history.b` PinRef самих хешируемых bytes создаёт
  циклическую зависимость (hash не вычислить, content должен уже содержать свой
  hash). Snapshot B содержит только существующие источники и предыдущие
  bindings; внешний immutable transition/approval связывает готовые A/B ПОСЛЕ
  их закрепления; полные refs B и зависимый от B approval не живут внутри
  хешируемого B. Outlook: показать замкнутый сериализуемый пример initial A и
  approved refresh B без placeholders/self-ref/исключения полей из full hash.
- **`compileall` пишет `.pyc` вопреки `-B`.** `python -B -m compileall` явно
  вызывает py_compile и создаёт `__pycache__/*.pyc` — `-B` лишь запрещает
  авто-запись при импорте. Если план требует clean-tree/no-write честно: заменить
  syntax-check без записи (compile прочитанных source bytes в памяти) либо
  направить результат в разрешённый isolated scratch. Не лечить cleanup-ом
  чужого candidate как неявное разрешение записи.

Каждая прореха = один дополнительный цикл архитектор→ревизор. Проверка плана на
эти классы ДО emit экономит раунд. При добавлении oracle обязательно невидимое
`rg` по candidate/live, что он либо существует, либо лежит в разрешённом путём
closure — невидимый/отсутствующий oracle — самый частый источник REQUEST-CHANGES.

## Входной комплект фазы не может требовать её собственные будущие результаты (R1-класс)

Ревизор фиксирует круговую зависимость, когда вход фазы (напр. B0) требует комплект, в который входят артефакты, создаваемые этой же фазой (release-actual рождается в B0) и фазой, которую вход гейтит (ready.json — результат B3): B0→комплект→B3→B0, и правило «каждый missing required input — BLOCKED» конфликтует с собственными выходами. Исправление по формуле ревизора:

- Разделить комплект на три группы: (1) входные документы/проверенный patch до фазы; (2) результаты самой фазы и предшественников; (3) итоговый пакет после всех фаз.
- У каждого артефакта — производитель и ПЕРВЫЙ этап-потребитель; маркер готовности (ready.json) создаётся после решения владельца и проверяется на входе СЛЕДУЮЩЕГО этапа, не на входе производителя и не внутри самого гейта.
- Вход фазы проверять только по группе (1); переход к следующему этапу требует доказательств завершённых предшественников.
- Проверка исправления: «пройти инструкцию из состояния без маркера готовности» без фиктивных ready/receipts для прохождения входного контроля.

Будущий результат не является входом своего производителя: отсутствие release-actual/ready.json не блокирует фазу, которая его создаёт.

## Альтернативный маршрут обязан иметь достижимые prerequisites (R2-класс)

Если план предлагает обходной путь Б «до гейта B3», а общий раздел требует B3 как prerequisite и назначает владельцем инструмента локальный процесс после готовности, путь Б неисполним до условия, перед которым он предложен. Ревизор требует выбрать S1 (только основной маршрут; альтернатива описана как непринятая) ЛИБО S2 (явно развести: подготовка и независимая ревизия исполнителя ДО автономности, preflight, запуск владельцем, гейт — только для основного маршрута). Право выбора S1/S2 с однострочным обоснованием остаётся архитектору; отсутствие готового исполнителя до гейта — ЧЕСТНЫЙ блокер, а не разрешение на raw-роли. Каждый оставленный маршрут обязан иметь доступного исполнителя и достижимые prerequisites; общие требования (backup, API-контракт, offline install/resume) сохраняются во всех маршрутах.

## Артефакты ролей пишут сами роли — оркестратор не подменяет их содержанием

Владелец проверяет «кто писал план/вердикт» по фактическому прогону, а не по словам. План, вердикты, ТЗ-дельты создаются реальными invok'ами ролей (архитектор/ревизор на своих моделях); оркестратор формулирует промпт (компактная директива + абсолютные пути источников), фиксирует директивы владельца и сверяет результат на диске (версия, SHA-256, mtime), но не сочиняет содержание вместо роли. На вопрос о авторстве отвечать, опираясь на реальные логи прогонов, а не на общую фразу.

## Прорехи в протоколе/матрице результатов, которые ревизор ловит при приёмке (REV результатов, напр. шаг-21 ревизия проверки реализуемости)

Когда ревизор проверяет ПРОТОКОЛ/матрицу выводов (а не план), он сверяет каждое
утверждение-вывод с фактическими exec-логами и файлами, а не с намерением автора.
Типовые прорехи и как их не создавать:

- **Вывод шире свидетельства: «краткий промпт ⇒ полные тела не загружались / чтения не повторялись / экономия токенов».** Краткий промпт с refs доказывает только состав ПОСТАНОВКИ, а не фактический вход: роль сама делает полные `cat` ТЗ/плана/протокола и повторные чтения пересекающихся разделов (видно в exec-логах). Поэтому заявлять только проверяемое: «компрессор не использовался, промпты краткие», а про загрузку тел — «по логам загружались через cat», экономию токенов — «не измерена и не обещается». Сверять каждый вывод с `rg 'cat |модель|reasoning' evidence/*.log` перед записью.
- **«Документировано» ≠ «подтверждено».** Запись в протоколе «результаты доставлены в топик X» — это сообщение протокола, не наблюдаемая доставка: без проверяемого message-ID/связки notify→wake готовность доставки не заявлять. Аналогично «файлы не менялись» — проверять по sha256, а не по отсутствию записей о записи.
- **Точные имена параметров/моделей.** `model_reasoning_effort="low"`, не «reasoning=low»; фактическое назначение («все 5 вызовов — gpt-6.1-terra/low»), не «не терры». Ревизор сверяет трассу по session-файлам построчно.
- **Способ закрытия NOT_RUN не перекладывать на ревизию документов.** «Ревизия сверит» не закрывает live-NOT_RUN: ревизия проверяет документы, а live-сценарий закрывается только отдельно допущенным наблюдением/испытанием или явным решением Саши об изменении объёма (§6 п.3). Явно разводить «документно завершено» и «проверка не завершена»; заявлять статус «НЕ завершена», а не «пилот завершён».
- **«Git-команд не было» — общий тезис неверен.** Read-only команды (напр. `git status --short`) — тоже команды: роль могла их выполнить (даже с exit>0). Заявлять только «Git-записей (add/commit/push) не обнаружено».
- **Ссылки на разделы точные.** «§1.4 контракта» ≠ «план §1.4»: контракт и план — разные документы, у каждого свой нумерация. Перед записью ref проверять фактическую принадлежность раздела.
- **Hash-ссылки на изменённые документы.** После правки протокола/матрицы обновлять зафиксированные SHA-256 на него в ТЗ/плане (паспорт источников, таблица refs) до выдачи на повторную ревизию; версию ТЗ бампать (v0.2 → v0.3) с записью изменений.

## Круг 2 и далее: построчная адресность обязательна, «заключительное закрытие» не работает (V2-класс)

Когда ревизор вернул REQUEST-CHANGES по протоколу/матрице, автоправка «одним завершающим абзацем» («это закрыто в строках H… и в паспорте» без самих адресов) порождает новый REQUEST-CHANGES. Исправление документа-основания строится построчно, иначе ревизор вернёт те же дефекты второй раз:

- **Каждой строке вывода — адресный ref на первичное свидетельство** (файл + версия/hash + строка/раздел), а не общая ссылка на паспорт/прежний вердикт. Практично: компактный реестр refs `R##` рядом с матрицей, из каждой строки H — однозначная ссылка на номер. Одной общей ссылки ревизору недостаточно: «ревизор воспроизводит каждую строку по указанному источнику, не разыскивая доказательство заново».
- **Раздельные поля в каждой строке матрицы**: результат/граница, причина NOT_RUN, способ наблюдения (live / offline-документный / read-only), уровень обеспечения (штатная техническая гарантия / проверенная процедура ролей / не обеспечено), условие закрытия. Смешение «Частично, документно/процедурно» в одной колонке статуса — прореха: результат и уровень свидетельства читаются независимо.
- **«С проверкой версии» требует sha256 входного файла ДО чтения.** Контрольные hash, снятые ПОСЛЕ записи (проверка неизменности прочих файлов), не доказывают, что исполнитель сверял версию входа перед использованием. Если в exec-логах нет `sha256sum <вход>` перед `cat` — писать «сверка версии входа не выполнялась, неизвестное остаётся неизвестным», не «переиспользовано с проверкой версии». Ревизор различает реконструкцию по логам (его чтение) и фактическую проверку исполнителем до чтения.
- **Не обещать закрыть live-классы документной ревизией.** Остаток вида «…live-часть в шаге 21» в строке результата обещает ревизии закрыть то, что она по определению не проверяет. Формулировать: документная ревизия выполнена; полный штатный вход/обрыв/доставка — отдельно допускаемые live-испытания, документной ревизией не закрываются.
- **Повтор дефекта во 2-м REV → диагноз до третьего круга** (план §3.1 / R07 / Б55): в документ вносится раздел «Диагноз неполного исправления и изменённый способ», где указано, что именно прежнее исправление делало не так (декларация вместо построчности) и чем заменено. Без этого диагноза третий круг запускать нельзя.
- **После правки протокола пересчитать зависимые hash в ТЗ** (E19 и внутренняя контрольная сумма), поднять версию ТЗ с записью изменений, предъявить точные версии на независимую проверку. Исторические exec-логи не переписывать.

Порядок исправления документного REQUEST-CHANGES: Сирень правит свою матрицу/протокол адресно М0 (без модельных вызовов) → архитектор (астра) вносит согласующие правки в ТЗ (hash, статусы, формулировки) одним фоновым вызовом → повторная независимая ревизия изменённых версий; между шагами стоп и предъявление Саше по С12-режим. На каждом круге тот же цикл; второй REQUEST-CHANGES по тем же дефектам — диагноз и изменённый способ, не продолжение той же тактики.
