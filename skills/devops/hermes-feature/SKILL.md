# Паттерн: hermes-feature

Применять при: новая фича, новый инструмент, задача требует ТЗ и вариантов решения.
Триггеры: *«разработай», «новый инструмент», «напиши ТЗ», «MoveFrom*», «ТЗ v»*

---

## Блок 0: ТЗ

- ТЗ пишет **Opus**, инициирует только Саша явным запросом
- Формат: Markdown → `WorkVault/Hermes-Backlog/ТЗ-[название].md`
- **Обязательные разделы:** Цель / Шаги / Критерии успеха / Что НЕ трогать
- Старт разработки: только явное **"ок, берём в работу"** от Саши в TG
- Неопределённость в процессе: Opus **стопится**, дополняет ТЗ предложением, ждёт ОК

### Брифование перед ТЗ (для сложных доработок)

Когда задача затрагивает безопасность, архитектуру хранения, взаимодействие с другими инструментами или пользовательский интерфейс — **перед написанием ТЗ провести бриф**:

1. Собрать все открытые вопросы по блокам (Хранение / Отображение / Фильтрация / Интеграции / Синхронизация)
2. Вывести полный список вопросов одним сообщением: «Всего N вопросов по X блокам. С какого начинаем?»
3. Идти по блокам последовательно, задавать вопросы по одному
4. Предлагать варианты (А/Б/В) а не открытые вопросы — быстрее согласовывается
5. После каждого блока — «Итог блока N: ...» с зафиксированными решениями
6. Только после завершения брифа → запускать Opus на написание ТЗ

**Триггеры для брифа:** безопасность/персданные, новый UI/TG-команды, взаимодействие 2+ инструментов, архитектурный выбор с несколькими равнозначными вариантами.

## Блок 1: Анализ вариантов

- **Критерии:** токены / безопасность / консистентность / поддерживаемость + специфичные для задачи
- **Количество:** 2-3 лучших; слабые Opus отсеивает сам
- **Подача:** сначала рекомендация с обоснованием → остальные кратко для справки
- После выбора: уточняющие вопросы **по одному** → ждёт "берём в работу"
- Саша может **прервать уточнения** в любой момент и перейти сразу к работе

## Блок 2: Разработка

### Кто пишет
- **Sonnet** — конфиг/скилл/memory, 1 модуль, не затрагивает ядро Hermes
- **Opus** — Python-код, новый модуль, архитектура, ядро Hermes, несколько компонентов

**ВАЖНО:** Даже если правки кажутся простыми (3 файла, 15 строк) — если задача про код, исправление бага в Python-модуле, или затрагивает несколько файлов — передавать Opus. Sonnet не должна самостоятельно вносить правки в код, оправдывая это простотой задачи.

### Чеклист перед первой строчкой кода
1. ТЗ согласовано + вариант выбран + явное "берём в работу"
2. **Бэкап создан** (см. Блок 5)
3. Opus пересказал что именно будет делать

### Фиксация решения
Opus обновляет ТЗ-файл: добавляет выбранный вариант + дату старта.

## Блок 3: Тестирование

- **Готово =** dry-run прошёл + Opus проверил каждый критерий из ТЗ (✅/❌)
- Opus запускает, присылает результат с рекомендациями → финальное "всё ок" говорит Саша
- **Проблема:** Opus пробует исправить сам (1 попытка) → не вышло: откат + сообщение Саше
- Результат: сообщение в TG с чеклистом ✅/❌

## Блок 6А: QA-проверка перед «Готово» (hermes-config-qa)

Обязательный финальный шаг **любой задачи** с 3+ изменениями: настройка конфига, подключение скиллов, разработка инструмента, финализация ТЗ.

### Когда применять
- Изменения в `config.yaml` (модели, delegation, fallback, gateway)
- Подключение/отключение скиллов или агентов
- Новый Python-инструмент / скрипт
- Любое «готово» сообщение по задаче с 3+ изменениями

### Процесс (4 шага)
1. **Собрать чек-лист через Opus** (`delegate_task` → `claude-opus-4-7`): проверить корректность изменений, смежный функционал, логические противоречия (особенно память vs конфиг).
2. **Исправить ❌ пункты** — применить рекомендации, обновить память или конфиг при противоречии.
3. **Повторить** (максимум 3 попытки).
4. **Все ✅ → сообщить о готовности с кратким отчётом. Остались ❌ после 3 попыток → откат + доклад об ошибках.**

### Откат конфигурации
```bash
hermes config edit  # открыть и вернуть вручную
# или точечно:
hermes config set delegation.model <старое значение>
hermes config set fallback_providers '[]'
```

### Типичные проблемы при QA конфига
- **При клонировании профиля (`--clone`):** наследуется `delegation.reasoning_effort`, `child_timeout`, `fallback_providers` — проверять. `model.api_key` обязателен для custom provider (хоть `dummy`).
- **Память vs конфиг:** правила в памяти не исполняются автоматически — это инструкции для модели.
- **`child_timeout_seconds = 600`** мало для Opus с reasoning (рекомендуется 1200).
- **`reasoning_effort` на custom/exo провайдерах:** при клонировании наследуется — обязательно очищать `hermes -p <profile> config set delegation.reasoning_effort ""`.
- **Per-task модель в `delegate_task`** не поддерживается (проверено delegate_tool.py:2066).
- **Субагент (Haiku) без явного запрета может испортить .env, удалить contacts.enc** — всегда писать в prompt запреты.
- **`hermes config show` не отображает секцию `delegation`** — UX-баг, параметры работают.

### QA ТЗ перед разработкой
Промпт для Opus: «Ты senior технический аналитик. Прочитай файлы ТЗ. Ответь ТОЛЬКО: ✅ ТЗ готово к разработке [список проверенного] ИЛИ ❌ Требуются уточнения: [конкретные вопросы].»

Типичные проблемы в ТЗ: противоречия между файлами, неотражённые реальные данные API, platform-specific артефакты (.bat на запланированном Linux), неполный алгоритм для edge cases, несогласованные enum-значения.

## Блок 7: Диагностика и отладка (hermes-debug)

Применять при: что-то сломалось, неожиданное поведение.
Триггеры: *«ошибка», «баг», «не работает», «упало», «падает», «разберись», «починить», «сломалось»*
Модель: **Sonnet** (не Haiku, не Opus — если не нужна глубокая архитектурная правка)

**Алгоритм:** Воспроизвести → Root cause (порядок: плейсхолдеры .env → batch API → broken imports/venv → дублирование правил → устаревший скилл) → Минимальная правка + бэкап → Регресс-тест → Фиксация в Pitfalls скилла.

**Эскалация к Opus:** root cause в архитектуре, правка ядра Hermes, не воспроизвелось за 2 попытки.
**Эскалация к Саше:** данные могут быть повреждены, production down, нужен доступ к внешнему сервису.

**Debug pitfalls:** `routing:` в config.yaml — мёртвая секция. `hermes gateway restart` → UnicodeDecodeError в stderr — косметика. `hermes skills list` не видит скилл — проверить `version` и `author` в frontmatter. `cronjob(action='update')` не умеет сбрасывать `no_agent` — менять в jobs.json напрямую.

## Блок 8: Исследования и анализ (hermes-research)

Применять при: нужно собрать данные, найти паттерн, оценить варианты — без изменений кода.
Триггеры: *«проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если»*
Модель: **Opus** для глубокого (архитектура, API, код); **Sonnet** для быстрого (история, конфиги)

**Алгоритм:** Scope → Сбор (session_search 1-3 слова FTS5, параллельные запросы; файлы через grep; API только чтение) → Анализ (таблица, выводы отдельно) → Рекомендации (2-3 варианта с оценкой).

**НЕ делать:** не менять код/конфиги/скиллы, не делать выводы без данных, не запускать API без ОК Саши.

**Research pitfalls:** FTS5 session_search — AND-логика, длинные запросы дают 0. FF API `outline` всегда null. `extended_sections` содержит 4 секции: Blockers/Questions/Meeting Outline/Topics. `apps_preview.outputs` — 2 кастомных скилла: `1:1` и `Meeting Summary Generator`.

## Pitfalls

### Изменение `no_agent` в cron-задаче
Инструмент `cronjob(action='update')` НЕ умеет сбрасывать `no_agent: true → false`. Нужна прямая правка JSON:
```
/home/tkachenkoav/.local/share/hermes/cron/jobs.json
```
Найти блок по `job_id`, поменять `"no_agent": true` → `"no_agent": false`, убрать `"script": "..."` → `"script": null`. Gateway перезапускать не нужно — scheduler читает jobs.json при следующем тике.
Hermes индексирует локальные скиллы через `.usage.json` + сканирование SKILL.md. Если скилл не появляется в `hermes skills list` после создания:

1. **Обязательные поля frontmatter** — без `version` и `author` скилл не индексируется:
   ```yaml
   version: 1.0.0
   author: agent
   platforms: [windows, linux, macos]  # НЕ писать [all] — не работает
   ```
2. **Добавить в `.usage.json`** вручную если всё равно не появляется:
   ```python
   import json
   path = r"C:\Users\tkachenkoav\AppData\Local\hermes\skills\.usage.json"
   with open(path) as f: data = json.load(f)
   template = data["hermes-config-qa"].copy()
   template.update({"use_count":0,"view_count":0,"patch_count":0,"last_activity_at":None,"state":"active","pinned":False})
   data["new-skill-name"] = template
   with open(path,"w",encoding="utf-8") as f: json.dump(data,f,ensure_ascii=False,indent=2)
   ```
3. Gateway перезапустить: `hermes gateway restart` — новая сессия подхватит скиллы

## Питфоллы

- **Реальный API может не совпасть с документацией/предположениями в ТЗ** — фиксировать отклонение в финальном отчёте Opus. Делать живой запрос к API **перед реализацией** (это блокер для ТЗ, не после). Пример: FF `extended_sections { title items text }` → реально `{ title content }`. Opus должен: (1) записать отклонение в отчёт; (2) реализовать по реальной схеме; (3) оставить опциональные поля из ТЗ для backward-compat с моками, если это разумно.
- **ТЗ не нужно переписывать после отклонения** — если ТЗ уже перемещено в `_Done/`, отклонение фиксируется в финальном отчёте Opus, не в самом ТЗ-файле.
- **Секция `routing:` в config.yaml не работает** — код Hermes её не читает (проверено 27.05.2026 grep по всем .py). Молча игнорируется. Для реальной маршрутизации нужен плагин/хук или правила в MEMORY.md как рекомендации агенту.
- **`hermes skills list` не подхватывает новые скиллы** пока у них нет полей `version` и `author` в frontmatter. Обязательные поля: `name`, `description`, `version`, `author`, `tags`, `platforms`. Без них скилл есть на диске но не виден в индексе.
- **Бэкап обязателен до первой строки кода** — Opus должен создать бэкап в `_Archives/hermes-backup-YYYYMMDD-HHMMSS/` перед любыми изменениями Opus-уровня.
- **ТЗ-файл после реализации** → переместить в `WorkVault/Hermes-Backlog/_Done/ТЗ-название-YYYYMMDD.md`, обновить статус внутри файла.
- **Живое master-ТЗ инструмента** хранится в папке инструмента: `USERTOOLS/<tool>/<tool>_TZ_vX.Y.md`. Hermes-Backlog/_Done/ = история точечных изменений. При каждой доработке — обновлять master-ТЗ в папке инструмента. Это правило введено 27.05.2026 явным требованием пользователя.
- **backfill-паттерн для MoveFrom*:** если нужно перекачать встречи/данные вне текущего временного окна — добавить второй проход по `pending`-записям с известным ID через прямой fetch по ID (минуя date-фильтр). Лимит 50 записей/прогон, сортировка newest-first (`reverse=True`), чтобы свежее появлялось первым. Для разового массового backfill: временно поднять константу `BACKFILL_MAX_PER_RUN` до нужного числа, запустить вручную `--mode test`, вернуть обратно. Проверить остаток API-лимита перед запуском (`x-ratelimit-remaining-api` в ответе заголовков).
- **`--mode manual` требует `--from-date` и `--to-date`** — для запуска backfill без дат использовать `--mode test` (берёт окно последних 5 дней + запускает backfill по pending). `--mode cron` — только новые встречи в окне last_synced_at → сейчас.
- **Дедупликация встреч:** при наличии двух записей с одинаковым названием и разницей во времени ≤10 минут — дубль. Сравнивать по длине транскрипта (символы/строки), более короткий → статус `duplicate`, файлы удалять. Статус `duplicate` пропускается в синке как `completed`. Если транскрипт недоступен — сравнивать по `duration_minutes`. Email = первичный ключ контакта, ФИО не схлопывать.
- **Bulk API rate-limit:** перед массовым запросом проверить заголовки `x-ratelimit-remaining-api` и `x-ratelimit-reset-api`. Оставлять запас ≥10 запросов. После исчерпания лимит сбрасывается автоматически (время в секундах в `x-ratelimit-reset-api`).
- **Reconciliation как паттерн доработки инструментов:** если пользователь хочет чтобы ручное удаление файлов запускало перекачку → добавить шаг reconciliation в начало синка: пройти по completed-записям реестра, проверить наличие файлов на диске, отсутствует ≥1 файл → сбросить статус в pending. Это универсальный паттерн для всех MoveFrom*-инструментов с файловым реестром.
- **MoveFromZulip синк:** первичный ключ контакта = `login` (часть email до @), не полный email. Schema v2: `sources: {zulip: {email, synced_at, active}}`, `active = any(source.active)`. Zulip отдаёт всех одним запросом `GET /api/v1/users`. Фильтры: `is_bot=true` и `is_active=false` — не писать вообще. messenger_ids хранятся с `{value, source, synced_at}`, `source: manual` не перезаписывается коннектором.
- **AnywhereContacts — PII при выводе:** функция `mask_contact(contact)` из `anywhere_contacts` ОБЯЗАТЕЛЬНА перед любым выводом контакта пользователю в Telegram или CLI. `store.read()` возвращает сырые данные намеренно (для записи в Jira/Confluence нужен настоящий email). Ошибка: показать `Криворотов Кирилл` вместо `Кр**в Ки**л`.
- **AnywhereContacts — общий lock:** все коннекторы используют единый lock-файл `WorkVault/Contacts/.contacts.enc.lock`, не per-tool lock.
- **USERTOOLS живут в `Documents/Cursor_projects/hermes-agent/USERTOOLS/`**, не в `WorkVault/USERTOOLS/`. При запуске Opus на написание ТЗ или реализацию — передавать именно этот путь. WorkVault — только для данных и логов, не для кода.
- **Футер в cron-ответах — реализовано 28.05.2026:** `_build_cron_footer(job)` добавлена в `cron/scheduler.py` (строки 569, 648). Формат: `claude-opus-4-7 · Имя задачи` в конце `wrap_response` блока. Если футер всё равно не появляется после рестарта — проверить что `_SEP` и `_model_short` из `gateway/runtime_footer.py` доступны (могут быть приватными). Fallback: дублировать литерал `" · "` локально в `scheduler.py`.
- **Gateway падает при рестарте во время обработки запроса:** если gateway перезапустить пока агент обрабатывает сообщение (крутит tool-вызовы) — ответ теряется, `response ready` в логе не появляется. Признак: запрос залогирован (`inbound message`), но `response ready` отсутствует, следом сразу `Starting Hermes Gateway`. Это не баг gateway, а штатное поведение при принудительном завершении процесса. Рекомендация: перед рестартом подождать пока ответ придёт (обычно видно по индикатору набора в Telegram).
- **Cron GitHub автосинк:** промпт задачи может устареть при архивировании репо на GitHub (403 на push). Симптом: `last_status: ok` но ничего не пушится. Проверять реальный вывод лога, не только статус. Решение: обновить промпт на актуальный скрипт `bash scripts/autosync.sh`. при переносе проекта в другую папку нужно обновлять пути в cron job-промпте (`jobs.json`). Симптом: `synced=0` без ошибок — скрипт не найден по старому пути. Проверять: `last_status` + вывод job-отчёта.
