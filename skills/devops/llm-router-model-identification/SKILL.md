# Опознание модели-роутера (router) перед планированием

## When to Use

- Пользователь называет модель коротким именем («jev», «router») и просит строить план/ТЗ вокруг неё (основная модель Hermes, «решатель всех ролей» dev-workflow).
- Кандидат из каталога шлюза встречается с `pricing = -1` либо именем `*-router`.

Класс задачи: пользователь называет модель коротким именем («jev», «router» и т.п.) и просит построить план/ТЗ вокруг неё — оценить как основную модель Hermes или как «решатель для всех ролей» dev-workflow. Прежде чем готовить развилку/ТЗ, установить по каталогу шлюза (туту-каталог `/api/openrouter/v1/models`, key из `custom_providers.tutu.api_key`): это НАСТОЯЩАЯ модель-снапшот или роутер.

## Как опознать по каталогу

- `pricing` = `-1` (цена не раскрыта статически — считается по фактической маршрутизации, `usage.cost` в каждом ответе).
- `architecture.tokenizer` = `Router` (или вида «Router») в полном объекте модели (`/models` → `pprint` по `id`), не стандартный токенизатор.
- `description` упоминает подбор / баланс качества / скорости / цены (напр. «picks the best model and reasoning effort ... balancing quality, speed and cost»).
- Класс не уникален для jev: роутеры как категория («X-router») появляются в каталогах OpenRouter-шлюзов; критерий — поля выше, а не только имя.

## Подтверждение smoke-тестом (решающий признак)

Отправить запрос через шлюз с tool calling + reasoning и прочитать в ответе поле **`model`**: роутер отвечает фактической моделью, которую выбрал (напр. `model: z-ai/glm-5.3`), т.е. под капотом это один из снапшотов каталога, а не своя архитектура.

- HTTP 200 + `finish_reason: tool_calls` валидирует доступность (tool calling и reasoning работают), но НЕ цену.
- `model` из ответа — это фактический вендор под капотом; зафиксировать его как факт в бриф архитектора.

## Следствия для оценки модели под роль

- **Цену роутера из каталога сравнивать нельзя** (`pricing = -1`) — только по фактическим `usage.cost` прогонов. Не делать вывод «роутер дешевле/дороже» из каталога.
- **Вендорная независимость ревизора** (ревизор ≠ семья архитектора/исполнителя) становится непредсказуемой per-request: фактический вендор роутится динамически, один и тот же запрос к роутеру может уйти на разных провайдеров. Учитывать при выборе роутера как «решателя всех ролей».
- **Роутер нельзя «поставить моделью роли» dev-workflow заменой `roles.*.model` на router ID.** Codex-CLI запускает КОНКРЕТНУЮ модель (`codex exec -m <id>`; `run_codex` передаёт model+effort, но НЕ задаёт Tutu provider/profile). Роутер — endpoint шлюза, а не конкретный id, до которого Codex умеет нативный вызов. Правильный паттерн «динамический выбор модели через роутер из пула Codex» — слой выбора (resolver) между поездом и invoke-role: запросить роутер с `allowed_models = {gpt-6-astra, gpt-6.1-sol, gpt-6-luna, gpt-6.1-terra}` + описание задачи, получить `{model, effort}` и invoke-role с выбранным точным `-m`. Это изменение pipeline (разрешающего слоя), не точечная правка конфига. Ревизора оставлять на фиксированной модели до доказанного разделения семейств.
- Перевод «все роли + основная модель сразу» на роутер не обоснован ни совместимостью, ни экономикой; рекомендуемый порядок — пилот основной Hermes, затем поштучный транспортный допуск ролей (пример полного разбора — `dev/ujemy-jev-router-rezhatel-dlya-vseh-roley-dev-wo/RS-analyze.md`).
- В бриф архитектора класть найденный кандидат как факт (полный id, smoke-результат, фактический `model` из ответа), а не как предположение о природе модели.

## Роутер ≠ decision-only селектор (для «селектора моделей ролей»)

Когда постановка — «агент-селектор выбирает модель под роль, а исполнение идёт на другой модели» (Jev-селектор для ролей dev-workflow на пуле Codex CLI), роутер НЕ подходит как интерфейс выбора:

- Публичный контракт роутера (`X-router`) включает **генерацию ответа выбранной downstream-моделью** — он сам исполняет после выбора, а не возвращает «тихий» выбор. `models`/`allowed_models` — ослабляемые предпочтения (могут выйти за include), `excluded_models` — жёсткое исключение, но и оно не превращает роутер в decision-only. Даже `response.model` фиксирует итог генерации, а не предварительный выбор.
- Для чистого «выбрал → другой исполнитель» нужен **отдельный decision-интерфейс** (OpenRouter `/api/alpha/decisions`, `/api/v1/systemone`, TypeSafe System One), выбирающий ОДИН вариант (`choice`) среди переданных допустимых пар без генерации. Поддержку конкретного decision-only маршрута твоим шлюзом надо доказать отдельно (`NOT_PROVEN` до проверки): имя роутера в allowlist шлюза этого не закрывает.
- При проектировании «селектор из пула Codex»: чистое решение — расширить resolver (один типизированный выбор Jev среди допустимых пар `(slug, effort)`) → локальная проверка → существующий Codex adapter. Второй диспетчер/очередь не нужны; `_resolve_model_backend` уже возвращает неизменяемую тройку model/backend/effort — это точка расширения.

## Стоящее правило владельца: пул исполнения ролей — только каталог Codex CLI

Для ролей dev-workflow **модели-исполнители берутся ONLY из каталога Codex CLI** (напр. `~/.codex/models_cache.json`, поле идентификатора — `slug`, не `id`; `codex models`/app-server `model/list`). Модели HTTP-шлюза (OpenRouter/Tutu) в роли **исполнителей запрещены** — включая fallback и compressor. Селектор (Jev и т.п.) может лишь ВЫБИРАТЬ из этого пула; исполнение всегда на slug кодесовой модели. «Каталог в cache» = членство/пригодность, но не доказанное live entitlement — успешный inference подтверждает доступ только к своему запросу.

## Питфолл

- Не строить план/ТЗ на природе модели из одного названия. Пользовательское короткое имя («jev») не говорит, одна это модель или роутер; искать по каталогу и smoke-тестировать ДО развилки.
- Не считать роутер «селектором без исполнения» и не передавать его ответ как `--model` роли: его контракт генерирует, а настройка `invoke-role --model` даёт модель, но НЕ effort (effort задаётся YAML/фазой/кейсом) — попытка передать пару `{slug, effort}` одним `--model` ломает семантику роли.
