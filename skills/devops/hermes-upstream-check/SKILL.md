# Hermes Upstream Check

Процедура структурированного анализа изменений в апстриме `NousResearch/hermes-agent` между нашей текущей базой и текущим HEAD `origin/main`. Цель — дать Саше решение "обновляться сейчас / подождать / отложить" на основе фактов из git log/diff, а не общего "440 коммитов, читай сам".

## Когда использовать

- Саша спрашивает "какая версия апстрима", "что нового в апстриме", "стоит ли обновляться"
- Еженедельный крон **"Upstream hermes-agent monitor"** (`upstream_monitor.sh` + этот скилл) — механический сбор данных уже в скрипте, этот скилл — как их читать/интерпретировать и что писать в отчёт
- Перед плановым `git pull --ff-only` в `~/hermes-agent`

## Технический сбор данных

```bash
cd ~/hermes-agent
REPO_BASE=$(hermes --version | grep -oP 'upstream \K[a-f0-9]+')   # наша база апстрима
git fetch origin main --quiet
HEAD_SHA=$(git rev-parse origin/main)
git log $REPO_BASE..$HEAD_SHA --format="%h %ai %s"    # список коммитов
git diff --name-only $REPO_BASE $HEAD_SHA              # затронутые файлы
```

Готовый скрипт `~/.hermes/scripts/upstream_monitor.sh` уже делает это + считает feat/fix/refactor, находит "наши" компоненты, ведёт `watch_list` (см. ниже) — предпочитай запускать его, а не писать git-команды с нуля.

## 8 критериев анализа

### 1. Донастройка конфигурации + риск конфликта с нашими правками
Смотреть: пересекается ли список файлов апстрим-диффа (`git diff --name-only`) с файлами, где живут наши 693 локальных коммита (`cron/`, `gateway/platforms/telegram`, `agent/prompt_builder.py`, кастомные toolset'ы). Также искать `config.*schema|DEFAULT_CONFIG|hermes_constants` — сигнал возможной миграции конфига.
- Если пересечение есть → 🟡 при git pull/rebase будут конфликты, планировать время на разрешение
- Если апстрим меняет схему config.yaml → проверить `hermes config migrate` перед/после

### 2. Экономия токенов / стоимость владения
Искать коммиты по `token|cost|cach|compress` — фиксы кэша промптов, компрессии контекста, дедупликации auxiliary-вызовов. Прямая экономия для нас = меньше денег/токенов на тот же объём работы.

### 3. Устранение ошибок в нашем функционале
Приоритетные зоны (по нашему реальному опыту падений): `telegram|gateway|cron|delegat|subagent|heartbeat|stale`. Каждый найденный fix — отдельная строка с человеческим объяснением "что было не так и что чинит".

### 4. Устойчивость и надёжность
Искать: `crash|corrupt|WAL|deadlock|race|leak|drain|SIGTERM`. Это самая весомая категория для VM-инфраструктуры — падения gateway/cron напрямую бьют по автономности Сирени.

### 5. Выдержка стабильности (объединённый критерий, было 6+10)
Не выкидывать фикс из рассмотрения совсем, а держать "на карантине" 2 цикла проверки (2 недели при еженедельном кроне), если:
- **(было 6)** коммит в диапазоне сам был `revert`-нут другим коммитом в этом же диапазоне — явный сигнал нестабильности области
- **(было 10)** `fix` без добавленных тестов (`git show --name-only <sha>` не содержит файлов с `test` в пути) в критичной зоне (`cron/`, `gateway/`, `hermes_state`, `agent/`, `delegat`)

Механика хранения — см. раздел "watch_list" ниже. НЕ выкидывать такие фиксы из отчёта навсегда — только отложить учёт в итоговой рекомендации до истечения выдержки.

### 6. Security/auth-фиксы — вне очереди
Искать: `security|CVE|vulnerab|auth.*bypass|credential leak|secret leak|privilege escalation`. Если найдены — помечать 🚨 отдельно от общей рекомендации и предлагать рассмотреть немедленно, не дожидаясь обычного еженедельного цикла решения.

### 7. Платформенный шум — жёсткое исключение
Искать: `windows|win32|macos|darwin|schtasks|powershell` (исключая упоминания `linux`). Мы работаем на Linux VM — эти фиксы физически нас не касаются. Не включать в основной анализ, но можно списком показать в отдельном свёрнутом разделе "не касается нас" — не путать объём диффа с реальной релевантностью для нас.

### 8. Новые фичи для осознанного внедрения (апсайд, не только риск)
Искать `feat(...)` коммиты в интересных для нас зонах: новые провайдеры, новые toolset'ы, улучшения delegation/cron API. Отдельная секция в отчёте "может быть полезно внедрить" — не всё в анализе апстрима должно быть про риски.

## watch_list — механизм "выдержки стабильности"

Хранится в `~/.hermes/upstream-monitor.json` рядом с `last_sha`:

```json
{
  "last_sha": "...",
  "checked_at": "...",
  "watch_list": [
    {"sha": "abc123", "subject": "fix(...)", "reason": "no_test_critical_zone|reverted",
     "first_seen": "2026-07-15", "cycles_pending": 1}
  ]
}
```

Логика (реализована в `upstream_monitor.sh`):
1. Новый коммит, подходящий под критерий 5 → добавляется в `watch_list` с `cycles_pending: 1`
2. Коммит, уже бывший в `watch_list` и всё ещё входящий в диапазон `last_sha..HEAD` → `cycles_pending += 1`
3. Как только `cycles_pending >= 2` → коммит выводится как "выдержал срок" и убирается из `watch_list` (дальше учитывается в обычной категоризации 1-4/8, скилл его больше не задерживает)
4. Если коммит перестал попадать в диапазон (значит `last_sha` продвинулся дальше него — апдейт применён) — запись из `watch_list` можно удалить, она больше не актуальна

## Правило продвижения last_sha (важно, чинили 15.07.2026)

**`last_sha` продвигается ТОЛЬКО когда локальный `~/hermes-agent` репозиторий реально обновлён** (Саша сделал `git pull`), а не на каждом запуске крона. Раньше скрипт перезаписывал `last_sha` на текущий `origin/main` в конце каждого прогона независимо от факта апдейта — из-за этого диапазон для следующей недели терял ещё не применённые коммиты, и идея "выдержки" технически не могла работать (коммит на карантине выпадал из диапазона на следующей неделе).

Механизм подтверждения: скрипт сравнивает локальный `git rev-parse HEAD` с сохранённым `last_sha`. Если `HEAD` реально ушёл вперёд (проверяется через `git merge-base --is-ancestor $LAST_SHA $LOCAL_HEAD`) — значит апдейт применён, `last_sha` продвигается до нового `HEAD`. Если репозиторий не менялся — `last_sha` остаётся прежним, диапазон анализа накапливается неделя за неделей до реального `git pull`.

## Паттерн применения обновления (после решения 🟢/🟡 обновляться)

Установлен 15.07.2026 как обязательный порядок для ЛЮБОГО реального апстрим-апдейта этого репозитория (не только разового случая) — Саша явно попросил закрепить это как стандарт "далее мы всегда проводим обновления апстрим согласно паттерну". Анализ по 8 критериям выше даёт решение "обновляться/ждать/отложить"; этот раздел — что делать ПОСЛЕ решения "обновляемся".

Четыре звена, каждое — отдельный `delegate_task`/`cronjob` на модель, указанную в скобках:

1. **Risk-анализ (Opus, read-only)** — реальные `git diff`/`git show` по каждому потенциально конфликтному файлу (не только заголовки коммитов), явный вердикт по security-фиксам/breaking changes/миграции конфига применительно к НАШЕЙ конкретной конфигурации (не абстрактно). Ноль side-effects на рабочую копию — либо чистое чтение (`git log/diff/show`), либо временный `git worktree add /tmp/<name> origin/main` для исследования (безопаснее чем merge на месте, не требует отката). Сохраняется в `~/WorkVault/Hermes-Backlog/upstream-update-analysis-<YYYY-MM-DD>.md`.
2. **План (Opus)** — читает файл анализа, пишет отдельный документ `~/WorkVault/Hermes-Backlog/upstream-update-PLAN-<YYYY-MM-DD>.md` с обязательными разделами: (а) git safety net ПЕРВЫМ шагом — backup-ветка текущего HEAD (`backup/pre-upstream-<date>`) + бэкап `~/.hermes/config.yaml`; (б) **ветка прогресса** `upstream-merge-in-progress` — реальный merge выполняется и коммитится В ЭТУ ветку, не в рабочую ветку напрямую, и НЕ откатывается при отклонениях (см. п.3); (в) поэтапный merge с критерием успеха на каждом этапе; (г) МОДУЛЬНОЕ тестирование по функциональным блокам (cron/scheduler, gateway/platforms, auxiliary-модели, config migration, MCP, base smoke) в порядке от быстрого/дешёвого к медленному/дорогому; (д) явный запрет исполнителю импровизировать/чинить проблему самостоятельно/расширять скоуп/пропускать шаги/откатывать без указания.
3. **Исполнение (Sonnet)** — получает план как ТЗ, выполняет пункт за пунктом в заданном порядке в ветке прогресса, коммитит каждый пройденный этап, ведёт чеклист прогресса прямо в файле плана (на случай обрыва сессии). Жёсткое правило (обновлено 15.07.2026): при ЛЮБОМ реальном отклонении от того, что предсказывал risk-анализ (неожиданный конфликт, неожиданная ошибка, упавший тест) — Sonnet **НЕ чинит сама, НЕ импровизирует, НЕ откатывает**. Она фиксирует точное состояние (полный текст ошибки, номер коммита в ветке прогресса, какие шаги уже пройдены) и возвращает отчёт с явной эскалацией к Opus. Ветка прогресса остаётся как есть — не трогается, не удаляется, не сбрасывается.
4. **Эскалация к Opus** — Opus разбирается в причине конкретного отклонения (реальная регрессия апстрима / flaky-тест / архитектурный рефакторинг / наша несовместимость) С УЧЁТОМ уже достигнутого прогресса в ветке — не начинает анализ с нуля и не теряет пройденные чистые шаги. По итогам Opus переделывает план (`-PLAN-<date>-vN.md`) одним из двух способов: (а) явный шаг обхода/фикса конкретной проблемы, работа продолжается в той же ветке прогресса — откат НЕ требуется; (б) явное решение "откатываемся" — только если новый план Opus прямо это предписывает. **Откат — всегда осознанное решение Opus в новом плане, никогда не автоматическая реакция Sonnet на отклонение.**

Данный порядок применяется по умолчанию к любому будущему upstream-апдейту этого репозитория, не только к текущему — не нужно заново спрашивать/придумывать процесс.

## Питфолл: content-diff недостаточен — нужен и structural/path diff

Прецедент 15.07.2026: risk-анализ (шаг 1) проверял `git diff <base> origin/main -- <file>` по content — все 10 потенциально конфликтных файлов показали 0 текстовых конфликтов при `git merge-tree`. Merge реально прошёл БЕЗ единого конфликта. Но модульный тест `gateway/platforms` упал с `ModuleNotFoundError: No module named 'gateway.platforms.telegram'` — апстрим в этом диапазоне коммитов **переместил** telegram-адаптер из плоского модуля `gateway/platforms/telegram.py` в отдельный плагин `plugins/platforms/telegram/adapter.py`. Content-diff этого не показывает (файл просто отсутствует по старому пути, no diff to show), а `git merge-tree` не ловит "модуль пропал с диска" как конфликт, если наш код на него не ссылается напрямую в изменённых строках.

**Правило на будущее:** risk-анализ ОБЯЗАН включать directory-tree diff, не только content diff — `git diff --stat <base> origin/main` смотрит только на изменённые файлы, нужно дополнительно `git ls-tree -r <base> -- <dir>` vs `git ls-tree -r origin/main -- <dir>` (или `git diff --summary`/`--find-renames`) по каждой затронутой директории, чтобы поймать файлы, которые переехали/переименовались/исчезли целиком, а не только те, что изменились по содержимому. Особенно критично для директорий вроде `gateway/platforms/`, `plugins/`, `agent/` — где апстрим практикует периодические архитектурные рефакторинги (platform→plugin и подобные), а не только точечные фиксы.

## Тестирование правок upstream_monitor.sh без риска для боевого state

Скрипт хардкодит `STATE=~/.hermes/upstream-monitor.json` и `REPO=~/hermes-agent` — нельзя просто запустить его "для проверки", не рискуя испортить боевой `last_sha`/`watch_list` или боевой репозиторий. Безопасный паттерн, использованный при правке 15.07.2026:

```bash
# 1. Копия репозитория во временную папку — можно свободно двигать HEAD
rm -rf /tmp/hermes-agent-test
cp -r ~/hermes-agent /tmp/hermes-agent-test
cd /tmp/hermes-agent-test && git checkout <some-sha-ahead> --quiet   # симулирует "апдейт применён"

# 2. Копия боевого state-файла во временный путь
cp ~/.hermes/upstream-monitor.json /tmp/test-state.json

# 3. sed-подмена путей внутри копии скрипта — не трогаем оригинал
sed "s|STATE=\"\$HOME/.hermes/upstream-monitor.json\"|STATE=\"/tmp/test-state.json\"|; \
     s|REPO=\"\$HOME/hermes-agent\"|REPO=\"/tmp/hermes-agent-test\"|" \
     ~/.hermes/scripts/upstream_monitor.sh > /tmp/test_monitor.sh
bash /tmp/test_monitor.sh

# 4. Проверить результат в /tmp/test-state.json, затем убрать все временные файлы
rm -rf /tmp/hermes-agent-test /tmp/test-state.json /tmp/test_monitor.sh
```

Прогнать так минимум два сценария перед тем как считать правку рабочей: (а) без апдейта — `last_sha` должен остаться прежним, диапазон полным; (б) с симулированным апдейтом (HEAD копии реально продвинут) — `last_sha` должен подтянуться до нового значения. После теста явно проверить, что боевой `~/.hermes/upstream-monitor.json` не изменился (сравнить `last_sha` до/после).

## Связанные материалы

- `~/.hermes/scripts/upstream_monitor.sh` — механический сбор данных + watch_list, no_agent-safe (пустой stdout = тихо)
- Крон `Upstream hermes-agent monitor` (job_id меняется — искать через `cronjob(action='list')` по имени) — еженедельный запуск, `0 4 * * 6`
- Скилл `hermes-agent` — общие команды (`hermes update`, `hermes config migrate`, `hermes doctor`) для применения самого обновления
- `~/WorkVault/Hermes-Backlog/upstream-update-analysis-<date>[-vN].md` / `upstream-update-PLAN-<date>[-vN].md` — конкретные документы risk-анализа и плана по каждой попытке обновления (см. паттерн выше)
