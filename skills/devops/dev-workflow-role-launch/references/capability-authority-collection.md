# Исследование CAP-гейта — чек-лист АРХИТЕКТОРА (не оркестратора)

Когда блокер CAP (допуск реализации) требует авторитетных данных реальных маршрутов (limits/tokenizer/framing/route/consumer), исследование делает РОЛЬ-АРХИТЕКТОР по директиве владельца, а не оркестратор (Саша: «Оркестратор не занимался исследованиями», «Отдай эту задачу исследования архитектору. Пусть он сам найдет ответы на свои вопросы»).

## Штатный ход оркестратора (запуск исследования)

1. Записать директиву владельца в `evidence/owner-directive-<дата>.md`: исследование CAP делает архитектор сам; запрещено — paid-прогоны, установка библиотек, изменение model/effort/window/reserves, обход канона, выдумывание authority; разрешено — чтение кода/конфигов/кэшей/vendor/uv, официальные источники, расчёты.
2. Зарегистрировать директиву в handoff-contract `inputs` (HF-plan.md) с `phase: ORCH`, `purpose: владелец-директива`.
3. repair-writer'ом переоткрыть фазу-владельца (HF:plan → WORK/awaiting_invoke=True, стереть proof/context_packet/pid/receipt) и сбросить downstream (REV:plan, HF:backup, HF:impl, HF:test, HF:docs-handoff, ORCH:shared-state) в todo — REV обязан согласовать новую ревизию заново.
4. Свежий emit-prompt (директива + прежние submission как rejected-candidates в пакет) → ОДИН background-invoke архитектора.
5. После исследования архитектор возвращает requirement-revision-request (ДВА пути + рекомендация) — решение владельца по пересмотру требования (Б55.5): поезд → waiting_operator, REV вслепую не запускать.

## Что ищет архитектор (фактические знания, проверенные в работе)

1. **Первоисточник — официальные домены провайдера.** Для OpenAI: `developers.openai.com/api/docs/models`, `openai.com/index/*`, `openai.com/api`. Искать по точным model-идентификаторам (`gpt-6.1-terra`, `gpt-6-astra`).
2. **web_extract на официальных страницах OpenAI блокируется** («URL targets a private or internal network address») — это НЕ «данных нет»: web_search по тому же домену возвращает сниппеты официальной модель-карточки (context/max output/pricing/reasoning/cutoff/tools). Сниппет официального домена + URL + дата сбора = авторитетный источник с происхождением. GitHub-релизы (`openai/codex/releases/tag/rust-v<ver>`) извлекаются нормально.
3. **Локальный models_cache.json — НЕ авторитет.** Он показывает client-side настройку (для gpt-6.1-terra: 500000/872000/95%), официальные данные провайдера — 1.05M context / 128K max output. В capability JSON писать официальные числа, расхождение фиксировать в sources-файле (client cache vs provider authority — разные уровни доверия).
4. **Tokenizer:** OpenAI не менял токенизатор с gpt-4o; gpt-5+/gpt-6 используют `o200k_base` (официальный cookbook `how_to_count_tokens_with_tiktoken` + подтверждение в Developer Community). Если модуль tiktoken не импортируется в активном venv — это НЕ значит, что локальных assets нет: vocab o200k_base и cached-библиотека лежат в vendor/uv-кэше (проверить `find ~ -name '*o200k*'`, `~/.cache/uv/`, vendor R1 слага). `asset_refs` заполнять реальными FileRef локальных vocab/implementation, а не пустым массивом.
5. **Формат CapabilitySet — закрытая схема из `delivery-contract.md`** (`devworkflow-compressor-capabilities/1.0`): `profiles[]` по backend (codex + hermes-internal); codex требует `cli_version`/`cli_ref`, native — null; `route_identity` без URL/credentials; reserves положительные. Обоснование reserves: Codex 95% effective-окно (1050000×0.95 → 997500 effective, 52500 на instructions/tools+margin), output ceiling = 128000.
6. **FileRef — объект, не строка; массивы refs непустые.** В закрытой схеме каждый ref (`cli_ref`, `instruction_refs[*]`, `authority_refs[*]`, `tokenizer.asset_refs[*]`) — объект `{path, resolved_path, sha256, size_bytes, mtime_ns}`, а не голая строка пути. Submission из строк и пустых массивов отвергается целиком (13+ нарушений за раз): один `config.toml` для `instruction_refs` недостаточен (найти реальные instruction sources: AGENTS.md, skills, plugin bundle), native `instruction_refs` пустым нельзя (закрепить framing source native adapter), `authority_refs` — проверенные первоисточники с хешами. Название файла `authoritative` и самостоятельно проставленный `approved=true` авторитетом не являются — REV сверяет происхождение refs.
7. **Локальные заявления проверять до записи в справочник** («skills пуст», «tiktoken нет», «config без override») — факты находятся локально (5 системных skills, 2 AGENTS.md, vocab в vendor), голословное утверждение опровергается как нарушение структуры. Недоказанное «пусто/отсутствует» писать как «не подтверждено», а не как факт.
8. **`route_identity` native проверять по коду worker, а не по YAML:** строка `via: call_llm` в EcosystemConfig НЕ описывает фактический вызов — native worker напрямую вызывает `client.chat.completions.create` (Chat Completions, retries=0). Указание Responses API/`via` в submission = структурная ошибка; читать код adapter до записи route_identity.
9. **Consumer capacity сверять с наблюдаемыми client bounds, не только с карточкой API:** фактическое окно завершённого Codex/Astra/high = 258400 (кэш CLI 272000, effective 95%) — наблюдение сильнее карточки; полный content carrier + reserves против неё (313227 > 258400, дефицит 54827) — OPEN-блокер с развилкой владельцу (Б55.3/Б55.5): Путь 1 — согласовать client capacity policy (адресное увеличение окна, рекомендация), Путь 2 — пересмотреть модельное представление consumer (убрать механические echo, packet/manifest указатели). Не подставлять vendor max 1.05M и не снижать reserves/ReadRefs/echo.
10. **Регистрация в поезде:** authority-файлы (`provider-authority-sources.md` + `capability-set.authoritative.json` + `consumer-capability.authoritative.json`) добавить в `inputs` handoff-contract (purpose: `model-capability` / `consumer capacity authority`), переоткрыть фазу-владельца repair-writer'ом, свежий `emit-prompt` (sha замораживается), один background-invoke. Authority-файлы можно не класть в write_scope роли — они inputs, не outputs.
11. **Стоящее правило Саши:** при каждом допуске сверять `roles.*` из `EcosystemConfig.yaml` (`dev_workflow.roles`: architect/reviewer/executor/executor_light/compressor) с записями capability-справочника; при изменении model/effort/backend любой роли — пересобрать соответствующий authoritative JSON до допуска. Факт сверки фиксировать в справочнике (раздел «Сверка моделей ролей») с датой.
