## 1. Цель

**С v0.5.0:** для единого конвейера действуют уточнения §20: приоритет только в перечисленных пересечениях §20 (архив/read-back и trust, идентичность, профиль представления, команда publish, receipts, baseline). Прежние нормы вне этих пересечений сохранены.

По команде в чате и присланному файлу `.mpp` сделать так, чтобы страница Confluence с макросом `gantt-chart-planner` показывала **тот же план, что в файле** (задачи, даты, ресурсы, назначения, связи FS, календарь рабочего времени), и чтобы над макросом стояла одна строка «Итого» вида `Итого: с DD.MM.YY по DD.MM.YY - N рабочих дней` (без строки «Трудозатраты»).

**С v0.4.0 (раздел 19):** та же публикация **обязательно** сопровождается архивом исходного MPP, точной публикации JSON и состояния «Итого» в рамках того же вызова, которым публикуется план; долговечная история версий хранится в MofsIndex, аналитика (diff, воспроизведение расписания, численные вклады изменений) считается отдельно и **не изменяет** даты, опубликованные на странице. ## 5. Архитектура прогона

Один прогон скилла (после резолва pageId и наличия `.mpp` или ветки «дочка без файла»):

1. Резолв цели: pageId из сообщения / сессии; иначе стоп и спросить. Для «создай дочку от <parent>» — parentId обязателен.
2. Прочитать страницу: storage + child/attachment. Есть ли макрос `gantt-chart-planner`.
3. Собрать новый JSON:
   - есть `.mpp` → конвертер MPP→JSON (+ календарь);
   - нет MPP, создание дочки, у родителя есть гант → копия JSON родителя;
   - нет источника → пустой шаблон (корень без детей, пустые deps/assignments).
4. Если макроса нет (или новая дочка) — сгенерировать новые uuid: `ac:macro-id`, параметры `id` и `hash`. Имя вложения = `gantt-chart-<macro-id>.json`. На **существующем** макросе `id`/`hash`/`macro-id` **не менять**.
5. Собрать строку «Итого» из MPP (даты и N корня; или из собранного JSON, если копия/пустой шаблон). `m_hours` можно считать внутри, в storage не выводить.
6. **Гейт:** показать дифф, ждать «лей» / «пиши». Без подтверждения — никаких POST/PUT.
7. Запись: вложение (POST `/data?conflictPolicy=override` или POST attachment, если первого нет) → PUT storage (макрос при установке; блок «Итого» всегда при заливке/создании). PUT страницы: re-read `version` сразу перед записью, в payload слать **current+1**. `conflictPolicy=override` на страницу не ставить (только на вложение).
8. Короткий отчёт: URL страницы, версия вложения, «Итого».

Каскад дат скилл **не считает**. Источник дат — MPP (или уже посчитанный JSON при копии).

**С v0.4.0 (§19):** шаг 6 (гейт) и шаг 7 (запись) дополняются обязательным архивированием и безопасным восстановлением (R-009/R-010):
- До шага 6 (до любого POST/PUT) долговечно сохраняются исходные байты MPP, подготовленные байты JSON и ожидаемое «Итого» (preflight-архив, R-009 п.5).
- После шага 7 выполняется **свежий** GET `body.storage`, `version` и title непосредственно перед PUT; патч «Итого»/макроса применяется к этому свежему body, не к тому, что было прочитано на шаге 2 (R-009 п.8, fresh body+version перед PUT — заменяет прежнее «только версия перед PUT»).
- При сбое/конфликте повтор идёт по стадиям (`archive`/`attachment_post`/`attachment_verify`/`storage_put`/`storage_verify`) — **stage-specific retry**, не слепой повторный полный `apply` (R-010). Таблица состояний — §19.5.2.
- Имя JSON-вложения строится по `param_id` макроса (`gantt-chart-<param_id>.json`), не по устаревшему `macro-id`; `macro_id`/`param_id`/`param_hash` различаются (§19.4.1, R-005).

## 6. Схема данных JSON вложения

Плагин: **Gantt Chart Planner for Confluence**, макрос `gantt-chart-planner`.

Storage макроса (не менять `id`/`hash` на живых копиях страниц — это идентификаторы экземпляра, не checksum содержимого):

```html
<p><ac:structured-macro ac:name="gantt-chart-planner" ac:schema-version="1" ac:macro-id="<uuid>">
<ac:parameter ac:name="id"><uuid-or-hex></ac:parameter>
<ac:parameter ac:name="hash"><uuid-or-hex></ac:parameter>
</ac:structured-macro></p>
```

Ключи верхнего уровня JSON: `eventsData`, `resourcesData`, `dependenciesData`, `assignmentsData`, `startDate`, `macroConfig`, `calendarsData`, `initialState`, `baselineVersions`, `customColumns`, `linkedSites`, `idCounter`.

| Ключ | Роль в v1 |
|---|---|
| `eventsData` | Массив из **одного** корня; дерево через `children`. Поля события: `id, parentIndex, startDate, endDate, duration, durationUnit, name, calendar, manuallyScheduled, unscheduled, ignoreResourceCalendar, constraintType, constraintDate, percentDone, effort, effortUnit, inactive, segments, baselines, parentId, rollup, children, effortDriven, schedulingMode`. `rollup: true` = сводная. Вехи: `duration=0`. |
| `resourcesData` | `{id, parentId, name, eventColor, resourceType:"custom"}`. Плагин плодит копии одного имени; активная группа = max id на имя. |
| `assignmentsData` | `{id, event, resource, units}`. `units` = % загрузки. |
| `dependenciesData` | `{id, from, to, type, lag, lagUnit, active}`. v1: только `type:2` (FS), `lag:0`. |
| `calendarsData` | Заменять из MPP при заливке файла. При копии с родителя — как в копии. |
| `startDate` | `YYYY-MM-DD` старта плана. |
| `idCounter` | Следующий свободный id = `max(все id событий/ресурсов/связей/назначений)+1`. **Не** хардкод `300000` из тестового скрипта. |
| `macroConfig`, `initialState`, `baselineVersions`, `customColumns`, `linkedSites` | Если на странице уже есть JSON — **сохранить как есть**. На новой странице — скопировать из шаблона (эталон тестового вложения v1). |

Идентификаторы: ключ страницы = **pageId**. Не считать уникальным ключом пару `id`+`hash` (у теста `519501810` и живой `519492935` они совпали из-за копирования страницы).

**С v0.4.0 (§19):** эта схема и профиль плагина v1 **не меняются**. Полный нормализованный экспорт MPP/Gantt (W2, §19.6, R-012-014) — отдельный версионированный набор таблиц MofsIndex для архива/аналитики, не новый ключ JSON вложения и не влияет на публикуемый `eventsData`/`calendarsData`.

## 8. MPP → JSON и календарь

Вход файла: путь к `.mpp` или к `.zip`, внутри которого `.mpp` (Telegram). JVM: `org.mpxj.*` (не `net.mpxj.*`), как в `read_mpp.py`.

```text
read_mpp.py <mpp> --format csv
  → __tasks.csv, __resources.csv, __assignments.csv
+ UniversalProjectReader.getDefaultCalendar() → calendarsData
```

### Задачи

- Строки с пустым `id` и `id=0` не брать в дерево (служебный корень MPP). Также отбрасывать узлы, у которых `outline_level` парсится как число **≤ 0** (служебная шапка MPP с настоящим id, напр. `id=217` / `outline_level=0`). Парс уровня безопасный: `int(float(raw))`; пустое/мусор → 0 → отброс. Корень дерева = первый узел с `outline_level >= 1`.
- `outline_level` (> 0) → вложенность `children`. `summary=True` → `rollup: true`.
- `duration` (дни) → `duration`. Вехи (`milestone` / duration 0) → `duration=0`, `effort=0`.
- `start` / `finish` → `startDate` / `endDate` (нормализовать до секунд, как в эталоне плагина).
- `parentId` / `parentIndex` проставить после сборки дерева.
- `percentDone` в v1: из MPP `percent_complete`, если колонка есть; иначе 0. Каскад % по родителям не считать.
- `schedulingMode`: `FixedDuration` (как в шаблоне плагина).

### Ресурсы и назначения

- Матч ресурса MPP → плагин **по точному `name`**.
- При полной заливке MPP на страницу, где уже был JSON: взять активную группу (max id на имя) как пул для матча; имена из MPP без матча — новый id, `resourceType: custom`. Старые неактивные копии имён (низкие id) **не включать** в новый `resourcesData` (как в успешном тесте 080926).
- `assignmentsData`: `event` = id события, `resource` = id плагина, `units` из MPP.
- `effort` листа = сумма `work` всех назначений этой задачи (часы). Сводные: не суммировать детей в `effort` корня для JSON (rollup рисует плагин).

### Связи

- Колонка `predecessors` (напр. `[2]`) → `{from: pred, to: task, type: 2, lag: 0, lagUnit: "day", active: true}`.
- Иные типы связей MPP в v1 не маппить (нет в приёмке). Если в файле не-FS — в диффе предупредить «пропущены связи не FS», не падать.

### Календарь (доказано Сашей «да супер»)

`calendarsData` — массив `{id, name, unspecifiedTimeIsWorking, intervals[]}`.

Нерабочие `intervals`:

- рекуррент: обед `at 12:00`–`at 13:00`; ночь по часам MPP (эталон 080926: `at 18:00`–`at 09:00`); `on Sat`–`on Sun`; `on Sun`–`on Mon`;
- исключения: `getCalendarExceptions()` где `working=False`; `startDate: YYYY-MM-DD 00:00`, `endDate: (toDate+1 день) 00:00`.

Часы MPP 09–13 / 14–18 → обед 12–13 и ночь 18–09 (как в `/tmp/build_calendar2.py`). Только `getDefaultCalendar()`. Календари ресурсов — не в v1.

### Пустой шаблон

Один корень (имя «Новый план» или title страницы), `duration=0`, без детей, пустые `dependenciesData`/`assignmentsData`, `calendarsData` — минимальный General (сб/вс + рабочие часы как в шаблоне теста) либо пустые intervals. В диффе явно: «план пустой».

### Копия с родителя

Скачать JSON вложения родителя, залить на дочку **как есть** (новые macro-id/id/hash у макроса дочки; содержимое JSON то же, кроме необходимости выставить согласованный `idCounter`). «Итого» пересчитать из этого JSON.

**С v0.4.0 (§19, Q7):** `read_mpp.py` получает отдельный версионированный режим полного нормализованного экспорта (W2, §19.6, R-012-014) для архива/аналитики — полный календарно-ресурсный граф, встроенные baseline-слоты, calendars/resources/assignments/timephased с явной отметкой `complete|partial|missing|unsupported`. Этот режим **не заменяет** и не меняет текущий CSV-контракт (`__tasks.csv`/`__resources.csv`/`__assignments.csv`) и маппинг этого раздела (§8) в плагин v1 — конвертер `mpp_convert.py`/публикационный профиль `mpp_calendar.py` используют тот же урезанный источник, что и сегодня. ## 9. Блок «Итого»

Канон — **одна** жирная строка в storage (`<p><strong>…</strong></p>`):

```
Итого: с <ДД.ММ.ГГ> по <ДД.ММ.ГГ> - <N> рабочих дней
```

Строка `Трудозатраты: <M> человек-часа` **не создаётся** (ни `build_itogo_html`, ни `patch_itogo`, ни `apply_itogo`) и **удаляется из storage**, если уже есть. Разделитель дат и N — дефис с пробелами: ` - ` (не em-dash). Даты: `DD.MM.YY`. N: целое, пробел как разряд тысяч (`1 960`).

Переменная `m_hours` из `compute_itogo_from_csv` / `compute_itogo_from_gantt` **остаётся** в кортеже и в сигнатурах (`build_itogo_html(..., m_hours)`), в HTML блока «Итого» не подставляется. Текст гейта `gate_diff.py` («…N р.д., M ч-ч») — не storage, в пакет render-fix не входит.

Источник цифр (при заливке MPP):

| Поле | Откуда |
|---|---|
| дата1, дата2 | start / finish **корня плана** (первый узел outline_level≥1, не служебный id=0 и не шапка outline_level≤0) |
| N | `duration` корня в днях, округление **вверх до целого** (`ceil`) |
| M (`m_hours`, не в HTML) | сумма `work` (часы) по **всем строкам назначений** `__assignments.csv` (не суммировать summary-задачи — иначе двойной счёт), затем `ceil` |

При копии JSON / пустом шаблоне: даты и N с корня `eventsData`; M внутри = сумма `effort` листьев (`rollup=false`) или `0`, если assignments пусты — в storage не выводить.

Правила патча:

1. Блока «Итого: с …» нет → **вставить над макросом** одну строку шаблона. Если в storage уже есть «Трудозатраты: …» — вырезать (вместе с обёрткой `<p>…</p>`, не оставлять пустой абзац).
2. Строка «Итого: с …» есть → заменить только даты и N. Хвост (в т.ч. про 70%) **не менять и не создавать**. Строку «Трудозатраты» вырезать, если есть; новую не писать.
3. Не искать «Итого» на других страницах и не синхронизировать соседние абзацы.

## 13. Риски

- Telegram не принимает `.mpp` — только `.zip` (как `read-mpp`).
- `conflictPolicy=override` затирает правки, сделанные в UI плагина.
- PUT вложения → 405; нужен POST `/data`.
- Версия страницы при PUT storage: re-read свежий `version` перед PUT, в payload слать **current+1**. Гонка между re-read и PUT → штатный 409 (чужая правка); повторный `apply` с новым re-read. `conflictPolicy=override` только на вложение, не на страницу. Слать current as-is → 409 `Version must be incremented` даже без гонки.
- Совпадающие `id`/`hash` у копии страниц — писать только по pageId.
- Тестовый конвертер: сломанный `idCounter=300000`; не переносить в прод-скрипт.
- Не-FS связи и ненулевой lag в MPP — молча пропуск с предупреждением в диффе.
- Сумма effort по всем задачам включая summary завысит `m_hours` в `compute_itogo_*` (гейт-дифф); канон расчёта M — сумма work назначений. В storage блока «Итого» M не выводится.
- Два шага записи (вложение + storage): если storage упал после JSON — гант новый, «Итого» старое. Повторить PUT storage; не откатывать вложение автоматически.
- Пустой шаблон: N=0, даты с `startDate` или одинаковые границы корня (`m_hours` внутри может быть 0; в HTML не попадает).
- Служебная шапка MPP с `outline_level≤0` и настоящим id (не 0) без фильтра попадает в `eventsData[0]` → плагин «No records to display». Фильтр в `build_event_tree` на `rows` (не только стек).

**С v0.4.0:** риски пакета §19 (утрата старых MPP/status_date, невоспроизводимость моделью MPXJ, расхождение вложение/страница/SQL при частичной записи, rebuild MofsIndex без потери долговечных данных, рост MD, конкурирующие публикации, неизвестные backup/SLA/дисковый бюджет) — отдельный реестр §19.13; не дублируются здесь.

### 19.4. Публикация, архивирование, восстановление

Единый процесс публикации (R-008/R-009), 10 шагов: разрешить проект/plan_id/линию/pageId/макрос/attachmentId → прочитать выбранный MPP (hash, runtime, единственный согласованный экспорт) → подготовить новые байты JSON → показать гейт (pageId/операция/«Итого»/план/линия/архивный путь/доступность baseline) → **до первого POST/PUT** долговечно сохранить исходные/подготовленные байты и `attempt_id` → проверить неизменность цели → POST вложения, сохранить ответ → GET **полученной конкретной версии** (не `latest`), сверить hash → **свежий** GET `body.storage,version,title` перед PUT, применить только согласованный патч к свежему body, PUT с `current+1` → сохранить ответ PUT и повторно прочитанное состояние → рендер MD/индекса из SQL, отчёт с раздельными флагами публикации/архива/аналитики.

Состояния и идемпотентность (R-010): раздельные стадии `archive`, `page_create`, `attachment_post`, `attachment_verify`, `storage_put`, `storage_verify`, `projection`; значения `not_started|prepared|confirmed|failed|unknown|conflict|not_applicable`. Таблица восстановления по месту сбоя — см. источник (`FINAL-TZ-arhiv-plana.md` §5.2). Ключевое правило: **stage-specific retry** — повтор только конкретной незавершённой стадии после проверки актуальности цели, не полный слепой `apply` сначала.

История ZD (R-011, Q5): явная операция импорта с пагинацией и картой пропусков. Пилот — host `dom.tutu.ru`, page `537561928`, attachment `537561929`. **Пилот = боевой контур сразу** (решение владельца Q5): рабочая БД `index.sqlite` и указанная боевая страница ZD — это и есть пилот; отдельный тестовый контур/копия БД или страницы **не создаётся**. Численный SLA не задаётся заранее — лимиты по факту измерений AC-143 (§19.12.1), отдельным решением владельца после пилота.

Каждая коллекция — `complete|partial|missing|unsupported` с count/причиной (R-013); каждое неизвестное поле — `null` с причиной. Duration/work/date-delta/рабочий drift — четыре разные метрики, не взаимозаменяемые. Обязательные инварианты (R-016): FK/UQ в пределах одного плана; снимок и коллекции фиксируются одной SQL-транзакцией; история append-only (`ON DELETE RESTRICT`, исправление — новая ревизия с supersedes); FK включены на каждом соединении, индексы по версии/времени/связям; проверка циклов/висячих концов/дублей UID; новая нормализация = новый snapshot при иной версии/параметрах.

Временная семантика (R-017/R-018): `published_at` ≠ `observed_at` ≠ `recorded_at`; `status_date` — отдельная граница факта/прогноза; `known_at`-запросы используют только известные на тот момент ревизии. Идентичность — подтверждённая линия + UID; confirmed mapping 1:1 не допускает склейку двух разных задач snapshot.

База сравнения (R-019): явно названная владельцем версия, иначе первая доступная опубликованная версия линии («базовая по умолчанию: первая доступная; предыстория не подтверждена»). Поздно обнаруженная более ранняя публикация меняет только **default**, новой записью выбора; **явный пользовательский выбор не меняется**.

Сохранность (R-020/R-021, Q4): миграция жизненного цикла MofsIndex до первой записи уникального baseline/mapping; долговечные `plan_*` сохраняются при общем/schema/docs/protocols rebuild; режим `synchronous=OFF` исключён из рабочих операций этой БД. **Решение владельца Q4 (ПРИНЯТО):** backup — расширение существующего `full_workvault_backup` (tgz-роль `~/WorkVault_backup/_full-WorkVault-backup/`), охват включает `index.sqlite` и файлы-артефакты планов; ретеншн **5→7**; существующий крон **23:30**, **без нового cron**; согласованная SQL-копия — Online Backup API/эквивалент при активном WAL; пробное восстановление до эксплуатации. Численные RPO/RTO и дисковый бюджет — открытый пункт O1 (§19.14), не выдумываются, закрываются измерениями.

Безопасность (R-022): без токенов в квитанциях/SQL/MD/ошибках; параметризованный SQL, типизированные операции, валидация путей/ZIP; никакой новый облачный сервис не получает MPP.

### 19.7. Diff, один MD, русские запросы (W4)

`diff_versions` (R-023) — конкретные A/B одного представления, mapping revision, параметры единиц; подтверждённые 1:1 дают Δ по полям; публикационные изменения (`drop-dep`, ручная правка Gantt) не приписываются MPP.

Контракт MD-витрины (R-024): **один** генерируемый MD на `plan_id`, свежая публикация первой, предыдущие — ниже в обратном порядке, со сворачиваемыми заголовками. **Решение владельца (Q2):** имя файла — `<slug>.ganttchart.md`, пилот `Entities/zd/Pages/zd.ganttchart.md`. Атомарная публикация файла: temporary MD → проверка полноты/hash → atomic replace → generation (R-025); ручная правка файла даёт конфликт, не silent overwrite.

Типизированные операции MofsIndex, маршрутизируемые через `workvault-rag` (R-026): `resolve_plan`, `list_versions`, `diff_versions`, `task_history`, `compare_baseline`, `explain_finish_change`. Свободный SQL/подсчёт чисел LLM/склейка версий **запрещены**. Индексация FTS по границам публикаций (R-027); селектор «последний» разрешается в SQL, не по FTS rank.

Обязательные русские сценарии: «что поменялось с прошлого плана», «на сколько дней уехал финал относительно базового», «как менялись сроки у задачи X», «какие связи удалили», «за счёт каких работ финал ушёл на дату Y», «что мы знали о базовом плане на дату X» (`known_at`).

### 19.8. Уровень В: воспроизведение и распределение изменения финала (W5)

Аналитический модуль в существующем контуре MppReader/EditPlanConfluence (R-028); MofsIndex хранит входы/результаты. Кандидат движка — MPXJ `MicrosoftScheduler`; совместимость подтверждается матрицей возможностей и эталонами на фактической версии runtime, не документацией. **Аналитика не пересчитывает и не публикует даты вместо MPP** — read-only относительно опубликованной страницы (§1, §4).

## TZ:patch 2026-10-01 — PUT storage `version+1` (HTTP 409)

Пакет `DEV/edit-plan-version-inc`. Баг скилла `productivity/edit-plan-confluence`, не USERTOOL. Источник: `_fix_plan_edit-plan-version_20261001` / `BUG:diagnose`. Версия ТЗ **не** бампится здесь (бамп — `TZ:finalize`). Код на этой фазе не меняется.

**I1.** `current`: `apply_plan` делает re-read страницы (`get_page(..., expand="version")`) и передаёт в `put_page` **текущий** `version.number` as-is. `ConfluenceClient.put_page` кладёт это число в payload без инкремента. Confluence REST на PUT требует **current+1**, иначе HTTP 409 `Version must be incremented. Current is: N`. Симптом двух подряд 409: вложение уходит с `conflictPolicy=override` (бампает версию вложения), PUT страницы падает, storage не сохраняется, повторный `apply` снова 409.  
`target`: re-read остаётся (optimistic lock); в `put_page` уходит `version + 1`. Клиент и вложение не рефакторятся. `conflictPolicy=override` на страницу не вводится.

Связь с соседями (reuse-first, без новых сущностей): ConfluenceSync `push` уже пишет PUT «с инкрементом version» — **не** импортировать его клиент (другой хост `conf.tutu.ru`, ТЗ запрещает менять пакет). Инкремент — на call-site в скилле (`pipeline.py`), сигнатура `put_page(..., version)` без изменения. MppReader / `read_mpp.py` к багу не относятся.

### Корневая причина (диск)

### 20.1. Цель

Доработать существующий скилл `productivity/edit-plan-confluence`, обеспечив:

1. Два явных сценария: публикация MPP на указанную страницу Confluence и сохранение MPP только в архив.
2. Однократный разбор исходного файла с повторным использованием подготовленных данных.
3. Сохранение семантики зависимостей, календарей, назначений и исходных дат.
4. Диагностику расхождений расписания без автоматической подгонки графа под длительность корня.
5. Подтверждение публикации только после проверки фактически сохранённых вложения и страницы.
6. Восстановление после сбоев без повторной загрузки уже записанного вложения.
7. Последовательное архивирование нескольких файлов одним запуском.
8. Долговечную историю, позволяющую получать хронологию поступлений и сравнивать конкретные снимки.
9. Раздельное отражение сохранности байтов, состояния страницы, качества расписания и достоверности исторических публикаций.

Обычная операция выполняется одним вызовом CLI. Дополнительное обращение к пользователю требуется при неоднозначном проекте, конфликте привязки, необходимости подтвердить происхождение задач или новом преобразовании смысла плана.

Успешное архивирование неполного плана допустимо по правилам §20.3.6. Оно не означает подтверждения корректности расписания.

### 20.3. Требования

#### 20.3.1. Общий конвейер

Реализовать две ветки поверх общего ядра.

**`save`:**

Приём файла → фиксация исходных байтов и хэша → разбор или кэш → проверка качества → архивирование → read-back архива → квитанция.

**`publish`:**

Приём файла → фиксация исходных байтов и хэша → разбор или кэш → локальное разрешение проекта и lineage, проверка идентификатора цели → первичное архивирование исходного snapshot и read-back → Confluence GET и проверка страницы → проверка идентичности, построение представления и диагностика → при необходимости `needs_decision → identity confirm → resume` → решение о допуске → долговечная фиксация производного представления и допущенного контекста → загрузка вложения → проверка вложения → PUT страницы → read-back страницы и её вложения → регистрация подтверждённой публикации → квитанция.

Первичный snapshot — обычный неизменяемый MPP snapshot по §20.5.3.1, созданный из исходных нормализованных данных **до** проверки применимости B/C и решения о публикации. Он не требует mapping revision, допуска к публикации или предварительного ручного `save`. Исключения меняют только производное представление. Совместное хранение снимков не подтверждает идентичность их задач.

Этот порядок обязателен и для `diff`: при разрешённом проекте/lineage и пригодном разборе команда создаёт либо переиспользует исходный snapshot, проверяет его и возвращает его ID даже при `needs_decision`. После подтверждения идентичности `resume` использует тот же snapshot; повторное поступление, повторный разбор при пригодном кэше и дублирующий snapshot не создаются. Выбор и фиксация revision определены в §20.6.3.3–6.3.5.

Если проект или lineage не разрешены либо snapshot невалиден, первичное архивирование не выполняется: сохраняются доступные исходные байты, поступление и причина остановки. Нельзя приписать snapshot произвольному проекту ради вызова `identity confirm`. Ошибка архивирования/read-back блокирует дальнейшую подготовку к сетевой записи.

Обязательные инварианты:

- `save` не создаёт Confluence-клиент, не требует токен Confluence и не выполняет запросы к Confluence.
- `save` и batch-save не меняют таблицы выбора baseline и не создают публикации.
- До первого POST/PUT долговечно сохранены исходник, подготовленное представление, решение о допуске и контекст попытки.
- Ошибка обязательного архивирования блокирует сетевые записи.
- Команда пользователя «залей на страницу …» с однозначным файлом и целью достаточна для обычной публикации. Повторное общее «да» не требуется.
- Новое изменение семантики плана возвращает `needs_decision` до сетевых записей.
- Согласованные исключения повторно не запрашиваются, если подтверждена их применимость.
- Допуск к публикации определяется таблицей §20.3.6. Исполнитель не выбирает самостоятельно, какое предупреждение считать блокирующим.
- Блокировка публикации не отменяет уже выполненное корректное архивирование. Квитанция отдельно сообщает состояние архива и публикации.
- При остановке после первичного архивирования квитанция содержит `snapshot_id`, `verification.archive:verified`, `published:false`, `external_effect:none`. Подготовка производного вложения и согласование могут оставаться незавершёнными; первичный snapshot не означает допуск к публикации.

Архив хранит исходные MPP и полный полученный экспорт, включая actuals/stop/resume; ограничения публикационного профиля не разрешают сокращать архив. `null` с `quality:missing, reason:not_set` сохраняется как отсутствие значения, а не заменяется нулём.

При локально разрешённых проекте/lineage сначала архивировать и проверить snapshot, затем обращаться к Confluence. При неоднозначном проекте произвольный snapshot по-прежнему запрещён. Отсутствие профиля, клиента или доступности Confluence не отменяет первичное архивирование в разрешённом локальном контексте.

#### 20.3.2. Приём файла

Приём входных данных перенести внутрь CLI.

Требования:

1. Поддержать локальный MPP и ZIP с одним MPP.
2. Определять ZIP по содержимому, а не только по расширению. Переименованный MPP не считать ZIP автоматически.
3. Для ZIP с несколькими MPP возвращать `multiple_mpp_candidates` со списком кандидатов. Не выбирать первый файл.
4. Создавать отдельный рабочий каталог операции. Не требовать ручного копирования во `/tmp`.
5. Сохранять исходное имя и происхождение файла отдельно от имени архивного объекта.
6. Рассчитывать SHA-256 по фактическим байтам MPP. Для ZIP дополнительно сохранять хэш контейнера и путь выбранного элемента.
7. Все стадии выполнять над зафиксированной копией файла. Изменение исходного пути после фиксации не меняет обрабатываемое содержимое.
8. При распаковке запрещать выход за рабочий каталог, коллизии имён и превышение документированных ограничений размера.
9. Ошибка чтения не должна выглядеть как пустой успешно сохранённый план.
10. Для batch выполнять фиксацию всех входов до разбора первого MPP согласно §20.5.2.

Фиксация включает запись копии, проверку её размера и хэша, атомарное завершение записи и регистрацию locator зафиксированных байтов.

Во время копирования проверять исходный файл: идентичность открытого файла, размер, время изменения и хэш контрольного чтения. Обнаруженное изменение возвращает `input_changed`. При отсутствии возможности получить согласованную копию файл не принимается.

#### 20.3.3. Однократный разбор и подготовленный результат

Основой сделать существующий полный экспорт `plan_export.export_full()`. CSV не должен оставаться обязательным промежуточным источником для каждой стадии.

Подготовленный результат включает:

| Группа | Обязательное содержание |
|---|---|
| Происхождение | SHA-256 MPP, размер, исходное имя, источник поступления, версии reader и формата экспорта |
| Проект | Метаданные, исходные начало/окончание, status date, параметры календарного пересчёта |
| Задачи | UID, исходный ID, иерархия, WBS, имя, summary/milestone, исходные даты и длительности |
| Планирование | Доступные ограничения, режим планирования, фактические значения, splits и прочие влияющие поля |
| Зависимости | Предшественник, последователь, тип, знак и величина лага, единицы, доступное основание календаря |
| Календари | Проектные, задач и ресурсов; рабочие интервалы, исключения, наследование и ссылки между ними |
| Ресурсы и назначения | Идентификаторы, units, work, доступные даты и календарные привязки |
| «Итого» | Исходные значения, вычисленные значения и правило их получения |
| Качество | Полнота коллекций и полей, отсутствующие/неподдерживаемые данные, ошибки графа |

Отсутствующее значение не заменять нулём или типом FS. Для коллекций использовать состояния `complete`, `partial`, `missing`, `unsupported`.

Наличие коллекции календарей не означает её полноту. Экспорт должен сохранять:

- все рабочие интервалы внутри каждого дня, включая разрывы;
- интервалы и признаки исключений;
- наследование базового календаря;
- проектный календарь;
- календарные привязки задач и ресурсов;
- доступные параметры взаимодействия календарей задачи и ресурса;
- используемые параметры перевода длительностей и трудозатрат.

Для каждого отсутствующего или неподдержанного поля сохранять качество и причину. Нельзя объявлять календарь `complete`, если извлечены только признаки рабочих дней.

**Критерий однократности:** на холодном кэше для одного файла и профиля экспорта выполняется не более одного вызова чтения проекта через MPXJ. Построение календаря, «Итого», диагностики и представления Confluence не должно повторно открывать MPP.

Если существующий аналитический компонент требует повторного чтения MPP, адаптировать его к подготовленным данным либо явно исключить его из штатной однопроходной ветки. Скрытый повторный разбор не допускается.

Разделять исходные факты, отображаемые значения и вычисляемое расписание. Исходный `percent_complete` сохраняется точно, включая дробные и summary-значения. Записывать следует исходный `percentDone`; статус использовать как производное отображение: 0 → `new`; 0<p<100 → `indeterminate`; 100 → `done`. Setter статуса для записи процента не использовать: он изменяет исходный процент.

Статус `done` означает завершённость по проценту. Дату фактического закрытия надо брать из `actual_finish`; подставлять `endDate` нельзя. Показывать её отдельным явно подписанным значением «Фактическое окончание MPP», при отсутствии — «не задано». Пользовательские текстовые колонки исходных percent/actual_start/actual_finish/actual_duration/actual_work/stop/resume сохраняют точную десятичную запись с единицей, без автоматического агрегирования.

При `percent=0` с заполненным actual start, отсутствующем проценте или `percent<100` с actual finish показывать исходные значения и «требует проверки». Неактивность задачи не означает её завершение. Плановые start/end/duration показываются отдельно от фактических значений.

#### 20.3.4. Кэш и воспроизводимость

Разделить два уровня:

| Уровень | Ключ |
|---|---|
| Разбор MPP | SHA-256 исходника + версия reader/MPXJ + версия экспорта + параметры, влияющие на экспорт |
| Подготовка представления | Хэш нормализованных данных + версия converter + ревизия правил + профиль целевого плагина + значимые параметры шаблона |

Требования:

- Изменение правил преобразования не требует повторного чтения MPP при пригодном кэше разбора.
- Изменение reader или схемы экспорта инвалидирует соответствующий кэш.
- Проверять целостность и завершённость записи кэша.
- Повреждённый кэш пересоздавать из архивного исходника.
- Время запуска, рабочие пути и operation ID не включать в семантическую идентичность результата.
- Обеспечить детерминированную сериализацию публикуемых байтов.
- Кэш можно удалить без потери истории.
- Кэш не заменяет свежую проверку страницы и вложения перед публикацией.
- Разрешённую таймзону и версию профиля нормализации фиксировать в подготовленном результате. Изменение значений, влияющих на нормализацию, меняет ключ соответствующего результата.

Ключ кэша и область дедупликации snapshot — разные контракты. Область дедупликации определена в §20.5.3.

#### 20.3.5. Сохранение зависимостей

Устранить принудительную запись всех связей как FS с нулевым лагом.

Для каждой зависимости сохранять:

- исходные и нормализованные идентификаторы концов;
- тип `FS`, `SS`, `FF`, `SF`;
- положительный, нулевой или отрицательный лаг;
- исходные единицы лага;
- различие рабочего и elapsed-времени, если оно есть в источнике;
- календарное основание, если доступно;
- качество извлечения и преобразования.

Создать явную таблицу соответствия типов и единиц формату конкретной установленной версии gantt-плагина. Числовые коды подтвердить документацией или контрольными примерами этой версии.

Если представление не поддерживается:

- исходные данные сохраняются;
- формируется диагностика;
- публикация с потерей смысла требует конкретного согласованного преобразования;
- тихая замена на FS/0 запрещена.

Самоссылки, циклы, неизвестные концы и внешние зависимости не должны молча исчезать. Они фиксируются как проблемы качества и обрабатываются по таблице допуска §20.3.6.

#### 20.3.6. Диагностика расписания и допуск к публикации

Равенство длительности корня и вычисленного пути не является достаточным доказательством корректности переноса. На расписание MS Project влияют также календари, ограничения, режимы планирования и назначения.

Диагностика последовательно проверяет:

1. Полноту извлечения исходных данных.
2. Сохранность типов связей и лагов.
3. Корректность календарей, единиц и трактовки дат.
4. Структуру графа, включая циклы и внешние связи.
5. Поддержку используемых возможностей целевым плагином.
6. Даты начала и окончания задач и вех.
7. Длительность и даты проекта как итоговую, но не единственную проверку.

Для каждой проверки различать:

- исходное значение MPP;
- значение подготовленного представления;
- результат модели, если применялась;
- фактически наблюдавшийся результат плагина, если он доступен.

Расчёт локальной модели нельзя выдавать за наблюдение работающего плагина.

Дополнительные требования:

- Корень и summary-задачи не включать как обычные последовательные работы в упрощённый longest-path.
- Связи с summary-задачами учитывать по подтверждённой семантике либо отмечать как неподдержанный профиль.
- Отсутствие поддерживаемого расчёта возвращать как `unsupported`/`not_verified`, а не как успешное совпадение.
- Сравнивать даты без округления до целых дней.
- Для дат с известной минутной точностью допустимое отклонение — не более одной минуты.
- Для неизвестной таймзоны абсолютное сравнение не заявлять подтверждённым.
- Для иной точности допуск фиксировать в версионируемом профиле проверки; отсутствие такого допуска не разрешает произвольное округление.
- Использовать существующую матрицу возможностей `MppReader/references/scheduler-capability-matrix.md`, учитывая её явно отмеченные ограничения.

Диагностический результат содержит проблемные задачи, связи, затронутую цепочку, отклонения дат и возможные преобразования с ожидаемыми последствиями.

Перебор удаляемых связей разрешён только как поиск кандидатов. Совпадение итогового числа не разрешает удаление автоматически.

Режим публикации «план + колонки факта» (решение владельца Д3): timeline строится по исходным плановым start/finish/duration, связям и календарям. Фактические actual_start/finish/duration/work, stop/resume, статус и точный процент показываются отдельными подписанными колонками факта. На странице и в отчёте явно: «по плану; факт — в колонках». Эквивалентный пересчёт расписания с участием факта не заявляется.

Классификация допуска: `display-only` — факты точно представлены открытыми customtext-колонками подтверждённого профиля, не переданы в поля расчёта и не изменяют плановые start/finish/duration; наличие таких фактов допускает публикацию с замечанием. `schedule-affecting` — факты меняют плановое расписание либо его корректность не подтверждена; сохраняется fail-closed. Потери отображения, плановых дат/длительностей, связей, календарей, ограничений и назначений продолжают блокировать публикацию. Пользовательская колонка доказывает только отображение; нативная поддержка actuals/stop/resume для этого режима не требуется. Исходный фактический пласт полностью сохраняется в архиве с качеством, отсутствием и единицами.

##### 20.3.6.1. Разделение подтверждений

Хранить независимо:

- `verification.archive` — прочитаны обратно архивные байты и snapshot;
- `verification.attachment` — проверены байты конкретной версии вложения;
- `verification.storage` — проверена фактически полученная страница;
- `verification.schedule` — качество проверки расписания.

Успешные первые три проверки не переводят расписание в `verified`.

`verification.schedule` содержит:

- `status`: `verified`, `not_verified`, `mismatch`, `accepted_deviation`, `not_applicable`;
- результаты проверок извлечения, представления, локальной модели и плагина;
- список ограничений;
- ссылки на профиль возможностей и принятые решения.

`verified` допустим только при достаточных данных и положительных проверках используемых возможностей, включая наблюдение результата установленного плагина для конкретного представления. Только локальная модель этого статуса не даёт.

`published:true` означает подтверждённое сохранение ожидаемых байтов и страницы. Статус расписания всегда выводится рядом и не подразумевается из `published`.

Отдельно фиксировать `verification.source_values` — проверку пользовательских значений (модель, видимый текст в обычном просмотре, повторное открытие, summary), и `verification.schedule` — проверку расписания. Проверка bytes/storage сама по себе не подтверждает видимость, точность процента или календарную семантику.

Неподтверждённая полнота перечисления и неизвестная причина блокируют публикацию. Повторное отражение причины в quality_issues не изменяет её классификацию. Исходные сведения о полноте сохраняются в архиве.

#### 20.3.7. Правила исключений проекта: B/C

Согласованное исключение хранить как версионируемое правило проекта.

Минимальный состав правила:

- `rule_id`, ревизия, `project_slug`;
- область применимости: подтверждённое происхождение или mapping revision;
- устойчивые ключи предшественника и последователя;
- ожидаемые тип и лаг исходной связи;
- контекст задач: иерархия, WBS и другие проверяемые признаки;
- действие над представлением Confluence;
- основание согласования, дата и ссылка на свидетельство;
- версия политики и условия прекращения применимости.

Порядок применения:

1. Проверить принадлежность проекту.
2. Подтвердить соответствие обеих задач по §20.6.3.
3. Проверить существование и контекст связи.
4. Проверить актуальность причины исключения после исправления конвертации.
5. Применить исключение только к представлению Confluence.
6. Повторить проверки допуска.
7. Записать результат применения в историю и квитанцию.

Номера строк `16:17`, имена задач или совпавшие UID между независимыми файлами сами по себе недостаточны.

Для B/C историческое согласование уже дано. Повторно спрашивать его не требуется при подтверждённом соответствии. Если исходники не позволяют установить устойчивые ключи, правило остаётся неактивированным, а операция возвращает конкретную неоднозначность.

Если корректная передача типа/лага устраняет расхождение, исключение не применять; зафиксировать `not_needed`.

#### 20.3.8. Проект и binding

- Добавить `--project-slug` в `publish`, совместимый `apply` и `diff`.
- При существующем однозначном binding разрешать отсутствие slug.
- Если slug передан явно, проверять его совпадение с существующей привязкой.
- Несовпадение возвращать как `binding_conflict`; не игнорировать переданный slug.
- Для страницы без binding требовать slug до создания пригодного к публикации контекста операции.
- Создавать binding штатной архивной стадией в составе публикации.
- Не требовать предварительного `save`.
- Не выводить slug из заголовка MPP.
- Не использовать ссылку на минутки из карточки проекта как целевую страницу плана.
- Не выбирать молча одну привязку, если в старых данных обнаружены противоречия.

`diff` сохраняет разрешённый slug в контексте операции. `resume` использует это значение. Для новой привязки `diff` без slug возвращает `project_slug_required`, exit code `2`; пригодный к публикации operation ID не выдаётся.

Уникальность binding в БД не считается доказательством идемпотентности всей публикации.

#### 20.3.9. Проверка публикации

**Отрицательный `verify_uploaded()` — блокирующая ошибка.**

Транспортный контракт общего клиента для GET конкретной версии уточнён в §21: сохранять `version=N`, не передавать `status`. Проверки байтов, актуальной цели и страницы ниже обязательны независимо от способа получения metadata.

После загрузки вложения:

1. Получить конкретную записанную версию вложения.
2. Вычислить SHA-256 полученных байтов.
3. Сравнить с хэшем подготовленных байтов.
4. При несовпадении остановить операцию до PUT страницы.
5. Не создавать подтверждённую публикацию и не возвращать успешный статус.

После PUT выполнить новый GET и проверить:

- на странице ровно один `gantt-chart-planner`;
- у существующего макроса сохранены `macro-id`, `id`, `hash`;
- для впервые созданного макроса параметры совпадают с сохранёнными параметрами операции;
- макрос ссылается на ожидаемое вложение;
- используемое им актуальное вложение соответствует ожидаемым байтам;
- строка «Итого» одна и содержит актуальные значения;
- устаревшего служебного блока «Трудозатраты» нет;
- постороннее содержимое страницы сохранено.

Параметр макроса `hash` и SHA-256 содержимого вложения — разные значения; проверять их независимо.

Для «Итого» сохранить формат:

```text
Итого: с DD.MM.YY по DD.MM.YY - N рабочих дней
```

Расчёт `N`, выбор корня и округление определены в §20.7.5. Дробные исходные значения хранить отдельно.

Человеко-часы получать из назначений без повторного суммирования summary-задач; в storage страницы не выводить.

`storage_verify` опирается на полученный ответ GET, а не на строку, отправленную в PUT.

Подтверждённую публикацию регистрировать только после:

- допуска по §20.3.6;
- положительного read-back архива;
- проверки вложения;
- проверки фактической страницы;
- отсутствия установленного конфликта цели.

Связать публикацию с исходным snapshot, опубликованным артефактом, наблюдением страницы, профилем проверки и результатом диагностики расписания.

Подтверждение относится к конкретным версиям и моменту наблюдения. Оно не гарантирует отсутствия последующих чужих изменений.

Каждая изменившаяся публикация полностью строит управляемое содержимое плана из выбранного архивного snapshot и версионированного профиля. Совпадающий повтор возвращает `unchanged`. Идентичность страницы и существующего макроса сохраняется. Не менять `macro-id`, `id`, `hash` существующего макроса. Полная замена содержимого вложения не означает удаление и пересоздание страницы или макроса.

#### 20.3.10. Конфликты и восстановление

Состояние операции хранить долговечно. Предусмотреть стадии:

```text
prepared → archived → admitted → attachment_uploaded → attachment_verified
→ storage_written → storage_verified → confirmed
```

Дополнительные состояния:

```text
needs_decision, failed, conflict, unknown, unchanged
```

Для `publish` стадия `archived` означает подтверждённое первичное архивирование исходного snapshot. Пауза `needs_decision` возможна после этой стадии и сохраняет её в `completed_stages`. `admitted` фиксируется только после выбора необходимой mapping revision, всех проверок допуска и сохранения производного представления. Для `save` достаточно `archived` и read-back; стадия `admitted` не требуется. Восстановление после паузы не откатывает уже подтверждённые стадии исходного архива.

Требования:

- До сетевого эффекта фиксировать намерение, после — наблюдаемый результат.
- Таймаут после POST/PUT означает неизвестный исход, пока не выполнена проверка.
- При возобновлении сначала определять фактическое состояние.
- Если нужное вложение уже загружено, проверено и после этого цель не изменилась, продолжать со страницы.
- Если страница уже корректна и актуальна, завершать локальную регистрацию без повторного PUT.
- При HTTP 409 перечитывать страницу и повторять только допустимый патч storage.
- Повтор после 409 разрешён, если изменения не затронули макрос, целевое вложение и управляемый блок.
- Изменение макроса, целевого вложения или управляемого блока другим процессом возвращает конфликт.
- Не применять `conflictPolicy=override` к PUT страницы.
- Число повторов ограничить; после исчерпания вернуть явную ошибку.
- Сохранять версии страницы и вложения, хэши управляемых фрагментов и наблюдения, необходимые для обнаружения конфликта.

Совпадение старой загруженной версии по хэшу недостаточно, если актуальная версия вложения уже изменена другим процессом.

Загрузка вложения может изменить отображаемый план ещё до PUT storage. Поэтому сбой после POST — частичный внешний эффект. Квитанция должна это отражать. Автоматический откат новой версией вложения в объём работы не входит.

Восстановление batch после SQL commit определено отдельно в §20.5.3.

Resume продолжает сохранённую операцию и не создаёт новую идентичность. Чужое изменение управляемой цели вызывает конфликт; постороннее содержимое страницы сохраняется. Архив и подготовленные bytes проверяются до сетевой записи; свежие GET/version и проверка конкретной версии вложения обязательны.

#### 20.3.11. Идемпотентность

Идемпотентность публикации определяется совокупностью:

- источника;
- версии преобразования и правил;
- целевой страницы и макроса;
- подготовленного содержимого;
- проверенного текущего состояния Confluence.

Повтор с тем же источником и преобразованием:

- при совпадающем целевом состоянии возвращает `unchanged`;
- не создаёт новую версию вложения;
- не выполняет лишний PUT страницы;
- не создаёт дубли подтверждённой публикации.

Если изменилось только ожидаемое «Итого» вследствие новой подготовки, разрешено исправить storage без повторной загрузки совпадающего вложения. Это не разрешает перезаписывать чужое изменение управляемого блока при продолжении старой операции.

Если изменился целевой план извне, одинаковый хэш MPP не даёт права молча перезаписать его.

Предусмотреть блокировку одновременных операций над одной целью и защиту от дублирующей архивной вставки. Внешние изменения дополнительно выявлять проверками версий и содержимого.

Запись при каждом одинаковом повторе недопустима (§20.3.11, AC-03). Если ожидаемые bytes и управляемое состояние совпадают, новый запуск не создаёт POST/PUT, новые версии страницы/вложения или новую идентичность макроса.

#### 20.3.12. Квитанция и диагностические артефакты

CLI выводит короткий JSON. Версия формата одиночной и пакетной квитанций — целое число `schema_version: 1`.

##### 20.3.12.1. Одиночная квитанция

Все перечисленные поля обязательны. Неизвестные значения представлены `null`, массивы без элементов — `[]`. Отсутствие поля не заменяет `null`.

| Поле | Тип и содержание |
|---|---|
| `schema_version` | Integer, строго `1` |
| `operation_id` | String; `null` только если операция не создана из-за ошибки аргументов или инфраструктуры |
| `item_id` | String; `null` до регистрации поступления |
| `status` | String: `prepared`, `saved`, `saved_with_warnings`, `published`, `published_with_warnings`, `unchanged`, `needs_decision`, `failed`, `conflict`, `unknown` |
| `mode` | `save` или `publish` |
| `exit_code` | Integer из §20.4.6 |
| `project_slug` | String либо `null`, если проект не разрешён |
| `source` | Object: `name`, `sha256`, `size_bytes`; каждое значение nullable до фиксации входа |
| `snapshot_id` | String либо `null` |
| `page_id`, `page_url` | String либо `null`; для `save` — `null` |
| `task_count` | Integer либо `null`; полное архивное количество по §20.7.5 |
| `display_task_count` | Integer либо `null`; количество без служебной ID=0 |
| `dependency_count` | Integer либо `null`; количество исходных зависимостей |
| `exceptions` | Array объектов с `rule_id`, `revision`, `result`, `evidence_id`; неприменимые ссылки nullable |
| `attachment_version` | Integer либо `null` |
| `verification` | Object с обязательными `archive`, `attachment`, `storage`, `source_values`, `schedule` |
| `published` | Boolean либо `null` |
| `warnings` | Array объектов `code`, `message`, `details_ref`; `details_ref` nullable |
| `completed_stages` | Array строк |
| `external_effect` | `none`, `attachment_written`, `storage_written`, `unknown` |
| `error` | `null` либо объект `code`, `message`, `retryable`, `next_action` |

Для `verification.archive`, `attachment`, `storage` допустимы `verified`, `failed`, `not_verified`, `not_applicable`.

`verification.source_values` содержит обязательные `status` (`verified`, `not_verified`, `mismatch`, `not_applicable`), `checks`, `limitations`, `evidence_ids`. GET байтов и storage не подтверждает видимость; для конкретного плана нужна привязанная к bytes/page/version/browser проверка модели, сериализуемых значений, видимого текста и повторного открытия.

`verification.schedule` содержит обязательные `status`, `checks`, `limitations`, `evidence_ids`. Статусы определены в §20.3.6.1; массивы могут быть пустыми.

Для `save` всегда `published:false`. Для подтверждённой публикации — `true`. После сетевой записи без подтверждения итогового состояния — `null`. До сетевых записей — `false`.

`unchanged` в режиме `publish` означает подтверждённое текущее состояние, поэтому `published:true`. При этом расписание может оставаться `not_verified`.

##### 20.3.12.2. Пакетная квитанция

Все поля обязательны:

| Поле | Тип и содержание |
|---|---|
| `schema_version` | Integer, строго `1` |
| `batch_id` | String; nullable только до создания пакета |
| `mode` | Строго `batch_save` |
| `status` | `completed`, `completed_with_errors`, `stopped`, `infrastructure_stopped`, `conflict`, `failed` |
| `exit_code` | Integer |
| `manifest_sha256` | String; nullable до фиксации канонического описания |
| `inputs_frozen_at` | ISO timestamp либо `null`, если фиксация не завершена |

| `counts` | Object с integer-полями `total`, `saved`, `saved_with_warnings`, `unchanged`, `failed`, `needs_decision`, `not_started` |
| `items` | Упорядоченный массив результатов всех элементов |

##### 20.3.12.3. Долговечные данные

Различать:

- обязательные долговечные данные: исходный MPP, нормализованный экспорт при успешном разборе, подготовленное вложение для публикации, контекст и квитанции;
- дополнительные диагностические дампы: CSV, дубли полного JSON, трассировки.

Обязательные данные сохраняются всегда, когда соответствующая стадия их сформировала. Неразбираемый вход не требует выдуманного нормализованного экспорта.

Дополнительные дампы создаются при ошибке; для `needs_decision` сохраняется адресное диагностическое предложение. Полные данные не выводятся в штатный stdout и не передаются модели без необходимости.

#### 20.3.13. Нефункциональные требования

- Использовать typed writer/query API MofsIndex; новые операции добавить в этот API.
- Миграции добавлять новыми версиями. Не менять задним числом применённый DDL.
- Сохранять долговечные `plan_*` при переиндексации MofsIndex.
- Записывать файлы атомарно; после записи проверять хэши и доступность.
- Сбой файловой записи или SQL не должен оставлять ложный успешный результат.
- Не хранить токены и Authorization в квитанциях и логах.
- Выбор Python с MPXJ выполнять централизованно; отсутствие рабочего окружения возвращать до сетевых записей.
- Для разбора и сетевых операций установить документированные таймауты.
- Последовательная обработка обязательна; распараллеливание MPP в batch не требуется.
- Измерять число разборов, попадания в кэш, длительность стадий, сетевые записи и вмешательства пользователя.
- Оценку экономии токенов 50–80% считать гипотезой. Приёмку основывать на измерениях и функциональных гарантиях.
- Обеспечить явный выбор изолированных БД, WorkVault и каталога кэша для тестирования.
- При восстановлении не подменять зафиксированные версии политики, профилей и правил текущими значениями по умолчанию.

Ниже — целевой интерфейс. Новые команды пока не считаются существующими.

Точка входа:

```text
/home/tkachenkoav/hermes-workspace/skills/productivity/edit-plan-confluence/scripts/cli.py
```

Глобальные параметры располагаются **до подкоманды**:

```text
cli.py [--db <sqlite>] [--workvault <dir>] [--cache-dir <dir>]
       [--allow-live-ab] <command> ...
```

При отсутствии параметров используются штатные пути. Тестовый запуск обязан передавать изолированные пути явно.

#### 20.4.1. Одиночные операции

```text
publish --mpp <file> --page-id <id> [--project-slug <slug>]
        [--timezone-hint <zone>]

save --mpp <file> --project-slug <slug>
     [--lineage-id <id>] [--timezone-hint <zone>]
     [--source-version-date <ISO-date>]

diff --mpp <file> --page-id <id> [--project-slug <slug>]
     [--timezone-hint <zone>]
```

`--source-version-date` — явно заданная дата версии плана; она не заменяет время поступления.

Таймзона разрешается из явного аргумента или подтверждённого профиля проекта. Константу другого проекта нельзя автоматически переносить на Trisigma.

`diff` готовит операцию режима `publish`, сохраняет источник, разрешённый slug, lineage, профиль, цель и operation ID. При пригодном разборе и разрешённом контексте обязательно создаёт либо переиспользует первичный snapshot с read-back по §20.3.1; его ID сохраняется в операции и квитанции. Сетевых записей не выполняет. Успешная подготовка возвращает `prepared / 0`; необходимость решения — `needs_decision / 3`, в том числе после успешного первичного архивирования.

Для новой привязки slug обязателен уже в `diff`. При существующем binding он разрешается из binding и фиксируется в операции.

Сохранить защиту страницы AB `519492935`: явная цель и флаг `--allow-live-ab`.

Точное расположение:

```text
cli.py --allow-live-ab publish --mpp <file> --page-id 519492935 ...
```

Для `resume` разрешение также передаётся перед подкомандой; отсутствие флага не разрешает новую запись на защищённую страницу.

#### 20.4.2. Продолжение операции

```text
resume --operation-id <id>

resume --operation-id <id> --accept-proposal <proposal-id>
       [--rule-scope once|project] --reason <text>

resume --operation-id <id> --timezone-hint <zone>

resume --operation-id <id> --mapping-revision <revision-id>
```

Принятие предложения связывается с точными хэшами источника, предложения и политики. По умолчанию область решения — `once`; постоянное правило проекта создаётся только при явном выборе `project`.

`--mapping-revision` выбирает подтверждённую revision для ожидающей решения пары snapshot по §20.6.3.3–6.3.5; он не создаёт подтверждение идентичности. Без аргумента `resume` может заполнить ещё не выбранную revision только единственным активным подходящим подтверждением. Уже зафиксированный выбор не заменяется автоматически. `--mapping-revision`, `--timezone-hint` и `--accept-proposal` — взаимоисключающие формы одного вызова; если решений несколько, выполнять их последовательно, сохраняя причины оставшихся остановок.

Для операции, принадлежащей batch-item, действует специальный контракт §20.5.3.4: `resume --accept-proposal ... --rule-scope once --reason ...` **только регистрирует решение** и не обрабатывает элемент. Последующее исполнение выполняет только `batch resume --retry-decisions`. Обычный одиночный `resume`, `--timezone-hint`, `--mapping-revision` и `--rule-scope project` для batch-item отклоняются с `batch_context_immutable / 4` и адресным `next_action`; менять зафиксированный контекст можно только новым пакетом. Неподдержанные сочетания аргументов возвращают `2`.

`--timezone-hint` при одиночном `resume` разрешён только для операции, остановленной из-за неразрешённой таймзоны, до сетевых записей. Он создаёт новую ревизию подготовки внутри операции, повторяет нормализацию и проверки. Если первичный snapshot уже создан с `unknown`, он сохраняется в истории, а новая ревизия подготовки получает snapshot в области новой таймзоны и новую связь с ним; старые revision/решения не переносятся на новую пару автоматически. Уже разрешённую таймзону молча менять нельзя; для этого требуется новая операция. Для batch этот аргумент запрещён, даже если зафиксирована таймзона `unknown`.

Перед продолжением проверяется актуальность цели. Устаревшее предложение нельзя применять к изменившимся данным.

Slug при `resume` берётся из сохранённого контекста. Если старая операция не содержит обязательный slug и не имеет однозначного binding, она не продолжается; вернуть `operation_context_incomplete` и предложить новый `diff --project-slug`.

Для просмотра состояния:

```text
operation show --operation-id <id>
```

Просмотр не возобновляет операцию.

`operation show` возвращает сохранённые `operation_id`, `item_id`, `batch_id` (nullable), хэш источника, `snapshot_id`, ревизию подготовки, `completed_stages`, причины `needs_decision`, предложения с `proposal_id`/SHA-256/областью действия и уже зарегистрированные решения. Обязательный массив `identity_requirements` содержит для каждой требуемой пары `from_snapshot_id`, `to_snapshot_id`, SHA-256 обоих MPP, применимое правило B/C и nullable `mapping_revision_id`; при отсутствии требований — `[]`. Один `resume --mapping-revision` заполняет соответствующую ещё не выбранную запись, остальные продолжают блокировать публикацию. Это данные для исполнимого продолжения, а не необходимость искать ID прямыми SQL-запросами.

#### 20.4.3. Пакетное архивирование

Три взаимоисключающих способа задать входы:

```text
batch save --project-slug trisigma
           --mpp /path/090726.mpp
           --mpp /path/230726.mpp

batch save --manifest /path/batch.json

batch save --inbox /home/tkachenkoav/WorkVault/Inbox/plans/trisigma/upload-001
           --project-slug trisigma
```

Общие параметры:

```text
[--batch-id <id>]
[--on-error continue|stop]
```

Для режимов `--mpp` и `--inbox` также доступны:

```text
[--lineage-id <id>] [--timezone-hint <zone>]
```

Для manifest проект, lineage и таймзона задаются в элементах; соответствующие общие аргументы отклоняются.

Правила ID и повторного запуска:

- Если `--batch-id` отсутствует, CLI создаёт новый ID.
- Явный новый ID создаёт новый пакет.
- `batch save --batch-id <existing-id> ...` повторно вычисляет каноническое описание запроса и сравнивает его с сохранённым.
- Совпадающее описание возвращает текущее состояние существующего пакета, не запускает повторную обработку и не создаёт новых поступлений.
- Изменённое описание, включая значимые параметры, возвращает `batch_manifest_conflict / 4`.
- Для фактического продолжения используется `batch resume`.
- Новый факт загрузки одинаковых файлов создаётся новым batch ID.

Приоритет `on_error`:

1. Явный `--on-error`.
2. Значение manifest.
3. Значение по умолчанию `continue`.

Эффективное значение фиксируется при создании пакета. `resume` его не меняет.

Возобновление и просмотр:

```text
batch resume --batch-id <id>
             [--retry-failed]
             [--retry-decisions]

batch show --batch-id <id>
           [--view all|errors]
```

`--view errors` показывает `failed`, `needs_decision`, причины остановки и оставшиеся `not_started`.

`batch resume` не принимает manifest: источником является зафиксированный пакет. Сценарий проверки изменённого manifest — повторный `batch save --batch-id ... --manifest ...`.

Регистрация решения для элемента:

```text
batch show --batch-id <id> --view errors
operation show --operation-id <item-operation-id>
resume --operation-id <item-operation-id>
       --accept-proposal <proposal-id> --rule-scope once --reason <text>
batch resume --batch-id <id> --retry-decisions
```

`item-operation-id` берётся из результата нужного элемента, а `proposal-id` — из `operation show`. Пара `batch_id + item_id` однозначно связывается с operation ID. Список допустимых причин, результат регистрации и ограничения определены в §20.5.3.4. Флаг `--retry-decisions` сам по себе не означает принятия ни одного предложения.

#### 20.4.4. Контракт manifest

Manifest — JSON с `schema_version: 1` и упорядоченным массивом элементов.

| Уровень | Поля |
|---|---|
| Пакет, обязательные | `schema_version`, непустой `items` |
| Пакет, необязательные | `label`, `on_error` |
| Элемент, обязательные | Уникальный в пакете `item_id`, `path`, `project_slug` |
| Элемент, необязательные | `lineage_id`, `source_version_date`, `expected_sha256`, `timezone_hint` |

Типы:

- `schema_version` — integer, строго `1`;
- `items` — array;
- остальные значения — непустые строки;
- `on_error` — `continue` или `stop`;
- `source_version_date` — `YYYY-MM-DD`;
- `expected_sha256` — 64 шестнадцатеричных символа SHA-256 фактического MPP;
- `timezone_hint` — допустимое имя IANA timezone.

Необязательные поля при отсутствии опускаются. Явный `null` в manifest не допускается.

Правила:

- Режим всех элементов в этой версии — `save`.
- `page_id`, `mode:publish`, `batch_id` внутри manifest и другие неизвестные поля отклоняются.
- Относительные пути разрешаются относительно manifest.
- Порядок массива является порядком обработки.
- Необязательный `expected_sha256` проверяется при фиксации входа до разбора.
- Для ZIP `expected_sha256` относится к извлечённому MPP; контейнер имеет отдельный фактический хэш.
- Дубли `item_id` считаются ошибкой.
- Структурная ошибка manifest обнаруживается до регистрации поступлений и обработки элементов.
- Пробелы JSON и порядок ключей объектов не влияют на канонический хэш.
- Порядок `items`, нормализованные абсолютные пути, поля элементов, метка и эффективный `on_error` входят в каноническое описание.
- Неявные значения lineage, таймзоны и профиля разрешаются при создании пакета и сохраняются. При проверке повторного запроса не подменяются новыми значениями конфигурации.

Минимальный пример:

```json
{
  "schema_version": 1,
  "on_error": "continue",
  "items": [
    {
      "item_id": "e",
      "path": "090726.mpp",
      "project_slug": "trisigma",
      "expected_sha256": "04aa6f521400af2c0e14e007a4fdff625d6bce956c6130052cb4a05a0c4d5e2a"
    },
    {
      "item_id": "f",
      "path": "230726.mpp",
      "project_slug": "trisigma",
      "expected_sha256": "58bd3830f4c126cb37ecc998702a980a67a84550cf9708950493cb358613395c"
    }
  ]
}
```

Отсутствие `expected_sha256` не отменяет обязательной фиксации фактических байтов и хэша.

#### 20.4.5. История, сравнение и проверка публикаций

```text
history --project-slug trisigma
        [--view files|snapshots|publications]
        [--order ingested|source]
        [--lineage-id <id>]
        [--since <ISO-timestamp>] [--until <ISO-timestamp>]
        [--time-field received|recorded|source|published]
        [--limit <N>] [--cursor <cursor>]

compare --project-slug trisigma
        --from snapshot:<snapshot-id>
        --to snapshot:<snapshot-id>
        [--mapping-revision <id>]

publication verify --project-slug trisigma
                   --publication-id <id>
```

Для сравнения публикаций использовать точные `publication:<publication-id>`. Один номер `v2` без страницы/вложения не является допустимым однозначным селектором.

Период задаётся полуинтервалом `[since, until)`. Timestamp обязан содержать `Z` или UTC offset. Для запроса «сегодня» скилл переводит локальные границы суток пользователя в такие timestamp.

Значения `time-field` по умолчанию:

- `files` → `received`;
- `snapshots` → `recorded`;
- `publications` → `published`.

При фильтрации по времени записи с неизвестным выбранным временем не включаются; ответ отдельно сообщает их количество. `--order source` не меняет поле фильтрации автоматически.

Сравнение показывает добавленные и удалённые задачи, изменения дат, длительностей, связей с типами/лагами, календарей и назначений. Неустановленное соответствие выводится отдельно.

Оба селектора проверяются на принадлежность указанному проекту до сравнения. Смешение MPP и Gantt JSON без явного подтверждённого mapping возвращает `representation_mismatch / 4`.

При неизвестной идентичности допустим read-only результат с `mapping:unknown`, перечнями несопоставленных сущностей и exit code `0`. Это не разрешает обозначать совпавшие UID как подтверждённые изменения одной задачи.

`publication verify` выполняет только чтение Confluence и добавляет локальные свидетельства по §20.6.7. POST/PUT запрещены.

Подтверждение идентичности:

```text
identity confirm --project-slug <slug>
                 --from snapshot:<id>
                 --to snapshot:<id>
                 --mode continuity|mapping
                 --evidence <file>
                 --reason <text>
                 [--mapping <file>]
                 [--supersedes <revision-id>]

identity show --project-slug <slug>
              --mapping-revision <id>
```

Контракт этих команд определён в §20.6.3.

Ответы запросов содержат `schema_version:1`, разрешённые точные ID, параметры запроса, результат и качество свидетельств. Они не маскируются под квитанции записи.

#### 20.4.6. Коды завершения

| Код | Значение |
|---|---|
| `0` | Успех, успех с замечаниями, `prepared` либо `unchanged`; для обработки batch все элементы успешно завершены; для отдельного `register_batch_decision` — только успешная регистрация решения, не обработка элемента |
| `2` | Некорректные аргументы или manifest |
| `3` | Требуется решение пользователя для одиночной операции |
| `4` | Конфликт binding, цели, входного хэша, проекта, mapping или описания существующего пакета |
| `5` | Ошибка выполнения, инфраструктурная остановка или неподтверждённый результат |
| `6` | Batch завершён либо остановлен политикой `stop` с неуспешными элементами |

Приоритет для batch:

1. Ошибка аргументов до принятия запроса — `2`.
2. Конфликт существующего batch ID/зафиксированного контекста — `4`.
3. Общая инфраструктурная остановка — `5`, даже если часть элементов успешно сохранена.
4. При отсутствии инфраструктурной остановки наличие `failed`, `needs_decision` или оставшихся из-за `stop` элементов — `6`.
5. Все элементы `saved`, `saved_with_warnings`, `unchanged` — `0`.

Локальные конфликты и решения отдельных элементов отражаются в их `error`; сами по себе они не превращают итоговый код batch в `3` или `4`.

Машинный stdout содержит только JSON результата. Краткий прогресс допускается в stderr.

#### 20.4.7. Совместимость

- Сохранить `preview`, `diff`, `convert`, `archive-history`.
- Существующий `apply` направить в общее ядро, добавить `--project-slug`.
- Прежний контракт `apply --confirm` можно сохранить для старых вызовов; новый `publish` не требует его.
- Старый `save --page-id` оставить как совместимый локальный режим привязки без Confluence-клиента.
- `--drop-dep FROM:TO` оставить только как явное исключение конкретного источника: разрешить номера в устойчивые ключи и связать решение с хэшем MPP. Не превращать его автоматически в правило следующих файлов.
- `diff` возвращает operation ID, пригодный для продолжения без повторного разбора, если обязательный контекст разрешён.
- Совместимые команды соблюдают те же проверки допуска, идентичности, проекта и достоверности публикации.

### 20.5. Многозагрузка и поведение по кейсам A–G

#### 20.5.1. Основной пользовательский сценарий многозагрузки

Основной обход ограничения Telegram:

1. Пользователь размещает несколько MPP в отдельной папке Inbox.
2. Отправляет одно текстовое сообщение: «Сохрани в архив Trisigma все MPP из …».
3. Скилл вызывает `batch save --inbox … --project-slug trisigma`.
4. CLI фиксирует входы и обрабатывает файлы по очереди.
5. Пользователь получает итог по пакету и отдельный результат каждого файла.

Таким образом, несколько планов обрабатываются по одному сообщению-команде без передачи нескольких вложений через проблемный вход шлюза.

Дополнительные варианты:

- несколько `--mpp` в одном CLI-вызове;
- manifest;
- несколько доступных локальных вложений, если транспорт уже успешно доставил их скиллу.

Нельзя обещать, что batch исправит отклонённое шлюзом сообщение: в таком случае скилл не получает ни команду, ни входные файлы.

#### 20.5.2. Обработка Inbox и фиксация входов

- Сканировать только явно указанную папку, без рекурсии по умолчанию.
- Принимать завершённые обычные `.mpp`; временные файлы и ссылки не включать молча.
- Зафиксировать список входов до начала обработки. Позднее добавленные файлы в текущий пакет не попадают.
- Для режима папки сортировать по относительному имени по Unicode code points, без зависимости от locale.
- Не считать этот порядок хронологией версий плана.
- Если нужен иной порядок, использовать manifest.
- Не удалять и не перемещать исходники автоматически.
- Не создавать постоянного наблюдателя Inbox.

**Выбранный контракт: фиксация байтов всех входов до разбора первого MPP.**

Порядок:

1. Проверить структуру запроса, зафиксировать список, порядок и разрешённые параметры.
2. Создать пакет в состоянии `freezing_inputs`.
3. Последовательно принять каждый вход по §20.3.2, сохранить неизменяемую копию и фактический хэш.
4. Для недоступного, исчезнувшего или изменившегося во время приёма входа сохранить конкретную ошибку.
5. Завершить фазу фиксации: атомарно зарегистрировать `inputs_frozen_at`, список принятых артефактов и ошибок.
6. Только после этого начать разбор MPP.

Фиксация не является одновременным снимком всего каталога: каждый файл имеет своё `frozen_at`. Гарантия состоит в том, что до обработки первого плана уже определены байты или ошибка каждого элемента.

Поведение при изменениях:

- Файл изменён во время копирования — `input_changed`, успешной фиксации элемента нет.
- Файл исчез до фиксации — `input_missing`.
- `expected_sha256` не совпал — `source_hash_mismatch`.
- Файл изменён или удалён после фиксации, пока обрабатывается другой элемент, — использовать зафиксированную копию.
- Файл изменён или удалён между остановкой и `batch resume` — использовать зафиксированную копию.
- Исходный путь при продолжении не перечитывается как новый источник.
- Утрата или повреждение зафиксированной копии — инфраструктурная ошибка. Допустимо восстановить её только байтами с уже зафиксированным SHA-256; принимать новые байты под прежним item ID запрещено.
- Новые или исправленные входные байты принимаются новым пакетом.

Если процесс прерван до завершения общей фазы фиксации, ни один snapshot этого пакета ещё не создаётся. `batch resume` возвращает `inputs_not_frozen / 4` и требует создать новый пакет. Уже сохранённые записи и артефакты незавершённой фиксации сохраняются как история; неизвестные входы не дочитываются с новыми байтами под прежним ID.

Политика `stop` влияет на последующую обработку. Фаза фиксации завершается для всего списка; при обработке первый неуспешный элемент останавливает дальнейший разбор.

#### 20.5.3. Последовательность, ошибки и восстановление batch

Для каждого принятого элемента:

Зафиксированный исходник → проверка отнесения к выбранному проекту/lineage (при необходимости решение по §20.5.3.4) → разбор/кэш → проверка качества → snapshot либо дедупликация → read-back → квитанция → следующий элемент.

Требования:

- Одновременно обрабатывается не более одного MPP.
- Каждый новый вариант содержимого в своей области дедупликации создаёт snapshot.
- Каждый элемент получает собственную запись поступления, даже при повторном содержимом.
- Ошибка одного файла по умолчанию не отменяет уже сохранённые и не блокирует остальные.
- При `--on-error stop` оставшиеся элементы отмечаются `not_started`.
- Общая ошибка инфраструктуры — недоступность БД, отказ архивного хранилища, невозможность журналирования — останавливает пакет.
- Все элементы сохраняют исходный порядок.
- Итог содержит количества из §20.3.12.2.
- Успешные элементы при продолжении не разбираются и не сохраняются повторно.

##### 20.5.3.1. Обязательная дедупликация

Одинаковые байты MPP **обязаны** использовать существующий snapshot при совпадении области:

```text
project / plan
+ lineage
+ source_mpp_sha256
+ representation
+ normalization_profile_fingerprint
+ resolved_timezone
```

`normalization_profile_fingerprint` включает:

- версию reader/MPXJ;
- версию экспорта;
- версию схемы нормализованных данных;
- параметры извлечения и нормализации, влияющие на snapshot.

Таймзона хранится как нормализованное IANA-имя либо отдельное значение `unknown`. `unknown` и конкретная таймзона — разные области.

Имя файла, locator, дата поступления, `source_version_date`, batch ID и item ID в ключ дедупликации не входят.

Правила B/C и профиль представления Confluence не входят в дедупликацию исходного MPP snapshot: они относятся к производному представлению.

Для одного ключа запрещено создавать второй snapshot, в том числе при конкурирующих операциях. Обеспечить ограничение уникальности или эквивалентный транзакционный механизм в typed writer.

Перед повторным использованием проверить доступность исходного артефакта, его SHA-256 и пригодность snapshot. Повреждённый существующий объект не считается успешно найденным дубликатом.

Новое поступление при дедупликации обязательно отражается в истории и связывается с существующим snapshot; результат элемента — `unchanged`.

Для ZIP область определяется фактическим MPP, поэтому разные ZIP с одинаковым MPP могут ссылаться на один snapshot. Контейнеры и их происхождение сохраняются отдельно.

Старые снимки без установленного профиля нормализации не объявлять эквивалентными автоматически. Их профиль либо доказательно восстанавливается миграцией, либо они остаются вне новой области дедупликации; историю не удалять.

##### 20.5.3.2. Правила продолжения состояний

| Состояние элемента | Обычный `batch resume` | Дополнительное действие |
|---|---|---|
| `saved`, `saved_with_warnings`, `unchanged` | Пропустить обработку; при необходимости восстановить зеркало квитанции | Новый разбор и новый snapshot запрещены |
| `not_started` при завершённой фиксации входов | Обработать автоматически | Использовать только зафиксированные байты и параметры |
| Прерванный `processing` / неизвестный исход SQL | Сначала выполнить reconciliation | Найти committed snapshot и связь с item до любой повторной вставки |
| `failed`, `retryable:true` | Не повторять автоматически | `--retry-failed` разрешает новую попытку на тех же байтах |
| `failed`, `retryable:false` | Не повторять | Исправленные байты, профиль или иной зафиксированный контекст — новый пакет |
| `needs_decision` | Оставить без изменения, даже при уже зарегистрированном решении | Зарегистрировать решение через `resume --operation-id <item-operation-id> --accept-proposal ...` по §20.5.3.4; только `batch resume --retry-decisions` повторяет проверку применимости и обработку |
| Ошибка фиксации входа | Не принимать файл заново | Новый пакет |
| Незавершённая общая фиксация входов | Не продолжать | `inputs_not_frozen / 4`, новый пакет |

Повторяемые ошибки: временный отказ reader-процесса, временный отказ инфраструктуры после её восстановления и аналогичные явно классифицированные ошибки.

Повреждённый формат MPP, несовпадение ожидаемого хэша и смена входных байтов не являются автоматически повторяемыми ошибками.

##### 20.5.3.3. Сбой после SQL commit

До обработки элемента долговечно сохранить:

- item ID;
- operation/attempt ID;
- ключ дедупликации;
- хэш исходника;
- намерение создать или использовать snapshot.

В одной SQL-транзакции выполнить:

1. Создание snapshot либо выбор существующего по ключу.
2. Запись версионных данных для нового snapshot.
3. Привязку `plan_import_item → snapshot`.
4. Событие `snapshot_committed` с operation/item ID.

Финальный read-back и файловая квитанция могут выполняться после commit.

Если процесс упал после commit, но до фиксации успешного результата элемента, `resume` обязан:

1. Найти связь item со snapshot и committed-событие.
2. Проверить snapshot и артефакты чтением.
3. Завершить результат элемента и восстановить квитанцию.
4. Не создавать новый snapshot и не выполнять повторный разбор MPP.

Если commit не произошёл, операция повторяет архивную стадию с тем же ключом. Неизвестный исход SQL сначала разрешается запросом, а не повторной вставкой.

##### 20.5.3.4. Причины `needs_decision` и регистрация решения batch-item

В `batch save` проект обязателен, lineage выбирается явно либо как стабильная архивная линия проекта. Исходное архивирование не требует идентичности задач, правил B/C, допуска scheduler или плагина. Неполнота данных, неизвестная таймзона, несколько содержательных корней и проблемы графа при пригодном snapshot дают `saved_with_warnings`, а не запрос разрешения на публикацию.

Допустимы только следующие причины `needs_decision`:

| `error.code` / причина | Условие | Допустимое предложение в текущем пакете | Когда нужен новый пакет |
|---|---|---|---|
| `archive_project_confirmation_required` | Проект уже явно выбран и зафиксирован, но локальная история происхождения содержит неподтверждённые противоречащие сведения об отнесении этого исходника к другому проекту; подтверждённого запрета нет | `confirm_archive_project`: подтвердить архивирование именно в зафиксированный `project_slug`, перечислив противоречащие сведения и их качество | Пользователь выбирает другой проект или требуется изменить иные параметры |
| `archive_lineage_confirmation_required` | Проект разрешён, конкретная lineage этого проекта уже выбрана и зафиксирована, но локальная история происхождения содержит неподтверждённые противоречащие сведения об отнесении к другой lineage того же проекта | `confirm_archive_lineage`: подтвердить только архивное размещение в уже выбранной lineage; это не подтверждает непрерывность UID | Пользователь выбирает другую lineage или требуется изменить иные параметры |

Обычное отсутствие истории, совпадение UID, неизвестный mapping или новое имя файла не являются основаниями этих остановок. Нельзя генерировать предложение лишь потому, что файл новый. Источники противоречащих сведений должны быть перечислены в диагностике с ID/хэшами; скилл не выдумывает их. Если противоречия относятся одновременно к проекту и lineage, сохраняются оба предложения; `error.code` указывает первую незакрытую причину, `operation show` возвращает полный список.

Отсутствующий обязательный slug или некорректный manifest — ошибка аргументов `2` до создания пакета. Не принадлежащая проекту lineage, доказанный конфликт проекта/контекста или несовпадение хэша — ошибка элемента, а не согласуемая неоднозначность; в пакетной квитанции элемент `failed` с конкретным кодом в `error`. Их нельзя разрешать общим согласием. Неудачная фиксация входов и неизвестный исход SQL обрабатываются по §20.5.2 и §20.5.3.3, а не через proposal.

Предложения не меняют архивируемые данные. Каждое неизменяемое предложение включает:

- `proposal_id`, тип, SHA-256 содержимого предложения;
- `batch_id`, `item_id`, `operation_id`, `manifest_sha256`;
- фактический SHA-256 MPP и fingerprint зафиксированного контекста;
- проект, lineage, профиль нормализации, разрешённую таймзону (включая `unknown`), дату версии и политику;
- ссылки на противоречащие сведения, точное подтверждаемое действие и последствия;
- признак, что действие не меняет зафиксированные параметры.

**Регистрация:**

```text
resume --operation-id <item-operation-id>
       --accept-proposal <proposal-id> --rule-scope once
       --reason "Подтверждаю архивирование в указанный в предложении проект/lineage"
```

CLI находит владельца операции — batch/item, получает ту же блокировку пакета, что и пакетный обработчик, проверяет `inputs_frozen_at`, состояние `needs_decision`, принадлежность и актуальность proposal. При живом владельце блокировки вернуть `batch_busy / 4` без изменения состояния. Регистрация решения и обработка элемента не могут выполняться одновременно. Решение сохраняется через typed writer в одной транзакции с событием `decision_registered`: точные ID, хэши, автор/источник, время и непустое основание.

Команда не запускает reader, не создаёт snapshot, не меняет baseline, manifest, профиль, таймзону, проект, lineage или политику ошибок. `--rule-scope` допускает только `once` (по умолчанию); проектное правило через batch-item не создаётся. Элемент остаётся `needs_decision`; в его состоянии и `operation show` появляется запись решения и `decision_ready`, истинное только после закрытия всех причин.

Успех регистрации возвращает отдельный JSON результата действия, не квитанцию архивирования: обязательные `schema_version:1`, `action:"register_batch_decision"`, `status:"decision_registered"`, `exit_code:0`, `batch_id`, `item_id`, `operation_id`, `proposal_id`, `decision_id`, `manifest_sha256`, `decision_ready`, `published:false`, `error:null`. `0` означает только долговечную регистрацию решения. Повтор того же принятия возвращает существующий `decision_id`, без нового решения или архивного эффекта. Попытка заменить основание/содержание уже зарегистрированного решения — `decision_conflict / 4`; история не переписывается.

Чужое, устаревшее или несовместимое предложение возвращает `proposal_context_mismatch / 4` и не записывает решение. Общее «игнорировать предупреждения» без подходящего proposal не допускается. Прямое редактирование manifest, событий или таблиц для регистрации решения запрещено.

**Продолжение:** только `batch resume --batch-id <id> --retry-decisions` получает блокировку, сверяет registered decision с неизменяемыми исходником, manifest и контекстом, повторяет проверку оснований и затем выполняет архивную обработку в исходном порядке. Переиспользуются те же item/operation ID; новые попытки добавляются в журнал. Обычный `batch resume` не потребляет зарегистрированное решение. Без подходящего решения либо при оставшихся причинах элемент сохраняет `needs_decision`; флаг не даёт права автоматически выбрать ответ. При `on_error:stop` этот элемент снова останавливает обход, при `continue` остальные допустимые элементы продолжаются. Новые противоречащие сведения инвалидируют применимость прежнего предложения: сохранить старую историю, выпустить новое адресное предложение и запросить новое решение.

`manifest_sha256` и каноническое описание остаются неизменными и при регистрации, и при исполнении. Решения хранятся отдельно как добавляемые события с привязкой к manifest; они не являются новой версией исходного запроса. После SQL commit и сбоя восстановления действует §20.5.3.3: повторно регистрировать решение, разбирать MPP и создавать snapshot не требуется.

Изменение проекта, lineage, байтов/выбранного элемента ZIP, профиля reader/нормализации, таймзоны (включая `unknown → IANA`), даты версии, порядка элементов или `on_error` требует **нового batch ID и нового пакета**. Изменённый запрос со старым ID возвращает `batch_manifest_conflict / 4`. Старые поступления и решения сохраняются. Команда одиночного `resume --timezone-hint` не служит обходом этого запрета.

**Исполнимый сценарий:**

```text
batch save --batch-id review-001 --manifest /absolute/path/batch.json
batch show --batch-id review-001 --view errors
operation show --operation-id <operation_id-элемента-с-needs_decision>
resume --operation-id <тот-же-operation_id>
       --accept-proposal <proposal_id-из-operation-show>
       --rule-scope once --reason "Подтверждаю выбранное архивное размещение"
batch resume --batch-id review-001 --retry-decisions
batch show --batch-id review-001 --view all
```

Все вызовы используют одни и те же глобальные `--db`, `--workvault`, `--cache-dir` перед подкомандой. При нескольких предложениях выполнить регистрацию каждого. Если пользователь вместо подтверждения выбирает иной контекст, подготовить manifest с нужными значениями и вызвать `batch save --batch-id review-002 --manifest <новый-файл>`; пакет `review-001` не переписывать.

### 20.6. Хранение истории

#### 20.6.1. Источник истины

Использовать существующую БД MofsIndex и её plan-схему.

| Сущность | Назначение |
|---|---|
| `plan` | Проект и его логический план |
| `plan_lineage` | Линия происхождения / привязка к странице |
| `plan_artifact` | Исходные и производные байты по SHA-256 |
| `plan_snapshot` | Нормализованный снимок |
| `plan_*_version` | Задачи, зависимости, ресурсы, назначения, календари |
| `plan_snapshot_collection` | Полнота и количества коллекций |
| `plan_import_attempt`, `plan_attempt_event` | Операции и события их выполнения |
| `plan_publication` | Регистрации публикаций с явным уровнем доверия |
| `plan_publication_snapshot` | Связь публикации со снимком |
| `plan_page_observation`, `plan_publication_page_link` | Проверенное состояние страницы и его связь с публикацией |
| `plan_mapping_revision`, `plan_identity_mapping` | Ревизии соответствий и соответствия сущностей |
| `plan_quality_issue` | Проблемы данных и переноса |

Не создавать параллельный архив в отдельной БД или Markdown-журнал как основной источник истины.

#### 20.6.2. Недостающие данные поступлений и пакетов

Добавить миграцией:

**`plan_import_batch`** — пакет:

- `batch_id`;
- версия, каноническое описание и SHA-256 manifest;
- источник: CLI, Inbox, доставленные вложения;
- время создания, завершения фиксации входов и завершения обработки;
- эффективная политика ошибок;
- зафиксированные профили и параметры;
- итоговое состояние и причина остановки.

**`plan_import_item`** — факт поступления файла:

- `item_id`, необязательный `batch_id`, порядковый номер;
- проект и lineage;
- исходное имя и исходный locator;
- транспортное происхождение, если известно;
- SHA-256 и размер;
- сведения о ZIP-контейнере, если применимо;
- время получения и фиксации;
- явно заданная дата версии и её основание;
- ссылки на зафиксированный artifact и snapshot;
- профиль нормализации и разрешённая таймзона;
- ключ дедупликации;
- итоговое состояние, код ошибки и признак повторяемости.

Для batch-item дополнительно хранить связь с неизменяемыми proposal, зарегистрированными решениями и их событиями по §20.5.3.4; `decision_ready` может быть проекцией этих событий. `manifest_sha256` не пересчитывается вследствие решения. Для publish-операции хранить ревизии подготовки, ссылки на первичные snapshot и точные выбранные mapping revision по §20.6.3.5; исходные снимки не переписывать.

Одиночный `save`/`publish` также создаёт запись поступления без обязательного batch.

Связать существующие попытки с `item_id`, чтобы повторные попытки не уничтожали историю одного элемента. События сохранять добавлением; текущее состояние может быть проекцией этих событий.

Для правил преобразований добавить версионируемое хранилище в той же plan-схеме с полями из §20.3.7. Исторические ревизии правил не перезаписывать.

Добавить данные для:

- области дедупликации snapshot;
- свидетельств происхождения и области mapping revision;
- уровня доверия публикации;
- версий проверок, результатов и наблюдений.

#### 20.6.3. Lineage и исполнимый контракт идентичности

- Локальную линию больше не создавать отдельно для каждого имени файла.
- При отсутствии явного `--lineage-id` использовать стабильную архивную линию проекта.
- Имя файла не является идентификатором линии или версии.
- Явный lineage должен принадлежать указанному проекту.
- Совместное хранение в одной линии не доказывает идентичность задач между независимо созданными MPP.
- Старые линии не сливать автоматически. Историю агрегировать по проекту с сохранением исходных связей.

##### 20.6.3.1. Подтверждение происхождения

Непрерывность происхождения подтверждается явной командой:

```text
identity confirm --project-slug <slug>
                 --from snapshot:<a>
                 --to snapshot:<b>
                 --mode continuity
                 --evidence <file>
                 --reason <text>
```

Команда означает утверждение уполномоченного пользователя: второй файл является продолжением первого с сохранением пространства идентичности UID, а не независимым планом с совпавшими номерами.

До записи проверить:

- существование обоих snapshot;
- принадлежность одному указанному проекту;
- представление MPP;
- уникальность и допустимость UID в каждом снимке;
- отсутствие конфликтующих подтверждённых соответствий.

Существование снимков обеспечивается первичным архивированием в `publish`/`diff` по §20.3.1: новый пригодный MPP должен получить snapshot до остановки на неизвестной идентичности. `identity confirm` не требует готового производного вложения или разрешения на публикацию. Если архивирование не удалось, сначала устраняется его ошибка; предварительный ручной `save` нового входа не является шагом этого сценария.

Имя файла, общая lineage, совпадение UID, похожие названия или проектные метаданные сами по себе не создают такого подтверждения.

Свидетельство сохраняется неизменяемым артефактом с SHA-256. Запись подтверждения содержит:

- ID обоих snapshot и хэши исходных MPP;
- проект;
- вид `continuity`;
- автора/источник действия и время;
- текст основания;
- ссылку и хэш свидетельства;
- ревизию политики;
- созданную mapping revision.

Допустимое свидетельство — сохранённое явное утверждение пользователя о происхождении либо документированная цепочка редакций с таким утверждением. Скилл не создаёт подтверждение от имени пользователя на основании догадки.

Подтверждение распространяется на указанную пару снимков. Для следующих пар нужна новая проверка и регистрация. Автоматическая транзитивность через произвольную цепочку не используется.

Успешный `identity confirm` возвращает `schema_version:1`, `status:"confirmed"`, `exit_code:0`, `project_slug`, точные `from_snapshot_id`/`to_snapshot_id`, хэши исходников, `mapping_revision_id`, `evidence_id` и SHA-256 сохранённого свидетельства. Команда только регистрирует подтверждение; ожидающую publish-операцию автоматически не запускает и ранее выбранную revision в ней не заменяет.

##### 20.6.3.2. Явный mapping

Для независимых планов или изменившихся UID:

```text
identity confirm --project-slug <slug>
                 --from snapshot:<a>
                 --to snapshot:<b>
                 --mode mapping
                 --mapping <file>
                 --evidence <file>
                 --reason <text>
```

Минимальная схема mapping-файла:

```json
{
  "schema_version": 1,
  "pairs": [
    {
      "entity_kind": "task",
      "from_key": "uid:164",
      "to_key": "uid:900",
      "identity_key": "trisigma:project-root"
    }
  ]
}
```

Все поля обязательны, `null` запрещён. Неизвестные поля отклоняются.

Допустимые `entity_kind`: `task`, `resource`, `calendar`, `assignment`. При необходимости расширить ограничения существующей схемы миграцией.

Проверять существование локальных ключей, тип сущности и однозначность соответствия в каждой стороне. Несопоставленные сущности не получают подтверждённую идентичность.

Mapping может быть частичным. В этом случае результат сравнения явно содержит область подтверждённого сопоставления и несопоставленные остатки.

##### 20.6.3.3. Выбор revision

Mapping revision неизменяема и привязана к точной паре снимков, их представлениям и проекту.

Правила выбора:

1. Если передан `--mapping-revision`, проверить её проект, пару селекторов, представления, статус подтверждения и отсутствие отзыва.
2. Если revision не передана и существует ровно одна активная подтверждённая revision для пары, выбрать её.
3. Если подтверждений нет, вернуть `mapping:unknown`; совпадение UID не повышает качество.
4. Если активных подходящих revision несколько, вернуть `mapping_ambiguous / 3`.
5. Замену активной revision выполнять явной командой с `--supersedes`; старую сохранить в истории.
6. Выбранный ID revision фиксировать в результате compare, правилах B/C и контексте операции.

Для ожидающей publish-операции выбор проверяется относительно пары `from = опорный snapshot правила/происхождения`, `to = первичный snapshot текущей ревизии подготовки`. Явный аргумент `resume --mapping-revision` имеет приоритет только при ещё не заполненном выборе этой пары; отсутствие подтверждения даёт `identity_confirmation_required / 3`, несколько подходящих — `mapping_ambiguous / 3`. Частичный mapping пригоден для B/C только если подтверждены обе задачи связи и все необходимые правилу сущности; иначе остаётся конкретное `needs_decision`.

Выбор фиксируется атомарно **после проверки достаточности mapping для требуемых сущностей, до применения правила** вместе с ID пары, SHA-256 источников, evidence, ревизией подготовки и ревизией правила. Недостаточный частичный mapping сохраняется как результат проверки, но не заполняет неизменяемый выбор операции: после регистрации достаточного подтверждения разрешён новый выбор. Повторный `resume` использует зафиксированный ID, не подставляя «последнюю» revision. Повтор того же аргумента идемпотентен; попытка выбрать другую revision вместо уже зафиксированной в той же подготовке возвращает `mapping_revision_conflict / 4` и требует новой операции. Отозванная, superseded или более не пригодная зафиксированная revision также блокирует сетевые записи, а не заменяется автоматически. Изменение нормализации/таймзоны создаёт новую ревизию подготовки с другой парой и самостоятельным выбором; прежняя сохраняется для аудита (§20.4.2).

Для сравнения snapshot с самим собой либо двумя снимками одинакового источника в одинаковом профиле допустимо доказательство `same_source`; оно не подтверждает происхождение других файлов.

##### 20.6.3.4. Обязательная доработка typed query API

Доработать `_diff_snapshots()` и публичные typed query-операции, а не только CLI-обёртку.

Обязательное поведение:

- Разрешать оба селектора и проверять их принадлежность указанному `project/plan`.
- Для публикаций проверять также страницу, вложение, snapshot и качество связи с источником.
- Не возвращать `confirmed_uid` без выбранного подтверждения происхождения.
- Сопоставлять задачи по выбранной revision.
- Возвращать ID revision и свидетельств.
- При неизвестной идентичности показывать несопоставленные сущности, не выдавая их за доказанные добавления/удаления одной линии.
- Сравнивать задачи по датам, длительностям, имени, иерархии, ограничениям, календарным привязкам и другим сохранённым значимым полям.
- Сравнивать зависимости с учётом сопоставленных концов, типа, величины и знака лага, единиц, рабочего/elapsed-времени и календарного основания.
- Изменение только типа или лага обязательно отражать в diff.
- Не терять параллельные зависимости между одинаковыми концами: сравнивать мультимножества полных записей либо использовать подтверждённую идентичность связи.
- Сравнивать календари: интервалы, исключения, наследование, параметры и привязки.
- Сравнивать назначения: задачу, ресурс, units, work, даты и доступные календарные данные.
- При неизвестной идентичности календаря или назначения показывать несопоставленные структурные записи, а не скрывать различия.
- Не выводить `calendar:known` только из наличия timezone.
- Не объявлять `completeness:complete`, если необходимые коллекции или поля неполны.
- Не вычислять абсолютные отклонения дат при неразрешённой таймзоне.

Аналогичную защиту применить к `task_history` и другим typed query, которые сейчас могут объявлять подтверждённую идентичность только по UID.

##### 20.6.3.5. Новый MPP: `needs_decision → identity confirm → resume`

Предусловие: опорный snapshot правила B/C уже существует как часть истории и содержит подтверждённый контекст исторического исключения. Новый входящий MPP ранее не архивирован. Если опорного snapshot нет, это отдельное отсутствие исходных данных правила: его нельзя выдумывать; правило остаётся неактивным с адресной диагностикой. Новый вход всё равно архивируется при разрешённом контексте.

1. Вызвать `publish --mpp <новый-MPP> --page-id <цель> --project-slug <slug>` либо `diff` с теми же аргументами. CLI фиксирует вход, один раз читает MPP, создаёт/находит исходный snapshot и выполняет read-back.
2. Если для требуемого правила нет подтверждённой идентичности, вернуть `needs_decision / 3` **после** архивирования и **до** применения исключения и POST/PUT. Квитанция содержит `snapshot_id`, `verification.archive:verified`, `published:false`; `error.next_action` указывает на `operation show` и точную пару для подтверждения.
3. Через `operation show` получить ID опорного и нового snapshot, хэши источников, правило и причину остановки. Сохранить явное свидетельство пользователя о continuity либо согласованный mapping; скилл не сочиняет это утверждение.
4. Выполнить `identity confirm` для этой точной пары. Команда возвращает новую `mapping_revision_id`; оба snapshot уже существуют благодаря шагу 1 и истории опорного файла.
5. Выполнить `resume --operation-id <тот-же-id> --mapping-revision <возвращённая-revision>`. CLI проверяет область и качество подтверждения, фиксирует revision, проверяет контекст связи и необходимость B/C, строит представление и повторяет допуск. Явный аргумент предпочтителен для воспроизводимости; без него допустим только единственный активный подходящий выбор по §20.6.3.3.
6. При наличии других нерешённых причин снова вернуть адресный `needs_decision`, сохранив уже принятый выбор. При допуске сохранить производное представление, проверить актуальность цели и продолжить сетевые стадии. Ни подтверждение идентичности, ни историческое согласование B/C не отменяют этих проверок.

```text
diff --mpp /absolute/path/new-plan.mpp --page-id <test-page> --project-slug trisigma
operation show --operation-id <operation-id-из-diff>
identity confirm --project-slug trisigma
                 --from snapshot:<опорный-id-из-operation-show>
                 --to snapshot:<новый-id-из-operation-show>
                 --mode continuity --evidence /absolute/path/user-confirmation.txt
                 --reason "Пользователь подтвердил продолжение указанного исходного плана"
resume --operation-id <operation-id-из-diff> --mapping-revision <revision-из-identity-confirm>
```

Для изменившихся UID использовать `--mode mapping --mapping <file>` вместо continuity. Все команды обращаются к одним и тем же БД/WorkVault/cache. В сценарии отсутствует отдельный `save` нового MPP. Исходный snapshot и поступление не дублируются при повторе `resume`; при неизменном профиле и пригодном кэше суммарно выполняется один разбор нового MPP.

#### 20.6.4. Байтовый архив

Сохранить действующую структуру:

```text
WorkVault/Entities/<slug>/Sources/plans/<plan-key>/artifacts/<sha256>.<ext>
```

Квитанции сохранять в существующем каталоге:

```text
WorkVault/_plan-receipts/<attempt-id>/
```

Их запись должна быть атомарной. Файловые квитанции — зеркало событий, а не замена БД.

При дедупликации через существующий `plan_artifact` проверять реальную доступность и хэш файла. Совпадение записи в БД само по себе недостаточно.

Зафиксированные входы batch должны находиться в долговечном хранилище, доступном после перезапуска процесса. Временный каталог ОС не является достаточным местом их единственной копии.

Полный исходник и нормализованный экспорт архивируются независимо от publication capabilities. Для расширенной гарантии внутри publish snapshot/read-back предшествуют Confluence GET при локально разрешённых проекте/lineage. Сохранность всех шести полей actual_start/finish/duration/work, stop/resume проверяется точным round-trip, включая отсутствие, качество и единицы.

#### 20.6.5. Времена и хронология

Разделять:

- `received_at` / `observed_at` — получение;
- `frozen_at` — фиксацию входных байтов;
- `recorded_at` — фиксацию в архиве;
- `source_version_date` — явно заданную дату версии;
- `status_date` — поле исходного плана;
- `published_at` — событие публикации, когда оно установлено;
- `verified_at` — время конкретной проверки публикации.

Не подставлять дату из имени файла вместо времени поступления. Не объявлять время импорта датой старой публикации.

По умолчанию `history` сортирует поступления по времени получения, затем по устойчивому порядку элементов. Для `--order source` записи без известной даты версии показывать отдельно.

NULL в `plan_snapshot.published_at` сам по себе не доказывает отсутствие публикаций этого снимка. Проверять связи с `plan_publication` и уровень доверия этих записей.

#### 20.6.6. Запросы пользователя

Скилл маршрутизирует:

- «Покажи хронологию планов Trisigma» → история поступлений с датами, именами, хэшами и snapshot ID.
- «Какие файлы загрузили сегодня?» → история поступлений за период с явными границами.
- «Сравни X и Y» → разрешение обеих версий в точные идентификаторы и typed query.
- «Какая версия опубликована на странице?» → конкретная страница, вложение, наблюдение и уровень подтверждения публикации.
- «Что не загрузилось в пакете?» → `batch show --view errors`.

В ответе на сравнение указывать выбранные snapshot/publication ID, представление, mapping revision и качество сопоставления. Неподтверждённые причины изменения сроков не выдавать за установленную причинность.

Если текущего наблюдения страницы нет, ответ о публикации формулировать как «последняя подтверждённая на момент …», а не как гарантированно текущее состояние.

#### 20.6.7. Доверие к старым публикациям после миграции

Сохранить все исторические записи и связи. Добавить независимый уровень доверия:

| Уровень | Значение |
|---|---|
| `legacy_unverified` | Старая регистрация без достаточных свидетельств новых проверок |
| `verified_observation` | Новая проверка подтвердила наблюдаемое состояние старой публикации на конкретный момент |
| `verified_v1` | Публикация завершена новым конвейером с обязательными проверками |
| `verification_failed` | Новая проверка обнаружила несоответствие; прежние события сохранены |

При миграции:

- Старый признак «confirmed» сам по себе недостаточен.
- Записи без полного проверяемого набора свидетельств получают `legacy_unverified`.
- Старое исходное значение статуса сохраняется как исторический атрибут.
- Миграция не обращается к Confluence и не выполняет сетевые записи.
- История показывает, что версия была зарегистрирована старым кодом, но её публикация новыми проверками не подтверждена.

Сценарий повторной проверки:

```text
publication verify --project-slug <slug> --publication-id <id>
```

Команда:

1. Проверяет принадлежность записи проекту и точность ссылок на страницу/вложение.
2. Загружает доступную конкретную версию вложения и проверяет её хэш по сохранённому ожидаемому артефакту.
3. Читает соответствующее доступное состояние страницы и проверяет макрос, вложение и управляемые блоки.
4. Для проверки текущей публикации дополнительно проверяет актуальные версии страницы и вложения.
5. Сохраняет новое наблюдение и результат без перезаписи старого события.
6. Не выполняет POST/PUT, не создаёт новую версию вложения и не меняет страницу.

Если нет ожидаемых байтов, точной связи со snapshot, исторического storage или иных необходимых свидетельств, результат — `not_verified` с причинами, exit code `5`. Совпадение имени вложения или только текущего хэша не восстанавливает отсутствующее историческое доказательство.

Подтверждение текущего состояния не доказывает, что такое же состояние существовало в прежнюю дату публикации. Сохранять область проверки: `current_state` либо `historical_version`.

Расписание проверяется и маркируется отдельно по §20.3.6.

### 20.7. Критерии приёмки

#### 20.7.1. Одиночный конвейер

Обязательный режим Д3 — «план + колонки факта», §20.3.6: A–D успешно публикуются по плановым датам, колонки факта видны в обычном просмотре и после повторного открытия, маркировка «по плану; факт — в колонках» присутствует. Повтор даёт unchanged без роста версий; полная замена сохраняет макрос. Даты каждой задачи/вехи наблюдаются живьём с прежним допуском; нормативные числа A–D и полный gate не смягчаются.

| ID | Проверка | Критерий |
|---|---|---|
| AC-01 | Холодный `save` | Один разбор MPP; snapshot и исходник читаются обратно; Confluence-клиент не создаётся, запросов нет |
| AC-02 | Холодный `publish` | Один разбор для всех стадий; сохраняются внутридневные интервалы календарей, интервалы исключений, наследование и привязки проекта/задач/ресурсов; «Итого» использует те же данные |
| AC-03 | Повтор | Кэш используется; неизменная цель даёт `unchanged`; версия вложения не растёт |
| AC-04 | Новая привязка и новый исходник | `publish --project-slug` создаёт binding без отдельного `save`; `diff` и `publish` архивируют новый исходный snapshot до решения; `needs_decision → identity confirm → resume --mapping-revision` использует тот же snapshot и поступление без повторного разбора |
| AC-05 | Конфликт slug | Нет сетевых записей; явный `binding_conflict` |
| AC-06 | Типы и лаги | FS/SS/FF/SF, положительный и отрицательный лаг сохраняются; неизвестное не превращается в FS/0 |
| AC-07 | Ошибки графа | Цикл, самоссылка, висячая и неразрешённая внешняя связь дают диагностику; архивный save успешен с замечаниями при пригодном snapshot; до допустимого решения POST/PUT отсутствуют |
| AC-08 | Проверка дат и полноты | Совпадение корня при сдвинутой задаче/вехе не считается успехом; для всех запрещающих строк §20.3.6 подтверждено отсутствие сетевых записей; неизвестная таймзона блокирует publish, но не архивный save |
| AC-09 | Правила B/C | Перенумерация строк не ломает подтверждённое правило; иной контекст или неподтверждённая идентичность запрещают автоматическое применение; выбранная revision фиксируется до применения, не подменяется при повторе и проверяется на точную пару |
| AC-10 | Хэш вложения | При mismatch или `verify_uploaded=False` PUT страницы не вызывается; успех не регистрируется |

На момент этой доработки функциональные прогоны остаются `not_run`; статус готовности исходника и результат теста — разные поля. Это подтверждение A не является mapping revision и не разрешает автоматически применять B/C к другим MPP.

#### 20.7.5. Методика подсчёта и «Итого»

#### Задачи

Ввести три показателя:

- `task_count` / `archive_task_count` — все корректно извлечённые непустые записи задач, включая ID=0, корень, summary и milestones;
- `service_task_count` — записи с исходным ID=0;
- `display_task_count` — архивные задачи за вычетом ID=0.

Summary и milestones не исключаются из отображаемого количества. Пустые записи MPXJ не считаются задачами. Ошибки извлечения учитываются отдельно и не превращаются в корректные пустые задачи.

Архив сохраняет служебную ID=0. Представление Confluence её не публикует.

Контрольные значения из доступных архивных экспортов:

| Кейс | Архивные задачи | Служебные ID=0 | Отображаемые задачи | Зависимости |
|---|---:|---:|---:|---:|
| A — 150526 | 58 | 1 | 57 | 53 |
| B | 62 | 1 | 61 | 60 |
| C | 62 | 1 | 61 | 61 |
| D | 72 | 1 | 71 | 76 |
| E | 78 | 1 | 77 | 84 |
| F | 86 | 1 | 85 | 93 |

Таким образом, исторические 58 для A и 78/86 для E/F относятся к архивному набору, а 61/61/71 для B–D — к набору без служебной строки. В новых отчётах всегда указывать оба количества.

Зависимости считать по исходным записям полного экспорта до применения исключений. Не удалять дубликаты или проблемные связи ради количества. Внешние зависимости учитывать отдельным показателем.

#### Трудозатраты

- Суммировать `work` назначений обычных задач и milestones.
- Исключить назначения служебной ID=0 и summary-задач, чтобы не суммировать агрегаты повторно.
- Каждое фактическое назначение учитывать один раз.
- Не складывать одновременно `work` и его timephased-разбиение.
- Переводить единицы по явным параметрам источника; не предполагать восемь часов в дне.
- Отсутствующее `work` не заменять нулём.
- При неполных назначениях возвращать известную сумму с качеством `partial`, а не подтверждённые общие трудозатраты.
- Для арифметики использовать точное десятичное представление; внутренние значения не округлять по задачам.
- В отчёте отображать до трёх знаков после запятой, `ROUND_HALF_UP`; целые значения — без дробной части.
- Для контрольных A–D сравнивать сумму до отображающего округления с допуском не более `0.001` часа.

Ожидаемые A–D: `1576`, `2096`, `2088`, `3136` ч-ч.

#### Корень и «Итого»

- Использовать единственную верхнеуровневую содержательную summary-задачу с ID≠0.
- Если корней несколько, требовать явный выбор; не выбирать последнюю запись.
- Начало и окончание брать из подготовленного корня. При отсутствии преобразования они равны исходным значениям MPP.
- Изменение этих дат допустимо только как часть конкретного согласованного преобразования.
- Рабочую длительность брать из длительности того же корня, переведённой в рабочие дни по параметрам источника.
- Не заменять её количеством календарных дат между началом и окончанием.
- Для `N` использовать округление вверх до целого: `ceil(duration_working_days)`.
- Нулевая длительность даёт `N=0`.
- Например, `84.875 → 85`, `76.875 → 77`, `106.875 → 107`.
- Исходную дробную длительность и коэффициенты перевода сохранять.
- При неизвестных единицах, elapsed-длительности без определённого преобразования или недоступном основании пересчёта не подставлять произвольное `N`; применять запрет публикации по §20.3.6.
- Даты для строки форматировать в разрешённой таймзоне профиля.
- Трудозатраты не включать в storage.

Зафиксировать методику как версию профиля, например `summary-v1`; её изменение создаёт новую ревизию представления.

#### 20.7.7. Минимальный порядок запуска приёмки

Реализация должна предоставить тесты с группами `unit`, `archive_integration`, `mpp_fixtures`, `confluence_live` и воспроизводимую инструкцию запуска.

Минимальная последовательность:

1. Создать отдельный каталог приёмки.
2. Создать новую тестовую SQLite БД и отдельные WorkVault/cache.
3. Проверить миграции на новой БД и на изолированной копии старой схемы.
4. Запустить unit-тесты без сетевого доступа.
5. Запустить архивную интеграцию с явными `--db`, `--workvault`, `--cache-dir`; создание Confluence-клиента в этих тестах должно приводить к падению теста.
6. Проверить хэши fixtures, выполнить холодные и повторные прогоны MPP.
7. Выполнить batch, дедупликацию, историю, typed compare и инъекции сбоев.
8. Проверить baseline до и после.
9. Отдельно выполнить `confluence_live` на выделенных тестовых страницах установленного плагина.
10. Сформировать отчёт AC с результатами, счётчиками чтений/записей, версиями окружения и ссылками на свидетельства.

Пример формы вызова CLI в изоляции:

```text
<python-with-mpxj> <skill-root>/scripts/cli.py
  --db <test-root>/state/index.sqlite
  --workvault <test-root>/WorkVault
  --cache-dir <test-root>/cache
  batch save --manifest <test-root>/fixtures/batch.json
```

Тестовый harness обязан отклонять запуск с production-путями БД/WorkVault. Рабочая БД в приёмке не изменяется.

Для проверки установленного плагина зафиксировать:

- версию Confluence и плагина;
- ID выделенных тестовых страниц;
- профиль кодов типов и единиц лага;
- исходные и полученные байты вложения;
- storage после GET;
- наблюдаемые даты задач/вех в самом плагине;
- результаты календарных контрольных примеров.

Локальный scheduler, mock HTTP и совпадение JSON не подтверждают поведение установленного плагина.

Если нет доступа к живому плагину, соответствующие проверки остаются `not_run`; полная приёмка не объявляется завершённой.

### 20.8. Порядок реализации

### Этап 1. Закрыть ложное подтверждение публикации

- Остановить выполнение при отрицательной проверке вложения.
- Добавить настоящий read-back storage.
- Перенести подтверждение операции и регистрацию публикации после проверок.
- Проверить аналогичные ветки дочерних страниц.
- Добавить тесты отрицательных результатов и частичных сбоев.
- Ввести минимальное различение старой регистрации и нового подтверждения, чтобы история не продолжала выдавать недостоверный успех.

**Результат:** ошибочная либо непроверенная публикация больше не выдаётся за успешную.

### Этап 2. Стабилизировать общее архивное ядро

- Зафиксировать контракт полного экспорта и качества полей.
- Реализовать общий подготовленный результат и кэш разбора.
- Сохранять исходную семантику зависимостей, календарей и назначений либо явно отмечать недоступность.
- Выполнить миграции поступлений, профиля snapshot и области дедупликации.
- Ввести стабильную локальную lineage.
- Реализовать фиксацию исходных байтов, архивный read-back и обязательную дедупликацию.
- Обеспечить транзакционную связь item со snapshot и восстановление после commit.
- Определить успешный `save` с замечаниями независимо от готовности scheduler.
- Унифицировать архивные квитанции.

**Результат:** общий воспроизводимый `save`, пригодный для одиночного и пакетного сценариев.

Полноценная диагностика расписания и правила B/C не являются зависимостью этого этапа.

### Этап 3. Реализовать batch и базовую историю

- Реализовать повторяемый `--mpp`, manifest и Inbox.
- Фиксировать все входы до первого разбора.
- Реализовать `batch-id`, проверку повторного manifest и приоритет `on_error`.
- Реализовать последовательную обработку и правила продолжения состояний.
- Реализовать регистрацию решения batch-item через `resume --accept-proposal` без исполнения элемента и потребление решения только через `batch resume --retry-decisions`; проверить неизменность manifest и запрет смены контекста.
- Добавить итоговую квитанцию и однозначные exit codes.
- Добавить историю поступлений за период и просмотр ошибок пакета.
- Проверить E/F, обязательную дедупликацию, сохранность baseline и сбой после commit.

**Результат:** готовый пакетный архив и базовая история задачи №2.

Этот этап следует непосредственно за стабилизацией общего `save`. Он не ждёт завершения расширенной диагностики публикации или полного механизма сетевого восстановления.

### Этап 4. Завершить ветку публикации

- Перевести календарь, «Итого» и публикацию на подготовленные данные.
- Добавить `publish`, передачу slug и создание binding в архивной стадии.
- Обеспечить первичный архивный snapshot и read-back для `publish` и `diff` до применения B/C и решения о допуске; реализовать цепочку `needs_decision → identity confirm → resume --mapping-revision` без предварительного save.
- Исправить перенос типов и лагов в представление плагина.
- Сформировать проверяемый профиль возможностей установленного плагина.
- Реализовать матрицу допуска §20.3.6.
- Заменить критерий «путь равен корню» проверкой дат и ограничений.
- Реализовать версионируемые правила B/C.
- Реализовать устойчивый контекст сетевой операции, `resume`, проверки конкурирующих изменений и блокировки.
- Устранить повторный upload после таймаутов.
- Реализовать `unchanged` и восстановление после POST/PUT.
- Добавить read-only перепроверку старых публикаций.

**Результат:** завершённая ветка публикации с явными ограничениями проверки расписания.

### Этап 5. Завершить доказательное сравнение и историю

- Реализовать подтверждение происхождения и mapping revision.
- Доработать typed query API, включая `_diff_snapshots()` и связанные запросы истории задач.
- Проверять принадлежность обоих селекторов проекту.
- Сравнивать типы/лаги, календари и назначения.
- Реализовать качество сопоставления, частичный mapping и точные селекторы.
- Завершить отображение уровней доверия старых и новых публикаций.

Механизм идентичности, необходимый правилам B/C этапа 4, реализуется до активации этих правил. Он не является зависимостью архивного batch.

### Этап 6. Завершить интеграцию скилла и полную приёмку

- Зарегистрировать канон в действующей библиотеке.
- Сократить обёртку до совместимого указателя.
- Перенести кейсы и сложную диагностику в references.
- Удалить инструкции об обязательном ручном `save`, копировании во `/tmp` и автоматической подгонке зависимостей.
- Документировать все CLI-контракты и схемы.
- Зафиксировать реестр fixtures с подтверждённым A `150526`, его именованным источником и SHA-256 из §20.7.4; отдельное согласование происхождения A не требуется.
- Прогнать общую и отдельную живую приёмку плагина.
- Представить измерения и итог по каждому AC.

Для каждого этапа исполнитель предоставляет список изменений, результаты проверок и известные ограничения.

Все миграции воспроизводимы. До изменения рабочей БД требуется проверенная резервная копия. Успешный выпуск пакетного архива не означает полной готовности всего ТЗ.

### 20.9. Риски

| Риск | Предусмотренное решение |
|---|---|
| Плагин иначе интерпретирует связи и календарь | Версионный профиль возможностей и живые контрольные примеры; неизвестность не считается поддержкой |
| Полный экспорт не содержит нужного поля | Расширение exporter либо явное качество `missing`/`unsupported` и действие по матрице допуска |
| Успех сохранения принимается за корректность расписания | Раздельные проверки архива, вложения, страницы и расписания |
| UID повторяются в независимых планах | Явное подтверждение происхождения или mapping revision; общая lineage недостаточна |
| Diff скрывает изменение типа/лага, календаря или назначения | Доработка typed query и отдельные приёмочные случаи |
| Историческое исключение стало ненужным | Повторная проверка применимости; результат `not_needed` |
| POST уже изменил видимый план, а PUT не завершён | Журнал частичных эффектов и продолжение после проверки актуальности цели |
| Страница изменена другим пользователем | Проверка значимых параметров, optimistic locking, конфликт вместо безусловного продолжения |
| Вход batch меняется во время обработки другого файла | Все байты фиксируются до первого разбора |
| Исходник исчез между остановкой и продолжением | Возобновление из долговечной зафиксированной копии |
| Сбой после SQL commit создаёт лишний snapshot | Транзакционная связь item/snapshot, ключ дедупликации и reconciliation |
| Дубли искусственно раздувают историю версий | Отдельные сущности поступления и snapshot; обязательная дедупликация в заданной области |
| Старые lineage зависят от имени файла | Сохранение старой истории и новая стабильная схема без автоматического слияния |
| Старая запись confirmed была ложной | `legacy_unverified`, сохранение исходного статуса и read-only перепроверка |
| Дата из имени принята за реальную хронологию | Раздельное хранение времени получения и явно установленной даты версии |
| Разные методики дают противоречивое количество задач | Отдельные архивное, служебное и отображаемое количества |

### 21.1. Проблема и границы доказательства

`ConfluenceClient.get_attachment(attachment_id, version=N)` формирует `status=any&version=N`. На установленном `dom.tutu.ru` такой GET возвращает HTTP 400 до скачивания байтов; после уже выполненного POST операция остаётся неподтверждённой. [GET-only evidence](../../dev/edit-plan-confluence-apply-padaet-na-post-verifi/evidence/read_only_rest_probe_explicit_id.json) от 16.11.2026 подтверждает: на тестовых page `519501810` / attachment `519501809` запрос без `status` возвращает правильные metadata текущей v5 и исторической v4; запрос с `status=any` для обеих версий даёт 400. Это наблюдение установленного сервера, не утверждение о любой версии Confluence. Запрет всех сочетаний `status` и `version` из brief чрезмерно широк: в том же probe `status=historical` работал. Выбран один доказанный вариант без `status`, без автоперебора вариантов.

Инцидент с производственной v7 известен из brief. Он не подтверждён этим тестовым probe; отсутствуют исходный attempt ID и полный набор ожидаемых байтов/наблюдений. Фикс клиента не меняет задним числом результат старой попытки и не разрешает повторную публикацию v7.

На диске публичный `apply_plan` уже делегирует `publish_plan`; новый `_verify_stage09_attachment` использует current metadata и скачивание точной версии. Дефект сохраняется в общем клиенте, используемом `_verify_written_attachment` / legacy- и дочерней ветками. Успешный новый `publish` сам по себе не доказывает исправление общего клиента. `pipeline.py` и `tests/conftest.py` меняются параллельно; baseline диагноза `53 passed, 1 deselected` относится к его снимку, не к последующему коду.

### 21.2. Обязательный контракт исправления

1. Для `get_attachment(attachment_id, version=N)` допустим только `type(N) is int` и `N >= 1`. До сети отклоняются `0`, отрицательные числа, `bool`, строки и float прежним `ValueError`. Query содержит `expand=version,container` и `version=str(N)`; ключ `status` отсутствует. Метод GET, путь `/rest/api/content/{attachment_id}` и `Cache-Control: no-cache` сохраняются. Ошибочный комментарий про `any` исправляется вместе с query.
2. Для `version=None` сохранить существующий GET metadata: `expand=version,container`, без `version` и `status`. Сигнатуры и контракт возвращаемых данных не меняются.
3. `download_attachment_version` сначала проверяет точные attachment ID, filename/title, container page ID и `version.number`. При несовпадении байты не скачиваются. Скачивание остаётся GET `/download/attachments/{page_id}/{encoded_filename}?api=v2&version=N` с no-cache. Нельзя заменить `N` на latest или убрать версию из download URL.
4. SHA-256 фактически полученных байтов сравнивается с ожидаемым. Отрицательный `verify_uploaded` и ложный `True` при неверных байтах блокируют продолжение. Ошибка первичной проверки после POST не допускает PUT страницы или регистрации успеха. Ошибка последующей проверки после PUT не допускает подтверждения публикации. Частичный внешний эффект сохраняется в существующих receipts; названия полей, enum, схема и уровень trust этим пакетом не меняются.
5. Успешное чтение исторической N не подтверждает актуальную публикацию, когда current уже N+1. После PUT сохраняются свежий GET storage, проверки макроса/«Итого»/чужого текста и отдельная проверка текущих ID/version/байтов вложения (§19.4, §20.3.9–20.3.11). Чужое изменение остаётся конфликтом. Параметр макроса `hash` не подменяет SHA-256 байтов.
6. HTTP 400/401/403/404/5xx и сетевые таймауты не превращаются в успех. Сохраняется существующее распространение ошибок; клиент не добавляет fallback на latest, перебор `status`/endpoint, retry GET или повторный POST. Исправление запроса не является реализацией нового механизма восстановления.
