# Паттерн: hermes-feature

## Overview

Единый процесс работы над фичами Hermes и USERTOOLS: от ТЗ и выбора варианта до кода, тестов, документации, диагностики и отката. Скилл фиксирует, кто пишет (Sonnet vs Opus), когда делать бэкап, как эскалировать, и что запрещено делать самостоятельно (правки security-конфига, рестарты gateway). Дополнительно: паттерн отладки (hermes-debug) и исследований (hermes-research), плюс handover контекста между инстансами.

## When to Use

Триггеры:
- «разработай», «новый инструмент», «напиши ТЗ», «MoveFrom*», «ТЗ v» — Блоки 0–4
- «ошибка», «баг», «не работает», «упало», «падает», «разберись», «починить», «сломалось» — Блок 7 (hermes-debug)
- «проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если» — Блок 8 (hermes-research)
- Задача с 3+ изменениями конфига/скиллов/инструментов — Блок 6А (QA)
- Запуск нового инстанса Сирени (новая VM, новый бот) — Блок 9 (handover)

Не для: правок стиля общения (см. `hermes-memory-hygiene`), простой рутины без ТЗ и вариантов.

## Блок 0: ТЗ (кратко)

- ТЗ пишет **Opus**, инициирует только Саша явным запросом.
- **Хранение:** один живой master-файл на инструмент → `WorkVault/Hermes-Backlog/TZ/<Tool>/<Tool>_TZ.md`. Точечная доработка → секция в master-файле, не новый файл. Независимая от инструмента → `TZ/_misc/TZ-<topic>-<YYYYMMDD>.md`.
- **Обязательные разделы:** Цель / Контекст / Шаги / Критерии успеха / Что НЕ трогать.
- **Предварительный сбор зависимостей — Sonnet/Haiku, ПЕРЕД Opus, не вместо него (решение Саши 09.07.2026).** Перед тем как Opus начнёт писать ТЗ, дешёвая модель (Sonnet или Haiku, смотря по объёму) прогоняет `search_files`/`grep` по всем скиллам и существующим ТЗ — собирает сырой список фактов: какие скиллы упоминают этот инструмент, какие ТЗ ссылаются друг на друга, где потенциальные пересечения. Это чисто механический сбор данных, не суждение — экономит дорогое Opus-время без потери качества. **Opus получает этот сырой материал как входные данные и пишет ТЗ целиком сам** — включая разделы «Контекст», «Что НЕ трогать», «Критерии успеха». Не разбивать это на «Opus анализирует зависимости → Sonnet пишет текст по выводам Opus» — само написание ТЗ это непрерывный процесс суждений (что из найденного важно, как формулировать), не механическая обработка чужого списка; передача через промежуточный документ теряет неявные нюансы, которые Opus держал бы в голове, если бы писал сам от начала до конца.
- **Согласование ТЗ ≠ команда на реализацию** — миграция/кодинг стартуют только по отдельной явной команде Саши («ок, берём в работу»).
- Неопределённость → Opus стопится, дополняет ТЗ предложением, ждёт ОК.
- Отчёт о ТЗ в чат — короткий (что поменялось + что требуется от Саши). Полный текст ТЗ не дублировать — Саша откроет файл сам.
- Открытые вопросы Opus выносит отдельным разделом «Открытые вопросы Саше» с рекомендацией + альтернативой, не выбирает «по умолчанию».
- Universal open-question protocol: во всех диалогах — сначала полный список вопросов, потом по одному, с рекомендацией и вариантами по номерам.

Полный набор правил (брифование, хранение материалов брифа, QA ТЗ, отклонения API от ТЗ, жизненный цикл файла) → `references/tz-workflow.md`. Родственный скилл: `tz-workflow`.

## Блок 1: Анализ вариантов

- **Критерии:** токены / безопасность / консистентность / поддерживаемость + специфичные для задачи.
- **Количество:** 2-3 лучших; слабые Opus отсеивает сам.
- **Подача:** сначала рекомендация с обоснованием → остальные кратко для справки.
- После выбора: уточняющие вопросы **по одному** → ждать «берём в работу». Саша может прервать уточнения и перейти сразу к работе.

**Completion criterion:** Саша сказал «берём в работу» по конкретному варианту.

## Блок 1А: Планирование *(приоритет — выполнять до Блока 2)*

**Перед любой реализацией Opus составляет пофайловый план:**
- Какие файлы создать / изменить
- Какие функции / классы / методы добавить
- Какие тесты написать (по одному на кейс)
- Промежуточные точки проверки с критерием завершения каждого этапа (по ТЗ если есть, по контексту если нет)

**ТЗ-файл только для задач с Python-кодом.** Для скиллов, конфигов, memory-правок — план Opus в чате (или временный файл), ТЗ-файл не нужен.

**Исключение (решение Саши 08.07.2026):** инфраструктурные планы настройки/интеграции существующего стороннего инструмента (не новый код, а установка/конфигурация — например RAG-инструмент, systemd-демон, MCP-интеграция) хранить **по аналогии с обычными ТЗ**, тем же способом что в `tz-workflow`: `TZ/<Topic>/<Topic>_TZ.md`, статус `draft`, запись в `MAIN_TZ_INVENTORY.md`. Прецедент: `TZ/QMD-Search/QMD-Search_TZ.md`. Это относится и к Блоку 7А (двухэтапный Opus-анализ) — план анализа тоже сохраняется файлом, не только в чат/отчёт крона.

**Sonnet проходит промежуточные точки молча** — сверяется с планом сама, без отчётов Саше после каждого этапа.

**Перед «берём в работу» — верификация плана против реальной среды (техника, найдена 08.07.2026).** Opus-план может содержать правдоподобные, но неверные предположения о среде (путь к бинарнику, формат конфиг-файла, значение переменной) — план пишется по логике/докам, не всегда по факту. Перед тем как согласовывать план для инфраструктурной задачи (systemd unit, cron-патч, конфиг стороннего инструмента), проверить ключевые фактические утверждения напрямую (`terminal`/`read_file`): пути к бинарникам (`which`), реальную схему JSON/YAML файлов, которые план собирается патчить, версии установленного ПО. Прецедент: план установки qmd предполагал путь к node в `~/.hermes/profiles/anthropic/node/bin/`, а реальный активный npm prefix оказался `~/.local/bin/` — на VM оказалось два независимых Node.js. Расхождение нашлось только при явной проверке `which node`/`npm config get prefix` перед стартом реализации — не будь эта проверка сделана, systemd unit ссылался бы на несуществующий путь. Это отдельный шаг, отличный от Блока 3 (Sonnet тестирует уже написанный код) — тут проверяется сам план, до того как код/конфиг начали писать.

**Устойчивость к сбою (питание/зависание) во время многошаговой реализации по плану (техника, 08.07.2026).** Для инфраструктурных планов из нескольких последовательных шагов (установка → конфигурация → systemd → интеграция) — прогресс ведётся **прямо в файле плана**, не в todo сессии и не только в чате: отдельный раздел `## Прогресс выполнения` со списком шагов-чекбоксов (`- [ ] §5.N <шаг>`), который исполнитель отмечает `[x]` с меткой времени **сразу после каждого шага**, а не пачкой в конце. Почему так: todo инструмента и чат — эфемерны (пропадают между сессиями/сбоями), файл плана — персистентен и синкается (owncloud-sync каждые 10 мин). Если процесс прервётся на середине — следующий запуск читает файл, видит последний `[x]`, продолжает с первого `[ ]`, не переделывая сделанное. Дополнительное условие безопасности: каждый шаг плана должен быть идемпотентным (повторный `ln -sf`/`mkdir -p`/`qmd collection add` на уже готовое состояние не ломает), иначе резюмирование после сбоя не сработает корректно.

**Completion criterion:** Саша сказал «берём в работу» по пофайловому плану.

## Блок 2: Реализация *(изменён 06.07.2026 — Sonnet пишет код)*

### Кто пишет
- **Sonnet** — пишет весь код по пофайловому плану Opus *(приоритет над всеми прежними правилами)*
- **Opus (fallback)** — только если Sonnet не справилась: архитектурная тупиковая ситуация или повторяющиеся необъяснимые ошибки. Sonnet даёт краткий вывод о причинах → **Саша решает** запускать ли Opus.

**Мелкое отклонение от плана** (≤2 файла, не меняет архитектуру) → Sonnet решает сама.
**Крупное отклонение (архитектурное)** → Sonnet стопится, коротко сообщает причину → Opus делает доплан → Sonnet продолжает.

**Системный/инфраструктурный блокер (недостающие OS-пакеты, sudo-права, библиотеки компиляции) — отдельная категория, найдено 08.07.2026, НЕ путать с архитектурным тупиком выше:** Sonnet стопится → **Сирень (не Opus) выносит вопрос напрямую Саше** с рекомендацией и обоснованием → после «да, разрешаю» Сирень сама выполняет системную правку (например `sudo dnf install`) → создаёт **новый** cronjob для Sonnet с явным описанием, что изменилось в среде, чтобы та продолжила с точки останова (используя `## Прогресс выполнения` в файле плана — см. Блок 1А). Opus здесь не нужен: вопрос не архитектурный, а «дать разрешение на системное изменение», это решает Саша напрямую. Прецедент: установка `qmd` упала на компиляции `node-llama-cpp` (отсутствовали `cmake`/`gcc-c++`) — Саша разрешил `sudo dnf install -y cmake gcc-c++`, Сирень поставила пакеты и запустила продолжающий cronjob.

**Явный override Сашей:** один раз подсветить конфликт с правилом, при явном подтверждении — выполнять без дальнейшего сопротивления. Пример 06.07.2026: bk-098 ExchangeOrgLookup — Саша настоял на Sonnet после одного предупреждения.

### Чеклист перед первой строкой кода
1. ТЗ согласовано (или план в чате) + явное «берём в работу».
2. **Бэкап создан** (см. Блок 5).
3. Пофайловый план Opus существует и согласован.

### Фиксация решения
Opus обновляет ТЗ-файл (если есть): добавляет выбранный вариант + дату старта.

## Блок 3: Тестирование *(изменён 06.07.2026 — Sonnet тестирует)*

- **Тестирует Sonnet** по плану тестирования от Opus *(приоритет над прежними правилами)*
- **Мелкий баг** (≤2 файла, очевидная причина) → Sonnet чинит сама (1 попытка)
- **Крупный/архитектурный баг** → Sonnet фиксирует причину → **Саша решает** запускать ли Opus на hotfix-план → Sonnet применяет
- **Готово =** все точки проверки из плана Opus пройдены (✅/❌)
- Финальное «всё ок» говорит Саша.

**Правило про самостоятельное завершение застрявших/интерактивных шагов и объявление «готово» (инцидент 09.07.2026, QMD-Search):** если Sonnet застряла на интерактивном шаге (например CLI-команда ждёт ответа на вопрос типа auth/подтверждение) — **Сирень НЕ доводит шаг сама молча**. Правильная последовательность: (1) сообщить Саше «застряло здесь, вот что конкретно нужно ответить/сделать, продолжать?», (2) выполнять только после явного «да/продолжай». Аналогично для любого следующего шага плана, который не был явно частью уже согласованного плана (например правка ещё одного крона, которая не была в исходном пофайловом плане) — сначала показать, что именно меняется, дождаться ОК, потом применять. Уклончивый или неполный ответ Саши («расскажи подробнее», вопрос вместо подтверждения) — это НЕ согласие, продолжать нельзя, пока не будет явного да/ок/делай.
**Статус «completed»/«готово» на весь план — ставит только Саша.** Даже если все шаги пройдены и верификация успешна, финальный отчёт заканчивается вопросом «готово подтвердить?», не утверждением. Прецедент: 09.07.2026 Сирень сама прошла интерактивный `hermes mcp add`, сама приняла решение `rerank: false` по неоднозначному ответу Саши, сама пометила план `status: completed` — Саша справедливо указал, что настройка выполнена без его одобрения на нескольких точках подряд.

## Блок 4: Документирование

- ТЗ-файл остаётся живым в `TZ/<Tool>/<Tool>_TZ.md` **пока инструмент используется**. Архивация — только когда сам инструмент выведен из эксплуатации, по явному решению Саши.
- **Скилл:** мелкая правка → Opus сам; новый раздел → предлагает Саше.
- **MEMORY:** Opus предлагает с объяснением, почему MEMORY а не скилл → Саша говорит ОК.
- **Разовая правка vs изменение шаблона/скилла:** при правках контента Саша явно разделяет два случая — разовая правка конкретного экземпляра (файла/отчёта) или изменение общего шаблона/скилла. По умолчанию любая правка — разовая, в общее правило её не переносить; сам скилл менять только по явному «доработай скилл» от Саши.

## Блок 5: Бэкапы и откат

### Когда создаётся
- Opus-задачи: всегда.
- Sonnet-задачи: только если затронут `config.yaml` или `jobs.json`.

### Состав
`config.yaml` + `jobs.json` + `skills/` + `MEMORY.md` + `USER.md` + файлы специфичные для задачи.

### Путь
Linux VM: `~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`.
Для бэкапов отдельных компонентов (unit-файлы, `rclone.conf` и т.п.) — рядом с файлом: `<file>.bak-<purpose>-YYYYMMDD-HHMMSS`.

### Хранение
2 недели, 1 бэкап в день (самый ранний). Self-check чистит автоматически.

### Откат
- **Авария** → Opus откатывает сам немедленно, сообщает Саше.
- **Плановый** → Opus предлагает какой бэкап, ждёт ОК.

## Блок 5А: Минимальное вмешательство в инфраструктуру

**Никогда не делать самостоятельно** (только по явной команде Саши):
- Менять `guest_mode`, `require_mention`, `allowed_chats` в `config.yaml`.
- Перезапускать gateway (даже после правки конфига).
- Ставить cron-рестарты «на потом».
- Применять рекомендации аудита/Opus без явного «делаем» от Саши, даже если рекомендация очевидна.

**Правило рестарта gateway:**
- Рестарт нужен после правки `config.yaml` или кода gateway.
- Делать ТОЛЬКО из внешнего шелла: `bash ~/.hermes/scripts/restart_gateway_MANUAL_ONLY.sh`. НЕ через no_agent cron (SIGTERM-петля, инцидент 26.06.2026).
- Не ставить рестарт-крон без явной просьбы — сообщить «нужен рестарт, поставить?».
- После рестарта предупредить: «через ~1 мин gateway перезапустится».

**Почему:** каждый рестарт прерывает активный диалог; несколько рестартов подряд = Саша не получает ответы и теряет доверие.

Примеры нарушений: `require_mention: true` применён по рекомендации → бот замолчал в группе; cron-рестарты gateway ставились сами → прерывали диалог. Детали и особо опасные параметры → `references/config-qa.md`.

## Блок 5Б: Классификация разрешающего сигнала перед side-effect-действием (обязательно)

**Триггер:** любой вызов `write_file`/`patch` на файлы вне `~/.hermes/_Archives/`, любой `cronjob(action='create'|'run')` с реальными side-effects, любой `terminal` с `curl -X POST|PUT|DELETE` к внешним API (Confluence/JIRA/Anywhere/EWS), любой `patch` на файлы в `WorkVault/Hermes-Backlog/TZ/**`.

**Обязательный шаг перед tool call:** в reasoning явно указать одну из категорий разрешающего сигнала:

| Категория | Определение | Разрешает действовать? |
|---|---|---|
| `direct-imperative` | В последнем сообщении Саши есть глагол-императив, ссылающийся именно на это действие: «обнови», «запусти», «делай», «фиксируй», «давай», «поставь», «удали» | ✅ Да |
| `continuation-of-approved-plan` | Действие — явный пункт из согласованного пофайлового плана Opus (Блок 1А), Саша сказал «берём в работу» по этому плану, действие соответствует одному из перечисленных шагов плана дословно | ✅ Да |
| `question-answer` | Саша задал информационный вопрос (где/как/почему/можно ли/что если), модель ответила — само действие «зафиксировать ответ в файле» Сашей не запрошено | ❌ Нет |
| `own-inference` | Модель логически вывела, что «раз X, значит нужно Y» — без явной команды от Саши | ❌ Нет |
| `conditional` | Саша дал условную команду «если X — делай Y», истинность X оценивает сама модель | ❌ Нет |

**Если категория ❌ — обязательно отдельный turn БЕЗ side-effect-инструментов:** текстовое сообщение Саше вида «Собираюсь [точное действие: файл, что меняю, зачем]. Разрешающий сигнал: [категория]. Продолжаю?» — и ждать явного «да»/«делай»/«ок». Уклончивый ответ, встречный вопрос, «расскажи подробнее» — НЕ согласие.

**Самореференциальный запрет:** факт, созданный самой моделью в этой же сессии предыдущим tool call-ом, **НЕ является** доказательством истинности условия для последующего действия. Пример нарушения: модель занесла паттерн в ТЗ (действие 1) → на условную команду «если ТЗ доработано — запускай» решила, что условие выполнено, ссылаясь на своё же действие 1 → запустила реализацию. Правильно: `conditional` → ❌ → отдельный вопрос «занёс §11.4 в ТЗ, считаю условие выполненным — запускаю реализацию? подтверди».

**Прецеденты, которые это правило закрывает:**

## Блок 6Б: Делегирование субагентов

### Инструмент запуска

**Правило против хардкода (решение Саши 08.07.2026 — переживает переключение Anthropic↔TUTU):**
- **Sonnet-задачи — НЕ передавать `model` вообще.** Sonnet это всегда текущий основной провайдер/модель Hermes (`model.default`/`delegation.model` в `config.yaml`) — эти два поля синхронно обновляются скриптами переключения (`switch_to_sonnet5.sh`, `user_change_delegation_models1.sh`). Если не указывать `model` в `cronjob`/`delegate_task`, система сама берёт актуальное значение — не нужно править скилл при каждом переключении профиля.
- **Opus/Haiku — модель передавать явно** (они намеренно НЕ основная модель), но БЕЗ `provider` (см. Pitfall 21 — провайдер система подставит сама). Конкретные ID (`claude-opus-4-7`, `claude-haiku-4-5`) подтверждены одинаковыми на Anthropic и TUTU (см. `WorkVault/UserManuals/LLM-Migration/README.md`, таблица моделей) — переживают переключение провайдера. Переживут смену **версии** модели (когда выйдет Opus 4.8 и т.п.) — только если кто-то обновит эту таблицу вручную; проверять актуальность раз в несколько недель, не считать вечной истиной.

| Задача | Модель (параметр `model`) | Инструмент | Таймаут |
|---|---|---|---|
| Opus: ТЗ / пофайловый план | `{"model": "claude-opus-4-7"}` (без provider) | `cronjob(repeat=1)` | — |
| Opus: сложная реализация (fallback) | `{"model": "claude-opus-4-7"}` (без provider) | `cronjob(repeat=1)` | — |
| Opus: инфраструктурный анализ | `{"model": "claude-opus-4-7"}` (без provider) | `cronjob(repeat=1)` | — |
| Sonnet: реализация по плану (>5 мин или многофайловая) | **не передавать** `model` — наследует текущий default | `cronjob(repeat=1)` | — |
| Sonnet: короткая задача (<5 мин) | **не передавать** `model` — наследует `delegation.*` | `delegate_task` | 300с |
| Haiku: справочный / терминальный запрос | `{"model": "claude-haiku-4-5"}` (без provider) | `delegate_task` | 120с |

**Никогда не использовать `delegate_task` с Opus** — reasoning_effort=high держит родительский стрим → gateway-зависания ("Stream stale for 180s"). Всегда `cronjob(repeat=1)`.

### Toolsets в кронах (сокращают контекст субагента)

| Задача | enabled_toolsets |
|---|---|
| Opus: ТЗ / план (читает файлы, не запускает код) | `["file", "terminal"]` |
| Sonnet: реализация кода | `["file", "terminal"]` |
| Sonnet: тестирование | `["file", "terminal"]` |
| Исследование / аудит с web | `["file", "terminal", "web"]` |

Не добавлять `web` если не нужен — каждый лишний toolset увеличивает контекст сессии.

### Что обязательно передавать в промпт субагента

1. **Роль и среда** — «Ты Opus/Sonnet на VM hermes-agents.devel.tutu.ru»
2. **Точные абсолютные пути** — `/home/tkachenkoav/...`, не `~/...` (в кронах `~` может не резолвиться предсказуемо)
3. **Полный контент ТЗ или плана** — не ссылку на файл, а текст; субагент не должен делать дополнительные lookup'ы
4. **Граница автономности** — явное правило: «механическое (форматирование, перенос, дозаполнение) — делай сам; семантическое (удаление блока, изменение архитектуры) — СТОП, опиши причину»
5. **Формат отчёта** — «не выводить полный текст файлов, только сводку изменений»
6. **Явные запреты** для безопасности — «не удалять contacts.enc и .env», «не менять security-параметры config.yaml»

### Чего НЕ нужно передавать — и важное уточнение про память (проверено по коду 08.07.2026)

**НЕ дублировать в промпте:** SOUL.md, системный промпт Hermes. Cron-сессии всегда грузят `SOUL.md` (`load_soul_identity=True`) — идентичность агента субагент получает автоматически.

**НО: cron-сессии НЕ получают MEMORY и USER PROFILE вообще.** Проверено по коду (`cron/scheduler.py`, флаг `skip_memory=True` с комментарием «Cron system prompts would corrupt user representations») — это намеренное архитектурное решение Hermes, не баг и не то, что можно включить конфигом. Субагент через `cronjob` не видит ни одной записи из MEMORY/USER PROFILE, даже если они содержат критичный для задачи факт (например «Саша сейчас на Anthropic, не TUTU» или правило про формат имён файлов WorkVault).

**Практическое следствие:** если факт из MEMORY/USER PROFILE нужен субагенту для корректного выполнения — **передавать его явно в промпте**, не полагаться, что «он и так знает». Особенно критично для: текущего активного провайдера/модели, стабильных конвенций именования (например «латиница-only в WorkVault»), организационных фактов (кто есть кто), правил из этого самого скилла (`hermes-feature`), если задача их использует. Секции `## Контекст и уже принятые решения` в промптах установочных планов (см. пример `QMD-Search`) — это правильный паттерн именно по этой причине.

`delegate_task`-субагенты (не cron) — эта проблема не подтверждена по коду отдельно, безопаснее считать то же правило действующим по умолчанию, пока не проверено обратное.

### Бэкап перед запуском субагента

Sonnet-задачи: бэкап если затронуты `config.yaml` / `jobs.json`.
Opus-задачи: бэкап всегда (`~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`).

## Common Pitfalls

Компактный список. Расширенные разборы с полным текстом инцидентов — `references/pitfalls-incidents.md` (номера совпадают). Родственные подтемы — в тематических references (пометки в скобках).

1. **`hermes skills list` не видит новый скилл** — обязательные поля frontmatter: `name`, `description`, `version`, `author`, `tags`, `platforms: [windows, linux, macos]` (не `[all]` — не работает). Если не помогло — вручную добавить запись в `.usage.json` (шаблон копирует поля с другого скилла: `use_count/view_count/patch_count=0`, `state=active`, `pinned=false`), затем рестарт gateway.

2. **Бэкап обязателен до первой строки кода** — Opus создаёт бэкап в `_Archives/hermes-backup-YYYYMMDD-HHMMSS/` перед любыми изменениями Opus-уровня.

3. **Правка security-sensitive `config.yaml`** — allowlist-ключи (`telegram.*`,`delegation.*`,`fallback_providers`) через `hermes config set`; ключи вне allowlist (`personas.*`, `system_prompt`) — только `execute_code` с Python `open/replace/write` (`patch`/`write_file` блокирует). Обязательно: бэкап, `assert old in content`, `yaml.safe_load` после, diff двух связанных файлов если правится один смысловой блок в двух местах. → `references/pitfalls-incidents.md#pitfall-3`

4. **Секция `routing:` в `config.yaml` не работает** — код Hermes её не читает. Молча игнорируется. Для реальной маршрутизации — плагин/хук или правила в MEMORY.md.

5. **Рестарт gateway изнутри заблокирован** — единственный способ: `bash ~/.hermes/scripts/restart_gateway_MANUAL_ONLY.sh` из внешнего шелла. **ЗАПРЕЩЕНО** ставить no_agent cron с этим скриптом изнутри gateway — SIGTERM-петля (инцидент 26.06.2026). (config-qa.md)

6. **`cronjob(action='update')` не сбрасывает `no_agent`** — прямая правка `~/.local/share/hermes/cron/jobs.json`. (cron-and-scheduler.md)

7. **`cronjob(action='run')` разрушает one-shot джоб** — не использовать как «запустить пораньше». Для one-shot: `schedule` относительной строкой (`"4m"`,`"every 2h"`), не абсолютным ISO-таймстампом; неверное время исправлять через `update`/`remove`+`create`. `execution_success: false` в ответе `run` — ложноотрицательный, факт результата читать из `~/.hermes/cron/output/<job_id>/*.md`. → `references/pitfalls-incidents.md#pitfall-7`

8. **`cronjob(action='create')` со `script`** — только имя файла в `~/.hermes/scripts/`, без путей и `&&`, без симлинков. (cron-and-scheduler.md)

9. **`[SILENT]` guard: last-line-equals** — Variant A с 05.07.2026, `_classify_silent_marker` в `cron/scheduler.py`. Три ветки: `deliver`/`silent_clean`/`silent_dirty`. (cron-and-scheduler.md)

10. **«Слепая зона» Sonnet при ожидании крона** — читать `~/.hermes/cron/output/<job_id>/*.md` вручную, не ждать TG-доставку. (cron-and-scheduler.md)

11. **Thread ID топиков не в sessions.db** — источник правды `gateway.log`, поле `reply_to_id`. Топики Sirene Workspace (-1004300127777): General=1, Tools=3, Hermes DEV=4, WorkVault=5, Backlog=6, Monitoring=7, Personal=8. (cron-and-scheduler.md)

12. **rclone `--size-only`** пропускает изменения одного размера (правки `.md`, ре-шифрование `contacts.enc`). Убрать — по умолчанию `size+mtime` надёжнее. (movefrom-and-anywhere.md)

13. **Триггер синка после USERTOOLS** — `subprocess.run(["systemctl","--user","start","--no-block","owncloud-sync.service"], check=False, timeout=5)`. (movefrom-and-anywhere.md)

14. **AnywhereContacts PII** — `mask_contact(c)` обязателен перед любым выводом контакта; `store.read()` возвращает сырые данные намеренно. Общий lock `WorkVault/Contacts/.contacts.enc.lock`. (movefrom-and-anywhere.md)

49. **Cron one-shot с абсолютным ISO `schedule` может сразу вернуться с `next_run_at: null`**, если к моменту фактического создания job'а указанное время уже в прошлом (round-trip между расчётом времени и вызовом `cronjob(create)` съедает минуты; либо просто неверно оценено текущее время). Повторилось дважды подряд в одной сессии (13.07.2026, TaskRefresh: `implementation-plan` и `implementation` jobs) несмотря на то, что фикс уже был известен (Pitfall 7). **Правило:** перед `cronjob(create, schedule=<абсолютный ISO>)` сначала `terminal(date)` чтобы узнать реальное текущее время, планировать с запасом (5+ минут вперёд); сразу после `create` проверить поле `next_run_at` в ответе — если `null`, немедленно `cronjob(update, job_id=..., schedule=<новое время с запасом>)`, не предполагать что задача всё равно выполнится позже. Ещё надёжнее — использовать относительную строку (`"5m"`) вместо абсолютного ISO там, где это возможно (см. Pitfall 7).

51. **Numbered-brief + apply-by-number flow: порядок, использованный для нумерации #N в выводе, ОБЯЗАН быть тем же списком (тем же порядком), что сохранён для последующего lookup «#N → элемент» — вычислять один раз, использовать одинаково в обоих местах.** Отдельный класс бага от Pitfall 48 (там пропущен шаг трансформации; здесь два независимых вычисления одного и того же порядка расходятся). Прецедент 13.07.2026 (TaskRefresh): `format_brief()` группировала и сортировала задачи только для отображения, а `save_session()` сохраняла исходный несортированный порядок сканирования — `#1` в брифе физически мог быть другим task_id, чем `session.tasks[0]`, используемый `apply "#N ..."`/`task_by_number()`. Ошибочная правка была поймана случайно перед применением, не гарантированно. **Фикс-паттерн:** вынести подсчёт порядка в ОДНУ функцию (`order_tasks_for_display()`), вызвать её один раз, передать РЕЗУЛЬТАТ и в персист (session/registry), и в рендер брифа — не пересчитывать дважды из одного и того же сырого списка. Применимо к любому инструменту, который показывает нумерованный список и затем принимает команды `#N <действие>`, ссылающиеся на сохранённое состояние (кроны, CLI-брифы, любой Task-подобный воркфлоу).

52. **Классификация сущности по нескольким сигналам (page_id vs текстовый тег, container vs explicit)** — если у сущности может быть ЯВНЫЙ маркер (текстовый тег в начале строки) И косвенный (page_id/расположение), явный маркер должен проверяться ПЕРВЫМ, косвенный — fallback только при отсутствии явного. Прецедент 13.07.2026 (TaskRefresh): `_annotate_project()` матчил `page_id` раньше текстового тега — задачи с явным тегом «AI-аналитик.», физически лежащие на общей 1-1-встрече-странице (используемой как контейнер для задач разных проектов), получали `project_tag` контейнера вместо своего явного тега. Усугубление: одна и та же страница может быть page_id-зарегистрирована сразу под двумя разными проектами — в этом случае page_id-матч в принципе неоднозначен и его нельзя использовать первым ни при каких условиях. **Правило:** порядок проверки сигналов классификации — от самого специфичного/явного к самому общему/косвенному, а не по порядку, в котором сигналы исторически появились в коде.

53. **Аперодическая maintenance-задача (аудит/скан/чистка), которая должна запускаться по достижении порога состояния (объём MEMORY, число накопленных пунктов), а не по календарю** — не создавать для неё отдельный `cronjob` с собственным `schedule`. Реальный job ставится на паузу (`enabled=false`, `schedule=null`), детект порога добавляется отдельным шагом в уже существующий периодический крон (например `vm_selfcheck`), который при достижении порога добавляет ОДНУ строку-рекомендацию в свой обычный отчёт с готовой командой запуска; если порог не достигнут — ничего не добавляет. Прецедент 13.07.2026: Pitfall Scan (`97d76357f2da`) создан с ежемесячным расписанием, затем по просьбе Саши переведён на триггер «MEMORY.md ≥ 1/3 лимита», сам job поставлен на паузу, детект добавлен в `vm_selfcheck`. → `references/cron-and-scheduler.md`
