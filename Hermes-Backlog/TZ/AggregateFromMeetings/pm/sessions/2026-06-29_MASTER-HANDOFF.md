## БЛОК 1. Архитектурные изменения (критичные)

### 1.1 Opus deprecated полностью (PD-028, PD-036)
- Opus убирается из pipeline **везде** включая bootstrap
- Весь прогон (bootstrap + инкремент) — **Haiku**
- Bootstrap ≠ инкремент: Bootstrap — Haiku; инкремент в проде — **Sonnet** (после выхода в прод, напоминалка 01.09)
- В TZ_C: убрать двухшаговую архитектуру (Шаг 1 Haiku + Шаг 2 Opus); заменить на единый алгоритм по PD-030

### 1.2 Алгоритм bootstrap + инкремент (PD-030, уточнён C4)

```
Bootstrap:
  -1. Встречи FF размечены по проектам/сущностям (classification_memory) — роутинг готов
   0. Идём поштучно по проекту/сущности
   1. Развилка:
      1.1 Проект/инициатива → если есть бриф/устав — формируем начальный набор
                              decisions+action_items+risks из него
                              Если нет → сразу шаг 2
      1.2 Мультисинк / 1-1 / АДМ → сразу шаг 2
   2. От самой ранней встречи к актуальной:
      Haiku делает СРЕЗ (G) из встречи →
      из среза пополняет decisions+action_items+risks,
      сравнивая с накопленным инкрементом:
        - актуальные → оставляем
        - неактуальные → закрываем
        - изменившиеся (срок/ответственный/суть) → дополняем
   3. Если проект/инициатива:
      → golden ref если есть → сравниваем через Sonnet
      → Sonnet ПРЕДЛАГАЕТ закрытые задачи → PM подтверждает через PM Notes (PD-041)
      → если golden ref нет — пропускаем
   4. Если мультисинк/синк-аид:
      → golden ref синка → сравниваем через Sonnet

Инкремент (каждый новый MoveFromFF):
  Тот же шаг 2.
  Заметки РП в срезе G имеют главенствующий приоритет для каждого блока.
  Встречи из MoveFromFF НЕ пересинкиваются и НЕ переобрабатываются — только ручной режим.
```

### 1.3 Поток данных PM Notes (PD-037, PD-044)
- PM Notes живут в срезах G (блоки `<!-- pm: --><!-- /pm -->`)
- PM Notes имеют приоритет при обработке информации из среза
- Информация из среза (с учётом PM Notes) идёт в блоки D (decisions/action_items/risks)
- Связь **G→D осознанная и допускается** — зафиксировать в TZ_G и TZ_D
- Каждый новый срез дополняет блоки новой информацией со встречи + новыми PM Notes

## БЛОК 2. Новые артефакты

### 2.1 risks.md (PD-031, PD-038, PD-039)
- Добавить `Projects/<slug>/ai/risks.md` — **только для проектов/инициатив**
- Не для синков, не для 1-1, не для АДМ
- Инициализируется из устава/брифа проекта; если нет — пустой файл
- Источник истины: накопительный, хронология, зачёркивание закрытых/смягчённых
- Срез G = per-meeting view рисков
- Дедуп по ключу `(text, type=risk, slug)`
- **Отдельного блока Risks в FF-summary нет** — Haiku распознаёт из `Bullet points` + `Notes` по контексту
- Авто-риски помечать `confidence` + `<!-- src: inferred -->`; PM подтверждает/снимает через PM Notes
- Recall проверить на golden ref ml-platforma

### 2.2 action_items.md = Tasks-query (PD-033, PD-035)
- **Задачи физически живут в срезах G** с тегами проекта и ответственного
- `action_items.md` = Tasks plugin query (агрегатор без дублирования)
- Закрытие чекбокса в query правит файл-источник (срез G)
- Иммутабельность срезов переосмыслить: закрытие чекбокса (признак выполнения) — допустимо, это не удаление
- Дедуп задач между срезами — отдельная задача разработки (не MVP)
- Глобальный список по всем проектам/людям = отдельный Tasks query
- Haiku пишет задачи **в срез G**, не в action_items.md напрямую

## БЛОК 3. Изменения схемы сигналов и форматов

### 3.1 Blockers (PD-032)
- Blockers живут в `decisions.md` (не в action_items.md, не в risks.md)
- Формат строки: `- [blocker] текст · статус · срок <!-- key: ... -->`
- Тег `[blocker]` машиночитаем для Haiku
- Дедуп-ключ включает `type=blocker`
- Закрытие = зачёркивание
- Совместимо с TZ_C схемой сигналов (`type` уже включает `blocker`)

### 3.2 Протечки portfolio (PD-040, PD-018)
- Добавить `scope=portfolio` (или флаг `cross_project_ranking`) в схему сигнала
- Детект Haiku: признак «ранжирование нескольких проектов» + route=1on1
- Сигналы с scope=portfolio **не пишутся** в карточку проекта
- Складываются в `adm` — не теряем

### 3.3 timeline.md (PD-043)
- Статический список wikilink-ов (дата + ссылка на summary)
- Генерируется при каждом прогоне
- Не Dataview-query (не зависит от frontmatter FF-summary)
