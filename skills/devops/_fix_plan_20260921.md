## 1. Root cause (почему Сирень пошла напрямую)

Сирень черпает поведение при багах из набора источников. Конфликт между ними — прямой триггер обхода. Ключевые строки:

### 1.1 Позитивный императив «диагностика/план → напрямую Cursor», стоящий ВЫШЕ BUG:diagnose

**hermes-feature SKILL.md, стр. 22–24 (Overview, «ЖЁСТКОЕ ПРАВИЛО»):**
> «Архитектор default (Сирень) НЕ пишет ТЗ, планы, анализ самостоятельно в чате. Все задачи архитектора — ТОЛЬКО через Cursor CLI (`agent -p`). Текущий агент default (Сирень) координирует: вызывает Cursor CLI, передаёт контекст, принимает результат.»

Это «жёсткое правило» создаёт АФФОРДАНС: любой «разбор/план» → сразу `agent -p cursor-grok-4.6-high`, без промежуточной карточки. Оно не встроено в канбан-поток и не оговаривает «но сначала — карточка BUG:diagnose».

**hermes-feature SKILL.md, стр. 46 («Вход»):**
> «Любой HF `agent -p` без корня `DEV/<slug>` → **стоп** + оркестратор. Исключения DPK: `BRF:*` в TG; одношаговый ответ; RESEARCH.»

Стоп-правило СУЩЕСТВУЕТ, но: (а) сформулировано как «стоп воркера HF-фазы», а не как «холодный старт по крон-ошибке = заведи карточку ПЕРВЫМ шагом»; (б) спрятано в разделе «Канбан-шаг → Вход» (стр. 40–49), ниже зоны «когда использовать», где фактически принимается решение о маршруте; (в) конкурирует с «Жёстким правилом» стр. 22–24.

### 1.2 Двумысленность «Крон архитектора только на диагностику» — прямой разрешающий сигнал

**hermes-feature SKILL.md, стр. 378–386 (Блок 6В «Диагностика перед починкой»):**
> 1. «**Крон архитектора только на диагностику** (только чтение, запрет правок) → root cause, план П.1…П.N»
> 2. «Саша просматривает план»
> 3. «Крон исполнителя реализует по плану»

Слово «Крон архитектора» ЧИТАЕТСЯ как вызов архитектора через `cronjob(repeat=1)` / прямое делегирование (что ниже прямо и закреплено в Блок 6Б, стр. 350):

**hermes-feature SKILL.md, стр. 350 (Блок 6Б «Делегирование субагентов»):**
> «Архитектор: ТЗ / план / анализ | `cursor-grok-4.6-high` | `cronjob(repeat=1)`».

При крон-ошибке (низ «отдай архитектору на разбор и план») и «жёстком правиле» (всё через Cursor) + таблице 6Б (архитектор через cronjob) Сирень получает ТРИ согласующихся прямых сигнала «зови архитектора напрямую». Блок 6В описывает «крон», а не «карточку BUG:diagnose» — и это ровно тот обход, который сработал.

### 1.3 Инвариант 8 / off-board сформулирован как «анти-параллельность», а не «анти-обход»

**GLOSSARY.md, §5.2, инвариант 8 (стр. 181):**
> «**One-pass не создаёт второй канал исполнения.** Пока граф `DEV/<slug>` диспатчится (есть дети `todo/ready/running`), координатор **не** вызывает `agent -p` на фазы графа. Прямой ручной cursor-cli по слагу = **сначала** выход из диспатча + off-board (comment `dispatch-paused: off-board` + retro-create `done off-board, session ids`), **и только при снятом `GATE:plan-approve`**…»

**kanban-dev-pipeline-orchestration SKILL.md, Питфолл 6 (стр. 141–145):** то же — «пока граф диспатчится … прямой cursor-cli запрещён; если нужен — dispatch-paused + off-board».

КЛЮЧЕВАЯ ДЫРА: предикат инварианта — «**живой** граф / по слагу». В холодном инциденте (крон-ошибка, слага ещё НЕТ) граф не жив и не существует → предикат ложен → Сирень считает прямой вызов легальным («охранник про параллельность мне не мешает, я ничего не дублирую»). Инвариант 8 — это правило против ДВОЙНОГО канала на живом графе, а НЕ против обхода-без-графа. Самого запрета «до создания BUG:diagnose-карточки прямой agent -p на диагностику/план/реализацию бага запрещён» в скиллах НЕТ.

### 1.4 «Режим делай в 1 проход» подталкивает к «пропустить канбан вообще»

**USER PROFILE:** «режим „делай в 1 проход" — цикл без гейтов, финальное подтверждение».
**hermes-feature SKILL.md, стр. 125:** «Режим „делай в 1 проход" — авто-проход: comment `auto-pass: one-pass mode` + `kanban_complete` без block». Стр. 150–158 (одно-pass раздел), стр. 156: «**Не auto:** `GATE:diagnose-review`, `GATE:go`, `GATE:block-accept`».

Канон (GLOSSARY §5.2 инвариант 3 стр. 176, инвариант 7 стр. 180; hermes-feature стр. 81 «Режим „1 проход" **не** обходит GATE:diagnose-review») ПРАВИЛЬНО говорит, что DX не one-pass. НО: «цикл без гейтов» в USER PROFILE — это мета-сигнал «дешевле, быстрее, без церемоний», который при живом ≪Жёстком правиле≫ (1.1) + «крон архитектора» (1.2) конвертируется в «мне не нужны карточки вовсе». Юзер-профиль перевешивает детальные оговорки скилла.

### 1.5 НЕТ явного «классификатора» триггеров

Скиллы различают маршрут по глаголам (When to Use hermes-feature стр. 28–34: «ошибка/баг/не работает → Блок 7», «почини → Блок 6В»), но НЕТ единой явной бинарной таблицы вида:
«{баг|ошибка|не работает|упало|почини|разберись|проанализируй ошибки} → ОБЯЗАТЕЛЬНО канбан-граф BUGFIX (BUG:diagnose) ДО любого agent -p» против «{спросить|проверить|вычислить|найти данные} → прямой ответ». Когда нет такого классификатора, решение отдаётся модели на усмотрение — и при давлении «жёсткого правила»+one-pass она выбирает прямой путь. Это и есть дыра, подтверждающая формулировку постановки.

### 1.6 Cron-troubleshooting прямо РАЗРЕШАЕТ прямой agent -p на баг-root-cause

**cron-troubleshooting SKILL.md, стр. 195:** «При сложном root cause — передать Cursor CLI архитектору (`--mode plan`) с найденными файлами и ошибками для анализа и плана». Это прямое разрешение на обход карточки BUG:diagnose именно для крон-ошибок — то же русло, что сработало. Стр. 185: «reconcile: cron run failed … чинить надо крон» — тоже поощряет прямую починку без канбана.

### Сводка root cause

Доминирующий аффорданс «разбор/план/реализация → прямой Cursor / cronjob» (hermes-feature стр. 22–24, 350, 378–382; cron-troubleshooting стр. 195) стоит ВЫШЕ и РАНЬШЕ, чем запоздалый негативный стоп-гейт «нужна карточка BUG:diagnose» (hermes-feature стр. 46, 71–81; GLOSSARY §2/§5.2). ## 3. Риски

1. **Переусложнение.** Прямой ответ правомерен для «спроси/проверь/найди данные» и RESEARCH. Классификатор (П.2) оставляет эти ветки открытыми; иначе каждый вопрос пойдёт в 16-карточный граф — перегруз. Классификатор = 3-4 строки, не процедура.
2. **One-pass скорость vs обязательный канбан.** «делай в 1 проход» не должен душиться полным хвостом для МЕЛКОГО бага (≤3 файла). Предусмотреть минимальный BUGFIX-хвост: BUG:diagnose → GATE:diagnose-review → (≤3 файла, REV OFF) HF:impl → HF:test → done, без HF:plan/backup/ORCH для лёгких. Корневой one-pass допустим, но корень = BUG:diagnose-карточка, не «без карточки».
3. **Правки user-профиля и MEMORY** — требуют явного «делай» Саши (R3), не выполняются этим планом.
4. **Где хранить правило, чтобы оно реально грузилось.** Расположение: основное — `hermes-feature` (грузится по баг-триггерам When-to-Use/описанию скилла), канон — GLOSSARY, страховка одной строкой — MEMORY (грузится всегда). НЕ AGENTS.md как основной носитель: он справочник структуры для Cursor, а не поведение Сирени (и грузится только при работе из WorkVault). Память не перегружать полным классификатором — иначе вытеснит остальные конвенции.
5. **Симлинки скиллов.** `~/.hermes/skills/devops/hermes-feature` и `mofs-operations` — симлинки на `profiles/default/skills/…`; правки ведутся в репозитории `hermes-workspace/skills/`, затем синк в профили через `restore-all-skills.sh` (AGENTS.md стр. 126) + git-синк. Неправильный порядок → рассинхрон между профилями.
