# Bounded-декомпозиция крупных исполняемых частей и граница P-nodeid

Проверено на W1-01/W1-02/W1-03 (прямой direct-режим вне канбана). Общее правило для
любой серии исполняемых частей, где каждая часть = свои nodeids + свои write-paths.

## Крупная часть > одного прогона = объём контракта, не сбой кода

- НЕ повторять общий scope сплошными прогонами. Дробить на под-батчи по ЯВНЫМ id
  (test_case[Kxx], test_component[W1-xx], пары «источник→цель») и давать в каждом раунде
  только адресные группы. Прогресс в десятках строк/кейсов за раунд — норма, не признак
  тупика.
- Исполнитель без текстов источника/нормы НЕ выдумывает span/assert — честно оставляет
  OPEN/NOT_RUN и перечисляет остаток. Это достоинство, не дефект: на него нельзя ретраить
  «тот же общий scope» до бесконечности.
- Подсказка исполнителю-редактору: читать НЕ giant-входы (250–100 КБ PREP/ARCH), а извлечённую
  закрытую таблицу/карту и/или явные адресные пары в промпте раунда.

## Паттерн component / полный parent (delta-граница)

Ситуация: полному протокольному nodeid (`test_protocol[Pxx]`) назначен текущий part, но его
ПОЛНЫЙ приёмочный смысл (правка/verifier/invoke/выбор роли/поздние readers/dispatch) физически
реализуется только в более поздних частях, которых ещё нет физически (serial).

Явные признаки: исполнитель после нескольких полных раундов честно не может закрыть P
без подмены; полный oracle требует API, отсутствующего в allowlist текущей части.

Правильный исход — НЕ крутить исполнителя в полных контрактных раундах по прецеденту одного P
и НЕ давать проходящий P-тест-заглушку:
1. Отдать архитектору адресный вердикт о границе: какие component-assertions РЕАЛЬНО ложатся
   на текущий part (доказать через настоящий candidate/native API), какой точный владелец
   полного parent + его dependencies + интеграционные вклады промежуточных частей.
2. Получить ОДНО адресное решение владельца (принять delta / оставить границу). НЕ объявлять
   перенос решённым по прецеденту предыдущего P — каждый перенос требует своего решения.
3. После решения синхронизировать нормативный документ (ARCH/N/PREP) с маркером дельты,
   сохранить множество nodeids и текст оракула побайтно; меняется только владелец полного
   доказательства и момент проверки.
4. Текущая часть закрывает component-вклад (lower-layer нижние группы P исполняются в её
   test_component), полный parent — у названного владельца; W1-12-style сборщик не получает
   чужие oracle.

## Питфоллы direct-режима (hered-канбан, candidate, W1_PY)

- pytest из candidate по умолчанию пишет temp под `~/.hermes/cache/scratch` — это нарушает
  границу H read-only. ВСЕ pytest-команды c `TMPDIR=/tmp`; в отчёт включать проверку «нет
  новых файлов H от этого прогона».
- `notify` без `background=true` — «notify only applies to background commands»: фон только
  с `background=true, notify=true, persist_on_release=true`.
- При фоне H продолжает жить сам (cron/gateway/другие pytest) — «нулевой общий diff H»
  независимо не доказуем. Фиксировать только свои прямые записи; чужие runtime-файлы
  не чистить и не объявлять устранёнными без отдельного доказательства.
- Write-scope части исчерпывающе перечислять в промпте (не «ровно N файлов» — N меняется,
  а «только эти»); base→HEAD name-status должен быть подмножеством scope.
- regression: каждая новая часть не ломает закрытые nodeid предыдущих (W1-02 сохраняется
  при закрытии W1-03); прогонять сохранённый node вместе со своими.
