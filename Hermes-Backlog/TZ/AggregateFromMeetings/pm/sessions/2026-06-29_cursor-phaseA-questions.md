## 2. Новые вопросы и рекомендации (нужно решение PM)

### Q-A1. Дедлайн по умолчанию «+5 рабочих дней» (PD-023) — потерян при переходе на Tasks-query
**Контекст:** PD-023 (25.06): если у задачи нет срока → ставить `due = дата встречи + 5 раб. дней`. При переходе на модель «задачи физически в срезах G» (PD-035) это правило в ТЗ **не перенесено** (IQ-A03 помечен частичным).
**Рекомендация:** оставить правило — Haiku при записи задачи в срез без явного срока ставит `due = meeting_date + 5 рабочих дней`, помечает `📅 (inferred)`; PM правит при необходимости. Включить в TZ_C/TZ_D.
**Нужно:** да / нет / иначе (напр. ставить `???` вместо +5 дней — как в решении H3 от 20.06).

> ⚠️ Тут есть прежнее противоречие: решение GATE H3 (20.06, TZ_C) говорит «нет срока → `???`», а PD-023 — «+5 раб. дней». Нужен один ответ.

### Q-A2. GATE H3 (precision модуля C) переоткрывается
**Контекст:** прежний H3 снимался на двухшаговой архитектуре с Opus. Opus убран → точность сборки decisions/action_items теперь на Haiku-only.
**Рекомендация:** переснять H3 на Haiku-only после IQ-B10 (единый проход); прежние цифры H3 не репрезентативны. Зафиксировать в BUILD_CHECKLIST как «H3-rework».
**Нужно:** подтвердить, что H3 переснимаем (не блокер, но влияет на сроки).

### Q-A3. Дедуп задач между срезами — подтвердить, что MVP живёт с дублями
**Контекст:** PD-035 явно вынес дедуп задач между срезами «в отдельную задачу разработки» (не MVP). Значит одна задача, обсуждённая на 3 встречах, в MVP может показываться 3 чекбоксами в query (PD-019 — «одна запись» — временно не выполняется).
**Рекомендация:** принять для MVP (дубли видны, но не теряем задачи); сделать stable-id дедуп в Фазе B+ (IQ-B12 follow-up). Альтернатива — query со встроенной группировкой по нормализованному тексту (косметика, не настоящий дедуп).
**Нужно:** ок жить с дублями в MVP? (Рекомендую да.)

### Q-A4. Tasks plugin — подтвердить инструмент и механику закрытия
**Контекст:** «закрытие чекбокса в query правит файл-источник (срез G)» — это поведение **Obsidian Tasks plugin** (toggling в query редактирует исходный файл). Dataview такого не умеет (read-only).
**Рекомендация:** источник истины-агрегатор — **Obsidian Tasks plugin** (не Dataview); задачи в срезах пишем в формате Tasks (`- [ ] текст 🏷️#slug 👤@login 📅 YYYY-MM-DD`). Проверить на одном проекте, что toggling из query правит файл в `snapshots/`.
**Нужно:** подтвердить выбор Tasks plugin + формат строки задачи.

### Q-A5. «Проект» vs «инициатива» — где заводить risks.md
**Контекст:** risks.md только для «проектов/инициатив» (PD-031). В роутере (B) есть `route = project / 1on1 / multisync / unclear`; отдельной сущности «инициатива» нет — инициативы это те же `Projects/<slug>/`.
**Рекомендация:** risks.md заводим для всех `scope=project` сущностей (Projects/<slug>/), кроме `adm` и синков; «инициатива» = проектный slug. Отдельный тип не вводим.
**Нужно:** подтвердить (инициатива = проектный slug).

### Q-A6. Куда именно писать portfolio-сигналы в adm
**Контекст:** PD-040 — сигналы `scope=portfolio` идут в `adm`, «не теряем». Но `adm` — служебная категория без Confluence; структура её артефактов не описана.
**Рекомендация:** складывать в `Projects/adm/ai/portfolio.md` (отдельный накопительный файл со ссылкой на встречу-источник), не смешивая с обычными decisions. В карточки проектов — не пишем.
**Нужно:** ок `adm/ai/portfolio.md`? или в `adm/ai/decisions.md`?

### Q-A7. Приоритет PM Notes vs более поздняя FF-встреча
**Контекст:** PD-037 — PM Notes «главенствующий приоритет»; PD-030 — новая инфа из следующей FF «учитывается наравне с инкрементом+PM Notes». Это потенциально конфликтует: что если свежая встреча противоречит PM Note?
**Рекомендация:** PM Notes «липкие» — перекрывают авто-сборку; более поздняя FF может **дополнить**, но **не отменяет** PM Note молча — при противоречии Haiku помечает конфликт (Warning в срезе) и оставляет версию PM до явного нового PM Note.
**Нужно:** подтвердить правило приоритета при конфликте.
