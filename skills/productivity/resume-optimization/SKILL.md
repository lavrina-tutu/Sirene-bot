# Resume / CV optimization (Саша)

## When to Use

Саша просит поработать с его резюме/CV: «разбери резюме», «сделай резюме удобно читаемым для ИИ/HR/руководителей», «внеси опыт в Туту», «обнови резюме». Резюме обычно приходит как .rtf (экспорт hh.ru) во вложении Telegram.

Класс задачи: привести резюме Саши в вид, читаемый ИИ, HR и руководителями/проектным офисом, сохранив шаблон и формат hh.ru, и внести текущую позицию в Туту.

2. **Собрать факты резюме** полностью: шапка (ФИО, возраст, контакты), желаемая должность, все места работы (периоды, компании, должности, стеки, команды, достижения), образование, курсы/сертификаты, навыки, языки.
3. **Собрать факты о роли в Туту** из внутренних источников, НЕ из головы. Это текущая позиция «по настоящее время», ей заменяется блок, где был «Синимекс — настоящее время».

Проверять их как кандидатов на доп.буллеты, прежде чем писать «опыт = только перечисленные проекты».
   - **Классификация найденного: отдельный проект vs функциональное направление.** Спросить Сашу про каждый неочевидный блок («это целый проект или функция?») — он различит: напр. Атрибуция = РУКОВОДИЛ ПРОЕКТОМ (в портфель/ключевые достижения), а Метротека/OKR = функциональные зоны → строкой в «Обязанности». Спрашивать по одному блоку, не наваливать 3 вопроса разом (R3).

Если проекта нет в зеркале — брать факты из `Entities/<slug>/card.md` (статус, заказчик, даты, `confluence_id`, критерии приёмки, кем согласован) + `Meetings/NewMeetings` summary + протокол встреч. Card.md достаточно, чтобы составить буллет «руководил проектом X (завершён)» даже без страницы-устава.
4b. **Стиль буллетов (предпочтение Саши — всегда):** результаты-глаголы в страдательно-результативной форме — «подготовлено экономическое обоснование», «проработаны подходы», «определены источники», «оценена стоимость», «получено КП» — НЕ действие от первого лица («я подготовил», «работал с поставщиками») и НЕ туманное «проект проработан». Каждый буллет отвечает «что получено», заканчивается явным исходом.
   Дополнительные стилевые правила этого класса (все из правок Саши):
   - **Выгоду для бизнеса — в начало буллета** («агент берёт на себя рутину аналитики…»), до перечисления работ. «О себе/что делает проект» — кратко и без раздувания.
   - **Финансовый эффект — «в разах», не в точных суммах.** Не писать конкретные суммы экономии (Саша: «точные цифры не важны»). Писать «экономия в разы» или перечислять состав экономии: на внедрении, на лицензиях, на ежегодном сопровождении вендора. Можно сравнить с доработкой собственной платформы («затраты на порядок выше доработки собственной»).
   - **Не писать «внутреннюю кухню»** — недоверие заказчика, споры, предпосылки-гипотезы. Только факты: проведено исследование/сравнение, подготовлено обоснование, выбран вариант. Причина «закрыт решением» — формула «бизнес признал продолжение нецелесообразным / комиссия приняла решение не внедрять», без мотивации недоверия.
   - **Не называть конкретные инструменты/технологии** (AI-DWH, Metabase, Hermes, MCP, DataKIT). Писать функционально: «выгрузка и расчёт метрик по витринным данным», «построение отчётов и визуализаций по запросу», «поиск дашбордов». Названия систем неважны — важна решаемая задача.
   - **Не внутренние аббревиатуры/жаргон** («АиД», «МАС»). Расшифровывать или заменять: «департамент аналитики», «мультиагентная система». Аудитория (HR, руководители, проектный офис) их не знает.

   - **Проект «закрыт решением (комиссии)»** (Trisigma, ML-платформа): статус такой формулировкой; показать что ДОСТАВЛЕНО (исследование, сравнение, уставы подготовлены, команда готова стартовать) + итог — выбрана собственная платформа и экономия. Аналог закрытого проекта, но акцент на выборе варианта, а не на провале.
5. **Переписать под HR/AI-читаемость** (предпочтения Саши, применять всегда):

   - Сохранять структуру шаблона hh.ru (Желаемая должность, Опыт работы, Образование, Курсы, Навыки).

6. **Подтвердить ключевые факты до финализации файла**: точную должность в Туту (по трудовой/должностной) и дату начала — НЕ выдумывать, НЕ дефолтить. Спросить у Саши варианты с рекомендацией, по одному вопросу (R3). После подтверждения — собрать итоговый RTF/файл в том же шаблоне.

## Сборка итогового RTF (клонирование эталона hh.ru)

Когда Саша просит итоговый RTF «по эталону» / «клон эталона с данными rev N» / «соблюди шрифты-блоки-таблицы как в эталоне»:

- **Эталон (актуальный)** = `~/WorkVault/Personal/resume/эталон_формат_резюме_rev6.rtf` — прислан Сашей 29.10 как финальный образец формата (~4.2 МБ, фото большого разрешения вшито через `jpegblip`). Это образец ТОЛЬКО визуального формата (шрифты, цвета, таблицы, границы, колонтитулы, фото). Исходный первый эталон — `эталон_формат_первоначальное_резюме_Ткаченко_100125.rtf` (первоначальное hh.ru-резюме, ~313 КБ).
- **Контент** = markdown `~/WorkVault/Personal/resume/резюме_итог_20261026revN.md` (актуальная rev: должности обёрнуты в `**…**`, языки — подраздел «Знание языков» внутри «Навыки»). Файл `_итоговый_rtf_source.md` — устаревший контент прежней rev, скрипту НЕ вход.
- **Скрипт-генератор** = `~/WorkVault/Personal/resume/build_resume_rtf.py`, запуск: `python3 build_resume_rtf.py --et <эталон.rtf> --md <контент.md> --photo <фото.jpg> --out <итог.rtf>`. Хранить в `resume/` (НЕ в scratch: он очищается за 24h idle, скрипт теряется).
- **Механика** (восстановленный скрипт): каркас+шапку (`data[:body_start]`, где `body_start` = `\trowd` перед hex-якорем «Желаемая») и хвост (`data[tail_start:]`, `{\*\latentstyles`) копирует из эталона ПОБАЙТОВО; тело генерирует из markdown, заворачивая каждый абзац в одноколоночную таблицу `\trowd … \cellx9638 … \pard … \cell \row`. Границы секций — по raw-оффсетам `\trowd` и hex-якорям заголовков.
- **Замена фото**: в эталоне фото — ДВА блоба (jpegblip + `\nonshppict` с несжатым DIB/WMF ~4 МБ). Скрипт заменяет hex JPEG (`ffd8…ffd9` после `jpegblip`) на hex нового фото, обновляет `\picw/\pich` на реальный размер, и ВЫРЕЗАЕТ `\nonshppict{…}` (WMF-фолбэк не нужен — jpegblip валиден сам по себе). Итог ~230 КБ вместо 4.2 МБ. Принцип: каркас (`[0:first_trowd]`), шапку (`[first_trowd:prev]`), хвост (`latentstyles+datastore`) копирует из эталона ПОБАЙТОВО; тело секций генерирует из markdown, завернув в собственные `\trowd/\cell/\row` таблицы в том же стиле. Границы секций — по raw-оффсетам `\trowd` и hex-якорам заголовков.
- **Результат** = `Ткаченко_Руководитель_проектов_резюме_итог_20261026revN.rtf`. Фото = `фото_резюме.jpg` (800×800).

Формат-иерархия (ровно как в эталоне):
- Заголовок секции = Arial `\f1` **12pt** (`\fs24`), **серый** `\cf22` (#AEAEAE), снизу линия `\brdrb\brdrs\brdrw15\brdrcf24` (#D8D8D8).
- Компании (`###`) и должности (цельно-`**жирный**` абзац) = Arial 12pt **жирный**, чёрный.
- Содержимое/буллеты = Arial **9pt** (`\fs18`), чёрный.
- colortbl ключевые: cf20=#605E5C, cf22=#AEAEAE (заголовки), cf24=#D8D8D8 (линии/границы).

Питфоллы генерации (несколько раз наступал):
- **Сброс цвета обязателен**: после `\cf22` заголовка секции цвет «протекает» в следующий абзац. Каждый абзац содержимого начинать с `\f1\cf0\fs…` — иначе всё содержимое серое. `\cf0` = чёрный по умолчанию.
- **Баг парсера markdown**: строки ДО первого `##` (шапка markdown) при `cur_title=None` копились и «прилипали» к первой секции (дубль контактов в «Желаемая должность»). Лечится: `flush()` очищает `cur_blocks` БЕЗУСЛОВНО (не только когда `cur_title` истинно).
- **Шапку править точечно, не пересобирать**: возраст/«Срок выхода» — `str.replace` по уникальному контексту в уже отрезанной строке шапки (напр. `, 46\~` уникален; «срок выхода» вставить перед `}{\rtlch` после слова «командировкам»). Замену делать ПОСЛЕ вычисления оффсетов границ, иначе сместишь `\trowd`-якоря.
- **Замена фото** = подмена hex JPEG внутри существующего `\jpegblip`: `\picw2514\pich3792\picwgoal1425\pichgoal2150` → новые размеры; hex-данные заменить между первым `ffd8` (после `\jpegblip`) и `ffd9` (+4). Новый JPEG читать как bytes → `.hex().lower()`. `ffd8` в счётчике может быть >1 — это совпадение в EXIF-данных, не ошибка; валидность проверять по `ffd9` (один EOI) и балансу `{}`.
- **Кириллица в RTF** — через `\'xx` (cp1251 hex) подряд, без `\loch/\hich`-обвязок (она не нужна для русского); финальный `.encode('cp1251')`. Юникод-текст пишет только мой enc(); эталон-строки уже в нужной кодировке.
- **Языки** в эталоне — подраздел блока «Навыки», НЕ отдельная секция. Оформлять как «Знание языков: Русский — родной · Английский — B2» в формате прочих навыков (`**префикс:**` жирным + значения 9pt), сливая языки в секцию «Навыки».
- **Отступы для читаемости** (правка Саши): `\sb` (space before) на компании/подзаголовки, `\sa` (space after) на буллеты и после компании — иначе всё «сливается».

## Pitfalls

- pandoc (2.14) НЕ читает rtf на входе (`Unknown input format rtf`) — не трать время на pandoc -f rtf; сразу ставь striprtf в uv venv.
- Должность и дату начала в Туту не выдумывать: это факты из трудовой. Если не найдены в источниках — спросить у Саши (варианты + рекомендация), не дефолтить.
- Файл резюме обычно приходит как приложение в Telegram (binary), текст НЕ инлайн — всегда извлекать самому, не просить Сашу вставить текст.
- Навыки блоками-перечислением без категорий ломают ИИ-парсинг и матчинг — всегда категоризировать.
- «Синимекс — настоящее время» после добавления Туту становится историей (период закрывается датой ухода), текущий блок — только Туту.
- Свои данные о роли Саши в Туту есть в WorkVault/Meetings — искать там ДО того как писать секцию, не полагаться на память/контекст.
- Писать фразы от первого лица в действии («я подготовил») → Саша возвращает на переформулировку в результативную форму. Пиши сразу «подготовлено/проработано/получено».
- Утверждения о проекте не сверять с документами → рискуешь внести специфику, которой в уставе/отчёте нет (верифицируемость резюме падает). Каждый тезис — только из устава/отчёта/брифа/протоколов.
- Один проект = один раунд «подтвердил факты → предложил буллет → Саша вычитал → записал»; не мешать несколько проектов в одно сообщение.
- Конкретные суммы экономии/внедрения в буллете → Саша правит на «в разах». Пиши сразу общую формулировку, суммы-источники в текст не тяни.
- Упомянуть технологии/названия инструментов (AI-DWH, Metabase, Hermes) → Саша просит убрать, оставить логику vs инструмент. Планируй функциональное описание сразу.
- Оставлять аббревиатуру («АиД») без расшифровки → читатель-не-в-контексте её не понимает. Пиши «департамент аналитики».
- Наваливать несколько вопросов-уточнений по разным блокам в одно сообщение → Саша последовательно отвечает и просит по одному. Спрашивай про каждый новый блок (проект/функция, как оформить) отдельным вопросом.
- Искать проект «в папке Проекты» и не находить → не значит, что его нет. Confluence-зеркало неполное: часть проектов синхронизирована, часть — только entity `card.md`. Падай на card.md, не на отсутствие страницы.
- Саша говорит про блок «это целый проект» (напр. Атрибуция), а ты планировал строку в обязанности → уточняй статус каждого функционального блока до оформления, иначе неверно категоризуешь достижение.
- Держать скрипт/генератор (build_resume_rtf.py) в scratch (`~/.hermes/cache/scratch`) → при очистке каталога за 24h idle скрипт безвозвратно теряется. Все переиспользуемые артефакты (скрипты, эталон, source) хранить в `~/WorkVault/Personal/resume/`, а не в scratch.
