# Принципы написания скиллов Hermes

## Самодостаточность — главный принцип

Скилл загружается по триггерам **независимо** от других скиллов. Когда в тексте скилла написано «см. скилл X» — referenced скилл физически **не загружается**. Агент видит только текст ссылки, не содержимое referenced скилла.

**Правило:** каждый скилл должен содержать всё необходимое для своей задачи. Если правило нужно в двух скиллах — продублировать, не ссылаться.

**Исключение:** ссылка оправдана только если оба скилла загружаются **явно вместе** через `skills=[...]` в промпте субагента.

**Пример нарушения:** `tz-workflow` ссылался на `hermes-feature` для правил реализации. Но `tz-workflow` загружается при написании ТЗ, а `hermes-feature` — при реализации. Они никогда не загружаются одновременно по триггерам → ссылка бесполезна.

## Логическая граница скилла

Скилл должен покрывать ровно свой этап, не захватывать соседний:

| Скилл | Начало | Конец |
|---|---|---|
| `tz-workflow` | Запрос на ТЗ | Финализация ТЗ + явное «берём в работу» |
| `hermes-feature` | «Берём в работу» | Тесты пройдены, Саша подтвердил «готово» |

STOP-гейт и чеклист реализации — зона `hermes-feature`, не `tz-workflow`.
Правила хранения ТЗ — зона `tz-workflow`, не `hermes-feature`.

Захват соседнего этапа = дублирование + риск расхождения при обновлении одного из скиллов.

## Критерий выбора модели — явно в скилле

Каждый скилл должен явно указывать какая модель выполняет задачу. Не «основная модель» или «дефолтная» — а конкретная версия:

| Задача | Модель |
|---|---|
| Собрать факты: grep, git, конфиги | **claude-haiku-4-5** |
| Анализ одного инструмента, рекомендация | **claude-sonnet-5** |
| Интеграционные вопросы, несколько инструментов, новый инструмент | **claude-opus-4-7** |

Провайдер — всегда из конфига по умолчанию, не хардкодить.

## Синхронизация с внешними источниками

Если скилл имеет зеркало в WorkVault (например `_TZ-WORKFLOW-RULES.md` для `tz-workflow`) — добавить в начало зеркала заголовок:

```markdown
> **Синхронизация:** этот файл является зеркалом скилла `<name>` (версия X.X.X, дата). При расхождении — скилл приоритетнее.
```

При обновлении скилла — обновить и зеркало в той же операции (или добавить в Verification Checklist скилла).

## Чеклист при создании нового скилла

- [ ] Скилл самодостаточен — не требует загрузки другого скилла для выполнения задачи
- [ ] Логическая граница чёткая — не захватывает соседний этап
- [ ] Модели указаны явно (конкретные версии, не «основная»)
- [ ] Триггеры специфичны — не пересекаются с другими скиллами
- [ ] Verification Checklist содержит только то, что проверяется в рамках этого скилла
- [ ] Ссылки на другие скиллы — только если они загружаются явно вместе

## Common Pitfalls

- **Ссылка вместо дублирования** — если правило нужно здесь, пиши его здесь. Ссылка не загружает скилл.
- **STOP-гейт не там** — STOP-гейт принадлежит скиллу реализации, не скиллу написания ТЗ.
- **Verification Checklist из соседнего этапа** — чеклист должен проверять только то, что делает этот скилл.
- **«Детали — в скилле X»** — если скилл X не загружается одновременно, это мёртвая ссылка.
