# WorkVault RAG — семантический поиск по MD-заметкам

## Overview

RAG-поиск по WorkVault (Obsidian MD-заметки: встречи, ТЗ, Confluence) через два возможных инструмента — **enzyme** (compile-time граф связей, быстрый, но не установлен) и **qmd** (BM25+vector с явными коллекциями, внедрён и работает с 09.07.2026). Скилл фиксирует выбор инструмента по типу задачи, реальные питфоллы установки/эксплуатации qmd на CPU-only VM, паттерн фильтрации разнородного контента (filter-farm) и решение по reranking-производительности.

## When to Use

**Триггер срабатывает автоматически (не дожидаться явного упоминания RAG/qmd от Саши) на любой из этих типов запроса:**

- Вопросы про **встречи**: "что обсуждали с X", "какая была встреча про Y", "когда говорили про Z"
- Вопросы про **задачи/поручения**: "какие задачи ждёт от меня X", "что я обещал сделать", "что поручили Y"
- Вопросы про **решения**: "что решили по X", "какое было решение насчёт Y"
- Вопросы про **риски/блокеры**: "какие риски по X", "что блокирует Y"
- Вопросы без структурного фильтра по сущности+датам (смысловые, "что вообще думают про X", PM Briefing) — через qmd как обычно.
- PM Briefing в начале сессии — «что важного по проектам?»
- Поиск по 1000+ файлам NewMeetings без явных ключевых слов
- Нужно найти связи между заметками (кто участвовал, какой проект упоминался)
- Добавление/удаление RAG-коллекции, диагностика медленного/нерелевантного поиска

**Для всех запросов со структурным фильтром (дата/участник/проект + тип сущности) — см. полный алгоритм ниже, не qmd в одиночку.**

## Алгоритм поиска по встречам (структурные запросы: дата/участники/проект + тип сущности)

Подтверждено с Сашей 09.07.2026. Применять к любому запросу вида "какие [задачи/решения/риски/блокеры] по [X/за период Y]".

### Шаг 1 — период

- Дата/период явно указан в запросе ("с 16.06", "за последние 2 недели", "в июне") → фильтр списка файлов по дате в имени файла (`YYYY-MM-DD HH-MM-SS ...`) на этот период.
- Период не указан → по умолчанию последние **6 месяцев**.
- Фильтрация по дате — **всегда через `search_files`/листинг директории по имени файла**, не через qmd (qmd не индексирует дату как отдельное фильтруемое поле — см. питфолл #8).

### Шаг 2 — участники

- Человек назван в запросе ("что обещал Аралов", "что мы обсуждали с Х") → из набора шага 1 оставить только встречи, где этот человек указан в секции **"Участники:"** файла (точное совпадение в списке участников, не любое упоминание имени по всему тексту — упоминание "в контексте" даёт слишком много шума).

### Шаг 3 — проект/тема

- Проект/тема назван в запросе ("по ML-платформе", "по мультиагентной системе") → из набора после шагов 1-2 оставить только встречи, где проект упоминается в тексте (заголовок встречи или содержимое).

### Шаг 4 — извлечение сущностей

Работать с финальным отфильтрованным набором файлов:
- **Если файлов >10** — не читать все инлайн: делегировать Haiku (`delegate_task`, таймаут 120с) — сырые Action Items/Риски/Решения из всех файлов набора + вопрос Саши → отфильтрованная выжимка.
- **Если файлов ≤10** — читать напрямую (`read_file`), без делегирования.
- **4.1 Запрошены НЕ задачи** (решения / риски / блокеры) → выдать все найденные сущности этого типа из всех файлов набора, без дополнительной фильтрации по назначенному лицу.
- **4.2 Запрошены задачи** → выдать только Action Items, где ответственный явно указан как один из упомянутых участников (точное имя в строке Action Item, не implicit-отнесение по контексту). Если Саша спрашивает про себя ("что мне поручили") — те же правила, явное указание его имени в Action Item.

### Признак "неясная запись / переговорка" (добавлено 09.07.2026)

На встречах в переговорках (особенно мультисинки и 1-1, где несколько человек говорят в одной комнате) Fireflies часто **неверно атрибутирует Action Items конкретному спикеру** — разметка голосов даёт сбой. Такие задачи **лучше по умолчанию относить к самому Саше** ("мои задачи, разберу вручную далее"), а не к тому, кому их формально приписал Fireflies.

**Признаки "неясной записи" (совпадение любых 2 из 3 = считать неясной):**
1. Файл встречи — загрузка аудио/видео (`.m4a`/`.mp4` фигурирует в названии файла) — то есть запись с диктофона/телефона в переговорке, не прямая интеграция с онлайн-звонком.
2. Action Items в summary не содержат чёткого разделения "Имя: задача" — общий список без явного автора.
3. Название встречи совпадает с известным названием переговорки ТУТУ. **Реализовано 09.07.2026** — актуальный список 31 переговорки получен через `orglookup rooms` (Exchange GAL Room Lists API, инструмент `~/USERTOOLS/OrgLookup`) и хранится в `WorkVault/Contacts/meeting-rooms.md`. Проверять название встречи на совпадение с колонкой "Название" в этом файле (например "Тайга", "Пустыня", "Мутный материк", "Джунгли", "Саванна" и т.д. — часто с суффиксом "- Zoom" или числом вместимости в скобках, которые в названии встречи обычно не повторяются, сверять по основному слову). Обновляется вручную запуском `orglookup rooms` по мере необходимости (не на кроне) — при использовании этого признака проверить дату `updated:` в frontmatter файла на актуальность.

При совпадении признаков — в шаге 4.2 такие Action Items помечать как задачи Саши, а не оригинального (возможно ошибочного) адресата, и явно указывать в ответе, что источник — запись из переговорки/неясная атрибуция, требует ручной проверки.

## Два инструмента: enzyme vs qmd

### enzyme — Hermes plugin (compile-time граф)

```bash
hermes plugin install jshph/enzyme-skill
cd ~/WorkVault && enzyme refresh   # первая индексация
enzyme petri                       # briefing: trending topics, thematic tensions
```

- 8мс поиск (compile-time, не per-query), 23MB embedding-модель (ONNX)
- Лучший для: «агент знает vault до первого сообщения», граф связей тегов/ссылок/папок, находит связи без совпадения ключевых слов (через catalysts)
- Scoping: `~/.enzyme/config.toml` — `folder:<path>` помечает важный узел графа, `targets = [...]` для точечного поиска вне обычного индекса. Нет строгого allowlist-режима — работает через приоритизацию + автоисключение служебных папок (`.hermes`, `.git`, `.obsidian`, `node_modules`)
- Не установлен на текущей VM — доступен как будущее расширение для широких/ассоциативных вопросов

### qmd — official optional-skill Hermes (внедрён 08-09.07.2026)

```bash
hermes skills install qmd
qmd collection add <path> --name <name>
qmd context add qmd://<name> "<описание для улучшения поиска>"
qmd embed
qmd query "запрос"          # рекомендуемый MCP-путь, см. раздел про rerank ниже
qmd search "запрос"         # BM25 keyword, ~0.3с
qmd vsearch "запрос"        # semantic only, ~4с
```

- 3 локальных GGUF-модели (~2GB): embeddinggemma-300M (embedding), qwen3-reranker-0.6b (reranking), qmd-query-expansion-1.7B. Требует Node.js ≥22
- MCP-интеграция: `qmd mcp --http` (демон) + `hermes mcp add` → инструмент `mcp_qmd_query`
- Scoping: явные именованные коллекции (`qmd collection add`) — настоящий allowlist, qmd видит только явно добавленные пути
- Лучший для: точечный факт-поиск (имена, даты, названия инструментов) — детерминированный BM25+vector надёжнее ассоциативного графа enzyme для этого класса запросов
- Не требует Obsidian запущенным — читает файловую систему напрямую, как и enzyme

## Выбор по задаче

| Задача | enzyme | qmd |
|---|---|---|
| PM Briefing, session start | лучше | — |
| Поиск по митингам/ТЗ с именем/датой | — | лучше (внедрён, работает) |
| Связи между темами/проектами | лучше | — |
| Интеграция в Python-скрипт | — | лучше |
| Запросы через Telegram к точечным фактам | — | лучше — детерминированность важнее скорости графа |

**Решение для текущего внедрения (08.07.2026):** для реального сценария Саши (точечные факт-запросы через Telegram — «что обещал Х», «какое ТЗ описывает Y») выбран **qmd**. Enzyme не разворачивается до появления реальной потребности в широком тематическом брифинге.

## Filter-farm: фильтрация разнородного контента (не индексировать папку целиком)

Проблема: любая папка, где вперемешку лежат финальные материалы и черновой/промежуточный процесс (например `Hermes-Backlog/TZ/` — master-ТЗ + `pm/sessions/*` черновые handoff-логи + `_TEMPLATE.md`/`README.md`/`MAIN_TZ_INVENTORY.md`), при полной индексации может выдать RAG устаревший промежуточный вариант вместо актуального финального. То же с встречами: `summary.md` (плотный, ~3KB) vs `transcript.md` (полный, ~31KB, ~30+ чанков) — при смешанной индексации transcript-чанки численно доминируют топ-кандидатов просто по объёму, даже если менее релевантны.

**Решение — copy-based filter-farm** (НЕ симлинки — см. Common Pitfalls):

```bash
COLL_ROOT="$HOME/.local/share/qmd-collections"
mkdir -p "$COLL_ROOT/<name>"

# Простой паттерн (один include):
rsync -a --include='<final-pattern>' --exclude='*' <source-dir>/ "$COLL_ROOT/<name>/"

# Сложный отбор (несколько масок + исключения путей):
find <source-dir> \( -name "<pattern-1>" -o -name "<pattern-2>" \) \
  -not -path "*/<draft-subdir>/*" -not -name "_TEMPLATE.md" \
  -print0 | xargs -0 -I{} cp {} "$COLL_ROOT/<name>/"

qmd collection add "$COLL_ROOT/<name>" --name <name>
```

Побочный эффект копирования: файл дублируется на диске (не критично, MD малы) и **не подхватывает изменения оригинала автоматически** — при обновлении источника нужно повторно скопировать (idempotent — перезаписывает существующий). Для контента без периодического крона (ТЗ правятся вручную через Opus, не по расписанию) — досоздание копий + `qmd embed` встраивать в конец соответствующей процедуры правки (`tz-workflow` Блок B/C), не в отдельный крон.

**Проверенные примеры (реализовано и работает 09.07.2026, `QMD-Search_TZ.md` v0.4):**
- `meetings-summary` — только `* - summary.md`, transcript исключён
- `tz-backlog` — `*_TZ.md` + `TZ_*.md` (master-ТЗ и модули) + `PM_DECISIONS_LOG.md`/`GOLDEN_REFS.md`; исключены `pm/sessions/*`, `_TEMPLATE.md`, `README.md`, `MAIN_TZ_INVENTORY.md`, `_TZ-WORKFLOW-RULES.md`, `cursor-*.md`
- `confluence` — прямой путь без filter-farm (контент уже чистый, всего 4 index.md файла)

## Управление коллекциями (добавление/удаление хранилищ)

**Добавление** — только по явному запросу пользователя:
1. Оценить: filter-farm через копирование (контент смешанный) или прямой путь (контент уже однородный, как Confluence).
2. `qmd collection add <path> --name <name>` + `qmd context add qmd://<name> "<описание>"` + `qmd embed`.
3. Зафиксировать в живом плане проекта (см. `QMD-Search_TZ.md` §5а — таблица активных коллекций).

**Удаление:**
1. `qmd collection remove <name>` — **синтаксис проверен на практике 09.07.2026** (тестовая коллекция создана/удалена, реальные данные не затронуты): удаляет документы из индекса немедленно.
2. **Обязательно запустить `qmd cleanup` после `remove`** — сам `remove` оставляет orphaned embedding-хеши в БД (не мешают работе, но занимают место); `cleanup` делает vacuum + очистку кэша, приводит `qmd status` к точному числу векторов.
3. Удалить filter-farm директорию, если была (`rm -rf ~/.local/share/qmd-collections/<name>`).
4. Убрать строку из таблицы коллекций в плане.

## Производительность и решение по reranking (09.07.2026)

Реальные замеры на CPU-only VM (4 vCPU Xeon Gold 6150, без GPU, 568 файлов, 3134 вектора):

| Режим | Время | Что даёт |
|---|---|---|
| `qmd search` (BM25) | ~0.3с | Точные термины/имена |
| `qmd vsearch` (vector only) | ~4с | Семантическое сходство, без реранжирования |
| `qmd query --no-rerank` (BM25+vector+expansion) | ~5-18с | Хороший компромисс качество/скорость |
| `qmd query` (полный, LLM-reranking) | **~558с (9+ мин)** | Лучшее качество, неприемлемо медленно на CPU |

**MCP-инструмент `mcp_qmd_query`** принимает булев параметр `rerank` (default `true` в схеме) — не отдельные search/vsearch tools.

**Решение: rerank делаем сами, без встроенного LLM-reranker qmd и без внешнего API:**
- **`rerank: false` по умолчанию** для всех MCP-запросов — для точечных фактов (имена/термины, типичный класс запросов) качество не страдает (5/5 тестов, score 72-96%)
- **Стандартный запрос (3-5 кандидатов)** — Sirene читает и синтезирует ответ инлайн, бесплатно, без отдельного вызова — это и есть фактическое переранжирование
- **Широкий запрос (>10 кандидатов, `candidateLimit: 20-40`)** — фильтрацию делегировать **Haiku через `delegate_task`**: сырые сниппеты + вопрос пользователя → топ-5. Экономит контекст основного диалога, дёшево (роль Haiku по Блоку 6Б `hermes-feature`)
- **Не строить кастомную интеграцию с внешним rerank API** (Cohere/Voyage/Jina, ~$2/1M токенов) — Sonnet/Haiku уже делают то же самое (оценка релевантности пары запрос+документ) без доп. инфраструктуры
- `rerank: true` — редкий ручной fallback, никогда не default на CPU-only машине

**Reranking нельзя вынести в фоновую/ночную операцию** (в отличие от embedding). Embedding зависит только от содержимого документа — можно посчитать заранее (это делает `qmd embed` в кроне). Reranking оценивает релевантность пары (конкретный запрос + кандидат) — без знания запроса заранее считать нечего.

**qmd не поддерживает внешний rerank API** — reranker жёстко зашит на локальную GGUF-модель через `node-llama-cpp`, нет флага/переменной для облачного rerank. Только `QMD_EMBED_MODEL` даёт выбор среди локальных embedding-моделей (не rerank). Если понадобится полный `rerank:true` в будущем — GPU на машине или кастомная надстройка поверх топ-N кандидатов, отдельная задача.

## Common Pitfalls

1. **qmd НЕ резолвит симлинки** (`fast-glob` не следует по `ln -sf`) — `qmd collection add` на директории с симлинками вернёт "No files found matching pattern" (0 файлов). Использовать copy-based filter-farm (`rsync`/`cp`), см. раздел выше. Не полагаться на недокументированные `--exclude`/`--include` флаги qmd — не описаны в SKILL.md, поведение не подтверждено.
2. **`npm install -g @tobilu/qmd` может упасть на компиляции native-биндингов** (`node-llama-cpp` тянет за собой сборку через `cmake`, если прекомпилированный бинарник не подходит под окружение). На минимальной установке ОС без `cmake`/`g++` — установка падает молча, оставляя битый симлинк в `~/.local/bin/qmd`. Фикс: `sudo dnf install -y cmake gcc-c++` (`apt install cmake g++` на Debian/Ubuntu), удалить битый симлинк, повторить установку. Актуально для любого npm-пакета с native-биндингами, не только qmd.
3. **На VM могут быть два независимых Node.js** — проверять фактически (`which node`, `which npm`, `npm config get prefix`) перед хардкодом пути к бинарнику в systemd unit/крон-скрипте, не полагаться на путь, который "кажется логичным".
4. **`hermes mcp add <name> --url <url>` требует интерактивного диалога** ("Does this server require authentication?", "Enable all N tools?") — не поддаётся прямому неинтерактивному запуску, нет флагов `--yes`/`--no-auth`. В cron-сессии виснет на первом промпте. Фикс — передать ответы через stdin: `printf "n\ny\n" | hermes mcp add qmd --url ...`. Выполнять вручную с реальным терминалом, не поручать cron-субагенту без проверки stdin.
5. **Systemd unit + собственный `--daemon`-флаг инструмента = конфликт.** Если у CLI-инструмента есть свой флаг самодемонизации (`qmd mcp --http --daemon`) — не комбинировать с systemd `Type=simple`: инструмент форкается в фон, foreground-процесс завершается exit 0, systemd считает сервис завершённым и убивает весь cgroup вместе с daemon-процессом (`curl` вернёт `000`). Фикс: убрать флаг самодемонизации из `ExecStart`, оставить в foreground — systemd сам управляет процессом (`Restart=on-failure`).
6. **Первый `qmd embed` на CPU может занять кратно дольше плановых 5-20 мин** — на 568 файлах реально ушло ~87 минут (несколько последовательных запусков батчами). Закладывать в план больше времени на CPU-only железе, не ожидать GPU-скорости.
7. **Не индексировать разнородную папку целиком** (черновики+финалы, summary+transcript) — см. раздел Filter-farm выше; полная индексация даёт RAG равный доступ к материалам разной надёжности, устаревший черновик может перевесить актуальный финал.
8. **qmd не подходит для exhaustive-запросов "все X от Y за период Z"** (проверено экспериментом 09.07.2026: запрос "какие задачи ждёт от меня Аралов за последние 2 недели" — из 8 реально релевантных встреч за 24.06–08.07 qmd в топ-60 из `candidateLimit=200` кандидатов вернул только 2, остальные 6 не попали вообще, включая самые свежие 07.07/08.07). Причина: qmd ранжирует по BM25+vector релевантности текста запроса, не по дате — упоминание "июль 2026" в тексте vec-запроса не работает как дата-фильтр, потому что даты в имени файла не участвуют в индексируемом тексте коллекции `meetings-summary`. Не пытаться "намекнуть" на период текстом запроса — это не фильтр, а иллюзия фильтра. Правильный пайплайн — см. раздел When to Use выше (пре-фильтр по дате в имени файла, потом чтение/qmd внутри уже суженного набора). Сырой лог сравнения grep vs qmd на этом примере — `references/qmd-vs-grep-exhaustive-query-example.md`.
