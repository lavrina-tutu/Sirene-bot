# Команды ручного процесса

## Подготовка и карточка

Используй существующее хранилище `/home/tkachenkoav/.hermes-kanban-manual`, доску `dev-manual`, DB в `kanban/boards/dev-manual/kanban.db`; доску не пересоздавай и окружение не устанавливай глобально для gateway. До работы проверь отсутствие gateway, dispatcher и daemon на этом хранилище. CLI `list` пересчитывает готовность, открытие хранилища может писать служебные данные: просмотр не гарантированно чистое чтение. В операторской сессии при унаследованных `HERMES_KANBAN_TASK`, `HERMES_KANBAN_RUN_ID`, `HERMES_KANBAN_DB` или иных worker-привязках перейди в обычную операторскую сессию, не очищая окружение worker для обхода ограничений.

```bash
kb_manual() {
  env HERMES_KANBAN_HOME=/home/tkachenkoav/.hermes-kanban-manual \
    hermes kanban --board dev-manual "$@"
}
```

Функция только сокращает команду. Заполни переменные и выполни [подготовку до claim](quickstart.md#подготовка-до-claim). Создание с реальным телом и уникальным ключом:

```bash
kb_manual create "[$WORK_ID] $PHASE — $TITLE" \
  --body-file "$CARD_BODY" --workspace "dir:$WORK_ROOT" \
  --tenant "$WORK_ID" --initial-status blocked \
  --completion-contract local-only \
  --idempotency-key "$CARD_KEY" --created-by sirene --json
```

Для следующей фазы добавь `--parent "$PREVIOUS_ID"` для каждого обязательного предшественника; первую создавай без родителя. Сохрани возвращённый `TASK_ID` и проверь `show`; после неопределённого исхода сначала ищи существующую карточку. Не применяй несуществующие для create параметры `--phase`, `--role`, `--labels`, `--metadata`. Фактический автор может отличаться от `sirene`. План и REV — родители решения о плане, решение — родитель реализации, тесты и итоговая REV — родители приёмки. Для решений Codex не запускается: после получения решения используется учётный цикл unblock → claim → проверка решения → complete.

## Запуск и проверка

После подготовки выполняй команды по отдельности, проверяя результат каждой; при ошибке не продолжай:

```bash
kb_manual show "$TASK_ID" --json
kb_manual comment "$TASK_ID" --author sirene "$START_BASIS"
kb_manual unblock "$TASK_ID" --reason 'Основание и подготовка проверены'
kb_manual claim "$TASK_ID" --ttl 14400
kb_manual show "$TASK_ID" --json
```

Проверь `running`, каталог, входы, основание, зависимости и отсутствие другого живого запуска. `claim` не запускает и не регистрирует внешний Codex как worker; TTL четыре часа не останавливает процесс, не разрешает повтор и не доказывает сохранение владения. Истечение TTL или неизвестный исход требуют сверки. Не используй `--force` или `reclaim` для обхода сообщения о живом worker.

Непосредственно перед запуском ещё раз проверь свободность трёх выходов: проверка до claim их не резервирует. Модель и effort должны совпадать в карточке, постановке и команде. Для плана и всех REV: `gpt-6-astra`, `high`, `read-only`, `WORK_ROOT=TASK_ROOT`; для реализации и тестов — адресное назначение (в пилоте `gpt-6.1-terra`, `high`, `workspace-write`), `WORK_ROOT=EXEC_ROOT`. При отсутствии адресного назначения сверяй общий YAML. При недоступности модели остановись, не меняй модель, backend или effort.

```bash
codex exec -C "$WORK_ROOT" -m "$MODEL" \
  -c 'model_reasoning_effort="high"' \
  --sandbox "$SANDBOX" --skip-git-repo-check --json \
  --output-last-message "$REPORT" - \
  < "$PROMPT" > "$JSONL" 2> "$STDERR_LOG"
ROLE_RC=$?
```

`--workspace "dir:$WORK_ROOT"` и `codex -C "$WORK_ROOT"` обозначают один физический каталог. Роль в `read-only` не пишет файлы; выход `--output-last-message` сохраняет запускающий CLI. Если роли необходимы записи вне `EXEC_ROOT`, перечисли и согласуй их и только тогда используй `--add-dir`; `workspace-write` сам по себе не ограничивает список файлов внутри каталога, проверяй фактические изменения.

После завершения установи rc, проверь непустой пригодный отчёт, входы, область, критерии и вердикт с хешами. Для тестов и REV проверь [версию кандидата](records.md#версия-кандидата-тесты-и-rev). Не считай один rc=0 или файл достаточным доказательством. Вычисли хеш и запиши факты до завершения:

```bash
sha256sum "$REPORT"
kb_manual comment "$TASK_ID" --author sirene "$RESULT_FACT"
kb_manual complete "$TASK_ID" --result "$RESULT" --summary "$SUMMARY"
kb_manual show "$TASK_ID" --json
```

`complete --metadata` допускает JSON фактов попытки. Не соединяй Codex и complete через `&&`. При проблеме вместо успешного завершения следуй процедуре остановки.

## Исправление и повторная ревизия

Сохрани отчёт REV, замечания, входные хеши, запиши вердикт и заблокируй REV с `needs_input`. Проверь, что разрешение охватывает исправление; если требования изменились или случай исключён, останови ветку по [границе скилла](../SKILL.md#граница). Создай отдельную карточку исправления с родителем — завершённой исходной фазой, не заблокированной REV. Исправление плана делает архитектор, реализации — исполнитель. Результат проверь и заверши; новая реализация получает новую версию кандидата.

План: исправленный `HF:plan → повторная REV:plan`. Реализация: исправленный `HF:impl → отдельная новая карточка и запуск HF:test → повторная REV:report`. Родитель теста — исправление; новые prompt, отчёт и журналы; тесты обязаны подтвердить новую версию. При FAIL, отсутствии отчёта или несовпадении остановись. Только после успешных тестов добавь исправление и тест как обязательные входы существующей заблокированной REV (для плана только исправление):

```bash
kb_manual link "$FIX_ID" "$REV_ID"
kb_manual link "$TEST_ID" "$REV_ID"
```

Вторую команду выполняй только для реализации. Проверяй результат каждой. Запиши новые входы, хеши и `review_round: 2` в комментарий и новый prompt; для реализации — версию кандидата и хеш нового тестового отчёта. Затем отдельно `unblock → claim` и вызов ревизора. REV при отсутствии совпадения или обязательных PASS выдаёт `REQUEST-CHANGES`. При APPROVE заверши REV; обнови входы приёмки: последняя реализация, новый тест и итоговая REV, при необходимости добавив тест через `link`. Старый тест остаётся историей и не подтверждает новую версию.

Допустим один круг исправления на поручение и предмет проверки. Второй `REQUEST-CHANGES` — `REVIEW-LIMIT`, остановка и разбор владельца; ни новый ID, ни новая сессия не обнуляют счёт. Сохраняй первоначальные отчёты. Новый согласованный предмет сохраняет связь с историей.

## Остановка и неизвестный исход

При ERROR, STOP, CANCEL, потере связи или ошибке записи сначала зафиксируй доступные [факты](records.md#отчёты-и-остановка), прекрати продвижение и заблокируй применимую карточку:

```bash
kb_manual comment "$TASK_ID" --author sirene "$STOP_FACT"
kb_manual block "$TASK_ID" --kind needs_input 'Работа остановлена; причина и условие продолжения записаны.'
kb_manual show "$TASK_ID" --json
```

Если карточка уже blocked, запиши факт и проверь статус, не разблокируй ради повторного block. Для человеческого ожидания не используй `--kind dependency`: завершение родителей может открыть карточку. При `triage` остановись для разбора, не используй `specify` или `decompose` для очистки состояния. При ошибке Kanban не считай статус изменённым.

`block` не останавливает внешний процесс. Определи нужный Codex по PID, времени, каталогу, команде и сессии; останови через исходный терминал или сигналом точному процессу, проверь завершение и известных потомков, прекращение наблюдаемых записей и запиши результат. Не завершай массово все процессы Codex. Проверка PID не доказывает отсутствия скрытых потомков или отмены запроса у провайдера. При неизвестном состоянии новый запуск запрещён процедурой.

Готовый результат после обрыва допустимо принять без вызова, если завершение и пригодность подтверждены, а разрешение не отозвано; частичный файл и rc=0 этого не доказывают. Повтор только по новому явному решению владельца на конкретную попытку с причиной, новыми обстоятельствами и ссылкой на прежнюю; неизвестный прежний процесс не основание для повтора. Никаких автоматических retry, resume, fallback или смены модели. При CANCEL завершённые карточки сохранить как историю, незавершённые заблокировать или оставить blocked с отметкой `ОТМЕНЕНО`; не архивировать предшественника для обхода зависимостей.
