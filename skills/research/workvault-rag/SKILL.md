# WorkVault — поиск по MD-заметкам (встречи, ТЗ)

## Overview

Поиск по WorkVault (Obsidian MD-заметки: встречи, ТЗ, Confluence) через прямую работу
с файловой системой — `search_files` (по имени файла/содержимому) + `read_file`.
**qmd (semantic search MCP) исключён из системы 16.07.2026** — был ненадёжен (CPU-only
эмбеддинг, частые "LLM session expired" сбои индексации, зависания по 300с таймауту на
простых запросах в рантайме) и оказался избыточен: файловый поиск по имени+дате
справляется с реальными запросами Саши быстрее и надёжнее. См. `references/qmd-retired-2026-07-16.md`
для истории и rollback-инструкции, если semantic search когда-то снова понадобится.

## When to Use

Триггер срабатывает на любой из этих типов запроса:

- Вопросы про **встречи**: "что обсуждали с X", "какая была встреча про Y", "когда говорили про Z"
- Вопросы про **задачи/поручения**: "какие задачи ждёт от меня X", "что я обещал сделать", "что поручили Y"
- Вопросы про **решения**: "что решили по X", "какое было решение насчёт Y"
- Вопросы про **риски/блокеры**: "какие риски по X", "что блокирует Y"
- PM Briefing в начале сессии — «что важного по проектам?»
- Поиск по 1000+ файлам NewMeetings без явных ключевых слов

## Алгоритм поиска по встречам (структурные запросы: дата/участники/проект + тип сущности)

Применять к любому запросу вида "какие [задачи/решения/риски/блокеры] по [X/за период Y]".

### Шаг 1 — период

- Дата/период явно указан в запросе ("с 16.06", "за последние 2 недели", "в июне") → фильтр списка файлов по дате в имени файла (`YYYY-MM-DD HH-MM-SS ...`) на этот период.
- Период не указан → по умолчанию последние **6 месяцев**.
- Фильтрация по дате — через `search_files(target="files")` по паттерну имени, отсортировано по времени изменения.

### Шаг 2 — участники

- Человек назван в запросе ("что обещал Аралов", "что мы обсуждали с Х") → из набора шага 1 оставить только встречи, где этот человек указан в секции **"Участники:"** файла (точное совпадение в списке участников, не любое упоминание имени по всему тексту — упоминание "в контексте" даёт слишком много шума).

### Шаг 3 — проект/тема

- Проект/тема назван в запросе ("по ML-платформе", "по мультиагентной системе") → из набора после шагов 1-2 оставить только встречи, где проект упоминается в тексте (заголовок встречи или содержимое).
- **Канонический реестр сущностей (EntityRegistry, 16.07.2026) — `WorkVault/Registries/entities.json`.** Это единый источник правды по проектам/сущностям, из которого читают PFS (`ROUTES`), TaskRefresh (`ProjectRegistry.load()`) и этот скилл. Схема: `{slug: {kind, parent, display_name, aliases, pfs?}}` — `aliases` (регистронезависимо) заменяет прежнее `name_match`; `parent` даёт иерархию (`cu → devrel`); наличие блока `pfs` означает, что у сущности есть Confluence-протокол (без него сущность просто видна для поиска, но не попадает в ROUTES). Полная схема — `WorkVault/Registries/README.md`.
- **Порядок матчинга проекта/темы в запросе или названии встречи:**
  1. Прочитать `WorkVault/Registries/entities.json` (file-tools).
  2. Пройти по `entities[*].aliases` регистронезависимо — startswith/substring, как в `route.py:_match_by_name` (тег с точкой в конце — startswith; свободный алиас — substring).
  3. При множественных матчах — приоритет по `kind`: `project` > `multisync` > `one_on_one` > `unknown` > `tool`. При остающейся неоднозначности — спросить Сашу.
  4. Если сущность найдена и у неё есть `parent` — при запросе про родителя («что по DevRel») подниматься по цепочке и собирать все дочерние (`devrel` → `cu`, потенциально `+ omd`).
  5. Если совпадения нет — прямо отметить Саше: «проекта нет в реестре entities.json, кандидат на добавление» (одна правка одного файла).
- Питфолл: «AB-платформа» может значить старую ТУТУ или новую Trisigma — реестр разруливает это отдельными slug'ами `trisigma` / `ab_platforma` с общим `pfs.page_id`, но разными `pfs.tag`. Не угадывать по контексту — сверяться с `aliases`.
- Актуальные `kind=project` записи (без `pfs` — новые, добавленные 16.07.2026): `devrel`, `cu` (parent=devrel). `omd` — `kind=tool`, самостоятельная запись, aliases=`["omd","openmetadata","кумд"]`.

### Шаг 4 — извлечение сущностей

Работать с финальным отфильтрованным набором файлов:
- **Если файлов >10** — не читать все инлайн: делегировать Haiku (`delegate_task`, таймаут 120с) — сырые Action Items/Риски/Решения из всех файлов набора + вопрос Саши → отфильтрованная выжимка.
- **Если файлов ≤10** — читать напрямую (`read_file`), без делегирования.
- **4.1 Запрошены НЕ задачи** (решения / риски / блокеры) → выдать все найденные сущности этого типа из всех файлов набора, без дополнительной фильтрации по назначенному лицу.
- **4.2 Запрошены задачи** → выдать только Action Items, где ответственный явно указан как один из упомянутых участников (точное имя в строке Action Item, не implicit-отнесение по контексту). Если Саша спрашивает про себя ("что мне поручили") — те же правила, явное указание его имени в Action Item.

### Быстрый путь для "последняя встреча с X" (без структурного фильтра по датам/сущностям)

Для запроса вида "что от X ожидается на встрече", "что решили с X в последний раз" —
не нужен весь 4-шаговый алгоритм, достаточно:
1. `search_files(pattern="*<Имя>*", target="files", path="WorkVault/Meetings/NewMeetings")`
2. Отсортировать по дате в имени файла, взять самый свежий `... - summary.md`.
3. `read_file` этого файла напрямую — саммари уже содержит структурированные секции
   (Участники/Решения/Задачи/Риски/Блокеры), доп. поиск не нужен.

Это единственный путь для такого класса запроса (не первая попытка) — не пытаться сначала
искать через MCP semantic search инструменты, если они появятся снова в будущем.

### Путь для "как менялась постановка X во времени" (эволюция темы, не срез на одну дату)

Отдельный класс запроса от 4-шагового алгоритма выше — там нужен ОДИН отфильтрованный набор
файлов для точки во времени; здесь нужна **упорядоченная последовательность** файлов, чтобы
показать, как формулировка/скоуп менялись между встречами.

1. Собрать набор файлов через Шаги 1-3 обычного алгоритма (период — если не указан, не сужать
   до 6 месяцев по умолчанию, брать всю историю проекта, раз явно спрошена эволюция; проект —
   по `aliases` записей `entities.json`, см. Шаг 3 выше).
2. **Отсортировать по дате в порядке возрастания** (не по релевантности, не по убыванию) — цель
   показать хронологию, а не последнюю встречу первой.
3. Для каждого файла — вытащить именно раздел про постановку задачи/цель/скоуп (не весь Action
   Items/Риски), одной короткой цитатой или перефразировкой с датой встречи.
4. Собрать в один ответ как таймлайн: `YYYY-MM-DD — <как формулировали на тот момент>`, явно
   отмечая точки, где формулировка/скоуп изменились, а не просто список всех упоминаний подряд.
5. Тот же путь применим к запросам "человек+дата+тема" ("что обсуждали с X в декабре, когда
   ставили Y") — сначала Шаг 2 (участник) сужает набор, затем этот путь вместо обычного Шага 4.

## Признак "неясная запись / переговорка"

На встречах в переговорках (особенно мультисинки и 1-1, где несколько человек говорят в одной комнате) Fireflies часто **неверно атрибутирует Action Items конкретному спикеру** — разметка голосов даёт сбой. Такие задачи **лучше по умолчанию относить к самому Саше** ("мои задачи, разберу вручную далее"), а не к тому, кому их формально приписал Fireflies.

**Признаки "неясной записи" (совпадение любых 2 из 3 = считать неясной):**
1. Файл встречи — загрузка аудио/видео (`.m4a`/`.mp4` фигурирует в названии файла) — то есть запись с диктофона/телефона в переговорке, не прямая интеграция с онлайн-звонком.
2. Action Items в summary не содержат чёткого разделения "Имя: задача" — общий список без явного автора.
3. Название встречи совпадает с известным названием переговорки ТУТУ — актуальный список переговорок в `WorkVault/Contacts/meeting-rooms.md` (обновляется вручную запуском `orglookup rooms`, `~/USERTOOLS/OrgLookup`). При использовании этого признака проверить дату `updated:` в frontmatter файла на актуальность.

При совпадении признаков — такие Action Items помечать как задачи Саши, а не оригинального (возможно ошибочного) адресата, и явно указывать в ответе, что источник — запись из переговорки/неясная атрибуция, требует ручной проверки.

## Использование MOFS-разметки при поиске (17.07.2026)

**Принцип:** поиск по встречам/задачам ведётся с учётом того, что MOFS уже разметил в frontmatter, а не только по свободному тексту. Однако в переходный период (пока `bootstrap --undo` баг не починен и бутстрап ещё не выполнен) реального тегирования в frontmatter нет.

**Карточки-агрегаторы** `WorkVault/Projects/<slug>.md` (Dataview backlinks) — основная точка входа для запросов по проекту, когда бутстрап уже выполнен. Если карточка существует — читать её вместо grep по всем файлам: быстрее и точнее.

**Переходный период (нет бутстрапа):** `projects`/`tools`/`rooms`/`contacts` во frontmatter пустые (`[]`). В этом случае — использовать только Шаги 1-3 алгоритма (дата/участники/проект по тексту тела), Шаг 4 по frontmatter не работает. Явно не сообщать Саше «нет матчей» — сначала проверить тело файла.

**Признак нетегированного архива:** `projects: []` и `tools: []` в frontmatter при ненулевом содержимом тела = MOFS не запускался или бутстрап ещё не применён, не ошибка данных.

## Архитектура поиска v2 — три режима одного скилла (21.07.2026)

Единый скилл `workvault-rag` покрывает три режима — глубину определяет характер вопроса:

| Вопрос | Режим | Источник | Время |
|---|---|---|---|
| «Какие встречи по ML в июле?» | Поиск | SQLite+FTS5 (`mofs index`) | <10 мс |
| «Что решили на встрече 10 июля?» | Детали | `summary.md` конкретной встречи | <1 сек |
| «Кто реально что сказал про ML?» | Транскрипт | `transcript.md` → LLM | <5 сек |

**Связь summary↔transcript** — детерминированная, замена суффикса:
```
2026-07-08 11-05-00 Кирилл 1-1 - summary.md
2026-07-08 11-05-00 Кирилл 1-1 - transcript.md
```
Хранить ссылку во frontmatter не нужно — вычисляется на лету.

**`mofs index`** — SQLite+FTS5 индекс, живёт в `~/USERTOOLS/MofsIndex/state/index.sqlite`.\nИндексирует: frontmatter (4 корзины slugs + date) + тело summary + тело transcript.\nОбновляется: хук в конце `mofs run`/`mofs rematch` (только real-mode, не dry-run).\nТЗ: `WorkVault/Hermes-Backlog/TZ/MofsIndex/MofsIndex_TZ.md` v0.1.0.\n\n**⚠️ Реальная польза mofs index (22.07.2026, подтверждена практикой):**\n- **Хорошо работает:** поиск встреч по slug проекта (нашёл 9 встреч ML-платформы за июль мгновенно). Поиск по тексту тоже работает — `search_meetings(query='отпуск')` нашёл 18 встреч с упоминанием.\n- **Слабое место — contacts:** frontmatter `contacts` заполнен только у ~50% встреч за июль 2026 и практически пуст в архиве до июля. Поиск `search_meetings(slugs={'contacts': ['Гладких Юрий']})` возвращает неполные результаты — нужно дополнять grep по тексту саммари.\n- **Практический вывод:** для поиска «кто что сделал» или «что обсуждали с N» — сначала индекс (список встреч по проекту/дате/тексту), потом grep по телу саммари и транскриптам для конкретных строк.\n\n**Ripgrep (grep по файлам)** при наличии mofs index — НЕ замена, а дополнение для другого класса запросов:
- `mofs index` → «какие встречи по теме X» — возвращает список встреч (meeting_id + title)
- `grep` → «какие именно строки говорят про X» — возвращает точные цитаты с контекстом из файлов

Когда нужны точные формулировки (например «что именно обсуждали про отпуск» → нужна строка «Криворотов планирует взять отпуск 20-26 июля»), grep по `*summary*` эффективнее:
```bash
grep -rn -i 'КЛЮЧЕВОЕ_СЛОВО' \
  '/home/tkachenkoav/WorkVault/Meetings/NewMeetings/' \
  --include='*2026-07*summary*'
```
Для широкого архивного поиска без фильтра по дате — сначала `search_meetings(query=...)` чтобы получить список файлов, затем grep только по ним.

Читать контекст вокруг найденной строки транскрипта (±15 строк от номера N):
```bash
sed -n '$((N-15)),$((N+15))p' '/path/to/transcript.md'
```

**НЕ создавать отдельные скиллы** `workvault-search` / `workvault-deep` — всё в одном `workvault-rag`.
Три режима определяются характером вопроса внутри скилла, не переключением между скиллами.

## Архитектурное решение: связи/wiki-links, не векторный RAG (16.07.2026)

Когда встаёт вопрос «как ещё улучшить качество/скорость поиска по WorkVault» — ответ **structural links (Obsidian wikilinks + Dataview + canonical entity registry), не переход на векторный RAG/semantic search**. Не переоткрывать этот вопрос с нуля каждый раз, если не появилось принципиально новое обстоятельство:

1. **qmd (semantic search) уже пробовали и отключили** (см. выше, 16.07.2026) — ненадёжен на практике (CPU-only эмбеддинги, сбои индексации, таймауты), не гипотетический недостаток.
2. **Основная причина, по которой обычно тянутся к RAG — «найти релевантное без точного текстового совпадения»** — у нас закрывается ДЕШЕВЛЕ через `entities.json` (canonical aliases устраняют неоднозначность текстового совпадения без единого эмбеддинга) и через wiki-ссылки/backlinks (Obsidian graph показывает связи «встреча ↔ проект» нативно, без агента).
3. **`MarkObjectsFromSummary` v0.2 (когда будет написан) — правильное место для проставления project-wiki-ссылок** в frontmatter встреч, тем же механизмом, что уже работает для контактов (v0.1). Тогда «эволюция постановки задачи во времени» решается через Obsidian backlinks + сортировку по дате, а не через агента, гоняющего Haiku по десяткам файлов при каждом запросе.
4. Готовое масштабируемое сравнение (тулинг RAG vs связи) — библиотечные скиллы `langchain-rag` (генерик RAG-пайплайн, требует эмбеддинги+векторную БД — тот же класс проблем, что и отключённый qmd) и `obsidian-vault` (простой grep+wikilinks, ближе к нашему подходу, но без структурных фильтров дата/участники/тип-сущности) — оба разобраны и отклонены в пользу уже работающего `entities.json`+4-шагового алгоритма этого скилла.

## Верхнеуровневая связь с EntityRegistry↔MOFS/AFM

Полное архитектурное решение по стыковке `entities.json` с `MarkObjectsFromSummary`/`AggregateFromMeetings` (naming-конфликт слугов, устав vs протокол-страница, двойная классификация типа «Метротека = проект и инструмент», 4 корзины при массовом NER-прогоне архива: люди/сущности/инструменты/переговорки) — см. `about_usr_skills`, секция «EntityRegistry ↔ MarkObjectsFromSummary (MOFS) / AggregateFromMeetings (AFM)».

## Алгоритм поиска через mofs index (быстрый путь, приоритет над grep)

Использовать ПЕРВЫМ при любом структурном запросе (slug/дата/текст). Fallback на grep — только если индекс не построен.

### Режим 1 — поиск встреч (список)

```python\n# Правильный импорт (после editable install фикса 22.07.2026):\nimport sys\nsys.path.insert(0, '/home/tkachenkoav/USERTOOLS/MofsIndex')\nfrom mofs_index.searcher import search_meetings\nfrom mofs_index.searcher import get_meeting, get_transcript_snippets  # если нужны\n# Альтернативно (если пакет правильно установлен):\n# from mofs_index import search_meetings  — может работать после pip install -e

# По slug проекта
hits = search_meetings(slugs={'projects': ['kirill_1on1']}, limit=20)

# По дате + slug
hits = search_meetings(
    date_from='2026-07-01', date_to='2026-07-31',
    slugs={'projects': ['ml_platforma']},
)

# По FTS-тексту + дата
hits = search_meetings(query='DWH метрики', date_from='2026-06-01')

# По контакту
hits = search_meetings(slugs={'contacts': ['Криворотов Кирилл']})

## Verification Checklist

- [ ] Структурный запрос (дата/участник/проект + сущность) прошёл 4-шаговый алгоритм, не угадан на глаз
- [ ] Проект/тема матчились по `aliases` записей `WorkVault/Registries/entities.json` (EntityRegistry), не по интуитивному текстовому совпадению — если проекта нет в реестре, это явно отмечено Саше
- [ ] Запрос "как менялась постановка X" / "что обсуждали в [дата], когда ставили Y" — файлы отсортированы по возрастанию даты (хронология), не по релевантности/убыванию
- [ ] Широкий запрос (>10 файлов) — фильтрация делегирована Haiku, не читается инлайн Sonnet целиком
- [ ] "Неясная запись" — при совпадении 2+ признаков задача отнесена к Саше, источник явно помечен
- [ ] Не предлагать/не пытаться восстанавливать qmd без явного запроса Саши
- [ ] При структурном запросе (slug/дата) — использовать `mofs index` через `search_meetings()` как первый путь; fallback на grep только если индекс не построен (`mofs-index verify` покажет)
- [ ] `MeetingHit` — dataclass, не dict. Использовать `h.meeting_date`, `h.title`, `h.meeting_id` — НЕ `h.get('...')` (AttributeError)
- [ ] Запрос «кто что сказал / детально что обсуждалось» — читать `transcript.md` (суффикс `-transcript.md` вместо `-summary.md`), не summary; LLM отвечает по тексту транскрипта
- [ ] Contacts заполнены только для встреч с июля 2026 и тех старых, где есть раздел «Участники». Для архива до июля без раздела «Участники» — contacts пустые. Не считать пустой contacts признаком бага — это ожидаемое состояние архива до backfill. При поиске по человеку — дополнять grep по тексту саммари.
- [ ] Если ответ на вопрос не найден в summary — проверить transcript, прежде чем сообщать «не нашла». Саммари часто не фиксирует мотивацию/контекст решений, только сами решения.
