# Пересмотр плана/фазы через invoke-role: сжатый вход, sidecar, recover

Три факта, которые стоят дороже всего при переоткрытии фазы пересмотра (например, MIG:plan после новых требований владельца).

## 1. Большой вход умирает по жёсткому потолку 3600 с в codex-субпроцессе invoke_role.py

- Кодекс-субпроцесс `invoke_role.py` имеет жёсткий лимит **3600 с**; пересмотр плана с большим входом (ТЗ + план + директива на десятки КБ) умирает `TimeoutExpired` с exit 1 **даже в background**, ничего не записав. Потолок — свойство рантайма invoke, не роли.
- Последствие: фаза остаётся WORK с мёртвым pid, артефакт не написан. Повторный invoke тем же большим пакетом упрётся в тот же 3600 с — повторы не лечат.
- Лечение, не зависящее от модели: **сжать вход** — отдавать роль не полный дамп, а директиву владельца + сжатое изложение сути требований/фактов, и давать `--workspace`, чтобы роль сама дочитывала недостающее из файлов. Полный ТЗ/план в packet не тащить.
- Проверять разумность входа ДО запуска: если промпт-файл килобайты-воды и планируется долгая работа — сжимать, а не считать, что фон спасёт.

## 2. invoke-role на рукописном prompt-файле падает с sidecar-ошибкой

- `invoke-role --prompt-file <файл>` требует рядом `<файл>.packet.json` — sidecar создаёт **только** `emit-prompt`.
- Рукописный промпт (вручную собранный task.md без emit) даёт мгновенный `[Errno 2] No such file or directory: '<файл>.packet.json'`, exit 1, роль не стартует. Это НЕ сбой фазы и не dead-pid — неверный способ запуска.
- Правильная последовательность для пересмотра: repair-writer'ом переоткрыть фазу-владельца (WORK / awaiting_invoke=True, стереть pid/receipt/proof) → **свежий `emit-prompt`** (создаст новый packet и заодно sidecar) → один background-invoke по этому emit. Промпт для invoke всегда брать из файла, который произвёл emit, не собирать самому.

## 3. recover --class dead-pid может отказывать «wrapper alive», пока умирающий wrapper виден в pgrep

- Механика: `_occupancy_refuse`/`occupancy_blocked` смотрит `invoke_wrapper_alive` (pgrep по строке команды invoke), а не только записанный pid — после TimeoutExpired умирающий wrapper висит в списке процессов короткое время.
- Признак: `recover` печатает `wrapper alive` и exit 1, хотя `pid_alive(<pid>)=False`, а фаза уже с мёртвым pid.
- Лечение: проверить фактическую чистоту occupancy ДО повторного recover (python: `invoke_wrapper_alive(slug)` / `occupancy_blocked(slug)` из `pipeline_gates` = False, pgrep пуст) и только тогда повторять recover. Непройденный recover state не трогает — повтор safe.
- Если и после чистоты pgrep recover упрямо отказывает — ставить фазу repair-writer'ом напрямую (WORK/awaiting_invoke=True), минуя recover; это штатный запасной путь, документированный в основном SKILL.md.
