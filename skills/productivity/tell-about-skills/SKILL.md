# Tell About Skills — рассказ о своих реальных возможностях

## Когда использовать

Саша спрашивает: «расскажи о себе», «что ты умеешь», «какие у тебя возможности»,
«чем ты можешь помочь по X» — и хочет услышать про **реально построенные под него
инструменты и процессы**, а не про общий каталог из 100+ generic-скиллов Hermes
(ascii-art, spotify, minecraft и т.п. — этого почти никогда не касаемся).

**Порядок приоритета в ответе:**
1. Наши собственные инструменты (USERTOOLS + ТЗ из MAIN_TZ_INVENTORY.md) — **первично**.
2. Наши доработанные/специфичные скиллы (tutu-*, movefrom-instruments, workvault-rag,
   pm-briefing, get-obsidian-link, tz-workflow и т.п.) — **вторично**.
3. Остальные generic-возможности Hermes «из коробки» — только если Саша спросит прямо
   («а ты можешь генерить картинки», «а с GitHub работаешь» и т.п.).

## Не хранить статичный текст — искать актуальные данные каждый раз

Инструменты и их статусы меняются (сегодня ProtocolFromSummary дошёл с draft до v1.1/active
за один день). Никогда не пересказывай зафиксированный в этом файле список версий как факт —
он устареет. Вместо этого при каждом вопросе:

### Шаг 1 — реестр инструментов (source of truth)

```
read_file("/home/tkachenkoav/WorkVault/Hermes-Backlog/TZ/MAIN_TZ_INVENTORY.md")
```

Таблица «Активные ТЗ» — это и есть список реальных инструментов с версией/статусом/датой.
Бери оттуда: MoveFromFF, AggregateFromMeetings, AnywhereContacts, ConfluenceSync,
DialogBacklog, ExchangeOrgLookup, MeetingScheduler, MoveFromJira, MoveFromZulip,
ProtocolFromSummary, SRTool, StatusSnapshot и др. — актуальный список именно оттуда,
не из памяти.

### Шаг 2 — детали конкретного инструмента, если Саша спросил про один

Прямое чтение `TZ/<Инструмент>/<Инструмент>_TZ.md` по пути из инвентаря — там всегда
есть история брифа с реальными решениями и договорённостями (не только финальный дизайн).
Если ТЗ большое — `search_files` по ключевому слову внутри файла вместо чтения целиком.

### Шаг 3 — наши скиллы

```
skills_list()
```
Отфильтровать на «наши» — категории и имена, привязанные к ТУТУ/WorkVault/нашим процессам:
`tutu-jira-okr`, `tutu-jira-sr`, `tutu-jira-contract-approval`, `tutu-confluence-jira`,
`movefrom-instruments`, `workvault-rag`, `pm-briefing`, `pm-requirement-review-simulator`,
`get-obsidian-link`, `obsidian`, `tz-workflow`, `multi-document-coordination`,
`check-cron-results`, `cron-journal-write`, `hermes-memory-hygiene`, `hermes-feature`,
`teams-meeting-pipeline`, `mpp-to-google-sheets`. Список меняется — не жёстко хардкодить,
можно опираться на признак: скилл описывает что-то специфичное про ТУТУ/Сашину работу
(упоминает Jira/Confluence/WorkVault/АИД/OKR/SR/протоколы встреч), а не про универсальный
внешний сервис (spotify, minecraft, github-*, ascii-*, creative-* и т.п.).

### Шаг 4 — примеры из реальных кейсов

Самое ценное в ответе — не абстрактное описание, а **конкретный пример из реального брифа**.
Источники примеров:
- `session_search(query="<тема>")` — найти реальный диалог, где обсуждался и разрабатывался
  инструмент, с конкретными деталями (например: «резолв участников через contacts.enc с
  fallback на Confluence API», «anchor-маркер переживает ручное редактирование Confluence»).
- Секции ТЗ вида «§1 Бриф-сессия», «§9 Вопросы для брифа», «§10 Решения» — там записаны
  реальные вопросы-ответы с обоснованиями, не сухие финальные формулировки.

## Формат ответа

1. Короткое общее резюме (2-3 предложения) — что за экосистема инструментов у Саши.
2. Список активных инструментов с ОДНОЙ строкой описания каждого (что делает, не как
   реализовано) — сгруппировать логически (MoveFrom*-семейство = выгрузка данных из
   корп.систем; Protocol/Aggregate = публикация протоколов встреч; tutu-jira-* = Jira-циклы
   SR/OKR/договоры).
3. Если вопрос про конкретную область — 1-2 живых примера из реальных брифов/сессий,
   с деталями (не «умеет резолвить участников», а «например, для протокола Кирилл 1-1 мы
   договорились, что переговорка в списке участников — не человек, задача на неё уходит
   на тебя как fallback-исполнителя»).
4. Только в конце, если спросят явно — упомянуть, что есть и другие generic-возможности
   (картинки, музыка, GitHub, и т.п.), не расписывая подробно, если не просили.

## Пример хорошего ответа (шаблон)

> У меня набор инструментов под твою работу — в основном вокруг встреч/протоколов и Jira/OKR:

> **Данные из корп.систем → WorkVault:** MoveFromFF (Fireflies), MoveFromJira, MoveFromZulip,

> конкретной встречи в Obsidian.

> Про что рассказать подробнее?

## Питфоллы

- Не пересказывать «из головы» версии/статусы — они меняются в течение одного дня работы
  (см. как ProtocolFromSummary прошёл draft→v1.1/active за один день брифа).
- Не путать «наш» скилл с generic — если непонятно, глянь описание: если оно про
  Jira/Confluence/WorkVault/АИД конкретно у Саши — наш, если про внешний сервис общего
  назначения — generic, упоминать по остаточному принципу.
- Если Саша спросил конкретно «а можешь X» — не отвечай общим списком, найди конкретный
  ответ (через шаги 1-4 выше), можешь ли реально это делать сейчас.
