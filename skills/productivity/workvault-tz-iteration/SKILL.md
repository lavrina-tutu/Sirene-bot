# WorkVault: итеративная правка пакета ТЗ-документов

Use this skill when the user delivers a numbered list of edits to one or more related ТЗ (Technical Spec) markdown files in `C:\Users\tkachenkoav\WorkVault\Meetings\` after a Q&A review round (often with Opus or another reviewer), and asks to «внести правки», «обновить ТЗ», «применить ответы на вопросы».

Triggers:
- "внеси правки в ТЗ ... на основе ответов на вопросы"
- "обнови файлы в WorkVault" + список нумерованных правок
- User cites a sibling Q&A / Brief file (e.g. `*_Brief_Questions.md`) and wants the answers propagated into the main spec
- Edits span 2-3 related files that must stay mutually consistent (main TZ + addendum + downstream TZ)

This is the documented form of a workflow the user runs often: spec → Q&A → batch edit → next round.

## Связанные навыки

- `obsidian` — общая работа с vault (читать/искать/писать заметки). **Этот skill дополняет его** для специфичного класса «синхронные правки набора ТЗ».
- `hermes-config-qa` — QA-проход через Opus перед коммитом изменений. Часто Q&A-раунд, который порождает правки этого skill'а, идёт через этот же механизм.

## Принципы

1. **Точечные правки, не переписывание.** Использовать `patch` mode='replace' с маленькими уникальными блоками. Не переписывать файл целиком даже если правок много — каждая правка отдельным патчем для трассируемости в diff.
2. **Синхронность между файлами.** Если правка про таймзону / схему / именование — она затрагивает ВСЕ файлы пакета (основное ТЗ + аддендум + downstream TZ). Не забыть ни один.
3. **Закрывать открытые вопросы.** Если файл содержит секцию «Открытые вопросы» / «Q1..QN» — обновить статус ответенных (`✅ Q2: ...закрыт: <решение>`), не удалять (история решения важна).
4. **Финальный sanity-check.** После всех правок прогнать `search_files` по «удалённым» терминам (старая таймзона, переименованные поля, устаревшие имена) — должно быть 0 совпадений.
5. **Отчёт по файлам с § ссылками.** В конце — структурированный отчёт: для каждого файла список изменённых разделов с номерами §. Пользователь так читает.

## Алгоритм

### Шаг 1. Прочитать все файлы пакета целиком
```
read_file(path) для каждого файла из списка пользователя
```
Не делать частичное чтение — нужен полный контекст для уникальности `old_string` в patch.

### Шаг 2. Сгруппировать правки по файлам
Перебрать список правок пользователя. Для каждой определить: какие файлы затрагивает (часто 2-3 одновременно из-за принципа синхронности).

### Шаг 3. Применить patch'и
Параллельные `patch` вызовы для независимых правок в РАЗНЫХ файлах — в одном tool block.
Последовательные правки в ОДНОМ файле — раздельными вызовами (race: повторный patch к тому же файлу сразу после первого может вернуть `Failed to read file` — см. Pitfalls).

### Шаг 4. Обновить «Открытые вопросы»
Если правки закрывают ранее открытые вопросы — обновить секцию `## Открытые вопросы` в основном ТЗ: `✅ QN: <вопрос> — закрыт: <решение>`.

### Шаг 5. Sanity-check
```
search_files(
  pattern="<удалённый термин 1>|<удалённый термин 2>|...",
  path="C:\\Users\\tkachenkoav\\WorkVault\\Meetings",
  file_glob="<маска пакета>"
)
```
Ожидаемый результат: `total_count: 0`. Если нет — найти и дочистить.

Типичные «удалённые термины» для проверки:
- Старая таймзона: `Europe/Moscow`, `\+03:00`, `MSK`
- Переименованные поля: `bullet_gist`, `shorthand_bullet` (FF Pro не имеет)
- Устаревшие enum'ы: `restored` в transfer_status

### Шаг 6. Отчёт
Структура (на русском, как ожидает пользователь):
```
## Отчёт

### 1. <filename1>.md — описание
- **§N (раздел):** что изменено
- **§M (раздел):** что изменено

### 2. <filename2>.md
...

### Проверка чистоты
Поиск по `<удалённые термины>` — **0 совпадений**.
```

## Pitfalls

- **`patch` race after success.** После успешного `patch` к файлу следующий `patch` к тому же файлу в том же tool block иногда возвращает `Failed to read file: ...`. Это не настоящая ошибка — повторный вызов в следующем tool block проходит. Решение: правки к одному файлу разносить по разным tool block'ам, либо просто повторить упавший patch.
- **Markdown table pipe escape.** В таблицах `|` внутри ячеек надо экранировать как `\|`. Особенно в столбце «тип» (`string \| string[] \| null`).
- **JSON примеры в .md — не запускать линт.** `patch` сам пропускает lint для `.md`, но если JSON-блок в коде синтаксически кривой — пользователь это заметит. Проверять глазами.
- **UTC ISO в примерах.** Если правка про переход на UTC — обновить НЕ ТОЛЬКО текстовые упоминания таймзоны, но и ВСЕ JSON-примеры в схемах реестра (`"+03:00"` → `"Z"`), и сдвинуть часы в примере (`14:30:00+03:00` → `11:30:00Z`).
- **«Не использовать X» — это правило, не предложение.** Если в правке сказано «использовать `Speaker {index}`, НЕ `speaker_id`, НЕ `Unknown Speaker`» — это explicit ban list, его надо записать в ТЗ дословно (с **жирным** «не»), иначе следующий разработчик не поймёт почему так.
- **Поля в нескольких местах.** Одно поле часто фигурирует в 3 местах одного ТЗ: таблица §13 (нормализация), JSON-схема §9 (реестр), enum / типы. При добавлении/изменении поля обновлять ВСЕ три точки.
- **Зеркальные ссылки между ТЗ.** Если правка пробрасывает обязанность из A в B (например «дальнейшая обработка keywords — в инструменте Y») — добавить пункт в обе стороны: в A («передаём в Y, см. ТЗ Y»), в B («принимаем X как входные данные, обработка такая-то»).

## Структура пакета ТЗ (типовая для WorkVault/Meetings)

- `<Tool>_TZ_v<N>.md` — основное ТЗ
- `<Tool>_TZ_v<N>.<M>_addendum.md` — аддендум с уточнениями (после Q&A)
- `<Tool>_Brief_Questions.md` — список вопросов для согласования
- `<Next-Tool>_TZ_v<N>.md` — ТЗ следующего инструмента в конвейере

Правки часто пробегают по всему конвейеру: изменение в producer (MoveFromFF) → синхронное изменение в consumer (MarkObjectsFromSummary).

## DoD (когда правки готовы к коммиту)

1. ✅ Все нумерованные пункты из запроса пользователя применены.
2. ✅ Кросс-файловая консистентность: одно поле/решение упомянуто одинаково во всех файлах пакета.
3. ✅ Sanity-check `search_files` по удалённым терминам = 0 совпадений.
4. ✅ Секция «Открытые вопросы» в основном ТЗ обновлена (закрытые помечены `✅`).
5. ✅ Отчёт по файлам с § ссылками отправлен пользователю.
