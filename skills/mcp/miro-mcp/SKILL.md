# Miro MCP — работа с досками

## Overview

Miro-доски читаются и правятся через MCP-инструменты `mcp__miro_mcp__*`. Ключевые принципы:
- **Никогда не читать доску целиком** — полный `canvas_read_as_svg` отваливается/обрезается (>~500 виджетов или >~100–230КБ вывода даже с persist). Большие фреймы читать **по квадрантам** или **точечно по `widget_ids`**.
- Считывание — свободно. Правка (создание/изменение/удаление элементов) — **только по явной команде Саши**, деструктив — с подтверждением.
- Логика работы с канвасом, диаграммами, таблицами задаётся в `canvas_get_canvas_composer_skill` (шаги `design`/`edit`) — перед правкой **обязательно** его запросить.

## Этапы работы с доской

### 0. Определи доску по URL
Доска идентифицируется URL вида `https://miro.com/app/board/uXjVMfOqP7M=/`. Инструменты принимают его в `miro_url`. Получить URL/имя можно через `board_search_boards` (поиск/список). **Внимание:** `board_search_boards` НЕ возвращает `modified_at`/`created_at` — определить «последнюю правленную доску» по нему нельзя (все поля null). За свежестью иди в ленту Miro или спроси название/ссылку.

### 1. Обзор структуры — `canvas_search(miro_url, result_mode="overview")`
Даёт список контейнеров (фреймов): `id`, `title`, `item_count`, `scope{x,y,width,height}`, `samples`. Полезно: title фрейма часто содержит даты («Оргструктура АИД актуальная версия - 14.09.26», «…- 26.05.26»), чтобы понять, какой вариант актуален.

### 2. Точечный поиск — `canvas_search(miro_url, result_mode="matches", patterns=[...])`
- `patterns` — обычный текст (case-insensitive), префикс `re:` для regex, `text:` — явный литерал. Посылать связанные паттерны вместе.
- Результат: `id`, `type`, `parent` (фрейм-владелец), `scope`, `matches`.
- С его помощью находить конкретных людей/элементы и их фреймы (parent).

### 3. Чтение содержимого — `canvas_read_as_svg`
- **Unscoped reads ОТКЛЮЧЕНЫ**: нужен либо `widget_ids` (точечный), либо полный scope `scope_x, scope_y, scope_width, scope_height` из `canvas_search`.
- Большой фрейм (>~500 виджетов или вывод >~100КБ) — **нарезать на 4 квадранта** (половины ширины/высоты scope фрейма) и читать по частям; результат большого квадранта persist-ится в `/tmp/hermes-results/*.txt` — парсить скриптом через `python3 file.py` (не `read_file`: длинные строки → «binary file»).
- Sticky-карточки людей распознаются по `data-type="sticky"` + `data-content="Имя"`.
- Каждая карточка-виджет имеет серверный `data-miro-id` — **единственный валидный идентификатор для последующих правок**. Не выдумывать, не транскрибировать по памяти; только из result_svg.

## Ретроспективы и рейтинг голосов (Miro Voting)
Частая задача — «главные выводы ретроспективы **с рейтингом**». Классический подводный камень:
- Голоса плагина Voting (`widgets_stack` «голосование» в углу фрейма) **не читаются через API**: ни `canvas_search` по «голос/vote/voting», ни `data-content` стикеров их не отдают — счётчики-стикеры лежат вне выгружаемого слоя. Точного числового рейтинга из доски не вытащить.
- **Точные числа — только по скриншотам доски через `vision_analyze`.** Саша часто сам присылает скрин фрейма («вот голоса…») — тогда читать счётчики голосов с картинки: `vision_analyze(image_url, question="для каждого стикера укажи, сколько голосов (синих меток с цифрами) на нём стоит")`. Считать **только синие метки с числом голосов**, голоса 0 по стикерам тоже фиксировать. Это единственный способ получить точный числовой рейтинг.
- Если скриншотов нет — сверяйся с транскриптом встречи в WorkVault: `~/WorkVault/Meetings/NewMeetings/<дата> Ретроспектива ... - transcript.md` — ведущий **зачитывает вслух**, какие стикеры набрали больше всего голосов по каждому блоку. Лидеры очевидны, остальные — «поединички» (без точных чисел). Но не заявлять лидеров рынка «по транскрипту», когда есть скриншоты с точными цифрами — предпочтительная очерёдность сначала скрин-счётчик, потом транскрипт.
- На доске также есть готовые фреймы `Summary / ...` — суммаризация блоков; использовать их как основу, но они БЕЗ рейтинга. Если и в транскрипте, и в суммах цифр нет — честно сказать «точного числового рейтинга в данных нет», не выдумывать цифры.

## ПОДСЧЁТ уникальных людей / объектов
Частая задача — «сколько всего человек в оргструктуре». Классический подводный камень: **один человек на нескольких карточках** (разные отделы/роли) и **разные формы имени** («Цветкова Лена» vs «Цветкова Елена», «Ларьков Саша (системный аналитик)» vs «Ларьков Саша»).
1. Прочитать все квадранты фрейма, вытащить все sticky с именами (с повторами как есть).
2. Продедуплицировать скриптом (см. `references/count-and-dedup-people.md`): нормализация (`ё→е`, регистр, пробелы), свод уменьшительных имён к полным (`лена=елена`, `саша=александр` и т.п.), группировка по паре {имя,фамилия} независимо от порядка слов.
3. Ответ Саше: число уникальных + список кого и сколько раз дублировали. Показать расхождение с заголовком доски, если он содержит число («…(80)» часто = число ДО дедупликации).
4. **Пересчёт чисел в скобках вложенных отделов** см. `references/recompute-department-counts.md`: коннекторное дерево ЧАСТИЧНО работает (большинство малых отделов считаются надёжно; перекрёстные коннекторы дают абсурд — отделу НЕ верить). Общий уникальный состав фрейма — всегда надёжен. Однозначные отделы правь смело, спорные сверяй с Сашей до записи.

## ПРАВКА существующих элементов (переименование)

1. **Сначала**: `canvas_get_canvas_composer_skill` с `step="edit"` — вернёт полный DSL (widget-атрибуты, PATCH-семантику).
2. `canvas_update_from_svg(miro_url, svg=...)` с **PATCH-семантикой**: элемент с `data-miro-id` — меняются ТОЛЬКО указанные атрибуты, пропущенные сохраняют значение. Минимальный стаб достаточно:
   ```xml
   <rect data-miro-id="3458..." data-type="sticky" data-content="Новое имя" />
   ```
   Тип (`data-type="sticky"`) обязательно сохранить — иначе тупой rect читается как shape.
3. `data-content=""` очищает текст sticky/shape; удаление — только `data-deleted="true"` + `data-miro-id` (подтверждать с пользователем).
4. **PITFALL — спуриозный фрейм.** НЕ оборачивать правку в `<g data-frame="" ...>` **без** корректного `data-miro-id` существующего фрейма: открытый `<g data-frame="">` без miro-id Майро создаёт НОВЫЙ пустой фрейм («1 created» в ответе). Варианты: либо вставить реальный `data-miro-id` фрейма-владельца на `<g>`, либо использовать «голый» элемент без обёртки `g data-frame`. Если спуриозный фрейм всё же создан — сразу удалить: `<g data-miro-id="<created_id>" data-deleted="true" />` (важно перед удалением проверить, что карточки-содержимое не были привязаны к нему и после удаления остались).
5. После правки — **перечитать** затронутые `widget_ids` и сверить фактический текст (self-report не верить).

## PITFALLS SUMMARY
- Полная доска/большой фрейм через `canvas_read_as_svg` — не работает/обрезается. Только квадранты или widget_ids.
- `board_search_boards` не отдаёт даты изменения.
- `canvas_read_as_svg` без scope — «Unscoped canvas reads are disabled».
- Правка: обязательно `canvas_get_canvas_composer_skill(step=edit)` перед update.
- `<g data-frame="" ...>` без реального `data-miro-id` → создаётся спуриозный фрейм.
- `read_file` на /tmp/hermes-results/*.txt с длинными строками → «binary file»; читать python-скриптом.
- Голоса Voting на ретроспективе через API НЕ читаются — за рейтингом иди в транскрипт встречи WorkVault (см. «Ретроспективы и рейтинг голосов»).
- Всегда перечитывать после update, `data-miro-id` брать только из result_svg.
