# FILL / заливка в Jira (transitions)

## FILL (план/факт через srtool)

TG-driven, transition **61**, буллет `·` (U+00B7), переносы `\r\n`, парсер `\d+\.\t`. Детали — `SRTool_TZ.md`. **Не** `PUT` на customfield SR.

## Заливка итогов (44404–44406)

Только по явной команде («перенеси итоги»), после согласования `_draft.md`.

1. **Только запрошенные поля.** «Только итоги» → 44404–44406, **не** 44401–44403.
2. Текст из `_draft.md` (структура `### N.`, `**Плановый результат:**` и т.д.) — plain text с переносами.
3. `\n` → `\r\n`.
4. **`GET /issue/{key}/transitions`** — для итогов id **`271`**, не `61`.
5. `POST /issue/{key}/transitions` с полями в `fields`.
6. GET-верификация: первые ~300 символов каждого поля; статус не должен измениться неожиданно.
7. Напомнить: «Согласование с руководителем» — вручную пользователем.

## Заливка плана (44401–44403)

Transition обычно **`61`**. Только 44401–44403. См. `flow-plan.md`.

## Перед КАЖДОЙ заливкой

`GET /transitions` заново — статус SR может измениться вручную в Jira между репликами. При `400` или отсутствии нужной transition — сообщить текущий статус, ждать правки пользователя.

## Обработка 204 / пустого ответа

Transition POST может вернуть `204 No Content` — это успех. Верифицировать GET полей, не только HTTP-код.

## SR_BYPASS

Ручной curl только если SRTool недоступен. Строка `SR_BYPASS: …` в ответе. После — сверить GET.
