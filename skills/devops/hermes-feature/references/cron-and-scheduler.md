# Cron / scheduler / gateway — питфоллы

Родственный скилл: `cron-journal-write` (журналирование результатов кронов).

## `cronjob(action='create')` со скриптом

Скрипт должен физически лежать в `~/.hermes/scripts/` под простым именем. **Симлинки не работают** — scheduler резолвит их в абсолютный путь и отклоняет.

```bash
cat source.sh > ~/.hermes/scripts/name.sh && chmod +x ~/.hermes/scripts/name.sh
```

Передавать только имя файла без пути: `script="name.sh"`.

**ВАЖНО:** в поле `script` нельзя передавать составную команду со `&&` — только имя одного файла. Если нужно несколько команд — создать враппер-скрипт.

## Делегирование через одноразовый cron

Паттерн для Opus-задач без прерывания текущей сессии:

```python
cronjob(action='create', schedule='Nm', repeat=1,
        deliver='telegram:400307920', model='claude-opus-4-7')
```

Результат приходит в TG. Job самоудаляется после выполнения (`repeat=1`).

## `cronjob(action='run')` на одноразовом кроне разрушает конфигурацию

После принудительного запуска разового job теряет все параметры (модель, deliver, промпт, schedule).

**Паттерн:** всегда создавать одноразовый крон с `schedule` на +3 минуты от `date '+%Y-%m-%dT%H:%M:%S'`. Не использовать `action='run'` для запуска — только для постоянных кронов. Одноразовые кроны запускать через **2–5 минут** после постановки задачи (правило Саши 01.07.2026).

**⚠️ НЕ использовать `action='run'` как способ «исправить» слишком позднее `schedule` на уже созданном one-shot job.** Прецедент 13.07.2026: джоб случайно создан с `schedule` на 5 часов вперёд вместо +3-5 минут; попытка форсировать немедленный запуск через `cronjob(action='run', job_id=...)` **сразу же разрушила конфигурацию** (ответ показал `name`→job_id, `schedule: "?"`, `repeat: "forever"`, `deliver: "local"` — все поля испорчены), несмотря на то что именно это поведение уже задокументировано абзацем выше — знание правила не спасло от его нарушения под давлением "надо быстро исправить". Правильное исправление неверного `schedule` — **`cronjob(action='update', job_id=..., schedule='Nm')`** (пересоздать расписание на несколько минут вперёд), либо `remove` + `create` заново с тем же промптом. Никогда не `run` как быстрый фикс — даже если кажется, что "разово запустить раньше" безопаснее, чем ждать 2-5 минут.

Симптом: `last_status: ok`, но ничего не пушится. Проверять реальный вывод лога, не только статус. При переносе проекта в другую папку нужно обновлять пути в cron-job промпте (`jobs.json`). Симптом: `synced=0` без ошибок — скрипт не найден по старому пути.

## `execution_success: false` после `action='run'` — не доверять, проверять файл вывода

Многократно подтверждено 10.07.2026 (сессия ProtocolFromSummary, 5+ повторений): после вызова `cronjob(action='run', job_id=...)` на просроченном one-shot (см. выше) ответ API стабильно содержит `"executed": true, "execution_success": false` — при этом сам джоб реально выполнился и вернул корректный, полезный результат. Флаг, судя по всему, отражает какой-то технический побочный аспект самого `run`-вызова (возможно способ доставки/финализации job после ручного запуска), а не бизнес-результат задачи.

**Правило:** после `action='run'` никогда не судить об успехе по `execution_success` в ответе. Единственный надёжный способ — прочитать `~/.hermes/cron/output/<job_id>/*.md` (файл может появиться не мгновенно, подождать несколько секунд/минут перед проверкой). Если пользователь спрашивает «в работе?»/«запустилось?» сразу после `run` — не отвечать по полю ответа, сходить проверить файл вывода.

## Изменение `no_agent` в cron-задаче

Инструмент `cronjob(action='update')` **НЕ умеет** сбрасывать `no_agent: true → false`. Нужна прямая правка JSON:

```
/home/tkachenkoav/.local/share/hermes/cron/jobs.json
```

Найти блок по `job_id`, поменять `"no_agent": true` → `"no_agent": false`, убрать `"script": "..."` → `"script": null`. Gateway перезапускать не нужно — scheduler читает jobs.json при следующем тике.

## `[SILENT]` guard в кронах — эволюция правила (Вариант A → апстрим-cutover, 05.07.2026)

**Текущее рабочее состояние (после cutover 05.07.2026):** `cron/scheduler.py::_is_cron_silence_response(text)` (~строка 263) — функция из апстрима, не наш локальный `_classify_silent_marker`. Она шире нашего Варианта A: ловит маркер как весь ответ, ИЛИ первую/последнюю строку, ПЛЮС bracketless-варианты (`SILENT`, `NO_REPLY`, `NO REPLY`) без квадратных скобок (issues #51438, #46917 апстрима). Guard вызывается в `tick()` ~строка 3236: `if should_deliver and success and _is_cron_silence_response(deliver_content): should_deliver = False`.

**История:** мы сами реализовали Вариант A (`_classify_silent_marker`, commit `276cb5296`, 05.07.2026, deliver/silent_clean/silent_dirty с WARNING-логом на «грязный» случай) в ответ на баг — Haiku писала «count = 0. Согласно ТЗ... [SILENT]» и plain-equality-guard не подавлял доставку рассуждений. При регулярном апстрим-синке в тот же день наш патч был **вытеснен** более широкой встроенной реализацией апстрима — она покрывает наш кейс полностью плюс больше. Коммит остался в истории как landing point, реальная логика — апстримная. Если видишь `_classify_silent_marker` в старом коде/бэкапе — это superseded, ориентируйся на `_is_cron_silence_response`.

**Причина правила «last-line-equals» / first-or-last-line:**
1. plain-equality (`strip().upper() == SILENT_MARKER`) пропускает частый паттерн модели «reasoning\n\n[SILENT]» — жалобы Саши 01.07.2026 и рецидив 05.07.2026.
2. Substring-проверка (`SILENT_MARKER in ...`) глушит содержательные отчёты, где `[SILENT]` встречается в примерах/цитатах.

**Диагностика ложного подавления:** `cat ~/.hermes/cron/output/<job_id>/*.md` + `grep -c "SILENT" file`. Перед тем как патчить scheduler.py заново — сначала `grep -n "_is_cron_silence_response\|_classify_silent_marker" cron/scheduler.py`, чтобы понять, какая версия сейчас реально в дереве (апстрим мог давно уже включить нужное поведение). Отдельные ветки no_agent/script-mode (~2427, ~2483) используют константу `SILENT_MARKER` напрямую, не классификатор — там своя логика.

**Процесс диагностики, который сработал (воспроизводимый паттерн):** (1) разовый Opus-крон только на анализ (без права патчить) → root cause + 2-3 варианта фикса с таблицей надёжность/риск/сложность, без выбора самому; (2) Саша выбирает вариант; (3) отдельный разовый Opus/Sonnet-крон на реализацию + тесты, с явным запретом коммитить/пушить и рестартовать gateway. Работает для любого «код ведёт себя не по спеке» бага, не только SILENT-guard.

## Миграция тестов при изменении семантики фикса

Когда правка ужесточает правило (substring → last-line-equals в SILENT-guard), часть **existing тестов может кодировать старую (буговую) семантику**, а не общее поведение. Признак: тест падает на новом коде, но название теста описывает валидное поведение (`test_silent_with_note_suppresses_delivery`).

Разбор: посмотреть фикстуру — если она заточена под старую механику (`"[SILENT] note"` в одну строку — работало только благодаря substring-check), обновить фикстуру под новую семантику (`"note\n\n[SILENT]"`), сохранив intent теста (проверка что suppress срабатывает). Не восстанавливать старое поведение и не удалять тест. Комментарий в тесте: «Marker must be on its own final line (Variant A: last-non-empty-line equals)».

## Извлечение чистого хелпера для тестируемости guard-ов

Когда логика (5–15 строк условной ветки) внутри огромной функции (`tick()`) должна получить unit-тесты — вынести её в pure-функцию рядом с константой, оставить guard-caller минимальным. Пример: `_classify_silent_marker(text) -> str` рядом с `SILENT_MARKER = "[SILENT]"`.

Плюсы:
1. Тесты не мокают `run_job`/`get_due_jobs`/`_deliver_result` для проверки одной строки.
2. Тесты быстрые (0.28s против 40s+ регресса).
3. Три ветки (`silent_clean`/`silent_dirty`/`deliver`) явно документированы docstring-ом.

Название начинается с `_` — приватный контракт модуля, не публичный API.

## Футер в cron-ответах

Формат: `claude-opus-4-7 · Имя задачи` в конце ответа, добавляется `_build_cron_footer(job)` в `cron/scheduler.py`. Если футер отсутствует после рестарта — проверить что `_SEP` и `_model_short` из `gateway/runtime_footer.py` доступны (могут быть приватными). Fallback: дублировать литерал `" · "` локально в `scheduler.py`.

## «Слепая зона» Sonnet при ожидании Opus-крона

Sonnet в живом диалоге **НЕ видит ответы кронов автоматически** — они доставляются в TG отдельным сообщением или пишутся в `~/.hermes/cron/output/<job_id>/`. Если пользователь ждёт результата крона в диалоге — не говорить «подожди, скоро придёт», а **проверить вывод вручную** после ожидаемого времени завершения: `cat ~/.hermes/cron/output/<job_id>/*.md`.

**Паттерн:** (1) запустить крон, (2) сообщить время ожидания, (3) когда пользователь проверяет — сразу читать файл вывода через terminal и пересказывать результат. Не ждать пока Telegram доставит.

## Thread ID топиков Telegram

Thread ID не хранится в `sessions.db`, `system_prompt`, `handoff_state`. Единственный источник правды — `gateway.log`, поле `reply_to_id` в строке `Flushing text batch agent:main:telegram:group:<chat_id>:<thread_id>`. Пример: `Flushing text batch agent:main:telegram:group:-1004300127777:4` → `thread_id=4`.

Паттерн: `grep "reply_to_id" ~/.hermes/logs/gateway.log` — строки вида `msg='топик X' reply_to_id=4`. Если пользователь написал «топик X» в каждый топик — это даёт полную карту `name → thread_id`. Сохранять в MEMORY сразу после извлечения.

**Топики «Сирень Workspace» (chat=-1004300127777):** General=1, Tools=3, Hermes DEV=4, WorkVault=5, Backlog=6, Monitoring=7, Personal=8. Доставка кронов: `deliver='telegram:-1004300127777:<thread_id>'`.

## Аудит списка кронов на устаревшие one-shot задачи

При разборе `cronjob(action='list')` встречаются разовые (`repeat: once`) job'ы в статусе `paused`, ни разу не запускавшиеся, назначение которых («финализация ТЗ X», «решения Саши по Y») уже выполнено вручную в диалоге, а не через сам крон. Это не баг, а забытый артефакт — крон создавался под конкретный шаг, шаг прошёл другим путём.

Проверять по имени/промпту job'а, совпадает ли задача с уже закрытой в MAIN_TZ_INVENTORY.md/диалоге; если да — предложить Саше удалить (`cronjob(action='remove')`), не удалять молча.

## Дизайн уведомлений batch-крона: маршрутизация по результату, не по факту запуска

Правило (Саша, 13.07.2026, прецедент ProtocolFromSummary): пользователь не просил отчёт о каждом рутинном прогоне батч-крона — получать сводку «N файлов, всё out_of_scope/skip, 0 опубликовано» в личку на каждый тик расписания (каждые 2 часа и т.п.) — чистый шум. Правильная маршрутизация по трём веткам результата, не по самому факту, что крон отработал:

| Исход прогона | Куда доставлять |
|---|---|
| Штатный/пустой (published=0, error=0 — всё skip/out_of_scope/файлов нет) | Никуда (только внутренний лог). Не отчитываться о том, что «ничего не произошло». |
| Успешные публикации (published>0) | Целевой топик по теме крона — но только если для этого нет уже отдельного notify-механизма (см. ниже); не дублировать. |
| Ошибки (error>0 — сбой публикации, 404, коллизия и т.п.) | Тот же целевой рабочий топик, НЕ личка — ошибка релевантна контексту задачи, которую видят все, кто следит за темой, а не только личный статус пользователя. |

**Если у самого крона/инструмента уже есть отдельный notify-механизм** (например второй крон, читающий реестр с флагом `notified: false` и шлющий уведомление по каждой успешной публикации в целевой топик) — главный batch-крон не должен вообще ничего слать при успехе, чтобы не задваивать сообщения. Его `deliver` можно смело поставить на `local`, а всю логику «когда всё-таки написать» — переложить в сам промпт агента явными условиями (не полагаться на глобальный `deliver`, который либо шлёт всегда, либо никогда):

```
- published=0, error=0 → ничего не отправлять, тихо завершить работу.
- published>0 → тоже ничего не отправлять сам — уведомления уже шлёт отдельный notify-крон.
- error>0 → единственный случай когда нужно уведомление; отправить его САМОМУ через terminal:
  hermes send --to "telegram:<chat_id>:<thread_id>" --file -
  (текст ошибки через stdin), в целевой рабочий топик, не в личку.
```

Прецедент: `a6e62d06249f` (ProtocolFromSummary batch) — `deliver` сменён с `telegram:400307920` (личка) на `local`; в промпт добавлены явные три ветки выше, error-ветка шлёт `hermes send` в топик WorkVault (`-1004300127777:5`), где уже живёт notify-крон успешных публикаций.

**Общий вывод для любого нового batch/watchdog-крона:** перед тем как ставить `deliver='telegram:<личка>'` по умолчанию — спросить (или прикинуть по аналогии), хочет ли пользователь видеть каждый тик расписания, или только отклонения от нормы. Молчание при штатном исходе — правильный default для периодических batch-джобов; личка — для вещей, которые реально требуют внимания пользователя лично (не общего рабочего контекста).

## Триггер аперодической maintenance-задачи — событие/порог через существующий периодический крон, не отдельное календарное расписание

Когда задача (аудит, чистка, скан) должна запускаться не по фиксированному календарю, а по достижении состояния (объём MEMORY, размер лога, число накопленных пунктов) — не создавать для неё отдельный `cronjob` с собственным `schedule`. Правильный паттерн (решение Саши 13.07.2026, применено к Pitfall Scan над `hermes-feature`):

1. Job, который реально выполняет тяжёлую работу, создаётся **на паузе** (`enabled=false`, `schedule=null`) — не привязан к календарю вообще, запускается только `cronjob(action='run', job_id=...)` вручную или по явной команде пользователя.
2. Детект условия («MEMORY ≥ 1/3 лимита», «пунктов накопилось больше N») добавляется отдельным шагом в уже существующий периодический крон (например `vm_selfcheck`, еженедельный self-check) — этот крон при каждом штатном прогоне читает текущее состояние и, если порог достигнут, добавляет ОДНУ строку-рекомендацию в свой обычный отчёт: «X достигло Y% — рекомендую запустить `cronjob(action='run', job_id=...)`».
3. Если порог не достигнут — детект-шаг ничего не добавляет в отчёт (не раздувать штатный отчёт пустой веткой).

**Почему так, а не отдельный календарный крон с разумной периодичностью:** (а) календарная дата — произвольная догадка о том, когда состояние достигнет порога, реальный рост непредсказуем (может быть быстрее или медленнее); (б) объединение детекта в уже читаемый пользователем периодический отчёт не плодит новых источников уведомлений; (в) сохраняет тот же принцип «детект — автоматически, реальное действие с side-effect — только по явной команде», что уже используется для гигиены MEMORY (`hermes-memory-hygiene`, "Two run modes").

Прецедент: `97d76357f2da` (Pitfall Scan над Common Pitfalls `hermes-feature`) изначально создан с `schedule='0 5 1 * *'` (ежемесячно) — пользователь после создания попросил заменить триггер на «когда MEMORY.md дорастёт до трети лимита». Job переведён на паузу (`enabled=false`), в `vm_selfcheck` добавлен шаг 9 с детектом заполнения MEMORY и рекомендацией команды запуска.

## Пользователь сужает скоуп one-shot job'а, который уже ушёл в исполнение

`cronjob(action='update', job_id=...)` иногда возвращает `Job with ID or name '<id>' not found`, даже если `cronjob(action='list')` секундами раньше показывал этот же `job_id` в статусе `scheduled`. Это не потеря job'а — one-shot задача, начавшая реально выполняться (агент уже читает файлы/вызывает API внутри неё), временно исчезает из реестра `list`/`update`, пока не завершится и не запишет отчёт.

Прецедент 14.07.2026: создан крон на выгрузку иерархии OKR-цели O1 в Obsidian + отдельную сводную таблицу по всем 12 годовым целям АИД. Через ~1 минуту пользователь написал «не надо 12 целей, только O1!» — попытка `cronjob(action='update')` с сокращённым промптом вернула `not found`: job уже перешёл в исполнение по старому, широкому промпту.

**Практическое следствие:**
- Окно для правки one-shot job'а после `create` — секунды, до того как планировщик успел его подхватить. Если корректировка скоупа нужна — делать её немедленно следующим tool-call, не откладывать на «сейчас отвечу пользователю, потом поправлю».
- Если `update` вернул `not found` на job, который только что был в `list` — это надёжный сигнал «уже выполняется», не повод пробовать `run` или пересоздавать job с тем же именем (получится дубль, а старый всё равно доработает и пришлёт отчёт).
- Правильная реакция: дождаться отчёта старого job'а, затем вручную обрезать/удалить из результата то, что вышло за пределы уточнённого скоупа (например удалить лишний файл сводной таблицы по нецелевым 11 годовым целям), не запускать второй параллельный джоб на «переделать всё заново» без необходимости.

## Формат гиперссылок в сообщениях, доставляемых через `no_agent` cron script

Когда `deliver='telegram:<chat_id>:<thread_id>'` доставляет stdout скрипта (`no_agent=true`) — HTML-теги (`<a href="...">текст</a>`) **не рендерятся**, приходят как сырой текст в чат (подтверждено скриншотом 10.07.2026, ProtocolFromSummary). **Использовать Markdown-синтаксис `[текст](url)`** — он рендерится корректно на этом пути доставки. Не путать с доставкой через прямой `hermes send`/gateway API — там формат может отличаться, проверять отдельно при переходе на другой канал доставки.

## Именование кронов и выбор модели

**Имена:** Саша предпочитает короткие читаемые `snake_case`-имена вместо hex-id. Переименовывать по запросу без уточнений.

**Модель для механических кронов:** операторские задачи без анализа (запустить команду, разобрать вывод) — Haiku. Подробнее — `hermes-feature` Блок 6Б (таблица моделей).
