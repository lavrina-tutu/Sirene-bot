# Epic Development — правила работы с эпиками

## Триггеры
- «Начнём работу с Epic [название]»
- «Следующий модуль [название]»
- «Бриф по [модуль]»
- Любая работа с ТЗ типа `TZ_aggregate_main.md` или папкой `modules/`

## Правило 0 — Контекст перед каждым модулем

Перед началом работы с любым модулем:
1. Прочитать главное ТЗ Epic (`TZ_*_main.md`) — цель, архитектура, статус модулей
2. Прочитать ТЗ всех **закрытых** модулей — зафиксировать их выходы
3. Уточнить план вопросов текущего модуля с учётом уже принятых решений
4. Не идти вслепую — каждый модуль знает о предыдущих

## Правило 1 — Карточка модуля перед брифом

Перед вопросами — показать и записать в ТЗ модуля:

```markdown
## Карточка модуля [X. Название]

🎯 **Функция:** [одно предложение — что делает этот модуль]
⬅️ **Вход:** [что получает на входе, от кого]
➡️ **Выход:** [что отдаёт, кому]
🔗 **Зависимости:** [от каких других модулей зависит]
📋 **Статус:** stub / в брифе / закрыт
```

Саша подтверждает карточку (или корректирует) → только потом идут вопросы.

## Правило 2 — Бриф по одному вопросу

Формат каждого вопроса:
```
**В[N] — [Тема вопроса]**

[1-2 предложения контекста почему этот вопрос важен]

**А** — [вариант]
**Б** — [вариант]
**В** — [вариант]

💡 **Рекомендую [X]** — [обоснование]
```

⚠️ **Обязательно:** варианты всегда обозначаются русскими буквами А/Б/В (не A/B/C латиницей). Единообразно во всех брифах по эпикам.

После ответа Саши — **сразу записать в ТЗ модуля**, не копить.

## Правило 3 — Порядок модулей по MVP-приоритету

Opus предлагает порядок по принципу **«минимум блокирует максимум»**:
- Сначала модули без зависимостей (фундамент)
- Потом модули, которые разблокируют несколько других
- В последнюю очередь — оркестрация и интеграция

Порядок фиксируется в главном ТЗ и не меняется без явного решения.

## Правило 4 — Итог модуля

После закрытия каждого модуля — краткое резюме перед переходом к следующему:

```
✅ Модуль [X. Название] закрыт

**Ключевые решения:**
- [решение 1]
- [решение 2]

**Выход:** [что передаёт следующему модулю]

→ Следующий: [Y. Название]
```

## Правило 5 — Хранение артефактов

Стандартная структура Epic в WorkVault:
```
WorkVault/Tools/{EpicName}/
├── TZ_{epic_slug}_main.md     # Главное ТЗ + ссылки на модули
├── modules/
│   ├── TZ_A_*.md
│   ├── TZ_B_*.md
│   └── ...
└── research/                  # Исходные исследования
```

Epic в бэклоге:
- Отдельная секция `## 🏗️ EPIC: [Название]`
- Связанные bk-пункты линкуются через `^epic-[slug]`
- Статус каждого модуля в таблице главного ТЗ

## Правило 6 — Кросс-вопросы между модулями

Если ответ в текущем модуле влияет на другой модуль — **сразу** добавить вопрос в ТЗ того модуля:

```markdown
⚠️ **[от модуля X, ВN]** [Формулировка вопроса для этого модуля]
```

При начале брифа по следующему модулю — прочитать все `⚠️` вопросы из его ТЗ и включить в план вопросов. Не терять кросс-зависимости.

## Правило 7 — Качество входных данных

При работе с Epic где есть «входные артефакты» (карточки, контекст, допущения) — проверять их качество:

> **Принцип:** «мусор на входе → мусор на выходе»

Если в брифе выясняется что входные данные важны для точности — добавить в главное ТЗ Epic раздел «Требование к качеству входных данных» с конкретными правилами.

## Правило 8 — Двухшаговая LLM-архитектура для больших датасетов

Когда Epic включает обработку большого объёма данных (сотни/тысячи записей) — разделять на два шага:

```
Шаг 1 — Разметка (дешёвая модель, ×N):
Каждая запись → минимальный набор тегов (классификация + флаги наличия)
Цель: индекс «что где есть», не детали
Модель: Haiku

Шаг 2 — Агрегация (качественная модель, ×M где M << N):
Все записи одной сущности → один вызов LLM → заполнение артефактов
M = количество уникальных сущностей (проектов, контактов)
Модель: Sonnet / тестировать
```

**Тестирование перед выбором модели:** всегда тестировать на реальных данных (Haiku vs Sonnet на 3-5 записей), Саша оценивает качество → только тогда выбирать.

## Правило 9 — Объяснять незнакомые концепции с примерами

Если пользователь спрашивает «что такое X подробнее с примерами» — останавливаемся и объясняем на конкретном примере из его контекста перед тем как двигаться дальше.

Формат объяснения:
1. Показать конкретный код/пример из его данных (не абстрактный)
2. Сравнить варианты в таблице если нужно
3. Затем вернуться к вопросу брифа

## Правило 10 — Уточнение по архитектурным допущениям

Когда пользователь предлагает вариант который меняет архитектуру — сначала зафиксировать что именно меняется, потом обновить карточку модуля и все ТЗ которых это касается.

## Правило 11 — Три продукта: разграничение аудиторий

При проектировании выходных артефактов Epic — всегда явно зафиксировать таблицу:

| Продукт | Аудитория | Где хранится | Кто отвечает | MVP | Фаза 2 |

Без этой таблицы модули начинают пересекаться. Провести калибровку по реальным данным: найти ручной аналог → сравнить → уточнить архитектуру.

## Правило 12 — Append-only как default для накопительных артефактов

При проектировании модуля, который пишет в файлы-артефакты:
- Первый вопрос: «append-only или перезапись?»
- Для накопительных (decisions, action_items, timeline) — всегда append-only по умолчанию
- Противоречия: зачёркивание `~~текст~~` с пометкой, не удаление
- Нумерация (action_items): **сквозная по сущности `#N`**, не по встрече
- pm_locked при append-only архитектуре — избыточен, убирать из scope

## Правило 13 — Пересмотр границ «внешний vs внутренний инструмент»

Если в ходе брифа выясняется что «внешний инструмент» не имеет смысла без текущего Epic — это сигнал для включения как модуля.

## Правило 14 — Сквозная нумерация action items

При проектировании модуля накопления задач — всегда закладывать сквозную нумерацию `#N` **по сущности** (не по встрече). Нумерация глобальная, инкрементальная, не сбрасывается при новых встречах. Это критично для PM-модерации: PM ссылается на `#N` в заметках `<!-- pm: #42 закрыто -->`.

## Правило 15 — Алиасы как первичный сигнал классификации

При проектировании модуля классификации/маршрутизации — алиасы из текста первичны, метаданные вторичны.

**Три неймспейса алиасов** (не путать!):
- Проекты → `classification_memory.json`, TG-команды: `алиас [текст] → [slug]`
- Контакты → AnywhereContacts (`add_alias()`), TG-команды: `алиас [текст] → [login]`
- Синки → `syncs_memory.json`, TG-команды: `алиас синка [текст] → [slug]`

Все три неймспейса симметричны: 4 операции (добавить / заблокировать / просмотреть / удалить soft-delete). TG-команды явно называют неймспейс («алиас», «алиас синка», «алиас контакта»).

**Soft delete для аудита** — не хард-удаление. Восстановление командой `восстанови алиас`.

## Правило 16 — Типизация встреч по алиасам

Алгоритм типизации (приоритет сверху вниз). **Шаг 0 — обязательно первым:**

```
Шаг 0: title/keywords матчит алиас из syncs_memory.json
        ИЛИ regex (Sync|Standup|Гильдия|DataTalks|Weekly) → multisync
        [ВАЖНО: без шага 0 рабочие встречи 3+ чел по 1 проекту ошибочно
         маршрутизируются как multisync — конфликт правил 1 и H.В1]

Шаг 1: алиасы → ровно 1 проект → project (любое кол-во участников)
Шаг 2: 2 участника + алиасы → 2+ проектов → 1on1
Шаг 3: 2 участника + нет алиасов + сигнал Daily/1-1 → 1on1
Шаг 4: 2 участника + нет алиасов + нет сигнала → 1on1 (fallback)
Шаг 5: алиасы → 2+ проектов + 3+ участников → multisync
Шаг 6: 0-1 участник + нет m4a/mp4 → unclear (ошибка парсинга FF)
Шаг 7: fallback → unclear → F дайджест → PM вручную
```

**Единственный владелец алгоритма — B.Роутер.** Модули E и H только ссылаются: «маршрут определяется B.Роутером». Дублирование алгоритма в E/H = источник конфликта при правках.

**Доказательная база:** реальное сканирование 478 FF summary (2026-06-18).

## Правило 17 — «Если сразу делаем по хорошему»

Когда PM спрашивает «а если сразу делаем по хорошему?» — сигнал к явному сравнению вариантов по расширяемости:
1. Таблица: вариант × фаза (MVP / Фаза 2 / Фаза 3) с ✅/❌/⚠️
2. Выделить «тупиковые» варианты
3. Рекомендовать вариант с наименьшим количеством переписываний

## Правило 18 — Надёжность пайплайна: логирование и ретраи

При проектировании автоматического пайплайна — обязательно в MVP:

- **Формат логов:** JSON Lines, поля: `ts`, `lvl`, `module`, `event`, `file`, `err_type`, `retry`, `can_retry`
- **Ретраи:** backoff 0→15→60 мин, max 3 попытки. Ретраить: llm_timeout, rate_limit, network. НЕ ретраить: parse_error, write_error, content_refusal, schema_error → TG PM немедленно
- **Haiku-диагностика** (предпочтительнее таблицы err_type→action): один промпт на все типы ошибок
- **Уведомления:** немедленно (критичные) + 20:00 (дайджест, молчит если чисто) + пн 09:00 (статистика)

## Правило 19 — Формат упоминания модулей

Всегда упоминать модуль в формате **«Буква.Название»**: `E.Люди`, `F.Дирижёр`, `D.База`, `G.Срез`, `H.Синки`. Никогда просто «модуль E» или «модуль Люди» — PM путается. Применять во всех сообщениях, ТЗ, вопросах брифа и решениях.

## Правило 20 — Аналогия с существующими решениями как аргумент целостности

Если в брифе возникает вопрос по карточке/блоку/механике для новой сущности — **всегда проверять как это решено в уже проработанных сущностях** (Projects, D.База, G.Срез). Если там уже есть решение — применять по аналогии и **явно называть это аргументом**: «по аналогии с Projects/card.md». Это поддерживает целостность системы и сокращает количество вопросов брифа.

Примеры применения из AggregateFromMeetings:
- dataviewjs в карточках People и Syncs — принят потому что уже используется в Projects/card.md
- Отсутствие сквозного PM Notes блока — по аналогии с Projects/card.md
- Навигационная строка без лишних секций — аналог Projects/card.md

## Правило 21 — Сравнение однотипных сущностей поштучно

Когда проектируются две похожие сущности (например `People/card.md` и `Syncs/card.md`):
1. Показать таблицу всех полей: `поле | сущность1 | сущность2 | статус (✅одинаково/❓обсудить)`
2. Каждое поле со статусом ❓ — отдельный мини-вопрос А/Б/В
3. Не принимать решения скопом — PM уточняет каждое поле независимо
4. После каждого ответа — сразу фиксировать в ТЗ, затем следующее поле

## Правило 22 — Порядок брифа карточки сущности

При брифе карточки сущности (People, Syncs и т.п.):
1. Показать карточку сущности: 🎯 Функция / ⬅️ Вход / ➡️ Выход / 🔗 Зависимости / 📋 Подструктура (список файлов)
2. PM подтверждает карточку
3. Затем поштучно: одинаковые блоки → разные блоки → вопросы А/Б/В по каждой секции
4. Только после явного «да» на каждый блок — следующий

## Правило 23 — Исследование реальных данных перед архитектурным решением

Когда архитектурный выбор зависит от фактических данных — **не гадать, исследовать**:

```
Паттерн: Opus/Haiku сканирует данные → находит паттерны → рекомендует решение
```

Применять когда PM говорит «откуда берём X?», «что там есть?», «проверь как устроено». Пример из AggregateFromMeetings: поле `**Участники:**` в FF ломается в ~50% встреч — это нашёл Opus на реальных данных, без этого знания архитектура была бы неверной.

## Правило 25 — Независимая верификация через внешнюю LLM

После завершения брифа всех модулей — подготовить пакет верификации для независимой LLM (Cursor, другой Claude):

**Шаги:**
1. Собрать `CURSOR_VERIFICATION_PACKAGE.md` — все ТЗ модулей + инструкция + схема пайплайна + таблица передачи данных + контрольные вопросы + глоссарий
2. Запаковать в `.zip` и отдать PM
3. PM загружает в Cursor — независимая LLM находит противоречия «свежим взглядом»
4. Верификатор возвращает CRITICAL/MAJOR/MINOR — обрабатывать в режиме брифа эпика
5. После исправлений — повторный Opus-аудит непротиворечивости

**Содержимое пакета верификации:**
- 🎯 Инструкция: что за система, стек, цель верификации
- 📐 ASCII-схема пайплайна (обязательно с новыми модулями)
- 🔗 Таблица передачи данных: все пары модулей, структуры, поля с типами
- Полные ТЗ всех модулей (без YAML frontmatter)
- Контрольные вопросы (10+) по нетривиальным местам архитектуры
- Глоссарий ключевых терминов

**Формат передачи PM (zip-архив):**
```bash
# Собрать все ТЗ + tutu-contacts.md + README в один zip
cd WorkVault/Tools/{EpicName}
zip -j /tmp/{EpicName}_TZ_v{VERSION}.zip \
  TZ_{slug}_main.md IMPLEMENTATION_PLAN.md \
  modules/TZ_A_*.md modules/TZ_B_*.md ... \
  briefs/brief_round2_results.md \
  CURSOR_VERIFICATION_PACKAGE.md \
  ~/WorkVault/Contacts/tutu-contacts.md  # путь: WorkVault/Contacts/, не contacts/
zip /tmp/{EpicName}_TZ_v{VERSION}.zip /tmp/README_FOR_CURSOR.md
```

**README_FOR_CURSOR.md** — обязательный файл-инструкция в архиве. Содержание:
- Таблица: файл → что это (одна строка)
- **Раздел «Изменения с прошлой верификации»** — список C1/C2/M1/m1 которые были исправлены. Без этого Cursor повторно проверяет уже одобренное и тратит контекст.
- Таблица: ВОП-N → решение → в каком файле проверять (только для новых решений)
- **Таблица «Что НЕ менялось»** — перечень разделов верифицированных в прошлых итерациях (v1.2–v1.3) с пометкой «проверено, стабильно». Cursor пропускает их и фокусируется на новом.
- Структура фаз (0/1/2)
- Что НЕ входит (за скоупом верификации)
- Следующий шаг после верификации

**Питфолл:** версионирование пакета и ТЗ — держать единую сквозную версию. Если ТЗ-файлы называются v1.5.7 а пакет v1.3 — это путает PM. Договориться на один номер (например v14) и проставить его везде: frontmatter всех TZ-файлов, имя zip-архива, имя MD-пакета, changelog. Иначе PM не понимает какой пакет актуальный.

**Питфолл:** без раздела «Изменения» Cursor каждый раз повторяет все проверки заново, включая уже закрытые. Это увеличивает отчёт вдвое и засоряет его повторными MINOR.

**Питфолл:** MINOR-остатки (r1/r2 после APPROVED) не требуют Opus — две строки правятся напрямую через `patch`. Запускать Opus только на CRITICAL/MAJOR правки или когда затронуты 3+ файлов. Признак что Opus нужен: правка требует чтения всего ТЗ для понимания контекста.

**Питфолл:** Opus-крон на правку ТЗ после MINOR-находок от Cursor — пауза, если задача уже запущена. `cronjob(action='pause')` не останавливает запущенную задачу — она продолжает работать. Останавливать можно только через `process(action='kill')` если знаешь PID, иначе ждать завершения и читать output вручную.

**Питфолл:** при использовании `patch` со строками содержащими `\n` — передавать через Python (`write_file`), а не через строковые параметры patch. Буквальный `\n` попадёт в файл как `\\n` и сломает форматирование Markdown.

**Питфолл:** `tutu-contacts.md` лежит в `WorkVault/Contacts/` (с заглавной C), не в `contacts/`. Без него верификатор не знает как резолвить имена.

**Питфолл:** верификатор может найти реальные противоречия которые аудит Opus пропустил — особенно конфликты алгоритмов между модулями (когда каждый ТЗ по отдельности верен, но вместе — противоречат).

## Правило 24 — Непротиворечивость ТЗ перед закрытием эпика

После закрытия всех модулей — запустить Opus-аудит непротиворечивости:

**Что проверять:**
1. Зависимости между модулями — каждый получает то что обещает предыдущий?
2. Типы сущностей везде одинаково определены?
3. Алиасы по неймспейсам — нигде не путаются, TG-команды не конфликтуют?
4. PM Notes правила везде одинаковые?
5. Кросс-поля (source_sync и т.п.) прокинуты через все затронутые модули?
6. Зависимости явно прописаны в карточках?
7. Пути файлов не конфликтуют?
8. Нумерация #N нигде не смешивается?
9. Фаза 2 решения явно помечены?
10. Snapshots/подкарточки генерируемые другими модулями — упомянуты в ТЗ сущности-владельца?

## Правило 27 — Автопроход HUMAN-GATES при реализации

При запуске автономной реализации (Opus-крон) — разделять gates на два класса:

**Автоматические (не останавливаться, если тесты зелёные):**
- H1 (diff интерфейсов) — зафиксировать в dev-log, продолжать
- H2 (B-checkpoint route) — если метрика достигнута (все sample_meetings верны) → следующий этап

**Обязательные остановки (ждать PM):**
- H3 — качество смысла (decisions/action_items) — PM оценивает содержимое, не метрику
- H4 — стоимость реальных LLM-прогонов (реальные деньги)
- H5 — разметка unclear-очереди и алиасов (живые данные, нужен человек)
- H6 — разрешение писать в боевые артефакты (необратимо)
- H7 — противоречие в ТЗ

**Формат промпта для автономного Opus:**
```
## ПРАВИЛО АВТОПРОДОЛЖЕНИЯ
Автоматические: H1, H2 (если тесты зелёные) → продолжай без стопа
Обязательные: H3, H4, H5, H6, H7 → СТОП, формат отчёта, ждать PM
```

**Питфолл:** не передавать это правило PM на утверждение — это техническое решение,
PM только называет какие gates ему нужны лично. По умолчанию: H3, H4, H5, H6 — всегда ручные.

## Правило 29 — Перевод GATE-отчётов для PM

Когда Opus-крон присылает машинный GATE-отчёт (JSON, технические метрики, списки сигнатур) — **не пересылать его PM напрямую**. PM не может принять решение по машинному выводу.

**Обязательный перевод по схеме:**

1. **Что сделано** — 2-3 предложения на русском: какой модуль написан, сколько тестов прошло, что это значит для системы
2. **Что PM должен увидеть и проверить** — конкретные примеры выхода (не метрики, а содержимое): 3 примера decisions/action_items, структура файла, пример команды
3. **Конкретные вопросы к PM** — не «precision ≥80% подтверждаешь?», а:
   - «Формат решений — без имени и без даты. Устраивает?»
   - «Задачи пишем с корпоративным логином (denis.aralov) или именем (Денис)?»
   - «Решение из синка АиД идёт в карточку проекта antibot со ссылкой на синк — правильно?»

**Питфолл:** PM говорит «мне такой машинный ответ непонятен» — сигнал что перевод не был сделан. Исправить сразу: прочитать полный вывод крона, разобрать по схеме выше.

**Что НЕ показывать PM:**
- Сигнатуры функций (`def add_alias(login: str, alias: str, source: str) -> bool`)
- Технические метрики (`mypy --strict: clean, ruff: clean`)
- JSON структуры целиком без объяснения что в них

## Правило 36 — Бриф unclear: анализировать саммари, группировать по сущностям

Когда PM говорит «поштучно брифуем» или «проанализируй саммари» — обязательный паттерн:

1. **Прочитать реальное содержимое саммари** (не опираться на название встречи)
2. **Определить сущность по саммари**: участники → 1on1; конкретный проект по контексту → project; общекомпанейское → adm/sync
3. **Сгруппировать похожие** перед показом PM — это экономит время (15 «Кирилл 1-1» = одна группа)
4. **Передавать по одной группе**, ждать подтверждения перед следующей
5. **Для каждой встречи внутри группы** — рекомендация основана на саммари, не на имени файла

**Паттерн группировки:**
```python
# Читать все саммари через execute_code
# Группировать: 1on1_kirya / 1on1_other / adm_Q / project_ids / trash_sys
# Внутри project_ids — читать bullet points и первые 600 символов
# Рекомендация = entity из контента, не из заголовка
```

**Питфолл:** Bootstrap флагует больше встреч чем реально unclear — потому что решения брифа ещё не применены в `classification_memory.json`. Не паниковать: «77 в файле» ≠ «77 новых». Сначала сравнить с уже решёнными, показать PM только реально новые.

**Питфолл:** встреча с неочевидным названием (например «Про BI-направление», «Delivery Discovery», «Встреча с ИБ») — всегда читать саммари перед рекомендацией. Название обманывает в ~30% случаев.

**Новые slug по результатам брифа** фиксировать в memory сразу после подтверждения PM. Например: `pro-pm = multisync (проектный офис / методология УП ТУТУ)`.

3. **Ждать ответа** — только после ответа PM переходить к следующему вопросу

**Запрещено:**
- Давать варианты через `clarify` без рекомендации — PM видит голосовалку без мнения агента. `clarify` без recommendation = 10-минутный таймаут и фраза «почему повисли?»
- Задавать два вопроса сразу даже если «они связаны»
- Перечислять варианты как равнозначные без явной рекомендации

**Правильный формат вопроса (НЕ clarify):**
```
**Q[N]: [Тема]**

[2-3 предложения контекст + данные]

**Рекомендую вариант X** — потому что [бизнес-обоснование, не техника].

Согласен?
```

**Сигнал нарушения:** PM говорит «давай как обычно для брифа с рекомендациями», «почему повисли?», «поштучно», или молчит 10+ минут.

## Правило 33 — Аудит логики перед правкой кода

Когда обнаруживается расхождение «код vs ТЗ»:
1. **Сначала анализ** (Opus-крон «только читать»): является ли расхождение багом кода, противоречием ТЗ, или верным расширением ТЗ?
2. **Только после анализа** — решение что и где исправлять (ТЗ / код / оба)
3. **Запрещено:** сразу «чиним» без понимания причины — код может быть правильнее ТЗ

**Питфолл из сессии 22.06:** B.Роутер имел `real_n≤1 + алиас → project` — это корректное расширение ТЗ. Буквальное ТЗ противоречило само себе (Шаг 1 vs Шаг 6). Код был правильнее ТЗ. Без аудита был бы откатан верный код.

**Когда код правильнее ТЗ:** ТЗ надо привести в соответствие с кодом, а не наоборот. Проверить: реализация закрывает реальный кейс? тесты зелёные? → значит реализация верна.

## Правило 35 — «Переписывать с нуля» vs «дописать»

Когда PM спрашивает «не проще ли всё переписать?» — сравнить честно:

**Переписывать НЕ нужно если:**
- Есть зелёные тесты (105+ тестов = огромная ценность, терять жалко)
- Архитектура (граф модулей, dataclasses, enum-ы) не менялась
- Аудит показывает только `CODE_OK` и `NOT_IMPL` (не `CONFLICT`)
- Новые R# — это дописывание функций поверх скелета, не замена старых

**Переписывать нужно если:**
- Аудит показывает `CODE_CONFLICT` — старая логика явно противоречит новому ТЗ
- Архитектура принципиально изменилась (граф модулей, способ хранения)
- Тестов нет или они покрывают устаревшее поведение

**Оценка для разговора с PM:** переписывание с нуля = 3-5× больше времени чем дописывание. «2.5 сессии на дописывание» vs «10 сессий + новые баги + новые несоответствия ТЗ».

## Правило 34 — explain_unclear: одна причина, решающая

При построении диагностики unclear-очереди — `explain_unclear()` должна называть **одну решающую причину**, а не перечислять все применимые:

```python
# Правило: если алиас найден — причина ТОЛЬКО «не матч», не «нет участников»
# Если алиаса нет — причина «не сматчился алиас», участники вторичны
```

**Питфолл:** перечисление всех причин вводит PM в заблуждение — он думает что участники «съели» алиас, хотя на самом деле алиас просто не нашёлся. Это ложная тревога которая приводит к неверному диагнозу и ненужным правкам.

## Правило 31 — Исследование по backlog-пункту: привязка к bk-NNN

Правильный chat_id группы Сирень Workspace: `-1004300127777`. Диагностика потерянных отчётов: `grep -a 'Chat not found' ~/.hermes/profiles/anthropic/logs/gateway.log`.

**Питфолл:** one-shot крон-задача с `next_run_at` в прошлом — не выполнится автоматически после рестарта gateway. Диагностировать: `last_run_at: null` + папка output не создалась. Восстановление: `cronjob(action='run', job_id=...)`. Если задача уже запущена — исправить deliver ДО завершения, иначе отчёт уйдёт на неверный адрес.

**Питфолл:** исправление deliver у уже запущенной задачи — `cronjob(action='update')` применяется только к следующему запуску. Если задача уже выполнилась и output есть в папке, но не доставился — читать output вручную: `cat ~/.hermes/profiles/anthropic/cron/output/<job_id>/*.md | grep -A 500 '## Response'`.
