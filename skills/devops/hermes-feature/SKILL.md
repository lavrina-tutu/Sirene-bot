# Паттерн: hermes-feature

## Overview

Единый процесс работы над фичами Hermes и USERTOOLS: от ТЗ и выбора варианта до кода, тестов, документации, диагностики и отката. Скилл фиксирует, кто пишет (Sonnet vs Opus), когда делать бэкап, как эскалировать, и что запрещено делать самостоятельно (правки security-конфига, рестарты gateway). Дополнительно: паттерн отладки (hermes-debug) и исследований (hermes-research), плюс handover контекста между инстансами.

## When to Use

Триггеры:
- «разработай», «новый инструмент», «напиши ТЗ», «MoveFrom*», «ТЗ v» — Блоки 0–4
- «ошибка», «баг», «не работает», «упало», «падает», «разберись», «починить», «сломалось» — Блок 7 (hermes-debug)
- «проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если» — Блок 8 (hermes-research)
- Задача с 3+ изменениями конфига/скиллов/инструментов — Блок 6А (QA)
- Запуск нового инстанса Сирени (новая VM, новый бот) — Блок 9 (handover)

Не для: правок стиля общения (см. `hermes-memory-hygiene`), простой рутины без ТЗ и вариантов.

## Блок 0: ТЗ (кратко)

- ТЗ пишет **Opus**, инициирует только Саша явным запросом.
- **Хранение:** один живой master-файл на инструмент → `WorkVault/Hermes-Backlog/TZ/<Tool>/<Tool>_TZ.md`. Точечная доработка → секция в master-файле, не новый файл. Независимая от инструмента → `TZ/_misc/TZ-<topic>-<YYYYMMDD>.md`.
- **Обязательные разделы:** Цель / Контекст / Шаги / Критерии успеха / Что НЕ трогать.
- **Согласование ТЗ ≠ команда на реализацию** — миграция/кодинг стартуют только по отдельной явной команде Саши («ок, берём в работу»).
- Неопределённость → Opus стопится, дополняет ТЗ предложением, ждёт ОК.
- Отчёт о ТЗ в чат — короткий (что поменялось + что требуется от Саши). Полный текст ТЗ не дублировать — Саша откроет файл сам.
- Открытые вопросы Opus выносит отдельным разделом «Открытые вопросы Саше» с рекомендацией + альтернативой, не выбирает «по умолчанию».
- Universal open-question protocol: во всех диалогах — сначала полный список вопросов, потом по одному, с рекомендацией и вариантами по номерам.

Полный набор правил (брифование, хранение материалов брифа, QA ТЗ, отклонения API от ТЗ, жизненный цикл файла) → `references/tz-workflow.md`. Родственный скилл: `tz-workflow`.

## Блок 1: Анализ вариантов

- **Критерии:** токены / безопасность / консистентность / поддерживаемость + специфичные для задачи.
- **Количество:** 2-3 лучших; слабые Opus отсеивает сам.
- **Подача:** сначала рекомендация с обоснованием → остальные кратко для справки.
- После выбора: уточняющие вопросы **по одному** → ждать «берём в работу». Саша может прервать уточнения и перейти сразу к работе.

**Completion criterion:** Саша сказал «берём в работу» по конкретному варианту.

## Блок 1А: Планирование *(приоритет — выполнять до Блока 2)*

**Перед любой реализацией Opus составляет пофайловый план:**
- Какие файлы создать / изменить
- Какие функции / классы / методы добавить
- Какие тесты написать (по одному на кейс)
- Промежуточные точки проверки с критерием завершения каждого этапа (по ТЗ если есть, по контексту если нет)

**ТЗ-файл только для задач с Python-кодом.** Для скиллов, конфигов, memory-правок — план Opus в чате (или временный файл), ТЗ-файл не нужен.

**Sonnet проходит промежуточные точки молча** — сверяется с планом сама, без отчётов Саше после каждого этапа.

**Completion criterion:** Саша сказал «берём в работу» по пофайловому плану.

## Блок 2: Реализация *(изменён 06.07.2026 — Sonnet пишет код)*

### Кто пишет
- **Sonnet** — пишет весь код по пофайловому плану Opus *(приоритет над всеми прежними правилами)*
- **Opus (fallback)** — только если Sonnet не справилась: архитектурная тупиковая ситуация или повторяющиеся необъяснимые ошибки. Sonnet даёт краткий вывод о причинах → **Саша решает** запускать ли Opus.

**Мелкое отклонение от плана** (≤2 файла, не меняет архитектуру) → Sonnet решает сама.
**Крупное отклонение** → Sonnet стопится, коротко сообщает причину → Opus делает доплан → Sonnet продолжает.

**Явный override Сашей:** один раз подсветить конфликт с правилом, при явном подтверждении — выполнять без дальнейшего сопротивления. Пример 06.07.2026: bk-098 ExchangeOrgLookup — Саша настоял на Sonnet после одного предупреждения.

### Чеклист перед первой строкой кода
1. ТЗ согласовано (или план в чате) + явное «берём в работу».
2. **Бэкап создан** (см. Блок 5).
3. Пофайловый план Opus существует и согласован.

### Фиксация решения
Opus обновляет ТЗ-файл (если есть): добавляет выбранный вариант + дату старта.

---

## Блок 3: Тестирование *(изменён 06.07.2026 — Sonnet тестирует)*

- **Тестирует Sonnet** по плану тестирования от Opus *(приоритет над прежними правилами)*
- **Мелкий баг** (≤2 файла, очевидная причина) → Sonnet чинит сама (1 попытка)
- **Крупный/архитектурный баг** → Sonnet фиксирует причину → **Саша решает** запускать ли Opus на hotfix-план → Sonnet применяет
- **Готово =** все точки проверки из плана Opus пройдены (✅/❌)
- Финальное «всё ок» говорит Саша.

---

## Блок 4: Документирование

- ТЗ-файл остаётся живым в `TZ/<Tool>/<Tool>_TZ.md` **пока инструмент используется**. Архивация — только когда сам инструмент выведен из эксплуатации, по явному решению Саши.
- **Скилл:** мелкая правка → Opus сам; новый раздел → предлагает Саше.
- **MEMORY:** Opus предлагает с объяснением, почему MEMORY а не скилл → Саша говорит ОК.

## Блок 5: Бэкапы и откат

### Когда создаётся
- Opus-задачи: всегда.
- Sonnet-задачи: только если затронут `config.yaml` или `jobs.json`.

### Состав
`config.yaml` + `jobs.json` + `skills/` + `MEMORY.md` + `USER.md` + файлы специфичные для задачи.

### Путь
Linux VM: `~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`.
Для бэкапов отдельных компонентов (unit-файлы, `rclone.conf` и т.п.) — рядом с файлом: `<file>.bak-<purpose>-YYYYMMDD-HHMMSS`.

### Хранение
2 недели, 1 бэкап в день (самый ранний). Self-check чистит автоматически.

### Откат
- **Авария** → Opus откатывает сам немедленно, сообщает Саше.
- **Плановый** → Opus предлагает какой бэкап, ждёт ОК.

## Блок 5А: Минимальное вмешательство в инфраструктуру

**Никогда не делать самостоятельно** (только по явной команде Саши):
- Менять `guest_mode`, `require_mention`, `allowed_chats` в `config.yaml`.
- Перезапускать gateway (даже после правки конфига).
- Ставить cron-рестарты «на потом».
- Применять рекомендации аудита/Opus без явного «делаем» от Саши, даже если рекомендация очевидна.

**Правило рестарта gateway:**
- Рестарт нужен после правки `config.yaml` или кода gateway.
- Делать ТОЛЬКО из внешнего шелла: `bash ~/.hermes/scripts/restart_gateway_MANUAL_ONLY.sh`. НЕ через no_agent cron (SIGTERM-петля, инцидент 26.06.2026).
- Не ставить рестарт-крон без явной просьбы — сообщить «нужен рестарт, поставить?».
- После рестарта предупредить: «через ~1 мин gateway перезапустится».

**Почему:** каждый рестарт прерывает активный диалог; несколько рестартов подряд = Саша не получает ответы и теряет доверие.

Примеры нарушений: `require_mention: true` применён по рекомендации → бот замолчал в группе; cron-рестарты gateway ставились сами → прерывали диалог. Детали и особо опасные параметры → `references/config-qa.md`.

## Блок 6: Эскалация

**Стоп + пишет Саше (даже ночью):**
1. Критическая поломка.
2. Неопределённость в ТЗ, которую нельзя решить самостоятельно.

**Ночью:** сохранить состояние в ТЗ-файл → «жду решения по [вопрос]» в TG → ждать утра.

**Молчит:** рутинные cron без ошибок.

## Блок 6А: QA-проверка перед «Готово»

Обязательный финальный шаг **любой задачи с 3+ изменениями**: настройка конфига, подключение скиллов, разработка инструмента, финализация ТЗ.

**Процесс (4 шага):**
1. Собрать чек-лист через Opus (`delegate_task` → `claude-opus-4-7`): корректность изменений, смежный функционал, логические противоречия (особенно память vs конфиг).
2. Исправить ❌ пункты.
3. Повторить (максимум 3 попытки).
4. Все ✅ → короткий отчёт. Остались ❌ после 3 попыток → откат + доклад.

Полные детали (когда применять, откат конфига, опасные параметры, типичные проблемы) → `references/config-qa.md`.

## Блок 6Б: Делегирование субагентов

### Инструмент запуска

| Задача | Модель | Инструмент | Таймаут |
|---|---|---|---|
| Opus: ТЗ / пофайловый план | claude-opus-4-7 | `cronjob(repeat=1)` | — |
| Opus: сложная реализация (fallback) | claude-opus-4-7 | `cronjob(repeat=1)` | — |
| Opus: инфраструктурный анализ | claude-opus-4-7 | `cronjob(repeat=1)` | — |
| Sonnet: реализация по плану (>5 мин или многофайловая) | claude-sonnet-4-6 | `cronjob(repeat=1)` | — |
| Sonnet: короткая задача (<5 мин) | claude-sonnet-4-6 | `delegate_task` | 300с |
| Haiku: справочный / терминальный запрос | claude-haiku-4-5 | `delegate_task` | 120с |

**Никогда не использовать `delegate_task` с Opus** — reasoning_effort=high держит родительский стрим → gateway-зависания ("Stream stale for 180s"). Всегда `cronjob(repeat=1)`.

### Toolsets в кронах (сокращают контекст субагента)

| Задача | enabled_toolsets |
|---|---|
| Opus: ТЗ / план (читает файлы, не запускает код) | `["file", "terminal"]` |
| Sonnet: реализация кода | `["file", "terminal"]` |
| Sonnet: тестирование | `["file", "terminal"]` |
| Исследование / аудит с web | `["file", "terminal", "web"]` |

Не добавлять `web` если не нужен — каждый лишний toolset увеличивает контекст сессии.

### Что обязательно передавать в промпт субагента

1. **Роль и среда** — «Ты Opus/Sonnet на VM hermes-agents.devel.tutu.ru»
2. **Точные абсолютные пути** — `/home/tkachenkoav/...`, не `~/...` (в кронах `~` может не резолвиться предсказуемо)
3. **Полный контент ТЗ или плана** — не ссылку на файл, а текст; субагент не должен делать дополнительные lookup'ы
4. **Граница автономности** — явное правило: «механическое (форматирование, перенос, дозаполнение) — делай сам; семантическое (удаление блока, изменение архитектуры) — СТОП, опиши причину»
5. **Формат отчёта** — «не выводить полный текст файлов, только сводку изменений»
6. **Явные запреты** для безопасности — «не удалять contacts.enc и .env», «не менять security-параметры config.yaml»

### Чего НЕ нужно передавать

Субагент уже получает через систему Hermes: SOUL.md, MEMORY, USER PROFILE, системный промпт. Не дублировать их в промпте — это увеличивает контекст без пользы.

### Бэкап перед запуском субагента

Sonnet-задачи: бэкап если затронуты `config.yaml` / `jobs.json`.
Opus-задачи: бэкап всегда (`~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`).

## Блок 7: Диагностика и отладка (hermes-debug)

Применять при: что-то сломалось, неожиданное поведение.
Триггеры: *«ошибка», «баг», «не работает», «упало», «падает», «разберись», «починить», «сломалось»*.
Модель: **Sonnet** (не Haiku, не Opus — если не нужна глубокая архитектурная правка).

**Алгоритм:** Воспроизвести → Root cause (порядок: плейсхолдеры `.env` → batch API → broken imports/venv → дублирование правил → устаревший скилл) → Минимальная правка + бэкап → Регресс-тест → Фиксация в Pitfalls скилла.

**Эскалация к Opus:** root cause в архитектуре, правка ядра Hermes, не воспроизвелось за 2 попытки.
**Эскалация к Саше:** данные могут быть повреждены, production down, нужен доступ к внешнему сервису.

**Debug pitfalls:** `routing:` в `config.yaml` — мёртвая секция. `hermes gateway restart` → `UnicodeDecodeError` в stderr — косметика. `hermes skills list` не видит скилл — проверить `version` и `author` в frontmatter. `cronjob(action='update')` не умеет сбрасывать `no_agent` — менять в jobs.json напрямую.

## Блок 7А: Двухэтапный Opus-анализ перед изменением конфигурации

Применять при: изменение systemd-юнитов, rclone-конфигов, синхронизации, инфраструктурных настроек.

**Паттерн:**
1. **Opus-крон №1** — только читает файлы, оценивает риски, даёт рекомендации с обоснованием.
2. Sonnet пересказывает результат Саше, получает подтверждение.
3. **Opus-крон №2** — реализует по согласованному ТЗ.

**Почему не сразу реализовывать:** инфраструктурные изменения (systemd, rclone, cron) могут иметь неочевидные риски (race condition, `--size-only` пропускает изменения). Opus может найти питфоллы, которые меняют план.

**Формат промпта для анализа:** «оцени риски → вывод (безопасно/требует доработки/не рекомендую) → ТЗ если применимо».

**Апгрейд самого upstream hermes-agent** — отдельный, более детальный паттерн → `references/upstream-cutover-procedure.md`.

## Блок 8: Исследования и анализ (hermes-research)

Применять при: нужно собрать данные, найти паттерн, оценить варианты — **без изменений кода**.
Триггеры: *«проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если»*.
Модель: **Opus** для глубокого (архитектура, API, код); **Sonnet** для быстрого (история, конфиги).

**Алгоритм:** Scope → Сбор (`session_search` 1-3 слова FTS5, параллельные запросы; файлы через grep; API только чтение) → Анализ (таблица, выводы отдельно) → Рекомендации (2-3 варианта с оценкой).

**НЕ делать:** не менять код/конфиги/скиллы, не делать выводы без данных, не запускать API без ОК Саши.

---

## Блок 9: Передача контекста между инстансами (handover)

Применять при: запуск нового инстанса Сирени (новая VM, новый бот, новая среда).

**Паттерн:** создать `~/.hermes/handover.md` на **источнике** перед переносом:
1. Кто ты и кто Саша (3-4 строки).
2. Статус миграции / последнего большого события.
3. Что нужно сделать в первую очередь (нумерованный список).
4. Открытые задачи из бэклога (кратко, по секциям).
5. Важные пути на новой машине.
6. Ключевые секреты и где они лежат.
7. Стиль общения (основные правила).

**На новом инстансе:** при первом запуске прочитать `handover.md` (`read_file`), войти в контекст, затем удалить или переименовать файл.

## Common Pitfalls

Компактный список. Расширенные разборы — в references (пометки в скобках).

1. **`hermes skills list` не видит новый скилл** — обязательные поля frontmatter: `name`, `description`, `version`, `author`, `tags`, `platforms: [windows, linux, macos]` (не `[all]` — не работает). Если не помогло — вручную добавить запись в `.usage.json` (шаблон копирует поля с другого скилла: `use_count/view_count/patch_count=0`, `state=active`, `pinned=false`), затем рестарт gateway.
2. **Бэкап обязателен до первой строки кода** — Opus создаёт бэкап в `_Archives/hermes-backup-YYYYMMDD-HHMMSS/` перед любыми изменениями Opus-уровня.
3. **Правка security-sensitive параметров `config.yaml`** — прямая запись через patch/write_file блокируется. Использовать `hermes config set telegram.guest_mode false` / `hermes config set telegram.require_mention true`. Работает для `telegram.*`, `delegation.*`, `fallback_providers`. (config-qa.md)
4. **Секция `routing:` в `config.yaml` не работает** — код Hermes её не читает. Молча игнорируется. Для реальной маршрутизации — плагин/хук или правила в MEMORY.md.
