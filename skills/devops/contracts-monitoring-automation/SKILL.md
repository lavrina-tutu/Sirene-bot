# Автоматизация мониторинга договоров ТУТУ — класс

Класс задач: инструмент/скилл должен **наблюдать за вопросами по договорам** (JIRA-комментарии, Loop, почта), готовить **проект ответа из фактов** и постинть наружу **только после явного OK владельца**.

Эталон реализации: ContractAssistant (ТЗ v0.3.0, user-owned skill, инструменты `~/USERTOOLS/ContractAssistant/`). Этот скилл — curator-проводник по классу: архитектурные решения, анти-паттерны, дизайн кронов, гейт безопасности.

## 🔒 Главный инвариант класса: пост наружу ТОЛЬКО по OK

**Никакой ответ наружу (JIRA-комментарий, Loop, почта, мессенджеры) без прямого явного OK владельца.** Для каждого инструмента:
- Два рубежа: (1) `auto_post: false` + `auto_post_slugs: []` — даже `true` не обходит пост; (2) явный OK на карточку проекта ответа.
- Крон **никогда** не передаёт `--apply` / `--sasha-ok`. POST — только интерактивно через скилл/CLI (`ca post --apply --sasha-ok`) после явной фразы.
- Ответ строится **только с цитатой** (`cite` на секцию агрегата/регламента). Нет цитаты → `unknown`, не выдумывать суммы/ИНН/комиссию/сроки.

## Дизайн кронов: отдельные job, НЕ встраивать в существующий мониторинг

Ключевой урок (решение 08.09.2026, вариант CA): похожий источник ≠ общий процесс.

**Симптом:** новый мониторинг (JIRA) очень похож на существующий MFL/Exchange (Loop/почта). Соблазн — «привязать к имеющимся кронам» (не плодить). **Нельзя встраивать в `mfl_*.py` как ExchangeMonitor**, если у нового контура другой жизненный цикл:
- лишний источник (JIRA), которого нет у MFL;
- свой watermark (`jira_last_ts`), изолированный `state/watermark.json` — не общий с MFL;
- окно работы (пн-пт 8-20), а не 24/7;
- есть LLM/эвристика classify + пост только по OK.

**Техническая причина:** Hermes отдаёт stdout в `deliver` **после exit** процесса. Любой встроенный вызов внутри `mfl_urgent_check.py` удлинит тик срочных Loop и сорвёт их SLO («<30с»). `try/except` гасит исключение, не время.

**Решение:** новый контур — **отдельные job** с тем же *рисунком* расписания, но со **сдвигом** минут, чтобы не бить существующие источники в ту же секунду:
- urgent: `1-59/3 8-20 * * 1-5` (vs MFL `*/3` = `0,3,6,…` 24/7)
- digest: `5 8-20 * * 1-5` (vs MFL `0 8-20` = `:00`)

Крон-скрипт самодостаточен: хардкод `_ROOT`, точечная загрузка .env (`load_env_keys` только нужных ключей, не `source` всего файла), окно 8-20 как защита в скрипте (вне — `exit 0` без poll), fail-quiet → ErrorBus, свой watchdog.

## Watermark: двигать всегда

- Свой изолированный watermark на каждый источник (`jira_last_ts`, `loop_last_ts`, `exchange_last_ts` — int ms).
- **Даже на пустом тике watermark двигается** (`max_ts if had else tick_now`) — иначе вечный lookback.
- Не читать/писать watermark и loop_rules.yaml MFL (критерий успеха: mtime/хеш MFL не меняется).

## Факты как источник ответа (канон)

- Файл-агрегат договора: `WorkVault/Entities/Contracts/<slug>/<slug>.md` — 11 обязательных H2 (Задачи JIRA, Контрагент, Суммы и сроки, ЮЛ и роли, Закупочная процедура, Выбор поставщика, Предмет/состав, Открытые вопросы, Журнал Q&A, Переписка, Источники).
- Регламент закупок: `Rules/purchase-rules.md` — пороги (до 5 млн: владелец бюджета + ГД, Комиссия не нужна), RACI.
- Поля Service Desk JIRA (`customfield_42092` ЗК, `customfield_42094` решение комиссии) **не редактируются через REST API** (PUT sdesk→500, PUT api/2→400). Через API только комментарий; правка полей — вручную в UI.

## Пошагово (проектирование нового мониторинга договоров)

1. Определи источники (JIRA comments по jira_keys, Loop DM/mention, почта).
2. Спроектируй `ca_watch` (poll, no_agent) + `ca_answer` (retrieve→classify) как **один** no_agent процесс (не плоди agent-job на пустой inbox).
3. Разведи watermark по источникам, свой state/.
4. Поставь **отдельные** job со сдвигом расписания, deliver в тот же Messages-топик, что и существующий мониторинг (единая лента для владельца).
5. Встрой fail-quiet → ErrorBus (`--tool <имя>`), exit 0 — падение источника не роняет соседние контуры.
6. Зафиксируй гейт OK: крон без `--apply/--sasha-ok`; пост — интерактивным CLI/скиллом после явной фразы.

## Pitfalls

- Встраивание обогатителя мониторинга в чужой скрипт (ExchangeMonitor-паттерн) для контура с другим ЖЦ — **архитектурный отказ** (SLO, watermark, окно 8-20, OK-гейт).
- `ca_answer` отдельным agent-job каждые 3 мин на пустой inbox — лишний спавн сессии. Склей watch+answer в один no_agent.
- Пустой тик без сдвига watermark → вечный lookback от старой точки.
- Ответ с суммой/ИНН/комиссией без цитаты → галлюцинация в прод-канале. Known только с `cite`.
