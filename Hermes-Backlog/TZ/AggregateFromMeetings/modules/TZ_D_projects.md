# Модуль D. Обновление проектов

## Назначение

Модуль D отвечает за **P3: Project Status** — накопленную историю проекта за все встречи. Это база данных проекта, источник для PM-отчётов на еженедельных 1-1 с начальством.

В отличие от G.Срез (срез по одной встрече), модуль D:
- накапливает информацию за всё время проекта,
- является источником истины по решениям и задачам,
- не генерирует срезы — генерирует D-артефакты.

## Карточка модуля

🎯 **Функция:** Применить сигналы из модуля C к артефактам проекта в `Projects/<slug>/ai/` — накапливать решения, задачи, риски, историю.

⬅️ **Вход:** `MeetingSignals` от модуля C (decisions, action_items, blockers, risks, status_signals)

➡️ **Выход:** <!-- изменено 2026-06-29: risks.md, семантика action_items.md/timeline.md -->
- `Projects/<slug>/ai/decisions.md` — зафиксированные решения + блокеры (`[blocker]`); редко меняется
- `Projects/<slug>/ai/risks.md` — **новый артефакт (PD-031/038)**: накопительный реестр рисков проекта/инициативы
- `Projects/<slug>/ai/action_items.md` — **Tasks-query-агрегатор (PD-035)**: задачи физически живут в срезах G, здесь — query без дублирования
- `Projects/<slug>/ai/timeline.md` — **статический список встреч** (дата + wikilink на summary), генерируется при каждом прогоне (PD-043)
- Обновление служебных полей `card.md` (`last_meeting`, `meetings_count`, `last_processed_at`)

🔗 **Зависимости:** C (сигналы), A (MeetingPackage), G.Срез (потребитель в Фазе 2)

### Bootstrap vs Инкремент <!-- изменено 2026-06-29: Opus убран, единый Haiku-проход -->

- **Bootstrap (первый запуск):** обработка ~940 FF-файлов; для классификации C используется подмножество — **478 summary с датой ≥ 12.08.2025** (M9). **Единый поштучный проход Haiku** от ранней встречи к актуальной (PD-028/030/036): из каждого среза G пополняются `decisions.md` / `risks.md`, накопленный инкремент передаётся контекстом. Двухшаговой Opus-агрегации больше нет (см. TZ_C «Архитектура (единый проход)»). Проекты с golden ref дополнительно сверяются Sonnet (предложение задач к закрытию → подтверждение PM, PD-041).
- **Инкремент (после каждой встречи):** обработка одной новой встречи тем же проходом. PM Notes из среза G имеют главенствующий приоритет (PD-037/044). Идемпотентность: встречи не пересинкиваются (PD-037); дедупликация по нормализованному ключу сигнала. Модель в проде — Sonnet (OQ-002, переключение вручную).

### risks.md (PD-031/038)

- Путь: `Projects/<slug>/ai/risks.md`. **Только для проектов/инициатив** — не создаётся для синков, 1-1, adm.
- Инициализация: из брифа/устава проекта (Confluence, «встреча №0»), если есть; иначе пустой файл.
- Семантика: **накопительный источник истины** — хронология, зачёркивание (`~~...~~`) закрытых/смягчённых рисков.
- Источник: Haiku из `Bullet points` + `Notes` FF-summary (отдельного блока Risks в summary нет, PD-034). Авто-риски помечаются `confidence` + `<!-- src: inferred -->`; PM подтверждает/снимает через PM Notes (PD-039).
- Дедуп по ключу `(normalized_text, type=risk, slug)` (PD-038).
- Срез G даёт per-meeting view рисков; `risks.md` — накопленный (аналогия decisions.md ↔ срез).
- Recall авто-рисков проверяется на golden ref `ml-platforma` (Фаза C).

### Блокеры в decisions.md (PD-032)

- Блокеры пишутся в `decisions.md` (не в action_items.md, не в risks.md).
- Формат строки: `- [blocker] текст · статус · срок <!-- key: ... -->`.
- Префикс `[blocker]` машиночитаем; дедуп-ключ включает `type=blocker`; закрытие = зачёркивание.

### action_items.md = Tasks-query (PD-035)

- **Источник истины задачи — срез G**, где задача физически записана с тегами проекта/ответственного (Haiku пишет задачу в срез, не в `action_items.md`).
- `action_items.md` — **агрегатор-query** (Obsidian Tasks/Dataview), собирает задачи по slug без дублирования.
- Закрытие чекбокса в query правит файл-источник (срез G) — единая точка закрытия.
- **Иммутабельность срезов переосмыслена:** закрытие чекбокса (признак выполнения) — допустимо, это не удаление и не перезапись содержания (см. TZ_G §4).
- **Дедуп задач между срезами** (одна задача на N встреч = одна запись, PD-019) — **в scope MVP** (решение Q-A3 от 30.06; пересматривает PD-035). Реализуется в Фазе B (IQ-B12), блокер перед GATE H6. Механизм — stable-id задачи, устойчивый между срезами; одна логическая задача = один чекбокс в query. <!-- изменено 2026-06-30: дедуп в MVP -->
- Глобальный список по всем проектам/людям — отдельный Tasks-query.
- People-аналог (`commitments.md`) — та же модель агрегатора.
- **Срок по умолчанию (PD-023/Q-A1):** если у задачи нет явного срока — Haiku ставит `дата встречи + 5 рабочих дней`, метка `📅 (inferred)`. Значение `???` не используется (отменено). PM правит через PM Notes. <!-- изменено 2026-06-30 -->

### Связь G→D и реконсиляция PM Notes (PD-044, PD-046/049-052)

<!-- изменено 2026-06-30: модель PM Notes reconciler -->

- Двунаправленность G↔D **осознанна и допускается**: D формирует контекст, а Haiku при обработке среза G переносит информацию (с приоритетом PM Notes) обратно в блоки D (`decisions.md` / `risks.md`) и в задачи среза (Tasks).
- **Два шага каждого прогона (PD-046/050):** перенос PM Notes в карточки делает **Шаг 1 — `pm_notes_reconciler`** (см. TZ_F), **до** обработки новых встреч (Шаг 2). Запуск всегда после MoveFromFF, даже без новых встреч.
- **Окно (PD-050):** сканируются срезы с изменёнными PM Notes за **5 календарных дней** (параметр конфига) + ручной запуск `--only-pm-notes <slug | snapshot>` для поздних правок.
- **Детект изменений (PD-051):** хэш по каждому блоку `### PM Notes (tasks|decisions|risks)`, ключ `(snapshot_path, block_index)` в `state.json.pm_notes_hashes`. Один изменённый блок → обновляется только соответствующий раздел карточки (decisions / risks / задачи). Не менялось → no-op без LLM.
- **Старшинство (PD-049):** обработка хронологическая (от старого к новому); более свежий срез перекрывает раннюю PM Note по стандартным правилам резолва конфликтов (см. ОВ 3 ниже). Конфликт-пометок нет — PM переопределяет в PM Notes нового среза.
- **Полномочия PM Notes (PD-052):** CRUD над задачами / решениями / рисками (создать — в т.ч. не найденное роботом; изменить; удалить/зачеркнуть); «комментарий» — без структурного эффекта. Непонятное → дайджест PM.
- Зафиксировано также в TZ_F (алгоритм reconciler) и TZ_G (срез — носитель PM Notes).

### timeline.md (PD-043)

- Статический список wikilink-ов: `- <YYYY-MM-DD> [[Meetings/<summary>]]`, отсортированный по дате.
- Генерируется **целиком при каждом прогоне**; не Dataview-query, не зависит от frontmatter FF-summary.
- Не лента LLM-сигналов (PD-025).

## Участники проекта в AnywhereContacts (M10, добавлено 2026-06-21)

Помимо записи D-артефактов в `Projects/<slug>/ai/`, модуль D обновляет **участие людей в проектах** в AnywhereContacts — поле `project_roles` контакта (см. AC `schema.py`; входит в `CUSTOM_FIELDS`, коннекторы Exchange/Zulip его не перезаписывают).

### Правило записи

Для каждой обработанной project-встречи (route=`project <slug>` или route=`multisync <slug>`):

1. Собрать список participants из `MeetingSignals` — речь идёт об уже отрезолвенных AC-логинах (S2 ∪ S3 из секции «Резолв участников» в TZ_E). Только участники с `status=resolved` (high|medium). Tentative-резолвы — пишем (как и в E), `ambiguous/not_found` — пропускаем, попадают в `unclear_names`.
2. Для каждого `login` вызвать:
   ```python
   store.add_project_role(login=login, slug=slug, source="aggregate_from")
   ```
3. Метод атомарный и идемпотентный: если у контакта уже есть активная запись (`slug==X AND until is None`), повторный вызов — no-op (`False`). Это значит, что прогон bootstrap по 478 summary даёт корректный финальный список без дублей; инкремент тоже безопасен.
4. **Роль не угадываем** — `role=None`. PM может проставить руками (`pm`, `analyst`, `developer`...) через CLI/прямую правку `notes`-pipeline или TG-команду фазы 2.
5. **Закрытие участия (`close_project_role`)** — модуль D **не делает** автоматически. Логика «человек ушёл с проекта» — приоритет фазы 2 (см. открытые вопросы).

### Что это даёт

- `People/{login}/card.md` → `projects: [...]` frontmatter — генерируется из активных `project_roles` контакта.
- Перекрёстная навигация: dataviewjs в `Projects/<slug>/card.md` секция «Команда» = `AC.contacts WHERE 'slug' in project_roles[until=null].slug`.
- Источник правды по «кто на каком проекте» — **AnywhereContacts**, не frontmatter Obsidian (Obsidian — derived view).

### Идемпотентность и порядок

Вызовы `add_project_role` идут **после** записи D-артефактов в рамках одной транзакции обработки встречи. Если запись в AC падает (file lock / шифрование) — D-артефакты уже на диске; повторный прогон встречи безопасен (идемпотентность по `(login, slug)` активной записи).

## Три выходных продукта системы (контекст)

Модуль D отвечает за **P3** в системе трёх продуктов:

| Продукт | Кто отвечает | Аудитория |
|---------|--------------|-----------|
| P1: PM Dashboard | Модуль G «Срез» | только PM |
| P2: Meeting Minutes | Модуль G «Срез» → PM → Confluence | команда + заказчик |
| **P3: Project Status** | **Модуль D «База»** | **PM + начальство (1-1)** |

PM ведёт еженедельные 1-1 с начальством по проектам. На 1-1 PM открывает D-артефакты в Obsidian и зачитывает статус.
