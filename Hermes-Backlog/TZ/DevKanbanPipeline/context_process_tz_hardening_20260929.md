## 1. ТРЕБОВАНИЕ САШИ ПО МОДЕЛИ ПРОЦЕССА (УТВЕРЖДЕНО, В НОВЫЙ КАНОН)

1. **Оркестрация плана — только на стороне Сирени-оркестратора.** С оркестратора весь процессный спрос. Решения о ходе процесса принимают только Саша и оркестратор, и только **на старте процесса**, на основании обсуждаемого кейса (доработка/новая разработка/исследование/починка бага и т.д.).

2. **Архитектор выполняет поставленную оркестратором задачу беспрекословно.** Ему дают полный контекст. Он отдаёт только: ТЗ, или план, или вопросы Саше. **Архитектор НЕ принимает решений о ходе процесса, НЕ строит граф, НЕ разворачивает фазы, НЕ решает какой граф/кейс.**

3. **Граф строит оркестратор** (Сирень). Решение о кейсе и построении графа принимается на старте совместно Сашей и оркестратором.

4. **Ревизор (REV:tz/REV:plan) проверяет** качество ТЗ/плана, возвращает на доработку. Не решает ход процесса.

## 2. ОПРЕДЕЛЕНИЯ (СОГЛАСОВАННЫЕ, ВНЕСТИ В ТЗ)

- **Граф** — развёрнутый пошаговый план работы над одной задачей. Одна задача = один граф. Фазы выполняются строго по очереди (одна завершилась → следующая началась).
- **Карточка** — один шаг внутри графа. У каждой карточки свой тип и ответственность. Соединены в цепочку: следующая начинается, когда предыдущая полностью готова.
- **Фаза** — шаг графа. Название указывает действие: TZ:patch=написать ТЗ-правку, HF:impl=написать код, REV:tz=проверить ТЗ ревизором, GATE:done=финальная приёмка.

## КЕЙСЫ (типы работ) — ПОЛНЫЙ СПИСОК (внести в ТЗ)

1. DEV — новая разработка (новый инструмент/фича с нуля).
2. CHANGE — доработка существующего (полный цикл).
3. CHANGE-LIGHT — лёгкая доработка, ≤3 файла кода+тест+скилл, без новых сущностей/cron/.env.
4. BUGFIX — починка бага (сначала диагностика DX, затем ТЗ→реализация).
5. BUGFIX-LIGHT — лёгкий баг, ≤3 файла кода+тесты, вне общих модулей.
6. RESEARCH — исследование/анализ без кода (только разобрать и доложить).
7. MIGRATION — миграция (перенос данных/сущностей по замороженной схеме).
8. DECOMM — удаление/вывод из эксплуатации инструмента.
9. SKILL-DEV — создание нового скилла.
10. SKILL-CHANGE — правка/удаление существующего скилла.

## ФАЗА ТЕСТИРОВАНИЯ (СОГЛАСОВАНО)

Тестирование НЕ выносится в отдельную роль. Архитектор на фазе плана (HF:plan) пишет план разработки И тестирования (таблица IAC с проверками). Исполнитель (composer) пишет код и сам гоняет тесты (HF:test) по плану архитектора, молча. Отчёт AC — на GATE:done. Решение Саши: «нет, тестирование пока не выносим в отдельную [роль]».
