# Модуль G. «Срез»

## Назначение

Генерация среза состояния сущности (проекта / человека / синка) после каждой встречи. Срез **иммутабелен по содержанию** (контент не перезаписывается), но допускает **закрытие чекбоксов задач** как признак выполнения (PD-035, см. §«Иммутабельность и задачи»). Два выходных продукта:
- **P1: PM Dashboard** — Warnings + аналитика, только для PM
- **P2: Meeting Minutes** — протокол встречи, PM модерирует → Confluence (Фаза 2)

Перенесён из отдельного инструмента `Tools/StatusSnapshot/` в состав Epic AggregateFromMeetings как модуль G.

## Карточка модуля
🎯 **Функция:** По одной встрече + контекст сущности → иммутабельный snapshot-файл. Три шаблона по типу встречи: `project-snapshot`, `1on1-snapshot`, `sync-snapshot`
⬅️ **Вход:** FF summary новой встречи + card.md сущности (Projects/People/Syncs) + предыдущий snapshot + PM-заметки из него + вызов от F.Дирижёр после fan_out по scope
➡️ **Выход:** snapshot-файл в папке сущности (`Projects/{slug}/snapshots/`, `People/{login}/snapshots/`, `Syncs/{slug}/snapshots/`)
🔗 **Зависимости:** A.Сборщик (данные встречи), D.База/E.Люди/H.Синки (card.md + контекст), F.Дирижёр (вызывающий)
📋 **Статус:** ✅ закрыт

| `MeetingPackage.route` | G запускает | project-snapshot для упомянутых проектов? |
|---|---|---|
| `project` | `project-snapshot` для основного `project_slugs[0]` | — |
| `1on1` | `1on1-snapshot` для пары контактов | — |
| `multisync` | **только `sync-snapshot`** для `sync_slug` | ❌ **НЕ генерируется** (ВП4 = Вариант А). PM видит затронутые проекты через D.База + секцию «Затронутые проекты» в самом sync-snapshot. |
| `unclear` | G НЕ вызывается | — |

⚠️ **Важно:** правило `multisync → только sync-snapshot` отменяет любые более ранние формулировки «G запускается для всех route project/1on1/multisync» в смысле «всегда генерируем project-snapshot для каждого затронутого проекта». Для project-снапшотов из встречи синка использовать D.База + Затронутые проекты в sync-snapshot.

## Иммутабельность и задачи (обновление 29.06)

### Иммутабельность переосмыслена (PD-035)

- Срез **иммутабелен по содержанию**: сгенерированный текст секций не перезаписывается, файлы не удаляются, алиасов `latest` нет.
- **Исключение — чекбоксы задач:** закрытие чекбокса (`- [ ]` → `- [x]`) допустимо, это признак выполнения, а не удаление/правка содержания. Tasks plugin при закрытии чекбокса в query физически правит срез-источник — это разрешённая операция.

### Задачи физически живут в срезе (PD-035)

- Haiku пишет задачи **в срез G** (с тегами проекта `#<slug>` и ответственного), **не** в `action_items.md` напрямую.
- `action_items.md` (D) / `commitments.md` (E) — Tasks-query-агрегаторы по срезам (см. TZ_D «action_items.md = Tasks-query»).
- Закрытие задачи из любого query правит срез-источник.
- Дедуп задач между срезами — отдельная задача разработки, не MVP (PD-035/PD-019).

### Поток G→D и PM Notes (PD-044, PD-046/049-052)

<!-- изменено 2026-06-30: reconciler -->

- При обработке среза Haiku переносит информацию из среза (с **приоритетом PM Notes**, PD-037) в блоки D — `decisions.md` / `risks.md`. Связь G→D допускается осознанно (раньше планировалась только D→G в Фазе 2).
- **Срез — носитель PM Notes:** PM пишет заметки в блоки `### PM Notes (tasks|decisions|risks)` среза (формат PD-053…058, см. §5). Их применяет к карточкам **Шаг 1 — `pm_notes_reconciler`** (см. TZ_F), отдельно от обработки новых встреч.
- **Окно 5 дней + ручной запуск**; детект по хэшу блока `(snapshot_path, block_index)` — изменённый блок обновляет только свой раздел карточки (PD-050/051).
- **Старшинство — хронология (PD-049):** свежий срез перекрывает раннюю PM Note; PM переопределяет в новом срезе. Конфликт-пометок нет.
- **CRUD (PD-052):** PM Note может создавать/изменять/удалять задачи, решения, риски; «комментарий» — без структурного эффекта.

### Риски и блокеры в срезе

- Секция «⚠️ Риски» среза = per-meeting view; накопительный реестр — в `risks.md` (D, PD-031/038).
- Секция «🚫 Блокеры» среза = per-meeting view; источник истины блокеров — `decisions.md` с префиксом `[blocker]` (D, PD-032).

## Три шаблона

### project-snapshot

**Путь:** `Projects/{slug}/snapshots/{slug}-snapshot-YYYY-MM-DD.md`

#### 1. Назначение шаблона
Иммутабельный срез состояния проекта по одной встрече: что решили, что в работе, что блокирует, какие предупреждения для PM. Заменяет `StatusSnapshot` MVP.

#### 2. Триггер
Вызывается F.Дирижёром после `D.База` для встреч с `route=project`. Для встреч с `route=multisync` project-snapshot **не** создаётся (M7 / ВП4) — см. таблицу «Правила выбора шаблона».

#### 3. Входные данные
- FF summary новой встречи
- Предыдущий срез (самый свежий `{slug}-snapshot-{YYYY-MM-DD}.md`)
- Карточка проекта (`Projects/{slug}/card.md`)
- PM Notes из предыдущего среза (блоки `### PM Notes (...)`) — используются как контекст генерации

#### 4. Имена файлов
- Шаблон: `{slug}-snapshot-{YYYY-MM-DD}.md`
- Расположение: `Projects/{slug}/snapshots/`
- «Текущий» = самый свежий файл по имени
- Нет перезаписей содержания, нет алиасов latest. Исключение — закрытие чекбоксов задач (PD-035, см. «Иммутабельность и задачи»). <!-- изменено 2026-06-29 -->

#### 5. PM Notes — блоки и маркеры (PD-053..058)

Вместо HTML-комментариев `<!-- pm: -->` каждый смысловой блок среза имеет
**явный подзаголовок** с лейблом типа сущности:

```markdown
## Tasks
- [ ] Задача A 📅 2026-07-05 @Иванов ^trx11
- [ ] Задача B 📅 2026-07-10 @Петрова ^trx12

### PM Notes (tasks)
_ADD: Запросить KPI у аналитики до 12.07 @Сидоров
_DELETE: trx12
_UPDATE: trx11 → Срок сдвинут на 15.07 @Козлов

## ✅ Задачи (добавлено PM)
- [ ] Запросить KPI у аналитики до 12.07 @Сидоров 📅 2026-07-12 ^trx13

## Decisions
- Перейти на микросервисную архитектуру — принято 2026-06-15 ^trx1
- Заморозить фичи до релиза — принято 2026-06-28 ^trx2

### PM Notes (decisions)
_UPDATE: trx2 → Заморозка снята, команда продолжает разработку
_ADD: Выбрать вендора для интеграции до конца квартала

## Risks
- 🔴 Нет выделенного QA — высокая вероятность ^trx1
- 🟡 Зависимость от внешнего API — средняя вероятность ^trx2

### PM Notes (risks)
_DELETE: trx2
_ADD: Риск потери ключевого разработчика в июле
```

**Правила маркеров (PD-056):**
- `_ADD: <текст>` — добавить новую запись в конец секции (для tasks — в `## ✅ Задачи (добавлено PM)`, Q-B1/PD-053)
- `_DELETE: <id>` — **физически удалить** строку из среза (была ошибкой распознавания, Q-B2/PD-054)
- `_UPDATE: <id> → <новый текст>` — перезаписать текст записи на месте, без истории (Q-B3/PD-055)
- Маркер `- [x]` на задаче = выполнена (штатное закрытие, Tasks plugin)

**Тип сущности** определяется заголовком `### PM Notes (tasks|decisions|risks)` — лейбл страхует от поломки разметки.

**Маппинг секций среза → блоки PM Notes (Q-C1, PD-056):** ровно 3 блока по D-артефактам:

| Секция среза | Блок PM Notes |
|---|---|
| ✅ Решения + 🚫 Блокеры | `### PM Notes (decisions)` (блокеры живут в decisions.md, PD-032) |
| ⚠️ Риски | `### PM Notes (risks)` |
| 🔄 В работе + ➡️ Следующие шаги | `### PM Notes (tasks)` |
| ❓ Открытые вопросы / ✅ Сделано | — (без блока; при необходимости — свободный комментарий в любом из трёх) |

Единый формат для всех доменов (Q-C2): 1-1 (E) — commitments→`tasks`, agreements→`decisions`; синки (H) — action_items→`tasks`, решения→`decisions`, риски→`risks`.

**ID-формат (PD-057):** `^{slug3}{hex}` — нативный Obsidian block reference:
- `slug3` — 3-буквенное сокращение проекта (`trx`, `crm`, …)
- `hex` — сквозной счётчик внутри проекта+тип, в hex без ведущих нулей
- Примеры: `^trx11`, `^trx55`, `^trx257`, `^trx27ff`
- Счётчики хранятся в `state.json → last_ids: {trx: {T: 18, D: 2, R: 2}}`
- **Источник `slug3` (Q-C3, PD-057):** явный `short_id` в `card.md` сущности (Projects/Syncs — из slug; People — `login3` (первые 3 символа login, коллизии маловероятны — login уникален в AD/LDAP)). Реестр уникальности — централизованно; коллизии запрещены. Если PM не задал — агент генерирует кандидата (первые 3 значимые буквы) и просит подтвердить. `short_id` стабилен навсегда (не меняется при переименовании).
- Ссылки из других заметок: `[[срез#^trx11]]`

**Удаление vs выполнение (PD-054):**
- `_DELETE: trx12` → строка `^trx12` физически убирается из среза
- `- [x]` → задача отмечена выполненной, остаётся в срезе

**Перезапись vs история (PD-055):**
- В срезе: перезаписываем без следов (срез = исправление ошибок транскрибации)
- В карточке (decisions.md): история хранится (зачёркивание удалённых)

#### 9. Правила формирования секций

Финализированы решения брифа от 2026-06-17.

##### 9.1 Критерии приёмки (В1)
- **Жёсткая фиксация** — если в `context.md` ссылка на Confluence-документ с критериями: любая правка = переоткрытие критерия + Warning HIGH.
- **Мягкая фиксация** — устная договорённость без документа: мелкие правки без флага, существенные = Warning MEDIUM.

##### 9.2 Baseline по срокам (В2)
- Исходный baseline = устав проекта (`context.md` → milestones).
- Каждый сдвиг срока требует явной записи в summary/решениях: «новый срок = X, потому что Y».
- Сдвиг без обоснования «потому что» → Warning HIGH.

##### 9.3 SDK/обязательства вендора (В3)
- Если в `context.md` есть обязательство вендора (SDK, API, лицензия) и оно не выполнено по факту встречи:
  - эскалация как нарушение обязательств вендора,
  - фиксация в секции «Риски»,
  - Warning HIGH до закрытия.

##### 9.4 Артефакты вне scope (В4)
- LLM сверяет упомянутые артефакты/задачи с `context.md` (scope).
- Артефакт вне scope → Warning MEDIUM «возможный scope creep».
- PM решает в `### PM Notes (decisions)`:
  - «расширение scope» → создаётся CR, обновляется `context.md`;
  - «побочный продукт» → Warning снимается в следующем срезе.

##### 9.5 Финансовый трекинг (В5)
- Полная стоимость не отслеживается.
- Контролируются только **сроки оплаты по договору**.
- Если в summary упомянут платёж → LLM сверяет срок с `context.md`:
  - срок < 5 рабочих дней или уже нарушен → Warning HIGH.

##### 9.6 Bus-factor (В6)
- Отсутствие ключевого ресурса (отпуск, болезнь, увольнение) без замены:
  - на критическом пути ≥ 1 нед. → Warning HIGH;
  - не на критическом пути ≥ 1 нед. → Warning MEDIUM.

##### 9.7 Сверка с card.md / context.md (В7)
Сверяются только ключевые поля (не весь документ):
- даты и сроки milestone,
- сроки платежей,
- критерии приёмки,
- допущения (assumptions).

##### 9.8 Устные договорённости (В8)
Jira не используется, источник истины — протокол встречи и срез.
- «Договорились что X» → секция **Решения**.
- «Юрий сделает Y» → секция **В работе**, владелец = Юрий.
- Непонятно кто исполнитель → секция **В работе**, исполнитель = «не определён» (PM назначит в `### PM Notes (tasks)`).

#### 10. Правила PM Warnings

Блок `> [!warning]-` генерируется в начале файла среза, если есть хотя бы одно срабатывание. Уровни:

##### HIGH (🔴) — требует действия на этой неделе
- Срок сдвинулся без обоснования «потому что» (см. §9.2).
- Артефакт/задача не в scope `context.md` и явно критичный (см. §9.4 при эскалации PM).
- Критерий приёмки имеет статус «✅» в `card.md`, но обсуждается пересмотр И есть Confluence-документ (см. §9.1, жёсткая фиксация).
- Риск повторяется 2+ среза подряд без митигации.
- Ключевой ресурс на критическом пути отсутствует ≥ 1 нед. без замены (см. §9.6).
- Срок платежа < 5 рабочих дней или уже нарушен (см. §9.5).
- Обязательство вендора зафиксировано в `context.md`, но не выполнено по факту (см. §9.3).

##### MEDIUM (🟡) — решить в течение спринта
- Возможный scope creep: артефакт вне `context.md`, но не явно критичный (см. §9.4).
- Критерий приёмки согласован устно (без Confluence) и обсуждается пересмотр (см. §9.1, мягкая фиксация).
- Action item повторяется 2+ недели подряд без прогресса.
- Ресурс не на критическом пути отсутствует ≥ 1 нед. без замены (см. §9.6).

##### LOW / инфо (🟢) — к сведению
- Устные договорённости без явного action item (исполнитель = «не определён»).
- Мелкие сдвиги сроков внутри допустимого окна (заранее согласованный буфер).

##### Снятие Warnings
- HIGH снимается явным закрытием в `### PM Notes (...)` или в следующем срезе при разрешении причины.
- MEDIUM может быть конвертирован PM в «расширение scope» (→ CR) или «побочный продукт» (→ снимается).
- LOW снимаются автоматически, если в следующем срезе не повторяются.

#### 11. Prompt-шаблон для LLM

Используется при вызове генератора: «Создай срез проекта по встрече {meeting_title}».

````markdown
## Prompt-шаблон: Генерация status_snapshot

### Входные данные
- FF summary встречи: {meeting_summary}
- Предыдущий срез: {prev_snapshot} (или "нет" если первый)
- Карточка проекта: {card_md}
- Контекст проекта: {context_md}
- PM Notes из предыдущего среза: {prev_pm_notes} (блоки ### PM Notes (...))

### Инструкция

Ты — PM-ассистент. Создай срез проекта в формате Obsidian markdown.

**Правила извлечения контента:**

РЕШЕНИЯ: Извлеки из summary все «договорились что», «решили», «согласовали». Каждое решение = отдельный пункт.

СДЕЛАНО: Только завершённые действия с глаголом совершенного вида + субъект. «Почти готово» и «100% но не проверено» → В РАБОТЕ, не СДЕЛАНО.

В РАБОТЕ: Незавершённые задачи с владельцем. Устные договорённости с исполнителем → сюда. Если исполнитель не назван → «не определён».

БЛОКЕРЫ: Факт + кто блокирует + что нужно + дата. Без даты разблокировки → дата «не определена» + Warning.

СЛЕДУЮЩИЕ ШАГИ: Только action items с владельцем И сроком. Без срока → ОТКРЫТЫЕ ВОПРОСЫ.

ОТКРЫТЫЕ ВОПРОСЫ: Всё без срока/владельца + устные договорённости без исполнителя.

**Правила PM Warnings (генерировать блок `[!warning]-` сверху если есть):**

HIGH (требует действия на этой неделе):
- Срок сдвинулся без обоснования «потому что»
- Артефакт/задача не в context.md scope (scope creep)
- Критерий приёмки «✅» в card.md, но обсуждается пересмотр И есть Confluence-документ
- Риск повторяется 2+ раза без митигации
- Ключевой ресурс на критическом пути отсутствует ≥1 нед. без замены
- Срок платежа < 5 рабочих дней или нарушен
- Обязательство вендора не выполнено (есть в context.md, отсутствует на деле)

MEDIUM (решить в течение спринта):
- Возможный scope creep (артефакт вне context.md, но не явно критичный)
- Критерий приёмки согласован устно и обсуждается пересмотр
- Action item повторяется 2+ нед. без прогресса
- Ресурс не на критическом пути отсутствует ≥1 нед. без замены

LOW / инфо:
- Устные договорённости без action item (попадают в «не определён»)
- Мелкие сдвиги внутри допустимого окна

**Сверка с card.md/context.md (только ключевые поля):**
- Сроки и даты milestone → сравнить с baseline, при отклонении Warning HIGH
- Критерии приёмки → статус каждого (без изменений / прогресс / деградация / пересматривается)
- Допущения → проверить выполнение, нарушенное = Warning HIGH
- Платежи → сверить с датами в context.md
````

### 1on1-snapshot

**Путь:** `People/{login}/snapshots/{login}-snapshot-YYYY-MM-DD.md`

**Входные данные:**
- FF summary новой встречи
- `People/{login}/card.md`
- `commitments.md` (открытые)
- Предыдущий 1on1-snapshot
- PM-заметки из предыдущего snapshot

**Секции:**
1. Невыполненные commitments (с прошлых встреч)
2. Новые commitments
3. Договорённости
4. Обсуждаемые проекты
5. PM Notes

**PM Warnings специфичные:**
- **HIGH** 🔴 — commitment просрочен (дата прошла, статус не закрыт)
- **HIGH** 🔴 — commitment повторяется 2+ встречи без прогресса
- **MEDIUM** 🟡 — упомянут новый проект которого нет в `card.md → projects`
- **MEDIUM** 🟡 — изменился тон/настрой (участились споры, напряжение в тексте)

**pm_locked:** не нужен (по аналогии с E.Люди — нет фоновых автообновлений между встречами).

### sync-snapshot

**Путь:** `Syncs/{slug}/snapshots/{slug}-snapshot-YYYY-MM-DD.md`

**Входные данные:**
- FF summary новой встречи
- `Syncs/{slug}/card.md`
- `action_items.md` (открытые)
- Предыдущий sync-snapshot
- PM-заметки из предыдущего snapshot

**Секции:**
1. Решения синка
2. Задачи синка (открытые / новые / закрытые)
3. Затронутые проекты
4. Состав участников
5. PM Notes

**PM Warnings специфичные:**
- **HIGH** 🔴 — action item синка просрочен 2+ встречи
- **MEDIUM** 🟡 — состав участников изменился (новый или выбыл постоянный)

**pm_locked:** не нужен.
