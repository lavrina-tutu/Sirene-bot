# Формат буллетов проектов (блок «Ключевые достижения», опыт Туту)

Правила для буллета по каждому проекту/инициативе в опыте Туту. Дают буллет, который Саша принимает без переписки.

## Структура буллета
1. **Официальное название проекта как в цели/уставе** + статус в скобках: `(в работе)`, `(закрыт)`, `(закрыт решением)`. Не внутренний слаг/кодовое имя.
2. **Открыть выгодой/сутью для бизнеса одной фразой**, потом факты. Пример-паттерн: «…призван брать на себя рутину аналитики — по всем вопросам, с которыми бизнес приходит в департамент аналитики».
3. **Роль/вклад — заголовок «Выполняемые задачи:»** (НЕ «Роль»), перечислением: управление, синхронизация команд, приоритизация задач, ведение плана и статус-отчётность.
4. Не дублировать внутри одного буллета блоки «Выполнено»/«В работе», если суть уже сказана во вводной фразе — буллет короткий.

## Описание функционала/сути
- **Описывать функцию и бизнес-логику, НЕ названия инструментов.** Для читателя резюме «AI-DWH», «Metabase», «AI-BI», «Hermes», «MCP», оркестратор — шум. Писать: «выгрузка и расчёт метрик по витринным данным, поиск и построение дашбордов, построение отчётов и визуализаций по запросу, интерпретация бизнес-метрик». Внутренние системы называть только если это отличительное преимущество.
- Указывать, что уже решает и какое направление развития (напр. работа от персональных учётных записей с уровнем доступа, подключение инженерных ролей).

## Экономика и бизнес-эффект
- **Подтверждённую экономию при согласованном основании можно писать «во сколько-то раз», а не конкретной суммой** («экономия в разы на внедрении, лицензиях и ежегодном сопровождении вендора»). Точные суммы Саша из резюме убирает — лучше сравнивать с доработкой собственного решения «во столько-то раз дешевле».
- Для проектов «собственная платформа vs вендор» (Trisigma, ML-платформа): **без внутренней кухни** (недоверие заказчика, орг-обстоятельства). Суть: провели сравнение/пилот сторонних решений с собственным, сделали вывод выбрать собственное, итог — подтверждённый эффект; кратность указывать только при наличии основания.

## Формулировки
- Результат-глаголы: **подготовлено, разработано, выполнено, проработано** (страдательные), не «я делал/веду процесс». Саша: подавать «разработанное, выполненное, подготовленное».
- Участие в программе без роли руководителя (напр. AI-ready): **«участвую в общем процессе трансформации компании», автоматизирую собственную роль** — не заявлять «руковожу трансформацией».
- Воды минимум; без повторов.

## Сбор фактов для буллета
- По каждому проекту тянуть: **устав** (цель/проблема/заказчик/статус) + **страницу «Задачи и договоренности (Минутки)»** (решения, статусы, что фактически сделано) + **отчёт о завершении/акселерации**, если есть. Решение типа «не идти в полную закупку» фиксируется в уставе/протоколах — искать там, затем формулировать по факту.
- Найти устав: CQL `title ~ "устав" and text ~ "<название проекта>"`; дерево страниц проекта — `ancestor = <rootPageId>`.
- Статус/план из присланного .mpp — читать `read_mpp.py` из `~/USERTOOLS/MppReader/` (запускать системным python, где стоит `mpxj`, не venv агента): `read_mpp.py <file> --format json --summary`; Log4j-строка в stdout ломает `json.load` — удалять только распознанный диагностический префикс, не первую строку безусловно.
- OKR-цели проекта брать из уже выгруженной картотеки `~/WorkVault/Entities/okr/<slug>/` (yearly O + quarterly O + KR), а не перечитывать Jira, если карточки актуальны.
