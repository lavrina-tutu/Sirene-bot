# Паттерн: hermes-feature

## Overview

Единый процесс работы над фичами Hermes и USERTOOLS: от ТЗ до кода, тестов, документации, диагностики и отката. Sonnet-5 пишет/тестирует, Opus 4-7 планирует.

## When to Use

- «разработай», «новый инструмент», «напиши ТЗ», «MoveFrom*» — Блоки 0–4
- «ошибка», «баг», «не работает», «упало», «разберись», «починить» — Блок 7 (диагностика)
- «проанализируй», «исследуй», «найди», «посчитай», «сравни» — Блок 8 (исследование)
- Задача с 3+ изменениями конфига/скиллов/инструментов — Блок 6А (QA)

Не для: правок стиля общения (см. `hermes-memory-hygiene`), простой рутины без ТЗ и вариантов.

---

## Блок 0: ТЗ

ТЗ финализировано Opus (скилл `tz-workflow`) и получено явное «берём в работу» от Саши. Реализация без финального ТЗ и явной команды — запрещена.

---

## Блок 1: Анализ вариантов

- **Критерии:** токены / безопасность / консистентность / поддерживаемость + специфичные для задачи.
- **Количество:** 2-3 лучших; слабые Opus отсеивает сам.
- **Подача:** сначала рекомендация с обоснованием → остальные кратко.
- **Варианты только цифрами 1/2/3**, никогда не A/B/C. Применяется ко всем брифами, опросам, вариантам — в любом контексте.
- После выбора: уточняющие вопросы **по одному** → ждать «берём в работу».

**Completion criterion:** Саша сказал «берём в работу» по конкретному варианту.

---

## Блок 1А: Планирование *(до Блока 2)*

**Opus составляет пофайловый план:**
- Какие файлы создать / изменить
- Какие функции / классы / методы добавить
- Какие тесты написать
- Промежуточные точки проверки с критериями

**ТЗ-файл только для задач с Python-кодом.** Для скиллов, конфигов, memory-правок — план в чате.

**Sonnet проходит промежуточные точки молча** — без отчётов Саше.

**Перед «берём в работу»** — проверить ключевые фактические утверждения плана напрямую (`which`, `read_file`).

**Устойчивость к сбою:** `## Прогресс выполнения` с чекбоксами в файле плана.

**Completion criterion:** Саша сказал «берём в работу» по пофайловому плану.

---

## Блок 2: Реализация

### Модели
**Sonnet-5** — пишет весь код по плану Opus. **Opus 4-7** — планирует и fallback при архитектурном тупике.

### Кто пишет
- **Sonnet-5** — пишет код по плану Opus
- **Opus 4-7 (fallback)** — только если Sonnet не справилась: архитектурный тупик или повторяющиеся необъяснимые ошибки. Sonnet даёт вывод → **Саша решает** запускать ли Opus.

**Мелкое отклонение** (≤2 файла, не меняет архитектуру) → Sonnet сама.
**Крупное отклонение** → Sonnet стопится → Opus делает доплан → Sonnet продолжает.
**Системный блокер** (пакеты, sudo) → Sonnet стопится → вопрос Саше напрямую.

### Чеклист перед первой строкой кода
1. ТЗ согласовано + явное «берём в работу».
2. **Бэкап создан** (см. Блок 5).
3. Пофайловый план Opus согласован.

---

## Блок 3: Тестирование

- **Sonnet-5** тестирует по плану Opus
- **Мелкий баг** (≤2 файла, очевидная причина) → Sonnet чинит сама (1 попытка)
- **Крупный баг** → Sonnet фиксирует причину → **Саша решает** → Opus делает hotfix-план → Sonnet применяет
- **Готово =** все точки проверки из плана Opus пройдены (✅/❌)
- Статус «completed» на весь план ставит только Саша.

---

## Блок 4: Документирование

- ТЗ-файл в `TZ/<Tool>/<Tool>_TZ.md` пока инструмент используется. Архивация — только при выводе из эксплуатации.
- **Скилл:** мелкая правка → Opus сам; новый раздел → предлагает Саше.
- **MEMORY и скиллы:** см. `hermes-memory-hygiene`.

---

## Блок 5: Бэкапы и откат

- **Opus-задачи:** бэкап всегда.
- **Sonnet-задачи:** только если затронут `config.yaml` или `jobs.json`.
- **Путь:** `~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`.
- **Хранение:** 2 недели, 1 бэкап в день. Self-check чистит.
- **Откат:** авария → Opus немедленно; плановый → Opus предлагает, ждёт ОК.

---

## Блок 5Б: Классификация разрешающего сигнала

**Триггер:** любой `write_file`/`patch` вне `_Archives/`, `cronjob(create|run)`, `curl -X POST|PUT|DELETE` к API.

| Категория | Разрешает? |
|---|---|
| `direct-imperative` — глагол-императив от Саши именно на это действие | ✅ |
| `continuation-of-approved-plan` — пункт из согласованного плана | ✅ |
| `question-answer` — ответ на вопрос, действие не запрошено | ❌ |
| `own-inference` — модель вывела «раз X, значит нужно Y» | ❌ |
| `conditional` — «если X — делай Y», истинность X оценивает модель | ❌ |

Если ❌ — отдельный turn без side-effect-инструментов, текстовый вопрос Саше.

---

## Блок 6: Эскалация

**Стоп + пишет Саше:** критическая поломка, неопределённость в ТЗ.
**Ночью:** сохранить состояние в ТЗ-файл → «жду решения» в TG → ждать утра.
**Молчит:** рутинные cron без ошибок.

---

## Блок 6А: QA-проверка

**Пропускается** если Opus уже написал план с тестами (Блок 1А) и Sonnet прошла его (Блок 3).

**Применяется** для изменений БЕЗ предварительного плана Opus (срочный hotfix, ручная правка).

Процесс: Opus-крон собирает чек-лист → исправить ❌ → повторить (макс 3 попытки) → все ✅ = короткий отчёт. Остались ❌ → откат + доклад.

---

## Блок 6Б: Делегирование субагентов

| Задача | Модель | Инструмент | Таймаут |
|---|---|---|---|
| Opus: ТЗ / план / анализ | `model: "deepseek/deepseek-v4-pro", reasoning: "high"` (без provider) | `cronjob(repeat=1)` | — |
| Opus: реализация (fallback) | то же | `cronjob(repeat=1)` | — |
| Sonnet: реализация >5 мин | **не передавать model** | `cronjob(repeat=1)` | — |
| Sonnet: короткая <5 мин | **не передавать model** | `delegate_task` | 300с |
| Haiku: справочный | `model: "deepseek/deepseek-v4-pro", reasoning: "low"` (без provider) | `delegate_task` | 120с |

**Никогда `delegate_task` с Opus** — reasoning_effort=high → gateway-зависания.

### Toolsets

| Задача | enabled_toolsets |
|---|---|
| Opus: ТЗ / план | `["file", "terminal"]` |
| Sonnet: реализация | `["file", "terminal"]` |
| Sonnet: тестирование | `["file", "terminal"]` |
| Исследование с web | `["file", "terminal", "web"]` |

### Что передавать в промпт

1. Роль и среда, абсолютные пути
2. Полный текст ТЗ или плана (не ссылку)
3. Граница автономности: «механическое — делай сам; семантическое — СТОП»
4. Формат отчёта, явные запреты
5. **Критичные факты из MEMORY — явно в промпт.** Cron-сессии НЕ получают MEMORY/USER PROFILE (`skip_memory=True`).

Полные правила: `references/subagent-rules.md`.

## Блок 6В: Диагностика перед починкой

Когда «что-то не работает» — **не чинить сразу**. Порядок:

1. **Opus-крон только на диагностику** (только чтение, запрет правок) → root cause, план П.1…П.N
2. Саша просматривает план
3. Sonnet-крон реализует по плану

План сохранить в `_fix_plan_YYYYMMDD.md` рядом с инструментом.

---

## Блок 7: Диагностика и отладка

**Метод:** скилл `systematic-debugging` (4 фазы: root cause → pattern → hypothesis → fix).

**Специфика:**
- Модель: Sonnet-5
- Мелкий баг → Sonnet чинит сама (1 попытка)
- Крупный → Саша решает → Opus на hotfix-план
- Системный блокер → вопрос Саше напрямую
- Эскалация к Opus: root cause в архитектуре, не воспроизвелось за 2 попытки
- Эскалация к Саше: данные могут быть повреждены, production down

---

## Блок 7А: Двухэтапный Opus-анализ конфигурации

При изменении systemd-юнитов, rclone-конфигов, синхронизации:

1. **Opus-крон №1** — только читает, оценивает риски, строит план
2. Sonnet пересказывает Саше, получает подтверждение
3. **Sonnet-крон №2** — реализует по согласованному плану

---

## Блок 8: Исследования и анализ

Триггеры: «проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если».

**Модель:** Haiku собирает данные → Sonnet-5 анализирует в рамках одного инструмента → Opus для интеграционных вопросов.

**Алгоритм:** Scope → Сбор (session_search, grep, API только чтение) → Анализ (таблица) → Рекомендации (2-3 варианта с оценкой).

**НЕ делать:** не менять код/конфиги/скиллы, не делать выводы без данных, не запускать API без ОК.
