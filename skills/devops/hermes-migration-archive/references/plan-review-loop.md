# Ревизия плана/ТЗ миграции независимым ревизором (цикл REQUEST-CHANGES)

## REV:tz / REV:plan отсутствуют в рецепте MIGRATION

Для кейса `MIGRATION` фазы `REV:tz` / `REV:plan` **не входят в рецепт**:
`emit-prompt --phase REV:tz` падает с `phase is not in recipe: REV:tz`.
Штатный маршрут `emit-prompt` → `invoke-role` для ревизора недоступен. Это не баг
и не обход gate-ов: канон `dev-workflow` допускает независимую ревизию «вне
процесса», ревизор не является ходом рецепта. Требование Саши «план/ТЗ должен
пройти ревизию ревизора» исполняется прямым вызовом ревизора с собственным промптом.

## Вызов ревизора вне invoke-role

Промпт — обычный текстовый файл (не packet); ревизор пишет вердикт в `evidence/REV-*.md`
и корневой указатель `REV-*.md`. Модель ревизора — из YAML `tools.dev_workflow.reviewer`
(проверять в каждом кейсе, не зашивать).

```text
# промпт как позиционный аргумент, НЕ -f (в codex exec `-f` = --output-format)
codex exec -m <reviewer-model> -c shell_environment_policy.inherit=all \
  --sandbox danger-full-access --dangerously-bypass-approvals-and-sandbox \
  "$(cat /tmp/task_rev_*.md)"
```

- `-f` конфликтует с `--output-format`; промпт передаётся как аргумент.
- `--sandbox danger-full-access` + `--dangerously-bypass-approvals-and-sandbox`
  нужны, чтобы ревизор смог записать вердикт в файл.
- Запускать в фоне с notify (вызов обычно > 1-2 мин).
- В промпт закладывать точные байты: версия/hashes плана, handoff, master, AC-list,
  предыдущий вердикт; требовать проверку по фактическому содержимому файлов и
  адресам, а не по заявлению в §13 отчёта архитектора.

## Цикл повторяющейся ревизии

1. Первая ревизия — `evidence/REV-plan.md`.
2. Каждый следующий круг — НОВЫЙ файл `evidence/REV-plan-2.md`, `REV-plan-3.md`, …
   (никакого перезаписи прошлого вердикта); корневой указатель можно перезаписать
   на актуальный, но прошлые вердикты хранить.
3. После каждого REQUEST-CHANGES: вернуть архитектору доработку с точным списком
   правок (по фактическим строкам приложений/JSON, не только номер ревью),
   счётчики кругов не сбрасывать; затем пересчитать hashes и запустить следующий круг.
4. Регламент «Повтор замечания»: один и тот же дефект в двух последовательных REV →
   второй REQUEST-CHANGES останавливает путь до третьего круга и требует диагноза.
   Третий и последующие круги допустимы ПОСЛЕ явного решения Саши (напр. «вариант 1`),
   не молча.
5. Прогресс докладывать по содержанию, а не «снова вернул»: 2-й/3-й круг часто
   закрывает часть правок и сужает остаток (R2/R3/R4 закрыты, остались R1.x) — это
   и есть движение к APPROVE.
6. Архитектор не выносит сам APPROVE и не создаёт state при приёме доработки;
   положительный вердикт — только отдельный независимый REV.

## Питфолл: полное закрытие vs честный остаток

Если архитектор не смог закрыть правку полностью, он обязан пометить остаток
(напр. `remaining_R1.optional_incomplete_command_consumers=845`) как условный на
открытый Q-вопрос, но НЕ выдавать пустой placeholder за «полную проектную матрицу».
Ревизор проверяет СОДЕРЖАНИЕ полей, а не наличие полей — диагноз «проверка наличия
полей подменила проверку содержания» повторяется и его надо ловить в цикле.

## Старый артефакт vs новый байт

Ревизор сверяет фактические SHA-256 (вычислять до вызова `sha256sum`), идентичность
source spans/block_sha, структуру JSON (количество записей, counts), встроенные
hashes источников против текущих source-файлов. При запросе ревизору передавать
эти числа, а не только пути.
