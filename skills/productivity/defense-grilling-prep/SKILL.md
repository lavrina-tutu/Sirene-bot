# Подготовка к защите и прожарка

Готовим Сашу к защите его же документа/фреймворка/методики перед аудиторией (руководитель, команда, заказчики). Две части: план подготовки + интерактивная прожарка по одному вопросу.

## Процедура

### 1. Прочитать первоисточник целиком
- Материал на Confluence → работать через скилл `tutu-confluence-jira` (REST + `load_confluence_env`), не через web_extract (блокирует dom.tutu.ru).
- Материал в WorkVault → `search_files` по имени; рядом с финалом обычно лежат сводка источников, черновики, комментарии. Искать и читать их — без контекста постановки прожарка будет неполной.

### 2. Собрать контекст постановки (до плана)
- Кто инициатор, на какой встрече поставлено, дословные требования, кто согласует.
- На защите Саша обязан уверенно ответить «какую проблему решаем и как её поставили» — это первый вопрос аудитории. Держать цитаты-опоры инициатора.

### 3. Предложить план подготовки (5 блоков)
1. **Питч на 30 сек**: проблема → единица работы → путь → артефакт в историю.
2. **Скелет документа**: каждый раздел в одно предложение; ядро назубок.
3. **Параметры «на визу»**: что явно визируется/согласуется (лимиты, пороги) — знать наизусть и уметь защитить «почему так».
4. **Вероятные вопросы аудитории**: у руководителя, исполнителей и заказчиков разные боли — готовить ответы под каждую роль.
5. **Слабые места для прожарки**: границы, условия перехода, тонкие различения.

### 4. Прожарка: по одному вопросу
- Один вопрос за раз; по ответу углубляться. Пачками — только если Саша явно попросил.
- Сначала требовать ответ **своими словами**, без пересказа документа; эталон давать только после попытки.
- Каждый ответ разбирать по фиксированной схеме: **«что хорошо» → «что поправить» → «чистовая версия»** (~30–45 сек).
- После разбора — следующий вопрос. Если Саша сам сворачивает на фундамент («давай начнём с начала») — идти за ним, это его способ проговаривать материал.

## Питфоллы

- **Сверять каждый ответ с первоисточником и явно исправлять фактические ошибки.** В устных ответах Саша путает распределение ролей и статус параметров (пример: «класс выбирает ведущий» вместо «Руководитель ПА»; «это предположение» вместо «параметр, визируемый при согласовании»). Неисправленная фактическая ошибка уйдёт на защиту как есть — называть её прямо: «неверно, по документу так-то».
- **Отвечать и строить эталоны по-человечески, без канбан-жаргона** — стоящее предпочтение Саши; сокращения расшифровывать.
- **Эталон — после попытки Саши, не до.** Красивый ответ, данный сразу, не заставляет его проговорить материал и найти свои дыры.
- **Требовать «стоимость проблемы».** Ответ «что решаем» без того, что теряем (время, статус в головах, повторные расчёты), звучит как теория. Явно запрашивать эту часть.
- **Разводить смешанные контуры.** Саша сливает в один абзац разные места работы (где ведём / где отдаём ответ / где храним историю). В чистовике разносить по отдельным предложениям — ответ становится структурным и устойчивым к вопросам.
- **Называть устные оговорки** (типа «фреймер» вместо «фреймворк») в разборе — на защите оговорка съедает внимание.
- **Не зашивать в SKILL.md конкретику сессии** (pageId, файлы, имена) — процедура переиспользуема; конкретика живёт в WorkVault/Confluence.
- **Сильную аналогию из ответа сохранять.** Когда Саша сам находит точный образ (напр. «лимит два S — это WIP-лимит из Kanban») — закреплять её в чистовике, не заменять.

## Связанные скиллы

- `tutu-confluence-jira` — чтение материала и источников из Confluence
- `workvault-rag` — поиск материалов и сводок в WorkVault
