# Live-smoke верификация guarded транспорта

## When to Use

Применять при RESEARCH/проверке кода, который делает ровно одну реальную отправку и
должен запрещать повторную: native adapter + guard, single-send ограничитель, платный
транспорт. Триггеры: «живой smoke», «проверь guard на реальном провайдере», «NOT_RUN
production runtime».

Подтверждает один реальный provider send и запрет второй отправки одним и тем же
экземпляром guard — без сжигания бюджета и без доказательства «отсутствия второго
запроса» как единственной улики.

## Процедура

1. **Проба с observer.** Исследовательский скрипт оборачивает настоящий transport
   (`HTTPTransport.handle_request`) observer-ом: перед реальной отправкой фиксирует
   URL/model/credential и устанавливает `spent=true`; сам запрос передаёт настоящему
   транспорту. Один жёсткий предохранитель запрещает любой второй физический dispatch
   независимо от guard.
2. **Один live send на фазу.** Живой вызов с реальным провайдером выполняется ровно
   один раз. Последующие вызовы фазы повторяют только offline-ветку, `provider_calls=0`.
3. **Повтор тем же guard.** Сохранённый экземпляр guard из первой попытки ставится на
   отдельный клиент с MockTransport: ожидаемый исход — RuntimeError до транспорта и
   `mock_transport_dispatches=0`. Это и есть доказательство, что блокирует guard, а не
   отсутствие второго платного запроса.
4. **Offline-валидация в дочернем процессе.** Повторный скрипт без `--live`:
   запретить `socket.connect`/`connect_ex`/`create_connection` (socket fuse), удалить
   ключи провайдера из окружения дочернего процесса, родительское окружение не менять.
5. **Хэши и неизменность.** Сохранить SHA-256 исполнявшегося source (live JSON фиксирует
   hash установленного кода), SHA улики и скрипта; before/after защищённых файлов должны
   совпасть байт-в-байт. Исходную live-улику не перезаписывать результатом нового запуска.

Вердикт — в `RS:collect`/`RS:analyze` артефактах, с ограничениями ниже.

## Pitfalls

- Не утверждать «guard блокирует» только по отсутствию второго платного запроса —
  предохранитель скрипта мог запретить его независимо от guard. Нужна отдельная попытка
  с тем же guard и mock-транспортом, где транспорт не достигнут.
- Не переносить identity-проверки observer-а на production guard: observer проверял
  URL/model/credential сам; это не доказывает, что их проверяет код под тестом.
- Каждый новый вызов adapter создаёт новый экземпляр guard; доказательство относится к
  одному экземпляру и последовательным попыткам, не к persistent mutex/бюджету.
- Не вводить новые константы настройки из имён наблюдаемой пробы: провайдер/модель в
  улике — значения той пробы, не конфигурация системы.
- Success live marker не заменяет негативные трассы (401/402/429/5xx/timeout) и полный
  маршрут (bootstrap → публикация → receipt). Ограничение выносить отдельной секцией.

## Границы

- Локальный HTTP-transport evidence ≠ независимый server-side журнал/биллинг.
- Прямой adapter call без штатного prepare/packet/публикации доказывает только узкий
  участок; полную готовность контура так не заявлять (`NOT_ESTABLISHED`/`NOT_RUN` честно
  в evidence).
- Это evidence для отдельного исследования, не APPROVE всей фичи и не закрытие всех AC.
