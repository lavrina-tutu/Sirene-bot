# USERTOOL cron verify — молчаливый крон не значит рабочий

## Когда использовать

- Недавно внедрённый USERTOOL (MoveFromKeyTalk, MoveFromFF, MFF и т.п.) поставили в крон, крон отдаёт
  `Status: silent (empty output)`, а пользователь уже ждёт результат (встречи, протоколы, файлы).
- Нужно понять, заработал ли инструмент на новом окружении, до того как звать пользователя проверять.

## Главное правило

**`silent (empty output)` доказывает только «раннер не увидел ошибки», а не «инструмент справился».**
Для НОВОГО инструмента всегда проверяй его собственный артефакт работы (реестр/state-файл, файлы в
каталоге назначения). Пустота при «silent» на давно поставленном кроне = скрытый крах при инициализации,
а не штатная пустота. Штатная тишина допустима только у инструмента с подтверждённой историей успешных
прогонов уведомляющего типа (нет новых pending и т.п.).

## Почему тишина лжёт (механизм)

Многие `bin/<tool>_sync.sh`-обёртки маскируют крах на этапе init:
```bash
set -euo pipefail
"$TOOL_DIR/.venv/bin/python" -m <tool> --mode cron
code=$?
set -e
if [[ code 0 || code 1 ]]; then exit 0; fi   # 1 трактуется как «частичный успех»
exit code
```
Ошибка конфигурации на стадии `load_tool_config` / чтения env кидает `KeyError` (`Missing config key
'LOGS_PATH' for tool '<tool>'`) с exit-кодом 1 → обёртка делает `exit 0` → раннер пишет
`silent (empty output)`. Traceback до output-файла крона никогда не доходит.

## Диагностика (в этом порядке)

1. **Проверить артефакт работы инструмента, а не лог крона:**
   ```bash
   cat ~/USERTOOLS/<Tool>/state/_registry.json   # или tools/<tool>/state/_registry.json
   ls -la <MEETINGS_DIR> | grep <сегодня>        # каталог назначения по конфигу
   ```
   Пусто / старое при «silent» на давно поставленном кроне — тревожный признак.

2. **Запустить CLI напрямую в venv инструмента, мимо обёртки (единственный путь к traceback):**
   ```bash
   cd ~/USERTOOLS/<Tool> && source .venv/bin/activate
   python -m <tool> --mode test --dry-run   # или --dry-run --no-tg
   ```
   Настоящий traceback (`Missing config key ...`) вылезает только так.

3. **Сверить ключи ORCH-конфига с требованием кода:**
   ```bash
   python3 -c "import yaml;print(yaml.safe_load(open('~/WorkVault/Registries/EcosystemConfig.yaml'))['tools']['<tool>'])"
   # и в коде:  grep -n "_MFKT_CONFIG_KEYS\|_req(" ~/USERTOOLS/<Tool>/<tool>/config.py
   ```
   Ключ, который код считает обязательным (`_req(...)`), но которого нет в `EcosystemConfig.yaml`
   `tools.<tool>` или в shared `~/.config/hermes/.env` — корень тишины.

## Питфолы

- **Не верь output-файлу крона как доказательству работы** — wrapper прячет крах за `exit 0/1`.
- **Инструмент-первенец из полного dev-цикла (GATE:done) НЕ значит «работает на проде»** — GATE закрывает
  реализацию и тесты, а живой конфиг (ключи ORCH, персональные токены в shared .env) внедряется отдельным
  шагом. После внедрения всегда верифицируй живым прогоном + артефактом.
- **Зелёный pytest с моками ≠ контур ходит по правильному эндпоинту.** Для инструмента, который зовёт
  живой внешний API, тест-фикстуры пишутся под текущий (неверный) код и закрепляют неверный контракт:
  они зелёные, даже когда клиент бьёт в мёртвый интеграторский путь (`/api/Domain/...` → 403), а рабочий
  путь другой (`/api/...` → 200). Ключ может быть рабочим, а 403 — результатом неверного пути/скоупа.
  Проверка «контур качает данные» — отдельный AC: живой smoke реального пути с реальным ключом
  (ping / list top=1 / один транскрипт), а не только pytest + fail-loud exit-2 (тот доказывает лишь
  конфиг, не data-path). При 403 на интеграторском пути сверяйся с документацией клиента (что реально
  шлёт авторизация: заголовок vs query-параметр; какие пути живы) и пробуй альтернативные пути тем же ключом.
- **Две параллельные цепочки встреч (Fireflies vs Контур.Толк/KeyTalk) пишут в РАЗНЫЕ реестры.**
  Прежде чем звать пользователя, пойми, из какого контура пришла запись и какой реестр смотреть
  (`WorkVault/Meetings/NewMeetings/_registry_meet.json` для MFF/FF vs `~/USERTOOLS/<Tool>/state/_registry.json`
  для нового инструмента) — иначе «нашёл встречу» может оказаться старой FF-записью, а новый контур всё ещё пуст.

## Запрещено (см. канон экосистемы)

- Рестартовать gateway из этого процесса.
- Прямой вызов `agent -p` архитектора на root-cause крон-ошибки — только через канбан-карточку `BUG:diagnose`
  (Блок 6В hermes-feature), если фикс идёт в код.
- Если причина — отсутствующий ключ конфига, это доработка/настройка, веди по канону с ревизором, а не
  точечной правкой.
