# Dev-Pipeline Reliability: не давать цепочкам схлопываться и ложно завершаться

Главный урок 08.09 (exchange-contact-upsert): оркестратор принял «делай в 1 проход»
как «один `agent -p` исполнителя» и **свернул** цепочку CHANGE — свёл TZ-WRITE
в один вызов, пропустил `HF:plan` / `GATE:plan-approve` / `REV:tz` / `HF:docs-handoff`,
и объявил задачу done. Внешний аудит показал: продукт есть, **процесс — нет**,
«закрыта» — нет. Этот скилл фиксирует, как вести цепочку, чтобы такое не повторялось.

Компаньоны (все user-owned — патч через Cursor, не напрямую): `tz-workflow`,
`hermes-feature`, `kanban-dev-pipeline-orchestration`, `cursor-cli`.

## Инвариант №0 — «гейт done при children=[]» = оборванный хвост, не норма

Симптом (повторялся многократно, 28-29.09, 30.09→12.10: topic-origin, pfs-task-slug,
mfl-exchange-lxml, mfl-digest-lxml): фазовый гейт/фаза (GATE:take-into-work, HF:plan,
REV:plan, GATE:plan-approve, **BUG:diagnose**) закрылся `done`, но **НЕ создал детей**
(`children=[]`), поэтому весь последующий хвост (GATE:diagnose-review → TZ:patch →
HF:backup → impl → test → docs → ORCH → GATE:done) НЕ развёрнут. Граф формально
весь done, а фактически **кода нет** — доработка/багфикс «зеленеет» без реализации
(тот же класс, что «ТЗ готово, код нет»). Для бага это особенно дорого: DX done,
корень done, но ошибка в ErrorBus ПРОДОЛЖАЕТ падать, Саша отвечает «это починили?»
через часы/дни.

**Правило prevent (главное — не допускать):** BUGFIX-граф разворачивается ПОЛНОСТЬЮ
в момент постановки — одним батчем корень `DEV/<slug>` + `BUG:diagnose` +
`GATE:diagnose-review` + (после классификации) LIGHT-хвост `TZ:patch → TZ:finalize
→ GATE:take-into-work → HF:impl → HF:test → HF:docs-handoff → GATE:done`. Диспетчер
промоутит по parents сам; **НЕ ждать dx-done, чтобы добавлять следующие карточки** —
диспетчер не строит хвост за тебя, и DX-done с `children=[]` тихо останавливается,
пока ошибка валится дальше. GATE:diagnose-review создаётся сразу (не после DX), как
gotовая parent для последующих фаз.

**Правило «раннее закрытие корня» (сигнатура мёртвого графа, подтверждено ревизором):**
корень `DEV/<slug>` закрывать контейнером ТОЛЬКО после того, как хвост развёрнут хотя
бы до `GATE:diagnose-review` + `GATE:done`-фазы. `complete` корня сразу после fan-out
детей, но ДО создания хвоста реализации, даёт `root status=done` при `GATE:done`
отсутствует — и это ровно тот признак, по которому граф «зеленеет» без кода (все
реальные мёртвые графы: root done, хвоста нет, ErrorBus продолжает падать).
При аудите «мёртвого» багфикса первым делом смотреть `SELECT status FROM tasks WHERE
id='<root>'` + `children=[]`: если root `done` без `GATE:done` — это преждевременное
закрытие контейнера, а не «блок-ветка не сработала». Блок-ветка на таких графах не
триггерится именно потому, что root уже `done` — не полагаться на неё как на
единственный сигнал.

**Правило cure (если беда уже случилась):**
1. **При аудите/проверке «все ли в done» — смотреть не только статусы, а целостность
   хвоста**: для каждого не-терминального гейта/рабочей фазы проверить
   `SELECT child_id FROM task_links WHERE parent_id=<id>` — если `children=[]`, а
   по канону должен быть ребёнок, граф БРЕД (хоть и весь done). «Все карточки done»
   ≠ «граф дошёл до кода».
2. **Если хвост не развёрнут — развернуть вручную** (координатор/оркестратор):
   создать недостающие фазы канона цепочкой (
   `kanban create "GATE:diagnose-review …" --parent <dx>; TZ:patch; TZ:finalize;
   HF:backup; HF:impl; HF:test; HF:docs-handoff; ORCH:shared-state; GATE:done`),
   связав правильно, и закомментировать «оборванный хвост — развёрнут вручную».
   Диспетчер подхватит и доедет до кода. НЕ дублировать повторную диагностику —
   переиспользовать уже готовый `_fix_plan_*.md` как body новой DX/продолжающей фазы.
   Root-as-container при это: корень в `ready` диспетчер немедленно забирает как
   рабочий (`running`) → `hermes kanban reclaim`, затем
   `complete --result "контейнер закрыт"` для промоушена детей.
3. **Не доверять «граф весь done»** в ответе на «проверь, не осталось ли подвисшего».
   Глубокий аудит хвостов обязателен — фиктивная видимость завершения маскирует
   нереализованную доработку.

## Инвариант №1 — auto-гейты — штат, не привилегия фразы

**Auto-гейты — норма (DKP 0.4.0, императив 28.09), НЕ привилегия фразы «1 проход».**
`GATE:take-into-work`, `GATE:plan-approve`, `GATE:done` — **always auto**:
- `GATE:take-into-work` — `auto-pass: ac-shown` после показа AC в origin;
- `GATE:plan-approve` — `auto-pass: architect-plan`;
- `GATE:done` — auto-complete после preflight exit 0 (префлайт достаточен, фраза
  «готово» = идемпотентный no-op).

Однопасс = **не** склейка рабочих фаз в один вызов и не пропуск обязательных
HF/TZ/REV-фаз. Каждая работающая фаза — отдельная карточка и (если нужен LLM)
отдельный `agent -p` своей ролью.

Never auto (кризисный HITL): `GATE:go`, `GATE:block-accept`, IDEA `blocked`,
crisis-block корня (`review-required: crisis`).

## Инвариант №2 — `TZ-WRITE` / `PLAN-IMPL-TAIL` не схлопывать

- **TZ-WRITE(full)** = отдельные карточки и отдельные `agent -p`:
  `TZ:stabilize`(может без LLM) → `TZ:compress`(оркестратор) → `TZ:patch`(architect grok)
  → `REV:tz`(sonnet, если флаг) → `TZ:finalize`(architect, запись+инвентарь).
- **`TZ:compress` — НЕ invoke-роль**: роль `compressor` = Hermes default (deepseek-flash),
  invoke-role для неё — stub/пустая единица. Работа оркестратором вручную: прочитать
  мастер-ТЗ (ключевые секции для слага), написать `dev/<slug>/extract.md` (3–5 КБ),
  дописать в `journal.md` маркер `context-used: phase=TZ:compress role=compressor
  evidence=path=…`, затем `complete-phase`. `emit-prompt` для неё не нужен.
- **`TZ:stabilize` и `TZ:compress` оба требуют маркер `context-used:` в journal.md**
  (G2: `complete-phase` падает «context-used marker required»), хотя это sirene-фазы
  без emit-prompt. Маркер дописывать напрямую в journal перед complete.
  Склейка даже с «ревизор где-то рядом» запрещена.
- **`TZ:stabilize` complete-phase: evidence обязан нести `path=/version=/mtime=` ТРОЙКОЙ, а не голый `path=`.**
  Первый вызов с `--evidence 'path=<мастер>'` → rc=1 «TZ:stabilize: need tz_path+tz_version on state or
  path=/version=/mtime= in evidence» (гейт парсит evidence на все три поля, state на stale-слоге их ещё не
  знает). Верная форма: `--evidence 'path=…/EcosystemIntegration_TZ.md version=0.7.0 mtime=2026-10-25T15:46:16+03:00'`.
  После этого гейт пустит к G2 (`context-used:` маркер), и только следом complete пройдёт.
- `--resume` архитектора — только повтор **той же** фазы (итерации TZ:patch),
  не «patch+finalize+impl в одной сессии».
- `HF:impl` и `HF:test` — разные карточки (иначе нет metadata тестов, parents лгут).
- Правило «1 `agent -p` = 1 роль»: если промпт просит исполнителя заодно дописать
  ТЗ/план/ревью — **стоп**, разделить.

## Инвариант №3 — GATE:done нельзя «наговорить»

Перед закрытием обязательно проверить (самому / preflight-скриптом):
1. Корень `DEV/<slug>` существует (не off-board Cursor-конвейер без графа).
2. Все обязательные фазы кейса есть и done (гейты: done или comment `auto-pass`).
3. Артефакты на месте: план-файл (`HF:plan`), в затронутых `*_TZ.md` **нет** строк
   «Реализация на диске: нет» / «на диске: нет», если docs-handoff заявлен done.
4. Если флаг `REV:tz` был ON — карточка done **или** явное `flag-waived: Sasha`.
   Не «заявил ревизора», а реальный прогон sonnet.
5. Эвристика свёртки: один `session_id` на фазах с разной моделью/ролью → не
   закрывать, `kanban_block(review-required: collapsed-chain)`.

Реализация: `~/WorkVault/Registries/pipeline_gate_done_preflight.py` (exit≠0 →
complete запрещён, comment с чек-листом провалов). Пока скрипта нет — делать те же
проверки вручную перед каждой «готово».

**Питфолл — на workflow-only (DevWorkflow file-state, канбан выключен) GATE:done
проверяется только `pipeline.cli preflight`, НЕ legacy-скриптом.**
`pipeline_gate_done_preflight.py` читает `~/.hermes/kanban.db` и ищет корень
`DEV/<slug>` в канбане; на fresh-слаге файлового состояния (состояние только
`dev/<slug>/_state.json`, канбан отключён) он закономерно падает «корень
DEV/<slug> не найден» и ложно краснеет `SKILL-CHANGE: нет skill_change_branch`.
Это НЕ баг инструмента — применён не тот checker. Правильный путь закрытия
GATE:done на workflow-only: `pipeline.cli preflight --slug <slug> --mode done`
(встроенный `pipeline_preflight.py`: мандаторные фазы, отсутствие open-questions /
operator-holds, AC-delivered, git-proof) — читает `_state.json`. Внутренний
`complete-phase GATE:done` на `next` даёт `{"action":"AUTO_GATE"}` → покажи AC в
origin → complete auto-pass; внешнюю legacy-проверку на workflow-only не зови.

**Preflight `--mode done` на workflow-only: `--case`-флаг отсутствует, пустой stdout + rc=0 = PASS, `AC-delivered` живёт в journal.md.** `pipeline.cli preflight --slug <slug> --mode done` НЕ принимает `--case` (`unrecognized arguments`) — режим уже известен из `_state.json`. Перед прогоном обязателен маркер `AC-delivered: origin` + секция «Отчёт AC» с числовыми якорями `AC-###` в `journal.md` (файл-эквивалент комментария гейта) — иначе «preflight fail: AC-report missing». Пустой stdout (ни одного слова) с exit 0 = PASS; НЕ интерпретировать пустоту как сбой. Типовые красные после первого прогона: `git proof: uncommitted impl files` (путь resolved от `~` — см. питфолл changed_files) и `AC-report missing` (маркер в journal).

**Питфолл `find_root` (09.09):** префлайт искал корень точным матчем
`title = 'DEV/<slug>'`, но оркестратор именует CHANGE/DEV-корни с суффиксом
описания, напр. `DEV/PIIScan-pii-hygiene (CHANGE: …)`. Точный матч не находил
корень → exit 1 «корень не найден» и **пропускал всю проверку графа**, хотя все
фазы done. Симптом обманчив: exit≠0 при завершённой цепочке.
**Фикс:** префиксный матч `LIKE 'DEV/<slug>%'` (`ORDER BY created_at ASC LIMIT 1` —
старейший корень при игре с одним slug на разном filling). Что повлияло: у
Change-кейса на GATE:done может «не находиться» корень именно из-за суффикса.
Веди вручную/диагностируй перед тем, как считать цепочку недоделанной.

**Питфолл `find_root`-блок (09.09, обратная сторона): НЕ создавать корень как `CHANGE/<slug>`.** Префлайт ищет корень **только** по префиксу `DEV/{slug}%` (docstring find_root: CHANGE/DEV-корни именуются `DEV/<slug> (CHANGE: …)`, префикс всегда `DEV/`). Если оркестратор при создании корневого kanban_create назвал title `CHANGE/<slug>` (или `BUG/<slug>` / без префикса) — префлайт вернёт exit 1 «корень DEV/<slug> не найден», хотя **вся цепочка фаз done**. Это не значит, что цепочка недоделана — это ошибка имени у корня. Доп. ось: **рег.истр slug** в title корня должен совпадать с `--slug` префлайта и с именем план-артефакта `HF-plan_<slug>*.md` (обычно нижний регистр; префлайт `glob HF-plan_%s*.md`). Правило при создании корня:
1. **Префикс всегда `DEV/`** независимо от кейса (`DEV/<slug>` для DEV, `DEV/<slug> (CHANGE: …)` для CHANGE, `BUG:<slug>` — тоже некорректно, префлайт ждёт DEV-префикс).
2. **slug держать в консистентном регистре** — нижний регистр, как в имени план-файла `HF-plan_*.md` и в `--slug` вызова.
3. Если GATE:done заблокировался «корень не найден», а граф весь done — сначала `SELECT id,title FROM tasks WHERE title LIKE '%<slug>%'` в kanban.db, убедиться, что корень есть и префикс `DEV/` + регистр slug совпадают; при необходимости прямой `UPDATE tasks SET title='DEV/<slug> (CHANGE: ...)' WHERE id=...` + `kanban_unblock` на GATE:done. Не списывать цепочку на «недоделанность» — имя корня лечится точечно.

**Питфолл — разделитель в заголовках ФАЗ («PHASE: slug» vs «PHASE — …») — ПОЧИНЕН (W1).**
`phase_of_title()` в `pipeline_gate_done_preflight.py` принимает **оба** формата:
`PHASE: slug` (двоеточие) и `PHASE — slug` (тире), т.е. канон заголовков
`PREFIX:фаза` больше не роняет префлайт. Если preflight всё же возвращает exit 1
«фаза отсутствует в графе» на формате `PHASE: slug` — сверь версию скрипта
(починка W1), и только при старом скрипте приводи заголовки к одному разделителю.

**Питфолл — G2 preflight требует `context-used:` блок на agent-p-фазах (AC-H06).**
Для каждой TZ/HF/BUG/REV-фазы `pipeline_gate_done_preflight.py` смотрит в
`task_runs.metadata` ключ `cursor_session_id`/`cursor_session_ids`/`cursor_session`.
Если фаза РЕАЛЬНО звала Cursor `agent -p` (что нормально для HF:plan/HF:impl/review
в контуре Cursor), preflight на GATE:done требует в body/result/комментариях карточки
блок `context-used:` c `card: <этот tid>`. Нет блока → preflight FAIL «нет
context-used:», даже при коде на диске и зелёных тестах. Regex:
`context-used:\s*\n\s*card:\s*(\S+)` — блок своими строками, `card` точно совпадает
с tid карточки. Фазы, НЕ звавшие agent -p (docs-handoff/test/finalize без Cursor),
auto-skip — маркер им не нужен.

**Правило:** закрывая агентную TZ/HF/BUG/REV-фазу, которая реально прогнала Cursor,
вложи в её complete-комментарий блок `context-used:` (card/root/phase/tz_version/
tz_mtime) сразу, при закрытии — а не ретро на GATE:done. Preflight не прощает слишком
короткий/совпавший сторонний маркер (mismatch тоже FAIL), и retro-добавка на GATE:done
лишнего круга стоит. Если GATE:done уже заблокировался — до-комментируй блок на саму
фазу (не на гейт) и перезапусти preflight; карточку гейта не трогай.

## Инвариант №3в — AC-отчёт: «наличие в графе» ≠ «доставка Саше в чат»

Префлайт `ac_report_ok()` считает PASS, если в *любом* источнике достижимого графа есть
`AC-\d{3}` + маркер секции («Отчёт AC»/«AC-report:»/«как тестир»): body+result корня,
body+result фаз GATE:done/HF:test/HF:docs-handoff, ВСЕ комментарии графа, fallback-файл
`AC-report_<slug>*.md`. Это проверка «текст похож на отчёт», **не** «Саша получил отчёт
в диалоге». Несколько ложных источников дают зелёный при отсутствии реальной доставки:
комментарий GATE:take-into-work со списком AC, body-шаблон GATE:done («…отчёт AC… как
тестировали. Саша.» — инструкция, не отчёт), комментарий HF:test с перечислением IAC
(тоже «как тестировали» + AC-001). Любого одного достаточно для ложного PASS.

**Правило:** окружение префлайта read-only и видит только kanban.db + файлы, чат Саши — нет.
Единственный согласованный замок доставки — явная аттестация воркером того же класса,
что `flag-waived: Sasha` / `auto-pass: one-pass mode`: контракт на GATE:done = воркер
(1) публикует отчёт `AC-### → как тестировали` в **origin-топик Саши** (не Monitoring :7),
(2) пишет маркер `AC-delivered: origin` в комментарий карточки GATE:done (regex
`AC-delivered:\s+\S+`; голый `AC-delivered:` — FAIL), (3) ЗАТЕМ запускает preflight.

**Как найти origin-топик графа (не угадывать):** origin = `thread_id` из `kanban_notify_subs`
для корня/карточек графа (`SELECT task_id,thread_id FROM kanban_notify_subs WHERE task_id='<root>'`).
У DEV-графа все карточки подписаны на один топик — он и есть origin (напр. Backlog = :6, Tools = :3).
Не дефолтить на Monitoring :7 и не слать в личный DM. Доставка — `TELEGRAM_BOT_TOKEN` из
`~/.hermes/.env` (бот sirene_vm_bot, админ группы), `sendMessage` c `chat_id=-1004300127777` +
`message_thread_id=<thread>`; доставка в топик подтверждается `ok:true` + `message_id` в ответе.
Перед реальным постом прогнать smoke в тот же топик (`text=smoke`), чтобы убедиться, что бот
состоит в группе и доставляет именно в этот топик (см. tutu-telegram-delivery).
Preflight проверяет маркер И сужает источники тела отчёта до комментариев GATE:done +
файла `AC-report_<slug>*.md` (исключить take-into-work / body-шаблон / HF:test).

**Питфолл — тело отчёта матчится case-sensitive подстрокой, не регэкспом регистронезависимым.**
`ac_report_ok()` = `any(m in text for m in ("Отчёт AC", "AC-report:", "как тестир"))`, где `in` —
буквальный подстроковый поиск с учётом регистра. Комментарий с русским заголовком
«AC-отчёт — …» и фразой «Как тестировали» (заглавная К/Т) НЕ проходит: ни один маркер не
совпадает. Фиксируется отдельным close-комментарием. Правило при составлении тела отчёта:
- заголовок ровно `AC-report:` (двоеточие, не тире/«AC-отчёт»),
- фраза «как тестировали» в нижнем регистре (`как тестир` — префикс маркера),
- каждый пункт с якорем `AC-###`; `AC-delivered: origin` — отдельная строка (regex `\s+\S+`,
  голый `AC-delivered:` = FAIL). Одна строка с `AC-report: … как тестировали` + список AC-###
  закрывает и тело, и маркер доставки за один комментарий.

**Правило — R5-подписку ставить явно при создании графа, не после.** `hermes kanban create`
(и канонич. батч корень+DX) НЕ создаёт строку в `kanban_notify_subs` автоматически. Если
оркестратор не вызовет `hermes kanban notify-subscribe <root> --platform telegram --chat-id
-1004300127777 --thread-id <origin> --chat-type group --delivery-mode notify+wake` сразу после
создания корня, фаза ИЗМЕНИТ SUB checkbox, но уведомления (done фазы, блокировки, AC-отчёт)
Никуда не уйдут — Саша шлёт «Где будет статус по задаче?» через часы, а не потому что
задача застряла. Делай subscribe как шаг разворота графа (в одном батче с корнем+DX), не
откладывай до первого вопроса. Это же снимает питфолл «origin нерезолвится из пустых subs».
Если граф УЖЕ создан без подписки — догони её сразу при обнаружении (`notify-subscribe` на
корень в origin-топик), не жди вопроса Саши.

**Питфолл — `scheduled` ≠ подвес: это retry-wait после рейпа воркера.** Диагностика показала
карточку (BUG:diagnose) в статусе `scheduled` с `last event terminal_worker_reaped` — воркер
убит, задача вернулась на автоперепланирование диспетчером. `hermes kanban promote` на такой
карточке вернёт `promoted:false` с причиной `promote only applies to 'todo' or 'blocked'` — это
НЕ ручной промоут и НЕ «промоут сломан»: `scheduled` обслуживает диспетчер сам. Не паниковать,
не заводить баг «зависания» и не мучить promote. Подождать перепланирование; если карточка так
и зависла в `scheduled`, переведи её в `todo`/`blocked` (снятие retry-gate) и только потом
promote. ПРОВЕРЕННЫЙ recovery при зависшей `scheduled` (когда диспетчер не перевзял после
reap даже при живом backend): `hermes kanban unblock <id>` (снимает `scheduled`→`ready`;
`reclaim` на `scheduled` НЕ работает — «not running», это НЕ путь),
затем один `hermes kanban dispatch` — диспетчер подхватит в `running` (новый run_id).
Частая первопричина самого рейпа — падающий Cursor CLI воркера, т.е. карточка —
симптом уже заведённого бага, а не самостоятельный дефект: не дублировать root cause.

**Питфолл — origin-топик, когда `kanban_notify_subs` пуст для всех карточек графа.**
Граф, развёрнутый оркестратором в не-подписанной сессии, не имеет строк в `kanban_notify_subs`, и
«origin = thread_id из kanban_notify_subs» не срабатывает. Резолвить через сессию оркестрации:
`~/.hermes/sessions/sessions.json` — ключ `agent:main:telegram:group:-1004300127777:<thread>` несёт
`session_id`; найти по session_id сессию, в которой создавался корень (`kanban create … DEV/<slug>`),
её thread и есть origin. Бот/доставка те же (sirene_vm_bot, chat `-1004300127777`), smoke-прогон в
топик обязателен перед реальным постом.

**Фатальная ошибка порядка (второй корень):** проверка доставки мертва, если в скилле
порядок СНАЧАЛА preflight, ПОТОМ чат — маркера ещё нет, PASS невозможен, и если маркер
обязателен, все живые GATE:done начнут FAIL. Доставка/маркер — **до** preflight, не после.

**Trust-баланс:** воркер теоретически может соврать (маркер без поста) — тот же принятый
trust, что у `flag-waived`. Страховка была «GATE:done HITL — без отчёта Саша не скажет
готово»; с переходом на **auto** GATE:done эта страховка снята — поэтому маркер
`AC-delivered: origin` и остаётся жёстким (preflight FAIL без него), а доставка строго
до auto-complete. Не проверять доставку списка AC-001 на GATE:take-into-work
в этой же починке (похожая дыра, другой гейт, отдельная карточка).

## Инвариант №3б — hold «ждать готово» после preflight exit 0 = ДЕФЕКТ поезда (ИНВЕРТИРОВАН)

**Прежняя норма v1.1.0 отменена (DKP 0.4.0, императив 28.09).** В пошаговом ходу
после preflight PASS (exit 0) воркер `GATE:done` обязан `kanban_complete`
(`auto-pass: preflight-0`), **НЕ** блокироваться в ожидании «готово» Саши. Снятие
`GATE:done` из пошагового хода вместо auto-complete = **дефект поезда** (hold
«ждать готово» после preflight 0 — это ровно та дыра HITL, которую убираем).

Признак дефекта: `GATE:done` в `blocked` c `review-required: ждать готово` при exit 0.
Действия: проверить preflight exit 0 → `kanban_complete` (auto-pass); не ждать фразу
«готово» (она идемпотентный no-op), не пересоздавать карточку. Отчёт AC уже доставлен
в origin до preflight (контракт `AC-delivered: origin`).

**Смежный питфолл:** не делать ручной `kanban complete`/`unblock` на гейте, который
`running` — диспетчер уже владеет им, вызов вернёт `cannot complete <id> (unknown id
or terminal state)`. Это означает «диспетчер обрабатывает», а не «неправильный id»:
проверь статус списком и дай диспетчеру доработать/авто-пасснуть.

## Инвариант №3г — пороги сторожа (первичный контур)

`kanban_stuck_monitor.py` (или sibling) на cron 5–10 мин исполняет детерминированные
правила (слаг dev-process-rework). Пороги:

- `running` без heartbeat **>20 мин** → reclaim + retry (не wall-clock от `started_at`;
  легитимный `agent -p` идёт часами при живом heartbeat).
- `protocol_violation` + D1 Cursor-slug (`cursor-*`/`composer-*`/`claude-sonnet-*`/`gemini-*`
  без `/`) → `set-model <id> none` на всех минах слага + retry.
- REV `CHANGES_REQUIRED` / `REQUEST_CHANGES` → rework-ребёнок рабочей фазы, не голый unblock.
- `running` >4ч при живом heartbeat → notify координатору origin графа (не обязательно Саше).
- `running` >8ч или 2 неудачных авто-рестарта → notify Саше в origin + `kanban_block`
  корня `review-required: stalled-train`.
- `ready` >20 мин при закрытых parents → алерт координатору (диспетчер не берёт);
  `triage` IDEA не трогать.

Сторож — не LLM-крон «проверь три графа» и не ядро dispatcher; mute при 0 инцидентов (R5).

- Это не «канбан сломан» — это транзиентная среда. Если потом спавн ожил,

4. Краш — про воркер, который забыл терминальный kanban-вызов, а не про качество
   работы. Это в той же категории, что инвариант №6 (среда vs конфиг): различай.

Триггер: карточка `blocked` сразу после того, как серия воркеров «тихо» упала
с rc=0.

стабилизация→compress→patch→[REV]→finalize (карточки по одной) → take-into-work

## Питфолл — BUG:diagnose (и любой child) нельзя complete, пока корень-контейнер `running`

Симптом (26.09, DEV/topic-origin-routing): BUG:diagnose с рабочей карточкой `running`
выполнил диагностику (emit-prompt + agent -p архитектора, план на диск), но
`kanban_complete` стабильно даёт `could not complete <id> (unknown id, stale run, or
already terminal)` при валидном lock/run. Причина — НЕ stale run и НЕ env: это
**dependency-гейт `_parents_satisfied`**. Если родитель (корень-контейнер
`DEV/<slug>`), созданный тем же create-батчем, остался в `status=running` (не закрыт
как контейнер сразу после fan-out), любой child не пройдёт `_parents_satisfied` →
`complete_task` → False → этот же generic-текст. Игнорировать текст ошибки как
«работу потеряли» — нельзя.

Правила (различай два сценария):
1. **Работу вёл я сам, корень закрыл кто-то другой** (орхестратор/Саша/диспетчер):
   проверить `SELECT status FROM tasks WHERE id='<root>'`. Если корень стал `done` —
   dependency-гейт снят, и если карточка ещё `running` у меня — повторить
   `kanban_complete`. Если карточка уже `todo`/`blocked` (я успел заblock'ить) —
   `kanban_block(kind=dependency, reason=…)` уже корректно поставил её в очередь
   авто-резюма: диспетчер снова возьмёт её после `done` родителя, воркер-потомок
   доcomplete'ит. Не мучить complete из stale-run сессии.
2. **Корень-контейнер создан пользователем и забыт `running`** (никто не закрывал):
   как воркер-scoped я не могу мутировать родителя (`kanban_complete` на корне →
   «worker is scoped to task <self>; refusing to mutate <parent>`). Это программная
   гарантия: закрыть корень-контейнер может только оркестратор/Саша в интерактивной
   сессии (`kanban_complete` на корне без кода, container=true) или канонический
   «закрой сразу после fan-out». Тогда: `kanban_comment` с полным handoff + кратким
   ⚠️ «закрой корень-контейнер» и `kanban_block(kind=dependency)`. Блокировать с
   dependency (не needs_input): это ждёт завершения родителя, не человека-решения.

Проверка диагноза до паники: `_parents_satisfied` = любой прямой parent НЕ в
`done|archived` → child не complete. Единственный вопрос — кто и когда закроет
корень (сам/диспетчер/орхестратор), а не «упал ли воркер».

## Инвариант №9 — мелкая CHANGE-доработка: конверт оркестрации ≈ 90%

Диагноз (09.09, задача Саши «раньше дешевле и быстрее — найди ускорение в разы»):
мелкая CHANGE-доработка (~1-3 файла, TaskRefresh §27) развернула **полный** пайплайн
нового инструмента — 16 карточек, ~162 мин активного + ~115 мин простоев, при этом
реально «делали фичу» (impl+test) ~12 мин (**7%**). Причины: CHANGE = полный TZ-WRITE
(+REV default ON), one-pass ≠ быстрый путь (гейты авто-проходят, но фазы остаются),
механика гонится через LLM-воркера, двойной архитектор (TZ:patch + HF:plan), канон
компрессора сам себе противоречит (скилл=composer vs промпт=gemini-flash).

**Класс-вывод:**
- **Сперва ищи лёгкую классификацию.** Если доработка по размеру близка к BUGFIX —
  не протаскивай её как «полный CHANGE с auto-pass». Кандидат на слим-путь
  CHANGE-LIGHT (6 карточек: TZ:patch→impl→test→docs→ORCH→GATE:done), критерии в
  `references/pipeline-optimization-small-change.md` §C.
- **Не смешивай «ускорить механику» с «устранить причину переделок».** Гейты/*.sh,
  skip compress и непрерывный spawn ускоряют конверт, но не починят «patch×2» (30%
  времени = одно решение записано трижды). Сначала диагностика причины, потом
  автоматизация.
- **Простои (82/33 мин) — подозревать poll-interval диспетчера, не «холодную модель»**:
  поднять логи оркестратора и проверить фиксированный poll прежде чем чинить spawn.
- **REV OFF для мелких — только вне shared/foundational-модулей** (парсинг дат,
  запись задач). Число файлов ≠ blast radius. В shared-модуле дорогой retry
  окупает REV.
- **Все множители — гипотеза (n=1).** Любой слим-граф/новый skip вводить пилотом на
  3-5 реальных циклах с метрикой follow-up BUGFIX, а не дефолтом с одного прогона.
- **Не склеивать impl+test+docs в один agent -p** (ломает роли и preflight) — это
  единственный «быстрый путь», который остаётся запрещённым даже в оптимизации.

Полный разбор, таблицы приоритетов и оговорки ревизора — в
`references/pipeline-optimization-small-change.md`.

## Инвариант №10 — довоз с оборванным хвостом: встроить канонический каркас, НЕ ковейл

Если довоз доработки построен как «голый HF-хвост» (`BUG:diagnose → GATE:diagnose-review
→ GATE:plan-approve → HF:impl → HF:test → … → GATE:done`), preflight GATE:done вернёт
exit 1 «фаза отсутствует в графе» по канону кейса (недостающие TZ:patch/TZ:finalize/
GATE:take-into-work/HF:plan/HF:backup/ORCH). Это структурная недостроенность графа —
**не лечится ковейлом** (waiver = снова «граф неполон, но закрыли»).

**Правило — встроить фазы по смыслу, не театром:**
1. Создать недостающие карточки канона в правильном порядке цепи
   (`TZ:patch → TZ:finalize → GATE:take-into-work → HF:plan → HF:backup → … →
   ORCH:shared-state`), связав `--parent` зеркально существующей линейной цепи; если
   фазы не в том порядке, **релинкнуть** через
   `DELETE/INSERT task_links` (бэкап kanban.db перед этим) так, что цепь станет
   канонической: `…→ TZ:patch → TZ:finalize → GATE:take-into-work → HF:plan →
   HF:backup → GATE:plan-approve → HF:impl → HF:test → HF:docs-handoff → ORCH →
   GATE:done`.
2. Закрывать встроенные TZ/plan-фазы как «артефакт довоза уже на диске», не
   требуя повторной имплементации: `TZ:patch/finalize` — «§29 на диске, новой
   секции нет», `GATE:take-into-work` — показать AC-### в origin + `auto-pass`,
   `HF:plan` — off-board на существующий план-файл `*HF-plan_<slug>*.md`,
   `HF:backup` — снимок текущего (пост-impl) дерева.
3. **docs-handoff: снять маркер «код не пишется»/«на диске: нет»** в ТЗ — он висит
   при коде на диске и даёт ложный красный (инвариант №4).
4. Ковейл preflight при структурной неполноте графа — запрещён; встраивай каркас.
5. **Встроенные фазы создавать СВЯЗАННЫМИ в цепь с первого шага (`--parent`), иначе диспетчер заберёт их в `running` до лимика.** Трап (tz-mirror-overwrite): создал GATE/TZ-фазы `kanban create … --parent <dx>` по разным шагам — GATE ушёл в `running` сам, и `kanban link <dx> <gate>` вернул `cannot link: child is already running`. Решение для РУЧНОЙ канонизации: (а) если гейт уже `running` — `reclaim` + `complete --result "auto-pass"` (ретро-фаза без реальной работы), затем `link` — или создавать сразу с `--parent` в одном батче; (б) если рабочие фазы (HF:impl и т.п.) уже привязаны к старому родителю (например DX), а каноническая цепь должна идти через новые GATE/TZ — `kanban unlink <old_parent> <work>` затем `link <new_phase> <work>`, бэкап kanban.db перед DELETE/INSERT task_links.
6. **Ретро-фазы закрывать как "артефакт уже на диске", не заставлять повторно писать код**: GATE:diagnose-review — `DX t_X done, root cause подтверждён, классификация LIGHT`; TZ:patch/TZ:finalize — план реализован в HF:impl (commit/commit), ретро-оформление; auto-pass через `reclaim`+`complete`, не через Kовейл гейта done.

## Питфолл — `needs_input` ≠ «ждёт Саши»: классифицируй по блок-ризоне, не по kind

`block_kind=needs_input` на канбан-карточке ставит воркер/архитектор и он НЕ означает
«жду решения Саши». Это может быть фон: авто-rework (`CHANGES_REQUIRED`), недоработка
архитектора, зависимость от другого графа, структурный дефект графа, уже решённый
вчера вопрос. Статус-отчёт/монитор, который помечает любой `needs_input` как
«ждёт Саши» (такое зашито в наивной ветке `if bkind == 'needs_input'`), врёт и спамит
Сашу ложными блокерами.

**Правило:** для отчёта/ответа «что ждёт Саши» читай **reason** последнего
`blocked`-события (`SELECT payload FROM task_events WHERE task_id=? AND kind='blocked'
ORDER BY created_at DESC`), а не `block_kind`. Реальный HITL = причина просит решение/реплику
(«нужно решение», «принять», «подтверди», «как поступить»). Фон = причина содержит
`CHANGES_REQUIRED`/`rework`/«недоработк»/«зона оркестратора»/«зависимост»/«оборван» —
это авто-цикл, до Саши не эскалировать, показывать отдельной строкой «фоновый блок» с
причиной. Ключевые терминальные события (done/blocked/crashed) — в origin, фоновые —
в сводку, не в «ждёт решения».

## Питфолл — НЕ двигать статусы карточек, чтобы «починить» отчёт: диспетчер защищён loop-guard

Когда отчёт/монитор ложно показывает блокер «ждёт Саши», правильный фикс — **правка
классификации отчёта** (см. предыдущий питфолл), а НЕ перемещение самих карточек.
Ручной `unblock` + повторный `block` (даже другой `--kind`) на канбане триггерит
защиту от петель: диспетчер сам рутит карточку в `triage` («unblock loop detected —
needs a human decision») или `review`/`cannot block`. Прямой `UPDATE tasks SET status=...`
в kanban.db для «восстановления» после этого обходит инварианты диспетчера и может
порвать graph/queue — откатывать такие правки тоже через CLI-механику, не сырым SQL.
Порядок действий при ложном блокере:
1. Проверить по факту `block_kind` И `reason` (это HITL или фон?).
2. Если фон — поправить отчёт/промпт, карточку НЕ трогать.
3. Если реальный HITL и решение уже дано — `hermes kanban unblock` ровно один раз.
   Не unblock→reblock: loop-guard воспримет повторный block как цикл и зашлёт в triage.

## Питфолл — `kanban specify` переименовывает карточку; root в `triage` блокирует `promote` детей

Два связанных CLI-факта постановки:
- **`hermes kanban specify <triage_id>` выводит из triage в todo, НО автоматически
  записывает новое англоязычное название** (ре-тайтлит по телу), затирая исходный
  русский/описательный заголовок. После specify проверь title и при необходимости
  верни осмысленное имя — иначе в отчётах/аудите потеряется, о чём карточка.
- **`promote` ребенка упирается в родителя в `triage`**: `promote <child>` →
  «unsatisfied parent dependencies» и rejected, пока корень `triage`. Сначала выведи
  корень из triage (`specify` → todo → диспетчер возьмёт как контейнер, закрой
  `complete --force` сразу после fan-out), затем промоутится ребёнок. Это не поломка
  promote — это dependency-гейт `_parents_satisfied`.

## Инвариант №11 — git-proof: закоммитить impl-пути ДО GATE:done (G3)

Перед закрытием GATE:done с кодом в git-worktree (не Vault-реестры) impl-пути из
`changed_files` HF:impl должны быть **закоммичены** (`git status --porcelain -- <path>`
пуст). Untracked/modified → preflight FAIL «git-proof». Это страх выпустить
прод-доработку, не зафиксированную в git (риск повторной потери: «код на диске,
но не в git»).

**Правило:**
1. Собрать `git status --short` по всем затронутым репозиториям (не только
   основному инструменту — правки могут быть в `EntityRegistryCLI`, `TaskRefresh`
   и т.п., рядом с инструментом). Закоммитить каждый репозиторий.
2. **Не тащить в коммит посторонние/вынесенные правки**: если ревизор вынес файл
   (напр. config.py §30 вне §29), оставить его в working tree, даже если стейдж
   выглядит «грязным». `git add` точечно по пути слага.
3. Связанные Vault/реестры (`~/WorkVault/Registries` — не git) — достаточно факта
   файла на диске; git-proof к ним неприменим. Не трать усилия на их «коммит».

**Питфолл — `changed_files` HF:impl должны резолвиться от `~`: home-relative ЛИБО абсолютные, НЕ repo-root-relative.**
`git_proof_paths()` резолвит каждый путь через `_to_abs_home()`: абсолютный возвращается как есть, остальное join с `~`. Путь от КОРНЯ РЕПО (`scripts/notify_pending.py` для репо `~/USERTOOLS/ProtocolFromSummary`) резолвится в `~/scripts/notify_pending.py` — файла нет → FAIL «не на диске», хотя файл закоммичен. Это ложный красный на закоммиченной работе, и симптом обманчив (exit 1 при валидном графе). Правило: пиши ЛИБО абсолютные пути (надёжней всего), ЛИБО home-relative с префиксом `~/<repo>/`; перед preflight вручную проверь `os.path.isfile` для каждого пути из `changed_files` и `git status --porcelain -- <path>` пуст. Также: файлы физически лежат под `~/<repo>/`, поэтому и коммитить их в `~/<repo>`, и в metadata указывать через префикс `~/<repo>/`.

**Питфолл — тело AC-отчёта требует ЧИСЛОВОЙ якорь `AC-\d{3}`, буквенный `AC-S##` не проходит.**
`ac_report_ok()` сначала требует `AC_ANCHOR_RE = AC-\d{3}` в тексте, потом маркер секции.
ТЗ, чьи критерии названы `AC-S01..S10` (suffix к классу, напр. слаг-специфичные AC),
дают в отчёте только буквенные якоря — preflight FAIL «нет артефакта AC», хотя отчёт
корректный. Правило: в тело отчёта ВКЛЮЧИТЬ хотя бы один числовой якорь `AC-###`
(напр. итоговую строку «регресс AC-001..AC-095 + критерии слага AC-S01..S10») — это
проходит и якорь, и секцию, один комментарий закрывает и тело, и маркер доставки.

## Питфолл — `kanban create` с `--priority critical` и длинным `--body` молча фейлит create, маскируясь JSON-парс-ошибкой

CLI-факты ручного разворота/починки графа (не канон, а механика вызова):
- **`--priority` — целое число-тайбрейкер, НЕ строковый класс (`critical`/`high`).**
  `hermes kanban create … --priority critical` падает `invalid int value: 'critical'`
  **ДО создания** карточки. Если вызов обёрнут `--json \| python3 -c "json.load()"`,
  ничего не создаётся, stdout пуст → `JSONDecodeError: Expecting value`. Ложный вывод:
  «парсер сломался», реальная причина — невалидный приоритет. Используй целочисленный
  (0-100; 90 = высокий).
- **Длинное/сложное тело через `--body "…"` в bash ломается** на `$`, обратных кавычках,
  кавычках и несбалансированных скобках в тексте (home-relative, $5.30, `{}` в примерах)
  → `eval: unexpected EOF / syntax error`. Пиши тело в temp-файл (`/tmp/<slug>_body.txt`)
  и передавай `--body-file` — это надёжно для любого содержимого.
- **`--json` на create возвращает пусто, когда create фейлит** (не JSON-строку ошибки).
  Не паникамь по JSONDecodeError как по «парсеру»: пустой stdout почти всегда = create
  не создал. Прежде чем верить `json.load`, покажи raw-вывод вызова; при пустом —
  перепроверь аргументы (приоритет/флаги), не списывай на json.

## Инвариант №12 — зелёные тесты фикса ≠ задача пользователя сделана: прогони ИСХОДНУЮ операцию против реального объекта

**Питфолл — вердикт архитектора ≠ принято: при развилке «идея Саши vs схема архитектора» заказать ПРЯМОЕ СРАВНЕНИЕ, не штамповать фазу/импл на одном варианте.**  Если Саша предложил собственный подход (напр. «положить актуальность/вероятности слага в реестр → промпт из данных»), а архитектор дал иной (overlay-константа в `task_slug.py`, мотивируя запретом SoT/`additionalProperties:false`), одного вердикта архитектора недостаточно: Саша может отвергнуть «нашлёпку/хардкод в промпте» и потребовать обоснованного сопоставления. Норма: прогнать архитектора на **прямое сравнение двух вариантов** с однозначным «какой лучше + почему» и разбором «что нормально / что ненормально» в каждом, показать Саше дословно; двухчастные вердикты («идею берём, схему нет» — источник в данных ✓, P()/числовые веса на сущности ✗) транслировать целиком. **Не `complete-phase` и не штамповать импл принять как успешный, даже если код написан и тесты зелёные (`pytest 496 passed` не снимает открытую архитектурную развилку).** Хранить паузу через `write_state` (перемотка фазы в `todo`/ждёт вердикта), а не закрывать её фразой «импл же принят». Это продолжение правила «NS, не выдавай своё мнение за вердикт»: если я уже подал pick_hint Саше как решённое, а он оспорил — не защищать как «архитектор предложил лучше», а честно вынести оба варианта на сравнение. Также: сужение BUGFIX→LIGHT после архитектурной развилки — только после закрытия вердикта, не до.

**Настройка вызова ролей (DevWorkflow file-state):** Роли (архитектор/ревизор/исполнитель) через `pipeline.cli invoke-role` — **только в фоне** (`terminal background=true, notify=true, persist_on_release`); foreground с таймаутом 180с убивает вызов до ответа, фаза остаётся `doing` с пустыми pid и без дописи journal. **Всегда передавать `--slug` и `--phase`** — без них вызов падает мгновенной пустой единицей (rc=1, лог пуст), g6/запись роли минуются. После rc=0 проверить `phases[PHASE]['role']` в `_state.json` (invoke-role мог вернуть 0, но роль `None` → complete падает по G6) и при необходимости проставить роль через `write_state`.

**Питфолл — CLI-сигнатура `invoke-role`: обязательны `--role`, `--prompt-file`, `--workspace` (НЕ `--prompt`/`--out`); `--workspace` = каталог слага.** `python3 -m pipeline.cli invoke-role` без `--workspace` мгновенно падает usage-ошибкой `error: the following arguments are required: --workspace`, а флаги `--prompt`/`--out` в CLI вообще не существуют (`--prompt-file` — человекочитаемый, `--out` отсутствует). Это сигнатурная ошибка вызова, а не сбой роли: роль не запускается, фаза не продвигается, journal не дописывается. Правильная полная форма (Codex-бэкенд): `invoke-role --role <architect|reviewer|executor> --prompt-file <packet.md> --workspace /путь/к/dev/<slug> --backend codex --model <gpt-модель-роли> --slug <slug> --phase <PHASE>`. `--workspace` — это каталог слага (существующий), куда роль кладёт артефакты; не путать с by-значением проверяемым `--slug`. При usage-ошибке сверь сигнатуру `invoke-role --help`, не пытайся «починить» промпт/фазу.

**RESEARCH-поезда (RS:collect/RS:analyze) — роль не назначается рецептом, «role None» тут штатно, лечится через оба level + сброс fail_class.** В RESEARCH-поезде `pipeline init --case RESEARCH` не прописывает `role` фазам ни в рецепте, ни в `phases[...]` — это НЕ дефект роли. После успешного invoke (rc=0, вердикт на диске /tmp) `complete-phase`/`check` падают `g6: phase <PHASE> role None != architect`, а в `phases[<PHASE>]` остаётся `fail_class: "provider_fatal"` (ложный срабатывание по лексике в статус-строке вердикта). Recovery через `write_state` (не перезапуск роли): проставить `role='architect'` в `phases[<PHASE>]` И на верхнем уровне `_state.json['role']='architect'` (g6 читает оба), сбросить `fail_class=None`, `status='done'`+`ended_at`, затем `check` → `complete-phase --evidence path=<вердикт>` → `next`. GATE:done RESEARCH-поезда закрывать обычным `complete-phase --evidence path=...` (флаг `--auto-pass` не существует — `unrecognized arguments`, закрывать сигнатурой complete-phase с evidence), отчёт уже в origin (сверка показана Саше), preflight необязателен для RESEARCH.

**RESEARCH по канону «с ревизором» (flag_rev) — перед GATE:done запустить ревизора (gpt-6-astra) на вердикт RS:analyze через фазу `REV:report`; recipe её не содержит — это ручной шаг вне рецепта.** Саша: «по канону с ревизором брать задачу на исследование и доработку». Рецепт RESEARCH фиксирован `RS:collect → RS:analyze → GATE:done` (pipeline_recipe), `flag_rev` НЕ добавляет REV-фазу (в отличие от BUGFIX), поэтому ревизия анализа — отдельное действие оркестратора. Ход: (1) `RS:collect` → роль пишет `RS-collect.md` (дефис, CANONICAL_ARTIFACT[RS:collect]), `complete-phase --evidence path=RS-collect.md` → `next` → WORK/`RS:analyze`; (2) `RS:analyze` → роль пишет `RS-analyze.md`, `complete-phase --evidence path=RS-analyze.md` → `next` → AUTO_GATE/`GATE:done`; (3) ПЕРЕД закрытием GATE:done запустить ревизора: `invoke-role --role reviewer --phase REV:report --model gpt-6-astra --prompt-file <rev_prompt>` c вердиктом приёмки по критериям Саши (нет дублирующих скиллов, один владелец на каждый триггер, нет коллизий вызовов, infra-риски cron/manifest/usage покрыты, ничего сверх канона/master), при REQUEST-CHANGES — вернуть на RS:analyze. `REV:report` в рецепте нет, поэтому её завершение — ручной APPROVE, не штатная фаза; после APPROVE закрывать GATE:done. Ревизор не пишет анализ — он валидирует вердикт архитектора по канону перед гейтом Саши.

**Цикл исследования/доработки «architect RS:analyze → REV:report → … → APPROVE» гонять по кругу, пока ревизор не APPROVE; блокеры ревизора передаются архитектору ДОПИСАННЫМ в тот же промпт-файл списком «устрани N пунктов», а не новым промптом с нуля.** Для решения «cursor-скиллы → codex, чтобы не было дублей и путаницы вызовов, по канону с ревизором» loop работает так: (1) архитектор RS:analyze → ревизор REV:report → `REQUEST-CHANGES` (список блокеров); (2) в конец ТОГО ЖЕ промпт-файла RS:analyze дописать заголовок `# Повторная доработка по ревизии` + пункты к устранению, повторно `invoke-role --role architect --phase RS:analyze`; (3) в конец промпт-файла ревизора дописать `# Повторная/третья ревизия` + что перепроверить, повторно `invoke-role --role reviewer --phase REV:report`; (4) повторять до `Вердикт: APPROVE`, затем GATE:done. Ревизор на каждом раунде ПЕРЕЗАПИСЫВАЕТ `REV-report.md` — блокеры раунда N передавать через текст промпта, не через архив (в отличие от `REV-tz.md`, где архив итерации обязателен).

**Нормы, которые ревизор (gpt-6-astra) жёстко требует в RESEARCH-вердикте — соблюдать изначально, иначе 2+ раунда REQUEST-CHANGES:** (а) single-owner на каждый trigger = **ровно один** активный владелец, а не «не более одного» (ноль допустим только для явно legacy-исторических фраз); (б) проверка владельца по predicates/description, не только буквальным `rg`-совпадением строк; (в) НЕ вводить жёсткие календарные сроки (напр. «до 2026-12-31») сверх master — срок убрать из нормативного вердикта, либо пометить как отдельное предложение, требующее operator/Sasha approval и собственного пакета; (г) каждая trigger/description-правка и каждая группа переписываемых внешних ссылок — с явным SKILL-CHANGE/ORCH-пакетом (owner + SK:preflight + GATE:done + ORCH) или REQUEST-CHANGES «привязано без владельца/гейта»; (д) boundary-пакет и будущий DECOMM разводить: GATE:done ограничения триггера не архивирует активную процедуру сам; (е) Cursor transport-питфоллы (`--resume`, envelope, усечение, digest) — владельцу `cursor-cli`, а pipeline recovery/empty-result/фазовые гейты — `dev-workflow` (Б43); (ж) перенос Cursor-моделей в `codex` как живых backend-ролей запрещён — только историческая миграционная справка/fallback. Эти пункты закладывать в постановку архитектору сразу, чтобы не гонять лишние раунды.

**Тот же recover — на КАЖДОЙ фазе BUGFIX-поезда, чей предмет сам является фатал-паттерном.** Если поезд чинит классификатор provider_fatal (цитата «Request timed out» в выводе роли и т.п.), архитектор обязан ПРОЦИТИРОВАТЬ паттерн в вердикте/TZ-patch/плане — значит каждая фаза, вывод которой несёт текст паттерна, может лечь `fail_class=provider_fatal` с `role=None` (21.10: BUG:diagnose и TZ:patch одного поезда оба легли, плюс сам RESEARCH-поезд). Это НЕ повторный запуск роли и НЕ «провайдер упал»: артефакт фазы уже на диске (вердикт/план записан). Recovery-слайс тот же: `phases[X]['role']=<роль по кейсу>`, `fail_class=None`, `status='done'`, `ended_at`, верхний `phase=None`/`status='in_phase'`, `pop('state_sha256')` → `next`. Проверяй `fail_class` в state ПОСЛЕ каждого invoke-role на таком слаге, ДО complete.
**Корень починен (21.10, DevWorkflow v0.6.2 Б48 AC-119/120, LIGHT `ktalk-tmo-fatal-classifier`):** `_fatal_reason` — трёхзначный control-flow: валидный JSON c `is_error=false`/без error-поля → `None` (не fatal) при ЛЮБОМ тексте в `result` (цитаты плана/ТЗ/кода не сбой провайдера); JSON `is_error=true` → fatal; не-JSON → fallback на строгие FATAL_PATTERNS по реальному сообщению процесса. После этого ложный «provider-fatal по цитате» больше НЕ должен бить; если он всё же появляется — сверить `detail` (инвариант №12: лексика vs реальный сбой).

**Сбой «Failed to reach the Cursor API» — провайдер, не задача.** Если курсор-роль вернула 1 с пустой ошибкой, смоук-проверь бэкенд минимальным `agent -p "ок" -f --model <модель> --workspace <ABS> --output-format json`: сеть до `api2.cursor.sh` может давать 200, токен в `~/.config/cursor/auth.json` на месте — если смоук возвращает `is_error:false`/результат, провайдер восстановился, фазу НЕ прерывать (не interrupt), просто перезапустить invoke-role. Решение: открой упавший тест и посмотри, какие пути/файлы он трогает; если НИ ОДНОГО из `changed_files` пакета — это предсуществующий красный вне скопа: зафиксируй «pre-existing, вне Б/п-пакета» в journal/AC-отчёт и ИДИ дальше (HF:test → docs → GATE:done), НЕ раскручивай rework-петлю на HF:impl и НЕ блокируй гейт этим красным. Только красный на тестах изменённых файлов, или на тестах, исполняющих изменённый код, — это регрессия пакета, требующая rework. Предсуществующий красный сам по себе — отдельный дефект (отдельный BUG:diagnose), а не повод держать текущий поезд.

**Питфолл — тесты USERTOOLS-инструмента, импортирующего кросс-инструментальные deps (`anywhere_contacts`, `protocolfromsummary`), гонять через `~/USERTOOLS/ProtocolFromSummary/.venv`, а НЕ системный python.** Исполнитель HF:impl/HF:test ставит `python3 -m pytest tests/test_config_env.py` → `ModuleNotFoundError: No module named 'anywhere_contacts'`, 5 errors за 0.2с — это НЕ сбой импл и НЕ регрессия: эти пакеты физически живут только в PFS .venv. Имплементация и тест — РАЗНЫЕ вызовы роли даже в rework-цикле (не склейка). Preflight/HF:test остаётся жёстким: до зелёного не двигаться к docs-handoff/GATE:done.

Не доверяй executor-самопроверке «walk 0>60» как закрытию AC-002 — длина и триггер две разные меры.

**Питфолл — occupancy-gate «wrapper alive» на собственном вызове (self-block, DevWorkflow AC-078): кодекс-роль может убить СВОЙ собственный wrapper → повторный invoke НЕ лечит, read-only фазу веди верификацией оркестратором.** Когда фоновый invoke-role вернул rc=130/143, канона нет и в journal нет `complete` — сверь хвост roll-out-лога сессии (`~/.codex/sessions/…/<rollout>.jsonl`, последние `custom_tool_call`/`turn_aborted`): если роль САМА выполнила `kill -TERM <свой pid>` (увидела себя на слаге как «живой wrapper» — тот же self-block только со стороны роли), повторный `invoke-role` той же ролью ВОСПРОИЗВЕДЁТ самокиль (на одном поезде роль упала так дважды подряд). Правило: (1) подтвердить по rollout; (2) если фаза READ-ONLY по плану (HF:test — без mutation, все IAC = контрольные команды) — оркестратор выполняет IAC.verify сам, пишет канонический артефакт фазы (`g3-test-tree-proof.json`) и `complete-phase` (role от сбойного invoke уже в state → G6 проходит; это «доделываю сама» для empty-result, НЕ обход G6); (3) для фазы с mutation (HF:impl) — rework-перемотка через write_state и повтор роли, а не оркестраторный complete.

**Coordinator-step с конфигом (AC-PW-08-тип): backup без трех smoke-логов = недоказанная фаза; «все в backup» — штат, обратное — recovery. Хэш `sha256sum ${cfg} > backup/config.sha256` снятый ДО mutation, после неё `sha256sum -c` честно FAIL — это НЕ порча.** Перед complete HF:backup проверь, что все требуемые планом before/after/negative smoke-логи лежат в backup_dir (HF:test потом только читает; baseline/mutation/sed в HF:test запрещены). Верификация снапшота: хэш-колонка == `sha256sum backup/config.yaml`, `diff backup/config.yaml live` == ровно одна мутированная строка, mode совпадает. **`status --check` «leftover occupancy: phase=X pid=None» на sirene-фазе, стоящей `doing` без роли — незакрытая фаза, не живой wrapper:** выполни работу фазы и `complete-phase` → leftover уходит, `status --check` снова rc=0; не искать wrapper и не re-invoke. `invoke-role`/`next` может вернуть exit 1 «wrapper alive» сразу, хотя `ps`/`pgrep --slug` по слагу пуст. Причина — harness запускает команду через **родительскую bash-обёртку** (`bash -lic '…python3 -m pipeline.cli invoke-role … --slug <slug>…'`), и `pgrep -af invoke-role` матчит и python-процесс, и его bash-родителя, несущего тот же `--slug` в argv; `exclude_pid=os.getpid()` исключает только python-потомка, родитель остаётся → ложный «живой wrapper». Это НЕ чужой invoke и НЕ интеррапт: не перематывай/не прерывай фазу по этому сигналу. Различение: если pgrep по точному `--slug` слага пуст (несколько совпадений нет) — это самоблок собственной обёртки, а не живой поезд. Обход для вызова: передай slug через shell-переменную `S=<slug>; … --slug "$S"`, чтобы в argv обёртки не было литерального токена `--slug <имя>` (pgrep-регекс его не заматчит). Если фаза уже упала по этому самоблоку — верни её исполнителю через `write_state` (та же перемотка, что после REQUEST-CHANGES) и доработай occupancy-детектор так, чтобы `exclude_pid` покрывал self **и цепочку предков** (`os.getppid()` вверх), или pgrep строго по python-маркеру CLI; AC-061 (pid = wrapper `os.getpid()`) при этом не менять.

**Транзиентный «wrapper alive» сразу после notify о завершении фонового invoke-role: подождать и повторить, не перематывать.** После того, как фоновый терминал (proc_*, notify=true) отрапортовал об успешном завершении invoke-role, `complete-phase`/`next` в первые секунды может всё ещё вернуть «wrapper alive», хотя `pgrep -af` по slug уже пуст (wrap-процесс умер, но bash-обёртка/зомби пережила на мгновение; или pgrep поймал хвост предка). Это НЕ чужой invoke и НЕ повод для write_state-перемотки: повторить тот же `complete-phase` через короткую паузу (или после явной проверки `invoke_wrapper_alive(slug)==False` из python) — проходит RC=0. Аналогично прогоняй `next` заново, он пересчитает из state.

**`TZ:finalize` — роль architect (G6), НЕ sirene-фаза: даже если оркестратор уже сделал запись мастера+инвентарь, закрывать только через invoke-role architect или write_state с role=architect.** `PHASE_ROLE` даёт TZ:patch=TZ:finalize=HF:plan=BUF:diagnose=architect; попытка `complete-phase` сразу (role=None) падает `g6: phase TZ:finalize role None != architect`. При этом сам текст финализации (штамп мастера + строка `MAIN_TZ_INVENTORY.md`) оркестратор может подготовить заранее — архитектор на TZ:finalize ревизует/подтверждает и закрывает; evidence — оба пути (мастер + инвентарь). Не назначай на неё Cursor-роль из прошлой фазы — «g6: ... has cursor role» — сброс role=None через write_state перед повторным invoke. **Если invoke-role архитектора на TZ:finalize убит таймаутом (RC=143) и артефактов роли нет, а весь текст финализации (секция мастера + строка инвентаря) уже положен оркестратором — recover+re-invoke НЕ нужен: проставь `phases['TZ:finalize']['role']='architect'` через write_state и `complete-phase` с evidence «мастер mtime/версия + инвентарь mtime». Это тот же вариант «нормы уже на диске, повтор роли не нужен», что у canonical exit 4 на TZ:patch; роль на TZ:finalize не пишет нового текста, она подтверждает существующий.

**Прямая правка `_state.json` (state-fix: поставить role/model в фазе) рвёт `state_sha256`: после менее complete-phase/`next` дают `CRISIS: state_sha256 mismatch`, и пересчитать хэш можно ТОЛЬКО под venv-питоном, не в песочнице.**
Иногда роль/модель в `phases[PHASE]` правится сырым `json.dump` (напр. TZ:finalize `role='architect'`, `model='gpt-6.1-sol'` до complete). Любое изменение содержимого `_state.json` инвалидирует записанный `state_sha256`, поэтому следующий вызов CLI (complete-phase ИЛИ next) падает `CRISIS: state_sha256 mismatch` — это не баг, это признак того, что raw-правку делали без пересчёта. **Не пытайся пересчитать в `execute_code`/песочнице**: `state_path()` → `paths.dev_state_root()` → `usertools_config → import yaml`, а в песочнице yaml нет → `ModuleNotFoundError: No module named 'yaml'`, даже сама попытка recompute падает. Правильный порядок: (1) сделать JSON-правку фаз; (2) через **venv-питон** (`/home/tkachenkoav/hermes-agent/.venv/bin/python3` c `PIPELINE_ROOT`/`PYTHONPATH`), скрипт: `import pipeline.pipeline_state as ps; raw=json.load(open(ps.state_path('<slug>'))); raw.pop('state_sha256',None); st=ps.PipelineState.from_dict(raw); raw['state_sha256']=st.to_dict()['state_sha256']; json.dump(raw,...)` — `from_dict` с пустым stored sha возвращается в режим пересчёта (без CRISIS), `to_dict()` даёт валидный хэш; (3) затем complete-phase/next проходят RC=0. Это тот же дух, что `d.pop('state_sha256')` у set-case: чем бы ты ни трогал state вручную, всегда пересчитывай хэш штатным способом из-под venv.

## Питфолл — REV-вердикт-парсер: «REV verdict unknown or conflict» когда в блоке `## Вердикт` у `verdict=APPROVE` фигурирует слово `REQUEST-CHANGES`

Раунд rework 2 (ревизор APPROVE) дал `complete-phase` rc=1 «REV verdict unknown or conflict». Причина — не реальный REQUEST-CHANGES и не перемотка, а механика `rev_verdict()` в `pipeline_gates.py`:

- `_verdict_from_block` — берёт текст под `## Вердикт` до следующего `##` и первым делом ищет `REQUEST CHANGES` (возвращает REQUEST-CHANGES раньше, чем APPROVE);
- `_verdict_evidence_field` — читает `verdict=APPROVE` (в секции `## Evidence` или по всему тексту);
- v1 ≠ v2 → `rev_verdict` возвращает `CONFLICT` → `can_complete` блокирует complete.

Ревизор раунда 2 закономерно пишет в прозе блока «закрыл оба замечания REQUEST-CHANGES» — это и триггерит ложный конфликт. Правило:
1. **Не перематывай/не rework** по этому сигналу — вердикт фактически APPROVE, state корректный.
2. Перефразируй прозу блока `## Вердикт`, убрав буквальное слово `REQUEST-CHANGES` (напр. «закрыл оба замечания раунда 1»). Вердикт и смысл не меняются — это текст-фикс для парсера, не редактирование вердикта ревизора.
3. Повтори `complete-phase` — проходит rc=0, `next` даёт следующий гейт (AUTO_GATE).

Проверка-предотвращение перед закрытием любой REV-фазы после rework-цикла: `python -c "from pipeline.pipeline_gates import rev_verdict; print(rev_verdict(slug, phase))"` — ожидаемо APPROVE; CONFLICT → чини текст блока, не state.

## Питфолл — HF:test runtime-гейт «реальный вызов той же командой» для входов без safe/dry-run режима — блокер `FAIL runtime call unsafe`, НЕ фейк-PASS и НЕ замена импортом

План HF:test требует для каждого live-входа один реальный вызов той же командой/обёрткой, что в registry, и явно запрещает подменять его импортом или фиктивным PASS («если безопасный режим не существует, зафиксировать FAIL/блокер runtime call unsafe и не закрывать IAC»). У части инструментов документированного dry-run нет, и реальный вызов = side-effect: записи в Jira/ErrorBus, создание встреч (meeting_scheduler), синк календаря (sync_aralov), PII-скан живых деревьев (piiscan), пересборка индексов (mofs_index), state-mutating pipeline CLI (dev_kanban_pipeline), live GAL lookup (exchange_org_lookup). Исполнитель в этой ситуации ОБЯЗАН зафиксировать `FAIL runtime call unsafe` для таких входов и НЕ закрывать их IAC — это зелёное поведение по плану, а не дефект фазы и не «исполнитель не доделал».

**Правило для оркестратора на таком блокере (25.10, eco-config-w3):**
1. НЕ abort/reinit и НЕ форсить `complete-phase` HF:test (can_complete по блокеру не закрывает, и это правильно — runtime-гейт не пройден).
2. Перемотать в производящую фазу `HF:plan` тем же механизмом, что REV REQUEST-CHANGES: `interrupt --reason 'HF:test блокер: … runtime call unsafe …'` (обязателен `--reason`), прямая правка `_state.json` (у `HF:plan`/`REV:plan`/`HF:test` `status='todo'`+`pid=None`, верх `status='idle'`, `phase='HF:plan'`), пересчёт `state_sha256` через venv-питон `PipelineState.from_dict`→`to_dict`, затем `next` → `{"action":"WORK","phase":"HF:plan"}`.

## Питфолл — класс ошибки «откатился» после закрытого графа: сверь `detail`, не переоткрывай вслепую

Когда EventBus-класс ошибки (напр. `invoke_role fatal role=executor backend=cursor-cli`) продолжаeт
падать ПОСЛЕ того, как его багфикс-граф закрылся GATE:done — сначала реши, тот ли это подкласс.
Закрытый граф мог чинить **ложные** срабатывания (по лексике/паттерну), а свежие события с тем же
`message` быть **реальными** провалами с другим механизмом. Различие лежит не в `message`, а в
`detail` (payload): смотреть `SELECT id,count,first_seen,last_seen,message,detail FROM errors
WHERE message LIKE '%<sig>%' ORDER BY id DESC`. Пример: закрытый `dev-workflow-cursor-cli` убрал
ложные FATAL-паттерны, а новые события — `Iteration budget exhausted` (штатный лимит воркера),
`HTTP 503` (транспорт), `rc=3 is_error` — это **другой подкласс** (реальный provider-fatal), а
не регрессия закрытого фикса.

**Правило:** перед «переоткрыть старый граф» / «фикс не сработал» — прочитай `detail` свежих
событий; если детерминированный механизм другой (лимит vs лексика vs транспорт) — это **новые
корень `DEV/<slug>` + `BUG:diagnose`, НЕ ре-опен старого** (тот же дух, что «новый симптом =
новый баг» в инварианте №12). И проверь slug-guard: закрытый граф с тем же slug уже done, новый
именуй иначе (напр. `cursor-provider-fatal` vs `dev-workflow-cursor-cli`), иначе диспетчер
смешает два класса в одном графе.

## Инвариант №14 — полный BUGFIX в file-state DevWorkflow: роль гейта наследуется от источника улики; HF:backup — sirene-фаза

На чисто файловом DevWorkflow (не канбан) **полный BUGFIX** (в отличие от BUGFIX-LIGHT) проходит более длинную цепь: `BUG:diagnose → GATE:diagnose-review → TZ:patch → REV:tz → GATE:take-into-work → HF:plan → REV:plan → GATE:plan-approve → HF:backup → HF:impl → HP:test → HF:docs-handoff → GATE:done`. LIGHT после диагноза идёт короче (`BUG:diagnose → GATE:diagnose-review → TZ:patch → TZ:finalize → GATE:take-into-work → HF:impl → …`) — **не минуй REV:tz/HF:plan/REV:plan/HF:backup на полном**, весь хвост это собственный объём пакета (больше 3 файлов+крон).

**Роль гейта при state-fix — от фазы, чью улику он пропускает, не дефолт в architect.** Когда `complete-phase` на `AUTO_GATE` падает `g6: role None` (auto-pass не дописался), проставь `phases[GATE]['role']` под источник: `GATE:diagnose-review`/`GATE:take-into-work` (после BUG:diagnose/TZ:finalize) = `architect`; `GATE:plan-approve` (после REV:plan) = **`reviewer`**; `GATE:done` = оркестратор (без cursor-роли). Ошибка «всегда architect» даёт повторный AUTO_GATE-цикл на plan-approve. Тот же слайс что при recover: статус `done`, `ended_at`, `fail_class=None`, верх `phase=None`/`status='in_phase'`, `pop('state_sha256')` → `next`.

**HF:backup — sirene-фаза (оркестратор, НЕ cursor-роль):** `emit-prompt` на ней g6-forbidden (`emit forbidden for sirene phase HF:backup`). Работа — руками: скопировать целевые файлы плана в `dev/<slug>/_backup_pre_HF/` (для не-git реестров это единственный откат), затем `complete-phase` с evidence-файлом (не глагол, канон `CANONICAL_ARTIFACT` для backup — любой, `path=` в evidence обязателен).

**Питфолл — `preflight --mode done` на полном BUGFIX закономерно FAIL «phase GATE:done not done»: GATE закрывать через `complete-phase` НАПРЯМУЮ, не через префлайт.** У полного BUGFIX (в отличие от LIGHT) `GATE:done` входит в обязательный набор `mandatory_phases_for_case` (PLAN_IMPL_TAIL с хвостом `…→ GATE:done`). Поэтому когда `next` возвращает `AUTO_GATE GATE:done` и мы ставим фазу `in_phase` (state-fix) — `pipeline_preflight.run_preflight` по `mandatory_phases_ok` видит `GATE:done != done` и FAIL «phase GATE:done not done» независимо от остального зелёного. Это НЕ преграда: внутренний `check_gate` для `GATE:done` (pipeline_gates.py) **явно исключает GATE:done из mandatory** (`[p for p in state.recipe if p != "GATE:done"]`), т.е. он достаточно green, чтобы complete-фазу принял. Порядок для полного BUGFIX: (1) auto-pass гейта при `role=None` → state-fix `phases['GATE:done']['role']=None`, `status='done'`, `ended_at`, `fail_class=None`, верх `phase=None`/`status='in_phase'`, `pop('state_sha256')`; (2) **НЕ гонять `preflight --mode done` как доказательство** — он всегда красный по самому гейту; (3) `complete-phase --evidence path=…` — при полном контенте (Отчёт AC с числовым `AC-###` + `AC-delivered: origin` в journal.md). Здесь префлайт-не-доказательство не ошибка, в отличие от LIGHT, где префлайт проходит ДО закрытия гейта и обязан быть 0. Если хочется зелёного префлайта — закрывай GATE:done complete-ом, тогда префлайт видит его done (для постфактум-верификации), а не как гейт в прогоне.

**LIGHT → полный через set-case:** после диагноза архитектор сам решает, снять ли LIGHT (`set-case BUGFIX`). На почти пустом графе (фазы ещё не заполнены) set-case применяется чисто; на уже засаженном графе после fill-фаз — только через `write_state` (`case`/`recipe`/новые `_empty_phase()`), set-case упадёт CRISIS: state_sha256.

**Питфолл — `interrupt` возвращает rc=2 пустым выводом, если не передать `--reason`.** `cmd_interrupt` первым делом `_require(ns, 'reason')` — голый `pipeline interrupt --slug <s>` молча выходит 2 без stderr, выглядит как «не отработал». Успешная форма всегда `--reason '…'`. То же для `abort` (обе требуют `--reason`).

**Питфолл — терминальная ошибка валидации `notify only applies to background commands` / `persist_on_release only applies to background commands` — контрактная, НЕ retryable: меняй форму вызова, не повторяй тождественный вызов.** Она значит, что флаги `notify`/`persist_on_release` переданы, а `background=true` нет (или наоборот), и команда не стартовала вовсе — pipeline не получил ни `invoke_prepare`, ни rc, ни артефакт. Это ошибка вызывающего оркестратора, а не provider-fatal и не транзиент. Лечение — **изменить аргументы** (`background=true` добавить/убрать), НЕ retry как есть: повтор одного и того же вызова несколько раз подряд даёт жёсткий стоп `identical_call_streak_halt` (внешний guard видит бит-в-бит одинаковый вызов с одинаковым результатом и останавливает ход; `phase_turns` его не ловит, т.к. до `invoke-role` не доходит). После первого validation error — сразу меняй форму вызова.

**Питфолл — SIGTERM/143 убитого фонового invoke — решай по `role` в `_state.json` и наличию артефакта, НЕ по тому, что wrapper вернул 143:**
- `role is None` + артефакт отсутствует (`ls` канонного имени пуст) + wrapper мёртв + `awaiting_invoke=false` → `recover --class dead-pid` (см. процедуру ниже): `doing→todo`, затем `next`→WORK и повторный `invoke-role`.
- `role` уже заполнен (≠ None) + артефакт на диске (mtime ≥ started_at) + часто `context_used=true` → роль ФАКТИЧЕСКИ завершила работу до сигнала (SIGTERM пришёл уже после записи канона и self-state роли через `repair`), wrapper не успел вернуть rc. `next` в этом случае вернёт `WORK` (а не RECOVER) — потому что `classify_doing` проверяет `ph.get("role")` ДО dead-pid/recover. Лечение — обычный `complete-phase --evidence path=<канонный артефакт>` с reason «SIGTERM после записи артефакта; роль завершена (post-invoke окно)». НЕ `recover`, НЕ повторный invoke (дублирует работу роли). Это и есть ошибка №7 класса BUGFIX «SIGTERM after artifact».
   - `pipeline recover` arg — **`--class`** (не `--phase`); валидные классы `RECOVER_CLASSES = {dead-pid, wrong-role, empty-result, rc0-no-complete, model-none}`; `--evidence` обязателен с `path=`/`sha256=`/`session_id=`. Порядок dead-pid: (1) факты — канонный артефакт отсутствует (`ls`), `pgrep -af "invoke-role.*<slug>"` пуст, `role is None`, `awaiting_invoke=False` (иначе это живой wrapper/post-invoke окно — `recover` запрещён, verify-dead живой); (2) `pipeline recover --slug <slug> --class dead-pid --reason '…' --evidence 'path=…'` → `doing→todo`; (3) `next` → снова `WORK` на той же фазе; (4) `emit-prompt` + `invoke-role` (фон) с `--slug` **и** `--phase`; (5) Саше кратко: сбой + что сделано, без ожидания его решения (правило «поезд встал → доделывай сама»). Событие остаётся `recover`/`canonical_artifact_fail` с active phase — новые event-имена не вводить.
Отдельно — если роля всё же УСПЕЛА частично отработать на диске (архив, перенос разделов, удаление source) до SIGTERM: в повторной постановке явно укажи «часть уже сделана — доделай остаток, не переделывай/не откатывай», иначе роль заново выполнит уже сделанное (напр. повторно удалит перенесённые файлы) или не поймёт, что source уже отсутствует. Если же канонный артефакт записан ПОЛНОСТЬЮ (mtime ≥ старта) — это не dead-pid, а уже завершённая роль (см. следующий питфолл про «мёртвый pid = след лишнего повтора»).

**Питфолл — `write_state` event-имя обязано быть из замкнутого набора `CLOSED_EVENTS`; паузу снимают существующим событием, а не новым `resume`/`continue`/`unpause`.**
Вернул поезд в работу после операторской паузы и назвал событие `resume` → `write_state` прокинул состояние, но журнал упал «Incomplete log event: unknown event 'resume'» и **мутация не записалась** — поезд остался `interrupted`, хотя ты думал, что снял паузу (диагностировалось повторным `read_state`). Новые имена событий не вводить: полный список в `pipeline_log.py:CLOSED_EVENTS` (`repair`, `operator_done`, `set_case`, `complete`, `interrupt`, `hold`, `recover`, ...). Для операторского возврата фазы в работу используй существующее `repair` (или `complete`/`operator_done` по смыслу), а не выдуманное слово — состояние меняется проброшенными полями (`status='idle'`, `phase=None`, фаза `doing`), а не именем события.

**Питфолл — `emit-prompt` на HF-фазе падает `G1 fail: validated extract metadata required`, когда у state пусты `extract_key`/`extract_sha256`/`extract_of_tz_version`/`extract_chars` или sha файла не совпал.** Пакет не создаётся (нет файла промпта, rc≠0) до заполнения. Проставь через `write_state`: `extract_sha256=sha256(<extract.md>)`, `extract_chars=len`, `extract_key=sha[:12]`, `extract_of_tz_version=<tz_version>`, `tz_version` — затем повторный `emit-prompt`. Это G1-гейт собранности пакета, не G2-маркер context-used, и не признак того, что роль не отработала.

**Питфолл — возобновление операторски-прерванной фазы (`interrupt` по решению Саши, не сбой роли): вернуть SAME фазу в работу через `write_state`, НЕ REQUEST-CHANGES-перемотку в прошлую фазу.** Поезд `interrupted` + фаза `doing` с мёртвым `pid`, `next` снова даёт `INTERRUPTED`. Когда Саша распорядился продолжить («довести до конца в автомате») и фаза уже частично прошла (артефакты/`session_id` на диске) — `write_state`: `status='idle'`, `phase=None`, `pid=None`, та же фаза остаётся `doing` (прогресс сохраняется), событие `repair`/`complete`. Затем `next` → `WORK`/<та же фаза> → `emit-prompt` → повторный `invoke-role` тем же `--resume <session_id>`. Паузу снимает только распоряжение Саши продолжить, а не авто-`next`. **Помни: `--resume` у Codex-бэкенда не поддерживается (`run_codex` не принимает resume) — возобновление Codex-роли = новый `invoke-role` с той же постановкой + дописанной инструкцией «часть уже сделана, начни с ключа N, сделанное не переделывай».**

**Питфолл — `--slug` без `--phase` в `invoke-role` = мгновенный `rc=2` `invoke-role requires --slug and --phase`, роль не спавнится вовсе.** Пара всё-или-ничего на уровне argv: `_require_slug_phase` реджектит, когда передан ровно один из пары (в help оба в скобках, но код требует оба вместе). Это контракт-ошибка ВЫЗЫВАЮЩЕГО, не provider-fatal, не empty-result, не dead-pid — `_state.json` не тронут (фаза остаётся `doing` с `pid=None` от `invoke_prepare`, где pid мог просто не записаться), журнал без `invoke_role`. Лечение: просто дополни `--phase` и повтори тот же `invoke-role` — никакого recover/rewind не нужно. Не путать с живым wrapper (pgrep показывает процесс: тот случай — occupancy, не дополняй фазу).

**Сводка триажа по exit-коду фонового `invoke-role` (решать по коду + диску, не по догадке):** exit 2 без stderr/«requires --slug and --phase» → контракт-ошибка аргументов, state не тронут, просто переиздай с обоими флагами; exit 143/SIGTERM → транспортный срыв, решай по `role`-полю и канон-артефакту на диске (см. питфолл ниже); exit 0 → **два разных исхода, различай по диску и журналу**: (а) канонный артефакт есть (mtime ≥ started_at) → `complete-phase` — rc=0 сам по себе фазу не закрывает; (б) канона НЕТ **и** в journal нет `complete` этой фазы → роль сама остановилась внутри кодекс-сессии (обычно rc=130, occupancy-самоблок «вижу живой wrapper» — роль честно пишет в последнем сообщении «фаза не завершена, артефакт отсутствует, state не трогал»), whilst wrapper вернул 0. Лечение (б) — НЕ recover/interrupt/rewind и НЕ complete: `next` вернёт WORK (classify_doing видит заполненную `role` и отсутствие канона → WORK, не RECOVER), затем повторный `invoke-role` той же ролью с тем же промпт-файлом; до этого подтвердить по хвосту rollout-лога сессии (`~/.codex/sessions/…/<rollout>.jsonl`, последний `task_complete`) причину остановки роли — она там объясняет, что не трогала state и что блокировало. До вызова `recover` или повторного invoke всегда смотри `journal.md`: там уже может стоять `complete`+`invoke_role` той же фазы (мёртвый pid = след лишнего повтора, не сбой — см. питфолл о мёртвом pid ниже).

**Питфолл — кодекс-роль убивает СВОЙ собственный wrapper (self-kill): сверь хвост rollout, НЕ повторять invoke; read-only фазы вести верификацией оркестратором.** Когда фоновый invoke-role вернул rc=130/143, канона нет и в journal нет `complete` — сверь хвост roll-out-лога сессии (`~/.codex/sessions/…/<rollout>.jsonl`, последние `custom_tool_call`/`turn_aborted`): если роль САМА выполнила `kill -TERM <свой pid>` (увидела себя на слаге как «живой wrapper» и убила собственный handle — тот же occupancy self-block AC-078, только со стороны роли; в последнем сообщении она честно пишет «фаза не завершена, артефакт отсутствует, state не трогал»), то повторный `invoke-role` той же ролью ВОСПРОИЗВЕДЁТ самокиль — на одном поезде роль упала так дважды подряд. Правило: (1) подтвердить по rollout; (2) если фаза READ-ONLY по плану (HF:test — без mutation, все IAC = контрольные команды: pytest, smoke через read-only фикстуру, `sha256sum`, `git diff --check`) — оркестратор выполняет IAC.verify сам, пишет канонический артефакт фазы (`g3-test-tree-proof.json`) и закрывает `complete-phase --evidence path=<артефакт>` (role от сбойного invoke уже записана в state → G6 проходит; это легальное «поезд встал → доделываю сама» для класса empty-result, НЕ обход G6); (3) для фазы с mutation (HF:impl) — rework-перемотка на роль через write_state и повтор, а не оркестраторный complete.

**Питфолл — кодекс-роль может вернуться rc=0, ПРОЖЕЧЬ полный бюджет токенов, но не тронуть работу: она уходит в оркестраторскую метапетлю «мониторинга самой себя», и программные гейты её не ловят.** После фонового invoke-role rc=0 с пустым evidence и неизменёнными реестрами НЕ объявляй «empty result» и НЕ re-invoke вслепую — диагностируй по rollout-логу сессии (`~/.codex/sessions/<date>/rollout-<id>.jsonl`): распарь все `custom_tool_call`-события типа `exec` и посмотри КОМАНДЫ. Кейс CHANGE, чей единственный результат — новая норма/текст в master-ТЗ (добавить критерий приёмки, который будет исполняться в будущих поездах приёмки инструментов), а не код/файлы/кроны/секреты. Значит и при пустой реализации executor-фазу надо прогнать через `invoke-role --role executor` (Codex) с постановкой «кода нет, зафиксируй no-code-change каноническим артефактом `HF-impl.md`/`HF-test.md`» — роль запишет вердикт и валидный канонный файл фазы; напрямую (без роли) оркестратор закрывает только sirene-фазы (`HF:backup`, `HF:docs-handoff`, `ORCH:shared-state`, гейты). Фазы одной роли идут отдельными вызовами (не склеивать `HF:impl`+`HF:test` в один промпт). Не заставляй архитектора сочинять вымышленную реализацию и не раздувай рамки: в постановку `HF:plan` прямо пиши «реализации кода/тестов/файлов/кронов/секретов в этом поезде нет; исполнение нормы — в будущих приёмках». Отдельно: если архитектор заложил в master открытую вердиктную развилку `Q-n` и Саша на неё ответил, перед закрытием поезда обнови секцию master с «Открытая развилка» на «решено Сашей: <вариант>» и запиши решение — не оставляй хвост «выбор оставлен Саше».

## Питфолл — HF:impl при «PLAN READY / PRECONDITION BLOCKED»: executor снапшотит предусловие, готовит patch, НО НЕ применяет, evidence `precondition=blocked`, production не трогается

**Класс пакета:** CHANGE-волны/единая чистка, где мастер-ТЗ ставит жёсткое предусловие на cutover (OverlayConfig §10.7): все active/draft/paused в `tools{}` = `unified_only`; сейчас на диске 30 `not_started` + 9 `dual_read` + 7 переходных `accepted` + 0 `unified_only` → предусловие не выполнено. Архитектор на HF:plan может корректно закрыть вердиктом `PLAN READY / PRECONDITION BLOCKED`: план полный (IAC-матрица + probe-строки), но применение patch запрещено до внешних миграционных гейтов (такие пакеты архитектор декомпозирует на 4a/4b/4-clean). План при этом открывается фразой вроде «этот план не является разрешением немедленно вырезать fallback».

**Правило для HF:impl (executor) на таком слаге — НЕ «сделать и применить»:**
1. Первый и ОБЯЗАТЕЛЬНЫЙ шаг — **снять снапшот предусловия** (`EcosystemManifest.json` → `config.tools`: счётчики по `migration_status`). Это machinely проверяемо: `not_started=0 && dual_read=0 && accepted=0 && unified_only=46` + актуальные `rollback_snapshot` + отсутствие разрешённых legacy/overlay-источников. Пока гейт красный (а он красный, пока внешние миграции не закрыты):
2. **Подготовить reviewable patch/diff** целевых файлов (для OverlayConfig-лоадера — `~/.hermes/lib/usertools_config.py` + `usertools_env.py`: удаление `USERTOOLS_CONFIG_MODE`/`_legacy_mode`/`config.overlay.yaml`/silent-fallback/`local_env_path`; сохранение allowed sources + fail-loud). Diff как отдельный артефакт поезда, НЕ применять к live-файлам;
3. Не менять `EcosystemManifest.json` статусы, `EcosystemConfig.yaml`/schema, `.env` из HF:impl — внешний writer статусов только `ORCH:shared-state`;
4. Записать evidence `precondition=blocked` с цифрами снапшота (30/9/7/0) и diff-stat;
5. Завершить фазу с блокером; production loader/manifest/YAML/.env не трогать. 47-я строка `dev_workflow` в `battle_interpreters.yaml` — отдельная probe-строка, не config.tool и не увеличивает their count.

**Оркестратор это кодирует в промпт HF:impl явно**, не полагаясь на догадку исполнителя: «сначала снапшот 4a/4b → если красный, prepare patch без apply, evidence precondition=blocked, НЕ трогать live». Бизнес-команды (Jira/ErrorBus/встречи/синк/PII-скан) не запускать, значения секретов не выводить — только имена ключей.

**Что НЕ делать:** применять patch вопреки красному предусловию; форсить `complete-phase` HF:test по реализации, которой нет; считать поезд застрявшим — фазы TZ (stabilize/compress/patch/finalize) и plan (HF:plan/REV:plan/backup) на условном пакете проходят штатно, пауза только на применение cutover. Плановые вердикты кодируют это и ревизор APPROVE-ом подтверждает условность; исполнитель при зелёном re-run после закрытия внешних гейтов применяет ранее подготовленный patch.

**Питфолл — «завершить precondition-blocked волну» = развилка с ДВУМЯ смыслами; оркестратор обязан спросить Сашу, а не выбрать сам. Разблок — миграционные партии, не довод поезда по рецепту.** После `HF:impl` с `precondition blocked` (patch готов, live не тронут) Саша говорит «завершаем по канону» — это НЕ одна операция: (а) довести поезд до GATE:done честно, зафиксировав `HF:test` как «cutover заблокирован, production=baseline»; либо (б) начать миграцию инструментов на единый конфиг партиями (A0 = 7 `accepted` → `unified_only`, потом по 10) — что и есть реальный разблок внешнего гейта, после которого cutover-патч становится применимым. Сформулировать оба смысла текстом в origin и ждать выбора; развилку судьбы карточки оркестратор не закрывает сам (rule 15.10: никаких собственных вердиктов по судьбе карточек).

**Rewind для миграционной партии (пере-скоуп HF:impl):** когда Саша выбрал «начать миграцию», исходный `HF:impl` (done, precondition-blocked) пере-скоупивается на партию — через `write_state`: `phases['HF:impl']['status']='doing'`, фазу, что шла следующей (`HF:test`), вернуть в `todo`, `status='in_phase'`, `phase='HF:impl'`, `pid=None` (+ event `event`+`actor`+`phase`). НЕ `set-case`, НЕ abort/reinit — это тот же поезд, та же фаза, narrower scope.

**Промпт executor'а миграционной партии фиксирует границы владения (иначе executor возьмёт на себя cutover):** scope = только N инструментов партии; по каждому — snapshot в `_Archives`, `explain` (нулевой overlay/legacy), `probe_battle_venv.py` на боевом python, `--check-drift` no-drift, ErrorBus-окно. Явно ЗАПРЕТИТЬ: трогать production loader (`usertools_config.py`/`usertools_env.py` — это 4-clean после всех партий), писать `manifest.config.tools.<key>.migration_status` (только `ORCH:shared-state`), удалять legacy `.env`/overlay (только по `operator:удаляй` на accepted+зелёном snapshot), печатать значения секретов, рестартовать Gateway/создавать кроны, подменять runtime-call импортом. Артефакт — в канонное имя фазы (`evidence/HF-impl.md` в каталоге слага); сводный вердикт: сколько из N готовы к `unified_only`, какие блокируются и почему.

**Питфолл — `migration_status=accepted` в манифесте НЕ доказывает, что инструмент реально переведён: статические explain/probe/drift зелёные, а реальный runtime-вызов падает.** Приёмка per-tool без одного живого вызова («accepted → unified_only» по голому probe) пропускает «недо-миграцию» — статус в манифесте опередил фактический перевод кода/секретов. Два канонических симптома, которые ловит только runtime: (1) `KeyError: Missing config key '<SECRET>' for tool '<name>'` — секрет по-прежнему лежит в старом per-tool `.env` (`~/USERTOOLS/<Tool>/.env`), а не перенесён в shared `~/.config/hermes/.env`; (2) «`<VAR> is empty`» — код читает `os.environ.get("<VAR>", "")` напрямую, а не через `usertools_config.load_tool_config`, хотя сам ключ в shared env ЕСТЬ. Правило: закрывать инструмент партии в `unified_only` только после **одного реального вызова боевого entry штатным venv (rc=0)**, а не по explain; статику рвёт только runtime — для инструментов без боевого крона это разовый прогон штатным `battle_python`/cron-скриптом с фиксацией rc/stdout, для прочих достаточно свежего ok-тика боевого крона (не копировать коротко-интервальные боевые кроны разовым прогоном — гонка слота и двойной side-effect).

## Питфолл — `explain` блокирует приёмку на `legacy=1` ЕЩЁ ДО runtime: секрет в per-tool `.env` резолвится `source=legacy`, а тот же секрет в shared `~/.config/hermes/.env` — `source=shared_env`
Гейт принятия `dual_read`-инструмента («нулевой legacy/overlay») падает на `HF:impl` **до всякого боевого вызова**: `usertools_config explain <tool>` печатает строку `<KEY> source=legacy`. Это не runtime-ошибка, а классификация источника. Механизм: `usertools_config._SECRET_KEY` (regex `.*(TOKEN|SECRET|PASSWORD|API_KEY).*`) помечает ключ секретным; секретный ключ, ещё лежащий в per-tool `~/USERTOOLS/<Tool>/.env`, резолвится как `legacy`, а добавленный в shared `~/.config/hermes/.env` — как `shared_env`. Несекретные ключи при этом НЕ блокируют (пути `WORKVAULT_PATH`/`TOOL_DIR`/`LOGS_PATH` из per-tool `.env` обычно уже есть в `EcosystemConfig.yaml tools.<key>` и резолвятся `ecosystem_config`/`shared`). Диагностика: `explain <tool> | grep -cE 'source=legacy|source=overlay'` и `grep <KEY>`, чтобы понять, какой ИМЕННО ключ блокирует; серия инструментов проходится по порядку, FAIL одного останавливает следующих (остatльные НЕ трогать).

## Питфолл — перенос секрета в shared env при приёмке инструмента: значение НЕ показывать, верифицировать только наличие + `source=shared_env`
Когда инструмент упирается в «секрет не в shared env» (лежит в legacy `~/USERTOOLS/<Tool>/.env`), нормальный порядок — оператор переносит. Но Саша может делегировать обратно («переноси сам»): тогда оркестратор двигает значение **redacted** — read значение из legacy `.env`, дописать `KEY=<значение>` в `~/.config/hermes/.env`, а наружу никогда не выводить значение (ни в чат, ни в stdout, ни в артефакт фазы). Верификация приёмки — не печать значения, а: (1) `python3 usertools_config.py explain <tool> | grep <KEY>` из `~/.hermes/lib` → строка `<KEY> source=shared_env` и ОТСУТСТВИЕ `source=legacy`/`source=overlay`; (2) если код чинит «читал `os.environ.get` мимо loader» — `explain` всё равно должен показать `source=shared_env` для секрета ПОСЛЕ перевода кода на `load_tool_config(keys=[…секрет…])`; (3) runtime smoke: боевой entry логирует `rc=0`. Проверять присутствие/непустоту ключа как булев факт (`get_key()` → `is not None and v != ''`), не печатать `v`. После переноса legacy-`.env` НЕ удалять — удаление отдельный императив Саши. **Если Саша сказал «удаляй» (или «N и удаляй»), то перенос секрета + `rm` per-tool `.env` происходят в ОДНОМ батче: перенеси секрет в shared → `rm ~/USERTOOLS/<Tool>/.env` → перезапусти `explain <tool>` (legacy=0) → перезапусти executor-фазу с инструкцией «продолжить с ключа N, уже сделанные 1..N-1 не переделывать».** Исполнитель миграционной партии идёт по порядку и честно останавливается на первом FAIL (это предусмотрено планом, не дефект); после устранения причины ресайзишь только оставшиеся ключи, а не всю партию. Прежде чем `rm` — убедись несекретные значения ключа уже в `EcosystemConfig.yaml`/`shared` (тогда пропадает только секретная строка `legacy`, а пути не остаются осиротевшими).

**Питфолл — invoke-role rc=0, но канонный артефакт фазы может лежать в НЕВЕРНОМ каталоге (соседний путь слага): «empty result» ≠ роль ничего не сделала.** Codex иногда пишет `HF-test.md` не в `~/WorkVault/Hermes-Backlog/dev/<slug>/`, а в `~/WorkVault/dev/<slug>/` (путь без `Hermes-Backlog`) — роль отработала, но файл уехал в соседа по дереву, и `cat` канонного пути даёт «No such file». После rc=0 с пустым логом НЕ объявляй «empty result» и не re-invoke вслепую: сначала `find ~/WorkVault -name <артефакт> -newermt '<время старта>'` по всему дереву — файл нашли в соседнем пути → `cp` в канонный каталог слага и `complete-phase --evidence path=<канонный путь>`. Только если файла нет НИГДЕ — это реальный сбой, чини recovery-правилами.

**Питфолл — фаза в `doing` с `pid=None` + `awaiting_invoke=True` после `next` = «переведена в работу, но invoke ещё не запускался» (сессия оборвалась между `next`→`WORK X` и запуском роли), НЕ упавший воркер и НЕ мёртвый pid.** Точка возврата в поезд (например после «зависания» прошлой сессии на партии миграции). Отличить от dead-pid: `awaiting_invoke=True` (фаза ЖДЁТ запуск роли) против мёртвого pid без этого флага (роль уже ходила). Recovery — НЕ rewind, НЕ interrupt, НЕ правка `_state.json`: `pgrep` пусто → просто запусти `invoke-role --role … --phase … --prompt-file …` той ролью из `PHASE_ROLE`; после rc=0 сверь канонный артефакт (см. питфолл неверного каталога выше) и `complete-phase`.

**Питфолл — ORCH:shared-state при миграции партии: перевод `accepted → unified_only` в манифесте канонически требует (1) актуального `rollback_snapshot` и (2) `operator:удаляй` старого per-tool `.env`; это operator-hold класса O, оркестратор НЕ закрывает сам.** Строки HF-plan вида «Переход из A0 — когда у всех семи: … rollback_snapshot + evidence удаления legacy; статус только ORCH» фиксируют жёсткие предусловия. Перед `complete-phase ORCH:shared-state` сверь манифест: `rollback_snapshot` в `config.tools.<key>` сейчас `null` (путь на YAML-снапшот из `_Archives/eco-config-w4-*/ecosystem-config/*.yaml` надо прописать), а `~/USERTOOLS/<Tool>/.env` ещё на диске — значит перевод в `unified_only` НЕ легитимен. Не переключай статус и не удаляй `.env` молча: доложи Саше, что всё зелёное (probe/explain/runtime/ErrorBus), но фиксация `unified_only` ждёт его операторского глагола `удаляй`; legacy-ветки в самих `config.py` вырезаются не здесь, а на финальном 4-clean (не трогай их в этой фазе). **После** ответа Саши исполнение — прямой батч по канону, НЕ через `operator-done` (на партии нет заведённого `hold`, `operator-done --verb удаляй` падает «requires evidence»+«missing phase»): перед `rm` убедись несекретные значения уже в едином конфиге/`shared` и секреты в shared `.env` → `rm` legacy `.env` → батч-запись манифеста (`migration_status=unified_only`+`overlay=null`+`rollback_snapshot`=путь к Archived YAML) → сверь счётчик (`accepted=0`) → `render_manifest.py --check-drift`/`--digest`/`--render` → карточка `ORCH-shared-state.md` → `complete-phase` → `next` GATE:done. Полный рецепт — скилл `ecosystem-manifest-ops` (раздел «перевод партии accepted → unified_only»).

## Питфолл — per-tool миграционная партия с реальным runtime-исполнением = CHANGE, а НЕ MIGRATION
MIGRATION-рецепт = `TZ:patch → TZ:finalize → GATE:take-into-work → MIG:plan → GATE:plan-approve → HF:backup → ORCH:shared-state → GATE:done` — в нём **нет фаз исполнения кода** (`HF:impl`/`HF:test`): MIG:plan только планирует, а ORCH только пишет статус. Поэтому «миграция»/«волна W*» как триггер работает ТОЛЬКО для чисто нормативно-планирующего переезда (master-ТЗ + план + запись). Если партия требует фактической работы на боевом входе каждого инструмента (probe + `explain` + живой runtime-вызов + переход `dual_read → accepted`), это исполнение = **CHANGE** с полной цепочкой `HF:plan → REV:plan → HF:impl → HF:test → HF:docs-handoff`. Признак того, что выбран не тот кейс: после `HF:backup` `next` даёт `ORCH:shared-state`, а 10 блоков плана исполнять негде. Правило: пробеги триггер по СОДЕРЖАНИЮ работы, а не по слову «миграция» — есть что исполнять кодом/runtime → CHANGE; только план+запись → MIGRATION.

## Питфолл — MIGRATION-кейс стартует сразу `TZ:patch` (нет `TZ:stabilize`/`TZ:compress`); оркестратор обязан сам проставить `tz_path`/`tz_version`/`tz_mtime` до запуска архитектора
Рецепт MIGRATION = `TZ:patch → TZ:finalize → GATE:take-into-work → MIG:plan → GATE:plan-approve → HF:backup → ORCH:shared-state → GATE:done` — фаз стабилизации/сжатия ТЗ нет. Поэтому `_state.json` приходит с `tz_path=None`, и `emit-prompt --phase TZ:patch` не кладёт строку `master_tz:` в пакет — архитектор остаётся без нормативного указателя на существующий master-ТЗ (миграция партии B1 опирается на уже живой `EcosystemIntegration_TZ.md`, новый freeze не пишется). Порядок: (1) `init --case MIGRATION` + `suggest-slug` (слаг даёт CLI, оркестратор не выдумывает); (2) `next` → `WORK TZ:patch`; (3) через venv-`write_state` проставить `st.tz_path`/`st.tz_version`/`st.tz_mtime` (на существующий master-ТЗ) с `event={'event':'tz_write','actor':'cli','phase':'TZ:patch',...}` — НЕ raw-правкой `_state.json` (рвёт `state_sha256`); (4) только затем emit-prompt + `invoke-role --role architect` на `TZ:patch`. `TZ:finalize` — тоже architect (бамп версии master, аддитивная секция); обе идут отдельными invoke-вызовами, не склеивать. `GATE:take-into-work` — sirene, `MIG:plan` — architect, `GATE:plan-approve` — sirene, `HF:backup`/`ORCH:shared-state` — sirene.

## Инвариант №15 — «уже в прод?»: утверждай деплой по фактам, не по отчёту поезда и не по самому коммиту
Когда Саша спрашивает «теперь это уже в прод? / всё работает?» после закрытого графа — НЕ отвечай по слову из финального отчета и НЕ подтверждай деплой только потому, что commit влит в `main`. Верифицируй фактическое состояние слоя, где код реально исполняется:
- **Commit влит и синкается:** `cd ~/hermes-workspace && git log --oneline -3 && git status -sb` → на `main`, пусто (`git status` чистое = синк с origin ок). `git show --stat <commit>` — показывает, что пакет ТОЛЬКО трогает скиллы/контракты и НЕ правит ядро (тогда и деплоя ядра не требуется).
- **Инстанс читает изменённый код или нет:** `ps aux | grep 'hermes serve'` + `readlink /proc/<pid>/cwd` → рабочий Hermes запущен из `~/hermes-agent` с `--skip-build`; скиллы симлинкованы на `~/hermes-workspace` (readlink -f). Разделяй слои: скиллы/pipeline-код (`~/WorkVault/Registries/pipeline`, симлинк скилла) против ядра hermes-agent. Изменение ТОЛЬКО скиллов/кода пайплайна = уже в проде без рестарта gateway (симлинк живой, diff пуст относительно hermes-workspace), изменение ядра hermes-agent — не в проде, пока не перезапущен/пересобран.
- **Тесты зелёные на текущем коде:** запустить набор с правильным `PYTHONPATH` (см. питфолл выше), не верить «192 passed» из отчёта.
- **Честный разрыв «развёрнуто» vs «живым прогоном не проверено»:** пакет, который чинит сам себя (напр. починка самоблокировки роли на баге, который упал на старом коде), тестами доказывает код-путь, но не боевой прогон. Так и сказать: «в проде + тесты зелёные, но следующий реальный прогон — первая проверка», и предложить верифицировать после следующей живой задачи вместо того, чтобы повторять баг ради проверки.

## Do NOT
- Не произноси «готово»/дона до preflight-проверок (граф, фазы, артефакты, REV).
- Не позволяй одному `agent -p` делать работу за архитектора+ревизора+исполнителя.
- Не заводи off-board-цепочку без канбан-графа (теряется audit trail, легко свернуть).
- Не ставь done, если в затронутых ТЗ остались хвосты «на диске: нет».
- Не «воскрешай» архивные `TZ:analyze`/`TZ:architect` (устаревшие фазы, бриф в TG).
