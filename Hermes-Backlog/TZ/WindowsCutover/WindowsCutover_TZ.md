# WindowsCutover — ТЗ переезда (клона) Hermes-инстанса на локальную Windows-машину

**Выжимка ≠ SoT; при расхождении открыть этот master.** Основание —
`dev/klon-germes-agenta-na-windows-mashinu/brief.md` и принятый пакет
`24dbcd067ccd10802ae9cddd2051bbbf7fd1fc5f58ad940ce884221140172cab`.
Директива владельца от 19.11.2026 во второй половине дня отменяет прежнее
предложение WSL2: целевая среда — **нативная Windows, без WSL, виртуализации
и контейнеризации**. Директива учтена во всех действующих разделах; Б36
фиксирует пересмотр требований. Выбор среды не является открытым вопросом.

Результат этого документа — проверяемый проект клона, а не выполненный переезд.
ТЗ имеет статус draft. `REV-tz.md`, `MIG-plan.md`, `REV-plan.md`, приёмки блоков
и проверки на Windows ещё не получены. Чужие прежние APPROVE их не заменяют.
Пошаговый порядок ниже задаёт требования к плану; исполняемый план выпускается
архитектором в `MIG:plan` после согласования ТЗ.

## Б0. Цель, решения и границы

### Б0.1 Результат для Саши

На его Windows-машине Ryzen AI7 с 32 ГБ RAM появляется самостоятельный Hermes
с личностью Сирени, актуальными навыками, рабочими данными и инструментами.
Саша вручную подготавливает ОС, доступ и первый диалог. После этого передаёт
живому локальному агенту проверенную инструкцию архитектора; дальнейшую
донастройку агент выполняет по согласованным блокам с доказательствами.

«Клон инстанса» означает функциональную полноту рабочего окружения. Это не
копия Linux-диска, не только USERTOOLS и не синхронизация всего домашнего каталога.
Код и зависимости устанавливаются заново; навыки и данные отбираются до доставки.

Зафиксированные решения владельца:

1. Цель — существующая Windows-машина; покупка оборудования не нужна.
2. На Windows — только актуальное рабочее состояние. История разработки,
   dev-кейсы, старые ТЗ, исследования, черновики и бэкапы остаются на ВМ.
3. Переносятся **все актуальные используемые навыки**, включая процессные,
   целиком с действующими `references/`, `scripts/` и прочими зависимостями.
4. В `hermes-workspace` Linux остаётся на `main`, Windows развивается в постоянной
   ветке `windows`. Автослияние запрещено; перенос одного навыка между линиями
   допускается только по решению Саши.
5. ВМ сохраняется как постоянный архив и страховка. Её выключение/удаление
   не является частью этого ТЗ, в том числе после приёмки.
6. Настройку Windows после первого живого диалога выполняет местный Hermes;
   содержательное ТЗ и план предварительно проверяет независимый ревизор.
7. Hermes устанавливается нативно под Windows. Скиллы и USERTOOLS адаптируются
   для этой среды; их работоспособность под Linux не считается Windows-проверкой.
   WSL, Hyper-V/другая ВМ и контейнеры не являются запасным путём установки.

### Б0.2 Уровни готовности

| Уровень | Что доказано | Чего ещё недостаточно для полной приёмки |
|---|---|---|
| Первый живой агент | CLI отвечает через выбранного провайдера и читает локальную инструкцию | Навыки, данные, интеграции ещё не восстановлены |
| Рабочий изолированный клон | Состав сверён, данные восстановлены, офлайн и read-only smoke выполнены | Внешние записи, доставка, расписания и основной маршрут ещё не включены |
| Основной локальный инстанс | Приняты включённые контуры, единственный владелец внешних действий, наблюдение и rollback проверены | ВМ всё равно сохраняется; не создаётся право удалить архив |

Нельзя назвать миграцию законченной по одному успешному ответу LLM. Невключённый
обязательный контур имеет `NOT_RUN`/`BLOCKED`, а не PASS. Исключить обязательный
контур можно только адресным решением владельца с изменением AC и ревизией.

## Б2. Целевая архитектура

### Б2.1 Принятая среда

Целевая цепочка: **Windows x64 → PowerShell/Windows Terminal → native Hermes
CLI с Windows Python/Node → нативные USERTOOLS и локальный WorkVault на NTFS**.
Это решение владельца, а не предложение повторно выбрать между Windows и
Linux. Виртуализация и контейнеризация в цепочку не входят. Windows Terminal —
терминал; shell и его версию план называет отдельно.

Официальная инструкция содержит native PowerShell installer; Python/Node
готовит PM выбранной сборки. Поддержка платформы Hermes не доказывает
переносимость наших навыков/USERTOOLS. [Hermes: installation](https://hermes-agent.nousresearch.com/docs/getting-started/installation/)

До выпуска исполняемого плана проверить фактические Windows edition/build,
x64, PowerShell version, локальный NTFS, права текущего пользователя и сеть.
Минимальную версию ОС/PowerShell и необходимость build tools устанавливают по
выбранному Windows installer и зависимостям, не по требованиям WSL. Установка
в пользовательские каталоги выполняется без постоянного admin-сеанса;
повышение прав — только для конкретной операции из памятки. Нельзя отключать
защиту ОС, корпоративные политики или менять execution policy всей машины
ради обхода отказа. Несовместимость означает блокер зависимого шага.

Известны Ryzen AI7 и 32 ГБ RAM; CPU topology, диск и сеть не измерялись.
Искусственный лимит виртуальной машины не задаётся. План фиксирует ресурсный
бюджет после измерений с резервом для Windows и рабочих приложений, а свободное
место — по Б4.4. Первый агент использует имеющийся LLM-доступ. NPU, локальная
LLM, новый Honcho/ownCloud-сервер и прокси не входят в базовую установку.

### Б2.2 Пути и данные Windows

Имя пользователя Windows сохраняется фактическое; создавать Linux-пользователя
или подставлять `tkachenkoav` в `C:\Users\…` нельзя. Ниже `%USERPROFILE%` —
обозначение корня профиля; в PowerShell используется `$env:USERPROFILE` и
`Join-Path`. Литералы `%USERPROFILE%`/`~` не считаются автоматически раскрытыми
в YAML, JSON, Python или argv другого процесса. MIG-план фиксирует разрешённые
абсолютные пути и consumer каждого значения.

| На ВМ | На native Windows | Правило |
|---|---|---|
| `/home/tkachenkoav/.hermes` | `%USERPROFILE%\.hermes` | Явный `-HermesHome`; новые runtime/identity, отобранные данные |
| `/home/tkachenkoav/hermes-agent` | `%USERPROFILE%\hermes-agent` | Явный `-InstallDir`; чистая pinned установка с Windows runtime |
| `/home/tkachenkoav/hermes-workspace` | `%USERPROFILE%\hermes-workspace` | Ветка `windows`, полный актуальный состав без dev-истории |
| `/home/tkachenkoav/USERTOOLS` | `%USERPROFILE%\USERTOOLS` | Исходники и рабочие данные, отдельные Windows-окружения |
| `/home/tkachenkoav/WorkVault` | `%USERPROFILE%\WorkVault` | Разрешённые рабочие материалы и действующие нормы |
| Нет пользовательского staging | `%USERPROFILE%\windows-cutover` | Разовая папка поставки/проверок, не сервис или управляющий реестр |

В прочитанном installer значение по умолчанию — `%LOCALAPPDATA%\hermes`,
поэтому здесь оба пути передаются явно. Windows-параметр `-HermesHome`
реализует требование brief о `--hermes-home`; POSIX-флаг в PowerShell не
переносится. Пользовательское `HERMES_HOME` должно указывать на
`%USERPROFILE%\.hermes` в новой сессии, включая запуск дочерних процессов.
Launcher публикуется в выбранный `HermesHome\bin`; его фактический путь и
runtime проверяются, не выводятся только из PATH. Эти детали подтверждены
локальным `scripts/install.ps1`; перед установкой проверяются на выбранном pin.

БД, рабочие деревья и окружения лежат на локальном NTFS, вне сетевых дисков и
автоматически синхронизируемых OneDrive/ownCloud-каталогов. GUI Obsidian читает
тот же локальный WorkVault; второй пишущий vault не создаётся. Для каждого
root проверяются права, reparse points и реальный target. При конфликте с
существующей установкой/redirected profile план требует адресного решения и
backup; установка поверх неизвестных данных запрещена.

Перед переносом проверяются имена с `:`, зарезервированные `CON`/`NUL` и др.,
хвостовые точки/пробелы, коллизии регистра, длина пути, пробелы и кириллица.
Несовместимые имена адресно отображаются в manifest с обновлением ссылок;
молчаливое усечение или overwrite запрещены. [Microsoft: имена файлов](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)

На первом запуске нет синхронизации двух vault, Windows Task Scheduler,
служб автозапуска, gateway poller, cron scheduler, канбан-dispatcher и
исходящих очередей. Базы не расшариваются между ВМ и Windows.

|---|---|---|

До установки архитектор фиксирует release record: source URL, branch/tag,
полный commit SHA, SHA installer, PM lock, actual managed generation/runtime,
перечень реально нужных local modifications и их доступность на целевой машине.
Dirty checkout не превращается в «опубликованный релиз». Форк или upstream
выбираются после проверки паритета нужных функций; fork указан по требованию
brief, но его remote freshness в этом ходе не проверялась.

Windows release record дополнительно содержит SHA-256 `scripts/install.ps1`,
Windows entries `pm/lock.json`, версии Python/Node/Git/PowerShell, архитектуру,
способ выбора source URL, точные параметры и stdout resolved paths без секретов.
В локально прочитанном installer source задаётся `HERMES_REPO_URL`, pins —
`-Branch`/`-Commit`, пути — `-InstallDir`/`-HermesHome`, первый запуск —
`-NonInteractive`. Параметра `-RepoUrl` у этой версии нет. Не использовать
интерфейс `install.sh` как спецификацию `.ps1`. Полный commit должен быть
доступен в выбранной remote branch; Windows-совместимость наших изменений
проверяется отдельно. Сборку для запуска нельзя назначить по одному наличию
`.ps1` в Linux checkout.

Нельзя обещать воспроизведение live-инстанса по HEAD checkout. Необходимые
неопубликованные изменения сначала описываются и проходят свой разрешённый
маршрут выпуска; отсутствующий commit/installer — стоп установки, без fallback
на `latest`. Установка pinned сборки не должна автоматически переключать канал,
обновлять source или перезапускать gateway. Новый platform-fork не создаётся.

### Б3.2 Постоянная ветка `windows` без перевозки истории

Копирование `.git` с ВМ и обычный полный clone workspace запрещены: в текущем
дереве есть `Hermes-Backlog`, `_bak-*` и implementation before/after. Даже
`--depth 1` сам по себе не исключает исторические файлы из текущего commit.

Для **первого** Windows-снимка предлагается корневой commit ветки `windows`
из отобранного актуального дерева без родителей `main` (orphan/root branch)
в том же репозитории. На ВМ только готовится список и содержимое, без commit,
checkout или push. На Windows сначала read-only проверяется наличие remote
`windows`; если её нет, создаётся локальный repo с начальной веткой `windows`,
добавляется существующий origin, затем принимается и пушится только эта ветка.
Источник каждого файла сохраняется в поставочном manifest: VM path, source
commit при наличии, SHA-256 выбранного файла. Это не новая сущность экосистемы.

Если remote `windows` уже есть, не перезаписывать и не force-push. Сначала
сопоставить её актуальное дерево с allowlist; затем использовать только эту
ветку. Существующее содержание с запрещённой историей требует отдельного
решения об очистке/поставке, а не скрытого полного скачивания.

Настройки ограничивают обычный push текущей веткой (`push.default=current`),
проверка перед push обязана показать `windows`; refspec — только
`HEAD:refs/heads/windows`. Не использовать `--all`, `--mirror`, `--force`,
автослияние или автоматический pull `main`. Новые git hooks не создаются.
Защита локальной конфигурацией не выдаётся за серверный запрет: refspec
и удалённый ref проверяются в evidence. Начальный push — после проверки
секретов и содержимого, уже живым Windows-агентом по принятому блоку.

После bootstrap изменяемые навыки имеют source of truth в `windows`. Отбор
версий из нескольких источников при клонировании — разовая сверка, не скрытый
двусторонний sync. Перенос изменений между `main` и `windows` — решение Саши,
один навык, отдельный diff и тест; merge-коммиты и массовый cherry-pick исключены.

### Б4.2 Запрещённое содержимое

Из всех корней и вложений исключаются `Hermes-Backlog/dev/**`, dev journals,
исследования/черновики разработки, ТЗ-история и старые редакции, `_Archives`,
`backups`, `profiles-backup`, `_bak-*`, `_backup_*`, `*.bak*`, implementation
before/after, дубликаты `copy-tmp`, тестовые DB, execution logs/receipts,
старые очереди и VM process identity. Общее дерево `Hermes-Backlog/TZ/**`
запрещено, кроме перечисленных действующих нормативных файлов.

Дистрибутивы `.hermes/tools`, `installs`, `environments`, `bin`, `lib`, `node`,
`lsp`, caches, скачанные модели, venv, `node_modules`, `__pycache__`, `.git`,
sockets/PID/locks и WAL/SHM не входят в перенос данных. Название `scripts/`
или `tools/` внутри навыка само по себе не основание удалить рабочий исходник:
маски привязаны к типу и корню, их применение проверяется по manifest.

Этот запрет `.git` относится к переносимым данным ВМ и исходному снимку
навыков/USERTOOLS. Git metadata, которую штатный pinned installer создаёт для
Hermes source checkout, — часть новой установки Б3.1, а не доставка dev-кейсов
или копия репозитория ВМ. В manifest эти категории различаются; это исключение
не разрешает клонировать всю историю `hermes-workspace`.

Нельзя сначала отправить весь каталог, а затем удалить историю на Windows.
Нельзя разыменованием symlink незаметно включить внешний каталог. Поставщик
фиксирует target каждого link; абсолютные и выходящие за разрешённое дерево
ссылки отклоняются либо адресно преобразуются с доказательством соответствия.
Nested archive проверяется по содержимому или исключается; расширения файла
недостаточно для контроля истории.

### Б4.3 SQLite и согласованность

1. Найти все реально используемые DB в выбранных корнях, не только `state.db`.
   Снять локальные схемы/версии и связи данных без печати содержимого/секретов.
2. Использовать штатный SQLite online backup либо поддерживаемый export.
   Raw cp/tar открытой DB, WAL/SHM как «довесок» и `immutable=1` для живой
   WAL-БД не являются способом получить согласованный снимок.
3. Каждый backup проверяется `PRAGMA integrity_check` на **копии**, row counts
   и прикладным чтением. Схемы и миграции проверяются на копии до установки.
4. Обычные файлы снимаются в новый staging. Проверяется стабильность manifest
   до/после; при изменении повторяется только затронутый набор, с ограничением
   попыток и явным отказом при непрерывном churn.
5. Отдельные backup разных DB не дают общей транзакции. Для связанных наборов
   (протокол/registry/индекс, sessions/state) нужен общий checkpoint/high-water
   mark или проверяемый reconciliation в плане. Если без остановки writers
   согласованность недостижима, фиксируется блокер будущего cutover. ВМ в этой
   фазе не останавливается ради снимка.
6. MofsIndex как производный индекс пересобирается на Windows из отобранных
   документов/registry; исходные данные не заменяются пустым индексом.

### Б4.4 Упаковка, секреты и доставка

Одна сборка пишет один новый staging вне WorkVault и один завершённый файл
поставки. Не переиспользовать непроверенный staging после сбоя. Удаление
допустимо только собственного staging в будущем разрешённом блоке, не ВМ-архива.

В поставке один `payload/home/`, несекретный README с порядком восстановления,
manifest и контрольными суммами. Секретные файлы включены в закрытую часть;
поставка с секретами шифруется согласованным существующим средством. Способ,
получатель/ключ и проверка расшифрования должны быть конкретны в MIG-плане;
ключ не кладётся рядом с архивом. Если согласованного средства/канала нет —
стоп доставки, без отправки plaintext в облако или чат.

Текущее принятое WindowsCutover-ТЗ, MIG-план, оба вердикта и инструкция
передаются как документы **этой поставки** в `%USERPROFILE%\windows-cutover`, с исходными
refs и hashes. Это не перенос старого `Hermes-Backlog/dev/**`: дерево кейса,
process state, research и прежние evidence туда не копируются. Ссылка на файл
в недоступном домашнем каталоге ВМ сама по себе не является доставкой инструкции.

Переиспользуется существующий доступ Саши: приватный SSH/SFTP или уже
настроенный ownCloud-клиент по скиллу доставки. Нового сервера не создаётся.
Включение/изменение sync-сервиса ВМ не разрешено этим packet. Для ownCloud
контроль — скачать доставленный файл и сверить его SHA-256, не только размер
или exit code sync. Передача секретов имеет отдельные ограничения Q-3.

До раскрытия архива проверяются SHA-256 и provenance; перед extraction —
путь каждого member (нет абсолютного пути, `..`, device/socket, link escape),
ожидаемый размер и единственный корень. На Windows дополнительно отклоняются
drive/UNC paths, alternate data streams, reparse/link escape и коллизии имён
Б2.2; сам `Expand-Archive`/tar без preflight не доказывает безопасность.
Разворачивать сначала в staging, не поверх live home. На ВМ секретные каталоги
0700, файлы 0600; на NTFS задаются и читаются Windows DACL. `chmod 600` из
brief — требование приватности, а не команда для Windows. До расшифрования
план проверяет owner SID, отключение широкого наследуемого доступа и отсутствие
чтения для посторонних пользователей; нужный доступ владельца и системных
администраторов не ломается массовым deny. Точные SID, команды `icacls` и
post-readback фиксирует MIG-план. `icacls /verify` проверяет структуру ACL,
но не заменяет проверку эффективного доступа. [Microsoft: icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls)
Значения не попадают в PowerShell transcript/history или CLI-аргументы.

Свободное место считается по факту: архив + staging + установленный payload +
backup затрагиваемых целевых данных + rebuilt environments/index + запас 20%.
Предварительные размеры из старого skill не считаются измерением этого клона.

## Б5. Полнота навыков

Сначала составляется матрица `skill id → live path → workspace path → profile
visibility → выбранный источник → hash дерева → зависимости → целевой путь`.
Источники обходятся с учётом symlink и реальной discovery выбранной версии
Hermes, без подсчёта вложенных копий как самостоятельных активных навыков.

Обязательные именованные навыки: `devops/dev-workflow`, `devops/hermes-feature`,
`devops/tz-workflow`, их `references/canon.md`, `context.md`, `invoke.md` и
прочие действующие references/scripts; `devops/hermes-migration-archive`,
`devops/hermes-managed-install`, `devops/mofs-operations`, инструментальные
навыки PFS/WorkVault/Ecosystem и весь подтверждённый активный набор.

Правила разрешения расхождений:

- Live-only рабочий навык не теряется при клонировании workspace; его актуальное
  дерево включается в исходный снимок `windows` после классификации.
- Workspace-only процессный навык не исключается лишь потому, что его нет
  в live root: учитываются профиль, ссылки и подтверждённые требования brief.
- Разные байты одного id не выбираются по mtime вслепую. Архитектор сравнивает
  содержание и действующий источник; выбор и причина сохраняются в matrix.
- Вложенная история (например `references/implementation/**/before|after`)
  не делает весь навык непереносимым и не легализует перенос истории. Выделяются
  реальные runtime references. Если обязательная инструкция зависит именно от
  исключаемого dev-артефакта, это явный конфликт нормативной closure Б6/Q-1.
- Весь актуальный набор доставляется; platform-specific возможности
  проверяются отдельно. Наличие файла не доказывает работоспособность macOS,
  Windows desktop automation, browser, Office, VPN или внешнего API в native Windows.

Restore-скрипты сначала анализируются на Windows-копии. Если текущий скрипт не
покрывает фактические discovery roots, корневые навыки или конфликт каталогов,
нужен адресный план исправления в `windows` через DevWorkflow. На ВМ скрипты
не меняются. Не создавать дубли навыков в нескольких roots «на всякий случай».

Приёмка: множества согласованных skill id совпадают; у каждого есть полный
список files/hash; ссылки разрешаются; discovery для каждого активного профиля
видит ожидаемый набор; 0 потерянных обязательных файлов. Команда
`hermes skills list --enabled-only` допускается, если она подтверждена `--help`
именно установленной версии; неподдерживаемый `skill validate` не используется
как фиктивная проверка. Валидация включает чтение frontmatter, ссылок и
контрольных инструкций выбранными профилями, без автоматического исполнения
всех scripts из навыков.

### Б5.1 Обязательная адаптация навыков к native Windows

Для **каждого** актуального навыка матрица дополнена полями: используемые
команды/скрипты, runtime и его версия, Windows entrypoint, список адаптаций,
зависимости, статус проверки и evidence. Статусы: `native-ready`,
`adaptation-required`, `blocked`; первый означает пройденный Windows smoke,
а не мнение по расширению `.py`. Сохраняются исходный и целевой hashes и diff
с причиной каждого изменения; полнота поставки проверяется отдельно от порта.
Для навыка без исполняемых файлов entrypoint отмечается «не требуется»;
проверяются discovery, обязательные ссылки и Windows-команды самой инструкции.

| Зависимость Linux | Требование к Windows-копии | Проверка |
|---|---|---|
| `.sh`, shebang, bash pipelines, `source`, `chmod`, `ln`, `rsync` | Перенос на `.ps1`/нативный Python или документированный Windows runtime для конкретного скрипта; bootstrap и обязательный процесс не зависят от Linux shell | Точная команда из PowerShell, версии/exit code, эквивалентный результат и отказ на ошибке |
| Жёсткие `/home`, `/tmp`, `~`, разделитель `:` в PATH | `Join-Path`/pathlib, Windows temp и env; mapping всех потребителей, без глобального search/replace | Путь с пробелами/кириллицей, temp cleanup только своих файлов, правильное раскрытие переменных |
| POSIX symlink, executable bit, UID/mode | Проверенный discovery без права создавать symlink либо адресный Windows link/copy с одним source of truth; NTFS ACL | Нет битых ссылок, дублей id и широкого доступа; root/profile видят одни принятые bytes |
| LF/CRLF, locale, BOM и shell quoting | Явный UTF-8 для данных/логов и совместимая с выбранной версией PowerShell кодировка `.ps1`; аргументы передаются списками | Кириллица и кавычки не искажены; hashes исходных данных не меняются при копировании; newline conversion — только заявленный diff |
| `fork`, signals, `/proc`, flock, Unix sockets, ps/kill/lsof | Штатные Windows/кроссплатформенные средства для process tree, locks, порта и таймаута | Нет зависших детей/ложного unlock; занятый порт и повторный запуск дают предсказуемый отказ |
| systemd, cron, Linux desktop/browser binary | Windows entrypoint без автозапуска; расписания/сервисы остаются выключены до Б11/Q-4 | Ручной smoke работает, новый task/service не появился |

Git for Windows не означает наличие подходящего Bash-окружения для всех
навыков. Допустимый Windows runtime для отдельного `.sh` должен быть назван,
зафиксирован и проверен; WSL/контейнер/Linux VM исключены. Если обязательный
навык не переносим, он остаётся в полном составе со статусом `BLOCKED`, а
рабочий клон не принимается до адаптации или адресного изменения требований
владельцем. Нельзя объявить его лишним лишь из-за платформы.

Конкретные изменения кода, `restore-all-skills.sh`/`sync-to-hermes.sh` и
инструкций делает разрешённый исполнитель по MIG-плану с независимой ревизией,
в Windows-копии/ветке `windows`. Здесь формулируются требования к порту;
живые навыки ВМ, `main` и restore на ВМ не изменяются и не запускаются.

## Б6. Процесс, нормы и реестры на Windows

Перенос процессных навыков должен сохранить штатный DevWorkflow, а не запускать
второй самодельный диспетчер. Read-only проверка выявила: актуальный master
DevWorkflow описывает native канбан и содержит ссылки на документы в `dev/…`;
часть локальных operational references описывает файловый маршрут. Этот
миграционный проект не чинит канон и не объявляет любую из старых реализаций
пригодной только по наличию файлов.

В поставочном manifest обязательно выделить:

1. Актуальные `EcosystemConfig.yaml`, schema, manifest/digest, `entities.json`,
   `entities.schema.json`, другие реально читаемые registry и их loaders.
   Значения с путями адаптируются только на Windows; никакой новой конфиг-БД.
2. Требуемые `WorkVault/Registries/pipeline/` модули, schema и prompts, включая
   внешние импорты/CLI entrypoints. Определить используемый runtime и исключить
   superseded implementation, backup и управляющие данные старого процесса.
3. DevWorkflow master, GLOSSARY и минимальную closure **действующих норм**.
   Различать обязательные нормативные ссылки и исторические evidence-ссылки.
   Старые approvals и приложения не перевозятся как разрешение нового запуска.
4. Действующие роли/профили и физические владельцы их моделей/настроек. На новой
   машине подтверждаются доступность backend и корректность выбранного
   runtime без выдумывания нового model/provider fallback.
5. Native entrypoints процессных скриптов: пути, subprocess/locking, transport
   и доступность выбранного backend на Windows. Linux `.sh` wrapper, `fcntl`,
   `/proc` или Unix socket не считаются доступными без проверки адаптации.
   Имена фаз, канон, guards и независимость ревизора при порте сохраняются.

Если необходимая норма существует только внутри исключённого dev-кейса,
нельзя тихо перенести весь кейс, стереть ссылку или выдать extract за master.
До утверждения manifest архитектор/владелец решают Q-1: публикация действующей
нормы в разрешённом нормативном месте отдельным согласованным изменением
либо точное исключение владельца. Пока closure не замкнута, локальный
DevWorkflow имеет `BLOCKED`; факт первого CLI-диалога при этом допустим.

Windows не наследует очередь, активный граф данной миграции, leases, receipts
и счётчики ВМ. Оркестрация миграции остаётся на ВМ; Windows-агент — получатель
инструкции и исполнитель разрешённых локальных операций. Для новых Windows
dev-задач используется локальный штатный процесс после его отдельной проверки,
без повторного исполнения VM-кейсов. Запрещён raw SQL-write/ручной JSON-reset
для «очистки» импортированного процесса.

Интеграционная проверка DevWorkflow выполняется изолированно по штатной
процедуре: discovery профилей/конфигов, доступность модулей и норм, допустимость
packet/recipe/roles; проверка исполнения — только разрешённый тестовый кейс с
собственными identity и независимым reviewer. Самостоятельная подмена ревизора
Windows-агентом или запуск второго wrapper для исходной миграции исключены.

До готовности локального DevWorkflow его нельзя поручить портировать самому
себе через неработающий launcher. В MIG-плане выделяется минимальный набор
native процессных entrypoints и валидаторов. Подготовка и ревизия такого
набора организуются существующим процессом на ВМ в отдельно разрешённом
изолированном write-set; живые код/навыки/конфиги ВМ и `main` не меняются.
Windows-агент по принятой инструкции применяет и проверяет поставленные
изменения локально как операции миграционного блока. Содержательный дефект
возвращается архитектору на ВМ; обход локального guard, raw role launch и
самоприёмка Windows-агентом не разрешаются. После доказанной native готовности
новые доработки ведутся штатным локальным процессом. Если необходимый backend
на Windows отсутствует, фиксируется блокер, а не новая модель/fallback.

каждого инструмента должны быть точные source path, dependency/lock, Python,
entrypoint, данные, необходимые credentials, Windows-adaptation и безопасный
smoke. При отсутствии lock записать воспроизводимую установленную версию
зависимостей; никогда не копировать venv с ВМ.

`MFKT` не найден как самостоятельный каталог: не выдумывать репозиторий или
новую сущность. Сопоставление с реальным навыком/инструментом — обязательный
пункт inventory перед freeze manifest, в том числе кандидат `MoveFromKeyTalk`.

MppReader отдельно требует Java/MPXJ/JPype по актуальному README; на ВМ указан
путь Python 3.9, который нельзя переносить как заведомо существующий на Windows.
Точный совместимый набор устанавливается и проверяется на локальном `.mpp`
или XML-примере без Google write. Python managed Hermes не считается
автоматически подходящим Python для всех USERTOOLS.

Для всех перечисленных USERTOOLS применяется матрица переносимости Б5.1:
Windows `.venv\Scripts\python.exe` вместо Linux `bin/python`, совместимые
Windows wheels/native libraries, версии Java/JPype той же архитектуры,
subprocess argv/cwd, UTF-8/CRLF, filesystem locks и таймауты. `.sh` entrypoints
адаптируются на `.ps1`/native Python либо обосновывается конкретный Windows
runtime. Компилятор/MSVC, Java и прочие системные зависимости включаются в
план адресно, без обещания автоматической установки всего через pip.
Для `proxycheck` проверяется сам Linux-контракт сетевых команд; успешный import
не доказывает переносимость. Каждому порту нужны fixture до/после, прикладной
результат, негативный случай и отсутствие внешней записи. Исходники ВМ
сохраняются; Windows diff и dependency pins входят в принятую поставку.

Для каждого активного инструмента результат PASS/FAIL/BLOCKED/NOT_RUN,
команда, exit code, время, версия и output-file фиксируются в smoke-матрице.
`--help`/import подтверждают только запуск; приёмка обязательной функции требует
прикладного результата и проверки отсутствия внешнего побочного действия.
Если безопасного режима у инструмента нет, используется изолированный fixture
или согласованное окно; нельзя выдумать флаг `--dry-run`.

Слово «ВМ» в таблицах — место работы, не новая роль DevWorkflow. Архитектор
пишет требования/инструкции, оркестратор ведёт штатный процесс, координатор/
разрешённый исполнитель делает backup и механические операции по принятому
scope. Саша выполняет физические/интерактивные действия на своём компьютере.
Живой Windows Hermes действует только в разрешённом локальном контуре.

| Шаг | Кто и где | Вход и действие | Выход/условие перехода |
|---|---|---|---|
| 1 | Архитектор, здесь | Прочитать brief/master, сопоставить реальные пути и ограничения | Это ТЗ, read-only inventory, вопросы Q-1…Q-4 |

до возврата архитектора. Саша не обязан вручную восстанавливать все USERTOOLS:
его минимальная ручная часть ограничена Б9 и интерактивными доступами.

### Б8.1 Требования к `MIG-plan.md`

Для каждого блока: id, владелец, среда, exact write-set, prerequisites,
команды со shell/cwd, ожидаемый результат, IAC `path / verify / depends / covers`,
negative cases, stop condition, rollback и evidence absolute path+hash+time.
Никаких запускаемых заглушек `latest`, `<SHA>` или «установить зависимости» без
расшифровки. Если значение ещё не установлено — блок не готов к исполнению.

Отдельно обязательны Windows portability matrix, порядок минимального порта
процессных зависимостей Б6, версии ОС/shell/runtimes, проверка имён и ACL,
полные native команды bootstrap и проверки каждой адаптации. Перенос `.sh`
в `.ps1` не является механическим переименованием. Shell каждой команды
обозначается явно: Linux-команды допустимы в шагах ВМ, не в ручной Windows-части.

Предлагаемые содержательные блоки для детализации: состав/сборка; Windows
bootstrap; локальная самонастройка; прикладная проверка; переключение внешних
контуров; наблюдение/приёмка. Их фактические номера `MIG:block-N` назначает
оркестратор штатным рецептом после плана; этот текст recipe не меняет.

Каждый `MIG:block-N` требует **собственного** never-auto `GATE:block-accept`
Саши и валидных identity/evidence/hash/timestamp/receipt предшественников.
Один общий «план одобрен» не является приёмкой всех блоков. Добавление
требуемой независимой `REV:plan` — задача оркестратора в рамках канона,
не команды архитектора из текущего wrapper.

## Б9. Что Саша делает до появления живого агента

Это последовательность для включения в проверенный MIG-план. Выполнять только
после выдачи конкретной принятой памятки; сейчас installer не запускался.

1. **Получить памятку.** На ВМ должны быть готовы: точная сборка/installer,
   SHA-256, способ приватной передачи, минимальные credentials для первого
   диалога и `WINDOWS-HANDOFF.md`. Полный архив ещё может доставляться отдельно;
   данные токенов в памятке отсутствуют. Памятка содержит рабочие PowerShell
   команды без незаполненных pins, подтверждение ревизии и условие остановки.
2. **Проверить Windows в PowerShell.** Выполнить `winver`,
   `$PSVersionTable.PSVersion`, `Get-CimInstance Win32_OperatingSystem`,
   `[Environment]::Is64BitOperatingSystem`, `Get-PSDrive -PSProvider FileSystem`,
   проверить `$env:USERPROFILE`, VPN и доступ к выбранным endpoints. Вывод
   с персональными данными сокращается перед передачей. Сопоставить build,
   архитектуру, свободное место и shell с release record. WSL не устанавливать
   и не использовать; BIOS/Hyper-V/контейнеры не настраивать.
3. **Подготовить каталоги и prerequisites.** В обычном пользовательском
   PowerShell проверить через `Test-Path -LiteralPath` существование путей Б2.2,
   а через `Get-Acl -LiteralPath` — владельца/доступ. Создать только отсутствующие
   каталоги поставки и приватного staging по памятке, на локальном NTFS.
   Предварительно существующий `.hermes` или checkout — остановка для адресного
   backup/сверки, не разрешение на overwrite. `Get-Command git -All` и
   `git --version` проверяют доступный Git for Windows. Если его нет, план
   выбирает конкретный проверенный Git package или bootstrap installer; после
   установки проверяются фактическая версия и доступность Git из новой shell.
   Python/Node для Hermes предоставляет pinned PM; USERTOOLS получают свои
   Windows-окружения позже. Дополнительные build tools — только указанные планом.
4. **Настроить приватный доступ.** Новый SSH-ключ для этой машины добавляет
   Саша в существующий GitHub-аккаунт; private key ВМ не копируется. Host key
   проверяется штатно, не отключать StrictHostKeyChecking. Секреты провайдера
   вводятся в файл с проверенными NTFS ACL либо в поддерживаемый auth flow.
5. **Проверить установщик.** Получить согласованный `install.ps1` из фиксированного
   source, сверить `Get-FileHash -LiteralPath` с `-Algorithm SHA256` и release
   record. Не выполнять скачанный текст через `Invoke-Expression`. При запрете
   исполнения скрипта использовать только принятый в плане способ для данного
   проверенного файла/процесса; корпоративную policy и защиту ОС не обходить.
6. **Установить Hermes нативно.** Запустить одну точную PowerShell-команду
   из MIG-плана. Контракт прочитанного installer:

   | Параметр/значение | Обязательное содержание памятки |
   |---|---|
   | `HERMES_REPO_URL` | Проверенный upstream/fork из Б3, доступный выбранному Git; секреты в URL запрещены |
   | `-Branch`, `-Commit` | Конкретная remote branch и полный доступный SHA; без `latest`/плавающей установки |
   | `-InstallDir` | Абсолютный результат `Join-Path $env:USERPROFILE 'hermes-agent'` |
   | `-HermesHome` | Абсолютный результат `Join-Path $env:USERPROFILE '.hermes'`; POSIX `--hermes-home` здесь не используется |
   | `-NonInteractive` | Обязателен; у прочитанной версии setup/gateway stages пропускаются |
   | `HERMES_HOME` | Тот же data home для текущей и новой пользовательской shell; проверка сохранения и фактического чтения |

   Параметры/поведение повторно проверяются по installer именно выбранного pin.
   Desktop не включается ради первого CLI. Exit code и install log сохраняются
   без секретов. Ненулевой exit, неподтверждённый source или неполные обязательные
   runtime-компоненты — стоп, без повторной установки поверх данных. После шага
   проверяется отсутствие созданных gateway service/task и расписаний.
7. **Минимальная настройка LLM.** В fresh home с пустыми очередями выполнить
   поддерживаемую настройку модели (`hermes model` в прочитанной документации)
   для уже имеющегося доступа. Не переносить весь VM config и не подключать
   Telegram/cron/hooks ради первого диалога. OAuth/2FA выполняет сам Саша.
8. **Проверить диалог и локальные инструменты.** Открыть новую Windows
   PowerShell shell. `Get-Command hermes -All` и `where.exe hermes` должны
   указывать на согласованный Windows launcher; фактические home/source/runtime
   сверяются по его диагностике. Через реальный runtime проверить
   `sys.platform == 'win32'`, `sys.executable` и архитектуру, версии Python/Node
   и отсутствие запуска Linux backend. Запустить `hermes` и получить ответ
   выбранной модели. Дать агенту безопасное локальное чтение инструкции
   `%USERPROFILE%\windows-cutover\WINDOWS-HANDOFF.md` и проверку каталога через
   native terminal tool. Агент должен назвать свой Windows path, текущий блок
   и границы; ответ LLM без работоспособного локального tool не подтверждает
   готовность к самонастройке. Backend/shell берутся из схемы выбранной версии,
   без выдуманного config key. Ошибка инструмента блокирует самонастройку.

Теперь агент жив и принимает дальнейшую настройку. При сбое Саша передаёт
сокращённую ошибку без токенов, текущий шаг и версию; повторная установка
поверх данных, full import и удаление home не являются универсальным лечением.

2. **Staging:** проверить checksum/member safety, расшифровать и распаковать

3. **Workspace:** создать/принять только `windows` по Б3; разложить выбранные

5. **Базы и личность:** offline проверить снимки и восстановить разрешённые

   ручной шаг после появления агента, не бесконтрольная самоперезапись.
6. **USERTOOLS:** восстановить исходники/данные, применить принятые Windows

При повторном запуске применяется resume по проверенным фактам, а не по
непроверенному «done» в текстовом чек-листе. Существующие целевые файлы
сначала сравниваются; несовпадение не приводит к overwrite без backup.

## Б11. Переключение внешних контуров и откат

### Б11.1 Единственный владелец

По умолчанию ВМ остаётся единственным владельцем Telegram polling,
планировщиков, импорта с побочными действиями и внешних публикаций. Windows
тестируется через CLI и read-only API. Скопированный токен не означает
разрешение запустить второй poller. Копия cron definitions не означает
разрешение расписаний.

| Контур | До cutover | Условие передачи |
|---|---|---|
| Telegram | ВМ poller, Windows CLI | Q-2; адресное выключение прежнего владельца после отдельного разрешения, проверка отсутствия второго poller, затем `поднимай` на цели |
| Cron/канбан-dispatcher | Только ВМ | Job-by-job ownership; никогда не импортировать старые runs/deliveries. Кроны только после `ставь кроны` |
| API writes/рассылки/auto-join | ВМ | Проверенные dedup/cursors, точный разрешённый сценарий, один writer |
| Vault/ownCloud sync | Действующий маршрут ВМ | Q-3 и mapping папок/направлений; read-only копия не становится вторым bidirectional sync |
| Git навыков | ВМ `main` | Windows только `windows`; независимость веток сохраняется постоянно |

Выполнение передачи требует отдельного разрешённого write-set на действия
старой машины: нынешний запрет менять ВМ не снимается словами «cutover по ТЗ».
До такого разрешения можно принять изолированный клон, но нельзя объявить
все контуры основного инстанса перенесёнными.

### Б11.2 Свежесть данных

Начальный snapshot имеет timestamp и high-water marks. Пока ВМ работает,
появляется delta. До передачи каждого writer определяется окно, в котором
Windows ещё не пишет этот контур, снимается финальная delta/checkpoint,
сверяются уникальные ids/cursors и только затем разрешается новый writer.
Если нет поддерживаемой дельты или согласованного окна, cutover блокируется;
последний полный snapshot «на глаз свежий» не проходит приёмку.

Если Windows уже создала полезные изменения, их нельзя потерять повторным
раскрытием snapshot ВМ. В плане нужен адресный merge по прикладным ids с
отчётом конфликтов; для DB не применяется двусторонний файловый rsync.

### Б11.3 Откат

| Сбой | Действие | Проверка |
|---|---|---|
| До внешней активации | Закрыть новый CLI/локальные процессы, восстановить только затронутые целевые файлы из backup либо оставить staging для разбора | ВМ продолжает работу, target не отправляет и не планирует задачи |
| Плохой навык/конфиг | На Windows вернуть адресный предшествующий снимок/commit; secrets восстанавливаются отдельно от git | Discovery и smoke снова проходят; `main` не затронута |
| Повреждение данных/версии | Остановить consumers на цели, сохранить ошибочный экземпляр, восстановить проверенную целевую копию | Integrity + прикладное чтение; DB миграции не откатываются слепым downgrade |
| После переключения writer | Сначала прекратить целевого writer, сохранить локальную delta/outbox и dedup facts; затем по отдельному разрешению вернуть владельца ВМ | Нет двух poller/writer и повторных доставок; новые данные не потеряны |
| Sleep/reboot/VPN outage | Приостановить затронутый контур, диагностировать по evidence; не включать вторую автоматику как fallback | Явно установлен владелец и возобновление без replay |

Rollback не удаляет исходный архив, ВМ или весь Windows-профиль/каталог данных.
Откатываются только перечисленные целевые файлы, ACL и изменённые пользовательские
env/PATH с сохранением исходных значений; не весь профиль PowerShell. Нельзя обещать
«просто вернуться на ВМ» после целевых записей без reconciliation.

## Б12. Эксплуатационная проверка

Проектный минимум наблюдения — три последовательных рабочих дня после
приёмки изолированного клона и повторно для реально включённых внешних контуров.
Условия уточняются Q-4, но не заменяются неопределённым «N дней».

За период: минимум по одному реальному согласованному сценарию памяти,
поиска MOFS, PFS/OFC, импорта/контактов и каждому обязательному активному
инструменту; один штатный перезапуск Windows, sleep/resume и разрыв сети;
нет потери данных, необъяснённых ошибок, дублирующих отправок или запуска
задач старого графа. Для редких cron не ждать произвольную неделю: отдельный
принятый контролируемый сценарий после `ставь кроны`, без production replay.

Измеряются peak RAM, свободное место, длительность старта, rebuild/поиска и
ответа, факт восстановления после сбоя. Числовые лимиты производительности
фиксирует MIG-план до теста по фактическому диску/составу и потребности Саши;
NPU и «быстрее ВМ» не являются недоказанными обещаниями.
После reboot заново проверяются Windows launcher, выбранный `.hermes`,
PowerShell/backend и доступы; отсутствие CLI из-за пользовательского PATH
не лечится запуском через WSL. Проверка включает занятый порт, блокировку
открытого файла и остановку дочерних процессов без затрагивания чужих PID.

Доступность 24/7 не обещается для спящего/выключенного ПК. По умолчанию ручной
запуск CLI при рабочем сеансе. Потребность в безнадзорной работе и автозапуске —
Q-4; новые task/service/hook — **[NEW-ENTITY, требует согласования Саши]**,
здесь их unit/trigger не проектируется. Не переносить ownCloud-сервер из
старого HomeCutover как молча согласованную часть нового проекта.

8. Stop зависимого блока: hash mismatch, unresolved skill/source conflict,
   отсутствие необходимой нормы, неподдерживаемый installer/runtime, нет
   достаточного места/доступа, mismatch DB, непринимаемый side effect.
9. Отсутствующий proof = NOT_RUN/BLOCKED. APPROVE пишет только независимый
   ревизор, соответствующие `REV-tz.md`/`REV-plan.md` не создаёт архитектор.
10. Native Windows — принятое решение владельца. Не устанавливать и не
    использовать WSL, виртуализацию или контейнеры для обхода несовместимости.
    Непереносимый обязательный навык/runtime/USERTOOL блокирует свою приёмку;
    его исключение или смена среды требует нового адресного решения владельца.
