# Доводка документа через архитектор + ревизор + бриф

## When to Use

Заказчик прислал рабочий документ (ТЗ, фреймворк, план) с новым раундом правок (зачёркнутое `~~...~~`, комментарии-пожелания `*(...)*`, прямые правки) и требует провести его через цепочку: **архитектор обрабатывает правки → ревизор сверяет → развилки идут брифом → согласованный итог на диск заказчику**. Триггеры: «обработай правки», «разбери комментарии», «нужны архитектор и ревизор», «согласуй итог», «сделай финальную редакцию». Это повторяющийся цикл: по одному документу проходит несколько таких раундов до финала. Если заказчик просил «правила все те же» — триггер-цепочка всегда включает ревизора, не только архитектора.

## Шаги (порядок обязательный)

1. **Сохрани версию заказчика с правками** из кеша документа (`~/.hermes/cache/documents/doc_*.md`) в `Inbox/` (`cp`). Эта копия — источник правок для архитектора; файл с комментариями и источники больше не трогать.

2. **Свериться с фактами, которые заказчик назвал сам**, прежде чем гнать в архитектора (например реальные имена статусов Jira ANL: Open/In Progress/Closed — заказчик дал ссылку на задачу). Если REST-аутентификация не даёт доступа — не застревать на браузерном логине: зафиксировать факт из слов заказчика и передать архитектору как требование.

3. **Промпт архитектора записать файлом** (`write_file /tmp/...md`, НЕ heredoc): полный путь к файлу с правками; явно попросить прочитать его ЦЕЛИКОМ дав путь (не инлайн содержимое огромного файла); перечислить содержательные замечания, требующие проработки с опорой на мировую практику, и что оставить на развилки.
   Вызов: `invoke-role` (codex CLI, role architect `gpt-6-astra`, `--resume <session_id>`) фоном.

4. **Развилки брифа — по одному, по регламенту.** Для каждой: контекст + нумерованные варианты + рекомендация архитектора с обоснованием из мировой практики (сжато). Рекомендацию ставить первой. После ответа заказчика фиксировать решение короткой строкой и переходить к следующей. Накопленный список решений лучше держать в сообщении.

5. **Финализация архитектором** одной пачкой: собрать все решения развилок в промпт, попросить перезаписать финальный файл, в result вернуть что изменил по каждому пункту. Затем **ревизор**: отдельный `invoke-role` (codex CLI, role reviewer `gpt-6-astra`, read-only) сверить файл против версии с комментариями по пунктам: исполнены ли замечания, внесены ли решения, нет ли непротиворечивости и остатков старой терминологии.

6. **Выложить согласованный итог отдельным файлом в Outbox**, синкануть и ОБЯЗАТЕЛЬНО подтвердить доставку `rclone lsjson owncloud:WorkVault/Outbox/` (подтверждение доставки = размер файла совпал, а не просто `systemctl` exit 0). Только после этого отчитаться.

## Pitfall — извлекать полный результат из process-results, не верить preview

Фоновый `invoke-role` возвращает в `process_manage poll` только хвост (`output_preview` обрезан). Полный текст результата лежит в `~/.hermes/logs/process-results/proc_<session_id>.json`: поле `.output` — это полная JSON-строка агента, искомый текст в её `.result`. Извлекать скриптом файлом (не инлайн):
```python
import json, sys
d = json.load(open(sys.argv[1]))
print(json.loads(d.get("output", "")).get("result", ""))
```
Это дешевле, чем лезть в `store.db`. Сначала пробовать этот путь, потом фолбэки из `codex-cli`. Не полагаться на `output_preview` при подготовке развилок брифа — брать полный `.result`.

## Pitfall — правки заказчика приходят трёх видов, обрабатывать каждый отдельно

Присылаемый файл содержит три способа правок, и архитектору надо явно назвать все:
- **зачёркнутое `~~...~~`** — убрать/заменить (рядом часто стоит его правка-замена);
- **комментарии-пожелания `*(...)*`** в скобках курсивом — это запросы, их ИСПОЛНЯЮТ или выносят в развилку; в итоговый текст скобки не попадают;
- **прямые правки** в тексте — принять как есть.
До передачи проверять самому (search_files по `\*\(` и `~~`), что в финале после архитектора скобок и зачёркиваний не осталось — это контроль исполнения.

## Pitfall — мета-пояснения не попадают в документ

Фразы вида «слова X и Y легко путаются», «это чтобы ты исправил» — это указания заказчика тебе/архитектору для правки, а не норма документа. В финальную редакцию они не попадают. Убирать их же и в исходнике при обработке, и проверять в финале.

## Pitfall — решение по логике документа принимает заказчик

Когда архитектор предлагает вариант решения, который меняет логику (например закрытие вопроса/эпика — кто закрывает), нельзя дефолтить на рекомендацию архитектора. Спрашивать заказчика вариантами. Если заказчик дал ответ, противоречащий рекомендации — фиксировать его решение (даже если архитектор предлагал иначе), затем передать архитектору как принятое.

## Pitfall — термины словаря форматировать единообразно

Заказчик требует: имена сущностей (роли, термины) с большой буквы и, при необходимости, жирным — единообразно по всему документу. Дубли терминов, означающих одно, свести к одному имени. Сленг/сокращения выносить в Словарь до первого упоминания. Проверять в финале поиском, что старой терминологии не осталось.

## Как выглядят «развилки брифа» (формат)

Каждая развилка в сообщении:
- **контекст** — откуда замечание/вопрос и почему он требует решения;
- рекомендация архитектора + обоснование (мировая практика, 1-2 абзаца максимум);
- нумерованные варианты (A/B/C), **рекомендуемый первым**.
На вопрос «что берём» заказчик отвечает буквой и, если надо, дополняет требование — это и есть решение. Обновить накопленный список решений и перейти к следующей развилке.
