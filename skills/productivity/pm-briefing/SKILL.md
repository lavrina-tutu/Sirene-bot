# PM-брифование (Telegram)

## Когда загружать

Саша говорит «брифуемся», «проводим бриф», «закрываем OQ» — по любому инструменту с pm/-структурой в WorkVault.

---

## Формат одного вопроса (ОБЯЗАТЕЛЬНО)

```
## Вопрос N — <ID> / <тема>

<Контекст: 2-3 предложения — почему вопрос важен и что на кону>

**Рекомендация:** <номер> — <одна фраза почему>

1. <вариант>
2. <вариант>
3. <вариант>  (если нужно)
4. <вариант>  (если нужно)
```

### Жёсткие правила формата

- **Варианты ВСЕГДА нумеруются 1-2-3-4** — никогда не через «или» в тексте
- **Рекомендация ВСЕГДА** перед вариантами — одна, конкретная, с обоснованием
- **«.» или «ю»** от Саши = подтверждение рекомендации (не выбор из вариантов)
- **Один вопрос за раз** — не задавать следующий до записи ответа на текущий
- **Никаких вводных абзацев** — сразу заголовок вопроса

---

## Алгоритм сессии

1. Прочитать `pm/OPEN_QUESTIONS.md` и `pm/PM_DECISIONS_LOG.md` перед началом
2. Согласовать повестку (какие OQ закрываем сегодня)
3. Для каждого вопроса:
   - Задать в формате выше
   - Получить ответ Саши
   - **Сразу записать** в нужный файл (не копить)
   - Подтвердить: `Записано ✅ OQ-NNN → answered`
   - Перейти к следующему

---

## Куда записывать

| Тип ответа | Файл | Действие |
|-----------|------|----------|
| Ответ на OQ | `pm/OPEN_QUESTIONS.md` | Заполнить колонку Answer строки OQ-NNN |
| Новое решение PM | `pm/PM_DECISIONS_LOG.md` | Добавить строку PD-NNN в секцию текущей даты |
| Уточнение к существующему PD | `pm/PM_DECISIONS_LOG.md` | Дополнить формулировку или добавить PD-NNN(b) |

### Нумерация PD
Следующий свободный после последнего в `PM_DECISIONS_LOG.md`. Проверять перед записью.

---

## Статусы после записи

- OQ ответ записан → статус `answered`
- PD записан → статус `accepted` (если Саша подтвердил)
- После переноса в ТЗ → `in_tz`

---

## Питфолы

- **Не давать рекомендацию** — нарушение формата, Саша поправит
- **Варианты через «или» в тексте** — нарушение, всегда 1-2-3-4
- **Не записывать сразу после ответа** — накопленные ответы теряются при обрыве
- **Задавать два вопроса сразу** — не делать
- **Предлагать менять ТЗ или код во время брифа** — бриф = только решения в pm/, код после «начинай обработку»
- **Перезаписывать строку PD целиком при добавлении новой** — при patch всегда добавлять новую строку отдельно, не заменять существующую; проверить что обе строки есть после записи
- **Не обновлять BUILD_CHECKLIST** — если OQ-решение меняет формулировку гейта (GATE H4 и др.), обновить и `OPEN_QUESTIONS.md` и `BUILD_CHECKLIST.md` в одном шаге; два файла могут рассинхронизироваться
- **Хранить ревью-материалы в оригинале** — если PM хочет разметить файлы (сигналы, чеклисты) и вернуть, скопировать их в `WorkVault/Inbox/<topic>-YYYY-MM-DD/` командой `cp -r`, оригиналы в `_review/` не трогать; после возврата PM читать из Inbox
- **Не создавать протокол сессии** — после каждого брифа обязательно писать `pm/sessions/YYYY-MM-DD_<topic>.md` с таблицей закрытых OQ/PD
- **Не делать rclone sync после операций с WorkVault** — после любого cp/mv/write в WorkVault (включая создание файлов в Inbox) всегда сразу запускать `rclone sync ~/WorkVault owncloud:WorkVault`; если папка исключена из основного sync (например `Inbox/**`), синкать отдельно: `rclone sync ~/WorkVault/Inbox owncloud:WorkVault/Inbox`
- **Не проверять исключения rclone перед синком в Inbox** — Inbox исключён из основного `rclone sync` через `~/.config/rclone/workvault-exclude.lst`; файлы туда надо синкать отдельной командой
- **Менять ответ OQ без сохранения исходного PD** — при уточнении ранее записанного PD (например, переформулировка) проверить что patch не затирает соседние строки таблицы; после записи убедиться что все строки PD на месте
- **Затирать существующий PD при добавлении нового** — при patch в таблицу PM_DECISIONS_LOG всегда добавлять новую строку рядом с существующей (не заменять). Алгоритм: old_string = строка которая БУДЕТ СОСЕДОМ, new_string = новая строка + сосед. Никогда не делать old=PD-NNN → new=PD-NEW (соседняя строка теряется)
- **Игнорировать запрос PM «подробнее» перед выбором** — если PM просит объяснить детали вопроса (входы, выходы, кейсы), сначала дать развёрнутое пояснение, потом заново предложить варианты 1-2-3-4 с рекомендацией
- **Удалять устаревшие материалы** — если PM решил что данные устарели (например, сигналы Opus после смены подхода), перемещать в `_archive/<topic>-YYYY-MM-DD/` а не удалять насовсем; так сохраняется возможность ретроспективного сравнения
- **Задавать вопрос по ТЗ без чтения ТЗ** — если вопрос требует знания текущего состояния ТЗ (что там написано про риски, blockers и т.д.), сначала прочитать нужный модуль ТЗ (`modules/TZ_*.md`), потом задавать вопрос с реальным контекстом — иначе варианты могут не учитывать то что уже есть
- **Не создавать cursor-handoff когда изменений много** — если за сессию накопилось 5+ новых PD или крупные архитектурные решения, создать отдельный файл `pm/sessions/YYYY-MM-DD_cursor-handoff.md` со структурированной сводкой «что изменилось / что не менялось / следующие шаги для Cursor»; не полагаться только на PM_DECISIONS_LOG
- **Не останавливаться когда PM пишет «стоп»** — если PM написал «стоп», немедленно прекратить ввод, написать только «Стоп, жду.» и ждать следующего сообщения молча
- **Не обновлять cursor-handoff при новых PD в той же сессии** — если cursor-handoff создан в середине сессии и после него появились новые PD, обновить handoff через patch до закрытия брифа; не оставлять handoff с неполным списком решений
- **Молча обновлять PD без указания на конфликт** — если новое решение (например, «Opus deprecated») противоречит уже записанному ранее PD (например, «Opus для bootstrap»), явно указать на конфликт и обновить оба: старый PD пометить superseded или скорректировать формулировку, новый PD зафиксировать с явной ссылкой на то что он заменяет
- **Принимать рекомендацию Cursor за истину** — если Cursor присылает ТЗ-анализ с конфликтами (cursor-tz-analysis.md), его рекомендации = варианты для PM, а не готовые решения; задавать вопрос по каждому конфликту в формате брифа 1-2-3-4; PM может выбрать «иначе» и настоять на своём (вариант 3 = «сделать как сказал»); записывать именно решение PM, а не рекомендацию Cursor
- **Не создавать отдельные вопросы по каждому разделу cursor-анализа автоматически** — сначала предложить PM повестку (какие конфликты/вопросы разбираем), потом идти поштучно; курсор может поднять 4 конфликта + 9 вопросов, но PM решает приоритет
- **Игнорировать «записывай ответы так чтобы передать в курсор»** — это напоминание что каждый ответ надо фиксировать в pm/ сразу после получения; не ждать конца сессии; конкретно: создать PD запись в PM_DECISIONS_LOG после каждого ответа PM, не после блока вопросов
- **Не читать ТЗ перед вопросом о текущем состоянии блока** — если PM спрашивает «что в ТЗ про X», прочитать нужный модуль (`modules/TZ_*.md`) сначала, потом отвечать; не угадывать и не опираться на память из более ранних частей разговора
- **Задавать вопрос PM как «или» вместо 1-2-3-4** — даже когда вариантов два, всегда нумеровать их 1. / 2. / ; никогда не писать «нужно A или B?» в тексте вопроса
- **Писать рекомендацию после вариантов** — рекомендация всегда ПЕРЕД списком вариантов, не после; формат: сначала контекст, потом «Рекомендация: N — обоснование», потом нумерованный список
- **Не обновлять cursor-handoff при закрытии брифа через Cursor-анализ** — если во второй части брифа PM отвечал на вопросы cursor-tz-analysis.md (конфликты C1-C4, вопросы Q1-Q9), обновить cursor-handoff дополнительными PD перед закрытием или создать отдельный файл `pm/sessions/YYYY-MM-DD_cursor-responses.md`

---

## Режим «для Cursor»

Бриф в Telegram удобен для PM, но **весь результат должен оседать в `pm/`** так, чтобы Cursor мог забрать без дополнительной передачи:

- Каждый ответ → сразу в `OPEN_QUESTIONS.md` или `PM_DECISIONS_LOG.md`
- В конце сессии → создать протокол `pm/sessions/YYYY-MM-DD_<topic>.md`
- Cursor читает `pm/` целиком и идёт в реализацию по команде «начинай обработку»

---

## Завершение сессии

После всех вопросов — краткий итог:

```
## Итог брифа YYYY-MM-DD
- OQ закрыто: OQ-001, OQ-003, OQ-004, OQ-005
- PD добавлено: PD-026
- Следующий шаг: [что делать дальше]
```

Cursor заберёт всё из `pm/` — дополнительной передачи не нужно.
