# Модуль H. Синки (Multisync / «Площадка»)

## Назначение
Обработать встречи типа `multisync` — командные синки на 3+ участников, где регулярно собирается группа (примеры: «Синк АиД», «DataTalks», «Гильдия», «Ежемесячный продуктовый синк»). Модуль ведёт идентичность самого синка как регулярной площадки: участники, повестка, решения и задачи **уровня синка** (организационные, без привязки к проекту).

⚠️ **Граница (C2):** Per-project сигналы со встречи синка H **не** обрабатывает. Их доставляет F.Дирижёр напрямую в D.База с тегом `source_sync=<slug>` — на основании `scope=project` в `MeetingSignals` от C.Добытчик. Связки H→D нет. H работает только с артефактами `Syncs/<slug>/`.

## Карточка модуля

🎯 **Функция:** Из встречи типа `multisync` извлечь повестку, решения и задачи **уровня синка**, обновить карточку синка в `Syncs/<slug>/`.
⬅️ **Вход:** `MeetingSignals` от C.Добытчик (только сигналы со `scope=sync`) + маршрут от B.Роутер (`route: "multisync"`) + список участников.
➡️ **Выход:** обновлённые артефакты `Syncs/<slug>/` (карточка, decisions, action_items, протоколы встреч). Per-project проброс — задача F (см. C2).
🔗 **Зависимости:** A.Сборщик (данные), B.Роутер (маршрут + slug синка через алиасы), C.Добытчик (сигналы scope=sync), **E.Люди (резолв участников через AnywhereContacts: `resolve_name()` + `add_alias()`)**.
📋 **Статус:** ✅ закрыт.

## Архитектура артефактов

Папка `Syncs/<slug>/` — зеркало `Projects/<slug>/` и `People/<имя>/`, но с фокусом на «площадку».

| Файл | Аналог в Projects/ | Аналог в People/ | Содержание |
|---|---|---|---|
| `card.md` | `card.md` | `card.md` | Точка входа карточки синка — frontmatter + навигация + dataviewjs-секции. |
| `decisions.md` | `decisions.md` | `agreements.md` | Решения уровня синка — то, что приняли всей командой на площадке (не привязано к одному проекту). Append-only. |
| `action_items.md` | `action_items.md` | `commitments.md` | Организационные задачи уровня синка (без привязки к проекту) с ID `^{slug3}{hex}` (PD-057). Выполнение = `[x]`; правка — `### PM Notes (tasks)`. |
| `meetings/<дата>.md` | `snapshots/` | `meetings/<дата>.md` | Протокол каждой встречи синка — инкремент. Содержит: участники, решения, задачи, упомянутые проекты со ссылками `[[Entities/<slug>]]`. |
| `meetings.md` | `meetings.md` | `meetings.md` | Авто-индекс протоколов встреч синка. |
| `snapshots/` | — | — | Генерируется G.Срез: `{slug}-snapshot-YYYY-MM-DD.md` после каждой встречи синка. Не редактировать вручную. |
| `projects_touched.md` | — | — | Индекс «синк ↔ проекты»: какие проекты в каких встречах упоминались. Двусторонний линк с `Projects/<slug>/card.md → mentioned_in_syncs`. |

`agenda.md` — **исключён** (повестка как отдельный мутируемый файл не ведётся; конкретная повестка живёт в `meetings/<дата>.md`).

Механика PM Notes — общая с D.База и E.Люди: блоки `### PM Notes (tasks|decisions|risks)` после соответствующих секций (Q-C2/PD-056). Маппинг синка: action_items → `tasks`, решения → `decisions`, риски → `risks`. LLM читает прошлые PM Notes как контекст при следующей генерации. Append-only поток → `pm_locked` не нужен (по аналогии с E.Люди, В5/В3).

## Архитектура карточки `Syncs/{slug}/card.md`

### YAML frontmatter

```yaml
entity: sync
slug: sync-aid
title: "Синк АиД"
core_members: ["kkrivorotov", "okotelnikova"]
projects: ["antibot", "adm"]
last_meeting: 2026-06-17
meetings_count: 23
last_processed_at: 2026-06-19
```

Поля, которых **нет** во frontmatter v1:

- `relation` — не требуется.
- `projects_touched` — переименован в `projects` (массив slug-ов затронутых проектов).

### Секции тела (порядок)

1. **☑️ Открытые action items** — dataviewjs, сборка из `Syncs/{slug}/action_items.md` по статусу `open`.
2. **🔗 Затронутые проекты** — dataviewjs, сборка из `meetings/<дата>.md` + поле `projects` (через `Projects/*/card.md` где `contains(mentioned_in_syncs, this.slug)`).
3. **👥 Участники** — dataviewjs из `meetings/<дата>.md` (S2 ∪ S3: speaker labels + action item owners из FF), нормализация имён через AC/E.Люди. **Exchange-интеграция (календарные приглашения) → Фаза 2.**
4. **Навигация** в конце карточки:
   `☑️ [[Syncs/{slug}/action_items]] · 🤝 [[Syncs/{slug}/decisions]] · 🔗 [[Syncs/{slug}/projects_touched]] · 📅 [[Syncs/{slug}/meetings]]`

Секции **исключены**:
- ~~🎯 Назначение площадки~~ — в MVP не ведём.
- ~~📋 Повестка~~ — и подкарточка `agenda.md` тоже убрана.

### PM Notes

После каждой секции — блок `### PM Notes (tasks|decisions|risks)` (единый формат, Q-C2/PD-056, см. TZ_G §5). Маппинг синка: action_items → `tasks`, решения → `decisions`, риски → `risks`. **Сквозного PM Notes блока нет.**

### Резолв участников для Syncs

H.Синки при обработке каждой встречи извлекает участников из S2 ∪ S3:
- **S2** — speaker labels из FF transcript;
- **S3** — owners action items из FF.

Имена нормализуются через **AC / E.Люди** (`resolve_name()` с каскадом email → fio → alias → token_subset → fuzzy 0.85). Поле `**Участники:**` в FF ненадёжно (~50% встреч содержат только организатора) — не используем как единственный источник. **Exchange/календарь** как источник состава встречи → Фаза 2.

## Система алиасов

У синка, как и у проекта, есть множество способов написания: «Синк АиД», «АиД синк», «AID sync», «DataTalks», «Дата-токс», «Гильдия PM» и т.п. Чтобы B.Роутер мог отнести встречу к нужному `<slug>` синка, нужна аналогичная проектам система алиасов.

### Где хранятся
Отдельный файл `syncs_memory.json` рядом с `classification_memory.json` (та же папка/механика, что у B.Роутер). Структура — зеркало `projects[slug].aliases`:

```json
{
  "syncs": {
    "sync-aid": {
      "title": "Синк АиД",
      "aliases": [
        {"text": "Синк АиД", "source": "bootstrap", "status": "confirmed", "matches": 23},
        {"text": "AID sync", "source": "pm_manual", "status": "confirmed", "matches": 4}
      ],
      "negative_keywords": [],
      "projects_touched": ["metroteka", "adm"]
    }
  }
}
```

### Источники алиасов
1. **Bootstrap** — предзаполненные карточки регулярных синков (`data-talks`, `sync-aid` — см. ВОП-4) + ручные PM-команды для добавления новых синков и алиасов. Автоматический скан FF-summary **не делаем** (согласовано с В5: PM создаёт синки явно через TG). PM подтверждает алиасы батчем.
2. **Авто-обучение** — при подтверждённом матче встречи на синк, B.Роутер извлекает варианты написания из title и складывает в `syncs_memory.json` (source: `auto`, status: `pending`).
3. **PM-ручное** — TG-команды (см. ниже), source: `pm_manual`, status: `confirmed`.

### TG-команды управления алиасами синков

Полный аналог 4 команд B.Роутер для алиасов проектов, но в неймспейсе «синк»:

1. **Переназначение встречи на синк**
   `встреча [название/id] → синк [slug]`
   *Пример:* `встреча "Дата-токс 2026-06-12" → синк data-talks`
   *Алгоритм:* fuzzy-поиск встречи → обновить route+sync_slug → извлечь алиас из title → дописать в `syncs_memory.json` (source: pm_manual, confirmed) → перегенерировать `Syncs/<slug>/meetings/<дата>.md`.

2. **Блокировка алиаса синка**
   `алиас синка [текст] не относится к [slug]`
   *Пример:* `алиас синка "гильдия" не относится к sync-aid`
   *Алгоритм:* status=blocked → пересчитать классификацию затронутых встреч → ответ «🚫 Алиас синка заблокирован, пересмотрено N встреч».

3. **Просмотр алиасов синка**
   `алиасы синка [slug]`
   *Формат ответа* — зеркало команды `алиасы [slug]` из B.Роутер (активные/заблокированные/негативы + счётчик встреч + затронутые проекты).

4. **Удаление алиаса синка**
   `удали алиас синка [текст] из [slug]`
   *Алгоритм:* soft-delete (status=deleted, deleted_at=now), физически не удаляем → восстановление командой `восстанови алиас синка [текст] в [slug]`.

Симметрия с B.Роутер (алиасы проектов) и E.Люди (алиасы контактов) — три неймспейса (`проект` / `контакт` / `синк`), один и тот же набор операций.

### Формат slug
Латиница, kebab-case, по тем же правилам, что у проектов: `sync-aid`, `data-talks`, `guild-pm`, `monthly-product`. Slug фиксируется при первом подтверждении синка PM-ом и не меняется автоматически.

## Открытые вопросы

**В1 — Граница «multisync» vs «project»:** ✅ **Закрыто 2026-06-19, обновлено 2026-06-19 (C1):** Маршрут `multisync` определяется B.Роутером (приоритет: матч на `syncs_memory.json` или regex `Sync|Standup|Гильдия|DataTalks|Weekly|Синк` — первичен; структурный fallback при 3+ участников + 2+ алиасов проектов — вторичен). Полная спецификация — `TZ_B_classification.md`. Правило «3+ участников → всегда multisync» снято: 3+ участников + ровно 1 проект → `project`. H.Синки обрабатывает встречи с `route=multisync`.

**В2 — Per-project проброс в D.База:** ✅ **Закрыто 2026-06-19, обновлено (C2):** Все сигналы со `scope=project` из `MeetingSignals` уходят в D.База с полем `source_sync: <slug>`. Проброс выполняет **F.Дирижёр** (fan_out по scope), не H.Синки. `source_sync` заполняет код-обёртка C на основании `B.route=multisync` + `B.sync_slug` (см. TZ_C_extractors).

**В3 — `action_items` уровня синка vs уровня проекта:** ✅ **Закрыто 2026-06-19** — Вариант А: по принципу владельца. Задача по конкретному проекту → только в `Projects/<slug>/action_items.md` (через D.База проброс с `source_sync`). В `Syncs/<slug>/action_items.md` — только организационные задачи синка без привязки к проекту.

**В4 — Регулярность и «мёртвые» синки:** ✅ **Закрыто 2026-06-19** — Вариант В: не отслеживаем регулярность автоматически. `card.md` содержит `last_meeting` — PM сам видит когда последний раз собирались. Dormant-логика не нужна. Поле `cadence` — **информационное поле карточки синка (не используется алгоритмически)**; остаётся в шаблоне как справочная метка для PM.

**В5 — Bootstrap-скан и порог создания синка:** ✅ **Закрыто 2026-06-19** — Вариант Б: PM создаёт синки вручную через TG-команду `создай синк [название] slug [slug]`. Bootstrap-скан не делаем. Начинаем с известных ~5–7 синков, система обучается через алиасы по мере использования.
