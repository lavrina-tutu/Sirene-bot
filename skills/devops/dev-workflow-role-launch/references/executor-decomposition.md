# Деление больших инвоков и подготовка lab-прогонов (codex-исполнитель)

Применяется, когда роль-исполнитель (codex, gpt-6.1-terra и т.п.) вызывается на
промпте, который описывает многошаговую программу: proof-программа из 5–9 проб,
полный компрессорный invoke, ErrorBus из нескольких групп. Механика идёт через
`codex exec -C <поезд> -m <модель> -c 'model_reasoning_effort="high"'
--skip-git-repo-check --json --sandbox danger-full-access -- "$(cat <prompt>)"
> <лог> 2>&1`, фоново с notify_on_complete.

## Главная ловушка: исполнитель останавливается на подготовке

Повторявшийся паттерн (B2, ErrorBus, B3, W1-09): при большом объёме исполнитель за
один инвок делает только preflight/диагностику (загружает среду, проверяет pinned
versions, пишет hashes, иногда правит один тест) и возвращает NOT_PROVEN/NOT_RUN,
не решив основную задачу. Это не дефект ядра и не fake — это несоответствие размера
программы одному прогону. Не повторять вслепую тот же промпт ещё раз: результат тот же.

## Правило деления

Делать НЕСКОЛЬКО узких инвоков, каждый решает ровно одну вещь за один проход:

1. Одна проба proof-программы (B3-01 отдельно, B3-02 отдельно…), либо одна кодовую
   функцию/один файл (coder-шаг «Coding-1»), либо одна группа ErrorBus.
2. В промпте явно: «На этот инвок возложена ТОЛЬКО проба X. Не разворачивай другие.»
3. Перед повторным инвоком зафиксировать в отчёте, что конкретно ожидается по oracle
   (PASS/FAIL/NOT_PROVEN, не «похоже на подготовку»).
4. Если предыдущий шаг уже доказал подмножество (например, harness работает, 429
   доставлен) — ВТОРОЙ промпт прямо говорит «это уже доказано, не переделывай,
   доведи только недостающее», иначе исполнитель тратит проход на повторение.

## Переиспользовать существующий harness, не строить с нуля

В кандидате обычно уже есть рабочий managed harness, подтверждённый зелёными
тестами (fixtures: board/cli-stub/worker/RunBoundary/journal). Давать инструкцию
«построй свой harness» — путь к срезу. Вместо этого:

- назвать конкретные готовые fixtures и настоящие API (invoke_once, RunBoundary,
  InvocationJournal, publish_compressor_response и т.п.);
- велеть реюзить их, а не переписывать; правки — только точные spans;
- после правки — прогон существующего теста (например `pytest .../tests/test_kanban_compressor.py -q`),
  не «создай новые тесты с нуля»;
- единый полностью зелёный прогон обязателен: «115 passed + 14 setup errors» не равно
  готово, даже если повтор раздельно даёт 14 passed (release-фикстуре нужен /tmp вне
  checkout — см. ниже).

## Вложенный bwrap внутри codex-sandbox — запрещён

Исполнитель уже бежит внутри изоляции (root read-only, отдельный /tmp, env -i).
Дополнительный вложенный `bwrap` внутри инвока падает:
`setting up uid map: Read-only file system` (rc 1), и до cli-stub дело не доходит.
Правило: изоляцию даёт внешняя обёртка инвока; внутри инвока не вложится bwrap,
fault-ввод — через cli-stub/loopback на уровне самого процесса.

## Capability-стаб vs готовый путь (proof-blocker)

Если resolver/caller содержит безусловный `return ResolvedInvocation(None, None, None,
"... W1-NN dependency ...")` — доказать oracle физически невозможно до реализации той
ветки: инвок застревает на local-error ДО транспорта, счётчик запросов = 0 (NOT_MEASURED,
не ноль). Это законная причина переставить порядок (сначала реализация зависимости,
потом proof), а не повторять proof. Также отличать честный FAIL/SETUP (доказанное
отсутствие capability на pinned-версии) от NOT_PROVEN (недостаточно evidence) — при
исправном стенде PASS только по полному oracle, не по «1 passed диагностического
скрипта» или по факту загрузки среды.

## Не перезаписывать evidence между инвоками

Новый шаг пишет в НОВЫЙ каталог runtime (например `runtime/e07-step1-v4`, очередной
`e02-*-vN`), не затирая прежний; hashes добавлять (bump версию), не удаляя старые.
Параллельные инвоки (W1-09 и ErrorBus-шаг ②) должны работать на НЕПЕРЕСЕКАЮЩИХСЯ
lab-корнях/write-сетах — иначе гонка за общий временный каталог ломает оба.
