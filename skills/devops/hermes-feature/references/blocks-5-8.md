## Блок 5: Бэкапы и откат

### Когда создаётся
- Opus-задачи: всегда.
- Sonnet-задачи: только если затронут `config.yaml` или `jobs.json`.

### Состав
`config.yaml` + `jobs.json` + `skills/` + `MEMORY.md` + `USER.md` + файлы специфичные для задачи.

### Путь
Linux VM: `~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`.
Для бэкапов отдельных компонентов (unit-файлы, `rclone.conf` и т.п.) — рядом с файлом: `<file>.bak-<purpose>-YYYYMMDD-HHMMSS`.

### Хранение
2 недели, 1 бэкап в день (самый ранний). Self-check чистит автоматически.

### Откат
- **Авария** → Opus откатывает сам немедленно, сообщает Саше.
- **Плановый** → Opus предлагает какой бэкап, ждёт ОК.

## Блок 5Б: Классификация разрешающего сигнала перед side-effect-действием (обязательно)

**Триггер:** любой вызов `write_file`/`patch` на файлы вне `~/.hermes/_Archives/`, любой `cronjob(action='create'|'run')` с реальными side-effects, любой `terminal` с `curl -X POST|PUT|DELETE` к внешним API (Confluence/JIRA/Anywhere/EWS), любой `patch` на файлы в `WorkVault/Hermes-Backlog/TZ/**`.

| Категория | Определение | Разрешает действовать? |
|---|---|---|
| `direct-imperative` | В последнем сообщении Саши есть глагол-императив, ссылающийся именно на это действие: «обнови», «запусти», «делай», «фиксируй», «давай», «поставь», «удали» | ✅ Да |
| `continuation-of-approved-plan` | Действие — явный пункт из согласованного пофайлового плана Opus (Блок 1А), Саша сказал «берём в работу» по этому плану, действие соответствует одному из перечисленных шагов плана дословно | ✅ Да |
| `question-answer` | Саша задал информационный вопрос (где/как/почему/можно ли/что если), модель ответила — само действие «зафиксировать ответ в файле» Сашей не запрошено | ❌ Нет |
| `own-inference` | Модель логически вывела, что «раз X, значит нужно Y» — без явной команды от Саши | ❌ Нет |
| `conditional` | Саша дал условную команду «если X — делай Y», истинность X оценивает сама модель | ❌ Нет |

Если категория ❌ — отдельный turn БЕЗ side-effect-инструментов, текстовый вопрос Саше.

Самореференциальный запрет: факт, созданный самой моделью в этой же сессии предыдущим tool call-ом, НЕ является доказательством истинности условия для последующего действия.

3. Повторить (максимум 3 попытки).
4. Все ✅ → короткий отчёт. Остались ❌ после 3 попыток → откат + доклад.

## Блок 6Б: Делегирование субагентов

### Критерий выбора модели

| Задача | Модель |
|---|---|
| Собрать факты: grep, git, конфиги, списки кронов | **Haiku 4-5** |
| Читать одно ТЗ, понять архитектуру, сформулировать рекомендацию — в рамках одного инструмента | **Sonnet-5** |
| Читать несколько ТЗ, интеграционные вопросы, связи между инструментами, новый инструмент | **Opus 4-7** |

**Короткое правило:** Haiku собирает данные → Sonnet-5 анализирует в рамках одного инструмента → Opus решает интеграционные и многоинструментальные задачи.

### Инструмент запуска

**Правило против хардкода:**
- **Sonnet-задачи — НЕ передавать `model` вообще.** Sonnet это всегда текущий основной провайдер/модель Hermes (`model.default`/`delegation.model` в `config.yaml`) — эти два поля синхронно обновляются скриптами переключения (`switch_to_sonnet5.sh`, `user_change_delegation_models1.sh`). Если не указывать `model` в `cronjob`/`delegate_task`, система сама берёт актуальное значение — не нужно править скилл при каждом переключении профиля.
- **Opus/Haiku — модель передавать явно** (они намеренно НЕ основная модель), но БЕЗ `provider` (см. Pitfall 23 — провайдер система подставит сама). Конкретные ID и `reasoning`-уровни берём из текущей таблицы ниже; если модель/режим поменяются, обновлять таблицу вручную и перепроверять перед использованием.

| Задача | Модель (параметр `model`) | Инструмент | Таймаут |
|---|---|---|---|
| Opus: ТЗ / пофайловый план | {"model": "deepseek/deepseek-v4-pro", "reasoning": "high"} (без provider) | `cronjob(repeat=1)` | — |
| Opus: сложная реализация (fallback) | {"model": "deepseek/deepseek-v4-pro", "reasoning": "high"} (без provider) | `cronjob(repeat=1)` | — |
| Opus: инфраструктурный анализ | {"model": "deepseek/deepseek-v4-pro", "reasoning": "high"} (без provider) | `cronjob(repeat=1)` | — |
| Sonnet: реализация по плану (>5 мин или многофайловая) | **не передавать** `model` — наследует текущий default | `cronjob(repeat=1)` | — |
| Sonnet: короткая задача (<5 мин) | **не передавать** `model` — наследует `delegation.*` | `delegate_task` | 300с |
| Haiku: справочный / терминальный запрос | {"model": "deepseek/deepseek-v4-pro", "reasoning": "low"} (без provider) | `delegate_task` | 120с |

**Никогда не использовать `delegate_task` с Opus** — reasoning_effort=high держит родительский стрим → gateway-зависания ("Stream stale for 180s"). Всегда `cronjob(repeat=1)`.

### Toolsets в кронах (сокращают контекст субагента)

| Задача | enabled_toolsets |
|---|---|
| Opus: ТЗ / план (читает файлы, не запускает код) | `["file", "terminal"]` |
| Sonnet: реализация кода | `["file", "terminal"]` |
| Sonnet: тестирование | `["file", "terminal"]` |
| Исследование / аудит с web | `["file", "terminal", "web"]` |

Не добавлять `web` если не нужен — каждый лишний toolset увеличивает контекст сессии.

### Что обязательно передавать в промпт субагента

1. **Роль и среда** — «Ты Opus/Sonnet на VM hermes-agents.devel.tutu.ru»
2. **Точные абсолютные пути** — `/home/tkachenkoav/...`, не `~/...` (в кронах `~` может не резолвиться предсказуемо)
3. **Полный контент ТЗ или плана** — не ссылку на файл, а текст; субагент не должен делать дополнительные lookup'ы
4. **Граница автономности** — явное правило: «механическое (форматирование, перенос, дозаполнение) — делай сам; семантическое (удаление блока, изменение архитектуры) — СТОП, опиши причину»
5. **Формат отчёта** — «не выводить полный текст файлов, только сводку изменений»
6. **Явные запреты** для безопасности — «не удалять contacts.enc и .env», «не менять security-параметры config.yaml»

### Чего НЕ нужно передавать — и важное уточнение про память (проверено по коду 08.07.2026)

**НЕ дублировать в промпте:** SOUL.md, системный промпт Hermes. Cron-сессии всегда грузят `SOUL.md` (`load_soul_identity=True`) — идентичность агента субагент получает автоматически.

**НО: cron-сессии НЕ получают MEMORY и USER PROFILE вообще.** Проверено по коду (`cron/scheduler.py`, флаг `skip_memory=True` с комментарием «Cron system prompts would corrupt user representations») — это намеренное архитектурное решение Hermes, не баг и не то, что можно включить конфигом. Субагент через `cronjob` не видит ни одной записи из MEMORY/USER PROFILE, даже если они содержат критичный для задачи факт (например текущий активный провайдер или правило про формат имён файлов WorkVault).

**Практическое следствие:** если факт из MEMORY/USER PROFILE нужен субагенту для корректного выполнения — **передавать его явно в промпте**, не полагаться, что «он и так знает». Особенно критично для: текущего активного провайдера/модели, стабильных конвенций именования (например «латиница-only в WorkVault»), организационных фактов (кто есть кто), правил из этого самого скилла (`hermes-feature`), если задача их использует. Секции `## Контекст и уже принятые решения` в промптах установочных планов (см. пример `QMD-Search`) — это правильный паттерн именно по этой причине.

`delegate_task`-субагенты (не cron) — эта проблема не подтверждена по коду отдельно, безопаснее считать то же правило действующим по умолчанию, пока не проверено обратное.

Шаблоны контекста субагента для профиля `tz-dev`: `~/.hermes/profiles/tz-dev/skills/devops/tz-workflow/references/subagent-context.md`. Фильтровать MEMORY по scope-тегам (`[impl]` / `[tz]` / `[coord]` / `[all]`).

### Бэкап перед запуском субагента

Sonnet-задачи: бэкап если затронуты `config.yaml` / `jobs.json`.
Opus-задачи: бэкап всегда (`~/.hermes/_Archives/hermes-backup-YYYYMMDD-HHMMSS/`).

## Блок 6В: Диагностика перед починкой — обязательный паттерн

Когда Саша говорит «что-то не работает» / «не заполняется» / «поиск не работает»: **не чинить сразу**. Правильный порядок:

1. **Opus-крон только на диагностику** (`enabled_toolsets: ["file", "terminal"]`, явный запрет «только читай, никаких правок файлов») → собирает реальные данные командами, выявляет root cause, предлагает план П.1…П.N с приоритетами и критериями приёмки.
2. **Саша просматривает план**, при необходимости корректирует.
3. **Sonnet-крон реализует** по плану Opus — пункт за пунктом, тесты после каждого.

Opus сохраняет план в `_fix_plan_YYYYMMDD.md` рядом с инструментом → удалить после выполнения всех пунктов.

**Почему важно:** без диагностики Sonnet может починить симптом, не причину. Прецедент 22.07.2026 (MOFS contacts = []): очевидная причина — «нет раздела Участники». Opus-диагностика выявила 4 отдельные проблемы (namespace-package, plain-text заголовки, стоп-лист, хук) — каждая с отдельным фиксом, и каждая не была бы найдена без сбора данных по реальным файлам.

## Блок 7: Диагностика и отладка

**Общий метод:** см. скилл `systematic-debugging` (4 фазы: root cause → pattern → hypothesis → fix).

**Наша специфика:**
- Модель: Sonnet-5 (не Haiku, не Opus — если не нужна архитектурная правка).
- Мелкий баг (≤2 файла, очевидная причина) → Sonnet чинит сама (1 попытка).
- Крупный/архитектурный баг → Sonnet стопится → Саша решает запускать ли Opus → Sonnet применяет план.
- Системный блокер (пакеты, sudo) → Сирень выносит вопрос Саше напрямую (не Opus).
- Эскалация к Opus: root cause в архитектуре, не воспроизвелось за 2 попытки.
- Эскалация к Саше: данные могут быть повреждены, production down.

**Hermes-специфичные питфоллы отладки:**
- `routing:` в `config.yaml` — мёртвая секция, код не читает.
- `hermes skills list` не видит скилл — проверить `version` и `author` в frontmatter.
- `cronjob(action='update')` не сбрасывает `no_agent` — менять в `jobs.json` напрямую.

## Блок 7А: Двухэтапный Opus-анализ перед изменением конфигурации

Применять при: изменение systemd-юнитов, rclone-конфигов, синхронизации, инфраструктурных настроек.

**Паттерн:**
1. **Opus-крон №1** — только читает файлы, оценивает риски, **строит план реализации**, даёт рекомендации.
2. Sonnet пересказывает результат Саше, получает подтверждение.
3. **Sonnet-5-крон №2** — реализует по согласованному плану Opus.

**Почему не сразу реализовывать:** инфраструктурные изменения (systemd, rclone, cron) могут иметь неочевидные риски (race condition, `--size-only` пропускает изменения). Opus может найти питфоллы, которые меняют план.

**Формат промпта для анализа:** «оцени риски → вывод (безопасно/требует доработки/не рекомендую) → ТЗ если применимо».

## Блок 8: Исследования и анализ (hermes-research)

Применять при: нужно собрать данные, найти паттерн, оценить варианты — **без изменений кода**.
Триггеры: *«проанализируй», «исследуй», «найди», «посчитай», «сравни», «что если»*.
**Модель — по критерию из Блока 6Б:** Haiku собирает данные (grep, конфиги, git), Sonnet-5 анализирует в рамках одного инструмента, Opus — интеграционные вопросы и несколько инструментов.

**Алгоритм:** Scope → Сбор (`session_search` 1-3 слова FTS5, параллельные запросы; файлы через grep; API только чтение) → Анализ (таблица, выводы отдельно) → Рекомендации (2-3 варианта с оценкой).

**НЕ делать:** не менять код/конфиги/скиллы, не делать выводы без данных, не запускать API без ОК Саши.
