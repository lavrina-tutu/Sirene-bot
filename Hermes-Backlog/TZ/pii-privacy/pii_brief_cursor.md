# Бриф на проработку: PII-защита вывода перс. данных контактов

## Дата
2026-08-27

## Контекст
Личный помощник Сирень (Hermes) ищет контакты в базе `contacts.enc` (инструмент AnywhereContacts) и выводит результат в Telegram. Сейчас в выдачу попадают ПОЛНЫЕ перс. данные сотрудников: email, username в Loop/Mattermost, должность, департамент, статус активности. Эти же данные попадают в контекст LLM и оседают в архивах сессий/памяти/кронах.

## Проблема
Персональные данные сотрудников (email, телефоны, usernames, личные поля) НЕ должны:
1. выводиться на экран (Telegram) в полном виде без необходимости;
2. храниться в контексте агента, архивах сессий, памяти, кронах, бэкапах.

## Архитектурная база
- База: `~/WorkVault/Contacts/contacts.enc` (AES-256-GCM, схема v2).
- Инструмент: AnywhereContacts Python-пакет (`~/USERTOOLS/AnywhereContacts/`).
  - Схема контакта: `{login, fio, display_name, department, team, position, is_room, active, sources{email...}, aliases, messenger_ids{telegram: @user}, notes}`.
  - В пакете УЖЕ ЕСТЬ выделяющийся механизм маскирования для логов: `logger.py` → `mask_pii()`, `PII_MASKERS`, `SyncLogger, create_logger`. Он используется только для логов синка, НЕ для выдачи на экран.
- Вывод в чат делает сам Сирёдь (LLM) — она видит весь контакт в контексте и печатает все поля.

## Задача проработки (read-only, НИЧЕГО не менять)
1. Найти все места, где контакты из `contacts.enc` попадают в контекст и/или выводятся наружу: CLI, скрипты, крон-логи, session-архивы, память (MEMORY), WorkVault. Куда именно текут раскрытые перс. данные.
2. Выделить чувствительные поля (email, мессенджер-юзернеймы, внутр логины, должность/департамент при открытой выдаче, notes).
3. Предложить 2–3 варианта решения с оценкой трейдоффов:
   - (а) маскирование на экране (выдавать имя+должность, email/телефон/юзернейм — только по явному запросу, свернуто);
   - (б) не класть полные перс. данные в контекст — от Human-friendly отображение: в контекст текст кидаем редсект только понадобившихся полей, остальное прятать;
   - (в) гибрид (маскирование на экране + запрет на запись полных перс.данных в память/архивы/кроны).
4. Указать конкретные файлы/модули/скиллы для правки и место для новой логики отображения (лучше всего — выделенная функция/скилл показа CONTACT, а не всякий раз печатать всё по черновому).

## Формат отчёта
Структурированный: найденные утечки (места) → чувствительные поля → варианты с трейдаффами → рекомендация → пофайловый план правки (без выполнения). Реализация пойдёт отдельным этапом после согласования с владельцем. Ничего не изменять, только чтение.
