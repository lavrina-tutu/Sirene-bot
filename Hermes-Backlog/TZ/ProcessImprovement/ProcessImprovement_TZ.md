# ProcessImprovement — доработка процесса разработки

## Назначение
Устранить выявленные 07.09.2026 нестыковки в процессе разработки скиллов через канбан (диспатч/HITL/LLM-расход), чтобы работа шла быстрее, качественнее и с меньшим расходом токенов. Изменяются ТЕКСТЫ скиллов и ТЗ, НЕ ядро канбана (по DevKanbanPipeline).

## Целевая модель процесса (формулировка Саши, 07.09)
Полное описание: `appendix_process-model_20260907.md`. Кратко:
1. Материал из сессии ТГ (с нужными ТЗ) → в Курсор → архитектору.
2. **Архитектор** готовит вопросы: каждому 2–3 варианта ответа + рекомендацию. Возвращает в чат Hermes.
3. **Базовая модель = оркестратор**: показывает Саше вопросы поштучно с вариантами и рекомендациями архитектора (строго, ничего сама не придумывает). Каждый вопрос+ответ сразу в **расширение ТЗ**.
4. После ответов на все вопросы → **архитектору на доработку ТЗ**. Новые вопросы → цикл. Итог: готовое ТЗ + вся переписка (в расширении ТЗ).
5. **Ревизор** (другая LLM через Курсор) — заточен на поиск слабых мест. Знает переписку и экосистему. Задаёт каверзные вопросы архитектору (через оркестратора), решает с ним в цикле. Итог: проверенное ТЗ.
5.1. **Ревизор опционален** (режим без ревизора): для простых/быстрых задач можно пропустить шаги ревизора и идти сразу: бриф → ТЗ → план → hermes feature (быстрый путь, меньше токенов). По умолчанию ревизор включён; отключение — по решению Саши для простых задач.
6. Архитектор создаёт **пофайловый план реализации и тестирования** (вкл. интеграционное).
7. **Ревизор проверяет план** (те же вводные; опционально, как п.5.1). По согласованию → **«золотой план»**.
8. По «золотому плану» — **hermes feature**.

**Модели (решение Саши 07.09):**
- **Архитектор:** `cursor-grok-4.6-high` (в Cursor-подписке, текущая).
- **Ревизор:** `claude-sonnet-5-medium` (в Cursor-пуле, сильнее и дороже grok-high — принято, что дороже допустимо ради адекватности поиска слабых мест).
- **Режим без ревизора:** предусмотрен (быстрый путь, меньше токенов) — по решению Саши для простых задач.

**Влияние на блоки:** целевая модель по сути определяет, как должны работать Блок 0 (бриф через оркестратор-модель в TG + Ревизор), Блок 5 (роль гейтов/один канонический процесс). Остальные блоки (1,2,3,4,6-9) — сервисные (чтобы диспетчер не мешал, не плодил дубли/триаge, не спавнил лишнего).

## v0.4.3 — штатный DEV = поезд (2026-09-28)

Аддитивный канон. История 08.09 / контур B **не переписывается**: тогда one-pass был способом auto трёх гейтов. Это **не** единственный способ.

**Перекрытие Блока 5 / контура B в части гейтов (не фазности, не B1–B4 как сверка 08.09):**

- Штатный DEV / CHANGE / BUGFIX после закрытого брифа = **поезд**: auto `GATE:take-into-work` / `GATE:plan-approve` / `GATE:done` / `GATE:diagnose-review` без фразы «делай в 1 проход».
- One-pass остаётся вестигиальным ярлыком: не склеивать роли, корневой one-pass не плодит второй полный хвост. Фраза не нужна, чтобы гейты AC стали auto.
- Never auto: `GATE:go`, `GATE:block-accept`; IDEA `blocked` до «разбери» / отказа.
- Норматив имён/набора фаз — GLOSSARY v0.2.12; механика поезда — DKP v0.4.0 / содержание v0.4.2.
- Класс O (operator-hold: действие Саши, без которого AC пакета неверен) блокирует `GATE:done` и напоминается сторожем; канон — GLOSSARY §3 слой AC/IAC и DKP «Поезд — канон v0.4.0», не этот файл.
- Скиллы / сторож / preflight-parser — волны W1–W2 `dev-process-rework` / done-gate, не эта запись.
