## Q-B1 — Где физически создаётся задача из PM Notes (CRUD «создать»)

**Решение PM:** Вариант A — **в тот же срез**, в отдельную секцию `## ✅ Задачи (добавлено PM)` этого среза (Tasks-формат). Срезы остаются единственным физическим источником задач. Tasks-query подхватывает штатно.

**Метка задачи:** `<!-- src: pm_manual, date: YYYY-MM-DD -->` для аудита.

**PD:** PD-053

## Q-B2 — Удаление задачи через PM Notes

**Решение PM:**
- **Удаление** = физически убираем строку из среза (задача была ошибочно распознана, её не должно существовать)
- **Выполнена** = отмечаем `- [x]` как обычно (закрыт штатный чекбокс)

Два разных глагола PM — два разных действия reconciler'а.

**PD:** PD-054

## Q-B3 — Изменение решения/риска через PM Notes: история

**Решение PM:** Вариант A — **перезаписываем текст на месте** в срезе без сохранения старой версии.

**Ключевое разграничение:**
- Срез (G) = сырая агрегация робота; PM Notes в срезе = исправление ошибок транскрибации → перезапись/удаление без следов (история не нужна, это мусор).
- Карточка проекта (D) = предобработанный артефакт → там история решений хранится (зачёркивание при удалении/изменении).

**PD:** PD-055

## Q-B4 — Формат команд PM Notes (CRUD)

**Решение PM:** Вариант C — маркеры + свободный текст.

Маркеры: `_ADD`, `_DELETE`, `_UPDATE`  
Тип сущности (task / risk / decision) определяется по тому, **под каким блоком среза** размещена секция PM Notes — не нужно указывать явно в маркере.

Пример:
```n## Задачи
...(строки задач)...
### PM Notes
_ADD: Согласовать бюджет с финансами до 07.07
_DELETE: Подготовить презентацию для стейкхолдеров
_UPDATE: Уточнить сроки → сроки сдвинуты на 2 недели
```n
**PD:** PD-056

## Уточнение к Q-B4 — Структура блоков PM Notes в срезе

**Решение PM:** Каждый смысловой блок среза имеет **свой** подблок PM Notes с явным лейблом в заголовке:

```markdown
## Tasks
- [ ] Задача 1 <!-- id: task-abc -->

### PM Notes (tasks)
_ADD: ..._DELETE: ...

## Decisions
- D-001: ..._

### PM Notes (decisions)
_UPDATE: D-001 → ..._

## Risks
### PM Notes (risks)
_ADD: ..._
```n
Лейбл `(tasks / decisions / risks)` в заголовке — страховка на случай поломки разметки Obsidian. Тип сущности определяется однозначно даже без парсинга структуры документа.

**PD:** дополнение к PD-056

## Q-B5 — Идентификация объекта для _DELETE / _UPDATE

**Решение PM:** Вариант C — Haiku ищет по смыслу.

**Плюс: единая система нумерации всех сущностей** (уникально между проектами и типами):

```n T-{project_slug}-{seq:03d}  — task
 D-{project_slug}-{seq:03d}  — decision
 R-{project_slug}-{seq:03d}  — risk
```n
Пример: `T-TRX-007`, `D-CRM-001`, `R-TRX-003`  
Номер проставляется роботом при создании сущности. Seq — сквозной внутри проекта+тип.

Этот id используется в PM Notes командах:
```n### PM Notes (tasks)
_DELETE: T-TRX-007
_UPDATE: T-TRX-003 → Срок сдвинут на 10.07
```n
**PD:** PD-057 (нумерация) + PD-058 (поиск по смыслу для CRUD)

## Q-B5/B6 — Финальный формат ID и вид сущностей в Obsidian

**Решение PM:** Формат подтверждён — фиксируем в ТЗ.

**ID-формат:** `^{slug3}{hex}` — нативный Obsidian block reference, без type-префикса (тип определяется блоком).

Пример реального среза:
```markdown
## Tasks
- [ ] Согласовать бюджет 📅 2026-07-05 @Иванов ^trx11
- [ ] Подготовить презентацию 📅 2026-07-10 @Петрова ^trx12
- [x] Провести ретроспективу ^trx9

### PM Notes (tasks)
_ADD: Запросить KPI у аналитики до 12.07 @Сидоров
_DELETE: trx12
_UPDATE: trx11 → Срок сдвинут на 15.07 @Козлов

---

## Decisions
- Перейти на микросервисную архитектуру — принято 2026-06-15 ^trx1
- Заморозить фичи до релиза — принято 2026-06-28 ^trx2

### PM Notes (decisions)
_UPDATE: trx2 → Заморозка снята
_ADD: Выбрать вендора до конца квартала

---

## Risks
- 🔴 Нет QA-инженера — высокая вероятность ^trx1
- 🟡 Зависимость от API — средняя вероятность ^trx2

### PM Notes (risks)
_DELETE: trx2
_ADD: Риск потери ключевого разработчика в июле
```n
**Счётчик ID:** хранится в `state.json` → `last_ids: {trx: {T: 18, D: 2, R: 2}}` (hex-значения).
**Ссылки:** `[[срез#^trx11]]` работают нативно в Obsidian.

**PD:** PD-057 (финал), PD-058

## Q-C1 — Маппинг секций среза → блоки PM Notes

**Решение PM:** подтверждён маппинг 3 блока по D-артефактам:

- Решения + Блокеры → `### PM Notes (decisions)`

- Открытые вопросы / Сделано → без блока PM Notes (разрешаются следующей встречей; при необходимости — свободный текст в любом из трёх блоков)

## Q-C2 — Лейблы PM Notes для 1-1 (E) и синков (H)

**Решение PM:** единый формат tasks/decisions/risks для всех доменов.

**Маппинг 1-1 (E):**
- Commitments (задачи с дедлайном/владельцем) → `### PM Notes (tasks)`  
- Agreements (договорённости без дедлайна) → `### PM Notes (decisions)`  

**Маппинг синки (H):**
- Action items синка → `### PM Notes (tasks)`  
- Решения синка → `### PM Notes (decisions)`  
- Риски синка → `### PM Notes (risks)`  

Результат: reconciler использует единый парсер для всех типов срезов (проект/1-1/синк). PD-056 (дополнение).

## Q-C3 — Формирование slug3 и защита от коллизий

**Решение PM:** Вариант A — явный `short_id` задаётся PM при заведении проекта.

- Поле `short_id: trx` в `card.md` проекта  
- Реестр уникальности — централизованно (рядом с реестром slug-ов)  
- Если не задан — агент генерирует кандидата (первые 3 значимых буквы) и просит PM подтвердить  
- `slug3` стабилен навсегда, не меняется при переименовании проекта

## ID-namespace для People (1-1)

**Решение PM:** Вариант A — `login3` (первые 3 символа login).

Пример: login `tkachenkoav` → `tka`; ID задачи в 1-1 срезе: `^tka11`  
Login уникален в системе (AD/LDAP) → коллизии login3 маловероятны. При коллизии — авто-кандидат с суффиксом и подтверждение PM.  
Дополнительного поля в `People/<login>/card.md` не нужно.

**PD:** PD-057 (дополнение — source для People)
