# OKR в JIRA (проекты OKRS / OKRAID) — карта полей и иерархия

Обнаружено 06.07.2026 при выгрузке целей АИД (сначала Q2, затем полная иерархия годовые+квартальные за 2026).

## Структура

- Проект **OKRS** — цели/проекты, issuetype "Большая задача" (**id = 6** в этом проекте — использовать `issuetype = 6` в JQL, имя "Большая задача" в кавычках может вернуть ошибку валидации поля).
- Проект **OKRAID** — цели департамента (аналог, не проверено детально, тот же паттерн полей ожидается).
- Различие годовая/квартальная цель — поле **Тип OKR** (`customfield_43701`): `Functional Annual OKR` vs `Functional Quarterly OKR`. Квартал дополнительно виден в `fixVersions` (`Q1 2026`…`Q4 2026`), годовая — `fixVersion = "2026 ф.г."`.

## JQL-фильтрация — что работает напрямую (уточнено 06.07.2026)

Прямая фильтрация по подразделению и релизу **работает без проблем**:
```
project = OKRS AND issuetype = 6 AND cf[43743] = "АИД" AND fixVersion = "2026 ф.г." ORDER BY key ASC
```
Не нужно вытягивать всё и фильтровать в питоне — `cf[43743]` (select-list "Подразделение") и `fixVersion` оба фильтруются в JQL корректно.

**Что НЕ работает:** `parent = OKRS-2` — возвращает `total: 0` даже когда у задачи де-факто есть родитель через связь Contains. Это не Jira epic/parent-link на этом инстансе — не пытаться чинить через parent в JQL вообще, сразу идти через issuelinks (см. ниже).

## Иерархия годовая → квартальная: связь Contains (issuelinks), НЕ customfield CSV

Правильный источник иерархии — `issuelinks` с `type.name == "Contains"`:
- У годовой цели: `outwardIssue.key` = квартальный ребёнок (`outward: "contains"`)
- У квартальной цели: `inwardIssue.key` = годовой родитель (`inward: "is contained in"`)

Нужно проверять **обе стороны** — не все годовые перечисляют своих детей одинаково (иногда связь видна только со стороны квартальной через inwardIssue). Рабочий алгоритм (python, execute_code):
```python
children_of = {}
parent_of = {}
for i in annual_issues:
    for link in i['fields'].get('issuelinks', []):
        if link['type']['name'] == 'Contains':
            out = link.get('outwardIssue')
            if out and out['key'] in quarterly_keys:
                children_of.setdefault(i['key'], []).append(out['key'])
                parent_of[out['key']] = i['key']
for i in quarterly_issues:
    for link in i['fields'].get('issuelinks', []):
        if link['type']['name'] == 'Contains':
            inw = link.get('inwardIssue')
            if inw and inw['key'] in annual_keys and i['key'] not in parent_of:
                parent_of[i['key']] = inw['key']
                children_of.setdefault(inw['key'], []).append(i['key'])
```
Проверено на реальных данных: 12 годовых АИД за 2026 → 44 квартальные, все 44 нашли родителя этим способом.

**Альтернатива (черновая, не для финального отчёта):** текстовые поля `customfield_44600` ("Вышестоящая задача", один ключ строкой) и `customfield_44601` ("Вложенные задачи", CSV ключей строкой). Быстро для беглой проверки, но это денормализованный текст без гарантии синхронности с реальными issuelinks — не использовать как источник правды в отчёте.

## Key Results (KR) — третий уровень иерархии (добавлено 06.07.2026)

KR — отдельные задачи **issuetype = UserStory** (не "Большая задача"), связаны со своей целью (Objective, годовой или квартальной) через тот же issuelinks-тип **Contains** (Objective `outward: contains` → KR). У KR своё **собственное** поле `fixVersions` — не наследуется от родительского Objective автоматически, сверять отдельно через `quarter_of(fields)` (см. код ниже).

Алгоритм сбора KR — обход Contains от каждого Objective (годового и квартального), собрать всех детей, ИСКЛЮЧИТЬ тех, кто уже входит в множество Objective (чтобы не задвоить квартальную цель как KR годовой):
```python
obj_keys = {i['key'] for i in all_objectives}  # annual + quarterly
kr_keys = set()
kr_parent = {}
for i in all_objectives:
    for link in i['fields'].get('issuelinks', []):
        if link['type']['name'] == 'Contains':
            out = link.get('outwardIssue')
            if out and out['key'] not in obj_keys:
                kr_keys.add(out['key'])
                kr_parent[out['key']] = i['key']
```

**Питфолл — не все найденные "дети" — реальные KR.** Contains может тянуть посторонние задачи из других проектов, случайно/легитимно связанные (напр. `SR-36323` из проекта `SR` = Self-Review, не OKR вообще; `OKRAID-40` — из соседнего проекта OKRAID, но тоже нужно проверять). **Обязательный фильтр после сборки:** дособрать `issuetype.name` для каждого найденного ключа и оставить только `issuetype.name == "UserStory"`. На реальных данных (12 годовых АИД + 44 квартальных → 166 кандидатов) один оказался посторонним (`SR-36323`), 165 подтвердились как валидные KR.

Получить чекин-поля + issuetype для проверки одним запросом:
```bash
source ~/.hermes/profiles/anthropic/.env
curl -s -H "Authorization: Bearer $JIRA_TOKEN" -H "Content-Type: application/json" -X POST \
  "$JIRA_BASE_URL/rest/api/2/search" \
  -d '{
    "jql": "key in (OKRAID-40,OKRS-641,SR-36323)",
    "maxResults": 200,
    "fields": ["summary","issuetype","project","customfield_43706","customfield_43822","customfield_43717","customfield_43713","customfield_43782","customfield_43715","fixVersions","status"]
  }'
```
Затем в питоне: `non_kr = [i['key'] for i in issues if i['fields']['issuetype']['name'] != 'UserStory']` — вручную решить, исключать ли (обычно да).

## Сверка цели против её KR (chekin sanity check, добавлено 06.07.2026)

Задача: для каждого Objective сравнить 5 чекин-полей (Уверенность/Что сделано/Риск/Метрика/%) с совокупностью тех же полей по её дочерним KR — обнаружить рассинхрон.

Алгоритм:
1. Собрать средний % по всем KR цели: `avg_pct = sum(kr['%'] for kr in krs) / len(krs)`.
2. Сравнить с % самой цели — на реальных данных (16 Q2-целей АИД) среднее по KR почти всегда **точно** совпадает с % цели (это не совпадение — цель явно агрегируется формулой из KR). Расхождение — красный флаг, не округление.
3. Сравнить текст "Что было сделано" цели с текстами KR — цель должна быть смысловым резюме, не обязана быть дословной копией. Заглушки типа "Выполнение цели Q2" или "Отражено в KR" — это **не ошибка агрегации %**, а просто не заполненное текстовое поле; не путать с реальным расхождением данных.
4. Не исправлять расхождения самостоятельно — только показать находку с кратким комментарием и оставить решение пользователю (обычно это сигнал сверить с ответственным в Jira).

Частые находки такой сверки на реальных данных:
- % цели не пересчитан после обновления % KR (может отличаться кратно, напр. 30% vs 60%) — сигнал на ручную проверку в Jira.
- Цель с единственным KR — поля 1:1 дублируются, это ожидаемо.
- Разброс % между отдельными KR внутри одной цели (напр. 0% и 90%) — нормально, если текст цели объясняет причину разброса.

## Формат отчёта с навигацией — Obsidian wiki-links, НЕ HTML-якоря (уточнено 06.07.2026)

Когда отчёт содержит и сводную таблицу, и детальный раздел на ту же сущность (напр. сверку) и открывается **в Obsidian** — HTML-якоря (`<a name=...>` и `<a id=...>`) и markdown `#anchor`-ссылки **не работают** для перехода: Obsidian их не резолвит (это GitHub/generic-markdown синтаксис). Проверено на практике 06.07.2026 — обе попытки (`name=` и `id=`) не дали перехода.

**Рабочий способ в Obsidian — нативные wiki-ссылки на заголовок:**
```markdown
| [OKRS-2128](...) | ... | [[#🔍 Сверка OKRS-2128\|⚠️ % цели 30%, у KR 60%]] |
...
### 🔍 Сверка OKRS-2128
```
Заголовок должен быть **коротким и уникальным** (`### 🔍 Сверка <KEY>`, без полного summary в заголовке — вынести summary отдельной строкой под заголовком) — Obsidian матчит `[[#Заголовок]]` по точному тексту заголовка, длинные заголовки с summary ломают матчинг при малейшем расхождении. Формат ссылки: `[[#Заголовок|текст ссылки]]`.

Текст самой ссылки должен нести краткий вердикт, не generic-слово вроде «Сверка»/«Подробнее» — это явное требование пользователя к формату таких отчётов. **Важно (уточнено 06.07.2026):** если сверка не выявила расхождений — писать в ссылке ровно «ОК», без каких-либо пояснений («ОК, но можно детализировать...», «ОК — образцовое резюме», «ОК (единственный KR, 1:1)» — всё это лишнее и подлежит удалению). Комментарий/пояснение в тексте ссылки добавлять **только** когда есть реальное расхождение, требующее ручной проверки (разошёлся %, текст-заглушка вместо содержания и т.п.) — само расхождение и есть причина писать длиннее «ОК».

Сводная таблица всегда идёт **первой** в файле (сразу после заголовка, до всех деталей) — тоже явное требование пользователя, не только для этой задачи.

## Верификация полей «Уровень» и «Квартал» — сверять с собственными полями задачи, не с унаследованными (добавлено 06.07.2026)

Когда пользователь просит проверить, что колонки «Уровень» (Годовая/Квартальная) и «Квартал» в отчёте корректны — не полагаться на то, что эти значения были правильно унаследованы от родителя при первичной сборке. Перепроверять напрямую:
- «Уровень» = `customfield_43701` (Тип OKR) самой задачи: `Functional Annual OKR` → Годовая, `Functional Quarterly OKR` → Квартальная. Проверять у Objective **и** у каждого её KR отдельно — не постулировать, что KR наследует уровень цели.
- «Квартал» = собственный `fixVersions` задачи (не родителя).

**Edge case — KR из проекта OKRAID (напр. `OKRAID-40`):** `customfield_43701` в проекте OKRAID может отсутствовать в схеме вообще (`None`), хотя fixVersion корректно проставлен (`2026 ф.г.`). Не считать это ошибкой/несоответствием — если `Тип OKR` пуст, использовать fixVersion как единственный источник истины для уровня. На реальной проверке (28 Objective + 77 KR) только этот один случай дал `None`, все остальные 76 KR + 28 Objective подтвердили собственные customfield_43701/fixVersions без единого расхождения с ранее проставленными в отчёте значениями.

## Паттерн «снапшот перед сужением отчёта» (добавлено 06.07.2026)

Когда пользователь просит после уже собранного полного отчёта сузить рабочий файл (убрать кварталы/детали, оставить только часть), но собранные из Jira данные дорого перезапрашивать — сначала сохранить полную версию как отдельный файл-снапшот (например `OKRS-all-OKR-<ddmmyy>.md`), и только потом урезать рабочий файл. Это позволяет вернуться к полным данным без повторных запросов к Jira API, если пользователь позже передумает или найдёт ошибку в урезанной версии. Использовать `terminal cp` для копии (не Jira-запрос заново), rclone sync — отдельно на оба файла.

## Питфолл — `|` внутри wiki-ссылки ломает markdown-таблицу (добавлено 06.07.2026)

Формат ссылки `[[#Заголовок|текст]]` (см. выше) внутри ячейки markdown-таблицы конфликтует с синтаксисом таблиц: любой непойманный `|` в самом тексте ссылки читается как разделитель столбцов и рвёт строку на лишние пустые ячейки, ломая отображение всей таблицы в Obsidian. Экранировать как `\|`:
```markdown
| ... | [[#🔍 Сверка OKRS-2124\|⚠️ % цели 30%, у KR 60% (текст идентичен, вдвое расходится)]] |
```
Перед доставкой отчёта — грепнуть файл на `\[\[#.*\|` внутри строк таблицы (строки начинающиеся с `|`), чтобы убедиться что все ссылки-с-вердиктом экранированы. Один пропущенный `|` тихо ломает все столбцы после себя именно в той строке.

## Визуальная группировка иерархии в отчёте — Obsidian callout (добавлено 06.07.2026)

Когда отчёт содержит несколько уровней иерархии (годовая цель → её KR → её квартальные цели → их KR) и нужно визуально отличить, что относится к какой годовой цели — оборачивать всю ветку одной годовой цели в Obsidian callout вместо одной большой плоской таблицы:
```markdown
> [!note] 🎯 [OKRS-640](...) — O1.Название годовой цели
>
> | Ключ | Objective/KR | Уровень | Квартал | Название | Сверка Q2 |
> |---|---|---|---|---|---|
> | [OKRS-640](...) | Objective | Годовая | 2026 ф.г. | ... |  |
> | [OKRS-641](...) | KR | Годовая | 2026 ф.г. | ... |  |
> | [OKRS-2128](...) | Objective | Квартальная | Q2 2026 | ... | [[#🔍 Сверка OKRS-2128\|ОК]] |
```
Каждая строка таблицы (заголовок, разделитель, данные) должна начинаться с `> `, иначе она выпадет из блока callout. Чередовать типы callout (`note`, `tip`, `success`, `question`, `quote`, `abstract`, ...) между соседними годовыми целями по кругу — тогда у смежных блоков будет заметно разный фон, и границу между целями видно с одного взгляда без чтения текста.

Порядок строк внутри callout-блока: сама годовая цель → все её годовые KR → каждая её квартальная Objective (если попадает в нужный квартал отчёта) → её KR сразу под ней. Так вложенность видна прямо в таблице, а не только по цвету фона.

## Обновление чекина ГОДОВОЙ цели на основе Q1 (своё поле) + Q2 (дочерние Objective) — отдельный паттерн от сверки Objective-vs-её-KR (добавлено 06.07.2026)

Это ДРУГАЯ задача, чем «сверка цели против её KR» выше: там сравнивали Objective с её собственными KR того же периода. Здесь — годовая цель (чекин = итоги Q1) против её **дочерних квартальных Objective за Q2** (не KR), чтобы предложить обновлённый чекин годовой цели, отражающий прогресс Q1+Q2 вместе.

Процедура:
1. Взять 5 чекин-полей годовой цели как есть (это фактически снимок на конец Q1).
2. Найти её дочерние квартальные Objective за Q2 (через Contains, как в разделе иерархии выше) — их тоже 5 чекин-полей, но за Q2.
3. Составить **краткое совокупное описание** по Q2-детям (не копировать целиком — сжать до сути: что выполнено/не выполнено/риски).
4. Предложить **обновлённые** значения всех 5 полей годовой цели — текст должен реально объединять факты Q1 (из самой цели) и факты Q2 (из детей), не выдумывая ничего нового. Если % годовой цели и % Q2-ребёнка расходятся сильно (напр. 15%→76%) — предлагать взвешенное/усреднённое значение с пометкой в комментарии, не просто брать любое одно число.
5. Явно маркировать это как **черновик/предложение для проверки перед внесением в Jira**, а не как выполненное изменение — агент не пишет в Jira автоматически.
6. Edge case — годовая цель без Q2-ребёнка вообще (напр. потому что цель уже закрыта на 100% в Q1, или Q2-Objective не заведена в Jira) — явно писать «нет Q2-цели для сравнения» / «обновление не требуется», не придумывать Q2-прогресс из воздуха.

**Конвенция текста ссылки различается по уровню** (важно не перепутать):
- Ссылка у **Q2-цели** (сверка Objective vs её собственный KR) → короткий вердикт: «ОК» или ⚠️ + суть расхождения (см. раздел выше).
- Ссылка у **годовой цели** (это предложение по обновлению) → короткая **цитата/выжимка из предложенного нового поля «Что было сделано»**, не «ОК»/вердикт — это отдельное явное требование пользователя для этого уровня ссылок.

## Полное исключение стороннего проекта из отчёта по одному подразделению (добавлено 06.07.2026)

Если при обходе Contains-иерархии всплыла задача из смежного, но нерелевантного проекта (напр. `OKRAID-40` в отчёте по подразделению АИД проекта OKRS) — по запросу пользователя убирать её **полностью и отовсюду**: и строку в сводной таблице, и детальный блок (если создавался), а не просто помечать сноской. Проверить после удаления, что упоминаний ключа не осталось нигде в файле (`search_files` по самому ключу), прежде чем считать задачу выполненной.

## Питфолл: rclone sync падал на несвязанном старом файле

При `rclone sync ~/WorkVault owncloud:WorkVault` может упасть с `FileNameTooLong` на давно существующем файле с длинным именем (не связанном с текущей задачей). Ошибка не мешает нужному файлу — синхронизировать точечно нужную папку отдельно и проверить `rclone lsf owncloud:WorkVault/<path>`, не считать весь sync проваленным.
