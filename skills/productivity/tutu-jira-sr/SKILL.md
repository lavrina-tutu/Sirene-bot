# TUTU Jira Self-Review (SR)

Работа с задачами Self-Review (issuetype `SR`, проект в Jira `hq.tutu.ru`, напр. `SR-37535`). Авторизация — тот же `JIRA_TOKEN`/`JIRA_BASE_URL`, см. `tutu-confluence-jira`, здесь не дублируется.

Полное архитектурное ТЗ (философия, TG-флоу заполнения, roadmap) — `WorkVault/Hermes-Backlog/TZ/SRTool/SRTool_TZ.md`. Здесь — рабочая карта полей + конкретно флоу **check** (проверка периода), которого не было в ТЗ до этой сессии.

## Поля SR (customfield ID)

| Поле | ID | Когда заполняется |
|---|---|---|
| Результат (план) | `customfield_44401` | начало периода |
| Критерии (план) | `customfield_44402` | начало периода, автодеривируется из 44401 |
| OKR/KPI (план) | `customfield_44403` | начало периода, автодеривируется из 44401 |
| Итог: выполнено (факт) | `customfield_44404` | конец периода |
| Итог: сложности (факт) | `customfield_44405` | конец периода |
| Итог: развитие/пробелы | `customfield_44406` | конец периода |
| Поведение | `customfield_44414` | конец периода, часто `None` |

Transitions: `61` = отредактировать (единственный способ записать поля — **PUT не работает**, см. питфолы в SRTool_TZ.md), `11` = согласовать (делает только пользователь, не Сирень).

Получить сырые поля:
```bash
source ~/.hermes/profiles/anthropic/.env
curl -s -H "Authorization: Bearer $JIRA_TOKEN" -H "Content-Type: application/json" \
  "https://hq.tutu.ru/rest/api/2/issue/SR-XXXXX?fields=summary,assignee,status,customfield_44401,customfield_44402,customfield_44403,customfield_44404,customfield_44405,customfield_44406,customfield_44414"
```

## Флоу FILL (заполнение плана/факта) — см. SRTool_TZ.md
TG-driven, сразу заливка через transition 61, буллет `·` (U+00B7), переносы `\r\n`, парсер по `\d+\.\t`. Не описываю повторно здесь — детали в ТЗ.

## Флоу CHECK (проверка ежемесячного review — новый, эта сессия)

**Цель:** сравнить план (44401-44403) с фактом (44404-44406) конкретного SR, оценить выполнение по каждому независимому пункту плана и объективность объяснений по недостижению.

### Файлы и пути
```
WorkVault/Projects/sr-tool/<ФИО исполнителя>/
├── SR-{key}_{месяц}_{год}.md        # сырые поля 1-6, как есть в Jira
└── SR-{key}_{месяц}_{год}_check.md  # таблица сравнения план/факт
```
ФИО — из summary задачи (`SR - Криворотов Кирилл (Июнь - 2026)` → папка `Криворотов Кирилл`). После записи — `rclone sync ~/WorkVault owncloud:WorkVault`.

### Формат raw-файла
Разбить 44401 на пронумерованные пункты (план), сопоставить с 44402 (критерии) и 44403 (OKR-ключи) — заголовки 1-3. Затем 44404-44406 — заголовки 4-6, с той же нумерацией пунктов (пункт N в плане = пункт N в факте).

### Формат check-файла: таблица сравнения
Одна строка таблицы = один независимый пункт плана (не всё SR целиком). Колонки:

| № | Что было запланировано | Критерии (список) и статус done/not done | Доп. успехи, не заявленные в плане | Объективность объяснений по недостижению |

**Правила заполнения:**
- Статус done/not done выставлять **по каждому критерию внутри пункта отдельно**, не по пункту целиком — пункт может быть done по 3 из 4 критериев.
- В колонку "доп. успехи" — только то, что реально есть в факте (44404) и отсутствует в плане (44401/44402). Не выдумывать.
- Объективность объяснения (44405) оценивать по критерию **причинно-следственная связь**: указана ли конкретная причина (кто/что/почему), напрямую объясняющая именно недостигнутый критерий — а не общая фраза типа "изменилась концепция задачи" без деталей. Общая фраза без деталей = низкая объективность, отметить явно.
- Для полностью done пунктов колонка объективности = "план не нарушал — n/a".
- В конце — краткий итог: сколько пунктов done/not done, есть ли системный паттерн в неточных объяснениях (напр. один и тот же общий оборот повторяется у нескольких невыполненных пунктов).

## ⚠️ Питфол: описание методики ≠ выполнение задачи

Когда пользователь в конце задачи просит **"напиши инструкцию как поняла"** или **"опиши как отработать"** — это сигнал остановиться на описании методики/подхода и отдать его на подтверждение, **прежде чем** применять эту методику к следующим SR или зашивать её в постоянный флоу/скилл. В этой сессии подход (методика check, критерии объективности) был придуман и сразу применён к SR-37535 без предварительного согласования формата — только после результата пользователь попросил зафиксировать правило "без согласования не выполнять". Правило см. в USER PROFILE Сирени (не дублируется здесь): при прямой просьбе "опиши/сформулируй" — отдавать только описание, ждать явного "делай"/"ок" перед реализацией.
