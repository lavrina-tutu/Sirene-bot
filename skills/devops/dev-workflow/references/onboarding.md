# Онбординг специалиста (не разработчик)

DevWorkflow упакован так, чтобы вести доработки **без чтения Python и мастер-ТЗ**. Ты — заказчик и приёмщик; машину ведёт Сирень (оркестратор).

## Ваша роль

1. **Постановка** — что нужно изменить, в каком инструменте, ограничения («не трогать прод», сроки).
2. **Бриф** — ответы на уточняющие вопросы в Telegram (обычно по одному).
3. **Приёмка** — смотрите `AC-report.md` и сообщения в топике задачи; подтверждаете, что критерии выполнены.
4. **Редкие действия** — только если в ТЗ пакета помечено `depends: operator:…` (поднять сервис, поставить крон, удалить после бэкапа, ответить на Q-n, откат на канбан). Без тега — от вас действие не требуется.

## Что вам не нужно делать

- Запускать `pipeline` или `agent` вручную.
- Читать `DevWorkflow_TZ.md` или код в `Registries/pipeline/`.
- Следить за канбан-доской на переходе W2–W3 для пилотных слагов — там работает новый процесс.

## Как понять статус

Попросите Сирень: «статус разработки» → она вызовет `pipeline status` (тот же привычный layout, на W0–W3 заголовок может быть «КАНБАН-СТАТУС»).

- **Жёлтый блок (HITL)** — нужно ваше действие или явная фраза (например «удаляй» на DECOMM).
- **Показ AC** — информация; поезд **не** ждёт, если это не operator-hold.

## Типы работ (одной фразой)

| Вы говорите | Обычно кейс |
|---|---|
| новый инструмент | DEV |
| доработай существующее | CHANGE |
| мелкая правка в паре файлов | CHANGE-LIGHT (после оценки объёма) |
| сломалось / баг | BUGFIX |
| разберись, код не нужен | RESEARCH |
| сними инструмент | DECOMM |
| новый или правка скилла Hermes | SKILL-DEV / SKILL-CHANGE |

Подробнее: `cases-guide.md`.
