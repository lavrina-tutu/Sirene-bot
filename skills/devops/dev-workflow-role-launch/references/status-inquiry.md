# Ответ на «статус» dev-топика в точечном режиме

## Файловый проход ≠ канбан-задача

В точечном режиме (invoke-role, полный канбан не гонять) реализация dev-топика (SQL-схема, RAG, приёмка, ингest) идёт **файловым проходом** `dev/<slug>/in|out|evidence`:
- `in/*-PROMPT-*.md` — промпты ролей по фазам (arch, rev, impl-phase1/2/3, acc),
- `out/*.md` — готовые артефакты ролей (FINAL-TZ, HF-PLAN, REVIEW, DECISIONS),
- `evidence/*-run.log` — журналы исполнения фаз (end-маркер `... run end <ts>`).

Этот проход существует ПАРАЛЛЕЛЬНО канбан-задаче Research/ТЗ со `_state.json` в том же `dev/`. У RESEARCH-задачи `status: done` означает только завершение Research, НЕ доставку реализации — не путать.

## Как отвечать на «статус»

1. Проверить ОБА контура: канбан `_state.json` (для Research/ТЗ-фактов) и файловый проход (для реализации). Не смотреть только `status` одной RESEARCH-задачи.
2. Найти активную/самую свежую `evidence/*-run.log` и существование фактического артефакта текущей фазы (витрина `*.md`, миграции в коде, сгенерированные файлы).
3. Заявленное в чате «Фаза N запущена» — НЕ evidence. Завершение фазы = end-маркер её `*-run.log` И наличие результата этой фазы.
4. Отсутствие следующего артефакта (напр. приёмочного/ACC-отчёта) при объявленном запуске = фаза ещё не завершена. Докладывать честно именно так, без выдачи объявленного запуска за готовность; предложить запустить закрытие фазы.

## Честная приёмка

При реальных ограничениях данных/кода (split-сегменты MPP, неполная capability-матрица, subprocess-вызов build_groups без полного replay) фиксировать их явно как «честно ограничено», не выдавать за tested_supported/уровень В. Итоговый приёмочный отчёт — отдельный артефакт фазы, его отсутствие = фаза приёмки не завершена.
