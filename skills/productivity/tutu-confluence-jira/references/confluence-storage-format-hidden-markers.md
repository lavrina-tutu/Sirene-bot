# Невидимые маркеры в Confluence storage format — экспериментальный протокол

Задача: связать строку таблицы Confluence с внешним стабильным ID (`meeting_id`) так,
чтобы связь пережила (а) сохранение через API PUT и (б) свободное ручное редактирование
текста той же ячейки человеком через веб-редактор.

Проверено реальными PUT/GET запросами на тестовой странице Confluence Server/DC
(`dom.tutu.ru`, PAT из `ConfluenceSync/.env`). Страница восстановлена после тестов
(побайтовое сравнение storage до/после — совпадает).

## Метод

1. Сохранить оригинальный `body.storage.value` (GET `?expand=body.storage,version`).
2. Собрать тестовую строку/property, вставить, PUT с `version.number = current+1`.
3. GET снова, сравнить storage — что осталось, что исчезло.
4. Откатить: PUT с оригинальным storage и `version.number = current+1` (не revert API —
   Server/DC REST не даёт "revert to version N" напрямую в этом инсталле, проще
   восстановить точный HTML).
5. Удалить тестовые content properties через DELETE `/rest/api/content/{id}/property/{key}`.

## Результаты по вариантам

| Вариант | PUT round-trip | Рендер (view) | Ручное редактирование в веб-UI |
|---|---|---|---|
| HTML-комментарий `<!-- pfs-row: ... -->` в `<td>` | **Исчезает.** Confluence Server/DC вырезает HTML-комментарии уже на этапе серверной валидации storage при PUT — не при рендере. | н/п | не проверено (не имеет смысла — не пережил даже API) |
| `data-*` атрибут на `<td>`/`<tr>` (`data-pfs-anchor="..."`) | **Исчезает.** Тот же санитайзер режет произвольные `data-*` атрибуты на любых элементах. | н/п | не проверено (аналогично) |
| `<ac:structured-macro ac:name="anchor" ac:macro-id="..."><ac:parameter ac:name="">ID</ac:parameter></ac:structured-macro>` | **Переживает** нетронутым. | Рендерится как невидимый `<span class="confluence-anchor-link" data-hasbody="false" id="...">` — визуально ничего не показывает. | **Не проверено** — нет доступного browser/computer-use инструмента в среде, где это тестировалось. |
| `<span style="display:none">ID</span>` внутри текста ячейки | **Переживает** нетронутым, включая inline `style`. | Невидим в браузере (display:none). | Не проверено. Риск: WYSIWYG "clear formatting" в тулбаре Confluence может снести inline-style при выделении текста рядом. |
| Невидимый текст (zero-width space `\u200b` + `pfsid:...`) как часть обычного текста ячейки | **Переживает** побайтово — это просто юникод-текст, не HTML, санитайзер его не трогает. | Невидим на глаз (zero-width). | Не проверено. Риск выше остальных: любое выделение+перепечатка текста ячейки человеком стирает и текст, и маркер вместе, т.к. это единая текстовая строка. Также "путешествует" при копипасте текста. |
| Content Properties API (`POST/GET/DELETE /rest/api/content/{id}/property`) | **Работает полностью** — произвольный JSON (`{"pfs-rows":[{"meeting_id":...,"row_index":N,"anchor":"..."}]}`) хранится и читается штатно, отдельно от тела страницы. | н/п (не в body) | Не применимо к тексту ячейки — правка текста никак не может задеть property. Но property привязана к странице целиком, не к строке — нужен якорь ВНУТРИ ячейки (напр. anchor-макрос) для сопоставления, иначе привязка по `row_index` ломается при перестановке/удалении строк человеком. |

## Ключевой вывод

Confluence Server/DC **вырезает HTML-комментарии и произвольные `data-*` атрибуты уже
на этапе API PUT** (серверная санобработка storage, видимо whitelist разрешённых
элементов/атрибутов) — это не проблема веб-редактора, эти два варианта отпадают ещё до
всякого ручного редактирования человеком.

## Риск ручного веб-редактирования — ПРОВЕРЕН И ЗАКРЫТ (10.07.2026, ProtocolFromSummary)

Изначально ни один из "работающих" вариантов не был протестирован на **реальном ручном
сохранении через веб-UI** (открыл страницу в браузере, поправил текст рядом, Save) — curl/API
эмулирует только round-trip, не WYSIWYG-редактор, а в среде не было `computer_use`.

**Закрыто реальным тестом:** anchor-макрос был опубликован на двух боевых страницах
(`Trisigma` pageId 490170597, `Кирилл 1-1` pageId 508804979), после чего владелец страниц
лично отредактировал текст строк через обычный веб-редактор Confluence (реальные правки
формулировок решений/задач, не тестовый сценарий). Повторный `GET ?expand=body.storage`
подтвердил: anchor-макрос **пережил** правку без изменений на обеих страницах
(`pfsrow-2f428a5e80b6` на Trisigma после version 82→83, `pfsrow-332dc4c50eaa` на Кирилл 1-1
после version 8→9). **Anchor-макрос подтверждён надёжным и для API round-trip, и для живого
ручного редактирования человеком.** Остальные варианты (`display:none` span, zero-width text)
по-прежнему не проверены на живом ручном редактировании — не нужно, раз anchor-макрос уже
подтверждён рабочим основным механизмом.

## Рекомендация (обновлено — оба пункта подтверждены практикой, не только теорией)

Комбинация: **Content Properties API как источник истины** для `meeting_id` (гарантированно
не задевается правкой текста, т.к. не в body) + **anchor-макрос внутри ячейки** как
физический якорь для определения "какая это строка" (искать по наличию macro-id/anchor
через `body.storage`, не по индексу строки) — **оба элемента комбинации подтверждены
реальными тестами**, включая ручное редактирование человеком. Zero-width text как fallback
на случай агрессивной ручной чистки форматирования остаётся неприоритетным — pipeline можно
строить сразу на anchor-макрос + Content Property без дополнительной защиты.
