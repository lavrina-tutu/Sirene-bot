# PM Warnings — PMBOK паттерны (из анализа Trisigma 17.06.2026)

Эти паттерны выведены из реального анализа 10 summary встреч Trisigma (май–июнь 2026).
Использовать как обучающие примеры при настройке LLM-промпта для извлечения Warnings.

## Типы противоречий с примерами

### 1. Скрытый сдвиг срока без change-request (HIGH)
**Паттерн:** дедлайн упомянут в summary N, в summary N+2 не упоминается, в N+3 — новый срок без объяснения.
**Пример Trisigma:** дедлайн «18 июня» (15.05) → молча исчез к 26.05 без CR.
**Правило:** если дата milestone изменилась и нет «потому что Y, новый срок X» → WARNING HIGH.

### 2. Scope creep — новый артефакт вне context.md (MEDIUM → HIGH)
**Паттерн:** в summary появляется задача/артефакт которого нет в context.md scope.
**Пример Trisigma:** дашборд 49 тестов, календарь A/B, скрипт пересечений (15.06) vs context.md «3 эксперимента + заключение».
**Правило:** LLM ставит MEDIUM, PM в `<!-- pm: -->` решает: CR или побочный продукт.

### 3. Обязательство вендора не выполнено (HIGH)
**Паттерн:** в context.md написано «Интеграция X от вендора», но в summary выясняется «X не входит в коробку».
**Пример Trisigma:** «SDK на Go не входит в коробочный комплект» (02.06) vs context.md «Интеграция go SDK вендора».
**Правило:** эскалировать как нарушение обязательств + фиксировать как риск. WARNING HIGH до закрытия.

### 4. Финансовое отклонение от договора (HIGH)
**Паттерн:** в summary упоминается платёж/лицензия/договор → проверить против context.md.
**Пример Trisigma:** лицензии оплачены частично (225 тыс из 1,775 млн), договор требует 100% за 5 дн. (05.06).
**Правило:** при любом упоминании платежа в summary — проверить срок из context.md. < 5 рабочих дней → WARNING HIGH.

### 5. Критерий приёмки «закрыт», но пересматривается (MEDIUM/HIGH)
**Паттерн:** в card.md критерий ✅, но на встречах обсуждаются новые требования к нему.
**Пример Trisigma:** К1 ✅ в card.md, но 28.05 — 5-балльная шкала, 15.06 — UX/UI критерии.
**Правило:** 
  - Есть Confluence-документ → WARNING HIGH (переоткрытие = официальный CR)
  - Только устная договорённость → WARNING MEDIUM

### 6. Bus-factor / нарушение допущения по ресурсам (HIGH если критический путь)
**Паттерн:** ключевой специалист уходит в отпуск ≥1 нед., замены нет, он на критическом пути.
**Пример Trisigma:** Юрий — единственный инженер по миграциям — отпуск с 29.06 на 2 нед. (15.06).
**Правило:** проверить допущение из context.md «замены согласованы». Нарушено → WARNING HIGH.

### 7. Риск без митигации 2+ встречи подряд (HIGH)
**Паттерн:** один и тот же риск упоминается в разных summary без прогресса в решении.
**Пример Trisigma:** ClickHouse-миграции (15.05 → 26.05 → 02.06 → исправлено вручную 15.06).
**Правило:** если риск в meetings_index помечен в 2+ summary → WARNING HIGH в следующем срезе.

### 8. Action item повторяется без прогресса (MEDIUM)
**Паттерн:** одинаковый action item встречается в нескольких summary подряд.
**Пример Trisigma:** Аралов «договориться с Азаматом» — дважды на 25.05 с разными таймкодами.
**Правило:** дедупликация по тексту (В5 модуля C) + флаг «висит» если 2+ встречи.

## Алгоритм сверки с card.md/context.md

Проверять только ключевые поля (не полный diff):
1. **Даты milestone** → сравнить с baseline из context.md
2. **Критерии приёмки** → статус каждого (без изменений / прогресс / деградация / пересматривается)
3. **Допущения** → проверить выполнение, нарушенное = WARNING HIGH
4. **Платежи** → сверить с датами из context.md при любом упоминании

## Принцип «мусор на входе → мусор в Warnings»

context.md, допущения и ограничения должны быть максимально точными и ёмкими:
- Допущения: конкретные («ресурсы выделены к 23.04»), не общие («команда поддержит»)
- Ограничения: измеримые («бюджет ≤ 5.99 млн», «срок до 18.06»)
- Цель: одно чёткое предложение о том чего хотим достичь

PM приводит эти секции в порядок ОДИН РАЗ перед первым запуском инструмента.
