# Процедура: ревизия и закрытие пунктов Common Pitfalls через доработку кода

Применять когда Саша просит пройтись по списку Common Pitfalls и определить, какие
можно закрыть доработкой инструментов (не только дисциплиной/памятью). Отработано

исправлены в коде, просто без теста; остальные потребовали реального фикса.

## Шаг 0 — классификация ДО начала работы

Не чинить весь список подряд. Сначала разложить кандидатов по типу:

- **Закрывается кодом USERTOOLS** — есть конкретный файл/функция, которую можно
  поправить или протестировать. Это единственная категория, которую стоит брать
  в работу в этом проходе.
- **Требует апстрим-фичи самого Hermes** (например `skill_manage` не авторегистрирует
  скилл в `.usage.json`, `search_files` даёт ложноотрицательный `total_count`) —
  не наш код, оформлять как issue/feature-request отдельно, не пытаться патчить.
- **Чисто поведенческое** (диалоговая дисциплина, R0-R3, разрешающие сигналы) —
  тулингом не закрывается никогда, эти пункты остаются как есть.

Показать Саше список первой категории и получить подтверждение прежде чем начинать
фиксы поштучно.

## Шаг 1 — для каждого пункта: сначала проверить реальность, не текст питфолла

Питфолл описывает инцидент на момент его написания — код с тех пор мог измениться
(параллельная сессия, другой инцидент задел тот же файл, сам исполнитель уже
починил). **Прежде чем писать код — прочитать актуальное состояние**:
`search_files`/`read_file` на функцию/файл, упомянутые в питфолле.

Дальше три исхода:

1. **Уже полностью исправлено и протестировано** — просто зафиксировать
   «ПРОВЕРЕНО, всё в порядке», ничего не менять.
2. **Исправлено в коде, но нет теста** (самый частый исход в этой сессии — 16а,
   16б, 28 были все именно такими) — **не переписывать логику заново**, написать
   регрессионный тест, воспроизводящий именно сценарий инцидента из текста
   питфолла (те же входные данные/структура, что в примере), прогнать его.
3. **Реально не исправлено** — обычный цикл: бэкап (если git — просто staged/commit
   по решению Саши; если не git-репозиторий — изменения только на диске, явно
   предупредить об этом в отчёте), точечный `patch`, тест на конкретный сценарий,
   прогон.

## Шаг 2 — после КАЖДОГО фикса или добавленного теста

- Прогнать **полный набор тестов пакета** (`pytest tests/`), не только новый тест —
  проверка регрессии обязательна, а не выборочная.
- Если venv пакета не содержит нужных зависимостей — прежде чем создавать новый
  venv, проверить venv соседних USERTOOLS-пакетов того же кластера (см. Pitfall 50)
  через `PYTHONPATH=<пакет> <сосед>/venv/bin/python -m pytest`.

## Шаг 3 — обновление самого пункта в SKILL.md, не удаление истории

Формат: зачеркнуть устаревшую часть исходного текста (`~~...~~`), добавить
**«ИСПРАВЛЕНО/ПРОВЕРЕНО <дата>:»** с конкретикой (файл, функция, имя теста, счётчик
«N/N тестов зелёных»). Номер пункта и общая формулировка правила остаются —
история находки не должна пропадать, даже если конкретный инцидент закрыт.

## Практическое: этот файл (`hermes-feature/SKILL.md`) сам часто правится параллельно

Во время такой ревизии `patch` может вернуть предупреждение «file was modified
since you last read it on disk» — self-check кроны/другие сессии тоже пишут в
этот скилл. Патч обычно всё равно применяется корректно (fuzzy-match находит
нужный текст), но **после каждого такого предупреждения** проверять
`grep -c "^## "` (число секций не изменилось) и что именно твой текст, а не чужой,
приземлился в нужном пункте — не полагаться на «раз patch не упал, значит всё ок».

## Автоматический скан (крон `vm_pitfall_scan`, добавлено 13.07.2026, триггер изменён 13.07.2026)

По решению Саши шаг 0 (классификация — какие пункты Common Pitfalls закрываемы
доработкой кода, сколько потенциально можно закрыть) выполняется через
`cronjob(job_id='97d76357f2da')` — но **не по календарю, а по росту MEMORY.md**.
Крон только **сканирует и отчитывается — никогда сам не патчит код**: реальный
фикс (Шаги 1-3 выше) стартует только по явной команде Саши после того, как он
увидел отчёт (например «поправь по паттернам» или «фиксим пункты 3 и 5»).

**Триггер запуска (решение Саши 13.07.2026):** не ежемесячно по расписанию, а
когда `MEMORY.md` вырастет до **1/3 своего лимита** (лимит — `memory_char_limit`
в `config.yaml`, на 13.07.2026 равен 2200 символов → порог ≈734 символа / 33%).
Идея: чистка Common Pitfalls и рост MEMORY — оба сигнала «пора прибраться», и
удобнее смотреть на них вместе, когда MEMORY уже начала заполняться, а не по
произвольной календарной дате.

**Механика:** сам job `97d76357f2da` стоит **на паузе** (`enabled=false`,
`schedule=null`, `next_run_at=null`) — он НЕ запускается сам по себе. Вместо
этого шаг 9 в `vm_selfcheck` (еженедельный self-check, суббота 03:30) при каждом
прогоне проверяет текущее заполнение MEMORY и, если оно ≥33% лимита, добавляет
строку-рекомендацию в отчёт: "📋 MEMORY выросла до XX% — рекомендую запустить
Pitfall Scan: `hermes cron run 97d76357f2da`". Саша видит рекомендацию в
еженедельном отчёте и решает сам, запускать ли скан именно сейчас — крон
никогда не запускает сканирующий job автоматически.

**Если нужно вернуть к календарному расписанию** (или добавить оба триггера
сразу) — просто выставить `schedule` обратно (было `'0 5 1 * *'`, ежемесячно
1-го числа в 05:00 МСК) через `cronjob(action='update', job_id='97d76357f2da',
schedule='0 5 1 * *')` и `enabled=True`; это не удалит текущую MEMORY-триггерную
рекомендацию в `vm_selfcheck` — оба механизма могут работать параллельно.

**Что делает крон-скан (сам job `97d76357f2da`, при ручном запуске):**
1. Прочитать секцию `## Common Pitfalls` в `hermes-feature/SKILL.md`.
2. Отбросить пункты, уже помеченные `ИСПРАВЛЕНО`/`ПРОВЕРЕНО`/`УЖЕ РЕАЛИЗОВАНО` —
   их не пересматривать повторно каждый месяц.
3. Для оставшихся — прогнать классификацию Шага 0 (закрывается кодом USERTOOLS /
   апстрим-фича Hermes / чисто поведенческое). Для категории «закрывается кодом» —
   выполнить Шаг 1 (прочитать актуальный код) БЕЗ патча — только чтобы понять,
   в каком из трёх исходов (уже исправлено-без-теста / нужен реальный фикс /
   не тронуто) находится каждый пункт.
4. Составить таблицу, ровно как в примере из основной задачи 13.07.2026:
   номер пункта → инструмент → предполагаемый исход → грубая оценка «что даст
   доработка» (например «убирает риск непредсказуемого exit code», «добавляет
   3-5 тестов», «сокращает N символов записи в SKILL.md после закрытия»).
5. Отчёт — **только детект, без изменений файлов** (даже без пометки
   ИСПРАВЛЕНО/ПРОВЕРЕНО в самом SKILL.md — это делает реальный ремедиэйшн-проход,
   не сканер, иначе теряется разница между «мы проверили и подтвердили тестом» и
   «сканер предположил по чтению кода»).

**После получения отчёта** — Саша даёт команду (`«поправь по паттернам»`,
`«фиксим 3 и 7»` и т.п.) → отдельный запуск полного цикла Шаги 1-3 выше (в
интерактивной сессии или отдельным cronjob с `repeat=1`, если объём большой) →
финальный отчёт «что было / что стало / что поправили» в том же формате, что
использовался 13.07.2026.

**Модель Opus** — классификация пунктов Шага 0 требует смыслового суждения
(закрывается кодом vs апстрим vs поведенческое), не механическое действие.
