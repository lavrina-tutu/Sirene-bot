# tz-workflow

## Overview

Единые правила хранения, версионирования и архивации технических заданий (ТЗ) по инструментам Hermes/USERTOOLS, включая инфраструктурные планы (RAG, systemd, MCP-интеграции). Действует и для Hermes на ВМ, и для внешних LLM (Cursor на ноутбуке через синк vault).

## Workflow разработки ТЗ

### Модели и провайдеры

Провайдер всегда берётся из конфига Hermes по умолчанию. Пинятся только версии моделей:

| Шаг | Модель | Когда |
|---|---|---|
| Шаг 1 — Анализ и драфт | `claude-sonnet-5` | Начало каждого нового ТЗ |
| Шаги 2, 3, 4 — Архитектура, написание, финализация | `claude-opus-4-7` | Архитектурные решения и текст ТЗ |
| Механические задачи | `claude-haiku-4-5` | Операторские кроны, лёгкие делегирования |

### Шаги разработки ТЗ

**Шаг 1 — Анализ и планирование** (Sonnet-5)
- Прочитать `WorkVault/Hermes-Backlog/TZ/MAIN_TZ_INVENTORY.md` — полный список существующих инструментов.
- Для КАЖДОГО существующего ТЗ оценить: есть ли хотя бы малейшая вероятность совместной работы с новым инструментом? Если да — зафиксировать связь.
- Проверить текущую инфраструктуру Hermes (`~/.hermes/config.yaml`, скиллы, кроны) — есть ли связь с разрабатываемым инструментом?
- Результат: драфт ТЗ с разделом «Связи с существующими инструментами» и «Связи с инфраструктурой Hermes».
- Записать в файл по процедуре A (новый инструмент) или B (доработка существующего).

**Шаг 2 — Архитектура и функциональные блоки** (Opus 4-7, повторяется до полной ясности)
- Роль: эксперт по архитектурным решениям.
- Проанализировать выявленные связи с имеющимися инструментами и инфраструктурой.
- Не додумывать — задавать вопросы с вариантами и рекомендациями (по правилам процедуры H).
- Спроектировать функциональные блоки инструмента, общую схему, место в экосистеме.
- Планировать максимальную связанность и переиспользование единых справочников/функциональностей (entities.json, contacts.enc, meeting-rooms.md и т.п.).
- Фиксировать результат в драфте ТЗ.
- **Повторяется** нужное количество раз до полной архитектурной ясности.

**Шаг 3 — Написание ТЗ** (Opus 4-7, повторяется до полной ясности)
- Роль: эксперт по разработке приложений.
- Обрабатывать вопросы пользователя, разрабатывать ТЗ.
- Сверяться с мировым опытом по разработке.
- При нестыковках по деталям реализации — уточнять у пользователя прямо здесь (со своими рекомендациями).
- При архитектурных нестыковках — возврат на Шаг 2.
- Фиксировать в драфте ТЗ по правилам workflow-tz.
- **Повторяется** нужное количество раз до полной ясности.

**Шаг 4 — Финализация ТЗ** (Opus 4-7)
- Роль: эксперт по разработке приложений.
- Критерий готовности: Opus завершил внутреннюю проверку И пользователь явно сказал «финализируй».
- Если нестыковки — возврат на Шаг 3.
- Перед финализацией — проверить по чеклисту качества:
  - [ ] Цель сформулирована одним предложением (что делает и зачем)
  - [ ] Все входные данные и выходные артефакты описаны явно
  - [ ] Каждый шаг реализации атомарен (один файл / одна функция)
  - [ ] Критерии успеха проверяемы (можно написать тест или команду)
  - [ ] Раздел «Что НЕ трогать» заполнен
  - [ ] Раздел «Связи с экосистемой» заполнен (или явно «Нет зависимостей»)
  - [ ] Открытые вопросы закрыты или зафиксированы с рекомендацией в разделе `## Открытые вопросы`
  - [ ] **Краткость + полнота:** ни одной лишней фразы, но ни одной пропущенной детали. Тест: если убрать любое предложение — потеряется важное.
- Записать финальное ТЗ по правилам workflow-tz, сообщить о готовности.

### Цикл разработки

1. **Бриф** — основная модель брифует по открытым вопросам (по правилам процедуры H), фиксирует решения в чате и в драфте ТЗ.
2. **ТЗ** — Шаги 2-4 выполняет Opus через `cronjob(repeat=1)`, читает все зависимости (смежные ТЗ, скиллы, реальный код на диске), версионирует (`v0.1.0 → v0.N.0`), регистрирует в `MAIN_TZ_INVENTORY.md`.
3. **Обновление ТЗ** — после каждого нового решения брифа Sonnet-5 вносит правки (bump версии, фиксирует `decisions_locked`); архитектурные изменения — Opus.
4. **Реализация** — после финализации ТЗ жди явного «берём в работу» от Саши. Реализация — отдельный процесс, не часть этого скилла.

### Правила автономии

- **Side-effect только по императиву** — никаких правок файлов/кронов/реестров без явного «делай».
- **Кроны НЕ создаются автоматически** — перечисляются в отчёте, создаются только по «ставь».

## Когда применять

- Пользователь просит создать/дополнить/переписать ТЗ инструмента или точечное ТЗ.
- Задача касается USERTOOLS (`MoveFromFF`, `AggregateFromMeetings`, …) и упоминается «ТЗ» / `*_TZ*.md`.
- Нужно заархивировать ТЗ или снапшот перед крупной правкой.
- Обновление реестра `MAIN_TZ_INVENTORY.md` или `MAIN_WORKVAULT_INVENTORY.md`.
- **Нужен план установки/настройки существующего инструмента** (RAG, systemd-демон, MCP-интеграция и т.п.) — хранится по той же схеме `TZ/<Topic>/<Topic>_TZ.md`.

Не применять для рабочих данных vault (`Projects/`, `People/`, `Meetings/`, `Contacts/`) и git-репозиториев Hermes-конфига.

## Ключевые инварианты

1. **Один master-файл на инструмент:** `WorkVault/Hermes-Backlog/TZ/<Tool>/<Tool>_TZ.md`.
2. **Не распыляться:** доработка существующего инструмента = новая датированная секция в master-ТЗ, НЕ отдельный файл. Точечные ТЗ — только если тема реально не привязана ни к какому инструменту, тогда `TZ/_misc/TZ-<topic>-<YYYYMMDD>.md`.
3. **Латиница-only** для новых имён файлов/папок в vault (Obsidian).
4. **Версия — только во frontmatter**, не в имени файла. `v1/v2/v3` в имени = старая схема, место в backup.
5. **Содержательный текст ТЗ пишет только Opus.** Sonnet/Haiku делают только механику: переносы, переименования, frontmatter, инвентарь, предварительный сбор зависимостей (search_files/grep по скиллам и существующим ТЗ).
6. **Согласование ТЗ ≠ команда на реализацию.** После финализации текста жди отдельного явного «берём в работу».
7. **Никогда не рестартовать gateway** из этого скилла.
8. **Master-ТЗ остаётся в WorkVault, пока инструмент используется.** Реализация конкретной доработки — не повод архивировать ТЗ. Архивация всей папки `TZ/<Tool>/` в `WorkVault_backup/Hermes-Backlog/TZ/_archived/<Tool>/` — только при выводе инструмента из эксплуатации, и только по явному решению Саши.
9. **`TZ/<Tool>/` содержит ТОЛЬКО ТЗ-документы.** Рабочие материалы инструмента — брифы (`briefs/`), research-заметки (`research/`), история обсуждений (`pm/sessions/`, `_review/`), runtime-state (`*.json` вроде `classification_memory.json`) — остаются в структуре самого инструмента (`USERTOOLS/<tool>/` или `WorkVault/Tools/<Tool>/`), не переносятся в `TZ/`. Составные ТЗ (модули, decisions-log ПРО сам текст ТЗ) — исключение, они часть ТЗ-контента.
10. **Backup не копит копии «на всякий случай/для истории».** Каждый файл в `WorkVault_backup/` — либо реальный архив выведенного из эксплуатации инструмента (по зеркальному пути), либо не нужен вовсе (уже есть в общем tgz-бэкапе миграции). Никаких доп. черновиков «сохранить на память» вне зеркальной структуры.
11. **Полная миграция — значит полная.** Если просят «пройтись по всем инструментам» — не работать по заранее данному списку, а сначала самому пройтись `search_files` по ВСЕМ `USERTOOLS/*` и `WorkVault/Tools/*` на `*TZ*.md`/`*ТЗ*.md`, и только потом переносить. Частичный список = придётся переделывать по второму заходу.
12. **Инфраструктурные планы** (systemd, RAG, MCP-интеграции) — хранить по той же схеме `TZ/<Topic>/<Topic>_TZ.md`. Критерий готовности: шаги выполнены + verification-команды прошли (не код/тесты).
13. **Формат открытых вопросов:** открытые вопросы в файле ТЗ — только в разделе `## Открытые вопросы` в конце файла. Формат: номер + вопрос + рекомендация Opus + варианты. После закрытия — переименовать в `## Решения (дата)`, варианты убрать, оставить только принятое решение. Решения интегрировать в тело плана, не только в отдельном разделе.
14. **Связи с экосистемой:** каждое ТЗ обязано содержать раздел `## Связи с экосистемой` (даже если связей нет — написать «Нет зависимостей»). Формат: список инструментов + тип связи (читает данные / пишет данные / использует справочник / запускается после).
15. **Язык:** ТЗ пишется на русском языке. Технические термины, пути файлов, имена классов/функций — на английском/латинице.

## Процедуры

### A0. Узкий инструмент, выделенный из крупного backlog-ТЗ

Если новый инструмент выделяется из крупного существующего ТЗ (например «Протокол from Summary» из «AggregateFromMeetings»):

1. Сначала — отдельный research-only Opus-кронджоб: читает все файлы крупного ТЗ + смежные скиллы + реальные примеры данных. **Явный запрет записи файлов** в промпте («только читай и анализируй»).
2. Результат research-прохода: резюме что переиспользуемо + черновик структуры разделов + пронумерованные открытые вопросы с рекомендациями + список блокеров.
3. Бриф с Сашей по открытым вопросам (процедура H).
4. Только после закрытия всех вопросов — создать файл ТЗ по процедуре A или B.

### A. Создать новое master-ТЗ для инструмента

1. Проверить, что нет уже `WorkVault/Hermes-Backlog/TZ/<Tool>/`. Если есть — не создавать заново, идти в процедуру B.
2. `mkdir -p ~/WorkVault/Hermes-Backlog/TZ/<Tool>/`.
3. Скопировать `templates/tool-tz-template.md` в `TZ/<Tool>/<Tool>_TZ.md`, подставить `<Tool>`, `version: 0.1`, `date`, `status: draft`.
4. Содержательное наполнение (Цель / Шаги / Критерии успеха / Что НЕ трогать / далее по контексту) — **делегируется Opus**.
5. Добавить строку в `TZ/MAIN_TZ_INVENTORY.md` (таблица активных, статус `draft`).

### B. Дописать секцию в существующее master-ТЗ

Мелкая доработка / новая фича существующего инструмента:

1. Открыть `TZ/<Tool>/<Tool>_TZ.md`, дописать в конец новую секцию с датой в подзаголовке (например `## Планируемая доработка: <название> (YYYY-MM-DD)`).
2. Обновить `last-section-added: YYYY-MM-DD` в frontmatter.
3. Не бампить `version` для мелких добавлений; бампить только для крупной ревизии/переписывания (>20% или смена major).
4. Обновить `updated:` и дату строки в `MAIN_TZ_INVENTORY.md`.
5. Не создавать новый файл под доработку — правило «не распыляться».

### B.1. Исключение — быстрая итеративная бамп-per-decision схема для многораундового брифа за один день

Когда ТЗ проходит **несколько раундов** архитектурного ревью/брифа в течение одного дня (несколько Opus-кронов «прочитать→доработать» подряд, каждый закрывает свою волну открытых вопросов) — правило B «не бампить version для мелких добавлений» **не применяется**. Вместо этого каждый раунд (даже одна короткая правка формата/уведомления/одно решение брифа) получает свой собственный minor-бамп (`0.1 → 0.2 → ... → 1.0 → 1.1`), с `last-section-added` в frontmatter, кратко описывающим суть именно этого раунда.

Почему это работает лучше обычного правила B в этом сценарии: при высокой скорости изменений (десятки правок за несколько часов) версия во frontmatter становится единственной надёжной контрольной точкой «что именно изменилось между раундом N и N+1» — без неё сложно отследить, какое именно архитектурное решение соответствует какой волне брифа, особенно когда несколько Opus-кронов работают последовательно над одним и тем же документом. Прецедент 10.07.2026 (ProtocolFromSummary): ТЗ прошло 11 версионных приращений за один день (v0.1 черновик → v1.1 финал с решениями брифа), каждое с понятным `last-section-added` — это позволило легко откатиться к «что решили на шаге X» при повторном обращении к документу позже в той же сессии.

Применять обычное правило B (не бампить по мелочи) для одиночных точечных правок вне контекста активного многораундового брифа/ревью.

### C. Крупная ревизия ТЗ (>20% содержимого или смена major-версии)

1. **Снапшот перед правкой** (см. `references/archiving.md`):
   ```
   TS=$(date +%Y%m%d-%H%M)
   mkdir -p ~/WorkVault_backup/Hermes-Backlog/TZ/<Tool>/
   tar czf ~/WorkVault_backup/Hermes-Backlog/TZ/<Tool>/<Tool>_TZ_snapshots-$TS.tgz \
       -C ~/WorkVault/Hermes-Backlog/TZ <Tool>/
   echo "[$(date +%H:%M:%S)] SNAPSHOT: <Tool>_TZ_snapshots-$TS.tgz" \
       >> ~/WorkVault_backup/_moved-$(date +%Y-%m-%d).log
   ```
2. Правки в текст — **делегируются Opus**.
3. Обновить `version:` и `date:` в frontmatter.
4. Обновить `MAIN_TZ_INVENTORY.md`.
5. Если стало >5 tgz-снапшотов на инструмент — удалить самый старый и записать в лог.

### D. Точечное ТЗ, не привязанное к инструменту

1. Создать в `TZ/_misc/TZ-<topic>-<YYYYMMDD>.md` (topic — латиница/транслит).
2. Frontmatter: `type: tz`, `topic`, `date`, `status: draft`.
3. Добавить в раздел "Точечные ТЗ" `MAIN_TZ_INVENTORY.md`.
4. По завершении работы над темой — переносим в `~/WorkVault_backup/Hermes-Backlog/_Done/TZ-<topic>-YYYYMMDD.md`, обновляем инвентарь.

### E. Архивация ТЗ инструмента (только при выводе инструмента из эксплуатации)

Триггер: **явное указание Саши**, что инструмент удаляется/не используется. Не срабатывает по завершению доработки, не по календарю.

1. `mkdir -p ~/WorkVault_backup/Hermes-Backlog/TZ/_archived/<Tool>/`
2. `mv ~/WorkVault/Hermes-Backlog/TZ/<Tool>/* ~/WorkVault_backup/Hermes-Backlog/TZ/_archived/<Tool>/`
3. Удалить пустую `TZ/<Tool>/`.
4. В `MAIN_TZ_INVENTORY.md` перенести строку из "Активные" в "Завершённые/архивные", статус `archived`.
5. Записать в `~/WorkVault_backup/_moved-YYYY-MM-DD.log`.

### G. Аудит-ревизия всех ТЗ («приведи все ТЗ в порядок / согласно воркфлоу»)

Триггер: пользователь просит проверить/привести в порядок все ТЗ сразу, не один конкретный инструмент.

1. Прочитать `MAIN_TZ_INVENTORY.md` — список всех master-ТЗ с их заявленным статусом.
2. Для каждого ТЗ проверить **три независимых пункта**, не полагаясь на память о более ранних выводах в этой же сессии (см. питфолл ниже):
   - **Frontmatter status** — входит ли в контролируемый enum (`active/draft/paused/archived/completed`)? Свободный текст в поле `status` (например описание фазы работ) — нарушение, значение переносится в `last-section-added`/тело документа, а не в поле статуса.
   - **Статус vs реальность кода** — физически проверить (`search_files`/`find`, не по отчёту субагента без сверки) существует ли код инструмента в `USERTOOLS/<tool>/` или `WorkVault/Tools/<Tool>/`. `status: active` без единого файла кода — расхождение, понижать до `draft`. Код есть и рабочий, а статус `draft` — расхождение в другую сторону, поднимать до `active`.
   - **Перекрёстные ссылки** — `refs:`/упоминания путей других ТЗ должны резолвиться на реально существующие файлы по актуальной схеме `TZ/<Tool>/<Tool>_TZ.md`. Старые пути (`Tools/<Tool>/`, `USERTOOLS/<tool>/<tool>_TZ.md`) — почти всегда устарели после миграции на текущую схему хранения.
3. Правки — чистая механика (frontmatter, пути, инвентарь), не переписывание содержания — можно выполнять не-Opus моделью.
4. Обновить `MAIN_TZ_INVENTORY.md` в той же операции — статусы и дата ревизии.
5. `rclone sync` в конце.

### H. Бриф по открытым вопросам ТЗ (один вопрос — один ответ)

Применять когда Opus вернул ТЗ с разделом «Открытые вопросы» (обычно 3-8 пунктов, каждый с рекомендацией) и пользователь просит пройтись по ним («в режиме брифа», «брифуемся», «давай открытые вопросы»).

1. **Один вопрос на сообщение.** Номер + краткая суть + варианты (цифрами 1/2/3, не буквами) + рекомендация с обоснованием одной строкой. Не вываливать весь список сразу как монолог, не переходить к следующему вопросу, пока предыдущий не получил ответ.
2. **Нумерация вариантов не переносится между вопросами.** Каждый вопрос — свой независимый набор 1/2/3, даже если предыдущий тоже был «1 или 2».
3. **Ответ пользователя = конец этого вопроса, сразу следующий.** Не переспрашивать, не резюмировать длинно — короткое «Принято — вариант N (обоснование в одну фразу)» и следующий пункт.
4. **Если пользователь просит «объясни понятнее» / «непонятно»** — не пересказывать прозой длиннее, а дать таблицу с конкретными примерами (реальные slug/значения из задачи), не абстрактные варианты A/Б.
5. **Если решение меняется по ходу брифа** (пользователь пересматривает более ранний ответ, например из-за нового критерия типа «а как это влияет на скорость поиска?») — прогнать оставшиеся/предыдущие пункты через тот же новый критерий явно, отметить какие пункты меняются, а какие нет, не молчать о пересмотре.
6. **После того как все вопросы закрыты** — отдать сводную таблицу «вопрос → решение» пользователю, затем делегировать Opus обновление самого файла ТЗ: раздел «Открытые вопросы» переименовать в «Решения Саши»/аналог, статус — принято (не рекомендация), явно отметить те пункты, где итоговое решение ОТличается от первоначальной рекомендации Opus, с обоснованием почему. Раздел решения должен быть интегрирован в тело плана (Шаги/Архитектура/Тесты), не просто пересказан в конце файла отдельным блоком.
7. **Один цикл ТЗ может проходить бриф несколько раз** (новые вопросы всплывают в диалоге уже после первого раунда решений — например пользователь предложил новый механизм, который сам поднимает новые вопросы) — каждый раунд бампит версию по процедуре B.1, не пытаться уместить всё в одну ревизию.

## Приложения к ТЗ

Когда в ходе работы над ТЗ накапливаются справочные материалы (реестры, бриф-решения, списки включений/исключений, таблицы анализа) — сохранять их как **приложения** рядом с master-ТЗ:

1. Файл приложения — в той же папке `TZ/<Tool>/`, имя: `appendix_<тема>_<YYYYMMDD>.md`.
2. В начале master-ТЗ (сразу после frontmatter, до раздела «Цель») — раздел **`## Приложения к ТЗ`** с таблицей:
   ```
   | Файл | Содержание | Дата |
   |---|---|---|
   | `appendix_<тема>_<YYYYMMDD>.md` | <одна строка что внутри> | YYYY-MM-DD |
   ```
3. При каждом новом приложении — добавлять строку в эту таблицу, не пропуская.
4. Приложения НЕ дублировать в других папках (`Registries/`, `Tools/` и т.п.) — единственная копия в `TZ/<Tool>/`.

**Цель:** при открытии любого ТЗ сразу видно все связанные материалы — не нужно искать по vault.

## Common Pitfalls

- **Не создавай `<Tool>_TZ_v2.md` в активной папке** — v-в-имени только для архивных снапшотов в `WorkVault_backup/`.
- **Не переименовывай кириллические архивные файлы** в `WorkVault_backup/` (это архив, не навигация Obsidian).
- **Не забудь обновить `MAIN_TZ_INVENTORY.md` в той же операции**, что и правку ТЗ, — иначе расхождение.
- **Не пиши содержание ТЗ сам, если ты не Opus** — делегируй. Механику (перенос, frontmatter, инвентарь) можешь.
- **Не рестартуй gateway.**
- **Не трогай `Projects/`, `People/`, `Meetings/`, `Contacts/`, `~/hermes-config*`, `~/hermes-workspace`.**
- **Не создавай отдельный точечный файл под доработку существующего инструмента** — это правило "не распыляться". Секция в master-ТЗ.
- **Согласовать текст ≠ начать реализацию.** Ждать отдельной команды.
- **Не путай "рабочие материалы инструмента" с "ТЗ-контентом"** — брифы/research/runtime-json остаются в папке инструмента, не в `TZ/<Tool>/`. Если сомневаешься к какой категории относится файл — не трогай его и зафиксируй как открытый вопрос, не переноси наугад.
- **Не оставляй файлы "для истории" в backup вне зеркальной структуры** — либо это архив выведенного из строя инструмента по правильному пути, либо оно уже есть в общем tgz-снапшоте и отдельно не нужно.
- **При задаче "перенести все ТЗ по всем инструментам" — сначала `search_files` по всему дереву**, не полагайся на список, данный в промпте: он может быть неполным (проверено на практике — первая волна пропустила 9 инструментов).
- **Заголовок секции доработки не обновляется сам, когда работа завершена и проверена.** Прецедент 13.07.2026 (MoveFromFF, byte-limit ownCloud): делегированный Opus-крон полностью реализовал доработку (код, тесты, ручная проверка на живом сервере), но оставил заголовок секции как `## Планируемая доработка: ...` — статус «завершено» был виден только по содержимому, не по названию раздела, пришлось поправлять вручную после факта. При делегировании реализации уже запланированной секции — явно указывай субагенту обновить сам заголовок по образцу уже существующих завершённых секций документа (например `## Доработка: ... — РЕАЛИЗОВАНО (дата)` / `— РЕАЛИЗОВАНО И ПРОВЕРЕНО`), не только `status`/`last-section-added` в frontmatter. Проверяй заголовок как отдельный пункт финальной сверки ТЗ, не полагайся, что раз тесты зелёные — заголовок тоже актуален.
- **В длинной цепочке ТЗ→бриф→обновление** — при каждом новом cronjob явно сообщать Саше: «это только правка ТЗ» или «начинаю реализацию». Не полагаться что тип операции очевиден из контекста.
- **Decommissioned-инструмент ≠ автоматическая архивация без подтверждения.** Отсутствие кода в `USERTOOLS/` — основание предложить архивацию (процедура E), но финальное решение всегда за Сашей: один явный вопрос с рекомендацией и обоснованием, не молчаливое действие.
- **Не доверяй отчёту субагента о существовании кода без собственной проверки.** Субагент может сказать "код есть (N .py)" на основе поверхностного листинга (venv/cache файлы, устаревшая память сессии) — перед правкой статуса `active`↔`draft` физически проверить `search_files`/`find` в реальном коде инструмента (не в `venv`/`node_modules`/`__pycache__`). Прецедент 06.07.2026: собственная более ранняя проверка в той же сессии дала "кода нет", а прямая повторная проверка нашла реальный пакет — расхождение из-за устаревшего вывода, не из-за ошибки субагента.

## Связанные файлы

- `templates/tool-tz-template.md` — каркас нового master-ТЗ.
- `templates/misc-tz-template.md` — каркас точечного ТЗ.
- `references/archiving.md` — эталонные команды tar/mv/логирования.
- В vault: `~/WorkVault/Hermes-Backlog/TZ/_TZ-WORKFLOW-RULES.md` — источник истины для правил (доступен и Cursor).
- В vault: `~/WorkVault/Hermes-Backlog/TZ/MAIN_TZ_INVENTORY.md` — реестр всех ТЗ.
- В vault: `~/WorkVault/MAIN_WORKVAULT_INVENTORY.md` — общий инвентарь vault.
- Backup: `~/WorkVault_backup/_Backup-Rules.md` — правила backup.

## Быстрая проверка (smoke)

Если LLM просят: «Создай ТЗ для нового инструмента `FooBar`» — файл должен оказаться строго по пути `~/WorkVault/Hermes-Backlog/TZ/FooBar/FooBar_TZ.md` (латиница, без `v`-суффикса), и `MAIN_TZ_INVENTORY.md` — обновлён. Если хоть одно из двух не выполнено — процедура нарушена.

## Verification Checklist

- [ ] Новое ТЗ создано строго по пути `~/WorkVault/Hermes-Backlog/TZ/<Tool>/<Tool>_TZ.md` (латиница, без `v`-суффикса в имени)
- [ ] `MAIN_TZ_INVENTORY.md` обновлён в той же операции, что и правка ТЗ
- [ ] Содержательный текст ТЗ писал Opus (не другая модель); механику (перенос, frontmatter, инвентарь) можно делать не-Opus
- [ ] Согласование текста ТЗ не спутано с командой на реализацию — есть отдельное явное «берём в работу»
- [ ] Полный аудит (процедура G) прошёл по всему дереву `search_files`, не по заранее данному списку инструментов
- [ ] Backup не содержит файлов «на всякий случай» вне зеркальной структуры
- [ ] Узкий инструмент, выделенный из крупного backlog-ТЗ: перед написанием текста был отдельный research-only Opus-кронджоб (без прав на запись файлов), вернувший резюме + черновик структуры + пронумерованные вопросы с рекомендациями + список блокеров
- [ ] Когда пользователь называет проект вместо прямой ссылки на блокер-документ — сначала искать через `card.md` → `confluence_id` → `/child/page` API, не переспрашивать ссылку сразу
- [ ] При многораундовом брифе/ревью за один день (несколько Opus-кронов подряд над одним ТЗ) — версия бампится на каждый раунд с осмысленным `last-section-added`, даже для мелких решений (процедура B.1), а не оставлена постоянной по правилу B
- [ ] Бриф открытых вопросов ведётся по одному вопросу за сообщение (процедура H), не монологом; финальные решения интегрированы в тело плана, не просто пересказаны отдельным блоком
- [ ] В цепочке ТЗ→бриф→обновление→реализация каждый cronjob явно помечен пользователю как «только правка документа» или «начинаю реализацию» (процедура H.1) — не полагаться, что это очевидно из контекста
- [ ] Если в ходе работы над ТЗ появились справочные материалы (брифовые решения, реестры, списки) — сохранены как `appendix_<тема>_<YYYYMMDD>.md` в папке `TZ/<Tool>/`, и таблица «Приложения к ТЗ» обновлена в самом ТЗ сверху
