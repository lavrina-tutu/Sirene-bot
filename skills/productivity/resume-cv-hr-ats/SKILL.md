# Резюме/CV: HR + ATS/AI-читаемость для Саши

## Триггеры
«сделай резюме», «почисти резюме», «переработай CV», «сделай резюме читаемым для ИИ/HR», «добавь текущий опыт в резюме».

## Главные правила (жесткие)

1. **Поштучно, не выдумывать факты и метрики.** Все цифры/эффекты, которые Саша не подтвердил, писать плейсхолдером `[вставить]` или `[на уточнение]`, и задавать по одному с вариантами+рекомендацией (R3). НИКОГДА не выдумывать проценты, деньги, «сократил в N раз», headcount, статусы инициатив. Плейсхолдер при финализации НЕ заменять фразой «детали расскажу на собеседовании» — такого рода хвосты в тексте резюме запрещены (Саша: «это и так понятно»). Заменять законченным нейтральным результатом без цифры («Решение позволило избежать лицензионных расходов», «меньшие затраты на развитие и владение») или оставлять `[вставить]`.
2. **Сохранять шаблон hh.ru** (структуру не менять): Шапка → Желаемая должность → Обо мне → Опыт (новый→старый) → Образование → Курсы/сертификаты → Тесты → Навыки → Языки.
3. **Желаемая должность — ровно одна, без «гирлянды».** Например «Руководитель проектов», не «Руководитель проектов / AI / PMO / Data». Синонимы целевой роли — только в «Обо мне», не в заголовок.
4. **Текущий работодатель — первым местом опыта; предыдущее место — закрыть точной датой ухода.** Два «настоящее время» подряд — красный флаг для ATS (парсер читает как ошибку дат или скрытую подработку).
5. **Никакого AI-washing.** Честно писать «фокус AI с <года>», если фокус свежий; не «10 лет AI». Роль называть по официальной должности, без self-назначений («Head of», «руководитель AI-направления»).
6. **Порядок внутри каждого места: достижения → обязанности → стек**, не наоборот. Достижения — 3–6 буллетов «действие — результат/эффект»; обязанности — 4–6 уникальных для места (не копипаст между работодателями).
7. **Даты в резюме не указывать** — решение Саши (в т.ч. не раскрывать период портфелей/внутренних проектов прошлых мест, «уйти от дат»). Блок, информацию о периодах несущую, писать без годов.
8. **Перерасход/неудачные метрики в резюме НЕ раскрывать** — «выполнили, но в бюджет не уложились» только при прямом вопросе на интервью. Не преподносить срыв бюджета без оговорки в резюме.
9. **Причину поиска подавать без слабости и по месту: текст резюме ≠ интервью.** НИКОГДА «меня могут сократить / новый начальник может не захотеть». В «О себе» hh-резюме внутренние обстоятельства работодателя (перестройка, смена гендиректора и собственника, уход руководителя департамента) — красный флаг по вердикту ревизора, подтверждено Сашей: писать только нейтральный мотив «Ищу среду, где проектный подход и развитие людей находятся в приоритете», детали перестройки — устно на собеседовании. Полный сюжет без слабости (перестройка после смены гендиректора, жёсткая оптимизация, ушёл руководитель, который выстроил департамент + позитивный мотив: компания и руководитель, приветствующие развитие) — материал для прожарки/интервью, не для текста резюме.
10. **Сильные нематериальные активы выносить в «О себе»/прожарку:** «частично автоматизировал свою роль» агентами на LLM (протоколы, архив встреч, корп.документы) и «documentation-first + работа в содружестве с LLM над ТЗ» — это редкая для РП ценность, закрывает вопрос «что ты технически умеешь». Подавать как «бизнес-аналитик нового типа» (фокус на бизнес-задаче, а не на ручном коде), честно оставляя «не senior заметный программист».

## Процедура

1. **Извлечь текст** из исходника резюме. Для RTF: pandoc в этой среде НЕ умеет `-f rtf`; рабочий путь — `uv venv .venv && uv pip install --python .venv/bin/python striprtf`, затем `striprtf.rtf_to_text` с `encoding='cp1251'` (см. pitfall ниже). Для .xlsx — `openpyxl` (прочитать каждый лист, `data_only=True`); для .docx — `pandoc -t plain` (таблицы договоров/заданий пантоком рвутся по колонкам — читать содержимое ячеек по смыслу, цифры-части сумм склеивать из соседних строк). Саша может прислать фактуру по предыдущим местам прямо файлом (xlsx/docx «lessons learned», «Задание» из договора) — это первоисточник, извлекать из него и даты, и суммы, и роли.
2. **Собрать факты о текущем работодателе из первоисточников**, не спрашивать вслепую: `~/WorkVault/Entities/*/` (card.md, protocol.md), `Meetings/NewMeetings|GoldProtocols`, Jira REST (`JIRA_TOKEN` из `~/.hermes/profiles/default/.env`, `hq.tutu.ru/rest/api/2/user`), Confluence (`CONFLUENCE_TOKEN` из `~/USERTOOLS/ConfluenceSync/.env`). Вытащить: официальную должность, дату начала, департамент, портфель проектов. **Статусы инициатив текущего работодателя закрывать не голословно** — искать корпоративную страницу «Проекты. Статус проектов» (Confluence АиД; в WorkVault под `Outbox/Проекты_Статус_проектов_*.md`): она несёт официальный статус и дату по каждому проекту (Завершён/В работе/Приостановка). Сверять по ней формулировки буллетов блока опыта вместо «спросить Сашу статус каждой» — большинство статусов уже подтверждено страницей.
3. **Собрать черновик** в Markdown в том же hh.ru-шаблоне: «Обо мне» (кто сейчас + домен, откуда сила, масштаб, как работает, что ищет), текущий работодатель первым местом, достижения вверх с `[вставить]`, навыки по приоритету.
4. **Запустить архитектора (Codex) на проработку/ревью** черновика по канону: роль архитектора через `codex exec -C "$HOME" -m gpt-6.1-sol -c 'model_reasoning_effort="high"' --skip-git-repo-check --sandbox read-only --json "$(cat /tmp/prompt.md)"` (ad-hoc консультация вне DevWorkflow — прямой codex exec, не pipeline invoke-role). Промпт файлом: полный текст резюме + факты + ограничение «не выдумывать, пробелы помечать, уважать решения Саши (не озвучивать перетрату, не указывать даты)». Парсить ответ из JSON-потока: agent_message НЕ является top-level типом — его надо искать как узел с `type=="item.completed"` и `item.type=="agent_message"` (текст в `item.text`); top-level `thread/turn.started/completed` — служебные, `item.completed` с `type=="command_execution"` — команды, которые архитектор сам выполнил (частый довод). Сканировать только `item.completed`, где `item.type=="agent_message"`. Cursor-cli — только откат/фоллбэк, не основной путь. Для РЕВИЗИИ готового чистовика (ATS-красные флаги, вода/канцелярит, читабельность для человека) роль ревизора, не архитектора: `codex exec -C "$HOME" -m gpt-6-astra -c 'model_reasoning_effort="high"' --skip-git-repo-check --sandbox read-only --json "$(cat /tmp/rev_prompt.md)"`. Промпт передавать ПОЗИЦИОННЫМ аргументом — флаг `-p`/`--prompt-file` в этой версии CLI падает («pass a plain name such as `work`»). Промпт ревизору: полный текст резюме + жёсткие решения Саши (даты не возвращать, перерасход МКБ не озвучивать, «300 запросов» не фигурирует, МИП/ИСПЗ раздельно, B2 единый, не выдумывать цифры) + формат правок «[секция] было → станет». Правки ревизора не применять слепо: стилистические — да; режущие фактуру/детали (плейсхолдеры эффекта, «благодарности руководства», полные названия проектов, полные редакции блоков) — откладывать в полный черновик Саше (см. п.7).
5. **Закрыть «Открытые вопросы» по одному** (R3): дата ухода, юр./hh-имя работодателя, метрики по каждому достижению, статусы инициатив, уровень английского, рабочие инструменты 2025–2026. **Для каждого плейсхолдера-строки проекта предыдущего работодателя собрать фактуру из файлов/речи Саши: заказчик, бюджет, период, роль, эффект.** Если в одном сообщении Саша назвал несколько проектов, не разносить их по строкам, пока не подтверждено, что это разные проекты: задать один связующий вопрос «это один и тот же проект или разные?» (всегда по одному вопросу за раз, варианты + рекомендация — R3).
6. **Сохранить черновик Саше** в `~/WorkVault/Outbox/` (не Inbox — см. workvault-outbox), запустить `systemctl --user start owncloud-sync.service` и ПОДТВЕРДИТЬ доставку `rclone lsjson owncloud:WorkVault/Outbox/` — exit 0 сам по себе не значит, что файл ушёл.

7. **Сборка итогового резюме** (когда Саша просит «собери весь блок резюме»): сперва закрыть открытые вопросы по фактуре, затем ОБЪЕДИНИТЬ отдельные block-faktura-файлы (ТУТУ, Синимекс, «прочие блоки») в один `resume_final_faktura_YYYYMMDD.md` в `~/WorkVault/Personal/resume/` — конкатенация с заголовком-меткой источника перед каждым файлом (execute_code + read_file: снять префикс `N|` с каждой строки; после склейки доставить в WorkVault и синхронизировать). Затем одним промптом архитектору (Codex) отдать этот единый файл фактуры + приоритет детализации. Аналогично сам чистовик `Ткаченко_*_чистовик_YYYYMMDD.md` класть в `~/WorkVault/Outbox/` и подтверждать доставку rclone. Приоритет блока — по релевантности целевой роли и «свежести», НЕ по длительности: текущий работодатель — самый подробный; ближайшие сильные места (Синимекс, Softline) — полноценные, в едином стиле, НЕ ужимать; давние позиции (инженерные) — компактно. Уточнять у Саши по каждому месту заранее: что развернуть, что сжать, что оставить «для общего развития». **После ревизии держать ДВА файла в Outbox:** чистовик (правки применены) и `..._черновик_полный_YYYYMMDD.md` = чистовик + блок «Полные сведения по проектам» со всеми убранными ревизором деталями и пометками, куда их вернуть. Саша правит полный черновик сам и решает, что убрать/оставить; в утверждённый финал блок не входит.
8. **Прожарка/подготовка к интервью через архитектора**: отдельный промпт Codex на генерацию вопросов нанимателя с ДВУХ перспектив — (А) бизнес-заказчик/руководитель департамента (сложные кейсы, подход, базовые знания, работа с людьми, гарантия результата в срок) и (Б) руководитель проектного офиса PMO (методологии/фреймворки, практические инструменты MS Project/Jira/Confluence, процессы, портфель и зрелость). Формат ответа: по каждому вопросу «на что проверяет» + «идея ответа» на фактах из резюме; отдельные разделы для «битых вопросов» (слабых мест) и топ-10 вероятных. Сохранить в `~/WorkVault/Personal/resume/`. Акцент на компетенциях и подходе, а не пересказ послужного списка. Это вопросы НАНИМАТЕЛЯ — их зададут Саше на интервью.
9. **Сбор материала полного блока опыта («разберём блок ТУТУ/Синимекс» под аудиторию)**: если Саша просит раскрыть конкретный блок «чтобы пройти HR-скрининг, увидел бизнес-заказчик и руководитель PMO» — не выпытывать факты вслепую: одним Codex-промптом заказать архитектору СПИСОК ВОПРОСОВ К САШЕ (это вопросы ассистента, собирающие фактуру для блока, — НЕ вопросы нанимателя из п.8), сгруппированный по блокам (ТУТУ: хайп/результаты, методология/PMO-взгляд, новая роль в аналитике; Синимекс: портфель/кейсы, методология/PMO; общие). Формат каждого вопроса: (а) сам вопрос, (б) зачем нужен / какую аудиторию закрывает, (в) пример желаемого раскрытия — без выдумывания, с `[вставить]` на неподтверждённые цифры. Промпт отдаёт Codex полный материал (резюме, фактура, вердикты, протокол сессии) + контекст «кто такой кандидат». Результат сохранить `~/WorkVault/Personal/resume/resume_context_questions_YYYYMMDD.md`, синхронизировать. Затем задавать вопросы Саше по ОДНОМУ (R3), фиксировать ответы в фактуру. Перед серией держать готовой сводку известных проектов с выгодами — Саша может спросить контекст («какие у нас проекты и какие в них выгоды») до ответа на первый вопрос; не подтверждённые выгоды/цифры помечать и просить подтвердить. Для текущего работодателя целевые метрики искать в Confluence-страницах проекта («<Проект>. Контроль достижения цели О1», «<Проект>. Метрики качества…», дашборды Metabase) через CQL title-поиск, а НЕ брать устно: страницы несут официальные KR (проценты/сроки/пользователи) — фиксировать их в фактуре как подтверждённые после одобрения Сашей найденных страниц; устную цифру, расходящуюся со страницей, помечать и уточнять. Когда официальные KR есть, блок строится вокруг достижения OKR, а не вокруг произвольной метрики. **В каждый блок опыта собирать и «эффект после запуска» (что получил заказчик после внедрения, кто пользовался результатом, что улучшилось), а не только факт доставки/акта.** Архитектор отмечает «доставка описана сильнее, чем результат заказчика» как типовой пробел; уточнять у Саши по 1–2 проектам блока, какой бизнес-/операционный эффект реально наступил после сдачи (налоговые преференции, перевод сервисов на новую платформу, запуск промышленной эксплуатации, совместимость со старым инструментом через адаптер) — это отличает РП от «просто довёл до акта».

## Pitfalls

- **Расшифровывать неразборчивые голосовые названия компаний/инструментов по фонетике+контексту, затем подтверждать.** Саша диктует транскрипцией, где названия ломаются: `cinemaxi`→Синимекс, `гера/жира`→Jira, `прожито`→MS Project, `хордовые офисные`→Microsoft Office, `сжигание (трудозатрат)`→burn-down, `даты гауменс`→data governance, `три сигма`→Trisigma, `мессерскую эль`→MS SQL. Сопоставить фонетически и по контексту (домен/период/стек), внести расшифровку, одну строку «понял как …» для сверки без раздувания диалога. Не выдумывать значение, если фонетического соответствия нет.
- **Точные названия и годы сертификатов/курсов брать из исходного файла резюме, не из пересказа и тем более не угадывать.** Голосовая формулировка («прошёл сертификацию по управлению проектами, аналог PMP») НЕ даёт ни точного имени сертификата, ни года. Перечитать раздел «Повышение квалификации/Тесты» черновика и взять строку дословно (напр. `2019 · PM Expert — «Эксперт по управлению проектами» (сертификат PME)`, `2020 · Scrum Trek — Certified ScrumMaster (Scrum Alliance)`, `2005 · M2073 … Microsoft SQL Server`). Помнить: в черновике уже есть все курсы и тесты.
- **Привязку сертификата к работодателю выводить из года сертификата против периода занятости, не из памяти.** Если не помнят, где получен сертификат, сопоставить год сертификата с интервалами работы (напр. PME-2019 → внутри Softline фев2017–фев2020; ScrumMaster-2020 → начало Синимекс март2020–2025) и проверить логикой рассказа; подтверждённую привязку зафиксировать. Не смещать факт по памяти.
- **Не выдумывать аббревиатуры/термины из неразборчивой голосовой фразы Саши.** Если в сообщении встретился неоднозначный термин («ПСДМ-вопросы» и т.п.) — нет такого однозначного расшифровщика, и НЕ домысливать и не подставлять своё значение как будто это его. Спросить простыми словами, что он имел в виду, прежде чем генерировать. Расшифровка по контексту допустима только для общеизвестных аббревиатур (МИП/ИСПЗ) с подтверждением, не для личных/новых.
- **RTF не конвертируется через `pandoc -f rtf`** в этой версии («Unknown input format rtf»). Решение: `uv venv` + `uv pip install striprtf` → `rtf_to_text(data, encoding='cp1251')`. Код cp1251 обязателен для русского Word-RTF. Копировать исходник в scratch (`~/.hermes/cache/scratch/`), работать с копией, не трогать оригинал.
- **Не принимать ответ Саши молча.** Каждый подтверждённый факт (дата, должность) сразу вносить в файл и пересинхронизировать; в «Открытых вопросах» помечать `✅ Закрыто`.
- **«О себе» без лида про общий стаж** («28+ лет в ИТ») — возраст + студенческие годы как главный хук слабы для скоринга; ядро — стаж управления проектами и текущий фокус. Студенческие подработки не выносить в лид.
- **Английский — один уровень.** Тест «Intermediate» (обычно B1) против заявленного B2 = рассинхрон для ИИ-скоринга; спросить, что реально.
- **Навыки на hh.ru — облако тегов по приоритету, не разделы с заголовками.** Первые 8–10 тегов читают и человек, и парсер. Порядок: PM-ядро → методологии → AI/data → PMO-инструменты → короткий бэкграунд. Архаичные теги (БОСС-Компания, Omnitracker, HTML, C#, time management, вождение) — шум для роли PM; спускать в текст опыта или убирать.
- **Метрика не обязательна — качественный эффект лучше фейковой цифры.** Если нет числа, писать «внедрил, запустил, провёл пилот, регламентировал» + статус, не «+30%».
- **Не брать наименования из текущего черновика некритично — в нём могут жить ошибки.** Строки прошлых мест («РСХБ — шина IBM», «ГАЗПРОМ — адаптер») часто неточны. Когда Саша называет реальное имя (МИП, DStar, ИСПЗ) — сверять с черновиком и исправлять, а непонятное сокращение платформы/продукта расшифровывать по интернету (в сочетании с вендором-работодателем, напр. «МИП РСХБ Синимекс»), уточняя у Саши, а не угадывать стек.
- **Аббревиатуры банковских проектов аппаратно неочевидны** (МИП — модернизированная интеграционная платформа, ИСПЗ — система проблемных задолженностей, СИП, DStar, АБС) — их полные формы не выводить из контекста, искать/спрашивать; роль назвать по реальной функции (пришёл на проблемный проект → закрыл с актом), а не по буквам аббревиатуры.
- **Присланные Сашей файлы-примеры — это НЕ обязательно фактура для резюме.** Сводные бюджеты, таблицы, обезличенные сверки (напр. «Обезличенный_сводный_бюджет_2024.xlsx») часто присылает «для общего развития» — как материал для подготовки к интервью и возможной «прожарки» по проектам, а не для раздувания буллетов. Перед внесением в резюме уточнять цель (в резюме / в архив-подготовка / просто посмотреть). Если в архив — сохранить разбор + исходник в `~/WorkVault/Personal/resume/`, синхранутировать, а резюме не трогать.
- **Разделять независимые проекты компании**, если Саша явно сказал «это разные проекты, не смешивай» (напр. РСХБ МИП/АБС и ИСПЗ) — не склеивать их в один буллет даже при общем заказчике; каждому отдельная строка.
- **Цифры по текущему работодателю брать из корпоративных страниц метрик/OKR, не из устного пересказа.** Устное («300 запросов») может не совпадать с зафиксированным KR («≥50 уникальных пользователей в неделю»); страницы «Контроль достижения цели О1»/«Метрики качества…» — авторитетный источник целевых метрик; после подтверждения Сашей страниц цифры из них можно использовать как подтверждённые. Как найти страницы без pageId: CQL по заголовку через Confluence REST search: `curl -s -H "Authorization: Bearer $CONFLUENCE_TOKEN" --get --data-urlencode 'cql=title ~ "AI-аналитик" ORDER BY title' "https://dom.tutu.ru/rest/api/search" | python3 -m json.tool` (кириллицу обязательно через `--data-urlencode`; при шуме сужать `space in (...)`).

## Итоговый RTF-файл (клон эталона hh.ru)

Когда Саша просит «отдать итоговый RTF по эталону» (формат оформления = выгрузка резюме с hh.ru в Word, со шрифтами/цветами/таблицами/местом под фото), не собирать RTF с нуля через pandoc — **клонировать исходный RTF-эталон**: скопировать каркас, шапку и хвост побайтово, перегенерировать только тела секций.

- **Что копировать как есть (побайтово), что генерировать:** префикс `raw[0 : offset(первый \trowd после \sectd)]` = шрифты (fonttbl), colortbl, stylesheet, header/footer-колонтитулы, нумерация; шапка `[первый \trowd : offset(последний \trowd перед заголовком первой секции)]` = блок с фото (\pict) + ФИО + контакты; хвост `raw[offset({\*\latentstyles}) : EOF]` (или от `{\*\datastore`, что раньше) = латентные стили + OLE-датастор + финальная `}`. Тела секций — генерировать в той же разметке.
- **Разметка секции** (клонируется по шаблону): строка-заголовок = таблица полной ширины `\trowd \trftsWidth1 ... \cellx9638` с нижней границей `\clbrdrb\brdrs\brdrw15\brdrcf24`, текст Arial `\f1\cf22\fs24` (серый заголовок); строка-контент = отдельная `\trowd` без границ, текст `\f1\fs24`. Валидная ячейка: `\pard \intbl \ql ...текст \cell \row`. Буллет = `\bullet \tab`.
- **Цвета в colortbl этого RTF:** cf22 = `#AEAEAE` (серые заголовки секций), cf24 = `#D8D8D8` (тонкие линии-разделители), cf27 = `#BCBCBC` (границы). Основной текст чёрный, без `\cf`.
- **Кириллица в RTF — `\'xx` hex-эскейпы cp1251**, слова разделены пробелом; для генерации писать hex подряд без вставок `\loch\f1\hich\f1` (они необязательны). Русский кодировать `''.join("\\'%02x" % c for c in ch.encode('cp1251'))`, ASCII оставлять как есть; итоговый файл писать `encode('cp1251')`.
- **Проверка после сборки:** баланс `{`/`}`; все заголовки секций и контрольные фразы присутствуют в расшифрованном тексте; `\pict` и `\datastore` на месте (фото и техданные сохранены).

## Дополнения слияния: область действия и источники

Эти уточнения имеют приоритет при противоречии с примерами выше; прежние строки сохранены. Триггеры также включают сбор портфолио и проектных достижений для резюме или self-review, а «вакансия» — только в контексте адаптации резюме.

- После ревизии сохранять чистовик и полный черновик, но выбирать одну текущую содержательную базу. Новая присланная ревизия становится базой; прежние сохранять до явного поручения удалить, не сливать их автоматически. Перед удалением сохранить уникальную фактуру.
- Даты: правила 4 и 7 выше неоднозначны в отношении периодов занятости. Сохранять даты в фактуре, не добавлять и не удалять их автоматически в документе; проверить последнее решение в архиве переписки, а если граница неясна — уточнить у Саши, относятся ли ограничения к периодам работы или только к внутренним проектам.
- Навыки в hh.ru — приоритетные теги; в Markdown/RTF их представление определяется выбранным шаблоном. Не утверждать, что отсутствие категорий само по себе ломает ATS.
- Компании и их кейсы держать каждый в своём блоке; «О себе» — глобальные обобщения. Пилот не равен внедрению, определение scope — проектированию продукта, а координация портфеля — разработке системы. Кратность эффекта тоже требует основания: разность стоимостей — расчёт, не цитата из документа; сохранить исходные значения и метод, фактическую экономию не суммировать автоматически с предотвращённым риском. Без основания — качественный результат.

Для незавершённого проекта использовать также минутки, план .mpp, актуальную OKR-картотеку и дерево проектных страниц; отсутствие отчёта не означает отсутствие источников. Происхождение, актуальность и достаточность проверять для каждого тезиса.
