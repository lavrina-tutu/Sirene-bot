# dev-workflow — единственный маршрут разработки

`pipeline_context.py` — единственный owner B56 emit/check/invoke binding; второй
сборщик или manual fallback prompt запрещены.

Норматив процесса — Б55 master-ТЗ DevWorkflow; при расхождении открыть `/home/tkachenkoav/WorkVault/Hermes-Backlog/TZ/DevWorkflow/DevWorkflow_TZ.md`. Этот скилл исполняет процесс, а `references/canon.md` сохраняет канон имён, ролей и G6. Модели и backend берутся только из `tools.dev_workflow` YAML, не из текста скиллов.

Оркестратор ведёт факты, очередь и вызовы; архитектор принимает содержательные решения, ревизор их согласует, исполнитель реализует по согласованному плану. Оркестратор не подменяет эти решения. Все новые сущности сохраняют маркер **[NEW-ENTITY, требует согласования Саши]** и не проектируются/не создаются без такого согласования.

## Исполняемая таблица

| Событие / состояние | Обязательное действие |
|---|---|
| Приём поручения | Зафиксировать факт приёма. `idea=true` — только triage, не автостарт. Готовая задача получает `ready_at`; одна задача владеет потоком до `GATE:done` и доставки отчёта. |
| Выбор работы | Выбрать первую готовую задачу по FIFO (`ready_at`, затем установленный порядок записи); порядок меняется только явным указанием Саши с evidence. Не пропускать удерживаемую задачу ради следующей. |
| `WORK` | Для фазы роли: `emit-prompt` с rc=0, затем единственный `invoke-role`. Для фазы оркестратора выполнить только действие из рецепта и подтвердить evidence. |
| `AUTO_GATE` | Проверить обязательную улику и завершить только штатным `complete-phase`. |
| `WAIT` | Записать причину, время, чей следующий шаг и условие возобновления. Блокер, квота, лимит, `interrupted` и `waiting_operator` удерживают поток. |
| `RECOVER` | Применить только «Техническое восстановление»: один corrective-повтор того же класса на фазу с новой уликой; второй такой сбой — диагноз/ожидание, не обход лимита. |
| `RECONCILE` | После обрыва сверить slug/phase, живость точного wrapper, журнал и канон. Notify не является завершением; готовый артефакт принимается только после этой сверки. |
| `INTERRUPTED` | Не запускать повтор молча. Зафиксировать факт и перейти в ожидание либо применить ровно один подходящий регламент. |
| Завершение | `done` возможен только после `GATE:done`, доставки AC-отчёта и evidence. `aborted` означает отменено. Runtime FAIL, отсутствие entry или мёртвый PID не равны PASS. |

Движение продолжается 24/7 по окончанию роли и проверенным событиям, без сообщения Саши; окно 19:00–09:00 не применяется. Лимиты провайдера не обходятся: при отказе ждать, после исчерпания — пауза до подтверждённого восстановления.

## Три разных регламента

1. **Техническое восстановление** — только recoverable-сбой того же класса и фазы; один corrective повтор, затем стоп и диагноз.
2. **Повтор замечания** — один и тот же дефект в двух последовательных `REV`; второй `REQUEST-CHANGES` останавливает путь до третьего круга и требует диагноза.
3. **Пересмотр требований** — новое указание Саши меняет контракт/AC/границы; это отдельная запись и согласование архитектора с ревизором. «Доделай» не является пересмотром и не сбрасывает счётчики.

Перед любым повтором указать один из этих регламентов, ссылку на прежний факт и новую улику. Счётчики не обнуляются.

## Границы роли и контекста

Перед каждой TZ/HF/BUG/REV-фазой обязателен только штатный путь:

```text
pipeline emit-prompt --slug <slug> --phase <PHASE> --out /tmp/task.md
# только после rc=0
pipeline invoke-role --role <architect|reviewer|executor> --prompt-file /tmp/task.md --workspace <ABS>
```

`/tmp/task.md` — выход `emit-prompt`, не архив; `--force` запрещён. Перед `complete-phase` проверять `context-used:` и применимый `pipeline check`. Пока жив wrapper, не выполнять `next`, `complete-phase`, `recover` или второй invoke.

Evidence SHA-256 — только реальный хеш артефакта, вычисленный ДО вызова: `sha256sum <файл>` в ту же команду, затем вставить его значение. Никогда не подставлять плейсхолдер (`____REAL____`) или выдуманный хеш — `complete-phase` записывает evidence дословно в journal, а прямой JSON/journal-edit запрещён, так что ложный отпечаток остаётся навсегда и превращается в расхождение при сверке. Первый вызов с заглушкой не «проверяется» последующим корректным — оба попадают в журнал. Полный контракт пакета и MUST-read — `references/context.md`; транспорт и граница wrapper — `references/invoke.md`.

## Состояние, ограничения и ссылки

Состояние меняется только штатным pipeline writer; прямой JSON-write запрещён. `status` показывает только последние 48 часов, архив — только по запросу. Нельзя создавать новый сервис, очередь, БД, канал, cron или обход guard-ов; Gateway не рестартовать. Боевой код pipeline, конфиг, state и журналы меняются только разрешённой фазой и write-set.

Предметные проверки, rollback и исторические пояснения остаются в references, но не образуют второй маршрут. `hermes-feature` и `tz-workflow` — предметные скиллы внутри этого процесса, не независимые очереди.

| Файл | Назначение |
|---|---|
| `references/canon.md` | имена, 10 кейсов, роли и G6 |
| `references/context.md` | пакет контекста и MUST-read |
| `references/invoke.md` | invoke, wrapper и evidence |
| `references/operational-pitfalls.md` | локальные pitfalls, восстановление и rollback |
| `references/cases-guide.md` | выбор кейса без изменения канона |
| `references/kanban-mechanics.md` | только историческая read-only справка |
| `references/onboarding.md` | краткий вход для заказчика |

B56 использует один owner контекста: `emit-prompt` выпускает immutable packet pair,
`invoke-role` принимает только эту пару, а G2 сверяет accepted binding. Ручной prompt и
fallback запрещены; правила полей и MUST-read — в `references/context.md`.

Для `MIGRATION` единственный owner допуска —
`pipeline_mig_complete_guard`: `next`, emit, invoke и direct complete требуют
побайтно проверенные proof каждого предшествующего блока. Aggregate `GATE:block-accept`
или ранний done не заменяют собственный accept; sirene-фазы не получают packet/invoke.
