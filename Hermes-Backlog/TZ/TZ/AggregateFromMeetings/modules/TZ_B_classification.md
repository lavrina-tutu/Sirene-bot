# Модуль B. Классификация встреч

## Назначение
Определить, к каким проектам и/или контактам относится встреча. Одна встреча → N проектов (типично 1‑1 и стратегические синки покрывают несколько). Использует: имя файла, заголовок, `Bullet points`, `Keywords`, участников, `classification_hints` из карточек проектов и `classification_memory.json`.

## Что уже зафиксировано
- Реестр проектов — гибридный: **16 slug-ов** (после брифа 21–22.06.2026, см. главное ТЗ §3.2; 13 проектов + 1 служебная категория `adm` + 2 синка), мелкое → unclear-очередь F на ревью (research v0.1, В1/В10). Концепция папки `_uncategorized/` снята (см. C3/M5): unclear-встречи C не обрабатывает.
- Learning layer: каждое подтверждённое соотнесение → `classification_memory.json`, подаётся в контекст LLM при следующем прогоне (research v0.1, В10).
- Slug — латиница, формат `Projects/<slug>/` (research v0.1, В9).
- Ключевые сигналы: `keywords` + `aliases` + участники + `classification_hints` + `negative_keywords` карточки (project-entity v0.1, Блок 2.6).

## Карточка модуля

🎯 **Функция:** Чистый Python (keywords, aliases, participants, syncs_memory) — определяет route и список slug-ов проектов/синка по заголовку и метаданным встречи. LLM-классификация при неопределённости — шаг в C.
⬅️ **Вход:** `MeetingPackage.summary_path` (заголовок) + участники + `projects.md` + `syncs_memory.json` + `classification_memory.json`
➡️ **Выход:** `{route: "project"|"1on1"|"multisync"|"unclear", project_slugs: list[str], sync_slug: Optional[str], people_hint: list[str], matched_aliases: dict}` → C (route=project/1on1/multisync) или F (route=unclear, без C)
🔗 **Зависимости:** A (данные), projects.md, syncs_memory.json
📋 **Архитектура:** Чистый Python, без LLM. Заголовок — подсказка, не источник истины. Получатели: C → {D, E, H}, G.

## Алгоритм классификации (финальный, 2026-06-19, единая точка истины)

⚠️ **Важно (C1):** алгоритм route живёт ТОЛЬКО в B.Роутере. Модули E.Люди и H.Синки на алгоритм только ссылаются. Enum route везде: `project | 1on1 | multisync | unclear` (вариант `unresolved` исключён).

Ключевой принцип: **матч на `syncs_memory.json` первичен**; алиасы проектов из текста встречи вторичны; количество участников — третичный фактор. (ВП1, Вариант В.)

### Обработка unclear

**Еженедельный дайджест (модуль F):**
- Раз в неделю PM получает TG-список всех накопленных `unclear` встреч
- Для каждой: название + дата + участники + что нашли в алиасах
- PM размечает: slug проекта / `1on1 <имя>` / `multisync` / `trash`

**После разметки PM:**
- Если slug/1on1/multisync → **обязательный повторный прогон** модуля C по этой встрече
- Алиас добавляется в `classification_memory.json` с `source: pm_manual, confidence: confirmed`
- Если `trash` → встреча помечается `skip: true`, больше не появляется в дайджестах

### Граница 1on1 vs project

- 2 участника + **1 проект** → `project` (встреча по проекту, сигналы только в D)
- 2 участника + **2+ проекта** → `1on1` (сигналы и в D по каждому проекту, и в E по человеку)

⚠️ **Исключение** (изменено 2026-06-22: I5 fix): при явном сигнале «1-1» в названии встречи — `route=1on1` даже при одном проекте (Шаг 0.5 алгоритма); проект уходит в `route_project_slug`. Шаг 3 — частный случай Шага 0.5 (нет алиаса в заголовке).

### route_project_slug для 1on1 (R7)

<!-- изменено 2026-06-22: R7 -->

Для `route=1on1` B парсит заголовок встречи на наличие явной проектной привязки и заполняет `MeetingPackage.route_project_slug` (см. В1, поле `route_project_slug`):

| Паттерн в заголовке | Пример | Результат |
|---|---|---|
| `1-1 <Имя> / <alias>` | `«1-1 Кирилл / antibot»` | `route_project_slug = "antibot"` |
| `1-1 <Имя> <alias>` (в конце через пробел) | `«1-1 Кирилл antibot»` | `route_project_slug = "antibot"` (если alias матчится по `classification_memory`) |
| `<Имя>-<Имя> / <alias>` | `«Кирилл-Илья / parsing»` | `route_project_slug = "parsing"` |
| просто `1-1 <Имя>` | `«1-1 Кирилл»` | `route_project_slug = None` |

Парсер:
1. Берёт фрагмент после последнего `/` или последний токен заголовка.
2. Нормализует (lower, trim).
3. Сверяет с `classification_memory.json/projects[*].aliases` (active).
4. При single-match → заполняет `route_project_slug`. При multi-match — `None` (неоднозначность, разбирает PM).

### Разрешение неоднозначных имён в названии 1-1 (через AC.reports_to) — добавлено 2026-06-21

При route=`1on1` имя в названии встречи (паттерны «1-1 <Имя>», «<Имя>-<Имя>», «Daily <Имя>») часто неоднозначно (несколько людей с одинаковым first name, например «Саша»). Алгоритм:

1. B берёт владельца пайплайна (PM) — `OWNER_LOGIN` из настроек (для текущей инсталляции: `tkachenkoav`).
2. Берёт у этого человека из AC множество подчинённых: `direct_reports(OWNER_LOGIN) = {login | contacts[login].reports_to == OWNER_LOGIN}`, а также менеджера: `manager = contacts[OWNER_LOGIN].reports_to`.
3. Передаёт в C/E подсказку `hierarchy_hint`:
   ```
   {
     "owner": "tkachenkoav",
     "manager": "aralov",
     "direct_reports": ["kkrivorotov", ...],
   }
   ```
4. **Правило преимущества:** если в названии встречи `1-1 <Имя>` имя матчит ровно одного человека из `direct_reports` ИЛИ совпадает с алиасом менеджера — выбирается этот кандидат, fuzzy не запускается.
5. Если кандидатов из `direct_reports ∪ {manager}` 2+ или 0 — стандартный каскад `resolve_name()` (см. TZ_E).

  Получатели маршрута: C (для project/1on1/multisync), F (для unclear). Далее C раздаёт сигналы по scope в D / E / H (см. C/F).
- **В2 — Алгоритм поиска:** Нормализация заголовка (lower, убрать даты/стоп-слова) + substring match по keywords/aliases каждого проекта + score. Порог >70% → уверенный slug. Ниже → None, передаём в C. ⚠️ Заголовок — только первичная подсказка, не источник истины.
- **В3 — Мультипроектные встречи (M1):** ✅ **Уточнено 2026-06-19** — **один `MeetingPackage` на встречу**, один `MeetingSignals` на встречу. Принадлежность сигнала проекту/контакту/синку выражается полями `scope`/`slug`/`login`/`sync_slug` в каждом сигнале (см. C). Отдельные `MeetingPackage` per project НЕ создаются.
- **В3 (LLM-классификация при неопределённости, M3):** ✅ **Закрыто 2026-06-19** — **Вариант В**: B остаётся чистым Python. Если детерминированные правила не дают результат — B возвращает `route=unclear` ИЛИ передаёт `low confidence` дальше; LLM-этап классификации (increment-промпт Haiku) выполняется как `C.pre_classify()` внутри C.Добытчика, не в B. <!-- изменено 2026-06-22: MAJOR-A fix R10 --> ⚠️ **R10 уточнение:** LLM-fallback (Шаг 7) вынесен в **оркестратор** (F.run_pipeline / bootstrap.py) — B.determine_route() остаётся чистым Python без LLM.
- **В4 — Встреча без проекта:** Не мусор — это встреча с людьми. Логика: B не нашёл project_slug → C резолвит участников → встреча идёт в E (1-1). Отдельный `unresolved.json` снят: неразрезолвенные люди → `state/unclear_names.jsonl` (см. F/E, M8).

## Система алиасов (classification_memory.json)

### Назначение
Хранит все текстовые маркеры, по которым система определяет принадлежность встречи к проекту или контакту. Пополняется автоматически (bootstrap, increment) и вручную (pm_manual).

### JSON-схема

```json
{
  "$schema": "classification_memory_v1",
  "version": "1.0",
  "last_updated": "ISO-8601 timestamp",
  
  "projects": {
    "<slug>": {
      "aliases": [
        {
          "text": "строка алиаса",
          "source": "bootstrap|increment|pm_manual",
          "added": "YYYY-MM-DD",
          "confidence": "auto|confirmed",
          "status": "active|blocked|deleted|archived",
          "occurrences": "число встреч где найден",
          "last_match": "YYYY-MM-DD",
          // Опционально для blocked:
          "blocked_by": "pm_manual",
          "blocked_at": "YYYY-MM-DD",
          "blocked_reason": "причина блокировки",
          // Опционально для archived:
          "archived_at": "YYYY-MM-DD",
          "successor_slug": "куда перенаправлять"
        }
      ],
      "negative_keywords": ["слова, блокирующие конкретный алиас (а не проект целиком). См. R5."],
      "priority": "приоритет проекта при конфликтах (1=высший)"
    }
  },
  
  "contacts": {
    // ⚠️ DEPRECATED (C4, 2026-06-19): секция помечена read-only кэшем.
    // Единственный writable store алиасов контактов — AnywhereContacts (AC).
    // E.Люди использует ContactStore.add_alias() / resolve_name() (см. TZ_E_1on1).
    // Поле остаётся в схеме для обратной совместимости bootstrap-импорта,
    // но новые записи в `classification_memory.json/contacts` НЕ пишутся.
    "<contact_id>": {
      "canonical_name": "Полное официальное имя",
      "email": "email@company.ru",
      "aliases": [
        {
          "text": "вариант написания имени",
          "source": "bootstrap|increment|pm_manual",
          "confidence": "auto|confirmed",
          "status": "active|blocked",
          "context_required": "true если алиас требует контекста (напр. только имя)"
        }
      ]
    }
  },
  
  "corrections": [
    {
      "meeting_id": "идентификатор встречи",
      "original_slug": "старый slug или null",
      "corrected_slug": "правильный slug",
      "trigger_alias": "какой алиас вызвал ошибку",
      "corrected_by": "pm_manual",
      "corrected_at": "YYYY-MM-DD",
      "action": "alias_created|reclassified|alias_blocked"
    }
  ],
  
  "ambiguous_aliases": {
    "<текст алиаса>": {
      "candidates": ["slug1", "slug2"],
      "resolution": "context_required|priority|rule_based",
      "priority_rules": [
        {"pattern": "regex паттерн контекста", "slug": "какой slug выбрать"}
      ],
      "default": "slug по умолчанию если правила не сработали"
    }
  },
  
  "config": {
    "min_alias_length": 3,
    "min_occurrences_for_auto_add": 3,
    "confidence_threshold_for_auto_add": "high",
    "audit_retention_days": 365
  }
}
```

### Источники алиасов (source)

| Источник | Когда | Confidence |
|----------|-------|------------|
| `bootstrap` | Первичный прогон по 478 summary (модуль C, Opus) | auto → confirmed после проверки |
| `increment` | Каждая новая встреча, Haiku не нашёл по существующим | auto, при high confidence |
| `pm_manual` | PM исправил классификацию или добавил алиас вручную | confirmed |

### Статусы алиасов (status)

| Статус | Значение | Используется для матча |
|--------|----------|----------------------|
| `active` | Рабочий алиас | ✅ Да |
| `blocked` | PM заблокировал, даёт ложные срабатывания | ❌ Нет |
| `deleted` | Soft delete для аудита | ❌ Нет |
| `archived` | Проект закрыт, алиас исторический | ⚠️ Только для старых встреч |

## Ручное управление PM

PM взаимодействует через TG-бота. Команды:

### 1. Исправление slug встречи

**Команда:** `встреча [название/id] → проект [slug]`

**Примеры:**
- `встреча "Атрибуция статус 2025-10-13" → проект metroteka  # синтетический пример`
- `встреча 2025-10-13_атрибуция → проект metroteka  # синтетический пример`

**Алгоритм:**
1. Fuzzy-поиск встречи в state.json
2. Если не найдена → «Встреча не найдена. Похожие: [список]»
3. Обновить project_slugs в state.json
4. Извлечь алиасы из заголовка → добавить в classification_memory.json (source: pm_manual, confidence: confirmed)
5. Записать в corrections
6. Ответ: «✅ Встреча переназначена: [old] → [new]. Добавлен алиас: [alias]»

### 2. Блокировка алиаса

**Команда:** `алиас [текст] не относится к [slug]`

**Пример:** `алиас "боты" не относится к antibot`

**Алгоритм:**
1. Найти алиас в projects[slug].aliases
2. Обновить: status=blocked, blocked_by=pm_manual, blocked_at=now
3. Найти все встречи, где этот алиас был триггером
4. Пересчитать classification без этого алиаса
5. Если новый confidence < threshold → переместить в unclear
6. Ответ: «🚫 Алиас заблокирован. Пересмотрено: N встреч. В unclear: M»

### 3. Просмотр алиасов

**Команда:** `алиасы [slug]`

**Формат ответа:**
```
📁 antibot — 12 алиасов

✅ Активные (8):
• Антибот [bootstrap, confirmed, 47 встреч]
• antibot [pm_manual, confirmed, 12 встреч]

🚫 Заблокированные (2):
• боты [blocked 2026-06-23: слишком общий]

⚠️ Negative keywords: бот-поддержка, чат-бот
```

### 4. Удаление алиаса

**Команда:** `удали алиас [текст] из [slug]`

**Алгоритм:**
1. Soft delete: status=deleted, deleted_at=now
2. Физически НЕ удалять (аудит)
3. Ответ: «🗑 Алиас удалён. Восстановить: `восстанови алиас [текст] в [slug]`»

## Граничные случаи алиасов

### 0. Семантика negative_keywords (R5)

<!-- изменено 2026-06-22: R5 -->

**Прежняя (ошибочная) семантика:** `negative_keywords` блокировали проект целиком — если в встрече встречалось любое из них, проект исключался даже при наличии валидного алиаса.

**Новая семантика (R5):** `negative_keywords` блокируют **конкретный алиас**, не весь проект. Алгоритм:

1. При матче алиаса `A` в тексте встречи B проверяет окружающий контекст (например, ±50 символов или вся строка).
2. Если в этом контексте встречается слово из `negative_keywords` — этот **конкретный матч** этого алиаса игнорируется.
3. Другие алиасы того же проекта проверяются независимо — если ещё один алиас матчится без negative-контекста, проект остаётся в `project_slugs`.

**Пример:** проект `antibot`, алиасы = ["бот", "антибот"], negative_keywords для алиаса «бот» = ["бот-поддержка", "чат-бот"].
- Встреча «Бот-поддержка по антибот» → матч «бот» блокируется negative «бот-поддержка»; матч «антибот» остаётся → `project_slugs=["antibot"]`.
- Прежняя логика бы исключила проект целиком — это неправильно.


### 1. Алиас совпадает с двумя проектами

**Пример:** «Атрибуция» — проект metroteka И тема adm (OKR). _Пример синтетический, иллюстрирует механику ambiguous_aliases._

**Решение:** Записать в `ambiguous_aliases` с контекстными правилами:
```json
"Атрибуция": {
  "candidates": ["metroteka", "adm"],
  "priority_rules": [
    {"pattern": "статус|планирование|внутренний", "slug": "metroteka"},
    {"pattern": "OKR|цели|метрики", "slug": "adm"}
  ],
  "default": "metroteka"
}
```
При матче без контекста → оба кандидата с confidence: medium → C разбирается по summary.

### 2. Алиас слишком короткий

**Пример:** «АиД» (3 буквы), «Cu» (2 буквы).

**Решение:**
- config.min_alias_length = 3
- Алиасы < 3 символов — только с context_required: true
- При матче короткого алиаса: confidence понижается до medium
- PM может подтвердить короткий алиас как надёжный

### 3. Алиас совпадает с именем человека

**Пример:** алиас «Кирилл» для проекта, но Кирилл — участник встреч.

**Решение:** Проверка при добавлении:
1. Сравнить с contacts[*].aliases
2. Если совпадение → предупреждение: «⚠️ Совпадает с именем [контакт]. Добавить? да/нет»
3. Если подтверждено → context_required: true
4. При матче: проверять, участник ли это или часть названия

### 4. Алиас устарел (проект закрыт)

**Пример:** parsing закрыл этап `parsing-zhd`, «парсинг конкурентов» теперь означает другое.

**Решение:**
- При архивации проекта: все его алиасы → status: archived
- Указать successor_slug для перенаправления
- Логика матча:
  - Встреча ДО archived_at → старый проект
  - Встреча ПОСЛЕ → successor или unclear
