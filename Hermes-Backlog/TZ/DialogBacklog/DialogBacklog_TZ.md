# ТЗ: Инструмент «Dialog Backlog»

## Назначение

Автоматическое ведение бэклога открытых задач из диалогов Саши с Сиренью.

**Три режима работы:**
1. **Автокрон (инкрементный)** — каждые 2 часа 8:00–22:00, Haiku, сканирует только новое с прошлого скана
2. **Еженедельная сводка** — понедельник 09:00 МСК, Sonnet, полный отчёт по всем открытым
3. **Команда «проверь бэклог»** — только чтение: открытые пункты + suggest close кандидаты + блок 🙋 «Ждёт тебя»

**Файл бэклога:** `~/WorkVault/Hermes-Backlog/dialog-backlog.md`
**Утилиты:** `~/USERTOOLS/DialogBacklog/`
**Доставка:** топик Backlog (thread 6, группа «Сирень Workspace»)

---

## Архитектура

```
backlog_fetch.py → JSON сообщений (фильтр: только рабочие топики)
       ↓
  LLM-анализ → plan.json
       ↓
backlog_merge.py → dialog-backlog.md
       ↓
  Сводка → Telegram топик Backlog (если нечего → [SILENT])
```

### Компоненты

| Файл | Назначение |
|---|---|
| `backlog_fetch.py` | Читает новые Telegram-сообщения из `state.db` за период `since → now` |
| `backlog_merge.py` | Детерминированно применяет `plan.json` к `dialog-backlog.md` |
| `backlog_stamp_dates.py` | **Разовая миграция** — проставляет `created::`/`updated::` в существующие пункты без дат. В регулярном пайплайне не используется. |

- Haiku анализирует контент сообщений и отсеивает личные/нерабочие по смыслу
- Personal-топик попадёт в контекст Haiku, но не должен порождать задачи в бэклог

## Правила наполнения бэклога

*Версия 1.3 — согласована с Сашей 29.06–01.07.2026*

### ✅ Что заносить

**Явные задачи и обязательства:**
- «Сделай X», «Реализуй Y», «Настрой Z» — если не выполнены в том же диалоге
- Отложенные решения: «разберёмся потом», «вернёмся к этому», «когда будет время»
- Открытые вопросы без ответа: Саша спросил — ответа нет или «нужно разобраться»
- Идеи с явным намерением: «было бы хорошо», «нужно бы», «хочу попробовать»
- Ожидания от Саши: «пришли X», «дай доступ к Y» — если не выполнено → пометить 🙋

**По времени сессии:**
- Работа над инструментом или ТЗ на инструмент **>30 минут** в рамках сессии, но без итоговой реализации → заносить как открытую задачу
  - Признаки: обсуждение архитектуры, написание ТЗ, брифы, исследования — без финального «реализовано»
  - Формулировка: «Реализовать [инструмент]» или «Завершить ТЗ [инструмент]»
  - Длительность оценивается по кластеру сообщений на одну тему внутри сессии (`sessions.started_at`)

### ❌ Что НЕ заносить
- Задача выполнена в том же диалоге
- Информационный обмен без действия («как работает X?» → объяснила → закрыто)
- Мелкие уточнения и правки, которые решаются сразу
- Разговоры без задачи (обсуждение, оценки, эмоции)
- Дубликаты уже открытых пунктов — **дедупликацию делает LLM на этапе формирования `plan.json`**, `backlog_merge.py` дубли не проверяет

### Тест на занесение
> *«Если это не записать — Саша об этом вспомнит и удивится, что не сделано?»*
> - **Да** → заносить
> - **Нет** → пропустить

## Пометка «Ждёт Сашу» 🙋

Тег `🙋` проставляется **в начале текста пункта** при создании, если задача заблокирована на Саше:
- Нужен доступ / токен / решение от Саши
- Саша должен что-то принести, ответить, подтвердить

**В сводках и по команде:** выводить отдельным блоком **«🙋 Ждёт тебя»** в начале отчёта, **до** общего списка открытых.

> 🙋-пункты **включаются и в блок «🙋 Ждёт тебя», и в общий список «Все открытые»** — для полноты картины.

Пример пункта в файле:
```
- [ ] 🙋 Получить PAT для Loop (loop.tutu.ru → Settings → Security) ^bk-028
```

## Suggest close (предложение закрыть)

Помечать `<!-- AI: suggest close -->` **автоматически** — не дожидаясь явной фразы Саши — если:
- В диалоге **подтверждена реализация** инструмента/ТЗ из бэклога
  - Признаки: «готово», «реализовано», «Opus сделал», «тесты прошли», «запущено», «выполнено»
- Саша **явно снял** задачу: «не надо», «забудь», «снимаем», «отменяем»
- Задача стала **неактуальной** из-за изменения контекста
- Работа >30мин: если реализация всё-таки состоялась → suggest close

> ⚠️ `suggest close` — только пометка. Окончательное закрытие (`[x]`) — **только Саша вручную**.

## Как формулировать пункты

- **Текст:** глагол + объект, без воды. «Реализовать X», «Проверить Y», «Настроить Z»
- **Тег 🙋:** в начале текста если задача ждёт Сашу
- **Контекст (💬):** одна строка — когда упомянуто, суть, почему важно
- **Секция:** выбирать по смыслу из существующих `##`-заголовков, при отсутствии — создавать новую
- **Якорь:** `^bk-NNN`, NNN = значение `next_id` из frontmatter, инкремент после добавления

## Правила merge-утилиты (технические)

| Операция | Поведение |
|---|---|
| `[x]` строки | **Никогда не изменяются** |
| `suggest_close` | К `[ ]` строке добавляется ` <!-- AI: suggest close -->` перед якорем. Статус не меняется. Автоматически обновляется `updated::` |
| `add_items` | Пункт вставляется в указанную секцию; якорь = `next_id`, затем инкремент. 🙋 — префикс внутри поля `text`, отдельного поля нет |
| `update_items` | **Легализовано v1.3, реализовано в коде.** LLM обновляет `context` (💬) и/или `updated::` существующего пункта по `anchor`. Код принимает также поле `text`, но по политике LLM **не переписывает текст** — только контекст и дату. Статус `[x]` строк не трогается никогда. Используется когда по задаче появился новый контекст (ограничения, уточнения архитектуры и т.п.) |
| Секция не найдена | Создаётся перед `## ✅ Закрытые` |
| Frontmatter | `last_scan_at` и `next_id` обновляются автоматически |
| Бэкап | Создаётся `.bak` рядом с файлом (если не `--dry-run`) |

### Пример `update_items` в `plan.json`
```json
{
  "update_items": [
    {
      "anchor": "bk-098",
      "context": "EWS ResolveNames ограничен 100 записями — нужен LDAP fallback. Упомянуто 30.06.",
      "updated": "2026-06-30"
    }
  ]
}
```

> Поле `text` в `update_items` **зарезервировано в коде**, но LLM его не использует — переписывание формулировки открытого пункта не входит в допустимые операции. Если формулировка неверна, Саша правит вручную.

### Полная структура `plan.json`
```json
{
  "suggest_close": ["bk-005", "bk-012"],
  "add_items": [
    {"section": "🔧 Hermes / Сирень",
     "text": "Реализовать X",
     "context": "Упомянуто 30.06 в топике Tools",
     "created": "2026-06-30",
     "updated": "2026-06-30"}
  ],
  "update_items": [
    {"anchor": "bk-098", "context": "Новый контекст", "updated": "2026-06-30"}
  ],
  "new_last_scan_at": "2026-06-30T15:00:00+03:00"
}
```
- `suggest_close` — плоский список anchor-строк (не объектов).
- `add_items.section` — заголовок `##` в файле; если не найден → создаётся перед `## ✅ Закрытые`.
- `add_items.text` — если задача ждёт Сашу, префикс `🙋` включается **внутрь `text`**.
- `created`/`updated` в `add_items` — опциональны, по умолчанию `today()`.

## Доработка: Режим сверки со скиллами (v1.5, 2026-07-26)

### 1. Цель

При каждой проверке бэклога (команда «проверь бэклог», еженедельная сводка `vm_dialogbacklog`, инкрементный крон) — автоматически находить открытые bk-задачи, для которых **уже существует реализация** (скилл или инструмент в проде), и помечать их `suggest close` с явной причиной, чтобы Саша мог быстро подтвердить закрытие вручную.

### 2. Алгоритм сверки

Выполняется **после** основной аналитики диалога, до формирования `plan.json`.

**Входные данные:**
1. Открытые пункты `[ ]` из `dialog-backlog.md` (без `<!-- AI: suggest close -->` — уже помеченные пропускаем).
2. `skills_list()` — список установленных скиллов с полями `name`, `description` (Hermes tool, доступен из промпта крона).
3. `~/WorkVault/Hermes-Backlog/TZ/MAIN_TZ_INVENTORY.md` — таблица «Активные ТЗ»; интересует пара `(Инструмент, Статус)`, кандидаты — строки со `status: active`.

**Шаги матчинга (для каждой открытой bk-задачи):**

1. **Классифицировать формулировку.** Из текста пункта выделить намерение:
   - `implement_skill` — «разработать/создать/написать/сделать скилл X», «оформить скилл X»
   - `implement_tool` — «реализовать/сделать инструмент X», «написать X», «реализовать ТЗ X»
   - иначе — задача не подлежит сверке, пропустить.

2. **Извлечь ключ (объект задачи).** Взять существительное-объект («allocate_meeting», «ExchangeMonitor», «синк Loop», «скилл matcher-contacts» и т.п.) + значимые слова из `context` (💬). Нормализация: lower-case, убрать пунктуацию, склеить дефис/подчёркивание/пробел (например `move-from-loop` ≈ `MoveFromLoop` ≈ `move from loop`).

3. **Сверить со скиллами.** Для `implement_skill`:
   - Собрать корпус: `skill.name + " " + skill.description` каждого скилла.
   - Считать совпадением: (а) прямое вхождение ключа в `skill.name` (после нормализации), **или** (б) ≥2 значимых слов ключа встречаются в `description` (стоп-слова «скилл», «инструмент», «сделать», предлоги — не считаются).
   - При совпадении → кандидат `suggest_close` с причиной: `«скилл \"<skill.name>\" уже реализован»`.

4. **Сверить с MAIN_TZ_INVENTORY.** Для `implement_tool` (и как fallback для `implement_skill`, если по скиллам ничего):
   - Взять только строки таблицы со `status: active` (draft/paused/completed — не учитываем; completed отдельно, см. ниже).
   - Совпадение: имя инструмента (колонка «Инструмент») нормализованно содержится в ключе **или** ключ содержится в имени. Дополнительно — ≥1 значимого совпадения слов между ключом и колонкой «Комментарий», если имя не сматчилось.
   - При совпадении → кандидат `suggest_close` с причиной: `«инструмент <Tool> в реестре, status=active (v<version>)»`.

5. **Порог уверенности.** Если единственный сигнал — 1 общее слово И нет прямого вхождения имени → **не предлагать** (шумно). Лучше пропустить, чем ложное предложение.

6. **Дедупликация.** Если задача уже имеет `<!-- AI: suggest close -->` — не дублировать. Если предложение сформировалось и по скиллам, и по реестру — оставить один пункт с обеими причинами через `; `.

7. **Границы.** Сверка добавляет пункты только в `suggest_close` списка `plan.json`. Никаких `[x]`, никаких `update_items` формулировок, ничего не удаляем.

### 3. Формат вывода в Telegram

В существующий блок `💡 Suggest close` (см. «Формат сводки») добавляются пункты из сверки — тем же форматом, но причина всегда конкретизирована:

```
💡 Suggest close (M):
- bk-093 Реализовать allocate_meeting — инструмент MeetingScheduler в реестре, status=active (v1.3) · 26.07
- bk-142 Оформить скилл workvault-rag — скилл "workvault-rag" уже реализован · 26.07
- bk-117 Реализовать выгрузку переговорок — инструмент ExchangeOrgLookup в реестре, status=active (v0.2); скилл "exchange-org-lookup" уже реализован · 26.07
```

- Причина — **человекочитаемая одна строка**, без служебных префиксов «MATCH:».
- В команде «проверь бэклог» блок остаётся отдельным разделом до общего списка (порядок из v1.2 не меняется).
- Если сверка не дала ни одного нового кандидата — блок формируется как раньше (только по диалоговым признакам); если и там пусто — блок не выводится.

### 4. Что НЕ трогать

- **Закрытие пунктов.** Крон никогда не ставит `[x]` — только `<!-- AI: suggest close -->`. Правило v1.2 сохраняется полностью.
- **Формулировки открытых пунктов.** `update_items.text` по-прежнему LLM не пишет.
- **Существующие блоки сводки** («🙋 Ждёт тебя», «📋 Все открытые», «Новые/Обновлено») — без изменений.
- **Скиллы и MAIN_TZ_INVENTORY** — только читаем. Никаких правок в `entities.json`, реестре ТЗ, файлах скиллов из этого крона.
- **Draft-инструменты реестра.** Если `status: draft` — это **не** повод предлагать закрытие (ТЗ есть, реализации нет). Задача остаётся открытой.

### 5. Связи с экосистемой

- **Hermes `skills_list()`** — источник актуального списка скиллов; вызывается один раз за проход крона (кешировать не нужно, объём мал).
- **MAIN_TZ_INVENTORY.md** — читается как markdown, парсится верхняя таблица «Активные ТЗ» (regexp по `| ... |`). При изменении структуры таблицы (см. `TZ-storage-system` v1.1) потребуется обновить парсер.
- **backlog_merge.py** — интерфейс не меняется: сверка формирует записи в существующий `suggest_close`, причины пишутся в тот же комментарий (`<!-- AI: suggest close: <причина> -->` — расширение синтаксиса, обратно совместимо, если merge оставляет весь `<!-- AI: ... -->` как есть; проверить в реализации).
- **Промпт крона** `vm_dialogbacklog` и будущего `vm_dialogbacklog_incremental` — добавить блок инструкции о вызове `skills_list()` и парсинге реестра. Актуализация промпта — открытая техзадача (см. ниже).

### 6. Решения брифа (2026-07-27)

Закрывают открытые вопросы v1.5. Все интегрированы в тело секции выше и в архитектуру двух скиллов (см. §7).

1. **Полиморфный `suggest_close` в `plan.json`.** Элемент — строка (легаси, `"bk-093"`) **или** объект `{"anchor": "bk-093", "reason": "..."}`. В файл пишется `<!-- AI: suggest close: <reason> -->` (если reason есть) либо старое `<!-- AI: suggest close -->` (если нет). Merge проверяет тип элемента — обратная совместимость сохранена.

2. **`status: completed` учитывается наравне с `active`.** Причина в формате: `«инструмент <Tool>, status=completed»`. Ложных срабатываний практически не будет — completed означает «сделано и заархивировано».

3. **Стоп-лист слов НЕ используется.** Матчинг «ключ ↔ скилл/инструмент» — не текстовый по словам, а **LLM-суждение Haiku** по двум явным сценариям (см. §7, промпт скилла 2). Стоп-лист хрупок и шумит — LLM принимает решение по смыслу.

4. **Разделение «создать X» vs «доработать X» — тоже LLM-суждение.** Haiku классифицирует намерение пункта и:
   - Если намерение «создать X» и X найден в скиллах/инвентаре → `suggest close: реализовано`.
   - Если намерение «доработать X» и X найден → читает ТЗ инструмента + поле `idea_summary` bk-задачи и выносит вердикт: `реализовано` / `не реализовано` / `не определено`. При `не определено` — **не** предлагать закрытие.

5. **Эпики (`^epic-*`) — пропускаются.** Пункты, чей anchor начинается с `epic-` или чей текст сформулирован как контейнер (без задачного глагола), в сверку не попадают.

## 7. Архитектура: два независимых скилла (v1.5.1)

Принцип **«один скилл = одна задача»**. DialogBacklog реализуется как **два независимых** cron-скилла с чёткими границами ответственности. Скиллы не вызывают друг друга — второй просто читает файл, который написал первый.

### 7.1 Скилл 1 — `backlog_collector` (Сборщик)

**Единственная ответственность:** читать сессии → находить открытые задачи → писать в `dialog-backlog.md`.

| Параметр | Значение |
|---|---|
| Расписание | `0 8 * * 1-5` (пн–пт 08:00 МСК) |
| Модель | `claude-haiku-4-5` (tutu) — см. рекомендацию ниже |
| Вход | новые сессии/сообщения с `last_scan_at` |
| Выход | обновлённый `dialog-backlog.md` (`add_items`, `update_items`); Telegram-сводка либо `[SILENT]` |
| Заменяет | старый инкрементный крон `defc4425a957` (каждые 2ч) — **отключить** |
| НЕ делает | не сверяет со скиллами и реестром, не предлагает `suggest_close` по инвентарю |

**Особенность v1.5.1 — поле `idea_summary`.** При записи новой bk-задачи скилл 1 обязан сохранить выжимку сути идеи из ~10 последних сообщений по теме. Это критично для скилла 2: без `idea_summary` он не сможет корректно судить «реализовано / не реализовано» по формулировкам «доработать X».

**Формат в `dialog-backlog.md`:**
```
- [ ] Доработать ExchangeMonitor — добавить фильтр по отделу ^bk-112
  - 💡 `idea_summary:: фильтровать письма только от сотрудников своего отдела`
  - 📅 `created:: 2026-07-27`
```

**Формат в `plan.json` (`add_items`):**
```json
{
  "section": "🔧 Hermes / Сирень",
  "text": "Доработать ExchangeMonitor — добавить фильтр по отделу",
  "context": "Упомянуто 27.07 в топике Tools",
  "idea_summary": "фильтровать письма только от сотрудников своего отдела",
  "created": "2026-07-27",
  "updated": "2026-07-27"
}
```

`backlog_merge.py` расширяется: принимает поле `idea_summary` в `add_items` и пишет его отдельной строкой-подпунктом с префиксом `💡 idea_summary::`.

### 7.2 Скилл 2 — `backlog_analyst` (Аналитик)

**Единственная ответственность:** читать бэклог → сверять со скиллами и `MAIN_TZ_INVENTORY` → предлагать `suggest_close` по реализованному.

| Параметр | Значение |
|---|---|
| Расписание | `5 8 * * 1-5` (пн–пт 08:05 МСК — через 5 минут после скилла 1) |
| Триггер по запросу | фраза «что в бэклоге» / «проверь бэклог» в диалоге |
| Модель | `claude-haiku-4-5` (tutu) |
| Вход | `dialog-backlog.md` (только чтение), `skills_list()`, `MAIN_TZ_INVENTORY.md`, ТЗ инструментов из реестра |
| Выход | `plan.json` только с `suggest_close` (полиморфный формат); Telegram-сводка либо `[SILENT]` |
| Заменяет | старый крон `vm_dialogbacklog` (пн 09:00) — **отключить** |
| НЕ делает | не собирает новые задачи, не пишет `add_items`/`update_items`, не ставит `[x]` |

Скилл 2 **не вызывает** скилл 1 — он просто читает уже записанный файл. Если по каким-то причинам скилл 1 не отработал, скилл 2 всё равно пройдёт по последнему актуальному состоянию бэклога.

### 7.3 Промпты для Haiku (скилл 2) — краткие, структурированные, без CoT

Промпты явно прописаны в конфиге скилла. Никаких «think step by step» — Haiku 4.5 при коротких структурированных инструкциях выдаёт стабильный JSON без цепочек рассуждений.

**Промпт A — классификация намерения bk-задачи:**
```
Дана открытая задача из бэклога. Определи намерение:
- "create" — создать/реализовать/написать/оформить новый X
- "improve" — доработать/дополнить/улучшить/починить/добавить в существующий X
- "other" — не подходит под create/improve (вопрос, обсуждение, blocker)

Текст задачи: <text>
Context: <context>

Ответ строго JSON: {"intent": "create"|"improve"|"other", "object": "<нормализованное имя X или null>"}
```

**Промпт B — сверка `create` со скиллами и инвентарём:**
```
Задача: создать <object>.
Установленные скиллы (name + description): <skills_list>
Активные инструменты реестра (name, status, version, комментарий): <inventory>

Есть ли среди них тот, что реализует <object>? Отвечай по существу, без рассуждений.

Ответ строго JSON:
{"match": true|false, "kind": "skill"|"tool"|null, "name": "<имя>"|null,
 "status": "active"|"completed"|null, "version": "<v>"|null,
 "reason": "<человекочитаемая одна строка для Telegram>"}
```

**Промпт C — вердикт для `improve` (реализовано ли доработка):**
```
Задача (доработка): <text>
idea_summary: <idea_summary>
Найденный инструмент/скилл <name>. Его ТЗ (ключевые разделы): <tz_excerpt>

Реализована ли конкретно эта доработка в текущей версии инструмента?
Отвечай строго одним из значений: "implemented" | "not_implemented" | "undetermined".

Ответ строго JSON: {"verdict": "...", "reason": "<одна строка>"}
```

Логика скилла 2:
- Прогоняет каждую открытую `[ ]` задачу через **A** → если `create` или `improve` c object → **B**.
- Если **B** дал `match=false` → пропуск.
- Если **A=create** и **B=true** → `suggest_close` с причиной из B.
- Если **A=improve** и **B=true** → **C**. При `verdict=implemented` → `suggest_close`. При `not_implemented`/`undetermined` → пропуск.
- Эпики (`^epic-*`) и уже помеченные `<!-- AI: suggest close` пропускаются на входе.
