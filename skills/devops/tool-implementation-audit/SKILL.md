# Tool implementation audit

Класс: прежде чем «делать» инструмент из реестра (`MAIN_TZ_INVENTORY.md`), убедиться, что его **фактически ещё нет в проде**. Правило tz-workflow «ТЗ draft / ждёт берем в работу» ≠ «кода нет». Сессия OFC (26.08.2026): ТЗ помечено `draft`, а полная реализация + активный крон уже лежали на диске — архитектор начал было планировать реализацию «с нуля» и только в процессе обнаружил готовый код.

## Главное правило / шаги

Когда Саша говорит «делаем» по инструменту в реестре — **до пофайлового плана (Блок 1А) сделай read-only разведку на диске**:

1. **Есть ли модули?** `find ~/USERTOOLS/<Tool> -name '*.py'`, проверь ключевые файлы по секциям ТЗ (экспортёр/конвертер, writer, оркестратор, indexer).
2. **Есть ли CLI + обёртка?** `scripts/` у инструмента + `~/.hermes/scripts/<name>.sh`.
3. **Есть ли крон?** grep по `~/.hermes/cron/jobs.json` (по имени/script) — активен ли, расписание, `no_agent`.
4. **Есть ли тесты?** `tests/` по имени.
5. Если **реализация уже есть** — НЕ составляй план «с нуля». Переключись на **gap-анализ**: что реально доделать/проверить (недостающие тесты, необработанные риски из §8 ТЗ), и вынеси **рассинхрон статуса** («draft в инвенторе, но код в проде») как явный открытый вопрос Саше с вариантами:
   - 1 — принять как факт, обновить статус на `active` задним числом *(обычно рекомендация)*;
   - 2 — провести полноценное read-only ревью соответствия ТЗ + интеграции с экосистемой, ПОТОМ менять статус;
   - 3 — считать черновым пилотом и переделать с нуля (обычно не нужно).

## Read-only конформ-аудит (вариант 2) — что проверять

Архитектор через Cursor (`--model claude-sonnet-5-thinking-medium`, стоп на любых side-effect), чек-лист по секциям ТЗ:
- Экспортёр/конвертер: переиспользован ли канонический конвертер (import, не форк) или создана дублирующая копия (риск дрейфа двух конвертеров).
- Writer: idempotent ли (mkdir + tmp + `os.replace`), корректный frontmatter (поля из §5 ТЗ), создаёт ли папку `Entities/<slug>/` при отсутствии.
- Оркестрация/триггер: фильтр по `kind=project` + непустой `pfs.page_id`; сверка `version` страницы с сохранённой; graceful-degradation на 404; fail-soft на уровне цикла по сущностям.
- Индексация/поиск: расширение СУЩЕСТВУЮЩЕЙ таблицы (не новая), не ломает ли соседние `doc_type`; подпись слоя в скилле поиска (два параллельных слоя показаны без приоритизации).
- **Интеграция с ErrorBus** (если шина уже есть): вызвается ли `report_error.sh`/`error_bus_wrap.sh` на технические сбои (неуспешный GET, 404-as-skip, ошибки конвертера/Writer, сбой индексации)? Реестр `instrumentation_registry.json` (режим A/B)? Соблюдено ли правило каналов: бизнес → штатный deliver (Monitoring :7), техника → events.db + Errors :11112 (`-1004300127777:11112`)? Нет ли двойной доставки? **Для no_agent-крона молчаливый stdout ошибок теряется** — без `report_error` сбой не дойдёт никуда, это ключевой пробел интеграции.
- Покрытие данных: на реальном `entities.json` посчитай, сколько сущностей подпадает под scope (напр. `kind=project` с `pfs.page_id`) и сколько «тихо» не получит артефакт — фиксируй как открытый вопрос.

## Формат отчёта

Секции: «Соответствие ТЗ» (по пунктам, ✅/⚠️/❌ + локация), «Интеграция с ErrorBus» (подключён ли, корректность, правило каналов), «Дефекты/риски» (по приоритету), «Открытые вопросы» (по одному, с рекомендацией), «Рекомендации» (что доделать, без реализации). Не переделывать корректное.

## Питфоллы

- **Реестр не отражает диск.** Статус в `MAIN_TZ_INVENTORY.md`/ТЗ (`draft`/`implemented`) часто отстаёт от реальности. Всегда сверяй наличие кода/крона, а не верь статусу.
- **`read_file` на файлах с очень длинными строками** ложно помечает обычный UTF-8 markdown (большой однострочный контент) как «Binary file». Распознать: `file -b <f>` вернёт «UTF-8 Unicode text»; читать через `open(f, encoding='utf-8').read()` / `execute_code`, а не через read_file.
- **Не верь самоотчёту субагента** про реализацию/ревью — подтверди ключевые файлы и крон на диске сам.
- **`search_files` (ripgrep) по скрытым дирам не ищет** — для `~/.hermes/` используй `grep -rn` в terminal.
