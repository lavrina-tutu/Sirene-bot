# DialogBacklog Analyst (скилл 2)

## Назначение
Единственная ответственность: **сверять открытые задачи с реализацией** и предлагать
`suggest close` для того, что уже сделано. Не собирает новые задачи — это скилл
`backlog-collector`.

## Расписание
`5 8 * * 1-5` — пн–пт 08:05 МСК (через 5 минут после сборщика). Также запускается
по фразе «что в бэклоге» / «проверь бэклог». Заменяет старый крон `vm_dialogbacklog`.

## Модель
`claude-haiku-4-5` (tutu). Обоснование: сверка на строго структурированных промптах A/B/C
(см. `backlog_analyst.py`), без креатива, JSON-only ответы — Haiku здесь оптимальна.

## Алгоритм
1. Читаешь `~/WorkVault/Hermes-Backlog/dialog-backlog.md`, собираешь открытые `[ ]`.
2. Через модуль `backlog_analyst` (Python):
   - парсинг бэклога: `parse_backlog(text)` → пропускает `epic-*` и уже помеченные `<!-- AI: suggest close`;
   - загрузка скиллов: `load_skills()` (пробует `hermes skills list --json`, иначе — файловая система);
   - загрузка инвентаря: `load_inventory(MAIN_TZ_INVENTORY.md)`.
3. Для каждой открытой задачи прогоняешь три промпта (константы `PROMPT_A_INTENT`, `PROMPT_B_MATCH`, `PROMPT_C_IMPROVE_VERDICT` в модуле):
   - **A**: намерение — `create` / `improve` / `other`.
   - **B**: сверка объекта со скиллами и активным/completed инвентарём.
   - **C** (только для `improve`): по ТЗ и `idea_summary` — реализована ли конкретно эта доработка.
4. Кандидаты собираются в `plan.json`:
   ```json
   {"suggest_close": [
     {"anchor": "bk-093", "reason": "инструмент MeetingScheduler в реестре, status=active (v1.3)"}
   ]}
   ```
5. `python3 ~/USERTOOLS/DialogBacklog/backlog_merge.py --plan /tmp/plan.json`.
6. Telegram-сводка в топик Backlog: блок `💡 Suggest close (N)`. Если предложений нет → `[SILENT]`.
7. Журнал через `cron-journal-write`.

## Правила приоритета вердикта
- Эпики (`^epic-*`) — пропускать на входе.
- Уже помеченные `<!-- AI: suggest close` — пропускать.
- `status: draft` в инвентаре — **НЕ** считается реализацией.
- `status: active` / `status: completed` — считаются реализацией.
- `verdict: undetermined` в C — **не** предлагать закрытие (лучше пропустить, чем ложный вердикт).

## Что НЕ делает
- Не собирает новые задачи (`add_items` пустой).
- Не меняет формулировки открытых пунктов (`update_items` пустой).
- Не ставит `[x]` — только `<!-- AI: suggest close: <reason> -->`.

## Ручной режим (по запросу Саши, без Haiku-скрипта)

Когда нужно прогнать анализ вручную в диалоге (а не через крон), используй следующий порядок:

### Шаг 1 — Собрать открытые задачи
```
search_files(pattern=r"^\- \[ \].*\^bk-", path=".../dialog-backlog.md")
```
Это даёт точный список всех `[ ]` с анкорами — надёжнее, чем парсить `read_file`.

### Шаг 2 — Читать файлы параллельно
```
read_file(dialog-backlog.md) + read_file(MAIN_TZ_INVENTORY.md)  — в одном вызове
```

### Шаг 3 — Проверка реализации по каждой задаче

**Для «создать X»:**
- `ls ~/USERTOOLS/<ToolName>/` — папка существует?
- `ls ~/WorkVault/...` — файл/артефакт создан?
- Сверка со списком скиллов из контекста (skills_list())
- Статус в MAIN_TZ_INVENTORY: `active`/`completed` = реализован, `draft` = ещё нет

**Для «добавить файл/настройку»:**
- `ls` целевой директории (например `.obsidian/snippets/`, `.obsidian/plugins/`)
- `cat data.json` или `head` файла конфига для проверки значения (не только наличия файла)

**Для «провести ревью/тест» (разовые действия):**
- Смотреть дату создания (`created::`) — если >30 дней назад и нет следов выполнения → устарело
- Смотреть `updated::` — если статус не изменился с даты создания → не выполнялось

**Для «устарело из-за смежной задачи»:**
- Если другая задача закрыта (`[x]`) и меняет контекст (например EntitiesMigration переструктурировала папки) → исходная задача теряет смысл
- Пример: bk-074 (Projects/index.md) стал неактуален после bk-145 (EntitiesMigration закрыт, папки переехали в Entities/)
- Пример: bk-076 (People/index.md) стал неактуален — папка People/ упразднена

### Шаг 4 — Формат ответа

```
## 💡 Suggest close (N)
- bk-NNN — текст задачи → причина

## 📋 Открытые (требуют работы)
- bk-NNN — текст одной строкой
```

Причина закрытия должна быть конкретной: не «выполнено», а «инструмент `~/USERTOOLS/X/` существует, ТЗ v1.2 active» или «папка People/ упразднена EntitiesMigration (bk-145)».

## Формат ручного закрытия (когда Саша сам закрывает пункты)

Когда Саша просит закрыть N пунктов вручную (не через `suggest close`), используй строго следующий формат:

1. `- [ ]` → `- [x]` на строке самого пункта.
2. Если уже есть строка `📅 created:: … · updated:: …` — **добавить** ` · \`closed:: YYYY-MM-DD\`` к ней (inline, не новая строка).
3. Если строки `📅` нет — создать: `  - 📅 \`closed:: YYYY-MM-DD\``.
4. Добавить строку причины: `  - 💬 <конкретная причина>` (например «MOFS v0.9.1, 148/148 тестов»).

**Порядок строк** внутри пункта:
```
- [x] Текст задачи ... ^bk-NNN
  - 💬 <существующий контекст, если был>
  - 📅 `created:: ...` · `updated:: ...` · `closed:: 2026-07-27`
  - 💬 <причина закрытия>
```

**Техника патчинга** (важно для надёжности):
- Один `patch` на пункт — не batch-замена всего файла.
- Сначала найти точный контекст: `search_files(pattern=r"bk-NNN", context=4)` или `read_file(offset=N, limit=5)`.
- `old_string` должен включать соседние строки для уникальности.
- Параллельная загрузка не нужна — патчи применяются последовательно (каждый зависит от предыдущего состояния файла).

**Граничный случай**: пункт уже `[x]` но без `closed::` и `💬` — добавить только недостающие строки, checkbox не трогать (прецедент: bk-148, 27.07.2026).

**Верификация** после всех патчей: `grep -n "bk-NNN"` для каждого anchor + Python-скрипт проверки `[x]` / `closed::` / `💬` по всем 8 (или N) пунктам одним вызовом.

## Паттерн: разовая сверка через delegate_task

Для разового «проверь бэклог» эффективнее `delegate_task` чем крон:
```python
delegate_task(goal="Прочитать dialog-backlog.md и MAIN_TZ_INVENTORY.md, сверить открытые [ ] задачи со скиллами, предложить suggest close. Формат: ## 💡 Suggest close (N) / ## 📋 Открытые")
```
Субагент получает список скиллов из контекста + файлы — возвращает структурированный отчёт.
Закрытие пунктов после подтверждения Сашей — отдельным `delegate_task` с точными anchor'ами и причинами.
Прецедент 27.07.2026: 27 задач проанализировано, 8 предложено к закрытию — всё через субагента без крона.

## Питфоллы

- **EntitiesMigration делает задачи Obsidian-структуры устаревшими** — после закрытия bk-145 (EntitiesMigration: Projects/+People/ → Entities/) задачи типа «создать Projects/index.md», «создать People/index.md» потеряли смысл. Всегда проверяй: не была ли реструктурирована целевая папка более поздней задачей. Алгоритм: grep по упомянутой директории в закрытых `[x]` задачах.

- **CSS-сниппет ≠ включён**: файл в `.obsidian/snippets/` может существовать, но не быть активным. Проверять `appearance.json → enabledCssSnippets: []`. Не считать задачу «добавить сниппет» выполненной по факту наличия файла — проверяй конфиг.

- **Аналитик не видит задачи закрытые вручную до его запуска** — `parse_backlog()` обрабатывает только `- [ ]`. Если Саша закрыл задачу вручную (`- [x]`) до запуска аналитика — аналитик её не обнаружит. Это ожидаемое поведение, не баг. Для аудита недавно закрытых без задокументированной причины — использовать `parse_recently_closed(text, days_window=14)` (добавить в следующей итерации ТЗ v1.6).
- **Смысловой gap между формулировкой задачи и инструментом** — задача «Расследовать ошибку ownCloud sync» → решение в MoveFromFF. Haiku может не связать `ownCloud` с `MoveFromFF` по промпту B. Прецедент bk-140 (27.07.2026): задача про sync, фикс в `filename.py` в MoveFromFF. Лечение: в `idea_summary` (поле из backlog-collector) должна быть явная связь «фикс в MoveFromFF».
- **Промпты A/B/C — JSON-only, без CoT** — Haiku нестабильна при длинных цепочках рассуждений. Если вердикт приходит не в JSON — использовать `_extract_json()` из модуля.
- **FTS-поиск по ТЗ перед LLM-матчингом** — `find_related_tz(keywords)` в `backlog_analyst.py` использует `mofs_index.search_docs()` для поиска связанных ТЗ по ключевым словам задачи. Это покрывает косвенные связи (задача «ownCloud sync» → MoveFromFF_TZ.md через FTS). Если `mofs_index` недоступен — graceful fallback, промпт C работает без `related_tz`. Индекс обновляется автоматически после каждого создания/обновления ТЗ через `tz-workflow` (хук `mofs-index index docs`), плюс ночной rebuild.
