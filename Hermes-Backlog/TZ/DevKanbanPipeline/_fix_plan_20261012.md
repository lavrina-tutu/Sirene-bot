## 0. Итог диагностики (факты, не ощущения)

### Явление A — BUGFIX-графы застревают после DX, хвост не доезжает до GATE:done

**Корень:** BUGFIX-граф разворачивается в ДВА шага, и второй шаг никем не гарантирован.

- Канон (DPK §311-312, tz-workflow §Багфикс) требует корень `DEV/<slug>` + `BUG:diagnose` в **одном** create-батче (инвариант 9). Этот шаг выполняется.
- `GATE:diagnose-review` + LIGHT-хвост (`TZ:patch→TZ:finalize→GATE:take-into-work→HF:impl→HF:test→HF:docs-handoff→GATE:done`) создаются **вторым батчем ПОСЛЕ done DX** (классификация LIGHT решается именно на `GATE:diagnose-review`). Это действие оркестратора (Сирени), **никакой детектор его не требует и не проверяет**.
- Наблюдение из базы (task_events/created_at):
  - **Рабочие:** mfl-exchange-lxml — корень+DX 19:31, GATE:diagnose-review 21:06, хвост 21:11. pfs-task-slug-fix — корень+DX 15:33, GATE:diagnose-review 17:08, хвост 17:10. Т.е. двухшаговый unfold был **вручную** выполнен.
  - **Мёртвые (4 из 6):** pfs-empty-entity-guard, pfs-sink-aid-unrouted, pfs-task-slug-picker, pfs-notify-stale — только корень+DX (done), **GATE:diagnose-review и хвост НЕ созданы** → граф умер после диагноза, реализация не пошла.
- Диспетчер фазы создать **не может** (он только промоутит существующие карточки по `parents`). Авто-разворота хвоста после done DX в ядре НЕТ (`kanban_db_dispatch.py` — ни одной ссылки на BUG:diagnose/GATE:diagnose-review/LIGHT).
- **Сторож тоже не ловит:** `kanban_stuck_monitor.py::rule8_broken_tail` (стр. 608) начинается с `if "HF:plan" not in self.board.phases_in_graph(root_id): continue` — т.е. проверяет ТОЛЬКО полный DEV-хвост (FULL_DEV_TAIL) и **пропускает все BUGFIX-LIGHT графы** (в них HF:plan нет). Проверки ребра `BUG:diagnose → GATE:diagnose-review → LIGHT-хвост` не существует вовсе. Поэтому «граф оборван после DX» сторож не видит.

**Следствие:** когда Сирень забывает второй unfold (4 из 6 случаев за 30.09–12.10), граф молча умирает после диагноза — нет ни автогарантии, ни алерта, ни блокировки.

### Явление B — подвес воркера (protocol_violation + iteration budget)

Подвес **разнородный**, две разные причины, обе НЕ связаны с «Telegram MarkdownV2 parse failed»:

1. **t_273cf112 (GATE:diagnose-review, «worker exited cleanly rc=0 protocol violation», 25.09):**

   - Это **не** формат тела/блока. Это известный класс «billing/транспортный фатал → rc=0 → protocol_violation» (документирован в kanban-health-audit / kanban-pipeline-forensics). Гипотеза контейнера «MarkdownV2 parse failed ('.' is reserved)» **опровергнута**: эта ошибка — нефатальный WARNING notifier-адаптера (fallback на plain text), встречается 14:42 12.10 в `agent.log`/`errors.log`/`gateway.log`, но к жизни воркера отношения не имеет.

2. **t_fc25892c (eco-config-w2, «Iteration budget exhausted (90/90)»):**

Это **настоящий** дефект формата тела (заполнение карточки из шаблона не сработало), но **единичный** (в БД только 1 карточка из 891 с литералом `{body}`, t_ff75e50e, done).

## 2. План П.1..П.N

### П.1 — Сторож: детект «BUGFIX-граф оборван после DX» (основной фикс явления A)

Файл: `~/.hermes/scripts/kanban_stuck_monitor.py`. Добавить правило (rule9_bugfix_broken_tail) рядом с rule8.

Логика (детерминированная, по БД, без LLM):
- Для каждого DEV-корня, в чьём графе есть карточка `BUG:diagnose` (phases_in_graph):
  - Если `BUG:diagnose` **done** И НЕТ карточки `GATE:diagnose-review` в графе → это «граф оборван после DX». Действие (две ветки — РАЗНЫЕ классы нарушения, не смешивать):
    - **Класс «корень ещё жив»** (root имеет status НЕ done): `kanban block <root> "review-required: broken-bugfix-tail: BUG:diagnose done без GATE:diagnose-review"` (как rule8 блокирует корень). Это блок корня.
    - **Класс «раннее закрытие корня до GATE:done без созданного хвоста»** (root status=done И `GATE:done` В ГРАФЕ НЕТ ИЛИ НЕ done) — ОТДЕЛЬНОЕ нарушение (инвариант GLOSSARY 233: «kanban_complete корня до GATE:done = done запрещён»). Действие СИЛЬНЕЕ nudge:
      - `kanban block <root> "operator-action: premature-close: root done до GATE:done без хвоста BUG:diagnose done без GATE:diagnose-review"` — как требование к оператору; если open/не done по любому из рёбер ещё возможно — эскалация needs-operator/operator-action на повторное открытие/восстановление графа (re-open/restore), а не просто alert+комментарий.
      - Не довольствоваться nudge-комментарием: раннее закрытие корня фиксируется как нарушение, требующее действия оператора (restore/re-open), а не пассивного уведомления.
  - Если `GATE:diagnose-review` **done** И НЕТ первой фазы хвоста (`TZ:patch` для LIGHT / `TZ:stabilize` для full) → «хвост оборван у гейта». Действие — как класс «корень ещё жив», если корень не done; если корень уже закрыт до GATE:done — как класс «раннее закрытие».
- Порог-троттлинг по nudge-комментарию — по образцу rule8 (BROKEN_NUDGE_RE / `broken-tail-nudge`). Эскалация operator-action/needs-operator троттлится отдельно (не чаще 1 на граф в тик).
- **Не** срабатывать на корректно завершённом графе (корень done И `GATE:done` done) / заархивированном графе.

Критерий приёмки: на живом БД прогон скипта детектит все 4 мёртвых графа (pfs-empty-entity-guard, pfs-sink-aid-unrouted, pfs-task-slug-picker, pfs-notify-stale). ВАЖНО: на всех 4 реальных мёртвых графах срабатывает ветка **«раннее закрытие корня»** (root status=done по БД, `GATE:done` в графе НЕ done — контейнер закрыт до GATE:done без хвоста), а НЕ block-ветка «корень ещё жив». Скипт должен на них выдавать operator-action/needs-operator, а НЕ просто alert+nudge. Рабочие графы (mfl-*, pfs-task-slug-fix) НЕ тревожить. Тесты: unit на ветку «раннее закрытие корня» (root done + BUG:diagnose done + нет GATE:diagnose-review) + unit на класс «корень ещё жив» + интеграционный на снимке БД, покрывающий ветку root-done-без-GATE:done.

# ОТДЕЛЬНЫЙ КЕЙС (BUG:diagnose t_e6724eae): needs_input (HITL) блок авто-рутится в triage

Кейс: DEV/eco-config-w2 (t_fc25892c) — миграция реализована и верифицирована, воркер на ревью дошёл до HITL-гейта AC-009 (нужна реплика Саши «принять» 12 инструментов), корректно НЕ выставил «принят», заблокировал задачу `kind=needs_input`. Диспетчер вынес `block_loop_detected` («AC-009: статус принят не выставляется без решения Саши — needs_input») и РУТНУЛ задачу в `triage`. Срез крона показал «эко-граф w2 ушёл в постановку» — хотя задача не зависла, а легитимно ждала человека на приёмке.

## Диагноз — root cause (факты кода + БД)

**Файл/функция: `hermes_cli/kanban_db.py` → `_route_block()` (стр. 3314-3340), вызывается из `block_task()` (стр. 3220-3311).**

Логика дефекта (в точности):
```python
def _route_block(kind, ...):
    if kind == "dependency":
        return "todo", "dependency_wait", ...          # единственный kind, обходящий счётчик
    recurrences = prev_recurrences + 1 if prev_kind == kind else 1
    if recurrences >= BLOCK_RECURRENCE_LIMIT:          # LIMIT=2 (стр. 114)
        return "triage", "block_loop_detected", ...    # <- needs_input попадает СЮДА
    return "blocked", "blocked", ...
```

1. **Только `dependency` обходит счётчик** «repeated blocks». **ВСЕ остальные kinds — включая `needs_input` (HITL)** — увеличивают `block_recurrences` и при `>= BLOCK_RECURRENCE_LIMIT` (2) роутятся в `triage` с событием `block_loop_detected`. Это и есть баг: HITL-ожидание = законная пауза воркера на человека, а не зацикливание воркера. Диспетчер смешивает два разных класса: «воркер зациклился на ретраях» (роут в triage оправдан только для capability/transient) и «воркер ждёт HITL-решение» (это НЕ роут, это пауза на needs_input).

2. **Усилитель: счётчик никогда не сбрасывается на unblock.** `unblock_task()` намеренно сохраняет `block_kind`/`block_recurrences` (стр. 3677-3681, комментарий: «resetting them is the amnesia that let cron-unblock <-> re-block loop unbounded; only complete_task clears them»). Т.е. одна карточка копит рекурренсы по РАЗНЫМ причинам за всю жизнь. По событийному следу t_fc25892c:
   - 14:47 `blocked(needs_input, recurrences=1)` — ждёт вердикт архитектора (законный HITL).

### П.8 — `_route_block`: genuine HITL `needs_input` НЕ роутится в triage (основной фикс)
В `_route_block`/`block_task` различать нативный `needs_input` (genuine HITL, `requested_kind is None`) от `needs_input`-rekind (dependency no_open_parent). ### П.9 — Счётчик рекурренсов: развязать по причинами (не копить чужие HITL)

Или: сбрасывать счётчик при переходе из `review`→`blocked(needs_input)` (HITL после успешного ревью — это свежая фаза, не повтор блоков), или вести счётчик per-cause. Аккуратно, чтобы не вернуть «амнезию» для cron-unblock<->re-block scenario (см. комментарий стр. 3677 и `test_kanban_block_kinds`).
