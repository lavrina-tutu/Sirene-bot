# ТЗ: Инструмент «Срез проекта» (status_snapshot)

**Версия:** 1.2
**Дата:** 2026-06-18
**Статус:** архитектура утверждена, правила сформированы, реализация pending (bk-085)

## История версий
- v1.0 (2026-06-17, утро) — базовая архитектура (триггер, входы, файлы, PM-блоки)
- v1.1 (2026-06-17, день) — §9 правила секций, §10 правила Warnings, §11 prompt-шаблон LLM
- v1.2 (2026-06-18) — триггер изменён с MoveFromFF на вызов от F «Дирижёр»

## 1. Назначение
Автоматическая генерация страницы текущего состояния проекта после каждой FF-встречи.

## 2. Триггер
Модуль F «Дирижёр» вызывает G после завершения D. Только для встреч route=project и route=1on1. Встречи с route=unclear не обрабатываются.

## 3. Входные данные
- FF summary новой встречи
- Предыдущий срез (самый свежий `{slug}-snapshot-{YYYY-MM-DD}.md`)
- Карточка проекта (`Projects/{slug}/card.md`)
- PM-заметки из предыдущего среза (блоки `<!-- pm: -->`) — используются как контекст генерации

## 4. Имена файлов
- Шаблон: `{slug}-snapshot-{YYYY-MM-DD}.md`
- Расположение: `Projects/{slug}/snapshots/`
- «Текущий» = самый свежий файл по имени
- Нет перезаписей, нет алиасов latest

## 5. PM-блоки
- В каждой секции среза — пустые блоки `<!-- pm: --><!-- /pm -->`
- PM пишет заметки между встречами
- При генерации нового среза: LLM читает прошлые PM-блоки как контекст → синтезирует обновлённый контент
- В новом файле блоки создаются пустыми заново

## 6. pm_locked
**Не реализуется в v1.** Причина: нет фоновых автообновлений среза между встречами.
Пересмотреть в v2 когда появятся автоисточники (Jira-sync, card.md cron).

## 7. Структура файла среза
(см. образец: `_test/snapshot/trisigma-snapshot-final.md`)
Секции: PM Warnings → Решения → Блокеры → Открытые вопросы → Что сделано → Что в работе → Следующие шаги → Предыдущие срезы (свёрнуто)

## 9. Правила формирования секций

Финализированы решения брифа от 2026-06-17.

### 9.1 Критерии приёмки (В1)
- **Жёсткая фиксация** — если в `context.md` ссылка на Confluence-документ с критериями: любая правка = переоткрытие критерия + Warning HIGH.
- **Мягкая фиксация** — устная договорённость без документа: мелкие правки без флага, существенные = Warning MEDIUM.

### 9.2 Baseline по срокам (В2)
- Исходный baseline = устав проекта (`context.md` → milestones).
- Каждый сдвиг срока требует явной записи в summary/решениях: «новый срок = X, потому что Y».
- Сдвиг без обоснования «потому что» → Warning HIGH.

### 9.3 SDK/обязательства вендора (В3)
- Если в `context.md` есть обязательство вендора (SDK, API, лицензия) и оно не выполнено по факту встречи:
  - эскалация как нарушение обязательств вендора,
  - фиксация в секции «Риски»,
  - Warning HIGH до закрытия.

### 9.4 Артефакты вне scope (В4)
- LLM сверяет упомянутые артефакты/задачи с `context.md` (scope).
- Артефакт вне scope → Warning MEDIUM «возможный scope creep».
- PM решает в `<!-- pm: -->`:
  - «расширение scope» → создаётся CR, обновляется `context.md`;
  - «побочный продукт» → Warning снимается в следующем срезе.

### 9.5 Финансовый трекинг (В5)
- Полная стоимость не отслеживается.
- Контролируются только **сроки оплаты по договору**.
- Если в summary упомянут платёж → LLM сверяет срок с `context.md`:
  - срок < 5 рабочих дней или уже нарушен → Warning HIGH.

### 9.6 Bus-factor (В6)
- Отсутствие ключевого ресурса (отпуск, болезнь, увольнение) без замены:
  - на критическом пути ≥ 1 нед. → Warning HIGH;
  - не на критическом пути ≥ 1 нед. → Warning MEDIUM.

### 9.7 Сверка с card.md / context.md (В7)
Сверяются только ключевые поля (не весь документ):
- даты и сроки milestone,
- сроки платежей,
- критерии приёмки,
- допущения (assumptions).

### 9.8 Устные договорённости (В8)
Jira не используется, источник истины — протокол встречи и срез.
- «Договорились что X» → секция **Решения**.
- «Юрий сделает Y» → секция **В работе**, владелец = Юрий.
- Непонятно кто исполнитель → секция **В работе**, исполнитель = «не определён» (PM назначит в `<!-- pm: -->`).

## 10. Правила PM Warnings

Блок `> [!warning]-` генерируется в начале файла среза, если есть хотя бы одно срабатывание. Уровни:

### HIGH (🔴) — требует действия на этой неделе
- Срок сдвинулся без обоснования «потому что» (см. §9.2).
- Артефакт/задача не в scope `context.md` и явно критичный (см. §9.4 при эскалации PM).
- Критерий приёмки имеет статус «✅» в `card.md`, но обсуждается пересмотр И есть Confluence-документ (см. §9.1, жёсткая фиксация).
- Риск повторяется 2+ среза подряд без митигации.
- Ключевой ресурс на критическом пути отсутствует ≥ 1 нед. без замены (см. §9.6).
- Срок платежа < 5 рабочих дней или уже нарушен (см. §9.5).
- Обязательство вендора зафиксировано в `context.md`, но не выполнено по факту (см. §9.3).

### MEDIUM (🟡) — решить в течение спринта
- Возможный scope creep: артефакт вне `context.md`, но не явно критичный (см. §9.4).
- Критерий приёмки согласован устно (без Confluence) и обсуждается пересмотр (см. §9.1, мягкая фиксация).
- Action item повторяется 2+ недели подряд без прогресса.
- Ресурс не на критическом пути отсутствует ≥ 1 нед. без замены (см. §9.6).

### LOW / инфо (🟢) — к сведению
- Устные договорённости без явного action item (исполнитель = «не определён»).
- Мелкие сдвиги сроков внутри допустимого окна (заранее согласованный буфер).

### Снятие Warnings
- HIGH снимается явным закрытием в `<!-- pm: -->` или в следующем срезе при разрешении причины.
- MEDIUM может быть конвертирован PM в «расширение scope» (→ CR) или «побочный продукт» (→ снимается).
- LOW снимаются автоматически, если в следующем срезе не повторяются.

## 11. Prompt-шаблон для LLM

Используется при вызове генератора: «Создай срез проекта по встрече {meeting_title}».

````markdown
## Prompt-шаблон: Генерация status_snapshot

### Входные данные
- FF summary встречи: {meeting_summary}
- Предыдущий срез: {prev_snapshot} (или "нет" если первый)
- Карточка проекта: {card_md}
- Контекст проекта: {context_md}
- PM-заметки из предыдущего среза: {prev_pm_notes} (блоки <!-- pm: -->)

### Инструкция

Ты — PM-ассистент. Создай срез проекта в формате Obsidian markdown.

**Правила извлечения контента:**

РЕШЕНИЯ: Извлеки из summary все «договорились что», «решили», «согласовали». Каждое решение = отдельный пункт.

СДЕЛАНО: Только завершённые действия с глаголом совершенного вида + субъект. «Почти готово» и «100% но не проверено» → В РАБОТЕ, не СДЕЛАНО.

В РАБОТЕ: Незавершённые задачи с владельцем. Устные договорённости с исполнителем → сюда. Если исполнитель не назван → «не определён».

БЛОКЕРЫ: Факт + кто блокирует + что нужно + дата. Без даты разблокировки → дата «не определена» + Warning.

СЛЕДУЮЩИЕ ШАГИ: Только action items с владельцем И сроком. Без срока → ОТКРЫТЫЕ ВОПРОСЫ.

ОТКРЫТЫЕ ВОПРОСЫ: Всё без срока/владельца + устные договорённости без исполнителя.

**Правила PM Warnings (генерировать блок `[!warning]-` сверху если есть):**

HIGH (требует действия на этой неделе):
- Срок сдвинулся без обоснования «потому что»
- Артефакт/задача не в context.md scope (scope creep)
- Критерий приёмки «✅» в card.md, но обсуждается пересмотр И есть Confluence-документ
- Риск повторяется 2+ раза без митигации
- Ключевой ресурс на критическом пути отсутствует ≥1 нед. без замены
- Срок платежа < 5 рабочих дней или нарушен
- Обязательство вендора не выполнено (есть в context.md, отсутствует на деле)

MEDIUM (решить в течение спринта):
- Возможный scope creep (артефакт вне context.md, но не явно критичный)
- Критерий приёмки согласован устно и обсуждается пересмотр
- Action item повторяется 2+ нед. без прогресса
- Ресурс не на критическом пути отсутствует ≥1 нед. без замены

LOW / инфо:
- Устные договорённости без action item (попадают в «не определён»)
- Мелкие сдвиги внутри допустимого окна

**Сверка с card.md/context.md (только ключевые поля):**
- Сроки и даты milestone → сравнить с baseline, при отклонении Warning HIGH
- Критерии приёмки → статус каждого (без изменений / прогресс / деградация / пересматривается)
- Допущения → проверить выполнение, нарушенное = Warning HIGH
- Платежи → сверить с датами в context.md

**PM-заметки из предыдущего среза:**
Читай блоки {prev_pm_notes}. Используй как дополнительный контекст при формулировке секций. В новом срезе создай пустые блоки <!-- pm: --><!-- /pm --> после каждой секции.
````
