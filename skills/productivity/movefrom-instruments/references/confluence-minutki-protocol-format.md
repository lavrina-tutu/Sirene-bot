## Как найти такую страницу по проекту

Страница "Минутки" — это **дочерняя** страница root-страницы проекта (`card.md: confluence_id`), не сама root-страница. Искать через:
```bash
source ~/USERTOOLS/ConfluenceSync/.env
curl -s -H "Authorization: Bearer $CONFLUENCE_TOKEN" \
  "https://dom.tutu.ru/rest/api/content/<root_confluence_id>/child/page?limit=50" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); [print(r['id'],'|',r['title']) for r in d.get('results',[])]"
```
Искать в списке заголовок, содержащий "Минутки" / "Задачи и договоренности".

## Два реальных формата таблицы (оба валидны, разные проекты используют разные)

### Формат А (2 колонки) — Trisigma, AI-ready
```html
<table><tr><th>Дата постановки</th><th>Задачи и Договоренности</th></tr>
<tr><td><time datetime="2026-07-07" /></td>
<td>
  <h2>Участники:</h2><ul><li>ФИО текстом (без mention)</li>...</ul>
  <h2>Решения:</h2><ul>...</ul>
  <h2>Блокеры:</h2><ul>...</ul>
  <h2>Задачи:</h2><ac:task-list>...</ac:task-list>
  <h2>Риски:</h2><ul>...</ul>
</td></tr>
</table>
```
Одна строка = один день/встреча. Участники — заголовок `<h2>Участники:</h2>` + `<ul>` внутри той же ячейки, **просто текст ФИО**, без `<ac:link>`/mention.

Trisigma: сортировка "последние сверху" (новая строка вставляется сразу после шапки).
AI-ready: сортировка "снизу-вверх" (новая строка добавляется в конец таблицы, перед строкой `вверх`) — **направление сортировки не универсально, уточнять для каждого проекта отдельно перед первой записью.**

### Формат Б (3 колонки) — AI-аналитик (AI-MAS)
```html
<table><tr><th>Дата</th><th>Участники</th><th>Итоги</th></tr>
<tr>
  <td><time datetime="2026-07-07" /></td>
  <td><ul><li>ФИО текстом</li>...</ul></td>
  <td>
    <h2>Решения:</h2><ul>...</ul>
    <h2>Блокеры:</h2><ul>...</ul>
    <h2>Задачи:</h2><ac:task-list>...</ac:task-list>
  </td>
</tr></table>
```
Участники — отдельная колонка, тоже просто текст ФИО (не mention), Решения/Блокеры/Задачи объединены в колонку "Итоги".

## Формат задачи (`<ac:task>`) — общий для обоих форматов

```xml
<ac:task>
<ac:task-id>101</ac:task-id>
<ac:task-status>incomplete</ac:task-status>  <!-- или complete -->
<ac:task-body>
  <ac:link><ri:user ri:userkey="8a8383b593a26ea60194abdf8d090020" /></ac:link>
  <текст задачи, обычно начинается с "Название проекта. ">
  <time datetime="2026-07-15" />
</ac:task-body>
</ac:task>
```

Ключевые находки:
- **Исполнитель задачи — реальный Confluence `@mention`**: `<ac:link><ri:user ri:userkey="..." /></ac:link>`. `userkey` — это Confluence Server internal user key (не email, не login, не modern `accountId` из Cloud API). Нужен резолв email/ФИО → `userkey` — источник этого маппинга **не найден** в текущей инфраструктуре AnywhereContacts/ExchangeGAL, это отдельный блокер для будущей реализации (вероятно `GET /rest/api/user?username=...` на Confluence Server API, не проверено).
- **"Тег проекта" — НЕ отдельный макрос/легенда.** Это просто вручную напечатанный текстовый префикс в начале текста задачи: `"Trisigma. <текст>"`, `"AI-ready.<текст>"`, `"AI-аналитик.<текст>"`. Никакой парсинг "легенды тегов снизу страницы" не нужен — префикс = название проекта как в `card.md` (или его разговорный вариант), напечатанное человеком руками.
- **Дата задачи — НЕ отдельный `<ac:date>` макрос.** Это inline `<time datetime="YYYY-MM-DD" />` **внутри** `<ac:task-body>`, после текста задачи (не отдельная колонка/поле).
- Участники в колонке "Участники"/блоке "Участники:" — **просто текст ФИО**, без mention/ссылки. Mention используется только внутри задач (кто исполнитель).

## Решено брифом с Сашей (09.07.2026) — стандарт для инструмента "Протокол from Summary"

1. **Формат таблицы — только формат А (2 колонки)**, как в Trisigma/AI-ready. Формат Б (3-колоночный, AI-MAS) — не используется для нового инструмента, остаётся легаси на своей странице.
2. **Новые встречи всегда вставляются сверху** (сразу под строкой заголовка) — единый стандарт для инструмента, независимо от того, что написано в текстовой подсказке конкретной существующей страницы (Trisigma говорит "сверху", AI-ready — "снизу-вверх"; новый инструмент игнорирует легаси-подсказку и всегда пишет сверху).
3. **Тег проекта в тексте задачи — отдельный реестр «как называть проект в тексте», не automatic из `card.md: name`.** Реальные теги в минутках не всегда совпадают со значением `name` (напр. slug `ai-transformaciya` → тег `"AI-ready"`, slug `ai-mas` → тег `"AI-аналитик"`). Реестр нужно собрать вручную по фактическим текстам в существующих минутках всех проектов, не выводить программно.

## Резолв Confluence `userkey` — РЕШЕНО (09.07.2026)

Источник маппинга найден и подтверждён рабочим на реальных данных:

- **По логину:** `GET /rest/api/user?username=<login>` — работает, но **Confluence username часто отличается от корпоративного login** (напр. `isereda`→`sereda`, `dnabiev`→`nabieva`, `kkrivorotov`→`krivorotov`, `azhirov`→`zhirov` — обычно просто фамилия без служебных букв). Нельзя полагаться на корпоративный login напрямую.
- **По ФИО — надёжный способ:** `GET /rest/api/search?cql=user.fullname~"ФИО"` (передавать кириллицу через `--data-urlencode`, не ручной percent-encoding). Возвращает `results[0].user.{username, userKey, displayName}`. Проверено на 24+ реальных сотрудниках — все нашлись с первого совпадения по полному ФИО.
- Оба способа читают из `dom.tutu.ru` (ConfluenceSync `.env`, `CONFLUENCE_TOKEN`), не из `hq.tutu.ru` (JIRA).
- Найденные `confluence_login`/`confluence_userkey` **обязательно сохранять сразу** в `contacts.enc` (см. `anywhere-contacts-architecture.md` — новые CUSTOM_FIELDS), чтобы не резолвить повторно того же человека при следующей встрече.
- Глобального листинга пользователей нет (`/rest/api/user/search` без точного username даёт 404 на этом Confluence Server) — резолв только точечный, по логину или по ФИО.

## Резолв участника, если ФИО в summary не совпадает с `contacts.enc` — РЕШЕНО (09.07.2026)

Базовый резолв участника — substring-match по `login`/`fio`/`email`/`aliases` в `contacts.enc` (`ContactStore.find_contacts`, простой код, не LLM). Если он **не находит** совпадения (участник в summary назван нестандартно — сокращённо, с опечаткой, в другом падеже):

1. **Одна попытка** фаззи-резолва через **Haiku**: передать модели упомянутое в summary имя + список кандидатов из `contacts.enc` (ФИО/aliases), попросить сопоставить.
2. Если Haiku даёт уверенное совпадение — использовать его для текущей задачи/mention. Не считать результат окончательным зафиксированным алиасом автоматически — сохранение найденного соответствия в `aliases` отдельно не решено брифом, уточнить при необходимости.
3. Если Haiku **не даёт уверенного совпадения** — не гадать дальше. Оставить имя как обычный текст без Confluence `@mention`, явно пометить в отчёте/уведомлении, что этого участника нужно проверить руками. **Не блокировать публикацию всей встречи** из-за одного нерезолвленного участника.
4. Только одна попытка — не повторять фаззи-резолв, не эскалировать на более дорогую модель автоматически.

## Резолв переговорных комнат в списке участников — РЕШЕНО (09.07.2026)

Если резолв строки-«участника» находит не человека, а запись из `meeting-rooms.md` (переговорка/зум-комната, залогиненная как отдельный «участник» встречи) — это переговорка, исключить её из списка участников протокола, не пытаться резолвить как человека.

**Задачи, привязанные к такому «участнику»-переговорке** (в исходном summary задача была назначена на переговорку, а не на реального человека) — **не пропускать и не блокировать**: исполнитель по умолчанию = `tkachenkoav` (fallback), Саша сам разбирается и переназначает вручную позже.

## Резолв проекта встречи — РЕШЕНО (09.07.2026)

**Первичный сигнал — название самой встречи**, не содержимое summary/список участников. Резолв проекта начинается с попытки сматчить заголовок встречи на `card.md`/aliases проекта.

**Множественные проекты в одной встрече:** если по названию встречи резолвится несколько проектов сразу — публикуем во все резолвленные протоколы (не выбираем «главный», не спрашиваем каждый раз).

**Общий список задач по всем проектам** — отдельная сущность (ссылку Саша даст отдельно), куда попадают задачи, которые явно не относятся к одному проекту или упомянуты «вообще по всем». Существует независимо от протоколов конкретных проектов.

**Fallback для нерезолвленных встреч:** если встреча не подошла ни в проект, ни в 1:1, ни в мультисинк (все три типа сущностей поддерживаются с самого начала первой итерации, не только «проекты») — не блокировать и не откладывать молча, а класть в тот же общий список задач как временный накопитель. Обязательно предусмотреть **ручной перенос** такой записи в правильный проект по последующей явной команде Саши (не одноразовая операция — устойчивый повторно вызываемый механизм).

## Семантика двух дат — РЕШЕНО (09.07.2026, финальный ответ Саши)

- **Левая колонка таблицы** (`Дата постановки`) = дата встречи = дата возникновения/постановки задачи. Не дублирует inline `<time>` — это другая по смыслу дата.
- **Inline `<time>` внутри `<ac:task-body>`** = дедлайн выполнения задачи. Единственная трактовка, подтверждена дословно.
- **Словесные форматы дат из summary** ("на следующей неделе", "к пятнице" и т.п.) — всегда переводить в конкретную календарную дату перед записью в `<time>`, не оставлять текстом.
- **Fallback, если дедлайн явно не назван в summary:** `текущая_дата + 7 календарных дней`. Логика Саши: синки обычно еженедельные, значит подразумеваемый срок — до следующего синка.

## Пилотный прогон подтверждён вживую (10.07.2026) — три доработки формата после ревью

Пилот (Trisigma 490170597, Кирилл 1-1 508804979) реализован через связку Opus-план → Sonnet-код+тест, реально опубликован (version 78→79 и 1→2 соответственно, проверено GET-запросом после PUT). После первого прогона Саша дал три уточнения к базовому формату:

1. **Хронологическая вставка строки — не всегда «сверху».** Таблица должна оставаться отсортированной по дате/времени встречи по убыванию. Штатный режим (обрабатываем встречу новее всех уже опубликованных) — строка встаёт первой, внешне «сверху». Backfill/историческая обработка (встреча прошла раньше некоторых уже опубликованных строк) — вставлять строку в хронологически корректное место между существующими, не механически в верх. Правило универсальное, включая 5-колоночный Синк АиД.
2. **Формат ячейки для 1:1-протоколов — без блоков «Наименование встречи» и «Участники».** Для персональных 1:1 (Илья/Аралов/Кирилл/Жиров и любые будущие) эти два блока избыточны — участники и так известны по самой странице. Ячейка начинается сразу с «Решения», далее «Блокеры»/«Задачи» как обычно. Для проектных и мультисинк-протоколов оба блока остаются на месте.
3. **Telegram-уведомление после каждой успешной публикации** — топик WorkVault (chat `-1004300127777`, thread `5`), отдельное сообщение на каждую опубликованную встречу (не сводка при нескольких за прогон). Точный формат — **ровно 2 строки**, без заголовка «Встреча опубликована» и без отдельной строки-ссылки:
   ```
   🗓 09.07.2026, 11:30
   📌 Trisigma. Обсуждаем мысли Ильи по подготовке к полному внедрению
   ```
   Вторая строка (название встречи) — сама гиперссылка на страницу протокола. Первый вариант формата (с заголовком-эмодзи 📋 и отдельной строкой 🔗 ссылка) Саша отклонил явно как избыточный после тестовой отправки — не повторять этот более многословный вариант.

**Технический урок из реального прогона — разбор дедлайна при двух датах в тексте задачи.** Summary Trisigma содержало задачу вида «Запустить AB-тесты к 15-18 июля / Завершить к началу августа» — два указания срока через ` / `. Спецификация плана (§4.1) предписывала брать **последний** фрагмент после разделителя `/` (не первый) как `deadline_raw` → итоговый дедлайн получился `2026-08-01`, не `2026-07-15/18`, как могло показаться интуитивно на первый взгляд. Это осознанное решение спецификации, не баг — но стоит помнить при написании парсера дедлайнов: если в тексте задачи несколько дат через `/`, семантически последняя — это финальный/итоговый срок, первая — промежуточный чек-поинт.

Каноническое ТЗ (актуальная версия v0.7) — `WorkVault/Hermes-Backlog/TZ/ProtocolFromSummary/ProtocolFromSummary_TZ.md`. При расхождении с этим reference-файлом — побеждает ТЗ.

## Архитектурный ревью Opus + бриф N-1..N-8 (10.07.2026, v0.4→v0.7) — фундаментальный пересмотр

Реальный republish-тест на пилоте вскрыл баг: `--confirm-republish` создавал **дубль строки**, а не заменял существующую (Trisigma 490170597 version 80→81, +1 `<tr>`; Кирилл 1-1 508804979 version 3→4, +1 `<tr>`) — обнаружено только живым GET-прогоном после отчёта субагента, не unit-тестами. Саша решил дубли не трогать («убираю руками сам»), а архитектуру исправить на будущее.

**Ключевое новое правило от Саши, отменяющее прежнюю модель «перепривязки» (важно для ЛЮБОГО будущего инструмента, который пишет в Confluence, не только этого):**
> «Инструмент НИКОГДА не удаляет ничего в Confluence сам. Удаление — всегда моё действие, вручную. Автоматика только копирует.»

Также Саша явно предупредил: он **регулярно и осознанно** правит текст уже опубликованных строк вручную (шлифует формулировки после публикации) — значит любая идентификация «той самой строки» по содержимому текста ненадёжна в принципе.

**Решение — `row_anchor` (невидимая привязка строки к встрече, действует с первой публикации, не только при republish/copy) — ИСПРАВЛЕНО 10.07.2026 после реального API-тестирования (delegate_task):** первоначальный план «HTML-комментарий `<!-- pfs-row: ... -->` первой нодой в `<td>`» **не работает** — подтверждено экспериментом, Confluence Server/DC сам вырезает HTML-комментарии и произвольные `data-*`-атрибуты уже на этапе API PUT (санитайзер сервера, не поведение веб-редактора — отваливается даже без открытия страницы в браузере). Рабочий механизм — **anchor-макрос**: `<ac:structured-macro ac:name="anchor"><ac:parameter ac:name="">pfsrow-{sha256(meeting_id)[:12]}</ac:parameter></ac:structured-macro>` первым узлом в первой `<td>`; в рендере превращается в невидимый `<span class="confluence-anchor-link" id="...">`. Дополнено Content Property (`/rest/api/content/{id}/property`, ключ `pfs-registry`) как page-level source of truth для маппинга `meeting_id↔anchor_id`, физически не задеваемый редактированием текста ячейки. **Реально протестировано и подтверждено**, что anchor-макрос переживает и API round-trip, и настоящее ручное редактирование текста строки через веб-UI Confluence (не только теоретический round-trip) — Саша сам отредактировал опубликованные строки, повторный GET показал anchor на месте. Все операции (republish, copy между Confluence-страницами, copy в Obsidian) ищут строку **по anchor**, не по тексту/дате. Строки, опубликованные до внедрения anchor, ищутся по fallback-цепочке (task-id → дата+заголовок → считать утраченной, не блокировать). **При копировании между страницами (МЕХАНИЗМ А) anchor остаётся ИДЕНТИЧНЫМ на всех копиях одной встречи** (не уникализируется per-page добавлением page_id в хэш) — уникальность конкретной строки на конкретной странице обеспечивается парой `(anchor_id, page_id)`, так как одна страница физически не содержит двух строк одной и той же встречи.

**МЕХАНИЗМ А — Confluence→Confluence copy (заменил модель «move» из §1.9 старого ТЗ):** явная команда Саши → найти строку по anchor на source-странице → скопировать XML → вставить в target через хронологическую вставку → **source НЕ трогаем, не удаляем**. Реестр указывает на target как primary + хранит `copied_from[]` историю.

**МЕХАНИЗМ Б — Confluence→Obsidian copy (новое, §8 ТЗ):** явная команда Саши → читаем **актуальное** (возможно вручную отредактированное) содержимое строки из Confluence (не исходный summary-файл, не архивную версию на момент первой публикации) → конвертируем storage XML в markdown (задачи → чекбоксы, mention → обычный текст ФИО) → сохраняем в новую папку `WorkVault/Meetings/PreparedProtocols/` (имя файла по аналогии с `NewMeetings/`: `YYYY-MM-DD HH-MM-SS <Название встречи> - protocol.md`). Полностью ручной триггер, не крон, не автоматика.

**Другие решения брифа N-1..N-8 (детали и рекомендации Opus — см. ТЗ §7):**
- Дубли на боевых страницах от бага — Саша убирает вручную сам, всегда (не только для этого случая — общее правило «я чищу задвоения синков сам»).
- Confluence 409 (version conflict) — один retry со свежим GET, затем пропуск встречи до следующего прогона (не писать в реестр).
- Дублирующийся `meeting_id` от MoveFromFF — dual-key реестр (`meeting_id` + `content_hash` от названия+даты+участников); совпадение id при разном hash → публикуем как отдельную запись с суффиксом + warning, не молчаливый skip.
- Лимит Confluence storage ~5MB — только мониторинг размера + явное Telegram-предупреждение при >4MB (не проактивный архивный сплит).
- pageId 404 / userKey сменился — graceful (не превентивные проверки), + Telegram-уведомление при обнаружении. Плюс отдельная будущая задача: инструмент замены pageId сущности в реестре тегов + republish **оригинального summary-файла** (не Confluence-контента) в новую страницу — отличается от МЕХАНИЗМА А источником данных.
- Реестр `_registry.json` — остаётся отдельным файлом, никакой миграции под будущий Aggregate From сейчас (миграция — тривиальный шаг, когда Aggregate реально появится).
- Точка входа `run_pilot()` → переименована в `protocol_publish()` (alias с DeprecationWarning оставлен), имя пакета не менялось.
- Telegram-доставка уведомлений — НЕ прямой Bot API POST из инструмента (токен намеренно недоступен инструменту, `TELEGRAM_BOT_TOKEN` замаскирован в .env — это правильная изоляция секрета, не баг). **ИТОГОВОЕ архитектурное решение (§10 Q-2, 10.07.2026, изменено относительно первоначального плана «через `hermes send`»):** реальный подтверждённый канал — реестр (`_registry.json`) получает поле `notified: bool`, отдельный НЕ-cron скрипт (`scripts/notify_pending.py`) читает записи с `notified=false`, печатает готовый Markdown-текст в stdout; подключается к Hermes cron через `no_agent=true` + `script=...` + `deliver="telegram:<chat_id>:<thread_id>"` — сам Hermes runner делает доставку. Решение принято по практическому критерию «не важна техническая реализация, важен результат — уведомление в утверждённом формате», не по архитектурной чистоте. **Формат ссылки в этом канале — Markdown `[текст](url)`, НЕ HTML `<a href>`** — HTML-теги приходят как сырой текст, не рендерятся (подтверждено тестом со скриншотом).

## Прод-хотфиксы после полного роллаута на все 16 протоколов (10-13.07.2026) — уроки для ЛЮБОГО будущего инструмента, читающего вывод MoveFromFF

**Контракт таймзоны MoveFromFF: имя файла хранит UTC, не МСК.** MoveFromFF (см. его ТЗ §6) осознанно хранит дату/время в имени summary-файла в UTC — архитектурное решение, не баг, не меняется. **Любой инструмент, который парсит `HH-MM-SS` из имени файла MoveFromFF и показывает его человеку (таблица, уведомление, отчёт) — обязан сконвертировать в МСК (UTC+3, без DST) сам**, через реальную арифметику `datetime` (собрать aware UTC datetime → `+timedelta(hours=3)` → взять `.date()`/`.strftime("%H:%M")`), включая перенос даты на +1 день при переходе через полночь. Единственная точка конвертации — на входе пайплайна потребителя. Забыть об этом контракте — гарантированный баг «время показывается неправильное», обнаруженный только когда реальный человек посмотрел на реальную страницу.

**Layout с числом колонок ≠ 2 — писать контент в контентную колонку, не во вторую слева по умолчанию.** Если целевая Confluence-страница имеет структуру `N > 2` колонок (легаси-формат Б, см. AI-аналитик 477061038 выше — `Дата | Участники | Итоги`) — генератор строки обязан писать единственный непустой `<td>` в колонку с содержательным названием (Итоги/Результаты/Решения), не механически «вторую после даты». Перед конфигурацией индекса — обязателен реальный `GET` структуры `<th>` каждой конкретной страницы, не полагаться на предположение «все протоколы 2-колоночные» (проверять при подключении новой страницы реестра).

**Резолв ФИО при неоднозначности (несколько кандидатов совпадают по подстроке в contacts.enc) — fallback на дефолтного исполнителя, если он один из кандидатов.** Если сокращённое написание (одна фамилия без имени-отчества) совпадает сразу с несколькими контактами в `contacts.enc` — и среди неоднозначных кандидатов есть `DEFAULT_ASSIGNEE_LOGIN` (владелец/основной пользователь инструмента) — резолвить именно в него, а не оставлять текстом. Это НЕ общее правило «бери первого при неоднозначности» — специфичный fallback только на дефолтного исполнителя.

**Blocking-требование перед включением автоматического крона: batch-раннер.** Если CLI инструмента, читающего папку типа `NewMeetings/` (пополняемую MoveFromFF), поддерживает только «обработать один явно указанный файл» — включать регулярный автоматический крон **нельзя**, пока не написан batch-скрипт, который сам сканирует директорию, вычисляет `meeting_id` каждого файла, сравнивает с уже обработанными в локальном реестре, и прогоняет по очереди каждый новый (не падая целиком при ошибке одного файла). Без этого шага крону физически нечего вызывать — общий питфолл для любого инструмента цепочки MoveFromFF→X, не только для ProtocolFromSummary.

Полные формулировки, схемы данных и код-контракты (S-1..S-9 совместимости с будущим Aggregate From) — читать ТЗ `ProtocolFromSummary_TZ.md` §1.2, §1.9, §5, §7, §8 напрямую, этот reference — только сжатая историческая память брифа.
