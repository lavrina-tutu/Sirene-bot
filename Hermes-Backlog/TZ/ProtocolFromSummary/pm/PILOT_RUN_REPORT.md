## 7. Ограничения и известные проблемы

1. **`AnywhereContacts` не ставится через `pip install -e`** — flat-layout
   setuptools конфликтует с `venv_linux/` внутри директории пакета
   (обнаруживает 2 top-level пакета). Обошёл через `.pth`-файл в venv
   ProtocolFromSummary, указывающий на исходники AnywhereContacts напрямую.
   Работает, но это технический долг — стоит поправить `pyproject.toml`
   AnywhereContacts (`packages.find.include`) в будущей итерации.
2. **`date_utils.parse_deadline`** не покрывает все словесные форматы из
   реальных summary один-в-один (напр. "После завершения текущих работ по
   платформе" → неразборчиво → fallback +7, с warning — это осознанное
   поведение по правилу "Всё остальное неразборчивое" из §2.6 плана, не
   баг).
3. **Republish-путь (`--confirm-republish`)** реализован в коде, но НЕ
   протестирован реальным повторным PUT — по плану это требует ручного
   отката Саши, что не автоматизировано (осознанно, чтобы не оставлять
   лишний дубль строки на боевых страницах без явного запроса).
4. Cron/автозапуск НЕ создавался (явный запрет в задаче и в §5 плана) —
   запуск только ручной через CLI.
5. Реестр `_registry.json` теперь содержит 2 живые записи о реально
   опубликованных встречах (T1, K1) — при следующем реальном использовании
   инструмента на этих же файлах результат будет `skipped_duplicate`, это
   ожидаемо.

## Batch-раннер (§11.4 ТЗ v1.3, 13.07.2026, Sonnet)

Реализация: `pipeline.py::process_pending()` + CLI `python -m protocolfromsummary run-pending
[--path DIR] [--dry-run]`. Выбран subcommand в существующем `__main__.py` (не отдельный
`scripts/*.py`) — консистентно с `run`/`status`/`verify`/`copy`/`export-to-obsidian`, вся логика уже
в Python, не требует агентного/LLM-рассуждения на файл.

### Подключение к cron (готовая команда, no_agent=true)

```bash
cd /home/tkachenkoav/USERTOOLS/ProtocolFromSummary && .venv/bin/python3 -m protocolfromsummary run-pending
```

Прямой bash-вызов без агента — обоснование: логика полностью детерминирована (сканирование
файлов, сравнение с реестром, вызов `protocol_publish`), никакого LLM-рассуждения не требуется,
поэтому агентный прогон (как у `vm_movefromff`) был бы избыточен по токенам. Cron-задача НЕ
создана этим прогоном (отдельный шаг, вне автономности задачи, явный запрет в задании).

### Логика (строго по §11.4 (а)-(е))

1. Сканирует `MEETINGS_DIR` (или `--path`) по glob `"* summary.md"` — реальный формат имени файла
   (пробел перед "summary.md", подтверждено на реальном каталоге NewMeetings/, 549 файлов).
2. meeting_id — через существующий `parse_summary_file` (та же логика).
3. Сравнение с `_registry.json` — через `Registry.get()`.
4. Для отсутствующих — `protocol_publish(confirm_republish=False)` (обычная публикация, не
   republish).
5. Логирование по каждому файлу — через `logger.py` (INFO/WARNING/ERROR), плюс финальный
   stdout-отчёт с разбивкой по категориям и перечислением meeting_id.
6. try/except вокруг каждого `protocol_publish` — ошибка одного файла не прерывает остальные.

### Дополнительные решения (не описаны явно в §11.4)

1. **Хронологический порядок**: сортировка обрабатываемых файлов по `(meeting_date, meeting_time)`
   из распарсенного `MeetingSummary` (не по имени файла) — важно, т.к. UTC→МСК конвертация (§11.1)
   может сдвинуть дату на +1 день относительно даты в имени файла.
2. **`out_of_scope`** (resolve_route не резолвит встречу ни в один протокол, §1.5 fallback-цепочка)
   — отдельная категория, НЕ считается ошибкой.
3. **Финальный summary-отчёт** в stdout: счётчики + meeting_id по каждой категории
   (published/skipped_duplicate/out_of_scope/error) + построчный JSON на файл (для машинного
   разбора при подключении к cron).
4. **confluence/store клиенты** создаются один раз на весь batch-прогон (лениво, только если есть
   что публиковать) — не пересоздаются на каждый файл.

## Исправление таймзоны UTC→МСК (10.07.2026, прод-инцидент)

**Симптом:** Саша заметил, что время встречи в опубликованных протоколах/
Telegram-уведомлениях показывалось в UTC вместо МСК (UTC+3, Россия без DST).

**Корневая причина (не менялась — не в скоупе):** `MoveFromFF` намеренно
кладёт UTC-время в имя файла summary (`filename.py:1-8`, §6 его ТЗ) — это
осознанное архитектурное решение.

**Фактическая причина бага:** `ProtocolFromSummary/summary_parser.py:115`
читал время буквально из имени файла (UTC) без конвертации в МСК.

**Исправление:**
- `protocolfromsummary/summary_parser.py`: добавлена функция `_utc_to_msk(d, hhmmss)`
  — собирает `datetime(..., tzinfo=timezone.utc)`, прибавляет `timedelta(hours=3)`,
  возвращает `(dt_msk.date(), dt_msk.strftime("%H:%M"))`. Используется в
  `parse_summary_file` при разборе имени файла — единственная точка конвертации
  для всего пайплайна (протокол, Telegram, хронологическая сортировка).
  Переход через полночь обрабатывается арифметикой `datetime`, без спецслучаев —
  `meeting_date` автоматически сдвигается на +1 день, если UTC+3 переходит
  полночь (например 22:30 UTC → 01:30 МСК следующего дня).
- **Важное открытие при аудите остальных мест кода (§ЗАДАЧА п.3):** ячейка
  "Дата" в реальных Confluence-таблицах протокола физически хранит ТОЛЬКО
  дату — `<time datetime="YYYY-MM-DD" />` (date-only macro Confluence), без
  HH:MM. Время в таблице протокола НЕ отображается вообще — ни в UTC, ни в
  МСК. Значит `pipeline.py`/`storage_xml.py`/`page_merger.py` (включая
  `insert_row_chronological`) не требовали правок: они работают с
  `meeting_date` (уже конвертированной МСК-датой из фикса выше), время в них
  не используется вообще. Единственный потребитель `meeting_time` —
  `_registry.json` → `notifier.py`/`scripts/notify_pending.py` (текст
  будущего Telegram-уведомления).
- Хронологическая вставка (`insert_row_chronological`) на граничных случаях
  не ломается: она сортирует по `meeting_date`, который после фикса уже
  корректно сдвинут на +1 день при переходе через полночь (проверено
  юнит-тестами, см. ниже).
