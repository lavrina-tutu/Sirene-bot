# Ручной режим через штатный native Kanban (когда полный контур/внешняя граница сломаны)

Когда полный dev-workflow pipeline (канбан-диспетчер) или его внешняя граница
допуска (BC) заблокированы, владелец может продолжать реальную работу через
ШТАТНЫЙ native Kanban Hermes в ручном режиме: карточки-поручения ведёт штатный
канбан, роли запускаются отдельными командами codex exec, компрессор/
автодиспетчер/автопубликация не участвуют. Это развязывает ежедневную разработку
и блокер-проект (W1-09/BC) идёт отдельно, не блокируя работу.

## Ключевое ограничение: нельзя просто создать карточки на общей живой доске

Живой конфиг может включать `dispatch_in_gateway: true` + диспетчер подставляющий
`default_assignee`; gateway автоматически обслуживает все доски своего
Kanban-хранилища. Новое имя доски в том же хранилище или пустой assignee НЕ
исключают автозапуск. Поэтому для ручного потока использовать ОТДЕЛЬНУЮ доску в
ОТДЕЛЬНОМ Kanban-хранилище, выбираемом переменной `HERMES_KANBAN_HOME` — это тот же
штатный CLI и формат, без своего сервиса/БД/плагина. Профиль Hermes хранилище
досок НЕ отделяет: новый профиль бесполезен.

```bash
# отдельное хранилище для ручной работы
env HERMES_KANBAN_HOME=/home/tkachenkoav/.hermes-kanban-manual \
  hermes kanban boards create dev-manual --name 'Dev-workflow: ручная работа'
# дальше все команды с тем же KANBAN_HOME и --board dev-manual
kb_manual() { env HERMES_KANBAN_HOME=/home/tkachenkoav/.hermes-kanban-manual \
  hermes kanban --board dev-manual "$@"; }
```

Проверить у операторского терминала отсутствие унаследованных worker-переменных
(`HERMES_KANBAN_TASK`, `HERMES_KANBAN_RUN_ID`, чужих `HERMES_KANBAN_DB`) — работу
вести в обычной операторской сессии, не в назначенном worker. Не менять `HOME`/
`CODEX_HOME`/глобальное окружение gateway; gateway не рестартуем; `hermes pause`
не решение (останавливает cron/gateway-игress, но не уже начатую работу).

## Процедура ручного цикла

- **Одна карточка = одна роль/фаза** с одним проверяемым результатом, создавать по
  мере работы, сразу `--initial-status blocked`. В заголовке `[<work_id>] <фаза> —
  <цель>`; в body: `phase`, `role`, модель/effort, цель и критерии, исходные
  материалы (абсолютные пути), разрешённые записи. `--initial-status` принимает
  `running`|`blocked` (по умолчанию `running`, пр�� обычном create реально
  становится `ready`/`todo`/`triage`) — поэтому явно `blocked`.
- Не вводить вымышленные `--phase/--role/--labels/--metadata` у create: их нет.
  Всё дополнительное — текст в body. Tenant/assignee для учёта, но assignee
  в ядре = профиль штатного worker, НЕ средство запрета автозапуска.
- Цикл фазы: `claim` (переводит ready→running, Codex НЕ запускает; `claim` не
  принимает `blocked`) → один `codex exec -C <рабочий каталог> -m <роль> ... <
  out/<промпт>.md` (роль пишет полный отчёт через `--output-last-message`) →
  Сирень проверяет процесс/отчёт/область/входы, хеширует, комментирует →
  `complete --result --summary --metadata`. НЕ приписывать `complete` через `&&`
  к команде модели: rc=0 ≠ принятие результата.
- Следующая роль/фаза — новая карточка в `blocked`, `--parent <предыдущая_id>`
  (проверяет только завершённость предшественника).
- **Решение владельца («да/нет/ждать») = комментарий** в следующую заблокированную
  карточку: ДА/НЕТ/ЖДАТЬ + автор + дата + ссылка + точные план/REV (путь+хеш) +
  разрешённое действие. До «да» реализация остаётся `blocked`. Сирень не
  подписывает своё мнение именем владельца.
- Ошибка/неясность/лимит → `block --kind needs_input` + причина, остановка до
  разбора владельцем; автоповтор/retry/fallback запрещены. НЕ использовать
  `--kind dependency` для ожидания человеческого решения (допускает автопереход).
  Повторная блокировка → `triage` = повод остановиться и разобрать историю, а не
  обнулять счётчик/`specify`/`decompose` (те вызывают LLM).

## Штатные Kanban-tools vs CLI

В toolset нет `kanban_claim` (ручное взятие — CLI `claim`); `kanban_create` требует
`assignee` и автоподписывает сессию → для старта без auto-доставки использовать CLI
`create`. `request-review` рассчитан на свой цикл; в ручной схеме ревизия —
отдельная карточка, берётся обычным `claim` из `ready`. `attachments/artifacts`
и подписки могут триггерить авто-доставку — не включать как скрытую замену ручной
передачи. Полные журналы остаются в `evidence/`, на доске — кратко (вердикт, пути,
SHA256, решения, причины).

## Что ручной режим НЕ даёт (не перепродавать)

Штатный Kanban даёт атомарное взятие и проверку статуса/предшественников, но НЕ
даёт: общего стоп-листа «этот заказ никогда не перезапустится», контроля всех
запусков и сети, удостоверения владельца, запрета произвольных записей роли.
Отдельный `HERMES_KANBAN_HOME` не мешает процессу с достаточными правами обратиться
напрямую. Ручной режим безопасен потому, что владелец/Сирень контролируют команды
и не подключают к потоку автоматических исполнителей; доказанная защита
(ENV-03/BC) остаётся отдельным блокер-проектом и этим режимом НЕ закрывается.

## Питфоллы

- Смена статуса карточки (block/complete) НЕ останавливает уже работающий внешний
  codex — оператор отдельно завершает точный процесс и проверяет потомков.
- Обрыв связи: сначала проверить живость процесса/лог/отчёт/файлы; готовый
  корректный результат принять без нового вызова модели, незавершённый не
  объявлять успехом.
- Переносить поручения ПО ОДНОМУ, не разом весь старый граф; по выбранному
  поручению не дублировать обе машины состояния (старый регламент и ручной
  режим) одновременно.
- Роли передавать полный список первоисточников, не требовать compressor
  receipt/extract.md как условия ручного запуска.
