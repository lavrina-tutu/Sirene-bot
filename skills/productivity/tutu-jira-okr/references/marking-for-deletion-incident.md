# Инцидент: переименование в "Удалить" привело к реальному удалению задач

Дата: сессия работы над OKRS-3433/OKRS-3137 (пометка на удаление).

## Что произошло

1. По запросу пользователя переименовали summary четырёх задач в **строго** "Удалить" (без префикса/суффикса, полная замена):
   - OKRS-3433 (Objective, "O8.Q2.Предоставление технической и методологической поддержки...")
   - OKRS-3434, OKRS-3435 (её дочерние KR через Contains)
   - OKRS-3137 (отдельная, не связанная с OKRS-3433 задача)
2. `PUT /issue/{key}` с `{"fields": {"summary": "Удалить"}}` вернул `204` для всех четырёх.
3. Немедленный `GET` после каждого PUT подтвердил новый summary "Удалить" — задачи были на месте, видимых проблем не было.
4. **Позже в той же сессии** (следующий кейс, поиск по техподдержке для другой цели) при обращении к тем же ключам все четыре вернули:
   ```
   {"errorMessages":["ЗАПРОС НЕ СУЩЕСТВУЕТ"]}  HTTP 404
   ```
   Задачи физически исчезли из Jira.

## Вывод

Смена summary на "Удалить" в этом Jira-инстансе, судя по всему, триггерит скрытый workflow/scheduled job, который асинхронно (с задержкой, не мгновенно при PUT) удаляет задачу целиком — не только переименовывает. Операция **необратима** и не является чисто визуальной меткой, как можно было бы предположить из названия действия.

## Последствия для будущей работы (уже отражены в SKILL.md кратким пунктом, см. раздел "Пометка задач на удаление")

- Предупреждать пользователя о риске необратимого удаления ДО выполнения, не только фиксировать формат текста.
- Не считать немедленный GET после PUT доказательством, что задача "просто переименована и цела" — 404 может прийти позже в той же или следующей сессии.
- Если сохранность данных критична — выгрузить и сохранить все поля (summary/description/чекины/issuelinks) в WorkVault до переименования.
- Если пользователь позже обращается к ключу, помеченному ранее как "Удалить", и получает 404 — это ожидаемый исход, не баг API — сообщить прямо, не тратить время на диагностику "почему не находится".
- Не проверено и не воспроизведено намеренно (риск необратимой потери данных) — является наблюдением с одним прецедентом на 4 задачах, не подтверждённым официальной документацией Jira/админом инстанса. Если возникнет случай, когда переименование НЕ привело к удалению — зафиксировать как контрпример и смягчить формулировку.
