## 1. Философия

### Что делает SRTool
- Автоматизирует заполнение Self-Review (SR) в Jira hq.tutu.ru
- Работает как **TG-ассистент** — пользователь пишет в Telegram, Сирень отвечает там же
- Читает **любые указанные источники** (OKR, прошлые SR, другие задачи — состав гибкий)
- Формирует черновик и **сразу заливает** в Jira (без промежуточного "заливай")
- Итерации правок — через Jira (пользователь смотрит результат в SR, даёт правки в TG)

### Чего НЕ делает
- Не принимает решений за пользователя о содержании SR
- Не редактирует уже согласованные SR без явного запроса
- Не работает с чужими SR (только assignee = текущий пользователь)
- Не меняет статус SR — только пользователь переводит в "Согласование с руководителем"
- Не пишет итоги периода (44404-44406) автоматически — только заготовку

### Ключевой принцип: единый источник истины
**Блок 1 (44401)** — единственное поле, которое редактирует пользователь.  
**Блоки 2 и 3 (44402, 44403)** — автоматически деривируются из блока 1.

## 4. Алгоритм генерации

### 4.1. Чтение источников

Сирень читает **все указанные пользователем источники** через Jira API:
- Парсит ссылки из сообщения пользователя
- Для каждой ссылки: `GET /rest/api/2/issue/{KEY}`
- Собирает summary, description, и кастомные поля (если SR)

**Пример:**
```python
sources = parse_links(user_message)
# ['SR-37492', 'OKRAID-1234', 'SR-36500', 'OKRS-5678']

data = {}
for key in sources:
    data[key] = jira.get_issue(key)
```

### 4.2. Генерация блока 1 (44401)

**Структура:**
```
1. [Название цели 1]
	· Подпункт детализации (если нужен)
	· Результат важен для [кого/чего]
	· Критерии приёмки – [измеримые критерии]
	· OKR – [КЛЮЧ-ЗАДАЧИ]

2. [Название цели 2]
	· Результат важен для [кого/чего]
	· Критерии приёмки – [измеримые критерии]
	· OKR – [КЛЮЧ-ЗАДАЧИ]
```

**Правила форматирования:**
- Нумерация: `1.`, `2.`, `3.` и т.д.
- Подпункты: символ `·` (U+00B7) + пробел
- Отступы: табуляция `\t`
- Переносы строк: `\r\n`
- Ключи задач пишутся КАК ЕСТЬ — Jira рендерит их как ссылки

### 4.3. Автодеривация блока 2 (44402 — Критерии)

```python
def derive_block2(block1_text: str) -> str:
    """
    Извлекает критерии приёмки из блока 1.
    """
    lines = block1_text.split('\r\n')
    result = []
    current_item = 0
    
    for line in lines:
        if re.match(r'^\d+\.', line.strip()):
            current_item = int(re.match(r'^(\d+)\.', line.strip()).group(1))
        
        if '· Критерии приёмки –' in line or '· Критерии приёмки —' in line:
            criteria = re.split(r'[–—]', line, maxsplit=1)[1].strip()
            result.append(f"{current_item}. {criteria}")
    
    return '\r\n'.join(result)
```

### 4.4. Автодеривация блока 3 (44403 — OKR)

```python
def derive_block3(block1_text: str, jira_client) -> str:
    """
    Извлекает OKR-ключи из блока 1 и дополняет summary.
    """
    lines = block1_text.split('\r\n')
    result = []
    current_item = 0
    
    for line in lines:
        if re.match(r'^\d+\.', line.strip()):
            current_item = int(re.match(r'^(\d+)\.', line.strip()).group(1))
        
        if '· OKR –' in line or '· OKR —' in line:
            okr_part = re.split(r'[–—]', line, maxsplit=1)[1].strip()
            key_match = re.match(r'^([A-Z]+-\d+)', okr_part)
            if key_match:
                key = key_match.group(1)
                issue = jira_client.get_issue(key)
                summary = issue['fields']['summary']
                result.append(f"{current_item}. {key} {summary}")
    
    return '\r\n'.join(result)
```

## 6. Питфолы (из опыта)

### ❌ PUT /issue/{key} не работает для полей SR
```
PUT /rest/api/2/issue/SR-37492
{"fields": {"customfield_44401": "..."}}
→ 400 Bad Request
```
**Причина:** поля не на основном экране редактирования.  
**Решение:** только через `POST /issue/{key}/transitions` с `transition.id=61`.

### ❌ Парсер: использовать `\t`, не `\s*`
Пункты блока 1 начинаются с `N.\t`. Паттерн `\d+\.\s*` ловит подпункты внутри.
```python
# ПРАВИЛЬНО
pattern = re.compile(r'(?:^|\n)(\d+)\.\t', re.MULTILINE)
```

### ⚠️ Формат переносов строк
Jira ожидает `\r\n` (CRLF), не `\n` (LF).

### ⚠️ Символ буллета
Использовать `·` (U+00B7 MIDDLE DOT), не `-` и не `•`.

### ⚠️ Confluence PAT ≠ Jira PAT
- `dom.tutu.ru` (Confluence) — отдельный токен
- `hq.tutu.ru` (Jira) — отдельный токен

# SRTool v2.0 — Доработка selfcheck конца периода

## 1. Постановка задачи

По итогам сессии selfcheck SR-38862 (июль 2026, 05.08.2026 11:59–20:00) выявлены новые требования к инструменту SRTool и скиллу `tutu-jira-sr`. Текущий инструмент (v1.1, см. `SRTool_TZ.md`) покрывает только **начало периода** (блоки 1-3). Не покрыто:

- Автоматический сбор закрытых задач из Confluence-минуток за отчётный период
- Предзаполнение блоков 4/5/6 на основе закрытых задач
- Интерактивный поштучный бриф по критериям
- Формат «Расширение задачи» / «Повышение контроля и управляемости»
- Вывод plain-text для Jira (без markdown-разметки)
- Read-only режим предпросмотра (без записи в Jira)
- Промежуточное сохранение `_draft.md` с возможностью прервать/продолжить

**Цель:** доработать SRTool и скилл `tutu-jira-sr` так, чтобы selfcheck конца периода (блоки 4-6) выполнялся по единому алгоритму, зафиксированному в этой сессии, и не конфликтовал с флоу начала периода (блоки 1-3, v1.1).

## 2. Различие workflow: начало vs конец периода

SRTool обслуживает два независимых, не пересекающихся по времени workflow одного и того же SR-тикета. Их нельзя путать ни по transition, ни по полям, ни по логике заполнения.

| | **Начало периода** (v1.1) | **Конец периода** (v2.0, этот документ) |
|---|---|---|
| Когда | Старт нового периода (месяц/квартал) | Завершение периода, selfcheck |
| Блоки | 1 (Результат), 2 (Критерии), 3 (OKR) | 4 (Итог: выполнено), 5 (Итог: сложности), 6 (Итог: развитие) |
| Поля Jira | `customfield_44401`, `44402`, `44403` | `customfield_44404`, `44405`, `44406` |
| Transition | **`61`** — «Отредактировать SR» | **`271`** — «Заполнить итоги» |
| Источник данных | OKR, прошлый SR, задачи (ссылки от пользователя) | Закрытые задачи из Confluence-минуток за период |
| Источник блока 2/3 | Автодеривация из блока 1 (regex по `· Критерии приёмки –`, `· OKR –`) | Не деривируется — берётся из брифа с пользователем |
| Интерфейс | TG-диалог, сразу заливка после генерации черновика | Интерактивный поштучный бриф по критериям + `_draft.md` |
| Итоговый MD | `SR-{KEY}_{период}.md` (только блоки 1-3) | Дополняет тот же MD блоками 4-6 (см. §8.1) |
| Документ | `SRTool_TZ.md` v1.1 | `SRTool_TZ_v2.md` v2.0 (это) |

**Правило:** transition `61` и transition `271` НИКОГДА не вызываются в рамках одного алгоритма/запроса. SRTool определяет нужный workflow по явному запросу пользователя (`/sr fill` → начало, `/sr report` или «сделай selfcheck» → конец), а не по эвристике над состоянием тикета.

⚠️ v1.1 и v2.0 — не версии одного алгоритма, а два независимых сценария внутри одного инструмента. После мержа v2.0 в мастер-файл `SRTool_TZ.md` оба раздела остаются как отдельные секции (не заменяют друг друга).

## 3. Алгоритм selfcheck конца периода (как делали 05.08.2026)

### 3.1. Получение плана (блоки 1-3, только чтение)

Источник: JIRA REST API v2 (`/rest/api/2/issue/SR-XXXXX`), поля:
- `customfield_44401` — Блок 1: Результат (план)
- `customfield_44402` — Блок 2: Критерии (план)
- `customfield_44403` — Блок 3: OKR/KPI (план)

Блоки 1-3 читаются **только для контекста** брифа (что было запланировано), не редактируются в рамках этого workflow.

⚠️ API v3 (`/rest/api/3/`) не работает с текущим JIRA_TOKEN — возвращает 302 на логин. Использовать только v2.

### 3.2. Сбор закрытых задач из Confluence

#### 10.3.1. Автопоиск предыдущего SR

```python
def find_previous_sr(jira_client, current_key: str, user: str) -> str:
    """
    Находит предыдущий SR текущего пользователя.
    Возвращает ключ или бросает PreviousSRNotFound.
    """
    jql = (
        f'issuetype = SR AND assignee = "{user}" '
        f'AND status != "Оценка установлена" '
        f'AND key != {current_key} '
        f'ORDER BY created DESC'
    )
    result = jira_client.search(jql, fields=["key", "created"], max_results=1)
    if not result["issues"]:
        raise PreviousSRNotFound(
            f"Не найден предыдущий SR для {user}. "
            f"Проверь вручную: {jql}"
        )
    return result["issues"][0]["key"]
```

⚠️ Статус `"Оценка установлена"` — финальный статус закрытого прошлого цикла (не участвует в поиске каркаса, т.к. по нему могут отсутствовать актуальные блоки). Если у пользователя всего один SR (первый цикл) — `PreviousSRNotFound` перехватывается вызывающим кодом CLI и печатает подсказку «нет предыдущего SR — используй v1.1 TG-флоу с ручными источниками».

#### 10.3.2. Извлечение каркаса KR

Каркас — упорядоченный список OKR-ключей, извлечённых из Блока 3 (`customfield_44403`) предыдущего SR. Формат поля (см. §4.4): `N. КЛЮЧ Summary`, разделитель строк `\r\n`.

```python
def extract_kr_framework(block3_text: str) -> list[dict]:
    """
    Парсит Блок 3 предыдущего SR, возвращает каркас KR в порядке пунктов.
    -> [{"order": 1, "key": "OKRS-3119", "summary": "..."}, ...]
    """
    framework = []
    pattern = re.compile(r'^(\d+)\.\s+([A-Z]+-\d+)\s+(.*)$', re.MULTILINE)
    for match in pattern.finditer(block3_text.replace('\r\n', '\n')):
        framework.append({
            "order": int(match.group(1)),
            "key": match.group(2),
            "summary": match.group(3).strip(),
        })
    if not framework:
        raise EmptyFramework("Блок 3 предыдущего SR не содержит распознаваемых KR-ключей")
    return framework
```

#### 10.3.3. Батч-запрос OKR-данных

Ключи каркаса запрашиваются одним батч-запросом (с проверкой кэша по правилу №0, см. §10.4) вместо N отдельных `GET /issue/{KEY}`:

```python
def load_kr_batch(jira_client, keys: list[str], quarter: str) -> dict[str, dict]:
    """
    Загружает данные по всем KR-ключам: сначала кэш (§10.4),
    для незакэшированных — один батч-запрос (§10.5).
    """
    cached, missing = {}, []
    for key in keys:
        data = load_okr_from_cache(key, quarter)
        if data is not None:
            cached[key] = data
        else:
            missing.append(key)

    if missing:
        fresh = batch_search_issues(jira_client, missing)
        for key, data in fresh.items():
            save_okr_cache(key, data)
        cached.update(fresh)

    return cached
```

Для связей OKRAID→OKRS (issuelinks), которые в ручном флоу требовали 3 отдельных `GET ...?fields=issuelinks`, поле `issuelinks` включается в список полей батч-запроса (§10.5) — отдельные запросы на связи не нужны.

#### 10.3.4. Авторасчёт целевого %

Правило: целевой % выполнения на новый период — не ниже `--target-pct` (default 50%) прироста от текущего фактического % к 100%, если из данных OKR не следует иного (например, KR уже закрыт).

```python
def calc_target_pct(current_pct: float, target_pct_flag: int = 50) -> int:
    """
    current_pct   — текущий % выполнения KR (0-100), из данных OKR (§10.3.3)
    target_pct_flag — минимальный прирост в % от разрыва до 100 (--target-pct)
    """
    if current_pct >= 100:
        return 100
    gap = 100 - current_pct
    increment = gap * (target_pct_flag / 100)
    target = current_pct + increment
    return min(100, round(target))
```

**Пример:** `current_pct=40`, `target_pct_flag=50` → `gap=60`, `increment=30` → `target=70`. Результат подставляется в предложенную формулировку критерия в `_plan_draft.md` (§10.3.6), пользователь может скорректировать в брифе (§10.3.7).

### 10.5. Батчинг API-запросов

**Проблема:** существующий `jira_client.py` (§3) реализует только `get_issue(key)` — один HTTP-запрос на один ключ. Для N незакэшированных ключей каркаса (§10.4) это N запросов.

**Решение:** новый метод `search_batch` в `jira_client.py`, использующий Jira Search API вместо серии GET по одному issue:

```python
def batch_search_issues(jira_client, keys: list[str], fields: list[str] = None) -> dict[str, dict]:
    """
    Один GET /search вместо N GET /issue/{key}.
    Возвращает {key: issue_data}.
    """
    if not keys:
        return {}
    fields = fields or ["summary", "status", "customfield_43782", "issuelinks"]
    jql = f"key IN ({', '.join(keys)})"
    result = jira_client.search(jql, fields=fields, max_results=len(keys))
    return {issue["key"]: issue for issue in result["issues"]}
```

**Лимиты Jira Search API:** до 100 ключей в одном `IN (...)`-выражении. Для SRTool (каркас обычно 7-12 KR) — гарантированно один запрос. Если незакэшированных ключей больше 100 (не встречается в реальных SR) — `batch_search_issues` разбивает на чанки по 100 и делает несколько батч-запросов, но это не основной путь и не требует отдельной обработки в UI.

**Экономия:** 7-9 отдельных `GET /issue/{key}` → 1 `GET /search`. Экономия HTTP-оверхеда (TLS handshake, auth-заголовки на каждый запрос) и токенов контекста на разбор N ответов вместо одного.

### 10.6. Интеграция с TaskRefresh

**Проблема:** после заливки плана в Jira пользователь вручную создаёт follow-up задачи в Confluence-минутках через `./tr do` (аналогично ручному шагу §3.7 в v2.0).

**Решение:** после успешной верификации заливки (§10.3.8) SRTool предлагает создать follow-up задачи по новым/изменённым KR, если не указан флаг `--no-taskrefresh`:

```
План залит в SR-39282. Создать follow-up задачи в минутках?
  1. ML-платформа: «Актуализация плана по вехам» //15.08.26
  2. ML-платформа: «Проверить достижение плана» //31.08.26
[да/нет/редактировать]
```

**Механика:** SRTool извлекает `project_tag` из каркаса (первое слово-тег KR-ключа/summary — та же логика группировки по тегам, что и в §3.3 v2.0), находит по нему целевую страницу минуток (маппинг `project_tag → pageId` — тот же реестр, что использует TaskRefresh) и вызывает TaskRefresh как внешнюю зависимость (не дублирует логику вставки `<ac:task>`, по аналогии с §4 — вызов ConfluenceSync):

```python
def suggest_followup_tasks(framework: list[dict], sr_key: str) -> list[dict]:
    """Строит список предложений follow-up задач по каркасу для TaskRefresh."""
    suggestions = []
    for item in framework:
        tag = extract_project_tag(item["summary"])
        page_id = resolve_minutes_page(tag)  # реестр TaskRefresh
        if page_id:
            suggestions.append({
                "project_tag": tag,
                "page_id": page_id,
                "text": f"Актуализация плана по вехам ({item['key']})",
                "due": None,  # запрашивается у пользователя в §10.3.7-подобном подтверждении
            })
    return suggestions
```

Если пользователь отвечает «да» — SRTool вызывает `taskrefresh.create_task(page_id, text, due)` для каждого подтверждённого пункта. Если «редактировать» — короткий инлайн-диалог правки текста/даты перед вызовом. Логика вставки `<ac:task>` в Confluence остаётся в TaskRefresh — SRTool не дублирует её (тот же принцип разделения ответственности, что в §4 для ConfluenceSync).

### 11.1. Постановка

### 11.2. CLI `fill-plan`

**Синтаксис:**

```bash
cd ~/USERTOOLS/SRTool
python3 -m srtool fill-plan SR-XXXXX --from-md <path> [--submit] [--yes] [--sync-md/--no-sync-md] [--dry-run]
```

| Флаг | По умолчанию | Поведение |
|---|---|---|
| `--from-md` | обязателен | Путь к локальному MD; парсятся секции `## Блок 1 …`, `## Блок 2 …`, `## Блок 3 …` |
| `--dry-run` | off | Показать transition и payload (JSON), **без** POST в Jira |
| `--submit` | off | После успешной заливки плана — transition согласования (имена «Согласовать» / «Согласование руководителем», типично id **11**) |
| `--yes` | off | Пропустить интерактивное подтверждение для `--submit` (агенты/Cursor, non-TTY) |
| `--sync-md` / `--no-sync-md` | **on** | После заливки обновить мета-строки шапки MD через `sync_md_header` |

**Механика:**

1. Чтение блоков 1–3 из MD (`parse_plan_md`); пустые или placeholder-тела отбрасываются.
2. `POST /rest/api/2/issue/{SR-KEY}/transitions` с transition **61** «Отредактировать SR» и полями `customfield_44401`–`44403` (CRLF, §6).
3. Verification: один `GET` issue с полями 44401–44403 и проверкой, что **статус SR не изменился** неожиданно на шаге заливки плана.
4. Опционально `--submit`: второй POST transition согласования (пустой `fields`).
5. Опционально `--sync-md`: `sync_md_header(md_path, …)` с описанием `fill-plan {id} «Отредактировать SR»` (+ `; submit {id}` при `--submit`).

### 11.3. Функция `sync_md_header`

```python
sync_md_header(path, *, status, write_desc, when=None)
```
