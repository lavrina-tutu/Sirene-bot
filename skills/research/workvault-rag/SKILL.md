# WorkVault — поиск по MD-заметкам (встречи, ТЗ)

## Overview

Поиск по WorkVault (Obsidian MD-заметки: встречи, ТЗ, Confluence) через прямую работу
с файловой системой — `search_files` (по имени файла/содержимому) + `read_file`.
**qmd (semantic search MCP) исключён из системы 16.07.2026** — был ненадёжен (CPU-only
эмбеддинг, частые "LLM session expired" сбои индексации, зависания по 300с таймауту на
простых запросах в рантайме) и оказался избыточен: файловый поиск по имени+дате
справляется с реальными запросами Саши быстрее и надёжнее. См. `references/qmd-retired-2026-07-16.md`
для истории и rollback-инструкции, если semantic search когда-то снова понадобится.

## When to Use

Триггер срабатывает на любой из этих типов запроса:

- Вопросы про **встречи**: "что обсуждали с X", "какая была встреча про Y", "когда говорили про Z"
- Вопросы про **задачи/поручения**: "какие задачи ждёт от меня X", "что я обещал сделать", "что поручили Y"
- Вопросы про **решения**: "что решили по X", "какое было решение насчёт Y"
- Вопросы про **риски/блокеры**: "какие риски по X", "что блокирует Y"
- PM Briefing в начале сессии — «что важного по проектам?»
- Поиск по 1000+ файлам NewMeetings без явных ключевых слов

## Алгоритм поиска по встречам (структурные запросы: дата/участники/проект + тип сущности)

Применять к любому запросу вида "какие [задачи/решения/риски/блокеры] по [X/за период Y]".

### Шаг 1 — период

- Дата/период явно указан в запросе ("с 16.06", "за последние 2 недели", "в июне") → фильтр списка файлов по дате в имени файла (`YYYY-MM-DD HH-MM-SS ...`) на этот период.
- Период не указан → по умолчанию последние **6 месяцев**.
- Фильтрация по дате — через `search_files(target="files")` по паттерну имени, отсортировано по времени изменения.

### Шаг 2 — участники

- Человек назван в запросе ("что обещал Аралов", "что мы обсуждали с Х") → из набора шага 1 оставить только встречи, где этот человек указан в секции **"Участники:"** файла (точное совпадение в списке участников, не любое упоминание имени по всему тексту — упоминание "в контексте" даёт слишком много шума).

### Шаг 3 — проект/тема

- Проект/тема назван в запросе ("по ML-платформе", "по мультиагентной системе") → из набора после шагов 1-2 оставить только встречи, где проект упоминается в тексте (заголовок встречи или содержимое).

### Шаг 4 — извлечение сущностей

Работать с финальным отфильтрованным набором файлов:
- **Если файлов >10** — не читать все инлайн: делегировать Haiku (`delegate_task`, таймаут 120с) — сырые Action Items/Риски/Решения из всех файлов набора + вопрос Саши → отфильтрованная выжимка.
- **Если файлов ≤10** — читать напрямую (`read_file`), без делегирования.
- **4.1 Запрошены НЕ задачи** (решения / риски / блокеры) → выдать все найденные сущности этого типа из всех файлов набора, без дополнительной фильтрации по назначенному лицу.
- **4.2 Запрошены задачи** → выдать только Action Items, где ответственный явно указан как один из упомянутых участников (точное имя в строке Action Item, не implicit-отнесение по контексту). Если Саша спрашивает про себя ("что мне поручили") — те же правила, явное указание его имени в Action Item.

### Быстрый путь для "последняя встреча с X" (без структурного фильтра по датам/сущностям)

Для запроса вида "что от X ожидается на встрече", "что решили с X в последний раз" —
не нужен весь 4-шаговый алгоритм, достаточно:
1. `search_files(pattern="*<Имя>*", target="files", path="WorkVault/Meetings/NewMeetings")`
2. Отсортировать по дате в имени файла, взять самый свежий `... - summary.md`.
3. `read_file` этого файла напрямую — саммари уже содержит структурированные секции
   (Участники/Решения/Задачи/Риски/Блокеры), доп. поиск не нужен.

Это единственный путь для такого класса запроса (не первая попытка) — не пытаться сначала
искать через MCP semantic search инструменты, если они появятся снова в будущем.

## Признак "неясная запись / переговорка"

На встречах в переговорках (особенно мультисинки и 1-1, где несколько человек говорят в одной комнате) Fireflies часто **неверно атрибутирует Action Items конкретному спикеру** — разметка голосов даёт сбой. Такие задачи **лучше по умолчанию относить к самому Саше** ("мои задачи, разберу вручную далее"), а не к тому, кому их формально приписал Fireflies.

**Признаки "неясной записи" (совпадение любых 2 из 3 = считать неясной):**
1. Файл встречи — загрузка аудио/видео (`.m4a`/`.mp4` фигурирует в названии файла) — то есть запись с диктофона/телефона в переговорке, не прямая интеграция с онлайн-звонком.
2. Action Items в summary не содержат чёткого разделения "Имя: задача" — общий список без явного автора.
3. Название встречи совпадает с известным названием переговорки ТУТУ — актуальный список переговорок в `WorkVault/Contacts/meeting-rooms.md` (обновляется вручную запуском `orglookup rooms`, `~/USERTOOLS/OrgLookup`). При использовании этого признака проверить дату `updated:` в frontmatter файла на актуальность.

При совпадении признаков — такие Action Items помечать как задачи Саши, а не оригинального (возможно ошибочного) адресата, и явно указывать в ответе, что источник — запись из переговорки/неясная атрибуция, требует ручной проверки.

## Filter-farm остался неактуален

Ранее использовался для qmd-коллекций (copy-based фильтрация разнородного контента
перед индексацией). Без qmd — не нужен: `search_files`/`read_file` работают напрямую
по исходным папкам WorkVault, фильтрация по паттерну имени файла делается на лету в
каждом запросе, не требует предварительного копирования.

## Verification Checklist

- [ ] Структурный запрос (дата/участник/проект + сущность) прошёл 4-шаговый алгоритм, не угадан на глаз
