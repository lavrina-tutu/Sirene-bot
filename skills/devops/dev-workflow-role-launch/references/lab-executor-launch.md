# Запуск lab-исполнителя: узкие гейты, честные негативы

Применимо, когда роль-исполнитель (codex exec, gpt-6.1-terra) должна построить lab-стенд
(плагины, адаптеры, observer) и прогнать матрицу проб по согласованному проекту.

## Одноразовый промпт «вся матрица» не работает

Полный промпт вида «реализуй плагины и прогони 52+132+P12» / «реализуй observer и прогони
~20 проб» на codex-исполнителе даёт rc=0, но роль останавливается на подготовке (source-audit,
проверка примитивов flock/изоляции, loader) и возвращает честный отчёт «плагины не реализованы,
всё NOT_RUN». Модель не пишет большой объём кода за один ход — она пишет частичный отчёт.

**Штатный ход:** разбить lab на узкие single-gate шаги, каждый своим фоновым codex-прогоном:
- «Шаг A: только identity gate» (B2) / «Шаг E: только E-03» (ErrorBus);
- явно написать «предыдущий прогон остановился на подготовке, твоя задача — закрыть ТОЛЬКО
  этот гейт»;
- запретить остальные группы («полную матрицу НЕ гоняй — это следующий шаг при PASS»);
- дать ссылки на конкретные точки кода: пример установки плагина
  (`tests/fakes/providers/fake_acp_agent.py` install_provider_plugin), реестр
  (`providers/__init__.py`), хуки (`plugins_dispatch.py`, `turn_context.py`), transport
  (`chat_completion_helpers.py` build_kwargs), ErrorBus (`kanban_db.py` write_txn/add_comment,
  `kanban_db_dispatch.py` after-lock tick);
- каждый шаг возвращает вердикт (PASS/FAIL/negative), следующий запускается только после.

## Отрицательный lab-результат — валидный вердикт

negative-B2 или FAIL свойства — это завершённый результат шага, а не незавершённость:
- по проекту negative identity gate = стоп carrier-матрицы (не расширять её «до достоверности»);
- не переименовывать negative/FAIL в PASS и не «достраивать» его полными пробами;
- развилку (B3 vs B1) передать архитектору с полным контекстом: что проверено, что NOT_RUN,
  какой публичный API отсутствует (напр. transport отдаёт session, но не turn/ordinal/main-aux);
- рекомендацию архитектора — владельцу, выбор владельца зафиксировать в evidence/;
- частичные «PASS примитива» в отчёте исполнителя не равны PASS oracle: P-BOARD/P-GUARD —
  примитивы (flock, одна запись), а не доказанный receipt-протокол.

## Почему это происходит (механизм)

Hook-плагин исполняется в отдельном потоке с копией контекста (plugins_dispatch); изменение
ContextVar в hook не переносится в вызывающий поток. Transport kwargs строятся из session без
turn/ordinal/main-aux. Поэтому identity-привязку внешнего вызова к текущему turn на публичном
API часто доказать нельзя — фиксировать отрицательный результат, а не private-field обход.

## Подписанная цепочка receipt: подделка ≠ порча доверенного материала

Reader HMAC-цепочки обязан различать «поддельная запись» и «повреждён доверенный ключ/цепочка»:
при несовпадении ключа/подписи НЕ возвращать пустую цепочку и НЕ допускать повторную отправку
— фиксировать AUTHENTICITY_NOT_PROVEN и стоп доставки. Механизм: молчаливый сброс всей
подписанной цепочки выглядит как «ещё не отправляли» и открывает окно re-send; публичный
comments API не отличает поддельную запись от повреждённой доверенной без дополнительного
защищённого свидетельства, а доверие к `author` подменой не является. Если защищённая
граница недостижима — отдельный отрицательный результат по свойству, не PASS.
