# Резюме/CV — разбор и доработка

Триггеры: резюме, CV, hh.ru, опыт работы, вакансия. Обновляем резюме Саши: сохраняем шаблон hh.ru, делаем читаемым для ИИ/ATS, HR, руководителей и проектного офиса, факты (особенно блок ТУТУ) берём из Confluence (уставы + отчёты о завершении), результат кладём в `~/WorkVault/Outbox/`.

## Процедура

1. **Извлечь исходник.** Резюме приходит RTF-экспортом hh.ru. Рабочий способ (pandoc 2.14 на ВМ **не умеет** input `rtf`):
   ```bash
   cd <scratch>
   uv venv .venv && uv pip install --python .venv/bin/python striprtf
   .venv/bin/python -c "from striprtf.striprtf import rtf_to_text; print(rtf_to_text(open('resume.rtf',encoding='cp1251',errors='replace').read(), errors='replace', encoding='cp1251'))" > resume.txt
   ```
   RTF-экспорт hh.ru в кодировке **cp1251** — читать с `encoding='cp1251'`. Всегда смотреть полный текст, не первые страницы.
2. **Построить карту структуры** (шаблон hh.ru): Шапка → Желаемая должность → Обо мне → Опыт (новый→старый) → Образование → Курсы → Тесты/экзамены → Навыки → Языки. Блок «Опыт вождения» удалять — шум.
3. **Собрать факты по текущему работодателю из Confluence** — не из пересказов. Для портфеля человека: статусная страница проектов + страница Проектного комитета + уставы/отчёты о завершении. Рецепт — `tutu-confluence-jira` → `references/person-project-portfolio.md`. Формулировки мест работы строить **только** на уставе (цель/зачем) и отчёте о завершении (сроки, критерии приёмки, решение комитета).
4. **Ревью архитектором (HR/ATS-читаемость).** Аналитическая задача → Cursor `cursor-grok-4.6-high` (см. `cursor-cli`). Промпт — файлом, read-only, писать отчёт в файл-артефакт (`/tmp/<...>.md`). **Питфолл:** `result` в JSON часто приходит пустым при большом `outputTokens` — читать отчёт с диска, а не из вывода процесса.
5. **Черновик в Outbox** — `~/WorkVault/Outbox/<ФИО>_резюме_черновик.md`, затем синк (`systemctl --user start owncloud-sync.service`) и подтверждение доставки через `rclone lsjson` (см. `workvault-outbox`).
6. **Шлифовать поштучно** (пользовательский стиль): идти по одному блоку/проекту, показывать текущий текст + факты из документов + предлагаемые варианты, ждать подтверждения.

## Сбор фактуры блока (поштучный опрос, 25.10.2026 валидирован)

Когда блок (ТУТУ/Синимекс/Softline/СИАМ) не дописан — собирать фактуру опросом, а не в один заход:

- **Задавать по одному вопросу** из заранее подготовленного списка архитектора (группы Т-1/Т-2/Т-3/С-1/С-2/О-1 — см. `~/WorkVault/Personal/resume/resume_context_questions_<дата>.md`). Каждый в списке уже содержит «зачем» (какую аудиторию закрывает) + «пример раскрытия» — использовать их для формулировки.
- **Формулировать вопрос с контекстом и ссылкой на уже сказанное:** «говоришь про/как… — а вот это расскажи, пожалуйста» (пользователь явно просил такой формат). Не абстрактный вопрос — а «ты заявляешь X, поясни Y».
- **Дёшево просить «одного-двух штрихов достаточно»** на каждый вопрос — пользователь отвечает компактно, дозирование ускоряет и не выжигает контекст.
- **После каждого ответа сразу фиксировать** в рабочий `*_block_faktura*.md` scratch (один файл на блок работодателя, напр. `tutu_block_faktura.md`, `sinimex_block_faktura_v2.md`, `other_blocks_faktura.md`), затем переносить в `~/WorkVault/Personal/resume/` + синк.
- **Транскрипцию Саши расшифровывать** в записи («гера/жира»=Jira, «хордовые офисные»=Microsoft Office, «прожито»=MS Project, «сноусими»=Синимекс, «сжигание бюджета»=burn-down, «даты гауменс»=data governance) — и озвучивать прочтение, чтобы он подтвердил.
- **Разделять чистовик и прожарку.** Когда идёт создание чистовика резюме — задавать только вопросы на дополнение фактуры блоков; провокационные интервью-вопросы (самый сложный кейс, провал, конфликт целей) — для отдельной прожарки, сюда не тащить.
- **Эффект после запуска — обязательный элемент каждого проекта** (архитектор стабильно отмечает пробел «доставка сильнее, чем результат заказчика»). Если в блоке только «сдано/акт подписан» — допросить: что реально изменилось у заказчика после внедрения, кто пользовался результатом, какая метрика/преференция получена.
- **Управление людьми — фиксировать честно по каждому месту:** прямые подчинённые vs матрица/функциональная координация, численность на пике, наличие SR/PR/кадровых решений. Завышать масштаб нельзя — на интервью вскроется. (СИАМ ≈ 7 чел. и руководитель отдела; Синимекс — матрица без прямых; Туту — 1 прямой аналитик.)
- **Инструменты — по каждому месту** (MS Project, Jira, Confluence, Google-стек, Excel/pivot, договоры в файлах), иначе PMO-вопрос «в чём реально вёл проекты» останется дырой.
- **Целевая роль/заголовок — определять первым** (у Саши: «Руководитель проектов» программных продуктов: развитие/доработка/сопровождение ПО + AI и аналитический продукт; контекст — онлайн). От неё зависит верх резюме.

## Жёсткие предпочтения пользователя (always-on)

- **Формат hh.ru сохранять.** Желаемая должность — `Руководитель проектов` (не «Руководитель IT проектов»); официальная длинная должность — только в поле места работы.
- **В блоке ТУТУ витрина = проекты, доведённые до завершения.** Поручения проектного комитета (PMOTECH) — НЕ достижения, только операционный контур в обязанностях.
- **Командо-формулировка:** «мы, команда проекта», «проведено внедрение», а не «я внедрил/выбрал».
- **Не писать «Успешно реализован / OTIF положительный».** Достаточно «проект завершён в срок, критерии приёмки выполнены, завершение без замечаний».
- **Достижения — над обязанностями**, формат «действие — результат»; метрики **только подтверждённые** документами, отсутствующие — `[вставить]`.
- **Обязательно польза для бизнеса** («что это позволило бизнесу»), а не пересказ процесса.
- **Цифры округлять** до защищаемого значения; сумму экономии можно собирать из нескольких статей (прямые затраты + избегаемые риски).
- **Навыки** — категориями/в порядке приоритета (PM-ядро → методологии → AI/data → PMO-инструменты → короткий бэкграунд); убирать архаику (БОСС-Компания, HTML/C# в топе, вождение, «Time management»).
- «О себе» без лида «28+ лет в ИТ»: сначала текущая поставка + внедренческий фундамент, AI/ML — как текущий контур роли РП, а не профессия (иначе AI-washing).

## Питфоллы

- **Не выдумывать достижения и цифры.** Каждый факт — из устава/отчёта. Если число выводится косвенно (напр. экономия = стоимость полного внедрения минус стоимость альтернативы) — так и говорить пользователю: «в документе буквально нет, выводится из цифр X и Y».
- **Приоритет — новый акцент пользователя, а не прошлый отчёт архитектора.** Рекомендации прошлых сессий могут противоречить новому акценту — акцент пользователя важнее.
- **Проверять заявленные пользователем факты по документам** — он может просить «проверь, что я сказал всё правильно на основе фактов»; давать цитаты/числа и честно отмечать расхождения.
- Конечный артефакт — md в Outbox; выгрузку в hh делает пользователь вручную.

## Открытые вопросы (закрывать с пользователем, не дефолтить)

Дата ухода с прошлого места; юр./hh-имя работодателя; метрики по каждому проекту (статус + эффект); уровень английского (один); рабочие ли Jira/Python/SQL сейчас; итог пилотов (go/no-go).
