# Точечный поезд ролей через прямой codex exec (вне pipeline)

Когда готового слага нет и поезд ведётся вне штатного kanban-контура, роли зовутся
напрямую из terminal через `codex exec`. Это рабочий путь для полного цикла
архитектор → ревизор → исполнитель на согласованных дельтах.

## Штатная команда запуска роли (фоново)

```bash
cd <workdir-поезда>
LOG=evidence/<РОЛЬ>.arch.log
rm -f "$LOG"
codex exec -m <РОЛЕВАЯ-МОДЕЛЬ> -c model_reasoning_effort="high" \
  --skip-git-repo-check --json --sandbox danger-full-access \
  < out/<ПРОМПТ>.md > "$LOG" 2>> "$LOG"
echo "exit=$? log=$LOG"; tail -20 "$LOG"
```

Промпт роли — готовый Markdown-файл в `out/`, подаётся через stdin (`<`). Лог —
JSON-поток codex в `evidence/*.arch.log`. Вердикт роли = последний `agent_message`
в логе (начинается с `## Вердикт`), его извлечь и сохранить отдельным out-файлом.

Ролевые модели (ChatGPT-контур codex): архитектор и ревизор — `gpt-6-astra`
(БЕЗ `.1`), исполнитель — `gpt-6.1-sol` (Сол 6.1).

## Инструмент terminal: notify/persist_on_release = только с background=true

`notify` и `persist_on_release` — валидные параметры ТОЛЬКО при `background=true`
на уровне вызова. Передать их без background → ошибка "notify only applies to
background commands". Перезапуск с корректным `terminal(command, background=true,
notify=true, persist_on_release=true)`. Шаблон фонового запуска роли (внешний обвес
то же): hashes до → команда → hashes после, всё в одну команду, notify=true.

## Петля REV (независимый ревизор → правки → повторная REV)

1. Ревизор = независимая роль (та же `gpt-6-astra`), промпт просит APPROVE /
   REQUEST-CHANGES с предметными адресуемыми замечаниями (R1/R2…). Вердикт в
   `out/REV-*.md`, только его и пишет.
2. REQUEST-CHANGES → правит АРХИТЕКТОР (не исполнитель): адресные замены в дельте,
   не перекрытие общей оговоркой в конце. REV-замечания часто про
   оставшиеся старые ограничивающие фразы в базе, противоречащие новой дельте.
3. Повторная REV на исправленной дельте → APPROVE. SHA нормы/плана должны совпасть
   с рецензированными (доказательство: их не тронули), SHA дельты — измениться.

## Целостность и честность (правила, доказанные в прогоне)

- **SHA до/после write-set кандидата** фиксируй в лог роли: это доказывает, ЧТО
  тронуто, и что ядро/норма/план/документы решений не изменены.
- Роль-архитектор read-only: она может писать только свои out-документы и свой
  log; ничего не создавать/править вне явного write-set. Самопроверку роли
  (assert на структуру, счётчик code-fences) включать в конец постановки.
- Постановка роли обязана содержать: границы (что править/не править, какие пути),
  контекст решений владельца (не пересматриваются), формат выхода, прямые запреты
  (не запускать managed proof / не трогать ядро / честно помечать NOT_RUN).
- НЕ запрашивать runtime-доказательство там, где роль не способна его дать;
  требовать честной пометки "требует следующего этапа" вместо смоделированного
  успеха.

## Питфолы

- Ожидание, что роль подтвердит готовый механизм, хотя capability ещё не доказана
  (BC-NOT_PROVEN): постановка должна требовать честного признания NOT_PROVEN,
  а не выдачу за сделанное. Не лакировать: лучший архитектор прямо ставит
  открытую capability вместо обещания рабочего барьера.
- Обратный порядок "fixtures только после proof" конфликтует с планом
  "coding → фиксация hashes → managed proof" — в дельте/базе не должно оставаться
  старых ограничивающих фраз, противоречащих новому плану (это и есть типичные
  R1/R2-замечания ревизора).
- Три подряд сбоя одной фазы = стоп (запрет слепых повторов) — действует и для
  точечных инвоков, и для поезда ролей.
