# Оптимизация dev-графа: мелкие CHANGE-доработки (09.09.2026)

Диагноз архитектора (cursor-grok-4.6-high) + независимый ревью ревизора
(claude-sonnet-5-medium) по запросу Саши «раньше было дешевле и быстрее, найди
ускорение в разы». Источник фактов: одна реальная доработка TaskRefresh
v2.4.1→2.4.2 «§27 Всё в одном для ./tr new» — ~сотни строк в 3 файлах (write_ops.py,
date_parse.py, task_block.py) + tests/test_new_task.py (18 тестов) + SKILL.md.
Режим «делай в 1 проход» (one-pass, auto-pass гейтов).

## Итог в одну строку
Мелкая CHANGE-доработка (~1-3 файла) разворачивает **полный пайплайн нового
инструмента** (16 карточек, ~162 мин активного + ~115 мин простоев), хотя по
размеру/риску это BUGFIX. Реально «делали фичу» (impl+test) — ~12 мин (**7%**).
Остальное — конверт оркестрации. Ускорение в разы — не «одна кнопка», а связка:
гейты-скрипт + skip compress + слим-граф CHANGE-LIGHT (пилот), поверх диагностики
причины повторного архитектурирования.

## Корневые причины (архитектор)
1. **CHANGE = полный пайплайн нового инструмента** (GLOSSARY §5.2: stabilize+compress,
   REV default ON, полный PLAN-IMPL-TAIL), хотя по размеру это BUGFIX (там compress
   skip, REV OFF при ≤3 файлах). Ярлык CHANGE перевешивает фактический размер.
2. **One-pass ≠ быстрый путь.** One-pass только auto-complete трёх гейтов; 16
   карточек × отдельный agent -p остаются.
3. **Механика через полноценного воркера.** TZ:stabilize / GATE:* в каноне — «без
   LLM / без agent -p», но по факту подняли LLM.
4. **Двойной архитектор.** TZ:patch спроектировал §27, затем HF:plan (15 мин grok)
   переписал то же пофайлово.
5. **Канон компрессора сам себе противоречит:** скилл говорит composer-2.5, промпт
   tz-compressor-prompt.md — gemini-3.6-flash-low (composer запрещён). Факт прогона
   совпал с промптом (flash), не со скиллом. Чинить «на composer» — дороже, не дешевле.

## C. Слим-граф CHANGE-LIGHT (структурно) — ГЛАВНЫЙ рычаг
**Критерии (все сразу):** ≤3 файлов кода + тесты + SKILL.md; аддитивная секция
master-ТЗ (не переписывание контрактов); нет новых сущностей/cron/.env/чужих ТЗ;
бриф закрыт + фраза one-pass; есть/будут тесты на новый путь. Любой пункт ломается
→ полный CHANGE.

**Граф (6 карточек вместо 16):**
```
TZ:patch (секция + bump version + инвентарь в том же ходе)
  → HF:impl → HF:test → HF:docs-handoff → ORCH:shared-state (скрипт) → GATE:done (скрипт)
```
Исключаются (и почему это не срез качества): TZ:stabilize (вшит в patch, mtime),
TZ:compress (skip — архитектор читает целевые §), REV:tz (см. B1, вне shared-модулей),
отдельный TZ:finalize (патч и есть запись), GATE:take-into-work (auto-pass скриптом),
HF:plan + GATE:plan-approve (план = секция ТЗ + список файлов в comment)
HF:backup (git/копия 3 файлов).

Ориентир: **25-40 мин стены** на мелкую доработку → активное ~4-6×, стена ~7-10×.

**Инварианты, которые НЕ нарушать:** ТЗ на диске до кода; тесты отдельной фазой;
preflight перед done; манифест не пишет исполнитель.

**Оговорки ревизора (критично):**
- n=1 — все множители это **гипотеза, не факт**. CHANGE-LIGHT вводить **пилотом на
  3-5 реальных доработках**, дефолтом не делать с одного прогона.
- В бюджете не учтены: restore-all-skills.sh (обязателен после правки SKILL.md),
  запись в MAIN_TZ_INVENTORY.md. Скриптовый GATE:done должен **реально валидировать**
  (тесты/манифест), а не только mtime/version — иначе это плацебо. Не убирать навсегда
  выборочный LLM-аудит поверх скрипта (скрытая деградация качества).
- Добавить эскалацию LIGHT→полный CHANGE (вдруг в impl выяснилось, что нужен 4-й файл).
- Ввести метрику «доля LIGHT-циклов → последующий BUGFIX» (обратная связь по качеству).

## D. Диспетчер и простои — РЕВИЗОР ПОПРАВИЛ ПРИЧИНУ
Архитектор предположил: гапы 82/33 мин — смена модели (cold spawn grok/sonnet).
**Ревизор: сомнительно.** 82/33 мин на порядок больше стоимости cold-spawn LLM
(обычно секунды-единицы минут). Величина похожа на **poll-interval диспетчера/крона**
(ожидание следующего цикла проверки очереди), который сработал бы одинаково при любой
модели. **ПЕРЕД фиксом «непрерывный spawn» поднять логи оркестратора и проверить
фиксированный poll-interval** — иначе «починишь» не ту причину и не получишь 115 мин.

Воздействия (если poll развеян): немедленный spawn ребёнка после complete; watchdog
ready>3-5 мин → алерт в TG; stabilize/backup/ORCH/гейты не диспатчить как Cursor-
агентов (меньше спавнов = меньше окон смерти); sticky `--resume` TZ:patch→retry→
finalize (retry 307с против первых 1318с — цена тёплой сессии); **не чередовать 4
модели на мелком графе** — одна composer на LIGHT; гейт complete'ит тот же воркер
или 10-строчный hook, не новый agent -p.

## Практичный порядок внедрения
1→3 сразу (процесс, не качество) → 4+0 как CHANGE-LIGHT в GLOSSARY §5.2 (и правила
скилла «нет шорткатов» сузить: он запрещал skip ТЗ-файла, а не skip compress/REV/
второго плана) → модели (7) после того, как граф станет коротким. Иначе дешёвая
модель на 16 фазах всё равно проиграет короткому графу на одной composer.
