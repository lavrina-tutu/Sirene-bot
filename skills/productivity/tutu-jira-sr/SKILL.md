# TUTU Jira Self-Review (SR)

Работа с задачами Self-Review (issuetype `SR`, проект в Jira `hq.tutu.ru`, напр. `SR-37535`). Авторизация — тот же `JIRA_TOKEN`/`JIRA_BASE_URL`, см. `tutu-confluence-jira`, здесь не дублируется.

Полное архитектурное ТЗ (философия, TG-флоу заполнения, roadmap) — `WorkVault/Hermes-Backlog/TZ/SRTool/SRTool_TZ.md`. Здесь — рабочая карта полей + конкретно флоу **check** (проверка периода), которого не было в ТЗ до этой сессии.

## Поля SR (customfield ID)

| Поле | ID | Когда заполняется |
|---|---|---|
| Результат (план) | `customfield_44401` | начало периода |
| Критерии (план) | `customfield_44402` | начало периода, автодеривируется из 44401 |
| OKR/KPI (план) | `customfield_44403` | начало периода, автодеривируется из 44401 |
| Итог: выполнено (факт) | `customfield_44404` | конец периода |
| Итог: сложности (факт) | `customfield_44405` | конец периода |
| Итог: развитие/пробелы | `customfield_44406` | конец периода |
| Поведение | `customfield_44414` | конец периода, часто `None` |

Поле `customfield_44405` в Jira называется «Итог: сложности».
В интерфейсе Confluence заголовок раздела — «Каких знаний или навыков не хватило и почему?».
Это один блок: по каждой цели — проблема (сложность / какой знаний-навыков не хватило) и решение;
в конце блока — совокупное предложение по развитию, корпоративной помощи или иным действиям.
Не трактовать 44405 как «список только невыполненных пунктов».

Transitions (PUT не работает для этих полей — только через transition, см. питфолы в SRTool_TZ.md):
- `61` = "Отредактировать SR" — для заполнения ПЛАНА (44401-44403) в начале периода.
- `271` = "Заполнить итоги" — для заполнения ИТОГОВ (44404-44406) в конце периода. **Не `61`** — попытка залить итоги через `61` возвращает `400` ("операция не действительна для текущего состояния"), т.к. это разные бизнес-процессы Jira для разных стадий SR. Всегда сверять доступную transition через `GET /issue/{key}/transitions` перед первой заливкой итогов, а не считать `61` универсальной.
- `11`/`281` = согласовать/отправить на оценку — делает только пользователь, не Сирень.
- Статус SR после заливки итогов остаётся как есть (напр. "В работе") — Сирень не переводит дальше без явной команды.

Получить сырые поля:
```bash
source ~/.hermes/profiles/anthropic/.env
curl -s -H "Authorization: Bearer $JIRA_TOKEN" -H "Content-Type: application/json" \
  "https://hq.tutu.ru/rest/api/2/issue/SR-XXXXX?fields=summary,assignee,status,customfield_44401,customfield_44402,customfield_44403,customfield_44404,customfield_44405,customfield_44406,customfield_44414"
```

## SRTool CLI v2.0 — инструмент для конца периода (блоки 4-6)

**Путь:** `~/USERTOOLS/SRTool/`. Не установлен как глобальная команда — запускать `python3 -m srtool <команда>` из этой директории (venv/зависимости — см. `pyproject.toml`, устанавливаются `pip install -e .`).

```bash
cd ~/USERTOOLS/SRTool

# Интерактивный бриф + заливка итогов (transition 271, блоки 4-6)
python3 -m srtool report SR-XXXXX [--from YYYY-MM-DD --to YYYY-MM-DD]

# Read-only превью: план + собранные закрытые задачи + авто-маппинг, БЕЗ файлов и БЕЗ transition
python3 -m srtool preview SR-XXXXX [--from YYYY-MM-DD --to YYYY-MM-DD]
```

- `report` — полный цикл SELFCHECK (см. ниже): читает план (44401-44403), собирает закрытые задачи из Confluence-минуток за период (через `confluencesync.tasks.parse_tasks_from_page`, см. `tutu-confluence-jira`), предлагает авто-маппинг задач на критерии, ведёт поштучный бриф (статус/расширение/контроль/проблемы-решения), автосохраняет `_draft.md` после каждого ответа, при подтверждении заливает 44404-44406 через **transition `271`** (не `61` — см. таблицу transitions выше).
- `preview` — те же шаги 1-3 (план + сбор задач + авто-маппинг), но без брифа, без записи `_draft.md`, без `transitions`. Использовать, когда нужно быстро посмотреть, что соберёт инструмент, прежде чем тратить время на полный бриф.
- Если найден незавершённый `_draft.md` — `report` предлагает продолжить с места остановки или начать заново (не теряет прогресс при разрыве сессии).
- Период по умолчанию (без `--from`/`--to`) — текущий отчётный месяц; см. `default_period()` в `srtool.selfcheck`.
- Полное ТЗ модулей (12 модулей, 49 тестов) и алгоритм — `WorkVault/Hermes-Backlog/TZ/SRTool/SRTool_TZ.md`, раздел «SRTool v2.0».

## Флоу FILL (заполнение плана/факта) — см. SRTool_TZ.md
TG-driven, сразу заливка через transition 61, буллет `·` (U+00B7), переносы `\r\n`, парсер по `\d+\.\t`. Не описываю повторно здесь — детали в ТЗ.

## Флоу PLAN (планирование нового периода с переносом открытых пунктов)

**Цель:** составить план (44401-44403) на новый период (напр. июль), опираясь на два источника: (1) SR завершённого предыдущего периода как первоисточник открытых/переходящих вопросов, (2) актуальный список Jira-задач OKR, где пользователь — исполнитель, на новый период.

### Порядок действий
1. **Сначала прочитать факт предыдущего SR (44404-44406), не план нового периода.** Это первоисточник: какие пункты не были выполнены/выполнены частично, какие проблемы остались нерешёнными, что явно anonсировано как "перенесено", "продолжаем в следующем периоде". Выписать их отдельным списком — это кандидаты на перенос.
2. **Сверить с Jira-задачами OKR на новый период**, которые пользователь дал как "мои задачи-исполнитель на Qx". Для каждой такой задачи — проверить `fixVersion` (см. `tutu-jira-okr`, фильтр по АИД по умолчанию), issuelinks (Contains — есть ли родитель/дочерние задачи), assignee.
3. **Если fixVersion задачи не совпадает с ожидаемым кварталом** (напр. осталось "2026 ф.г." или битое значение вместо "Q3 2026") — не отбрасывать и не додумывать самостоятельно, спросить пользователя explicit: включаем ли задачу несмотря на некорректный fixVersion, или сначала должен быть поправлен fixVersion. Если пользователь говорит "уже поправил" — перепроверить GET-ом перед тем как продолжать (не полагаться на слова без верификации, но и не блокировать бриф, если fixVersion всё ещё не поправлен, а пользователь настаивает включать — его решение приоритетнее технического поля).
4. **Каждый переходящий пункт из предыдущего SR обсуждать в брифе по одному** (как в SELFCHECK) — не молчаливо копировать формулировку из старого плана или из Jira KR текстом. Частый паттерн: годовая/квартальная Jira-цель шире, чем то, что реально нужно сделать за один месяц отчётного периода — явно разделять "рамку на квартал" и "конкретный результат к концу именно этого месяца". Пример из сессии: KR "проверить фреймворк ещё на 3 ролях" — квартальная рамка; конкретно на месяц пользователь сузил до 2 named-ролей (HR, РП АИД).
5. **Ссылки на Jira давать всегда**, когда речь идёт о конкретной задаче/KR/SR в вопросах брифа — пользователь прямо просил "если ссылаешься на Jira — давай ссылки, чтобы понять о чём речь". Не описывать задачу только словами без гиперссылки на ключ.
6. **Пункты, которые Jira формально не включает в исходный список пользователя, но которые логически завершают открытый вопрос предыдущего периода** (напр. AI-ready роль HR из предыдущего SR не была в исходном списке "5 моих задач Q3", но напрямую продолжает открытый пункт июня) — включать в бриф отдельным вопросом, не молчать о них только потому что явно не упомянуты в новом списке.
7. По завершении брифа по всем пунктам — переходить к оформлению как обычно (можно сразу в формате, готовом для 44401-44403, без отдельного этапа draft/check — тот двухшаговый draft→check применим к ИТОГАМ (44404-44406), а не к плану).

### Формат Блока 2 (критерии, 44402) в режиме PLAN

Каждый пункт Блока 2 оформляется зеркально Блоку 1: **заголовок пункта — дословно тот же текст**, что в соответствующем пункте Блока 1 (не сокращать, не перефразировать — чтобы план и критерии визуально сопоставлялись один в один). Сами критерии — **буллиты в столбик** (`- критерий`), а не одна строка через `;`/`,` — даже если критериев всего один-два. Итоговый файл плана сохраняется по тому же пути и имени, что raw-файл в CHECK/SELFCHECK: `WorkVault/Projects/sr-tool/<ФИО>/SR-{key}_{месяц}_{год}.md`, с блоками 1-3 (без отдельного суффикса `_draft`/`_plan` — это черновик плана целиком, а не часть большего файла).

### Заголовки пунктов — полное summary из Jira, одинаково во всех трёх блоках

Заголовок каждого пункта (в Блоке 1, 2 и 3 одинаково) — **дословное полное `summary` задачи из Jira**, не сокращённый OKR-код (`K1.Q3.О1...` без остального текста — недостаточно, читателю плана нужно видеть, о чём речь, не заглядывая в Jira). Если у пункта две связанные задачи (Objective + её KR, напр. `OKRS-3121`/`OKRS-3122`), брать summary той, что ближе описывает конкретный измеримый результат (обычно KR, а не родительская Objective) — но при сомнении уточнить у пользователя, чьё название использовать. Получить summary можно одним batch-запросом `POST /search` с `jql=key in (...)`, вместе со сбором остальных данных на шаге 2 флоу PLAN — не отдельным вызовом.

### Заливка плана нового периода в Jira

После того как бриф по всем пунктам завершён и MD-файл плана согласован построчно (аналогично финализации SELFCHECK, но без промежуточного draft/check — план заливается сразу после согласования):

1. Собрать текст каждого блока из согласованного MD (Блок 1 → 44401, Блок 2 → 44402, Блок 3 → 44403), конвертировать `\n` → `\r\n`.
2. **Определить актуальную transition через `GET /issue/{key}/transitions`** — для нового периода (SR ещё не заполнялся) это обычно `61` "Отредактировать SR", но сверять всегда, не считать номер универсальным по аналогии с прошлым SR.
3. `POST /issue/{key}/transitions` с полями 44401-44403 в `fields` — **не включать 44404-44406** (итоги), даже если они технически доступны в том же transition, план и итоги — разные стадии одного SR, не заливаются вместе.
4. **Финальная верификация** — `GET` по всем трём полям, сверить текст, убедиться что статус SR изменился на ожидаемый (обычно "Заполнение сотрудником").

### Пункты плана без отдельной задачи в Jira

Не каждый пункт плана обязан иметь свою Jira-задачу — например, обучающий курс/сертификация без учёта в Jira. В этом случае: Блок 1/2 оформляются как обычно (заголовок пункта — свободная формулировка темы, не OKR-код), а в Блоке 3 всё равно указывается **существующий OKR-ключ**, на который пункт влияет по смыслу (напр. курс по AI-инструменту разработки влияет на тот же ключ, что и соседний пункт про AI-агентов), с пометкой `(без отдельной задачи в Jira)`. Не оставлять Блок 3 пустым для такого пункта — он должен указывать на реальный OKR, даже без 1:1 связи с отдельной задачей.

### Сравнительная таблица критериев по нескольким исполнителям

Частый последующий запрос после согласования плана: собрать критерии приёмки (Блок 2) в таблицу, сравнивая, что должен сделать сам пользователь и что — другой человек (напр. подчинённый) по тем же/смежным пунктам.

Формат: `№ | Задача (полное summary/тема пункта) | Критерии <Имя 1> | Критерии <Имя 2> | ...` — критерии внутри ячейки как буллиты, не строка через запятую. Номер пункта (`№`) — тот же, что в исходном плане (не сквозная перенумерация).

- Не заполнять чужую колонку по умолчанию (домыслом) — оставлять пустой, пока пользователь явно не скажет, какие пункты и какие критерии перенести туда.
- Когда пользователь просит "перенеси такие же критерии как мои по задачам N, M, K" — переносить **дословно** те же формулировки без адаптации под роль другого человека, даже если по смыслу это кажется странным (напр. управленческая задача формально приписывается подчинённому) — это осознанное решение пользователя, не ошибка агента, спросить один раз при первом расхождении, дальше не переспрашивать по каждому такому переносу.
- Таблица выводится прямо в чат (не обязательно сохранять как отдельный MD-файл), если пользователь не просит сохранить её в WorkVault.

### ⚠️ Питфол: статус SR может измениться в Jira между этапами сессии — пере-проверять transitions перед КАЖДОЙ заливкой

Пользователь может вручную сменить статус SR через интерфейс Jira в любой момент сессии (напр. случайно/намеренно перевёл в "Согласование руководителем"), независимо от того, что было проверено в начале работы. Признак: `PUT`/`POST /transitions` с ранее рабочим transition id внезапно возвращает `400 "Field cannot be set. It is not on the appropriate screen"` или сама transition отсутствует в списке. **Не считать однократную проверку `GET /transitions` в начале сессии достаточной на весь диалог** — если между составлением плана и заливкой прошло несколько реплик пользователя, повторить `GET /transitions` непосредственно перед `POST`, а не переиспользовать id/статус из более раннего запроса. Если transition, дающая доступ к нужным полям, отсутствует — сообщить пользователю прямо (какой сейчас статус, что доступной transition для нужных полей нет) и подождать, пока он не переведёт статус вручную обратно; затем повторно проверить и только тогда заливать.

### ⚠️ Питфол: `patch` может повредить файл с повторяющейся по-пунктовой структурой

При точечной правке одного пункта в MD-файле, где несколько блоков имеют похожую структуру (`N. Заголовок` → списки критериев по каждому пункту), `patch` с `old_string`/`new_string` рискует зацепить не ту часть текста или продублировать контент при неудачном совпадении — особенно если `old_string` не включает достаточно уникального контекста вокруг правки. Прецедент: правка последнего пункта Блока 2 привела к потере заголовка соседнего пункта и дублированию критериев. **Признак, что патч пошёл не так** — сразу после патча вызвать `read_file` на весь файл и визуально сверить структуру (число пунктов, отсутствие дублей, наличие всех заголовков), не полагаться только на diff в ответе `patch`. Если структура похожа на цепочку "заголовок → буллиты → заголовок → буллиты" и правка не тривиальна (не просто одна строка) — безопаснее переписать файл целиком через `write_file`, чем чинить точечным `patch`.

## Флоу CHECK (проверка ежемесячного review — новый, эта сессия)

**Цель:** сравнить план (44401-44403) с фактом (44404-44406) конкретного SR, оценить выполнение по каждому независимому пункту плана и объективность объяснений по недостижению.

### Файлы и пути
```
WorkVault/Projects/sr-tool/<ФИО исполнителя>/
├── SR-{key}_{месяц}_{год}.md        # сырые поля 1-6, как есть в Jira
└── SR-{key}_{месяц}_{год}_check.md  # таблица сравнения план/факт
```
ФИО — из summary задачи (`SR - Криворотов Кирилл (Июнь - 2026)` → папка `Криворотов Кирилл`). После записи — `rclone sync ~/WorkVault owncloud:WorkVault`.

### Формат raw-файла
Разбить 44401 на пронумерованные пункты (план), сопоставить с 44402 (критерии) и 44403 (OKR-ключи) — заголовки 1-3. Затем 44404-44406 — заголовки 4-6, с той же нумерацией пунктов (пункт N в плане = пункт N в факте).

### Формат check-файла: таблица сравнения
Одна строка таблицы = один независимый пункт плана (не всё SR целиком). Колонки:

| № | Что было запланировано | Критерии (список) и статус done/not done | Доп. успехи, не заявленные в плане | Объективность объяснений по недостижению |

**Правила заполнения:**
- Статус done/not done выставлять **по каждому критерию внутри пункта отдельно**, не по пункту целиком — пункт может быть done по 3 из 4 критериев.
- В колонку "доп. успехи" — только то, что реально есть в факте (44404) и отсутствует в плане (44401/44402). Не выдумывать.
- Объективность объяснения (44405) оценивать по критерию **причинно-следственная связь**: указана ли конкретная причина (кто/что/почему), напрямую объясняющая именно недостигнутый критерий — а не общая фраза типа "изменилась концепция задачи" без деталей. Общая фраза без деталей = низкая объективность, отметить явно.
- Для полностью done пунктов колонка объективности = "план не нарушал — n/a".
- В конце — краткий итог: сколько пунктов done/not done, есть ли системный паттерн в неточных объяснениях (напр. один и тот же общий оборот повторяется у нескольких невыполненных пунктов).

## Флоу SELFCHECK (подготовка своих итогов SR в режиме брифа)

**Отличие от CHECK:** CHECK анализирует уже заполненный чужой SR (поля 44404-44406 не пустые). SELFCHECK готовит черновик итогов для **своего** SR, у которого 44404-44406 ещё пусты — цель не оценить, а помочь сформулировать, что туда внести.

**С SRTool v2.0 этот флоу выполняется инструментом, а не вручную построчно:** `python3 -m srtool report SR-XXXXX` из `~/USERTOOLS/SRTool/` реализует шаги 1-7 ниже автоматически (чтение плана, сбор закрытых задач из минуток, авто-маппинг, поштучный бриф, автосохранение `_draft.md`, заливка через transition `271`). Ручной алгоритм ниже остаётся источником истины для того, **что** должно происходить на каждом шаге (используется для отладки/расхождений с инструментом или если инструмент недоступен) — сначала пробовать `srtool report`, к ручному флоу переходить только при сбое инструмента.

### Порядок действий
1. Прочитать план своего SR (44401-44403) — как в режиме CHECK.
2. **Найти пересечения по OKR-ключам** с SR подчинённых/коллег за тот же период. Список подчинённых — через `contacts.enc`, не по памяти/предположению: `store.find_subordinates(login)` (см. `tutu-jira-okr` → «Оргструктура»). `key in (SR-A, SR-B,...)` не подходит для поиска пересечений — сверять построчно по значению 44403, ключ OKR совпадает → значит работа могла вестись совместно. Если у коллеги по тому же OKR уже есть заполненные 44404-44406 — использовать как источник фактов, которые сам мог не упомянуть (совместная работа, вклад команды).
3. **Подтянуть чекины по своим OKR/KR за период** (см. `tutu-jira-okr` — карта customfield, JQL-паттерны). Это независимый от SR источник фактов: `% выполнения`, `Что было сделано`, `Уверенность`, `Риск`.
4. Сохранить raw-файл `WorkVault/Projects/sr-tool/<ФИО>/SR-{key}_{месяц}_{год}.md` — план + карту пересечений с чекинами OKR (те же поля, что в CHECK, плюс отдельная таблица чекинов OKR).
5. Сохранить `SR-{key}_{месяц}_{год}_selfcheck.md` (не `_check.md` — суффикс `_selfcheck` зарезервирован именно для своего SR, чтобы визуально не путать с проверкой чужого) — таблица по каждому пункту плана: план / данные из Jira-чекина или от коллег / предварительный статус (done/not done/частично/нет данных).
6. **Явно пометить пункты без данных** — если по OKR/KR нет чекина и нет пересечения с чужим SR, не придумывать факт, а вынести отдельным списком "открытые вопросы" и спросить у пользователя, прежде чем формулировать итог.
7. Только после ответов на открытые вопросы по фактам — три последовательных прохода
   (не смешивать блоки в одном вопросе):
   7.1. Блок 4 (44404) — по каждой цели: Плановый / Дополнительный результат.
   7.2. Блок 5 (44405) — по каждой цели, включая выполненные: Проблема / Решение
        или «Проблем не было»; затем одна итоговая сводка по развитию.
   7.3. Блок 6 (44406) — пробелы в знаниях/навыках по пунктам (уроки, не план на следующий месяц).
   Формулировки предлагает пользователь или подтверждает правкой; агент не фильтрует цели
   по статусу и не оценивает «объективность» — это флоу CHECK чужих SR.

### Бриф Блока 5 (44405) — отдельный проход по всем целям

После того как Блок 4 согласован по всем N целям — не предлагать Блок 5 списком
«по ключевым/невыполненным». Идти по каждой цели, включая успешно выполненные.

Вопрос (один пункт = одно сообщение, открытый, без вариантов):

«П.N. <заголовок цели одной строкой>. Каких знаний или навыков не хватило
или какая была сложность при достижении этой цели, и как её решили?»

Правила:
- НИКОГДА не фильтровать опрос по статусу (выполнено / частично / не выполнено).
  Выполненная цель тоже могла иметь проблемы; они решены — это показатель качества.
- Не пересказывать «Проблему» как сам статус. «Не выполнено» — не проблема.
  Проблема = конкретная причина/сложность, напрямую объясняющая затруднение
  (кто / что / почему), а не повтор строки из Блока 4.
- На одну цель может быть несколько пар Проблема/Решение (спрашивать
  «ещё была сложность по этой цели?» только если пользователь сам намекнул
  на вторую; иначе не размножать).
- Ответ «нет» / «проблем не было» → в черновик писать ровно «Проблем не было».
- Если решение названо — «Решение: …». Если не названо — строку «Решение:» не выводить
  (не писать «решения не было» / «нет решения»).
- После последней цели — один вопрос на итог Блока 5:
  «Какое совокупное предложение по развитию, корпоративной помощи или иным
  действиям следует из этих пунктов?»
  Ответ → абзац «Итог: …» в конце 44405.

Не слать промежуточный отчёт «Блок 5 пока такой-то» между пунктами.
Не перепечатывать уже согласованный Блок 4.

### Питфол: % чекина может противоречить тексту "Что было сделано"
Встречается ситуация, когда `% выполнения` (43782) и `Уверенность` (43706) показывают высокое значение ("100%", "On Track"), а текст в "Что было сделано" явно говорит о незавершённости ("осталось провести 8 из 10 появлений"). Это противоречие — не ошибка выгрузки, не сглаживать автоматически в одну сторону. Вынести как открытый вопрос пользователю: что было целью на сам отчётный период (не на год), и как это отражается в итоге SR.

### Питфол: дополняющий факт от пользователя может относиться к ДРУГОМУ пункту плана
В брифе "по одному пункту" пользователь иногда добавляет детали без повторного указания, к какому именно пункту они относятся ("к п.1 добавлю ещё..."). Нельзя автоматически считать, что новые детали продолжают текущий обсуждаемый пункт — особенно когда несколько пунктов плана тематически похожи (напр. два разных технических интеграционных проекта: "AI-аналитик/оркестратор" и "Trisigma" — оба про SDK/агентов/интеграции). "SDK", "АА-тест" не встречались в плане п.1, но естественны для интеграционного проекта). При малейшем сомнении — переспросить одной строкой, к какому пункту относится факт, до того как включать его в черновик формулировки.

### Финализация SELFCHECK: draft → check

После того как брифинг по всем пунктам завершён (пользователь подтвердил формулировки построчно), SELFCHECK производит ещё 2 файла в той же папке:

1. **`SR-{key}_{месяц}_{год}_draft.md`** — финальный текст, готовый к ручной вставке в Jira. Три раздела (Блок 4/5/6 = 44404/44405/44406), каждый пункт плана — отдельный подзаголовок `### N. <тема>`.
   - **Блок 4 (44404)** — на каждый пункт: `**Плановый результат:**` (список формулировок из плана 44401/44402, каждая с текстовой отметкой — выполнено / не выполнено / в процессе, БЕЗ иконок ✅❌⚠️ — поле переносится в Jira как обычный текст) + `**Дополнительный результат:**` (то, чего не было в плане). Если по пункту нет дополнительного результата — **не выводить заголовок "Дополнительный результат" вообще**, не писать `—`/прочерк.
   - **Блок 5 (44405)** — ровно N пунктов, та же нумерация, что в плане.
     Заголовок пункта — тот же, что в Блоке 1 (можно короткий, но номер обязателен).
     На каждый пункт:
       `Проблема: <текст>`
       `Решение: <текст>`   ← строку не выводить, если решения нет
     либо одна строка `Проблем не было` (без пары).
     Несколько пар на пункт — допустимо, каждая пара с новой строки.
     После пункта N — абзац `Итог: <совокупное предложение по развитию /
     корпоративной помощи / иным действиям>`.
     Не фильтровать пункты: выполненные без проблем тоже входят в поле.
     Не использовать заголовок «Сложность:» — только «Проблема:».
     Правило «объективность объяснения» сюда не применять (это CHECK чужих SR).
   - **Блок 6 (44406)** — развитие/пробелы по тем же N пунктам: какой навык/знание
     не хватило и что с этим делать (урок), не дублировать Блок 4 и не писать
     сюда план на следующий месяц. Пункты без пробела — `-`. Не оставлять блок
     пустым целиком, если в Блоке 5 уже есть материал для урока — вынести урок сюда,
     а в Блоке 5 оставить факт проблемы/решения.
   - Не переизобретать формулировки на этом шаге — брать ровно то, что согласовано в брифе, только раскладывать по новой структуре.
2. **`SR-{key}_{месяц}_{год}_check.md`** — самопроверка `_draft.md` перед заливкой. Критерии:
   - Блок 4: у каждой цели есть Плановый результат со статусами; «Дополнительный результат» только если непустой;
   - Блок 5: ровно N пунктов; у каждого пара или «Проблем не было»; есть абзац «Итог:»;
   - Блок 6: не пустой шаблон «что дальше», а пробелы/уроки (или `-`).

Порядок: selfcheck.md (гэп-анализ, открытые вопросы) → бриф построчно → draft.md (финальный текст) → check.md (верификация draft) → заливка в Jira (см. ниже) — отдельный явный шаг, не автоматическая.

### Заливка согласованных итогов в Jira

Выполняется **только по явной команде** (напр. "переноси итоги в SR"), после того как `_draft.md` полностью согласован построчно.

1. **Заливать только те поля, которые явно указаны пользователем.** Если запрошено "перенеси итоги, только отчётные пункты — не плановые", заливать **исключительно** 44404-44406 (Блок 4/5/6 из draft.md), не включать в payload 44401-44403 (план), даже если они тоже есть в draft.md и transition технически позволяет их перезаписать. Плановые поля к этому моменту уже согласованы и залиты ранее (Режим FILL) — повторная заливка риска не несёт содержательно, но не запрошена явно, значит не делается.
2. Собрать текст каждого поля из соответствующего раздела `_draft.md` (Блок 4 → 44404, Блок 5 → 44405, Блок 6 → 44406), сохранив структуру (`### N. <тема>`, `**Плановый результат:**`/`**Дополнительный результат:**`, `**Проблема:**`/`**Решение:**`) как обычный текст — Jira рендерит вложенные заголовки/буллеты без Markdown-разметки, но структура остаётся читаемой через переносы строк.
3. Конвертировать `\n` → `\r\n` перед отправкой (см. формат текста полей в FILL).
4. **Определить актуальную transition через `GET /issue/{key}/transitions`, не полагаться на `61`** — см. таблицу transitions выше (`271` "Заполнить итоги" для итогов, а не `61`).
5. `POST /issue/{key}/transitions` с найденным id и полями 44404-44406 в `fields`.
6. **Финальная верификация** — `GET` по каждому из залитых полей, сверить первые ~300 символов с ожидаемым текстом, убедиться что статус SR не изменился сверх ожидаемого.
7. Напомнить пользователю перевести статус в "Согласование с руководителем" вручную — Сирень этого не делает.
