# Модуль C. Extractors

## Назначение
Из пакета одной встречи извлечь сигналы с тегами scope (project/person/sync) — один MeetingPackage → один MeetingSignals. На вход — summary целиком + релевантные куски transcript. Выход — типизированные объекты для модулей D/E/H и G.Срез.

## Что уже зафиксировано
- Источники сигналов в FF summary разобраны: `Bullet points`, `Notes (с таймкодами)`, `Action items`, `Blockers`, `Questions`, `Keywords` (project-entity v0.1, Блок 0).
- Маркеры решений: «решено», «договорились», «согласовали» + жирный текст в начале буллета.
- Action items уже структурированы FF: «человек → задача → таймкод» — берём как есть, нормализуем по AnywhereContacts.
- Артефакты на выходе: `decisions.md` (включая блокеры с префиксом `[blocker]`), `action_items.md`, `timeline.md`, `risks.md` (для проектов/инициатив — PD-031, см. TZ_D); `open_questions.md` — в перспективе. <!-- изменено 2026-06-29: risks.md в scope -->

## Карточка модуля

🎯 **Функция:** Из `MeetingPackage` извлекает структурированные сигналы — решения, задачи, риски, блокеры, открытые вопросы.
⬅️ **Вход:** `MeetingPackage` от модуля A
➡️ **Выход:** `MeetingSignals` → `F.fan_out` → {D, E, H}; для G.Срез — вызов F.trigger_snapshot после fan_out
🔗 **Зависимости:** A (данные), B (project_slug), AnywhereContacts (AC — резолв имён, единственный writable store алиасов контактов), H (через F.fan_out для scope=sync). G.Срез — потребитель не C, а F.trigger_snapshot.

## Архитектура (единый проход, без Opus) <!-- изменено 2026-06-29: PD-028/030/036, Фаза A -->

> **Изменение брифа 29.06 (PD-028, PD-036):** двухшаговая архитектура (Haiku-разметка «Шаг 1» → Opus-агрегация «Шаг 2») **отменена**. Opus убран из пайплайна полностью (bootstrap + инкремент). Весь прогон выполняет **Haiku** единым поштучным проходом по встречам с накоплением инкремента. Разделения на «Шаг 1 / Шаг 2» больше нет.

### Алгоритм bootstrap (PD-030, уточнён C4/PD-037)

```
-1. Встречи FF размечены по проектам/сущностям (classification_memory) — роутинг готов (B).
 0. Идём поштучно по каждому проекту/сущности.
 1. Развилка по типу сущности:
    1.1 Проект / инициатива → если есть бриф/устав (Confluence) — формируем
        начальный набор decisions + action_items + risks из него («встреча №0»).
        Если устава нет → сразу шаг 2.
    1.2 Мультисинк / 1-1 / АДМ → сразу шаг 2.
 2. От самой ранней встречи к актуальной (Haiku):
    - Haiku делает СРЕЗ (G) из встречи;
    - из среза пополняет decisions + action_items + risks, сравнивая с
      накопленным инкрементом:
        • актуальные → оставляем,
        • неактуальные → закрываем (зачёркивание),
        • изменившиеся (срок / ответственный / суть) → дополняем;
    - на каждом шаге Haiku получает накопленный инкремент (decisions/action_items/
      risks к этому моменту) как контекст — компенсирует отсутствие Opus-агрегации.
 3. Проект / инициатива и есть golden ref → сравнение через Sonnet:
    Sonnet ПРЕДЛАГАЕТ задачи к закрытию → PM подтверждает через PM Notes (PD-041).
    Авто-закрытие без PM не допускается. Если golden ref нет — шаг пропускается.
 4. Мультисинк / синк-аид → golden ref синка, сравнение через Sonnet.
```

### Алгоритм инкремента (каждый новый MoveFromFF)

```
Тот же шаг 2.
- Заметки РП (PM Notes) в срезе G имеют ГЛАВЕНСТВУЮЩИЙ приоритет для каждого
  блока (decisions/action_items/risks) — PD-037/044, поток G→D.
- Встречи из MoveFromFF НЕ пересинкиваются и НЕ переобрабатываются (PD-037);
  переобработка одной встречи — только в ручном режиме с явными вводными PM.
```

**Модель по фазам (PD-028, OQ-002):**
- **Bootstrap** — Haiku (весь проход).
- **Инкремент в проде** — Sonnet; переключение вручную после выхода в прод (напоминалка 01.09).
- **Opus** — deprecated, в пайплайне не используется.

⚠️ **Риск для приёмки:** Haiku на длинной истории без агрегирующего Opus-контекста может терять длинные связи («решение X отменено через 3 встречи»). Митигация — передача накопленного инкремента контекстом на каждом шаге (шаг 2). Проверяется на golden compare (Фаза C, IQ-C01/C02).

- **В8 — Блокеры (PD-032):** <!-- изменено 2026-06-29 --> сигнал `type=blocker, scope=project` пишется в `decisions.md` (не в action_items.md, не в risks.md). Формат строки в D: `- [blocker] текст · статус · срок <!-- key: ... -->`. Машиночитаемый префикс `[blocker]`; дедуп-ключ включает `type=blocker`; закрытие = зачёркивание.
- **В9 — Кросс-проектные приоритизации (PD-045, упраздняет PD-040/PD-018):** <!-- изменено 2026-06-30 --> отдельной сущности «portfolio» нет. Кросс-проектное ранжирование/приоритизация (типично из 1-1: «проект X важнее Y/Z») записывается как обычное `decision` в **сущность-источник встречи**: 1-1 → E.Люди (`agreements`/срез контакта), мультисинк → H.Синки, проектная встреча → D.Проект. Дальше изменяется по стандартным правилам резолва конфликтов (хронология, зачёркивание). Никаких `scope=portfolio`, `cross_project_ranking`, `adm/ai/portfolio.md` — упразднено.

### Поля `source_sync` vs `sync_slug` (m6)

В `MeetingPackage` от B: поле называется **`sync_slug`** — slug синка-площадки, к которой относится встреча (для route=multisync).

В каждом сигнале `MeetingSignals`: поле называется **`source_sync`** — slug синка-источника. Семантически это **то же самое значение**, что `MeetingPackage.sync_slug` (для multisync-встречи), но имя поля в сигнале другое, потому что:
- для сигнала со `scope=sync` есть собственный `sync_slug` (slug целевого синка как сущности),
- `source_sync` всегда обозначает «откуда пришёл сигнал» — источник, а не цель.

Для project-встречи (route=project / 1on1) `source_sync = null`. Заполняет код-обёртка C, не LLM.

## C.pre_classify() — расширенное описание (R10)

**Назначение:** LLM-классификация встречи через Haiku при недостаточной уверенности детерминированных правил B.

**Места вызова:**
1. **Инкрементальный пайплайн** — при `low confidence` от B.determine_route() (существующее поведение, M3/ВП3)
2. **Bootstrap Шаг 7** — для всех `route=unclear` встреч с доступным summary (новое, R10)

**Сигнатура:**
```python
def pre_classify(
    summary_text: str,
    title: str,
    known_projects: list[str],
    context: str = "bootstrap"  # "bootstrap" | "increment"
) -> PreClassifyResult:
    ...
```

**Параметры:**
- `summary_text` — текст summary (первые ~2000 символов для Bootstrap)
- `title` — заголовок встречи
- `known_projects` — список slug-ов из classification_memory.json
- `context` — режим вызова для выбора промпта

**Возвращает:**
```python
@dataclass
class PreClassifyResult:
    route: str  # "project" | "1on1" | "multisync" | "unclear"
    project_slug: str | None  # slug проекта если определён
    confidence: float  # 0.0..1.0
    reasoning: str  # объяснение LLM
```

<!-- изменено 2026-06-22: MINOR-C fix -->
**Маппинг confidence для совместимости с остальным пайплайном:** `pre_classify` возвращает `confidence: float`. Для логирования и интеграции с остальной системой (где используется enum `high|medium|low`) применяется маппинг: ≥0.8 → high, 0.6–0.79 → medium, <0.6 → low. В пайплайне для логов используется строковый alias, для принятия решений — численное значение (порог 0.7 для R10).

**Промпт для Bootstrap-режима (context="bootstrap"):**
```
SYSTEM:
Определи к какому проекту относится встреча. Используй ТОЛЬКО предоставленный список проектов.
Если не уверен — верни route="unclear".

USER:
Встреча: {title}
Текст summary (первые 2000 символов):
---
{summary_text[:2000]}
---

Список проектов: {known_projects}

Верни JSON:
{
  "route": "project" | "1on1" | "multisync" | "unclear",
  "project_slug": "<slug>" | null,
  "confidence": 0.0..1.0,
  "reasoning": "объяснение"
}
```

**Порог принятия (R10):** `confidence ≥ 0.7` — принять route + source="llm_fallback". При `confidence < 0.7` — оставить unclear, сохранить `llm_hint` для PM.
