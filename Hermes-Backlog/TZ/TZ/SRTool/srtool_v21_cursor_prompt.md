## ЗАДАЧА

### 1. Проблема
Таблица ручных шагов сессии августа 2026 (поиск SR, чтение блоков, OKR-чекины, новые KR, связи, заливка, верификация) → ~15 запросов, ~30K токенов контекста.

### 2. Новый режим `srtool plan`
CLI-команда автоматизирующая планирование начала периода (блоки 1-3):
- Автопоиск предыдущего SR (JQL: issuetype=SR, assignee=user, status!="Оценка установлена", ORDER BY created DESC)
- Извлечение каркаса KR из customfield_44403 (Блок 3 предыдущего SR), парсинг OKR-ключей в порядке
- Батч-запрос OKR-данных (один GET /search с key IN (...) вместо N отдельных GET)
- Авторасчёт целевого % (>=50% от текущего к 100%, настраиваемый --target-pct)
- Поиск новых KR (JQL: issuetype in OKR/Sub-task, assignee=user, fixVersion=Q3 2026, key NOT IN каркас)
- Генерация _plan_draft.md с каркасом и предложенными формулировками
- Поштучный бриф по каждому пункту
- Заливка через POST transition 61

### 3. Кэширование OKR-данных (правило №0)
- Перед запросом в Jira проверить WorkVault/Projects/okr-tool/<KEY>.md
- Если файл существует и обновлён в текущем квартале — использовать локально
- Иначе — GET из Jira + сохранение в MD
- Экономия: 7-9 GET → 0-2

### 4. Батчинг API-запросов
- Вместо N GET /issue/KEY → один GET /search?jql=key IN (A,B,C...)
- До 100 ключей в IN-выражении, для SR обычно 7-12 KR
- Экономия: N-1 HTTP-запросов

### 5. Интеграция TaskRefresh
- После заливки плана — предложение создать follow-up задачи в Confluence-минутках
- SRTool знает project_tag из каркаса → находит страницу минуток → вызывает TaskRefresh

### 6. Расчёт экономии токенов
- Jira API: ~15 → 3-4 запросов (75%)
- Токены контекста: ~30K → ~6K (~24K экономии)
- Кэширование OKR: ~14K экономии
- Ручной труд: ~15 мин → ~3 мин
- Итого за сессию: ~38K токенов, за год (12 сессий): ~$2-4 + 2.5 часа
