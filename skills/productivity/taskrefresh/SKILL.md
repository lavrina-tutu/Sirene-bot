# TaskRefresh — задачи Саши из Confluence

Механический CLI-цикл: `read`/`mine` → показ → Саша называет номер+действие → `apply` (preview)
→ `confirm` (пишет). Минимум reasoning нужен — подходит для Haiku. ТЗ:
`WorkVault/Hermes-Backlog/TZ/TaskRefresh/TaskRefresh_TZ.md`.

## Дефолт вывода при «поработаем с задачами»

Всегда делать `./tr mine --links` и показывать задачи в двух группах:
1. **⚠️ Просроченные** — со срочным акцентом
2. **На этой неделе** — остальные с дедлайном

**Текст задачи выводить оригинальный** — без сокращений и перефразирований, ровно как хранится в Confluence.

**Источник = все задачи из `https://dom.tutu.ru/display/~tkachenkoav/OpenTasks`** — это Confluence `tasks-report-macro` с `spaces=DPAN,~tkachenkoav`, `assignees=tkachenkoav`, `labels=_aid`. TR сканирует по тому же критерию (`CQL_LABEL="_aid"`) → покрытие полное, без пропусков.

Саша сам называет что делать с каждой — менять дедлайн, текст, закрывать. После этого батч apply→confirm **по одному на каждое изменение** (не накапливать несколько apply перед одним confirm — confirm применяет только последнее apply в очереди).

## Дефолт (без явного запроса иного)

Только `incomplete` + только с указанным дедлайном (без дедлайна — не показывать).
Группировка по `[Проект]`, просроченные — маркировать ⚠️.

## Команда (экономия токенов — используй `tr`, не длинный venv-путь)

```bash
cd ~/USERTOOLS/TaskRefresh
./tr mine                          # дефолтный срез "мои задачи" одной командой
./tr mine --links                  # + Confluence-ссылка на каждую задачу
./tr mine --any-deadline           # включая задачи без дедлайна
./tr read --assignee X --project Y --deadline overdue --status any   # произвольный фильтр
./tr apply "#N дедлайн ДД.ММ"      # preview, ещё НЕ пишет
./tr apply "#N закрыть"            # → status=complete
./tr apply "#N открыть"            # → status=incomplete
./tr apply "#N ссылка <URL> [подпись]"  # добавляет настоящую <a href> гиперссылку (не текст URL!), дефолт-подпись "(ссылка)"
./tr confirm                       # пишет + встроенная верификация (перечитывает страницу)
./tr show                          # перепечатать последнюю сессию без нового скана
```

`./tr` — bash-wrapper, сам находит `ProtocolFromSummary/.venv` (TaskRefresh не имеет своего venv).
Если `./tr` недоступен (отсутствует/не exec) — fallback:
`~/USERTOOLS/ProtocolFromSummary/.venv/bin/python3 -m taskrefresh <args>`.

## Что уже решено кодом (не переоткрывать, не диагностировать заново)

- **Нумерация #N** в брифе и в `apply`/`confirm` гарантированно совпадает (после `read`/`mine`) —
  `order_tasks_for_display()` считает порядок один раз, сохраняется в сессию. Если между показом
  брифа и `apply` был долгий перерыв или правился код — перезапустить `read`/`mine` перед `apply`.
- **project_tag** — сначала текстовый тег в начале задачи ("Trisigma. ...", "АДМ. ..."), page_id
  страницы — fallback только для задач без тега. Персональные 1-1-страницы (Кирилл 1-1, Аралов 1-1
  и т.д.) — общий контейнер для разных проектов, не единый проект сами по себе.
- **`<time>` (дедлайн) и видимый текст задачи** ищутся на любой глубине вложенности html
  (не только прямой потомок task-body) — не создают дубль на задачах с ручной html-разметкой
  из веб-редактора Confluence (`rebuild_task_block`/`_replace_visible_text` оба используют
  рекурсивный обход, см. §14/§19 ТЗ).
- **Верификация после `confirm`** встроена в пайплайн (`verify=True` по умолчанию) — перечитывает
  изменённые страницы сама, покрывает все три поля (`deadline`/`status`/`text`), печатает
  "Верификация после записи: ок" или явную проблему. **Не нужен отдельный curl/read_file
  проход** — если строка "...ок" есть в выводе `confirm`, результат подтверждён.
- **`--links`** на `read`/`mine` дописывает `https://dom.tutu.ru/pages/viewpage.action?pageId=<id>`
  в конец каждой строки брифа — если Саша попросит "сверюсь с Confluence", сразу используй `--links`
  вместо построчного curl после факта.

## Правило «перенести на N вперёд» (зафиксировано Сашей 13.07.2026)

Для ПРОСРОЧЕННОЙ задачи команда «перенеси на N дней/недель вперёд» считается ОТ ТЕКУЩЕЙ
ДАТЫ, а не от старого (просроченного) дедлайна задачи. Пример: сегодня 13.07, дедлайн
задачи 22.06 (просрочен), «перенеси на 2 недели вперёд» → новый дедлайн 27.07 (13.07+14д),
НЕ 06.07 (22.06+14д). Если дедлайн ещё не просрочен — можно уточнить у Саши базу, если
неочевидно из контекста.

## ⚠️ Сохранение гиперссылок при модификации задачи

Если в теле задачи есть `<a href="...">текст</a>` — это кликабельная HTML-ссылка, которую **нельзя потерять при правке текста или дедлайна**.

**Как проверить наличие ссылки перед правкой:** прочитать сырой XML задачи через API (`/rest/api/content/<pageId>?expand=body.storage`) и найти `<a href=` в нужном `<ac:task-body>`. `./tr mine` в бриф-выводе ссылку не показывает — только ссылку на страницу.

**Когда ссылка есть — не использовать `./tr apply "#N текст: ..."`.** `apply text` заменяет весь видимый текст задачи plain-текстом, что уничтожает HTML-разметку ссылки.

**Правильный путь — прямая правка через API:**
1. GET страницы (`?expand=body.storage,version`)
2. Найти `<a href="URL">старый текст ссылки</a>` в нужном task-body
3. Заменить только текст внутри `<a>...</a>`, оставив `href` нетронутым
4. Если меняется дедлайн — заменить `datetime="YYYY-MM-DD"` только в этом же task-body
5. PUT с `version + 1`
6. Верифицировать: новый текст ссылки есть, старый ушёл, `href` и `datetime` корректны

**Дедлайн без ссылки** — можно через `./tr apply "#N дедлайн ДД.ММ"` без риска.

## Добавление ссылки в задачу — ВСЕГДА настоящая гиперссылка

Если Саша просит "добавить ссылку" в конец задачи — это ВСЕГДА кликабельная HTML-ссылка
`<a href="URL">(ссылка)</a>` (Confluence storage format), НЕ голый текст URL. Использовать
`apply "#N ссылка <URL>"` (не `apply "#N текст: ..."` с URL внутри строки — тот вставляет
только plain text, будет виден как обычный текст, не кликабельная ссылка). Подпись по
умолчанию "(ссылка)", можно переопределить: `apply "#N ссылка <URL> подробнее"`.

## Контракт команды «Проект — X» (номер задачи + новый/другой проект)

Задача НЕ переносится на другую страницу — только меняется/добавляется `project_tag`
(классификационная метка для группировки в брифе). Механизм: правка
`WorkVault/Tools/TaskRefresh/project_registry.json` — добавить/поправить slug с `tag` (текстовый
префикс задачи). **Побочный эффект, о котором всегда предупреждать Сашу:** реклассификация идёт по

per-task override без этого эффекта — текущий механизм не поддерживает, не изобретать workaround,

## ⚠️ ПИТФОЛЛ: `tr apply текст` уничтожает HTML-гиперссылку в задаче (22.07.2026)

**Симптом:** задача содержит кликабельную ссылку `<a href="...">текст</a>` (созданную вручную в Confluence или через `tr apply ссылка`). Команда `./tr apply "#N текст: \"новый текст\""` перезаписывает весь visible text как plain text — гиперссылка теряется.

**Проверка перед apply:** если `./tr mine` показывает ссылку в тексте задачи или если задача правилась вручную в веб-UI — проверить сырой XML перед изменением текста:
```python
import sys; sys.path.insert(0, '/home/tkachenkoav/USERTOOLS/TaskRefresh')
import taskrefresh.config as c, urllib.request, json
req = urllib.request.Request(
    f"{c.CONFLUENCE_BASE_URL}/rest/api/content/<pageId>?expand=body.storage",
    headers={"Authorization": f"Bearer {c.CONFLUENCE_TOKEN}"}
)
with urllib.request.urlopen(req) as r: data = json.load(r)
# Ищем <a href> вблизи нужного текста задачи
```

**Фикс — прямой Python PUT с сохранением href:**
```python
HREF = "https://..."
old_a = f'<a href="{HREF}">Старый текст ссылки</a>'
new_a = f'<a href="{HREF}">Новый текст ссылки</a>'
new_body = body.replace(old_a, new_a, 1)
# Дедлайн — только в блоке нужной задачи (не глобально!):
idx = new_body.find(HREF)
task_end = new_body.find("</ac:task-body>", idx)
segment = new_body[idx:task_end].replace('datetime="YYYY-MM-DD"', 'datetime="YYYY-MM-DD"', 1)
new_body = new_body[:idx] + segment + new_body[task_end:]
# PUT с version+1, верификация GET после
```
Удалить временные файлы после PUT. Дать ссылку на страницу.

**Когда `tr apply` безопасен для текста:** только plain text без `<a>`, `<strong>` и другой HTML-разметки в task-body.

## Многошаговая правка одной задачи (текст + ссылка + дедлайн одновременно)

Частый запрос Саши — сразу несколько правок над одной и той же задачей (например:
"измени текст + добавь ссылку" или "текст + ссылка + дедлайн на дату"). Каждое поле —
**отдельный `apply`/`confirm` цикл**, и между циклами сессию нужно ОБЯЗАТЕЛЬНО обновлять
(`./tr mine` заново), даже если код инструмента не менялся и перерыва не было:

1. `apply "#N текст: \"...\""` → `confirm`
2. **`./tr mine` заново** (не `show` — нужен реальный пересчёт `text_clean` под новый текст)
3. `apply "#N ссылка <URL>"` → `confirm`
4. Если нужен ещё и дедлайн — **`./tr mine` заново** перед `apply "#N дедлайн ..."`

Причина: `confirm` пишет на Confluence корректно, но **не обновляет текущую in-memory
сессию** сам — следующий `apply` в той же сессии покажет preview со СТАРЫМ текстом задачи
(до предыдущей правки) как `old_value`, хотя реальная запись на Confluence уже содержит
новый текст. Само применение всё равно попадёт в правильный `task_id`/`page_id` (они не
меняются), но preview будет вводить в заблуждение — сверяй его с ожиданием осторожно, и
предпочитай освежить сессию, а не полагаться на `old_value` в устаревшем preview.

## Ручная вставка задачи в task-list Минуток (без `./tr`)

Использовать когда задача заводится вручную — не через инструмент, а прямым curl+python.

**Правило порядка строк: новые даты — ВЫШЕ старых** (таблица Минуток идёт от новых к старым сверху вниз).

1. `curl ... "https://dom.tutu.ru/rest/api/content/<pageId>?expand=body.storage,version" > /tmp/page.json`  
   ⚠️ `json.load(open(...))`, не `json.loads(stdout)` — body содержит `\`-escape, curl stdout ломает парсер.
2. `python3 - << 'PYEOF'` — найти `max task-id` через `re.finditer(r'<ac:task-id>(\d+)</ac:task-id>', body)`, `new_id = max_id + 1`
3. Если добавляем в **существующую дату**: `idx = body.find('YYYY-MM-DD')` → точка вставки `body.find('</ac:task-list>', idx)` — вставить задачу перед ним.
4. Если создаём **новую строку с новой датой** — строить новый `<tr>` по образцу standalone-строки и вставить его **перед** первой строкой с предыдущей (более старой) датой. Новее = выше.
5. PUT с `version.number + 1`, title, `type: page`, representation `storage`.
6. Верифицировать: GET → убедиться что текст задачи есть в body и порядок дат корректен.
7. Удалить `/tmp/page.json`, `/tmp/put.json` сразу (PII).

**Формат новой задачи:**
```xml
<ac:task>
<ac:task-id>N</ac:task-id>
<ac:task-status>incomplete</ac:task-status>
<ac:task-body><ac:link><ri:user ri:userkey="USERKEY" /></ac:link> Текст задачи <time datetime="YYYY-MM-DD" /></ac:task-body>
</ac:task>
```

**Формат standalone-строки (без заголовка встречи):**
```xml
<tr><td><div class="content-wrapper"><p><time datetime="YYYY-MM-DD" /></p></div></td>
<td><div class="content-wrapper"><ac:task-list>
... задачи ...
</ac:task-list></div></td></tr>
```

Userkey резолвить через CQL по ФИО (см. скилл `tutu-confluence-jira`, раздел «Резолв пользователя»).

**Правила что является протоколом встречи, а что — самостоятельной задачей:**
- Протоколы встреч (`<h2>Участники:</h2>`, `<h2>Решения:</h2>`) — только автоматикой или вручную по итогам встречи. Новые задачи туда НЕ добавлять.
- Самостоятельные задачи (followup, контроль, поручения) — отдельная строка с текущей датой выше всех протоколов.

## Ручное удаление строки таблицы минуток (по явной команде Саши)

Парный раздел к «Ручной вставке» выше. Использовать когда Саша явно просит «удали из протоколов» — это не автономное действие инструмента.

**Техника (проверена на живой странице, безопасна при anchor-разметке):**
1. `curl ... "https://dom.tutu.ru/rest/api/content/<pageId>?expand=body.storage,version" > /tmp/page.json` — получить текущий HTML и версию.
2. Найти якорь искомой строки (`ac:macro-id`/текстовый параметр anchor-макроса, либо уникальный текст) через `body.find(marker)`.
3. От найденной позиции — `body.rfind('<tr>', 0, idx)` назад (начало строки) и `body.find('</tr>', idx) + len('</tr>')` вперёд (конец строки). Вырезать точно этот диапазон: `new_body = body[:tr_start] + body[tr_end:]`.
4. **Не строить new_body руками/регекспом на глаз** — печатать вырезаемый фрагмент перед PUT и визуально сверять, что это ровно нужная строка (похожие соседние `<tr>`, особенно пустые технические в конце таблицы, легко перепутать).
5. PUT с `version.number = <старая версия + 1>`, тем же `title`, `type: page`, `body.storage.value = new_body`.
6. Подтвердить: повторный GET — маркер/текст удалённой строки отсутствует, version увеличилась ровно на 1.
7. Удалить `/tmp/page.json`, `/tmp/put.json` сразу (PII).
8. Если строку писал инструмент с `_registry.json` (напр. ProtocolFromSummary) — синхронно пометить запись исключённой (флаг `historical_no_reload: true` / `entity: excluded_personal`), не удалять физически — иначе следующий прогон republish-нет удалённую строку заново.

**Когда применять эту ручную технику vs `remove_row_by_anchor()` инструмента:** только если удаляемая строка НЕ относится к штатному потоку данных инструмента (например разовая личная встреча в fallback-контейнере «Встречи неразобранное»). Для штатных batch-операций — искать и использовать встроенную inverse-функцию, не изобретать ручной curl-патч.

## Питфолл: задача может быть не на той странице, которую показал Саша

Если Саша показывает задачу из какого-то контекста (например, из протокола встречи Trisigma) и просит что-то изменить — **не предполагай, что она лежит на этой же странице**. Задачи на Сашу хранятся на разных страницах (Trisigma-минутки, AI-аналитик-минутки, Аралов 1-1, Кирилл 1-1 и др.).

**Правильный порядок при переформулировке/правке существующей задачи:**
1. Сначала `./tr mine --any-deadline` — найти задачу по #N и узнать реальную страницу
2. Затем `./tr apply "#N текст: ..."` → `confirm` — TR сам знает нужный pageId

**Не искать задачу вручную через curl на конкретную страницу** — если её там нет, потеряешь время и можешь добавить дубль.

Прецедент (21.07.2026): задача «Обсудить с Денисом Малым необходимость AB AB...» показалась в контексте Trisigma, но реально лежала на странице Аралов 1-1. Поиск через `./tr mine` нашёл её сразу.

## Питфолл: зелёные тесты не гарантируют рабочий сквозной путь

При первичной реализации инструмента (13.07.2026) юниты дали 78/78 зелёных, но реальный
`read --assignee tkachenkoav` вернул пустой список — `pipeline.py` передавал сырую строку
ФИО/login прямо в `TaskFilter`, ни разу не вызывая уже готовую и рабочую функцию
`resolve_assignee()`. Юниты не поймали это, потому что тестировали `TaskFilter` изолированно
с уже готовыми userkey в фикстурах — не сквозной путь «сырой ввод пользователя → результат».
Аналогичный второй баг — `assignee_display` (обратный резолв userkey→ФИО) не вызывался нигде
в `page_reader`/`task_model`, из-за чего бриф показывал сырой userkey вместо имени; тоже не
пойман юнитами, только личным прогоном на реальных данных.

**Правило:** после любой доработки, где есть резолв/парсинг/маппинг между "сырым вводом" и
"внутренним представлением" — недостаточно unit-теста на сам резолвер в изоляции. Нужен ХОТЯ БЫ
один интеграционный прогон полного пути на реальных (или явно замоканных end-to-end) данных,
и обязательно — реальный smoke-тест на живом Confluence перед тем как сообщать пользователю
"инструмент работает" или "готов к использованию". Модуль, который просто существует и
экспортирует нужную функцию, не значит, что он реально вызывается там, где должен.
