# PLAN — план нового периода (44401–44403)

**Цель:** план на новый период из (1) факта завершённого SR (44404–44406) и (2) OKR-задач исполнителя на период.

**Источник правды:** блоки 1–3 оформляем и правим в MD (Obsidian), затем заливаем утверждённый текст в Jira.
Доработки — снова сначала MD, потом Jira. Шапка MD после заливки (`sync_md_header`, `--sync-md`) — только метаданные о последней записи в Jira.

## Порядок

1. **Сначала факт предыдущего SR (44404–44406)** — невыполненное, частичное, «перенесено». Список кандидатов на перенос.
2. Сверить с OKR на новый период (`fixVersion`, Contains, assignee; фильтр АИД — `tutu-jira-okr`).
3. **fixVersion не совпадает** — спросить пользователя; «уже поправил» → GET-верификация.
4. Каждый переходящий пункт — **бриф по одному**; квартальная рамка ≠ месячный результат.
5. Ссылки на Jira — **гиперссылки на ключ**, не только текст.
6. Логически связанные пункты вне списка пользователя — отдельный вопрос в брифе.
7. После брифа — оформление готово для 44401–44403 (без draft/check как у итогов).

## Формат блоков

### Блок 2 (44402)

- Заголовок пункта **дословно** как в Блоке 1.
- Критерии — буллиты в столбик (`- …`), не через `;`/`,`.

### Заголовки во всех 3 блоках

**Полное `summary` из Jira**, не сокращённый OKR-код. Objective+KR — summary KR (измеримый результат), при сомнении уточнить.
Batch: `jql=key in (...)` на шаге 2.

### Путь файла

`WorkVault/Projects/sr-tool/<ФИО>/SR-{key}_{месяц}_{год}.md` — блоки 1–3, без `_draft`/`_plan`.

### Пункты без задачи в Jira

Блок 1/2 — свободная формулировка. Блок 3 — существующий OKR-ключ по смыслу + `(без отдельной задачи в Jira)`.

## Сравнительная таблица критериев

`№ | Задача | Критерии <Имя1> | Критерии <Имя2> | …` — буллиты в ячейках.
Чужую колонку не домысливать. «Перенеси как мои по N,M,K» — дословно, без адаптации.

## Заливка плана (MD → Jira)

**Перед заливкой:** бриф и правки блоков 1–3 завершены в локальном MD (`SR-{key}_{месяц}_{год}.md`).

1. `python3 -m srtool fill-plan SR-XXXXX --from-md <path> [--yes] [--sync-md]` (или эквивалентный POST после подготовки текста из MD); `\n` → `\r\n`.
2. `GET /transitions` — обычно `61`, сверять всегда.
3. `POST /transitions` — только 44401–44403, **не** 44404–44406.
4. GET-верификация всех трёх полей + статус (обычно «Заполнение сотрудником»).
5. **`sync_md_header`** (флаг `--sync-md`): обновить шапку **того же** MD — статус Jira, дата, transition; тела блоков из Jira не подтягивать. После `61` статус часто **не меняется** («Заполнение сотрудником»); после `--submit` — «Согласование руководителем».
6. `systemctl --user start owncloud-sync.service` (скилл `workvault-sync`; не ручной `rclone sync`).

## Питфол: статус меняется вручную

Между брифом и заливкой пользователь может сменить статус в Jira. Признак: `400` на transition или id отсутствует. Повторить `GET /transitions` непосредственно перед `POST`; если transition нет — сообщить статус и ждать ручной правки.
