# Personal Data Sweep — кросс-зонный поиск следов и подготовка к необратимому удалению

Ручной sweep по всей системе (Hermes + диск + WorkVault + бэкапы + облако), когда Саша просит «найди все данные по <email/телеграм/ФИО>», «есть ли пароли рядом с этими именами», «найди и классифицируй всё по миграции/переезду, подготовь к удалению без восстановления, сейчас не удаляй». Это ручной поиск, НЕ запуск PIIScan-инструмента (его контракт — `pii-data-scanning`). Полный рецепт с командами — `references/sweep-recipe.md`.

## When to Use

Триггеры: «найди все данные по <email/телеграм/ФИО>» (в WorkVault, сессиях, облаке, архивах); «есть ли пароли рядом с этими именами»; «найди и классифицируй всё по миграции/переезду и подготовь к удалению без восстановления»; любой запрос на полный инвентарь следов человека/адреса по системе перед чисткой.

## Always-on правила

- **Read-only до явного императива.** Sweep и классификацию делать только чтением; удаление — после явного «удаляй»/«чисти» и утверждённого Сашей списка. Ничего не менять по ходу поиска.
- **Зоны и порядок:** `~/WorkVault` → `~/WorkVault_backup` → `~/.hermes/{sessions,cron,logs,error_bus,pii_scan}` → `~/USERTOOLS` → `~/hermes-workspace` → локальные скиллы → мелкие user-папки (`~/Documents ~/Downloads ~/Desktop ~/scripts ~/bin`) → облако через `rclone lsf`/`cat` (read-only). Сверять актуальность бэкапов: каталог мог быть вычищен между запросами.
- **История сессий:** `session_search` (FTS5) покрывает только живой state.db; старые дампы `~/.hermes/sessions/*.json|jsonl` искать `search_files`/`rg` напрямую — пустой FTS-ответ (`sessions_searched: 0`) НЕ означает «данных нет».
- **Секреты проверять только в файлах, уже совпавших по идентификатору** (не по всему дереву): паттерн `(password|пароль|token|secret|api[_-]?key|client[_-]?secret|BEGIN PRIVATE KEY)\s*[=:]\s*\S+`, затем отсечь ссылки на env (`os.environ[...]`, `getenv`) и обфусцированное хранилище (rclone `pass = <obfuscated>`).
- **Распространение секрета проверять значением:** `rg <само значение>` по всем зонам — найденный в WorkVault пароль почти наверняка уехал и в дампы сессий, и в облако-зеркало; подтверждать облако `rclone cat owncloud:<path>`.
- **Ложные совпадения:** склонения имени («Ткаченко Александра» = род./вин. падеж мужского имени, не отдельное лицо) и соседние адреса (yandex vs gmail) — атрибуцию по одному точному паттерну на запрос, не общим списком файлов (файл часто матчится сразу по нескольким паттернам).
- **Отчёт:** секреты не выводить (маскировать; называть тип: «app-пароль Яндекса», «VNC-пароль» + путь), группировать по идентификатору и характеру данных (ТЗ/код, встречи, дампы сессий, облако-зеркало); отдельной строкой — что не найдено вообще (0 во всех зонах).
- **Облако = зеркало WorkVault:** файл, найденный локально, есть и в ownCloud; локальное `rm` НЕ гарантирует удаление в облаке (осиротевшие архивы вроде `Hermes-Archive-1/*.tar.gz` остаются) — для «без восстановления» чистить облако отдельно (`rclone delete`) и корзину `.trash`.

## Деcommission-инвентарь (удаление следов миграции без восстановления)

Когда переезд завершён и Саша просит необратимо удалить следы, инвентарь берётся из предсказуемых мест; составить список ДО удаления и показать Саше:

- WorkVault: `Hermes-Backlog/MigrationToVM`, `Hermes-Backlog/MigrationToWindows`, `Hermes-Backlog/TZ/WindowsCutover`, dev-кейсы переезда (`dev/pereezd-*`, `dev/klon-*`, `dev/*windows*`), `_research/hermes-migration-plan`, файлы вида «Подключение к ВМ …» в корне (часто содержат пароли в открытом виде).
- Дампы сессий `~/.hermes/sessions/` — по дате-префиксу имени (миграция на VM — июнь, remote gateway/desktop — август, cutover — ноябрь) и по содержимому (`MigrationToVM`, `hermes serve`, `9119`, `WindowsCutover`). **Одна сессия живёт в трёх формах файлов** — `session_<id>.json`, парный `<id>.jsonl` и `request_dump_<id>_*.json`; при удалении по id/префиксу снимать все три, иначе остаются осколки.
- **Идентификаторный поиск НЕ достаёт тематические файлы.** Grep по email/телеграм/ФИО находит только файлы с этими строками; сессии темы (миграции) без идентификаторов находятся только по периоду + маркерам содержимого: `VM|owncloud|Яндекс.Диск|YandexDisk|XFCE|Obsidian|setup_owncloud|STATUS\.md|9119|hermes serve|VNC|MigrationToVM|миграц|переезд|перенос`. После сбора кандидатов по периоду каждый файл проверять маркерами и удалять только подтверждённые.
- **Ложные маркеры «миграц»:** служебные дампы (`request_dump_cron_*`) матчатся только потому, что системный промпт перечисляет скиллы (`hermes-vm-migration`) или глоссарий (`MIG=миграция`) — это НЕ артефакты темы. Перед включением в список удаления смотреть фактический совпавший фрагмент (`grep -o '.{60}миграц.{80}'`), а не наличие файла в выдаче.
- `/tmp` остатки сборки/доставки: `build_migration.*`, `hermes-migration-arch-*`, `delivery_*`, `delivery_full_check/` (там `hermes-state/sessions-export.jsonl` — до ГБ).
- Облако: осиротевшие архивы (локально удалено, в ownCloud осталось) — `rclone lsf` по зеркальным путям.
- Живой контур НЕ трогать: systemd (`hermes-serve.service`), `.env` auth-переменные, скиллы миграции (`hermes-desktop-remote`, `hermes-migration-archive`) — рабочие, не кандидаты.
- Перед составлением списка проверить, не проведена ли чистка ранее: `session_search` по «миграция/очистка» покажет следы (удалённые staging, бэкапы, снесённые интерактивные сессии) — не перечислять уже удалённое как актуальное.

## Rebrand / передача владельца (найди и замени идентификатор по всей системе)

Смежная с sweep задача — не «найди и удали», а «найди и замени <идентификатор владельца> на <новый> по всей системе» (эмэйл/ФИО/логин при смене владельца Hermes). Отличия от decommission-свипа:

- **Личность живёт в большем числе слоёв, чем три очевидных.** Обязательно проверить (кроме SOUL/USER/MEMORY): fallback-профили `~/.hermes/<alt-profile>/memories/USER.md` (haiku-fallback, qwen-fast); скиллы — `EXCHANGE_EMAIL`, `TUTU_USERNAME`, `SHARE_EMAILS`, owner user-ID (Zoom и т.п.); код USERTOOLS и `hermes-workspace/docs/tz/*`. Легко пропустить fallback-профиль и скиллы — там email копируется.
- **Спросить СРАЗУ о границе правки** (имя+роль или полный персональный блок) и про фигуры речи (обратиться на «ты» или «Вы», род местоимений он/она). Смена владельца НЕ даёт права переписывать рабочие правила/поведенческие преференции — их сохранять.
- **Живое vs историческое.** Менять идентификатор только в живых/содержательных файлах (SOUL, USER, fallback USER, скиллы, конфиги, docs). НЕ трогать неизменяемую историю — `.git` логи, `state.db`, `logs/`, кэш-саммари, `*_candidates.json` записи встреч: замена там портит фактический рекорд без результата.
- **Не делать «полную замену без вопросов»:** идентификатор из чужого контура (например Zoom user-ID старого владельца) нельзя подставлять без нового логина — честно пометить как нетронутое и спросить.
- **Защита записи на SOUL/USER/MEMORY:** `write_file` даёт «Refusing to overwrite … task has not seen its full current content», если файл видели только через `cat`/`grep`/системный промпт, а не через `read_file` из этой сессии. Для правок личности предпочесть `patch` (точечный, сохраняет соседние строки и проходит guard) либо сначала `read_file` всего файла, потом `write_file`.
- **Гвард блокирует inline-цикл `for f in ...; sed -i`** с длинным списком путей (lifecycle-guard scan budget). Для замены в многих файлах использовать `execute_code` с `read_file`+`write_file` по явному списку путей.
- **После замены верифицировать** `grep -l <старый>` по всем правленным путям → 0, и показать примеры новой записи.

## Исполнение удаления (decommission run)

Когда Саша подтвердил список и сказал «удаляй»:

1. **Проверка безопасности ДО удаления (не сломает Hermes):** `rg` целевых путей по живому контуру — `cron/jobs.json`, `config.yaml`, `.env`, `~/.hermes/scripts`, `~/hermes-workspace`, `~/USERTOOLS`, локальные скиллы. Различать реальные зависимости и безобидные совпадения: комментарий-исключение в скрипте (`НЕ трогаем: MigrationToVM/`) — не зависимость; слово «миграция»/даты в тексте скилла — не зависимость; запись в реестре инструмента (MarkObjectsFromSummary, MofsIndex) — устареет, но инструмент не сломается. Проверить открытые дескрипторы на удаляемые (`lsof | grep <путь>`, ожидание 0) и что Hermes жив ДО (`systemctl --user is-active hermes-serve.service`, `/api/status` → gateway running).
2. **Удаление локально точными путями** (без wildcard на корень): `rm -f` для файлов, `rm -rf` для каталога целиком; после каждого блока сразу проверять остатки (`ls | grep <префикс>`).
3. **Облако = зеркало:** запустить `owncloud-sync.service`; если синк падает на симлинках dev/** («not deleting files as there were IO errors») — точечные `rclone deletefile`/`purge` по точным путям (см. `workvault-cloud-targeted-delete`), `directory not found` при повторном листинге = подтверждение удаления.
4. **Верификация после:** локальные пути отсутствуют; облачные зеркала отсутствуют; Hermes жив ПОСЛЕ (serve active, gateway running, платформа connected). Это и есть критерий «без потери работоспособности».
5. **Не заявлять «без восстановления» из одного rclone:** корзина ownCloud `.trash` может быть не видна через rclone (`directory not found`) — для гарантии сверить корзину/версии в веб-UI отдельно и честно пометить в отчёте.

## Связанные

- `pii-data-scanning` — контракт PIIScan-инструмента (baseline/audit/ErrorBus), не ручной sweep
- `workvault-rag` — поиск по заметкам WorkVault (mofs index)
- `hermes-migration-archive` — сборка архива для переноса (включить/исключить), противоположная задача
- `hermes-data-purge` — удаление персональных сессий из живого state.db
- Смена владельца/персоны Hermes через SOUL/USER/MEMORY — контекст слоёв в `hermes-prompt-architecture`; rebrand-свип по идентификатору — этот скилл
