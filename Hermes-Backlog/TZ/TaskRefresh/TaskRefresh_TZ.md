# TaskRefresh — ТЗ (черновик)

Инструмент для гибкого извлечения задач `<ac:task>` из Confluence по комбинируемым фильтрам
(исполнитель / проект / дедлайн / дата создания) и последующего точечного редактирования
этих же задач (название, исполнитель, дата) прямо на странице-источнике, в режиме диалогового
брифа (поштучно / пачкой). Формализует и расширяет разовый механизм, отработанный Сиренью
13.07.2026 на странице OpenTasks (`~tkachenkoav`, pageId 492610494).

## Контракты экосистемы

### Источник истины
- Владелец записи: Confluence (`<ac:task>` на страницах-источниках); рантайм-сессия в `WorkVault/Tools/TaskRefresh/`

### Входные контракты
| Поле | Тип | Обязательность | Источник (кто отдаёт) | Формат/enum |
|---|---|---|---|---|
| contact.sources | str | optional | AnywhereContacts | json:contact_v2 |
| pfs.page_id | int | required | EntityRegistry | pageId Confluence |
| pfs.tag | str | required | EntityRegistry | префикс-тег проекта (напр. "Trisigma.") |
| row_anchor | str | optional | ProtocolFromSummary | pfsrow-{sha256(meeting_id)[:12]} |
| meeting_date | datetime(iso8601) | optional | ProtocolFromSummary | YYYY-MM-DD из _registry.json |

### Выходные контракты
| Поле | Тип | Потребитель (кто получает) | Формат/enum |
|---|---|---|---|
| task_status | enum[incomplete, complete] | Confluence, SRTool | ac:task-status |
| deadline | datetime(iso8601) | Confluence, SRTool | YYYY-MM-DD в time datetime |

### Зависимости
- Получает от: [AnywhereContacts, EntityRegistry, ProtocolFromSummary, Confluence]
- Отдаёт: [Confluence, SRTool]

### Breaking changes policy
- Версионирование формата: semver на уровне CLI-команд `./tr` и формата `pending_apply.json`
- При breaking change: сохранять совместимость параметров CLI и фильтров F1-F6

### Границы («что НЕ трогать»)
- Не удалять задачи и блоки в Confluence
- Не редактировать контент `<ac:task-body>` за пределами изменяемых полей (W1/W2/W3/W4/W5)
- Не создавать статичных whitelist страниц (динамический CQL)

## §1. Цель и происхождение

Дословный запрос Саши (сессия 13.07.2026, Сирень):

> «Нужен инструмент по изъятию такой информации из конфлюенс, вводные могут меняться,
> другое ФИО исполнителя, или уточняться проект (slug, что мы определяли для проектов из
> названия задачи) или по конкретным дедлайнам, или по полю когда задача создана (дата
> встречи из ТЗ ProtocolFromSummary). И далее, в режиме брифа, поштучно или пачкой, будем
> менять название, исполнителя и чаще всего дату по такой задаче. Причём информация должна
> меняться на странице источнике задачи.»

Триггер обнаружения: Саша попросил вывести список открытых задач со страницы OpenTasks
(492610494) — плагин Confluence, собирающий задачи по фильтрам assignee в единый лист.
Сирень воспроизвела ту же логику через прямые API-запросы (CQL + regex по storage), реально
достала список из 27 incomplete-задач Саши по 8 spaces из 35 найденных страниц-источников.
Работоспособность подхода **практически подтверждена** — TaskRefresh переводит его в
постоянный, повторно используемый и расширяемый инструмент.

## §2. Контекст и связь с существующими ТЗ

- **ProtocolFromSummary** (`TZ/ProtocolFromSummary/ProtocolFromSummary_TZ.md`, v1.4) —
  публикует задачи в тех же протоколах, использует тот же storage-формат `<ac:task>`,
  тот же реестр pageId/тегов проектов (§1.3), тот же механизм резолва участников через
  `contacts.enc` (§1.4), тот же принцип graceful degradation при конкурентных правках
  (§1.2 N-3, «инструмент никогда не удаляет ничего в Confluence сам»), тот же механизм
  привязки строк `row_anchor` (§1.2). **TaskRefresh обязан переиспользовать все эти
  контракты без изменений**, не изобретать альтернатив.
- **AnywhereContacts** (`USERTOOLS/AnywhereContacts`) — единственный источник резолва
  ФИО ↔ userkey, шифрованный `contacts.enc`. TaskRefresh читает и, если нужно,
  дозаписывает в него так же, как ProtocolFromSummary.
- **ConfluenceSync** (`TZ/ConfluenceSync/ConfluenceSync_TZ.md`) — общий низкоуровневый
  клиент Confluence Server/DC API (auth, GET, PUT, version handling, retry). TaskRefresh
  использует его как есть, не реализует свой HTTP-слой.
- **DialogBacklog** — TaskRefresh, вероятно, порождает новый источник диалоговых
  задач (например, «изменить дедлайн задачи X»), но сам инструмент — не про диалог-бэклог
  Саши, а про Confluence-задачи. Пересечения нет.

## §3. Технический вход (проверенные факты — не переоткрывать)

### 3.1 Страница-плагин OpenTasks

`https://dom.tutu.ru/display/~tkachenkoav/OpenTasks`, pageId **492610494**. Это не хранилище
задач — это композиция из 12 вкладок (`ac:structured-macro ac:name="tab-pane"`), внутри
каждой — 1–2 макроса `ac:structured-macro ac:name="tasks-report-macro"` (нативный Confluence
Server Reporting Plugin, **не Jira**) с параметрами:

- `spaces` — список ключей пространств через запятую (`DPAN,~tkachenkoav`,
  `DPAN,analytics,DATA`, …).
- `assignees` — один или несколько `<ri:user ri:userkey="…"/>`.
- `labels` — метка (везде используется `_aid`).
- `status` — опционально `complete` (наблюдается на вкладке DONE; поведение без параметра —
  см. §9 Q-2, требует явной проверки).

Макрос агрегирует на лету, ничего не хранит. TaskRefresh **воспроизводит эту же логику
сам**, не парсит рендер таблицы плагина.

### 3.4 Формат задачи в storage

Идентичен ProtocolFromSummary §1.2:

```
<ac:task>
  <ac:task-id>N</ac:task-id>
  <ac:task-status>incomplete|complete</ac:task-status>
  <ac:task-body>[mention <ac:link><ri:user ri:userkey="..."/></ac:link>] текст [<time datetime="YYYY-MM-DD"/>]</ac:task-body>
</ac:task>
```

- Дедлайн — `<time datetime="YYYY-MM-DD"/>` внутри `ac:task-body`.
- Исполнитель — `userkey` внутри `<ri:user>`.
- `ac:task-id` — **локален для страницы** (важно, см. §9 Q-4).

### 3.5 Проверенный алгоритм извлечения (baseline)

Для каждой из N выбранных страниц:
1. `GET /rest/api/content/{pageId}?expand=body.storage,title,version` — получить storage_html.
2. Найти все `<ac:task>…</ac:task>` (регулярка или XML-парсер, устойчивый к вложенности; в
   proof-of-concept использовалась нежадная регулярка, работает — но реализация выберет
   более надёжный парсер, см. §9 Q-5).
3. Отфильтровать по вхождению искомых userkey в `<ri:user>` внутри блока.
4. Извлечь: `task-id`, `task-status`, чистый текст (очищенный от inline-тегов),
   `<time datetime>`, `source_page_id`, `source_page_title`, `row_anchor` найденной
   родительской строки (см. §5.2).

В proof-of-concept 13.07.2026 из 35 страниц получено 700 задач суммарно (по всем видимым
assignee), из них 27 incomplete на Сашу (userkey `8a8383b593a26ea60194abdf8d090020`).

### 3.6 Резолв ФИО ↔ userkey

Полностью переиспользуется механизм ProtocolFromSummary §1.4:
`contacts.enc` → substring-match → (если пусто) CQL `user.fullname~"…"` → сохранить в
`contacts.enc` → (если и это не дало) fallback Haiku на список кандидатов. Никакого
собственного механизма TaskRefresh не заводит.

### 3.7 Дата создания задачи

**«Дата создания» = `meeting_date` строки протокола, в которой задача появилась**, не
метка «created» самой Confluence (её у отдельного `<ac:task>` в storage нет). Источник —
`_registry.json` инструмента ProtocolFromSummary
(`/home/tkachenkoav/WorkVault/ProtocolFromSummary/_registry.json`), связка идёт через
`row_anchor` (§1.2 ProtocolFromSummary): по `row_anchor` строки, содержащей задачу,
находим `meeting_id` → `meeting_date`. Для страниц ВНЕ покрытия ProtocolFromSummary
(старые ручные протоколы без anchor) — механизм не работает by design, см. §9 Q-8.

## §4. Функциональные требования

### 4.1 Функция 1 — READ (извлечение задач по фильтрам)

Комбинируемые фильтры (все опциональны, комбинируются логическим И):

| # | Фильтр | Значения | Источник |
|---|---|---|---|
| F1 | Исполнитель | ФИО / login / userkey / список | Резолв через `contacts.enc` (§3.6). Мульти-assignee по OR внутри F1. |
| F2 | Проект | slug (`Trisigma`, `AI-ready`, …) / pageId / тег (`Trisigma.`) / список | Реестр `ProtocolFromSummary_TZ §1.3`. Матч по (a) `source_page_id` из реестра, (b) префикс-тегу в тексте задачи. Обе стратегии OR. |
| F3 | Дедлайн | точная дата `YYYY-MM-DD` / диапазон `from..to` / `overdue` (дедлайн < today, статус incomplete) / `this-week` / `next-week` / `no-deadline` (нет `<time>`) | `<time datetime>` из тела задачи + `today()` VM. Точный набор именованных пресетов — §9 Q-3. |
| F4 | Дата создания | точная дата / диапазон / `this-month` / … | `meeting_date` через `row_anchor` → PFS registry (§3.7). Только для страниц с anchor. Fallback — §9 Q-8. |
| F5 | Статус | `incomplete` (default) / `complete` / `any` | `<ac:task-status>`. Default — `incomplete`, т.к. основной use-case «мои открытые задачи». |
| F6 | Пространства/страницы | whitelist / blacklist pageId | Дефолтный набор spaces — §9 Q-1. |

Выход — список объектов задач. Минимальные поля объекта:

```
{
  task_id: int,                     # <ac:task-id> — локален для source_page_id
  source_page_id: int,
  source_page_title: str,
  source_space_key: str,
  row_anchor: str | null,           # pfsrow-... из первой <td> строки, если есть
  assignee_userkey: str | null,
  assignee_display: str | null,     # резолв через contacts.enc обратно в ФИО
  status: "incomplete" | "complete",
  text_clean: str,                  # текст без тегов, для показа Саше
  text_storage: str,                # оригинальный XML task-body (для будущих write-операций)
  deadline: str | null,             # ISO YYYY-MM-DD
  project_tag: str | null,          # префикс из §1.3 PFS, если определился
  meeting_id: str | null,           # из PFS registry по row_anchor
  meeting_date: str | null,         # из PFS registry
  page_version_at_read: int         # для оптимистической блокировки при последующем PUT
}
```

Формат вывода Саше — компактный человекочитаемый брифинг: пронумерованный список,
одна задача в 1–2 строки, группировка по проекту, сортировка по дедлайну (просроченные
первыми). Точный визуальный формат — §9 Q-6.

### 4.2 Функция 2 — WRITE (изменение задач в режиме брифа)

Инвариант: **изменения пишутся на страницу-источник задачи**. Никаких локальных копий,
никаких «параллельных списков». Одна задача — один PUT одной страницы (или откладываем
и группируем несколько задач одной страницы в один PUT — §9 Q-7).

Разрешённые изменения (по прямой команде Саши):

| # | Операция | Что меняется в storage | Ограничения |
|---|---|---|---|
| W1 | Изменить текст | Содержимое `ac:task-body` **между** mention и `<time>` | Mention и `<time>` не трогаем (это отдельные W2/W3). Форматирование внутри text сохраняется bytes-for-bytes для не-меняемых частей. |
| W2 | Изменить исполнителя | `<ri:user ri:userkey="…"/>` внутри mention | Новый userkey резолвится по §3.6. Если резолв неуспешен — §9 Q-9. |
| W3 | Изменить дедлайн | `<time datetime="…"/>` в теле задачи | Если тега `<time>` не было — добавить в конец task-body. Если есть, но новое значение = null (Саша сказал «убрать дедлайн») — удалить тег. |
| W4 | Изменить статус (opt) | `<ac:task-status>` | Не главный сценарий (Саша обычно закрывает задачи галочкой в веб-UI), но технически поддерживается. Включать в MVP — §9 Q-10. |

**Не поддерживается в MVP** (явно): удаление задач, перенос задачи между страницами
(это МЕХАНИЗМ А из ProtocolFromSummary §1.9, отдельный тул), массовое переоформление
строки протокола (это republish в PFS §1.7).

**Дисциплина graceful degradation (перенос из PFS §1.2 N-3, дословно):** TaskRefresh
никогда не удаляет чужой материал; редактирует ровно один `<ac:task>` за раз, точечной
заменой в storage_html. Если исходный `<ac:task>` не найден на PUT (Саша удалил вручную
между READ и WRITE) — считаем утраченным, warning в лог + сообщение Саше в брифе,
пропускаем эту задачу, продолжаем остальные.

**Оптимистическая блокировка:** перед PUT — свежий GET страницы. Сверяем
`page_version_at_read` с текущей. Если разошлись — retry с новым GET (один раз, как в
PFS §1.7 N-2). Если и второй раз конфликт — откладываем, warning, следующая задача.

**Dry-run режим:** рекомендуется как обязательный default, см. §9 Q-11.

### 4.3 UX брифа (Функция 1 → Функция 2)

Диалоговый цикл:

1. Саша формулирует фильтр (естественным языком или структурированно).
2. TaskRefresh выдаёт пронумерованный список (§4.1).
3. Саша указывает изменение: `#3 дедлайн 2026-07-20`, `#5,#7,#9 → Кирилл`,
   `#12 текст: "…"`, или пачкой (`все просроченные Илье → +7 дней`).
4. TaskRefresh показывает preview изменений (dry-run diff) + просит подтверждение.
5. По подтверждению — реальные PUT, отчёт что прошло/что откатилось.

Точный синтаксис команд шага 3 — §9 Q-6/Q-7. Универсальный протокол уточнений — по
существующему `TZ-Workflow/Universal open-question protocol`, отдельного не заводим.

## §5. Архитектура (высокоуровнево, без пофайлового плана)

### 5.1 Границы

- Код-side: `USERTOOLS/TaskRefresh/` (Python-пакет, как остальные MoveFrom*, PFS).
- Vault-side: `WorkVault/Tools/TaskRefresh/` для runtime — конфиг spaces/labels,
  кэш последней READ-сессии (для номеров `#N` в брифе), лог операций.
- ТЗ и pm-заметки: `WorkVault/Hermes-Backlog/TZ/TaskRefresh/` (сам этот файл + `pm/`).

### 5.2 Поиск `<ac:task>` внутри `<tr>` для WRITE

Ключевой вопрос — как однозначно найти конкретную задачу на PUT. Варианты — §9 Q-4.

Родительская строка (`<tr>`), в которой лежит задача — определяется по `row_anchor`
(pfsrow-…) первой `<td>` этой строки (см. PFS §1.2). Это нужно для функции F4
(дата создания), а также для лога/показа Саше «эта задача из встречи от такого-то числа».

### 5.3 Реестры и переиспользование

- Реестр pageId ↔ slug ↔ project_tag — читаем из `TZ/ProtocolFromSummary/ProtocolFromSummary_TZ.md`
  §1.3, программно (парсим таблицу или выносим в общий JSON — §9 Q-1).
- Реестр meeting_id ↔ meeting_date ↔ row_anchor — читаем `_registry.json` PFS.
- Contacts — `contacts.enc` через `AnywhereContacts`, read+write.

TaskRefresh НЕ дублирует эти реестры своими копиями.

## §6. Критерии успеха (для приёмки после реализации)

## §12. Решения брифа 13.07.2026 (финальные, заменяют рекомендации §9 где расходятся)

Бриф проведён Сиренью поштучно по каждому Q, с конкретными примерами на реальных данных.
Везде, где решение Саши расходится с рекомендацией Опуса — решение Саши в силе, рекомендация

**Q-1 (spaces/pageId) — ОТКЛОНЕНА рекомендация (4).** Никакого статичного whitelist/конфига.
TaskRefresh сканирует **живым CQL-запросом на каждый прогон**: `label="_aid"` БЕЗ ограничения
по `space` — по всей Confluence, к которой есть доступ у токена. Список страниц целенаправленно
меняется во времени (новые протоколы появляются, старые могут архивироваться) — TaskRefresh
не хранит собственный реестр страниц, переоткрывает актуальный набор каждый раз заново.
READ и WRITE используют один и тот же набор найденных страниц — никакого отдельного, более
узкого whitelist для WRITE (никаких исключений вроде 432316254). Единственная защита от
случайных правок — обязательное согласование перед PUT (см. Q-11, общий режим брифа).

**Q-2 (макрос без `status`) — подтверждено практикой, тест не требуется.** Саша показал
реальный скриншот вкладки DONE (`status=complete`) с полностью другим набором задач,
датированных ещё мартом 2025 — этим механизмом фильтрации Саша пользуется больше года.
Финально: `status` — явный фильтр F5, `incomplete` — default (открытые задачи), `complete`
и `any` — по явному запросу. Никакой неопределённости, отдельный тест не нужен.

**Q-3 (пресеты F3) — расширенный финальный список.** `overdue`, `no-deadline`, `this-week`
(календарная, пн-вс), `next-week`, `today`, `tomorrow`, `next-N-days` (N параметризуется),
диапазон `YYYY-MM-DD..YYYY-MM-DD`, точная дата `YYYY-MM-DD`.

**Q-4 (ключ для PUT) — принят вариант 1, `ac:task-id` без защитной сверки.** Причина отказа
от рекомендованной сверки (было d/4): реальный workflow брифа — TaskRefresh показывает список
→ Саша называет номер конкретной задачи → TaskRefresh сразу применяет правку. Обработка всегда
поштучно или пачкой **в рамках одного непрерывного диалога** — риск, что кто-то удалит задачу и
Confluence переиспользует её `ac:task-id` между показом списка и применением правки (секунды-
минуты одного диалога), признан пренебрежимо малым и не учитывается. Anchor-миграция (вариант c)
и текстовая сверка (вариант d) — отклонены как избыточная сложность для этого риска.

**Q-5 (парсер) — подтверждён вариант 2 (`lxml` READ + string.replace WRITE), с уточнением.**
Уточнение Саши: при правке даты ИЛИ исполнителя (не только текста) — не редактируется
подстрока внутри блока, а **весь блок `<ac:task>...</ac:task>` разбирается через lxml,
собирается заново целиком** (с изменённым `<ri:user ri:userkey>` и/или `<time datetime>`,
остальным без изменений) и одним `string.replace` старый полный блок меняется на новый полный
блок в storage_html всей страницы. Остальной XML документа не затрагивается вообще.

**Q-6 (формат брифа) — подтверждён вариант 3, группировка по проекту.** Внутри группы —
сортировка по дедлайну (просроченные первыми). Уточнение по всему брифу (не только Q-6):
варианты вопросов давать **цифрами (1, 2, 3…), не буквами** — принято как стандарт для
всех будущих уточнений TaskRefresh (и вообще всех будущих ТЗ).

**Q-7 (пачка изменений) — уточнена формулировка, не просто вариант 2.** Пачка ОБРАБАТЫВАЕТСЯ
(не отклонена в пользу чисто поштучного режима), но показ пачки **уже содержит конкретное
«было → станет» по каждой строке**, не общее описание правила. Одно подтверждение относится
ко всей пачке сразу, но т.к. каждая строка самодостаточна и проверяема — по сути это визуальный
эквивалент поштучного согласования каждой задачи, просто одним экраном и одним «да». Пример
формата (зафиксирован дословно):
```
Подтверди изменения (5 задач):
1. [Trisigma] "Собрать таймлайн" — было 20.07 → станет 27.07
2. [ML-платформа] "Уточнить у вендора список почт" — было 10.07 → станет 27.07
...
```
Группировка PUT по странице (из рекомендации) — остаётся как техническая деталь реализации,
не влияет на UX-формат показа.

**Q-8 (дата создания задачи, F4) — ОТКЛОНЕНА рекомендация (1), принято универсальное правило
без anchor.** Дата создания/назначения задачи = **дата из первого столбца (`<td>`) строки
таблицы (`<tr>`), в которой физически находится `<ac:task>`** — большинство протокольных
таблиц имеют формат «Дата | Задачи», и первая колонка содержит дату встречи/создания
независимо от того, публиковал ли туда ProtocolFromSummary (с anchor) или Саша сам вписал
строку вручную много лет назад. `row_anchor`/PFS `_registry.json` НЕ требуется для этого
фильтра вообще — anchor нужен исключительно для механизма republish/copy в PFS, не для чтения
даты. Единственное реальное ограничение — страницы БЕЗ табличной структуры вообще (плоский
список задач без даты в принципе, например «Мысли онлайн») — там физически нет данных для
F4, и это должно явно показываться в брифе (сколько/какие страницы не имеют данных для

не просто выдавать более короткий список.

**Q-9 (резолв нового исполнителя не удался) — ОТКЛОНЕНА рекомендация (1), принят вариант 2.**

## §14. Баг: дубль `<time>` при правке дедлайна на вложенной разметке (13.07.2026)

### Обнаружено в проде

При первом реальном использовании (`taskrefresh apply "#N дедлайн ..."` на живых задачах
Саши, page_id 499570832 "Саша А. 1-1") задача task_id=18 ("AI-ready.Взятие под контроль
вопроса в ИБ") получила **дублирующийся** `<time>` — старое значение осталось внутри
`<p><span><span>...<time datetime="2026-07-10"/>...`, новое (`2026-07-15`) было добавлено
СНАРУЖИ этой вложенной структуры, прямым потомком `<ac:task-body>`.

**Root cause:** `task_block.py::rebuild_task_block` искал существующий `<time>` только
среди **прямых потомков** `<ac:task-body>` (`body_el.find("time")`). Задачи, где визуальный
текст обёрнут в `<p><span><span>...</span></span></p>` (реальный формат части задач на этой
странице — вероятно, результат ручного редактирования Сашей через веб-редактор Confluence,
который сам оборачивает inline-контент), имеют `<time>` вложенным на 3 уровня глубже —

### Ручное исправление испорченной задачи

Дубль на task_id=18 (page_id 499570832) исправлен вручную прямым PUT — оставлен только

удалён. Подтверждено GET после PUT (`count("<time") == 1` в блоке задачи).

### Фикс кода

`task_block.py::rebuild_task_block` — поиск `<time>` заменён с `body_el.find("time")`
(прямые потомки) на обход `body_el.iter()` (весь поддерево, любая глубина вложенности).

`body_el.remove()` (которое падает, если `<time>` не прямой потомок).

**Не в скоупе этого фикса:** `_replace_visible_text()` (правка текста задачи, W1) имеет ту же
потенциальную уязвимость — `link_el`/`time_el` там тоже ищутся среди прямых потомков
`body_el`, и линейная логика (`link_el.tail = ...`) не переживёт такую же вложенность.
Пока не воспроизведено на реальных данных (сегодняшний баг — только про дедлайн), но
зафиксировать как известное ограничение: если правка текста задачи (`apply "#N текст: ..."`)
даст похожий дубль/потерю контента на вложенной разметке — чинить по тому же паттерну
(`.iter()` вместо `.find()`).

**Тесты:** 2 новых в `tests/test_task_block.py` (`test_change_deadline_nested_time_no_duplicate`,

## §15. Критичный баг рассинхронизации нумерации #N (13.07.2026) + добавление W4

### Баг: #N в брифе ≠ #N в apply/task_by_number

При попытке применить правку "#1"/"#2" сразу после первого `read` оказалось, что
`apply "#1 дедлайн ..."` показывает preview **другой** задачи, чем #1 в тексте брифа,
показанном Саше.

**Root cause:** `formatter.format_brief()` группировала задачи по проекту и сортировала
по дедлайну **только для отображения**, но `pipeline.run_read()` передавала в
`session_store.save_session()` **исходный несортированный** список (`result.kept`,
порядок сканирования Confluence-страниц). `session.task_by_number(n)` берёт
`session.tasks[n-1]` — то есть #N в apply означал позицию в порядке сканирования,
а #N в брифе — позицию после группировки/сортировки. Эти два порядка расходились
на любом непустом наборе задач из нескольких проектов.

Обнаружено сразу на первом реальном прогоне: правка "#1"/"#2" (по брифу — "Тестировать
skill"/"Взятие под контроль ИБ") реально попала на "ML-платформа. Собрать таймлайн"
(случайно поймано и остановлено до применения) и правильную задачу (после сверки вручную).

### Фикс

Добавлена `formatter.order_tasks_for_display()` — единственное место, где считается
итоговый порядок (группировка + сортировка). `pipeline.run_read()` теперь вызывает её
**один раз**, передаёт результат и в `save_session()`, и в `format_brief()` — гарантируя,
что `session.tasks[n-1]` физически совпадает с #n в тексте брифа. `format_brief()` больше
не сортирует сама — только нумерует уже упорядоченный список и печатает заголовки групп
при смене `project_tag`.

**Тест-регресс:** `test_order_tasks_for_display_matches_brief_numbering` — явно проверяет,
что позиция задачи в `order_tasks_for_display()` совпадает с номером `#N`, который
`format_brief()` печатает для этой же задачи (4 задачи, 3 проекта, смешанный overdue/не-overdue).

### W4 — закрытие/переоткрытие задачи (включено в MVP)

## §16. Баг классификации проекта: текстовый тег vs page_id контейнера (13.07.2026)

### Обнаружено

Саша указал, что задача #15 ("Подготовить список вопросов для встречи по разработке
в Гермесе") должна относиться к проекту **AI-аналитик**, а бриф показывал её в группе
**"Кирилл 1-1"**. Текст задачи явно начинается с тега `"AI-аналитик. "` — классификация
была неверной.

**Root cause:** `filters.py::TaskFilter._annotate_project()` проверял
`registry.match_by_page_id(task.source_page_id)` **первым**, безусловно, и только
при `None` падал на `match_by_text()`. Персональные 1-1-страницы (Кирилл 1-1, Аралов
1-1, Илья 1-1, Жиров 1-1) зарегистрированы в `project_registry.json` как единые
проекты **без tag** (`"tag": None`) — это общие контейнеры для задач РАЗНЫХ проектов,
обсуждённых на конкретной личной встрече. Любая задача на такой странице с явным
текстовым тегом («AI-аналитик.», «Trisigma.» и т.д.) получала `project_tag` контейнерной
страницы вместо своего реального тега, потому что page_id матчился раньше текста.

Дополнительно обнаружено на аудите: страница `490170597` зарегистрирована ОБОИМИ
проектами Trisigma и AB-платформа одновременно — `match_by_page_id` для неё
принципиально неоднозначен (возвращает первый slug по порядку итерации словаря
Python), тогда как `match_by_text` разруливает корректно по фактическому тегу
каждой конкретной задачи.

### Фикс

`filters.py::_annotate_project()` — приоритет изменён: сначала `match_by_text()`
(явный тег в начале текста задачи), `match_by_page_id()` — fallback только когда
текстовый тег отсутствует (для задач без явной классификации, где отнесение к
1-1-встрече как к "проекту" — единственный доступный сигнал).

**Тесты:** 2 новых в `test_filters.py` (`test_text_tag_wins_over_container_page_id` —
текстовый тег побеждает; `test_page_id_fallback_when_no_text_tag` — fallback
на page_id сохранён для задач без тега). Тестовый `project_registry_json` fixture
дополнен записью `AI-аналитик`. Вся сборка — **96/96 тестов, без регрессий**.

**Живая проверка:** после фикса `read` вернул корректную классификацию — группа
"Кирилл 1-1" пропала из брифа (была искусственной), задача перешла в "AI-аналитик"
автоматически (без ручной правки project_tag). Отдельно применена правка дедлайна
(#3 "Обсудить best practice... в курсоре" → 16.07, task_id=684, page_id 432316254),
подтверждено GET после PUT — один `<time>`, без дублей.

## §17. Контракт команды «Проект — X» (13.07.2026, зафиксировано Сашей явно)

**Формулировка Саши:** «Когда я говорю проект такой-то — это значит в том списке
задач, где задача, она остаётся, но в ней меняется или добавляется slug для задач».

**Контракт:** команда «#N проект — X» (или голосом «16 проект — АДМ») НЕ перемещает
задачу в другой список/другую страницу Confluence — задача физически остаётся там же
(тот же `source_page_id`, тот же `<ac:task>` блок). Меняется/добавляется только
**классификация** — `project_tag`, используемый исключительно для группировки в брифе
TaskRefresh. Это НЕ поле Confluence (не пишется в тело задачи), а чисто локальная
метаданные уровня `project_registry.json` (реестр tag→slug, см. §1.3 механизма).

**Практическая реализация (13.07.2026, живой кейс):** для задачи «АДМ. OKR проверить
кол-во конференций» (page_id 432316254, task_id 620), которая ошибочно попадала в
группу «Без проекта» (текст начинается с «АДМ.», но такого slug не было в реестре) —
добавлена новая запись `"АДМ": {"pageIds": [], "tag": "АДМ."}` в
`WorkVault/Tools/TaskRefresh/project_registry.json`. После этого ВСЕ задачи с текстовым
тегом «АДМ.» (не только целевая — ещё и «Обсудить на СИНК АИД вопрос Central University»,
ранее сидевшая в «Аралов 1-1») автоматически переклассифицировались в группу «АДМ» —
это ожидаемое и корректное поведение самого механизма match_by_text (§16), не побочный
эффект. **Инструмент группирует по факту текстового тега в задаче, а не по разовому
решению для одной конкретной задачи** — если новый slug добавлен в реестр, он
применяется ко ВСЕМ задачам с этим тегом, а не только к той, ради которой добавлялся.

Если Саше нужно перенести/добавить slug только ОДНОЙ конкретной задаче без текстового
тега (или с тегом, который не должен триггерить массовую переклассификацию) — это НЕ
покрыто текущим механизмом `match_by_text`/`project_registry.json` (нет точечного
per-task override project_tag, не завязанного на текст). Если такой кейс встретится —
потребуется отдельная доработка (например поле `project_tag_override` в самой задаче
или отдельный whitelist по `task_id`).

## §18. Оптимизация под низкий cost (Haiku), экономия токенов (13.07.2026)

### Задача

По итогам первого полного рабочего цикла (§13-§17) Саша попросил доработать инструмент
и скилл так, чтобы аналогичная работа с задачами в будущем занимала минимум токенов и
могла выполняться Haiku (а не только Sonnet/Opus). Цикл до этой доработки требовал:
длинную venv-команду на каждый вызов, отдельный curl-проход для ссылок Confluence при
сверке, отдельный ручной curl-проход для верификации после каждого `confirm`, два похожих
скилла (`taskrefresh` + `tutu-taskrefresh`) с дублирующимся содержимым.

### Реализованные доработки

1. **`tr` — bash-wrapper** (`~/USERTOOLS/TaskRefresh/tr`, exec bit). Устраняет
   необходимость писать полный путь до `ProtocolFromSummary/.venv/bin/python3` в каждом
   вызове — `./tr mine` вместо `cd ... && /home/.../venv/bin/python3 -m taskrefresh read
   --assignee ... --status incomplete --deadline "2020-01-01..2099-12-31"`.

2. **Команда `mine`** (`__main__.py`) — однокомандный дефолтный срез Саши
   (`--assignee tkachenkoav --status incomplete --deadline <широкий диапазон>`), зашитый
   как константы (`_MINE_DEADLINE_STUB`, `_MINE_DEFAULT_ASSIGNEE`). Флаги `--any-deadline`,
   `--project`, `--status` позволяют отойти от дефолта явно без переписывания всей
   команды. Экономит целый round-trip формулирования длинного `read`-вызова на каждый
   запрос "мои задачи".

3. **`format_brief(with_links=True)` + `run_read(with_links=True)` + CLI-флаг `--links`**
   (`formatter.py`, `pipeline.py`, `__main__.py`) — дописывает
   `https://dom.tutu.ru/pages/viewpage.action?pageId=<source_page_id>` в конец каждой
   строки брифа. Устраняет отдельный проход curl/read_file по каждой задаче, который
   раньше требовался при запросе Саши "выведи итог, сверюсь с Confluence" (прецедент
   §17 — токены тратились на 16 отдельных построчных подтверждений через curl).

4. **Встроенная верификация после `confirm`** (`pipeline._verify_applied()`,
   `run_apply_confirmed(verify=True)` по умолчанию, CLI-флаг `--no-verify` для отключения).
   Перечитывает изменённые страницы **сама**, тем же вызовом `confirm` — без отдельного
   ручного curl-прохода, который раньше делался вручную после каждого `confirm` для
   проверки "не задублился ли `<time>`" (§14) и "применилось ли значение". Печатает
   "Верификация после записи: ок" при отсутствии проблем, либо явную строку с описанием
   расхождения (дубль `<time>`, не найден блок, значение не совпало). Опирается на тот же
   `apply_changes`/`ApplyReport`, не требует нового обращения к инструменту.

5. **Консолидация скиллов**: `taskrefresh` и `tutu-taskrefresh` содержали пересекающийся
   контент (venv-питфолл, нумерация #N, формат вывода) — объединены в единый компактный
   `taskrefresh` (v2.0.0), `tutu-taskrefresh` удалён (`absorbed_into=taskrefresh`). Меньше
   токенов на загрузку скилла, нет риска расхождения дублирующихся инструкций.

**Тесты:** 5 новых в `test_pipeline_e2e.py` (`with_links` дописывает URL / не дописывает
без флага, verify подтверждает отсутствие дубля / детектирует дубль на испорченных данных,
`verify=False` не делает лишний GET). Вся сборка — **101/101 тестов, без регрессий**.

**Живая проверка:** `./tr mine --links` — работает, вывод идентичен предыдущему ручному
циклу read+curl, но за один вызов вместо read + N curl-запросов. Реальные задачи Саши
не изменялись в ходе этой доработки (только read-only проверки).

## §19. Баг дубля текста при `apply "#N текст: ..."` на вложенной разметке (13.07.2026)

### Обнаружено

Саша попросил добавить ссылку в конец текста задачи «AI-ready. Взятие под контроль
вопроса в ИБ» (task_id=18, page_id=499570832 — та же задача, на которой чинили дубль
`<time>` в §14!). Первый `apply "#1 текст: ..."` → `confirm` прошёл без ошибок и
верификация (§18, проверяет только `deadline`/`status`) не заметила проблему — но живая
проверка на Confluence показала **дублированный видимый текст**: новый текст (с добавленной
ссылкой, без mention) был вписан в `body_el.text` ПЕРЕД дочерним `<p>`, а старый текст
(с mention и `<time>`) остался нетронутым внутри `<p><span><span>`.

**Root cause:** `_replace_visible_text()` искала `<ac:link>`/`<time>` только среди
**прямых потомков** `body_el` (`body_el.find("ac:link")`, `body_el.find("time")`) — тот же
класс уязвимости, что чинили для `<time>` в `rebuild_task_block()` в §14, но
**отдельная функция**, фикс §14 её не покрыл (это было явно задокументировано как известное
ограничение в §14/скилле — и ограничение реализовалось на первой же реальной правке текста).

### Фикс

`_replace_visible_text()` переписана на `_find_nested()` — обходит поддерево `body_el.iter()`
на любой глубине (та же логика, что уже была в `rebuild_task_block` для `<time>`). Три ветки:
- mention найден (на любой глубине) → текст пишется в `link_el.tail`, `body_el.text`
  обнуляется, если mention вложен глубже прямого потомка (иначе старый текст остаётся
  сиротой перед вложенным деревом)
- mention нет, time есть (на любой глубине) → текст пишется в `.text` родителя time
- ни mention, ни time — весь текст мог быть вложен глубже (`<p><span>текст</span></p>`):
  все дочерние элементы `body_el` удаляются, остаётся только новый текст (дубль-safe)

**Тесты:** 2 новых в `test_task_block.py` (`test_change_text_nested_no_duplicate` —
mention+time вложены, `test_change_text_nested_no_mention_no_time` — вообще без
mention/time, текст сам вложен) + 1 новый в `test_pipeline_e2e.py`
(`test_confirmed_verify_detects_duplicated_text`, юнит-тест `_verify_applied` напрямую).
Вся сборка — **104/104 тестов, без регрессий**.

**Живая проверка:** реальная задача (task_id=18, page_id=499570832) переприменена через
исправленный код — `body.count("Взятие под контроль")` == 1 (было 2 на момент обнаружения
бага), mention и `<time>` сохранены, ссылка добавлена в конец.

**Дополнительно: верификация (§18) расширена на `field="text"`** — теперь `_verify_applied`

## §22.3. §A — Мульти-полевой парсер команды

### §22.3.1 Синтаксис

**Разделитель между полями одной команды: `;`.** Пробелы вокруг `;` игнорируются. Разделитель `;` выбран, потому что не встречается ни в текстах задач Саши (все известные тексты — по-русски, `;` не используется), ни в датах, ни в URL, ни в ФИО.

Обязательные требования:

1. **Обратная совместимость.** Команда без `;` парсится строго как раньше — старым кодом, без изменений поведения. Все существующие 112 тестов остаются зелёными без правок.
2. **Мульти-поле для одной задачи или пачки.** Ведущий `#N[,#M...]` или `#N-#M` — общий для всех токенов после разделения. Пример: `#3 закрыть; текст: "..."` — оба действия применяются к задаче #3. Пример пачки: `#3,#5 закрыть; дедлайн 05.08` — к обеим задачам применяется и закрытие, и новый дедлайн.
3. **Кавычки внутри `текст: "..."` защищены** — `;` внутри строкового литерала между двойными кавычками **не** является разделителем. Токенизатор должен уметь распознать `текст: "финал; готово"` как один токен со значением `финал; готово`.
4. **Порядок применения полей** (строго, независимо от порядка ввода):
   1. `text` (W1)
   2. `assignee` (W2)
   3. `deadline` (W3)
   4. `status` (W4)
   5. `link` (W5)
   Причина порядка: смена текста через `_replace_visible_text` работает над всем `<ac:task-body>`; она не должна перезаписывать mention/`<time>`, но если исполнитель/дедлайн меняются в той же команде — их запись идёт **после** правки текста, работает по обновлённому блоку, ничего не теряется. Статус меняется в самом конце, чтобы `<ac:task-status>` не сбивал верификацию промежуточных шагов.
5. **Один `apply` = один `ChangeSpec` на пару (задача, поле).** Мульти-поле разворачивается в список `ChangeSpec`-ов, каждый со своим `field`. Существующий `write_ops` уже умеет применять несколько spec'ов подряд к одной странице — новых write-путей не появляется.

### §22.3.2 Реализация

Псевдокод (уточняется реализатором):

```python
def parse_change_command(cmd, session, today=None):
    cmd = cmd.strip()
    # 1) batch «все просроченные ...» — как раньше, отдельная ветка
    if re.match(r"^все\s+просроченные\s+", cmd, re.I):
        return _parse_all_overdue(cmd, session, today)

    # 2) разделяем ведущий # N[,#M...] и хвост
    numbers, tail = _split_leading_numbers(cmd)  # None, cmd если нет ведущих номеров
    if numbers is None:
        raise ValueError(...)

    # 3) токенизация по ';' с учётом двойных кавычек
    tokens = _split_actions_respecting_quotes(tail, sep=";")

    # 4) старый путь при отсутствии ';': один токен = вся оставшаяся команда
    #    → пропускаем токен через уже существующие классификаторы полей
    specs = []
    for tok in tokens:
        specs.extend(_classify_and_build(numbers, tok, session, today))

    # 5) сортировка по фиксированному порядку полей
    field_order = {"text": 0, "assignee": 1, "deadline": 2, "status": 3, "link": 4}
    specs.sort(key=lambda s: (numbers.index(s.task_id_display_number), field_order[s.field]))
    return specs
```

`_classify_and_build` — новая приватная функция, содержащая ту же регулярную логику, что и текущий `parse_change_command`, но принимающая уже готовые `numbers` и один токен (не всю строку). Ветки «без дедлайна», «дедлайн X», «исполнитель X», «→ X», «текст: "..."», «закрыть/открыть», «ссылка URL [подпись]» — переносятся сюда 1:1.

`_split_actions_respecting_quotes` — простой автомат: идёт по символам, флаг `in_quotes` переключается на `"` (без экранирования), разбивает по `;` только когда `in_quotes == False`.

### §22.3.3 Ошибки и краевые случаи

- Пустой токен между `;;` — игнорируется без ошибки (робастность к опечаткам).
- Незакрытая кавычка в `текст: "..."` без завершающего `"` — `ValueError("незакрытая кавычка в текст:")`, чтобы Сирень не отправила частичную команду.
- Дубликат поля в одной команде (`#3 закрыть; открыть`) — `ValueError("поле status указано дважды: closed, open")`. Не пытаемся угадать намерение.
- Токен, который не парсится ни одной ветвью — `ValueError("не удалось распознать токен: ...")` с указанием проблемного токена (не всей команды).

## §23. Batch-режим и экономия токенов (10.08.2026, v2.2)

**Версия:** v2.1 → v2.2
**Основание:** Саша при работе с 20+ задачами каждую применяет через отдельный `./tr do` — apply (полный preview) + confirm (верификация) + детальный stdout на каждую задачу. На 24 задачи это ~15–20K токенов только на вывод CLI, при том что смысловая нагрузка — 24 однотипных изменения.

### §23.1. Цель

Свернуть N CLI-вызовов (по одному на задачу) в 1 вызов для batch-обработки. Текущий цикл 24 задач = 24× (apply + confirm + verify) = ~15–20K токенов stdout. Цель: 1 вызов batch, ~300–500 токенов stdout. Экономия ~30–40×.

### §23.2. Команда `./tr batch`

Принимает N команд изменений, выполняет один `mine` (если сессия пуста/stale), применяет все изменения, один `confirm` с агрегированной верификацией.

```
./tr batch "<команда1>" "<команда2>" ... "<командаN>"
./tr batch --from-file commands.txt
```

**Механика:**
1. Если сессия пуста/stale — авто-`mine` (как в `do`, см. §22.4.2).
2. Для каждой команды: `parse_change_command(cmd, session)` → накопление specs (НЕ перезапись `pending_apply.json`).
3. Все specs объединяются в один список.
4. Один `apply_changes` на все specs (группировка по `page_id` — один PUT на страницу, как уже делает `apply_changes`).
5. Один `_verify_applied` с агрегированной верификацией.

**Флаги:**
- `--dry-run` — показать preview всех изменений, записать в `pending_apply.json`, НЕ применять. Ждёт последующего `./tr confirm`.
- `--quiet` — подавляет детальный preview каждой команды. Вывод: `batch: N команд, M задач, ok` или `batch: N команд, M задач, K ошибок` (одна строка).
- `--from-file <path>` — читать команды из файла (по одной на строку, пустые строки и `#comments` игнорируются).
- `--no-mine` — не делать авто-`mine`, использовать текущую сессию.

**Поведение по умолчанию (без `--dry-run`):**
- Без `--quiet` (verbose по умолчанию): показать краткий preview каждой команды + агрегированный итог `confirm`.
- С `--quiet`: показать только итог.

### §23.3. Флаг `--quiet` для `do`

Расширить существующую команду `do` (§22.4) флагом `--quiet`:
- `--quiet` → вывод: `do: #N ok` или `do: #N ошибка — <причина>` (одна строка).
- Без `--quiet`: текущее поведение (полный preview + confirm, §22.4.2).

### §23.4. Изменения в `pipeline.py`

**Новая функция `run_batch(commands: list[str], dry_run: bool = False, quiet: bool = False, no_mine: bool = False, verify: bool = True)`:**

1. Авто-`mine` если сессия пуста/stale и `not no_mine`.
2. Для каждой команды в `commands`:
   - `parse_change_command(cmd, session)` → specs.
   - Проверка `<a href>` (как в `run_do`) — если есть, добавить WARN в отчёт, пропустить эту команду.
3. Если `dry_run=True`:
   - Записать все specs в `pending_apply.json` (накопление, не перезапись!).
   - Вернуть форматированный preview всех изменений.
4. Если `dry_run=False`:
   - `apply_changes(all_specs)` — один вызов.
   - `_verify_applied(report)` — одна верификация.
   - Вернуть агрегированный отчёт.

**Изменение `run_apply`:** `pending_apply.json` должен накапливать, а не перезаписывать, если вызывается из batch-контекста. Или: `run_batch` напрямую пишет объединённый список specs (реализатор выбирает подход; ключевое требование — обратная совместимость одиночного `run_apply`, §23.7).

### §23.5. Изменения в `__main__.py`

Новый subparser `batch`:

```
./tr batch "<команда1>" ["<команда2>" ...] [--dry-run] [--quiet] [--from-file PATH] [--no-mine]
```

Добавить `--quiet` флаг в subparser `do`.

### §23.6. Тест-кейсы

1. `batch` с 3 командами на разные задачи — все применены, один `confirm`.
2. `batch` с `--dry-run` — `pending_apply.json` содержит все specs, страница не изменена.
3. `batch` с `--quiet` — вывод содержит только итог.
4. `batch` с задачей содержащей `<a href>` — WARN, эта задача пропущена, остальные применены.
5. `batch` с `--from-file` — команды из файла обработаны корректно.
6. `batch` с пустым списком команд — warning, nothing to do.
7. `do --quiet` — одна строка вывода вместо полного preview.

### §23.7. Что НЕ трогать

- Существующие команды `mine`, `read`, `show`, `apply`, `confirm` — без изменений.
- Формат `pending_apply.json` — обратно совместимый.
- Логика `parse_change_command` — без изменений (§22.3, мульти-полевой синтаксис через `;` продолжает работать как есть).
- `apply_changes` — уже группирует по `page_id`, не менять.
- `_verify_applied` — уже работает на уровне `ApplyReport`, не менять.

### §23.8. Критерии успеха (приёмка v2.2)

- [ ] `./tr batch "#3 закрыть" "#5 дедлайн 10.08"` — обе задачи изменены, один confirm.

## §24. Баг вставки новой задачи в неправильную строку даты (18.08.2026, v2.3)

**Версия:** v2.2 → v2.3
**Обнаружено:** воспроизведено 2026-08-18 при ручной вставке задачи в «Общий список задач» (`pageId=432316254`) по паттерну SKILL «Ручная вставка задачи в task-list Минуток» (прямой Confluence API PUT, без `./tr` — команды вставки новой задачи в коде `./tr` **не существует**, см. §24.5).
**Только ТЗ.** Код `~/USERTOOLS/TaskRefresh/` в рамках этой секции не менялся — ниже зафиксирован root cause и план фикса, реализация — отдельным шагом по команде «берём в работу».

### §24.1. Что произошло

**Ожидалось:** новая задача размещается в строку таблицы с датой постановки — сегодня, `2026-08-18`. Строки на эту дату на странице не было → нужно было создать новую `<tr>` с датой `2026-08-18` и вставить её **перед** строкой `17.08` (правило «новые даты — выше старых», см. раздел SKILL «Ручная вставка задачи в task-list Минуток»), а задачу положить в неё.

**Факт:** задача создалась в существующей строке за **17.08** (ближайшую доступную вниз по документу). Строка `18.08` не была создана вовсе.

### §24.2. Root cause

Скрипт вставки (ad hoc curl+python по паттерну SKILL, шаг 3–4) искал точку вставки так:

```python
idx = body.find('2026-08-18')           # ЛЮБОЕ вхождение подстроки-даты в body
ins = body.find('</ac:task-list>', idx) # ближайший конец task-list ПОСЛЕ этой позиции
```

`body.find('2026-08-18')` вернул **первое** вхождение подстроки «2026-08-18» на всей странице — и это оказался не искомый `<p><time datetime="2026-08-18">` в ячейке-дате строки таблицы, а `<time datetime="2026-08-18">` **внутри `<ac:task-body>` другой задачи** (ADD-622138, «Провалидировать витрины…») — это дедлайн той задачи, синтаксически идентичная подстрока «2026-08-18», но семантически не имеющая никакого отношения к дате-строке.

Найденная позиция физически лежала внутри блока другой, уже существующей задачи → `body.find('</ac:task-list>', idx)` нашёл ближайший `</ac:task-list>` **после неё**, которым оказался конец task-list строки `17.08` (строка `18.08` вообще не рассматривалась, потому что скрипт решил, что «дата найдена» — и остановился на первом совпадении подстроки).

**Ключевая ошибка:** поиск строки-даты вёлся по «голому» вхождению даты в тексте страницы, а не по паттерну **именно ячейки строки таблицы**. Дата встречается на странице минимум в двух ролях — (а) дата-ячейка `<tr><td>` (то, что нужно искать) и (б) дедлайн внутри `<ac:task-body>` любой другой задачи (посторонний контекст) — и обе выглядят как одна и та же подстрока `YYYY-MM-DD` без разметки-маркера роли.

### §24.3. Корректный алгоритм (обязателен для фикса и для любой будущей ручной/кодовой вставки)

1. **Искать дату-строку строго по паттерну ячейки**, не по голому вхождению даты в тексте:
   `<p><time datetime="YYYY-MM-DD"` (первая `<td>` строки `<tr>`, вариант с `/>`/`>` — оба закрытия тега допустимы). Голый `body.find('YYYY-MM-DD')` **запрещён** как способ найти дату-строку — см. питфолл §24.4.
2. Если ячейка с искомой датой **найдена** — точка вставки задачи: `</ac:task-list>` этой же строки (как и раньше), НЕ произвольный ближайший `</ac:task-list>` после случайного вхождения подстроки.
3. Если ячейки с искомой датой **нет** — создать новую строку `<tr>` по standalone-шаблону (SKILL, раздел «Формат standalone-строки») с датой постановки и вставить её:
   - **перед** ближайшей строкой с более старой датой (следуя правилу «новые даты — выше старых»);
   - **после** ближайшей строки с более новой датой, если такая есть выше искомой позиции.
   Для этого нужен полный, упорядоченный по документу список позиций всех дата-строк (`<tr>` → первая `<td>` → `<p><time datetime=...`), а не одна найденная позиция — иначе некорректно определить «ближе к какой дате» вставлять.
4. Задачу размещать **внутри** найденной или созданной строки (её `<ac:task-list>`), не рядом с ней и не в соседней случайно найденной.

### §24.4. Питфолл (зафиксировать в SKILL при реализации фикса)

**НЕ искать дату-строку через `body.find('<голая дата YYYY-MM-DD>')`.** Дата как значение `datetime="..."` встречается на странице протокола в двух несвязанных ролях — ячейка строки таблицы (дата постановки/встречи) и дедлайн внутри `<ac:task-body>` произвольной другой задачи. Обе дают идентичную подстроку. Если страница содержит хотя бы одну задачу с дедлайном на ту же дату, что и искомая дата-строка, — `body.find()` может (и будет) находить дедлайн раньше, чем ячейку строки, если дедлайн физически стоит выше в документе. Это не краевой случай — на практике на многозадачных минутках вероятность совпадения дедлайна одной из задач с сегодняшней датой постановки другой задачи не мала.

### §24.5. Предполагаемый фикс кода (план, НЕ реализован в рамках этой секции)

Ключевое наблюдение: вставка новой задачи сейчас — **не код `./tr`, а разовый ad hoc curl+python-скрипт**, писавшийся руками каждый раз по инструкции SKILL. Правильный фикс — не только исправить логику поиска, но и перенести операцию в тестируемый код инструмента, чтобы класс багов «ручной python-скрипт написан немного иначе в этот раз» не повторялся. Пофайловый план — в отчёте Сирени/координатору (см. ниже), не в этом ТЗ-файле целиком, чтобы не дублировать; здесь фиксируется только обязательный контракт:

- Новая функция поиска дата-строки должна возвращать позицию **ячейки**, а не позицию произвольного вхождения даты.
- Новая функция создания строки должна использовать полный упорядоченный список дата-строк документа для выбора точки вставки, а не одну найденную позицию.
- Обе функции должны быть покрыты юнит-тестом на фикстуре, воспроизводящей ровно этот баг: страница с (а) существующей задачей, чей дедлайн равен искомой дате постановки, физически расположенной ВЫШЕ в документе, чем настоящая дата-строка соответствующей даты (или чем место, где эта дата-строка должна быть создана), и (б) отсутствующей дата-строкой на искомую дату — ожидание: новая строка создаётся в правильном месте, а не рядом с чужим дедлайном.

### §24.6. Критерии успеха фикса

1. На фикстуре из §24.5 — вставка задачи с датой постановки, для которой: а) строки нет, но есть чужой дедлайн с той же датой выше по документу — создаёт новую строку в правильном месте (по правилу «новые выше старых»), не путает с чужим дедлайном.
2. На фикстуре с реально существующей дата-строкой — задача вставляется в неё, независимо от наличия совпадающих по дате дедлайнов других задач на странице.
3. Регресс: все существующие тесты пакета зелёные (112+ на момент v2.2, без снижения).
4. Живая проверка на Confluence: воспроизведение бага 18.08.2026 (пусть на тестовой/копии страницы или через dry-run) — GET после операции показывает новую строку `18.08` с задачей, строка `17.08` не тронута.
5. SKILL.md обновлён — ручная инструкция «Ручная вставка задачи в task-list Минуток» либо (а) заменена ссылкой на новую команду `./tr`, либо (б), если фикс решено оставить ad hoc, минимально исправлена так, чтобы шаг поиска даты явно требовал паттерна ячейки `<p><time datetime="..."`, а не голого `body.find(date)`.

## §27. «Всё в одном» для `./tr new`: срок и ссылки из строки постановки (09.09.2026, v2.4.2)

**Версия:** v2.4.2
**Основание:** бриф-решение «вариант 3» — одна постановка строкой, инструмент сам разбирает составные (срок + ссылки).
**Смещение §25.1:** утверждение «`./tr new` — только plain text, ссылок не умеет» снимается этой секцией. `apply "#N ссылка …"` / §25 остаются для уже существующих задач.
**Не ломает:** `--deadline` + `normalize_deadline` (§26), `--assignee`, `--date` (дата-строка таблицы, §24), `--page`/`--page-id`, `--project` (если есть в CLI). Новых флагов нет.

### §27.1. Цель

`./tr new` принимает одну строку постановки и сам извлекает из неё дедлайн (если в тексте есть дата) и ссылки (URL → в тело задачи тем же механизмом, что `apply … ссылка` / §25). Явные флаги `--deadline` / `--assignee` / `--date` сохраняют текущую семантику и имеют приоритет там, где пересекаются с текстом. Итог: не нужен второй шаг `apply "#N ссылка …"` после создания задачи.

### §27.2. Синтаксис CLI

Флаги `new` **не расширяются и не переименовываются**. Строка постановки — существующий позиционный аргумент `text` (`./tr new "..."`).

```
./tr new TEXT --page-id PAGE_ID [--assignee FIO] [--deadline DATE] [--date DATE]
```

`--project` в `new` не существует и не добавляется. Из строки постановки проект **не парсится** (префикс `<Проект>. ` по-прежнему часть текста, как в SKILL).

| Флаг | Семантика (без изменений) | Парсинг из строки постановки |
|---|---|---|
| `--page-id` | страница-источник | нет |
| `text` (позиционный) | строка постановки (единственный новый источник разбора) | да: дата + URL |
| `--assignee` | исполнитель (резолв как сейчас) | **нет** (эта итерация) |
| `--deadline` | явный дедлайн; через `normalize_deadline` (§26) | перекрывает дату из строки |
| `--date` | дата-строка таблицы (постановка задачи), default = сегодня | **нет** — дата из строки ≠ `--date` |

Парсинг строки выполняется в `write_ops.insert_new_task` (choke-point), не в argparse / `_cmd_new`. `_cmd_new` по-прежнему передаёт сырой `text` + флаги.

### §27.3. Парсинг строки постановки

Формат (всё в одной строке, порядок свободный):

```
[префикс проекта.] <текст> [<дата>] [<URL> …]
```

Пример: `Trisigma. Обсудить AB 14.09 https://hq.tutu.ru/browse/ADD-1 https://loop.tutu.ru/x`

**Шаг A — URL.** Из исходной строки извлечь все вхождения `http://` / `https://` (без схемы `www.` не считать URL). Хвост пунктуации `.,;:!? )]` в URL не входит. Порядок списка = порядок в тексте. Извлечённые URL **удаляются** из видимого текста (они станут элементами тела, не голой подстрокой).

**Шаг B — дата → дедлайн.** По оставшемуся тексту найти первое вхождение даты теми же календарными форматами, что `parse_first_td_date` в `date_parse.py`: `YYYY-MM-DD`, `DD.MM.YYYY`, `DD.MM.YY`, `DD.MM` (год = `today.year`), русские месяцы (`10 июля 2026`). Токены CLI `+Nд` / `today` / «без дедлайна» **в строке постановки не распознаются** — только через флаг `--deadline` и `normalize_deadline`. Несколько дат: берётся **первая** слева направо; она потребляется (токен удаляется из видимого текста). Остальные дата-подобные подстроки остаются текстом. Если дата из строки пошла в дедлайн — прогнать через `normalize_deadline(value, today)` (как `--deadline`).

**Шаг C — видимый текст.** Остаток после A+B: trim, схлопнуть повторные пробелы. Пустой остаток допустим, если есть хотя бы один URL и/или дедлайн (тело = ссылки ± `<time>`).

**Приоритет дедлайна (жёстко):**

1. Флаг `--deadline` (если передан) — `normalize_deadline`; дата в строке **не потребляется** (остаётся видимым текстом). Если `--deadline` передан — Шаг B **не выполняется** (дата в строке не ищется и не вырезается).
2. Иначе дата из строки постановки (шаг B) — становится дедлайном задачи (`<time datetime="YYYY-MM-DD"/>`).
3. Иначе дедлайна нет (как сейчас при `new` без `--deadline`). **Не подставлять сегодня как дедлайн.**

**Дата постановки (строка таблицы) не смешивается с дедлайном.** `--date` / default «сегодня» — это ячейка `<p><time datetime="YYYY-MM-DD"` (§24). Дата из `--text` **не** меняет `--date` и **не** выбирает строку таблицы. Поиск строки — по паттерну ячейки, не по голому `body.find(date)`.

**Исполнитель:** только `--assignee`. ФИО/логин в строке постановки не парсятся.

**Ссылки:** все URL из шага A передаются списком в сборку тела (это и есть «всё в одном»). Автодетект JIRA — не здесь, а в существующем `_is_jira_url` / `_append_link_or_jira` (§25): `^https://hq\.tutu\.ru/browse/([A-Za-z]+-\d+)$` → `ac:structured-macro ac:name="jira"` (key=group(1), `JIRA_SERVER_NAME` / `JIRA_SERVER_ID` из `config.py`); любой иной URL → `<a href>`. Подпись не парсится; label не-JIRA = дефолт `rebuild_task_block` (`"(ссылка)"`).

**Краевые случаи:**

- Нет даты и нет URL → поведение как до §27 (plain text, `--deadline`/`--assignee`/`--date` как сейчас).
- `--deadline` нераспознан → `insert_new_task` rejected **без PUT** (§26), даже если в строке есть своя дата (явный флаг сломан — не молчать и не падать на дату из строки).
- URL внутри JIRA-паттерна с хвостом (`/browse/ADD-1/extra`, query) → не JIRA-макрос, обычный `<a href>` (как `_is_jira_url` сейчас).

### §27.4. Изменения кода

Reuse-first: **не** дублировать макросы/href. Новая логика — только разбор строки постановки и прокидка списка URL. Константы JIRA, regex, lxml-сборка макроса — существующие.

- **`date_parse.py`:** разбор даты из постановки — через уже существующие `parse_first_td_date` / `normalize_deadline`. Не плодить третий парсер форматов. Тонкая обёртка возвращает `(date, start, end)`: `date` — распознанная дата, `start`/`end` — span **того же** regex-матча, которым дата найдена. Вырезание — по span, `visible = text[:start] + text[end:]`. **Не** `str.replace(token, '', 1)` (риск срезать не тот фрагмент). Форматы 1-в-1 как у `parse_first_td_date`.
- **Извлечение URL:** отдельный маленький helper (рядом с choke-point, не копия §25). На выходе `list[str]` в порядке текста. Тип макроса/href **не** решать здесь.
- **`write_ops.insert_new_task`:**
  1. Разобрать исходный `text` (сырой позиционный аргумент CLI, **до** применения префикса unresolved-assignee) → `(visible_text, urls, date_from_text)`.
  2. Резолв дедлайна по приоритету §27.3; затем существующая ранняя валидация `normalize_deadline` (rejected без PUT).
  3. Резолв `--assignee` как сейчас. При неудачном резолве префикс `f"{display} {text}"` применяется к **уже разобранному** `visible_text` (`visible_text = f"{display} {visible_text}".strip()`), не к исходной строке: дата и URL уже извлечены, `display` в разбор не попадает.
  4. Вызов `build_new_task_block(..., deadline=…, append_link_urls=urls или None)` с этим `visible_text`.
  5. Retry при 409: те же исходные `text` / `assignee_raw` / `deadline` (как сейчас); список URL вычислять заново из исходного `text`, не из уже вырезанной строки.
  6. Сигнатура: добавить `append_link_urls` **не обязательно публично**, если список считается внутри из `text`. Внешним контрактом остаётся сырой `text`. Не тащить разбор в `__main__.py`.
- **`task_block.build_new_task_block`:** добавить `append_link_urls: list[str] | None = None` (тот же контракт, что у `rebuild_task_block`). После mention/текста вставить каждый URL через **существующий** `_append_link_or_jira(body_el, url, label)` — до `<time>` ( `_insert_element_before_time` уже это делает). Порядок вызовов (ссылки до или после вставки `<time>`) **не важен**: существующий `_insert_element_before_time` находит `<time>` на любой глубине или добавляет элемент в конец. Не копировать `_is_jira_url` / `_build_jira_macro_element`. Не собирать макрос f-string. `JIRA_SERVER_NAME` / `JIRA_SERVER_ID` — только из `config.py` (уже используются в `task_block.py`).
- **`rebuild_task_block`:** не менять поведение `append_link_urls`. Если удобнее — `build_new_task_block` может собрать блок без ссылок и прогнать через `rebuild_task_block(..., append_link_urls=...)`; оба пути допустимы, дублировать вставку — нет.
- **`__main__.py` `_cmd_new`:** без новых аргументов; по-прежнему `insert_new_task(..., text, assignee_raw, deadline)`.
- **SKILL `taskrefresh`:** снять «`./tr new` НЕ добавляет ссылки»; описать однопроходный разбор (дата → дедлайн, URL → макрос/`<a href>`), приоритет `--deadline`, что `--date` ≠ дедлайн из строки. Чеклист: создание с URL в `--text` больше не требует отдельного `apply "#N ссылка"`.

### §27.5. Тест-кейсы

Юниты на разбор строки + `build_new_task_block` / `insert_new_task` (фикстура storage, без живого PUT кроме smoke). `today` фиксировать.

1. **Дата в строке → дедлайн, строка таблицы не из даты.** `--text "Сделать X 14.09"` без `--deadline` без `--date` → `<time datetime>` = `YYYY-09-14` (год=`today`), дата-строка вставки = сегодня. Не искать строку таблицы по `14.09`.
2. **ISO в строке.** `--text "Сделать X 2026-09-14"` → дедлайн `2026-09-14`.
3. **`--deadline` > дата из строки.** `--text "Сделать X 14.09" --deadline 20.09` → дедлайн с `20.09`; токен `14.09` остаётся в видимом тексте.
4. **Нет даты, нет `--deadline`.** Дедлайна нет; `--date` default = сегодня. Не писать `<time datetime="{today}">` «за компанию».
5. **JIRA URL.** `--text "Разбор https://hq.tutu.ru/browse/ADD-1"` → ровно один `ac:structured-macro ac:name="jira"` с key=ADD-1; в видимом тексте нет голого URL; нет `<a href="https://hq.tutu.ru/browse/`.
6. **Не-JIRA URL.** loop/любой иной → `<a href>` через `_append_link_or_jira`, не макрос.
7. **Смешанный список, порядок.** JIRA + loop в одной строке → макрос затем `<a href>` (порядок как в тексте), как `rebuild_task_block(..., append_link_urls=...)`.
8. **Дата + ссылки в одной строке («всё в одном»).** `--text "Trisigma. Обсудить 14.09 https://hq.tutu.ru/browse/ADD-1 https://loop.tutu.ru/x"` без `--deadline` → дедлайн с `14.09`, два элемента ссылок, префикс/текст сохранены, URL из текста вырезаны.
9. **`--assignee` жив.** `--assignee` + строка с датой и URL → mention как сейчас, плюс дедлайн/ссылки из строки.
10. **Регресс §26.** `--deadline 99.99` → `insert_new_task` status=`rejected`, PUT не было; дата в `--text` не спасает.
11. **Регресс §24.** Дата в `--text` не меняет выбор `<tr>`: вставка по `--date` / сегодня, паттерн ячейки `<p><time datetime="YYYY-MM-DD"`.
12. **Регресс §25 `apply`.** Существующие тесты `append_link_urls` / `_is_jira_url` зелёные без правок контракта.
13. **`--deadline` + URL без даты в тексте.** Ссылки из строки вставляются, дедлайн только из флага.
14. **Unresolved-assignee + дата/URL в строке.** `--assignee <нерезолвленное ФИО>` + `--text "X 14.09 https://loop.tutu.ru/y"` → дедлайн и ссылка извлечены из исходного `text`; видимый текст = `"<display> " + visible_text` (без даты и URL).
