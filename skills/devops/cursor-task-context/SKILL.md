# cursor-task-context

## Когда использовать
Любая передача задачи разработки в Cursor (новый инструмент, доработка, багфикс), где есть ТЗ с накопленной историей постановки. Решает две проблемы: раздутый контекст при передаче всех связанных ТЗ + отсутствие единой карты экосистемы.

## Проблема (факты)
- ТЗ-файлы — это **накопительная история постановки** (фича, не баг; НЕ редактируется и НЕ ужимается на диске).
- ТЗ растут неограниченно: `ProtocolFromSummary_TZ.md` = **271 КБ ≈ 90К токенов**; задача с 2–3 зависимостями → ~200К токенов до первой строки плана.
- Перед оценкой контекста — **измерить фактический размер**: `wc -c TZ/<Tool>/<Tool>_TZ.md`, не верить предположениям.

## Карта экосистемы (digest)
Единый машиночитаемый манифест `WorkVault/Registries/EcosystemManifest.json` (JSON, не YAML — stdlib json у потребителей, паттерн как `entities.json`):
- `tools{}` — инструменты (usertool / hermes_skill / infra_service): name, category, status, path, tz_ref, purpose, owner.
- `entities{}` — сущности единым типом с полем `kind` (folder/file/json_registry/table/api): path, purpose, source_of_truth, owner_tool, lifecycle.
- `links[]` — граф «кто читает/пишет/дублирует кого».
- `conflicts[]` — живой реестр открытых противоречий/дублей.
Запись `entities.json` НЕ переписывается — включается одной записью `entities[kind=json_registry]` (манифест индексирует, не заменяет).

Компактный рендер `EcosystemManifest.digest.md` (~300–800 токенов) — «карта местности», всегда подаётся в Cursor; `render.md` — полный, для человека (печать/просмотр).

## 3-слойная подача контекста в Cursor

Контекст подаётся через **`emit-prompt`** (тройка **abs-путей** digest+GLOSSARY+ТЗ в `/tmp/task.md`), **не копированием** файлов digest/GLOSSARY/ТЗ в промпт и не созданием `*.extract.md` рядом с `--out`. Перед любым `agent -p` по инструменту: `pipeline_context_bundle.py check` (маркер `context-bundle:` на карточке) → `emit-prompt` (exit 0) → только then `agent -p "$(cat /tmp/task.md)"`. Обхода context-bundle нет — скрипт `check`/`emit-prompt` блокируют старт всегда; `flag-waived` и `--force` не являются обходом тройки (решение Саши 26.09).

0. **digest** экосистемы + **GLOSSARY** (`~/WorkVault/Hermes-Backlog/TZ/GLOSSARY.md`) — всегда первым слоем (в промпте — abs-пути из `emit-prompt`, агент читает с диска).
1. **сжатый экстракт** ТЗ своего + зависимых (не весь ТЗ; текст экстракта из comment `TZ:compress` вставляет `emit-prompt`, не отдельный файл-копия).
2. **полный текст** ТЗ — только по явному запросу, точечно (тоже через путь в бандле, не вставкой целиком вручную).

> **ЖЁСТКОЕ правило (требование Саши): полная документация передаётся при КАЖДОЙ**
> разработке/доработке/починке инструмента — не отдавать архитектору/воркеру краткий
> контекст «текст бага + пара фактов» вместо бандла. Сборка обязательна:**digest,
> GLOSSARY, сжатые ТЗ инструмента И его смежников (по `EcosystemManifest.links[]`),
> для PFS — ещё реестр протоколов `_registry.json`**. Пропуск празднечно превращает
> багфикс в разбор по живым данным без мастер-ТЗ и карты экосистемы (это и был гэп,
> унёсший баг в off-track). Делать непередачу невозможной: бандл собирается *до*
> старта воркера и фиксируется в body карточки BUG:diagnose / промпта; наличие маркера
> сборки проверяется перед каждым `agent -p` через `check` + `emit-prompt` (см. выше).
>
> **Два уточнения Саши (правило без исключений; обхода тройки нет):**
> 1. *Только нужные ТЗ.* В бандл включать только релевантные инструменту ТЗ, не тянуть
>    весь пул смежников вслепую — лишние нерелевантные ТЗ раздувают контекст и шумят.
> 2. *Явно перечислять вход.* В карточке/промпте перечислять входящие ТЗ списком, чтобы
>    Саша мог видеть, что именно вошло в контекст задачи. Это отдельный пункт AC/теста.

**Питфолл серфинга по живому во время багфикса:** не заменяй чтение мастер-ТЗ чтением
живых данных (страницы, реестр, код) — воркер, начавший с живых данных без ТЗ, лезет
в главе promote/ingest и теряет экосистемный контекст. Сначала бандл (ТЗ + digest),
затем живые данные для подтверждения.

## Чеклист воркера (DevKanbanPipeline)

**Первый шаг** любого канбан-воркера с ТЗ — перечитать с диска `version` (YAML-frontmatter) и `mtime` (`st_mtime` ISO UTC) мастер-файла `TZ/<Tool>/<Tool>_TZ.md`:

1. `kanban_show()` — карточка ещё running?
2. Если в body/metadata есть `tz_path` — `stat` + парсинг `version:` с диска.
3. Сверить с `tz_version`/`tz_mtime` на карточке.
4. Расхождение → `kanban_comment` «TZ drift: disk version=… mtime=… card version=… mtime=…» + `kanban_block(kind=dependency, reason="TZ master changed on disk")`.
5. Экстракты компрессора — **без кэша на диск**; каждый воркер сжимает заново (tz-compressor-prompt.md).
6. Только после сверки — `cd $HERMES_KANBAN_WORKSPACE` и работа шага.

## Промпт-компрессор ТЗ (full-coverage)
Файл `WorkVault/Registries/tz-compressor-prompt.md`, модель **`composer-2.5`** (канон GLOSSARY §3). Превращает полное ТЗ → «актуальную спецификацию» (~3–5КБ) с гарантией полноты.

**Жёсткие требования компрессора (согласовано с Сашей):**
- **full-coverage:** не потерять НИ одной сущности/таблицы/поля/связи/API. Имена **дословно** (`ROUTES` остаётся `ROUTES`). Сжимать только нарратив/историю/дубли, НЕ данные.
- **Сжатие ДЛЯ LLM, не для человека:** структурированный машинно-анализируемый вывод (таблицы/списки/схемы), чтобы ЛЮБАЯ LLM, прочитав экстракт, увидела ВСЕ возможности системы.
- **Симметрия фича/багфикс:** компрессор НЕ затачивается под конкретную задачу — всегда отдаёт полный инвентарь возможностей (иначе при багфиксе потеряются сущности).
- Не модифицировать исходный ТЗ никогда.

## Выбор модели для сжатия
- Перед выбором — **перечислить фактические модели**: `agent --list-models`.
- Канон (GLOSSARY §3, инвариант 31.08): компрессор = **`composer-2.5`**. Не `gemini-3.6-flash-*`.

## Предпочтения Саши (обязательно при проектировании любых скиллов/схем)
1. **НЕ плодить standalone-скиллы, которые Саша должен запускать вручную** — он их забудет. Триггеры встраивать в существующие скиллы (`hermes-feature`, `tz-workflow`) как обязательный шаг/чеклист, срабатывающий автоматически.
2. **ТЗ не «ужимать» на месте и не разбивать** — оно есть накопительная история. Менять только то, что подаётся в Cursor (компрессия на handoff).
3. **Избегать кэша производных файлов без явной необходимости** — поддержка актуальности кэша дороже лишнего перепрохода компрессии.
4. Дрейф/устаревание ловится **автоматически в точке изменения** (check-point при передаче в Cursor), а не ручным запуском. Еженедельный крон — только страховка.

## Оркестрация разных моделей: один вызов Cursor = одна модель
Нельзя дать одну задачу Cursor с двумя разными моделями внутри. **Сирень запускает отдельные последовательные вызовы**, каждый на своей модели (GLOSSARY §3):
1. **Сжатие** → `composer-2.5` с `tz-compressor-prompt`.
2. **ТЗ/план** → `cursor-grok-4.6-high` (архитектор).
3. **Ревизия (опц.)** → `claude-sonnet-5-medium` (`REV:tz` / `REV:plan`).
4. **Реализация** → `composer-2.5`, в промпт вложены digest + GLOSSARY + экстракты.
5. **Тестирование** → `composer-2.5` (исполнитель/контроль).

## Питфоллы
- **Промпт Cursor/субагента всегда самодостаточен.** `agent -p` и крон-субагент НЕ наследуют историю чата Сирени — «см. ТЗ/план в истории диалога» физически недоступно. Передавай ПОЛНЫЙ текст ТЗ, плана и согласованных ответов прямо в промпт (или `-p "$(cat /tmp/...)"`).
- Не передавать «весь текст связанных ТЗ как контекст» — прямой источник раздувания.
- Не зашивать в промпт-компрессор список моделей по памяти — модели меняются, проверять `--list-models` (у ревьюера может быть иной/сокращённый список — сверяться с фактом на ВМ).
- Не путать `tools{}` манифеста(софт-компоненты экосистемы) с `kind=tool` внутри `entities.json` (бизнес-инструменты на встречах) — разные понятия.

## Handoff из переписки за день

Команды «отдай переписку за сегодня в курсор на доработку ТЗ» / «отдавай
все кейсы в курсор архитектору»: Сирень сама собирает самодостаточный промпт
из фактической переписки сессии — state.db → conversation-файл → склейка с брифом →
архитектор фоном через Cursoroflight. Схема `messages`(НЕ `created_at`, а `timestamp REAL`],
фильтр фонового шума, и pitfall про верификацию правок архитектора на диске —
полный рецепт: `references/conversation-handoff.md`。
