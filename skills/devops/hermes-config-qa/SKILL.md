# Hermes Config QA — финальная проверка перед сообщением о готовности

Обязательный процесс для **любых задач**: настройка конфига, подключение скиллов/агентов, разработка нового функционала. Запускается **до** того, как сообщить пользователю о готовности.

## Когда применять

- Изменения в `config.yaml` (модели, delegation, fallback, gateway и т.д.)
- Подключение или отключение скиллов
- Настройка нового агента или интеграции
- Разработка нового Python-инструмента / скрипта
- Финализация ТЗ перед передачей в разработку
- Любое «готово» сообщение по задаче с 3+ изменениями

## Процесс (4 шага)

### Шаг 1 — Собрать чек-лист через Opus

Делегировать `delegate_task` на `claude-opus-4-7` с задачей:
1. Проверить корректность всех изменений
2. Выявить **смежный функционал**, который мог быть затронут
3. Найти логические противоречия (особенно между памятью и конфигом)
4. Вернуть: чек-лист ✅/❌ + список проблем с рекомендациями

Пример промпта для Opus:
```
Ты QA-инженер. Проверь конфигурацию по чек-листу.

ИЗМЕНЕНИЯ:
[перечислить что изменилось]

ТЕКУЩИЙ КОНФИГ (релевантные секции):
[вставить конфиг]

ПРАВИЛА ИЗ ПАМЯТИ:
[вставить актуальные правила]

Проверь:
A. Корректность каждого изменения
B. Смежный функционал (что ещё могло сломаться)
C. Логические противоречия между памятью и конфигом
D. Достаточность таймаутов и лимитов для новых моделей

Верни: чек-лист ✅/❌ и список проблем с рекомендациями.
```

### Шаг 2 — Исправить найденные ошибки

Для каждой ❌ в чек-листе:
- Применить рекомендованное исправление
- Обновить память если правила противоречат конфигу
- Обновить конфиг если настройки неоптимальны

### Шаг 3 — Повторить (макс. 3 попытки)

Если после исправлений остались ❌ — повторить шаги 1-2.  
Максимум **3 попытки исправления**.

### Шаг 4 — Откат или доклад

**Если все ✅:** сообщить пользователю о готовности с кратким отчётом.

**Если после 3 попыток остались ❌:**
1. Откатить изменения к рабочей версии (см. ниже)
2. Дать отчёт об ошибках: что не удалось исправить и почему

## Откат конфигурации

```bash
# Посмотреть историю изменений конфига
hermes config edit  # открывает файл, можно вернуть вручную

# Или восстановить конкретные значения
hermes config set delegation.model <старое значение>
hermes config set delegation.provider <старое значение>
hermes config set fallback_providers '[]'
```

## Типичные проблемы при проверке Hermes конфига

### Профили Hermes при клонировании
- `--clone` копирует весь config.yaml включая `delegation.reasoning_effort`, `child_timeout`, `fallback_providers`
- Проверять что клонированный профиль не унаследовал несовместимые настройки (например `reasoning_effort=high` для exo)
- `model.api_key` в блоке `model:` обязателен для custom provider (даже `dummy`) — иначе openai SDK падает до запроса
- `auxiliary.*` секции клонируются тоже — если в основном конфиге они на Qwen, профиль унаследует то же. Синхронизировать вручную если нужно другое поведение

### Логические противоречия память vs конфиг
- Память содержит правило про модель X, но `delegation.model` указывает на Y
- Правила delegation в памяти неисполняемы автоматически — это инструкции для основной модели
- **Решение:** переформулировать правило памяти как поведение Sonnet, а не как ожидание автомагии конфига

### Таймауты и лимиты
- `child_timeout_seconds = 600` — мало для Opus с reasoning (рекомендуется 1200)
- `reasoning_effort` пустой для Opus — лучше явно задать `high`

### reasoning_effort на custom/exo провайдерах
- При клонировании профиля (`--clone`) наследуется `delegation.reasoning_effort: high` от default-профиля
- exo/MLX серверы **не поддерживают** параметр `reasoning_effort` — запросы падают с 400
- **Обязательно** очищать при создании профилей с custom provider:
  ```bash
  hermes -p <profile> config set delegation.reasoning_effort ""
  hermes -p <profile> config set agent.reasoning_effort ""
  ```

### Per-task модель в delegate_task
- `delegate_task` **не поддерживает** per-task model/provider (проверено в коде, строка 2066 delegate_tool.py)
- Модель всегда берётся из `delegation.model` в config
- Маршрутизация «разные модели для разных задач» — только через поведение основной модели или через профили

### Маршрутизация по профилям (правильный паттерн)

Для разных моделей на разных задачах — создавать изолированные профили:

```bash
hermes profile create qwen-fast --clone --description "Быстрые задачи на Qwen"
hermes -p qwen-fast config set model.default "mlx-community/Qwen3.6-35B-A3B-8bit"
hermes -p qwen-fast config set model.provider custom
hermes -p qwen-fast config set model.base_url "http://10.8.4.100:52415/v1"
hermes -p qwen-fast config set model.api_key "dummy"        # обязателен для custom
hermes -p qwen-fast config set delegation.reasoning_effort ""   # exo не поддерживает
hermes -p qwen-fast config set agent.reasoning_effort ""
```

Вызов из основной сессии:
```python
terminal(command="hermes -p qwen-fast chat -q 'задача'", timeout=120)
```

**Текущие профили пользователя (tkachenkoav):**
- `default` — Sonnet основная + Opus для delegation (исследования/разработка)
- `qwen-fast` — Qwen3.6-35B на http://10.8.4.100:52415/v1 (простые/быстрые задачи)
- `haiku-fallback` — claude-haiku-4-5 (средние задачи, fallback при недоступности Qwen)

**Auxiliary модели:**
- `auxiliary.session_search` → Qwen (экономия токенов)
- `auxiliary.compression` → Haiku (надёжность, не зависит от корп. сервера)

### Fallback providers
- Формат: список объектов `[{"model": "...", "provider": "..."}]`
- Срабатывает при connection error, не при плохом ответе модели

### Cron-задачи
- Удалить устаревшие cron-задачи которые конфликтуют с новой логикой
- Проверить что не осталось старых скриптов авто-переключения

## Формат финального отчёта пользователю

```
✅ Готово. Результаты проверки:

Чек-лист:
- delegation.model: claude-opus-4-7 ✅
- fallback_providers: haiku ✅
- base_url очищен ✅
- cron удалён ✅
- Память согласована с конфигом ✅
- child_timeout: 1200с ✅

Исправлено в ходе проверки:
- child_timeout поднят 600 → 1200 (мало для Opus)
- reasoning_effort задан high
- Правило Qwen переформулировано (было противоречие с delegation)
```

## QA технического задания перед разработкой

Когда ТЗ финализировано и пользователь хочет передать в разработку — делегировать Opus проверку ТЗ.

### Промпт для Opus (ТЗ-проверка)

```
Ты — senior технический аналитик. Прочитай файлы ТЗ и выполни финальную проверку.

ФАЙЛЫ:
[список файлов]

РЕАЛЬНЫЕ ДАННЫЕ (если есть — вставить верифицированную схему API, ответы брифа, решения):
[данные]

ЗАДАЧА:
Ответь ТОЛЬКО одним из двух вариантов:

ВАРИАНТ А — если всё OK:
"✅ ТЗ готово к разработке. [краткий список что проверено]"

ВАРИАНТ Б — если есть вопросы/проблемы:
"❌ Требуются уточнения: [конкретный список вопросов/противоречий]"

Будь краток. На русском языке.
```

### Типичные проблемы в ТЗ

- **Противоречия между файлами**: основное ТЗ и аддендум говорят разное об одном поле
- **Неотражённые реальные данные**: схема API верифицирована, но ТЗ описывает предполагаемые поля
- **Platform-specific артефакты**: `.bat`-скрипты и жёсткие Windows-пути при планируемом переезде на Linux
- **Неполный алгоритм для edge cases**: ошибка одной записи из пачки — что происходит с остальными?
- **Смешение периодических и регулярных задач**: проверка deleted (раз в месяц) должна быть отдельным CLI-режимом, не частью штатного cron
- **Несогласованные enum-значения**: бриф упоминает статус `restored`, но enum в ТЗ его не содержит

**Симптом:** субагент с `toolset=["web"]` формально вызывает `web_search` (tool_trace непустой, api_calls>0), но возвращает правдоподобные вымышленные URL и данные без реальных результатов.

**Причина:** тулсет `web` зарегистрирован и виден модели, но ни один поисковый провайдер не сконфигурирован. Модель компенсирует отсутствие реального backend галлюцинациями.

**Диагностика:**
```bash
hermes config show  # проверить Exa/Tavily/Firecrawl/Parallel — все "not set"?
grep -i "EXA_API_KEY\|TAVILY_API_KEY\|SERPER_API_KEY" ~/.hermes/.env
```

**Фикс:** добавить хотя бы один поисковый API-ключ:
```bash
# Tavily — бесплатно 1000 req/мес, https://tavily.com
echo "TAVILY_API_KEY=tvly-..." >> ~/.hermes/.env
# Перезапустить gateway чтобы подхватить .env
```

**Верификация через curl:**
```bash
curl -s -X POST https://api.tavily.com/search \
  -H "Content-Type: application/json" \
  -d '{"api_key":"<key>","query":"test","max_results":2}' | python -c "import sys,json; [print(r['url']) for r in json.load(sys.stdin).get('results',[])]"
```

## Pitfalls

- **Не делегировать QA на Qwen** — только Opus для финальной проверки
- **Не сообщать о готовности до завершения QA** — даже если кажется что всё ок
- **Память ≠ конфиг**: правила в памяти не исполняются автоматически, это инструкции для модели
- **После исправлений перепроверить смежный функционал** — одно исправление может сломать другое
