# Confluence task extraction pattern (CQL + tasks-report-macro)

Применять при: нужно прочитать/агрегировать `<ac:task>` с нескольких страниц Confluence по
исполнителю/метке/проекту — не только на страницах, которыми уже управляет какой-то конкретный
инструмент (прецедент: TaskRefresh, найдено 13.07.2026 при анализе плагин-страницы OpenTasks
`~tkachenkoav`, pageId 492610494).

## Проверенные факты (реальные API-запросы к dom.tutu.ru, 13.07.2026)

- Страницы вида «мои открытые задачи» на Confluence Server реализованы нативным макросом
  **`tasks-report-macro`** (Confluence Server Reporting Plugin) — **не Jira-плагином**. Параметры
  в storage:
  - `ac:parameter ac:name="spaces"` — ключи пространств через запятую (`DPAN,~username`).
  - `ac:parameter ac:name="assignees"` — один/несколько `<ri:user ri:userkey="..."/>`.
  - `ac:parameter ac:name="labels"` — метка-фильтр (в этом проекте конвенция — `_aid`).
  - `ac:parameter ac:name="status"` — опционально `complete`; без параметра наблюдалось только
    `incomplete` (это **наблюдение, не подтверждено документацией плагина** — перед тем как
    закладывать как архитектурное допущение нового инструмента, стоит явный живой тест:
    создать в песочнице задачу со статусом complete, посмотреть рендер без параметра `status`).
  Макрос агрегирует **на лету** — ничего не хранится как текст на самой странице. Значит нельзя
  «распарсить таблицу» напрямую — нужно воспроизвести ту же логику агрегации отдельно.

- **CQL реально находит тот же набор источников, что сканирует макрос:**
  ```
  GET /rest/api/content/search?cql=label="<label>" AND space in (<space1>,<space2>,...)
  ```
  Пример (этот проект): `label="_aid" AND space in (DPAN,PMO,analytics,DATA,"~tkachenkoav")` →
  35 страниц одним запросом, без пагинации (`size` совпал с `_links` без `next`).

- **Формат задачи в storage** (тот же, что использует `ProtocolFromSummary` для записи):
  ```xml
  <ac:task>
    <ac:task-id>N</ac:task-id>
    <ac:task-status>incomplete|complete</ac:task-status>
    <ac:task-body>[<ac:link><ri:user ri:userkey="..."/></ac:link>] текст [<time datetime="YYYY-MM-DD"/>]</ac:task-body>
  </ac:task>
  ```
  `ac:task-id` **локален для страницы** — не считать глобально уникальным между страницами.

## Проверенный алгоритм извлечения (35 страниц / 700 задач за ~3 секунды)

1. CQL-поиск (см. выше) → список pageId.
2. Для каждой страницы: `GET /rest/api/content/{id}?expand=body.storage,title`.
3. Найти все блоки `<ac:task>...</ac:task>` — нежадный regex работал на практике для READ;
   для WRITE-операций (точечная правка одной задачи) надёжнее XML-парсер (`lxml`) для разбора +
   точечный `string.replace()` именно найденного блока `<ac:task>...</ac:task>` на новый — это
   гарантирует, что остальной storage страницы не переформатируется побайтно.
4. Фильтр по вхождению нужного `ri:userkey` внутри блока (assignee).
5. Извлечь `ac:task-status`, дедлайн (`<time datetime>` внутри task-body), очищенный от тегов
   текст (`re.sub(r'<[^>]+>', ' ', body)` + `html.unescape` + схлопнуть пробелы).

## Питфолл (закрыт 13.07.2026)

«Макрос без `status` показывает только incomplete» — изначально считалось наблюдением по одному
прогону, требующим отдельного теста на песочнице. **Закрыто без искусственного теста**: владелец
страницы подтвердил реальным годовым использованием (скриншот вкладки DONE с явным
`status=complete`, показывающей совсем другой набор задач с чекбоксами и датами из истории) — это
не разовое наблюдение, а стабильное поведение, которым пользуются постоянно. Если аналогичное
допущение о поведении внешнего плагина всплывёт в другом проекте — сначала спросить, пользуется
ли владелец страницы этим фильтром на практике (может закрыть вопрос без искусственного теста
быстрее, чем 15-минутный эксперимент), и только если ответа из практики нет — тестировать реально.

## Архитектурные решения брифа TaskRefresh (13.07.2026) — переиспользовать для похожих READ+WRITE
## инструментов над Confluence `<ac:task>`

Полный бриф ТЗ прошёл через несколько раундов вопрос-по-одному (см. `pm-briefing`). Ключевые
решения, обобщаемые на любой будущий инструмент того же класса (агрегация + точечное
редактирование задач/строк на множестве Confluence-страниц):

- **Скоуп страниц — живой, не статичный whitelist.** Не хранить список pageId в конфиге; каждый
  прогон заново ищет через CQL (`label="..." AND ...`, без ограничения по space, если требуется
  максимальная автоматичность). Страницы естественно появляются/архивируются во времени — жёсткий
  список пришлось бы поддерживать руками, живой CQL-запрос — нет.
- **WRITE разрешён на любой найденной странице** без отдельных архитектурных исключений
  (например «не трогать общий список задач») — единственная защита — процедурное подтверждение
  перед применением (см. Pitfall 45), не структурный whitelist/blacklist.
- **Ключ для точечной правки конкретной задачи — простой `ac:task-id`, без anchor-миграции**,
  если реальный рабочий процесс — синхронный диалог «покажи список → пользователь называет
  один элемент → правка сразу применяется» (не отложенный batch с риском, что задача изменится
  между показом и правкой). Anchor-механизм (по аналогии с `row_anchor` ProtocolFromSummary)
  оправдан только когда между READ и WRITE может пройти значительное время/действие третьей
  стороны — для синхронного бри­фа это оверинжиниринг.
- **Парсер: XML (`lxml`) для чтения структуры, точечный `string.replace()` всего блока
  `<ac:task>...</ac:task>` целиком для записи** — даже когда меняются multiple подполя сразу
  (и дата, и исполнитель) — не точечный regex на подстроку внутри тега. Пересобрать блок целиком
  через XML, затем одна строковая замена старого блока на новый в общем storage_html.
- **Формат вывода списка — группировка по смысловой категории (проект/сущность), сортировка
  внутри — по возрастанию срока (просроченные вперёд).** Подтверждено пользователем как удобный
  формат для последующей ссылки по номеру.
- **Именованные пресеты диапазона дат, которые реально были нужны:** `overdue`, `no-deadline`,
  `this-week`, `next-week`, `today`, `tomorrow`, `next-N-days`, плюс точная дата и диапазон
  `YYYY-MM-DD..YYYY-MM-DD`. Хороший стартовый набор для любого похожего дедлайн-фильтра.
- **Дата создания/назначения задачи — НЕ требует anchor-механизма или PFS-регистрации.**
  Изначальное предположение автора ТЗ (Opus) было: «дата создания» доступна только для страниц,
  управляемых ProtocolFromSummary (через `row_anchor` → `_registry.json` → `meeting_date`), для
  остальных ~25 старых ручных Confluence-страниц-задачников — недоступна вовсе. Пользователь
  отклонил это ограничение: **дата создания = дата из первого столбца (`<td>`) той же строки
  таблицы (`<tr>`), где физически лежит `<ac:task>`** — большинство протокольных таблиц Confluence
  имеют универсальный формат «Дата | Задачи», и первая колонка содержит дату встречи/создания
  независимо от того, кто и чем публиковал туда строку (автоматика или ручной ввод много лет
  назад). Anchor нужен исключительно для другой задачи (republish/copy без дублирования строки),
  не для чтения даты. **Обобщаемый вывод:** для любой задачи «когда создана эта задача/строка» на
  Confluence-таблицах протокольного формата — сначала проверить структуру самой строки (первая
  колонка), не сразу городить отдельный anchor-based registry; anchor/registry нужны для куда
  более узкой цели (устойчивая идентификация строки при редактировании), не для извлечения уже
  присутствующих в структуре данных.

## WRITE-путь подтверждён реальным round-trip тестом (13.07.2026, TaskRefresh MVP)

После двух раундов Sonnet-реализации + личной проверки (не отчёта субагента) паттерн
`lxml`-парсинг + `string.replace()` целого блока `<ac:task>` подтверждён на живом Confluence,
не только юнит-тестами:
- Взята реальная задача (`ac:task-id` известен из READ-сессии), дедлайн изменён через
  `apply`+`confirm` CLI-цикл (preview «было→станет» → подтверждение → PUT).
- Версия страницы выросла ровно на 1 (10→11), `<ac:link>`/`ri:userkey` и текст задачи побайтно
  не изменились — правки затронул только `<time datetime>`.
- Задача возвращена к исходному значению тем же циклом (11→12), финальный diff идентичен
  исходному состоянию (кроме номера версии страницы, что ожидаемо).
**Вывод: для этого класса инструментов реальный round-trip тест (взять→изменить→проверить diff
API-запросом→вернуть обратно) — не опциональный, а обязательный последний шаг перед объявлением
WRITE-пути рабочим**, даже если все юнит-тесты зелёные (см. Pitfall 24/48) — сами юнит-тесты
мокают `ConfluenceClient` и не ловят разрывы контракта между модулями пайплайна.

## Два обнаруженных разрыва контракта одного класса (см. Pitfall 48)

Оба бага нашла ТОЛЬКО личная проверка на живых данных, не unit-тесты (78-84 теста были зелёными
всё это время):
1. `pipeline.run_read()` передавал сырую строку ФИО прямо в `TaskFilter`, не резолвя её через уже
   существующую `resolve_assignee()` — фильтр по имени возвращал пустой список.
2. `assignee_display` (обратный резолв userkey→ФИО для читаемого вывода) нигде не заполнялся —
   бриф показывал сырой userkey вместо имени.
Общая причина: резолв-функции существовали и работали изолированно, но не были явно подключены
в КАЖДОЙ точке пайплайна, где их результат нужен (и на входе-фильтрации, и на выводе-отображении).
При реализации похожего инструмента — явно пройтись по списку «где ФИО/userkey входит и выходит
из пайплайна» и для каждой точки проверить, что резолв реально вызван, не считать это само собой
разумеющимся раз функция где-то есть в кодовой базе.
