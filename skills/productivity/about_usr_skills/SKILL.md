# USERTOOLS — экосистема инструментов Саши (мастер-гайд)

Мастер-скилл по ВСЕМ пользовательским инструментам (не только MoveFrom*): выгрузка, разметка, публикация, поиск, индексация, реестры. Он же — единственная точка входа на вопрос «что ты умеешь / расскажи о себе / какие инструменты / что автоматизировано».

## Точка входа: «что ты умеешь / расскажи о себе / какие инструменты»

Когда Саша спрашивает про мои возможности — НИКОГДА не пересказывать список из этого файла как факт: версии/статусы/кроны меняются в течение одного дня. Вместо этого выполнить 4-шаговый алгоритм и собрать ответ из живых данных.

**Приоритет в ответе:** (1) наши USERTOOLS + активные ТЗ; (2) наши доработанные скиллы (tutu-*, workvault-rag, pm-briefing, get-obsidian-link, tz-workflow и т.п.); (3) generic Hermes-возможности «из коробки» — только если Саша спросил прямо.

Прочитать `TZ/<Инструмент>/<Инструмент>_TZ.md` по пути из инвентаря — там история брифа с реальными решениями. Если ТЗ большое — `search_files` внутри файла по ключевому слову.

# Операционная часть: MoveFrom* и смежные инструменты

Семейство Python-инструментов: выгрузка данных из корпоративных сервисов в локальный Obsidian vault (`WorkVault`). Каждый инструмент — поставщик данных для конвейера обработки.

## Overview

- **Слой 0 — Сбор (MoveFrom*):** сырые данные из источников, без обработки смысла
- **Слой 1 — Резолвер сущностей:** Exchange GAL как «золотые записи» людей; email = универсальный ключ связи между источниками
- **Слой 2 — Структурирование (MarkObjects*/ProcessFrom*):** извлечение сущностей, YAML-frontmatter
- **Слой 3 — Аналитика (PMBOK + риски):** сигналы из реального потока данных

**Распределение ответственности:** Fireflies и внешние сервисы — дешёвая первичная обработка 24/7 (STT, черновые таски). MoveFrom* — минимальный транспорт, не оценивает качество источника. Entity Resolver + Opus — качественная обработка только на уже структурированных данных.

## Принципы (обязательны для всех инструментов)

1. **Минимум файлов на единицу данных** — количество файлов определяется ценностью, не полнотой. Не добавлять файлы ради полноты.
2. **Идемпотентность через `_registry.json`** — не качать повторно уже загруженное.
3. **Никакой постобработки** — это зона следующих инструментов конвейера (MarkObjectsFromSummary и др.).
4. **Минимальная статусная машина загрузки:** `pending` / `completed` / `error`.
5. **`_registry.md`** — рендерится из JSON через Jinja2, без доп. запросов к API.
6. **TG-алерты только при ручном запуске** с ошибкой. Cron — тишина, всё в `_log.md`.
7. **Атомарная запись:** `tmp + os.replace` для файлов и реестра.
8. **Разработка и ТЗ — только через Opus** (`delegate_task model=claude-opus-4-7` или cronjob).

## Структура инструмента (шаблон)

```
MoveFrom<Service>/
├── movefrom<service>/
│   ├── __main__.py      ← CLI: preflight → ping → skip-or-download → finalize
│   ├── config.py        ← Settings из .env (pydantic Settings, НЕ модульные os.getenv!)
│   ├── client.py        ← API клиент (requests + tenacity retry)
│   ├── schema.py        ← Pydantic модели данных
│   ├── writer.py        ← атомарная запись, rollback при ошибке
│   ├── renderer.py      ← _registry.md из JSON через Jinja2
│   ├── registry.py      ← _registry.json: load/save/migrate, portalocker
│   ├── lock.py          ← portalocker single-instance guard
│   ├── logger.py        ← _log.md (одна строка/запуск) + jsonl events
│   ├── tg.py            ← TG-алерты (только manual; cron молчит)
│   └── templates/
│       ├── registry.md.j2
│       └── *.md.j2
├── tests/
├── .env
└── .venv/
```

Пример MoveFromFF: 2 файла на встречу (transcript + summary). `actions.md` — дубль Action Items из summary, не создаётся (финальное решение май 2026).

## Стандарты CLI

**Коды выхода:** `0` успех / `1` частичный успех / `2` lock/preflight / `3` сервис/auth / `4` фатально.

**⚠️ Питфолл крон-промпта: exit code 1 НЕ всегда означает «нет новых встреч» — иногда это необработанный traceback.** Прецедент 13.07.2026 (`vm_movefromff`): формулировка в промпте крона «если exit code 0 или 1 — нет новых встреч, шли [SILENT]» заставила модель молчать несколько часов подряд, хотя `1` был реальным `pydantic.ValidationError` traceback от сломанного реестра, а не штатным «частичный успех». Различать по СОДЕРЖИМОМУ вывода, не только по коду: если stdout/stderr содержит `Traceback`, `Error`, `Exception` — это сбой, треб��ющий алерта, независимо от exit code. Штатный «нет новых» узнаётся по строке `[*] Summary: downloaded=0, skipped=N, errors=0` в выводе, не по голому коду возврата.

**Режимы:**
- `--mode test` — последние 5 дней
- `--mode cron` — новые с `_last_sync - overlap`
- `--mode manual --from-date ... --to-date ...` — произвольный период

2. **MoveFromJira (только OKRAID + OKRS)** — цели департамента и проекты. Нужен для быстрой постановки задач через TG.

Если предлагается разработка другого инструмента раньше — напомнить про порядок.

**Постановка задачи через TG:** пользователь наговаривает → Сирень показывает «кому/что/срок» → задаёт по одному: 1) к какой цели департамента (OKRAID), 2) к какому проекту (OKRS) → подтверждение → публикация. Когда OKRAID+OKRS в кэше — предлагать сама, не спрашивать каждый раз.

## Железное правило публикации

Система **никогда не публикует автономно** в Jira, мессенджеры и публичные каналы. Только через человека: система нашла → пишет в TG → пользователь подтверждает/правит → публикация.

## Резолвер сущностей — правила (22.05.2026)

**Три состояния:**
- `resolved` — точное совпадение с `canonical_name`/`aliases` или email из Exchange GAL
- `ambiguous` — суффикс `(?)` в тексте (сигнал для ручного ревью в Obsidian)
- `unknown` — сущность не тронута, оставлена сырым текстом

**Главное: не угадывать.** Лучше пропустить чем соврать.

**Ключи сущностей:** контакт → `email` (Exchange GAL); проект → `canonical_name` + `aliases` в файле проекта. В ТУТУ за 5 лет не повторилось ни одного проекта → коллизии крайне маловероятны, реестр aliases пополняется, процент авторезолва растёт сам.

**Исключение:** один термин может означать разные сущности («АБ платформа» = старая ТУТУ или новая Trisigma) → `ambiguous`, не угадывать по контексту.

## Wiki-ссылки и карточки контактов (24.05.2026)

Все сущности в frontmatter summary.md — wiki-ссылки Obsidian:
```yaml
contacts:
  - "[[Иван Иванов]]"
projects:
  - "[[Тризигма]]"
```

Формат имени контакта: `[[Имя Фамилия]]` (без отчества). Для каждого смэтченного контакта создаётся/обновляется `Contacts/Иван Иванов.md` (иначе Obsidian покажет сломанную ссылку). MarkObjectsFromSummary создаёт файлы автоматически из contacts.enc.

**Источник правды — `contacts.enc`.** Карточка `.md` — только отображение, генерируется автоматически. Карточка НЕ удаляется инструментом — только создаётся/обновляется. Старые файлы (до перехода на contacts.enc) удаляет пользователь вручную.

**Проекты тоже wiki-ссылки** — файл проекта создаётся отдельным инструментом (не MarkObjectsFromSummary v0.1). В v0.1 — только контакты.

## Архитектура хранилища сущностей

- **Хранилище + редактирование** → `.md` файлы в WorkVault с YAML frontmatter (Obsidian)
- **Аналитика и запросы** → Obsidian Dataview plugin (SQL-подобный синтаксис по frontmatter)
- **Один источник правды** — никакой параллельной БД рядом с `.md` файлами

Почему не SQLite: два источника правды сложнее поддерживать. `.md`+Dataview — нативно для Obsidian, уже установлен.

## Правила разработки (ОБЯЗАТЕЛЬНО)

- **ТЗ пишет и правит только Opus** (`delegate_task model=claude-opus-4-7`). Даже мелкие правки. Haiku для ТЗ недопустим.
- **После правки ТЗ — Opus проверяет все смежные ТЗ** на непротиворечивость (смежные = читают/пишут общие файлы или вызывают друг друга).
- **Код пишет Opus.**
- **Финальная проверка кода — Haiku:** читает код и ТЗ, находит расхождения.
- **Справочные вопросы** («как работает X», «что написано в ТЗ») → Haiku с fallback на Sonnet.
- **Разработку любого инструмента запускать ТОЛЬКО по ТЗ и ТОЛЬКО после явного «ок, берём в работу» от Саши в TG.** Никакой реализации «по ходу».

- **⚠️ «Только читать / только диагностика» — ЯВНО ЗАПРЕЩАТЬ МУТАЦИИ в промпте субагента/cronjob, не полагаться на здравый смысл.** Прецедент 17.07.2026: cronjob с задачей «читать код matcher_contacts.py, взять 2-3 файла встреч, прогнать точечный тест на одном файле» по факту выполнил `mofs rematch --all --bucket=all` на 564 встречах всего архива (2025-08-12 — 2026-07-16), изменив frontmatter 517 файлов и создав 30 карточек. **Дополнительно:** диапазон дат («прогони на июнь-июль») тоже был проигнорирован — агент выбрал `--all` вместо `--from/--to`. Команду передавать ДОСЛОВНО готовой строкой: ✅ `mofs rematch --all --bucket projects --from 2026-06-01 --to 2026-07-17 --dry-run` ❌ «прогони на диапазоне июнь-июль». Явно включать в промпт: «НЕ запускать никаких команд, изменяющих файлы WorkVault или реестры. НЕ вызывать `mofs run/rematch/bootstrap` без `--dry-run`. Если обнаружишь, что для диагностики нужна мутация — опиши это в отчёте и остановись». Один `os.system()` или `terminal()` без проверки флагов разносит архив.

- **⚠️ `--dry-run` флаг — проверять работоспособность ПЕРЕД первым боевым использованием, не доверять что реализован корректно.** Прецедент 17.07.2026: `mofs bootstrap --dry-run` по факту применял изменения к файлам (баг в реализации — флаг читался, но мутация не блокировалась). Обнаружено только по `stat` файла и timestamp. **Обязательный smoke-тест перед прогоном на архиве:** `mofs rematch --meeting-id <один ID> --dry-run` → проверить `mtime` файла до и после → не изменился = dry-run работает → идти дальше. Изменился = СТОП, баг, не запускать на архиве. Откат через `mofs bootstrap --undo <timestamp> --yes` (manifest в `state/`). После отката — `systemctl --user start owncloud-sync.service`.
- **Делегирование на Opus длинных задач (>5 мин) — через cronjob, не delegate_task.** `delegate_task` с Opus (reasoning_effort=high, child_timeout=1200) держит родительский стрим и вызывает gateway-зависания. `delegate_task` — только для коротких задач на Sonnet/Haiku.
- **Расширение объёма уже поставленной cronjob-задачи ДО её первого запуска (техника, 16.07.2026):** если сразу после `cronjob(action='create', schedule='1m', ...)` для Opus-задачи (написание/правка ТЗ) выясняется, что нужно расширить объём (напр. добавить ещё один под-шаг, которого не было в первом промпте) — проверить `cronjob(action='list')` на `last_run_at: null` у этого job_id (значит минутный таймер ещё не сработал) и обновить промпт через `cronjob(action='update', job_id=..., prompt=<полный новый текст>)` ДО срабатывания, а не создавать вторую задачу или ждать результата первой и потом делать доп. проход. Экономит один полный цикл Opus (время+токены). Работает только в узком окне до первого тика — если `last_run_at` уже не `null`, поздно, реагировать по факту готового результата.

- **«Делаем»/«берём в работу» авторизует РЕАЛИЗАЦИЮ КОДА конкретной задачи, но НЕ авторизует постановку кронов на автоматическое расписание — это два разных разрешения, даже если оба возникают в одной цепочке работ.** Прецедент 17.07.2026 (MOFS): Саша сказал «Делаем» после согласованного ТЗ → реализация кода запущена и выполнена корректно; отдельно, тот же прогон Opus **только перечислил** 3 готовых к постановке крона в финальном отчёте, ни один не был создан через `cronjob(action='create')` — это было изначально прописано в промпте субагента как обязательное разделение («НЕ создавай кроны автоматически, оставь как todo-пункт»). Когда Саша позже написал «без моего согласия нельзя выполнять реализацию, я не давал согласие» — необходимо было спокойно и честно разложить факты: что именно было явно авторизовано (реализация кода — да, по «Делаем»), что не было создано вообще (кроны — не создавались), и явно уточнить, что конкретно имелось в виду, вместо того чтобы либо молча продолжать, либо сразу извиняться за то, чего не произошло. Проверка через `cronjob(action='list')` перед ответом — обязательна, не полагаться на память о том, что «вроде не создавала».

### ProtocolFromSummary — расписание кронов (закреплено 14.07.2026)

### EntityRegistry — паттерн сведения дублирующих реестров к одному каноническому источнику (16.07.2026)

**Проблема-класс:** несколько независимых инструментов одного семейства держат СВОИ копии одного и того же справочника (в этом случае — проекты/сущности-темы): `ProtocolFromSummary/config.py::ROUTES` (16 записей), `TaskRefresh/project_registry.json` (те же 16, вручную поддерживались в синхроне), плюс скилл `workvault-rag` резолвил проект по свободному тексту вместо явного списка. Рассинхрон рано или поздно случается — руками синхронизировать 2+ копии не масштабируется.

**Решение — один канонический JSON-реестр + тонкие read-адаптеры, не переписывание consumers с нуля:**
1. Создать один файл вне репозиториев инструментов (`WorkVault/Registries/entities.json`) — общее место, доступное и Python-коду, и агентским скиллам (через file-tools).
2. Каждый существующий потребитель получает **тонкую функцию-обёртку** поверх старого API (`config.py::ROUTES` стал функцией, читающей JSON и на лету собирающей идентичную по форме структуру — сам `route.py`, потребляющий `ROUTES`, не тронут НИ СТРОКОЙ).
3. **Baseline-инвариант — обязательное условие успеха:** снять `repr(sorted(ROUTES.items()))` ДО миграции, сверить с тем же после — diff должен быть пустым. Без этого «рефакторинг» не доказан безопасным, только предположительно безопасным.
4. Для потребителя со своим файлом-дублем (TaskRefresh) — старый файл не удаляется сразу, становится **legacy-fallback** (используется только если новый реестр недоступен/битый, с явным log-warning при срабатывании) на переходный период (1-2 недели наблюдения), удаление — отдельный follow-up.

**Порядок отката при многошаговой миграции нескольких инструментов — последовательно с жёстким стоп-гейтом, не параллельно:** если пользователь явно задаёт приоритет («сначала инструмент A, потом B» — было дано 16.07.2026 «первым делом восстановить PFS, потом TR»), это не пожелание, а обязательный чек-пойнт: полный regression первого инструмента (100% тестов + baseline-diff пуст) должен пройти, ПРЕЖДЕ чем субагент вообще притронется к файлам второго. Если первый инструмент не проходит — работа над вторым не начинается, отчёт о поломке идёт до попытки продолжить. Явно прописывать это в промпте субагента как STOP-точку, а не полагаться, что порядок шагов ТЗ сам по себе это гарантирует.

**Применимо повторно:** любой следующий случай дублирующихся конфигов/реестров между USERTOOLS-инструментами одного семейства (не только проекты — потенциально те же грабли для расписаний, названий сущностей, маппингов полей) стоит решать этим же паттерном, а не точечной синхронизацией руками. Полное ТЗ-решение (7 открытых вопросов, финальная схема) — `WorkVault/Hermes-Backlog/TZ/EntityRegistry/EntityRegistry_TZ.md`.

**⚠️ ЖЕЛЕЗНОЕ ПРАВИЛО (16.07.2026, аналог правила contacts.enc): новые сущности (проекты/темы/инструменты) добавляются/удаляются/переименовываются ТОЛЬКО через `WorkVault/Registries/entities.json`.** Никогда не править `ProtocolFromSummary/config.py::ROUTES` напрямую (это теперь read-only функция-обёртка, не литерал для правки) и не заводить отдельную запись в legacy `TaskRefresh/project_registry.json` (только fallback, не source of truth). Если нужной сущности нет в `entities.json` — сначала добавить её туда (через CLI-инструмент управления реестром, см. ниже, когда он появится, либо вручную по схеме из `WorkVault/Registries/README.md` с последующей валидацией по `entities.schema.json`), и только после этого она станет видна PFS/TaskRefresh/workvault-rag — без единой правки кода. Прецедент, который это правило закрывает: до 16.07.2026 один и тот же справочник проектов дублировался в 3 местах (`ROUTES`, `project_registry.json`, свободнотекстовый поиск workvault-rag) — рассинхрон был почти неизбежен при ручной правке.

**CLI-инструмент управления `entities.json` (add/remove/edit/list/validate) — `EntityRegistryCLI`, ТЗ `WorkVault/Hermes-Backlog/TZ/EntityRegistryCLI/EntityRegistryCLI_TZ.md`** (draft на 16.07.2026, entry-point `entity-registry`, запускается через ОБЩИЙ venv `~/USERTOOLS/ProtocolFromSummary/.venv/` — не свой отдельный venv, решение Саши после брифа 16.07.2026, отклонение от исходной рекомендации Opus). Схема реестра (набор полей) заведомо будет меняться со временем — инструмент читает `entities.schema.json` в рантайме (интроспекция, не хардкод списка полей): новое поле в схеме подхватывается автоматически без правки кода CLI. Валидация двухслойная — JSON Schema (Draft-07) + бизнес-инварианты (уникальность slug, целостность `parent`-ссылок, уникальность пары `page_id,tag`). Мутации записи с блоком `pfs` (влияет на прод PFS/TaskRefresh) требуют явного подтверждения. Лог операций в stderr — компактный `key=value` формат (`op=add slug=... result=ok`), оптимизирован для машинного парсинга (Haiku при отладке), не для чтения человеком.

### EntityRegistry ↔ MarkObjectsFromSummary (MOFS) / AggregateFromMeetings (AFM) — бриф 16.07.2026

**Контекст:** AFM (ТЗ `TZ/AggregateFromMeetings/TZ_aggregate_main.md`, v1.8, ещё НЕ реализован физически — только ТЗ) уже содержит собственный §3.2 «Реестр проектов» (16 slug-ов, `classification_memory.json`), написанный ДО EntityRegistry и с другим неймингом (`ml-platforma`, `ab-platform`, `ai-mas` — дефисы; entities.json — `ml_platforma`, `ab_platforma`, `ai_analitik` — подчёркивания) и другими Confluence ID у части проектов (напр. Trisigma: AFM=`480923430`, entities.json/PFS=`490170597`).

**Решение Саши (не путать AFM-ID с PFS-ID):** это НЕ ошибка/дубль данных — это две РАЗНЫЕ страницы одного проекта:
- **PFS `pfs.page_id`** = страница «Минутки»/протокол встреч (куда PFS автоматом пишет строки).
- **AFM устав-ID** = страница устава/index проекта (структура, брифы, состав команды — источник для модуля A AFM).
Обе страницы легитимно относятся к одному slug, разные назначения.

**Итоговая архитектура (принята, ещё не реализована):**
1. **`entities.json` остаётся единственным каноническим источником** — AFM при реализации НЕ заводит свой `classification_memory.json` с нуля, а либо мапится на `entities.json`, либо (выбрано Сашей) **обогащает** его схему.
2. **Naming-конфликт решён через `aliases`, не через маппинг-таблицу:** канонические slug — из `entities.json` (уже в проде). AFM-варианты именования (`ml-platforma`, `ab-platform`, `ai-mas` и т.п.) добавляются как ДОПОЛНИТЕЛЬНЫЕ записи в существующий массив `aliases` соответствующего slug — не отдельный файл-маппинг, не переименование канонического ключа.
3. **Новый опциональный блок `charter`** — по аналогии с `pfs`: `"charter": {"confluence_id": "..."}`. Наличие = у сущности есть устав-страница, которую читает модуль A AFM. Отсутствие = «пока нет» ИЛИ «не будет никогда» — схема НЕ различает эти два случая (сознательное решение — не городить лишний field-level инвариант ради гипотетической ошибки, которая ничего не ломает: если `charter` случайно окажется у записи `kind≠project`, AFM просто не читает это поле в контексте синков/1-1, реального риска для прод-инструментов, читающих `pfs`, нет).
4. **Кто пишет `charter`:** только через `entity-registry edit <slug> charter --set '{"confluence_id":"..."}'` (человек, вручную) — НЕ автоматически модулем A AFM при первом Confluence-pull. Причина: то же самое железное правило «мутация реестра только через CLI», которое уже действует для остальных полей — разрешить AFM писать в `entities.json` напрямую создало бы второй, менее контролируемый канал записи того же файла (в обход валидации/бэкапов/confirm-диалогов CLI), в точности повторяя проблему, которую EntityRegistry был призван решить.
5. **Двойная классификация (проект = ещё и инструмент, напр. Метротека — и проект АИД, и внутренний инструмент)** — решено добавочным полем `tags: [...]` рядом с основным `kind` (напр. `kind=project, tags=["tool"]`), НЕ через создание двух отдельных записей с одинаковыми алиасами (это создало бы риск двойного матча одного текстового упоминания на два slug — усложняет резолв без выгоды) и НЕ через enum-массив вместо скалярного `kind` (сломало бы существующую PFS-логику, которая читает `kind` как единственное значение).
6. **Ретроактивный охват архива — гибридная стратегия:** новые сущности резолвятся вперёд сразу (MOFS v0.2 на новых встречах через обычный крон-прогон), НЕ требуют полного разового прохода 1000+ файлов NewMeetings. Для подтягивания исторических упоминаний уже добавленной сущности — переиспользовать существующий механизм `--rematch --all` (тот же, что уже описан выше для контактов «добавлен задним числом») применительно к проектам: после `entity-registry add <slug>` следующий логичный шаг — `mofs --rematch --all` (или ограниченный период), не отдельная незапланированная операция.
7. **Классификация при массовом NER-прогоне архива (если/когда будет) — 4 отдельные корзины, не смешивать:** (a) люди → сверка с `contacts.enc`, никогда не в entities.json; (b) сущности-проекты/темы → `entities.json`; (c) инструменты → `entities.json` с `kind=tool`; (d) переговорки → сверка с `WorkVault/Contacts/meeting-rooms.md`, никогда не в entities.json. Смешение любых двух корзин — архитектурная ошибка, не просто неаккуратность.

## Общие питфоллы (все инструменты)

- **Никогда не вписывать произвольную строку в enum-поле (`status` и т.п.) любого `_registry*.json` без проверки допустимых значений в pydantic-модели кода.** Невалидное значение ломает `load_registry()` целиком для ВСЕХ записей, не только для одной — инструмент тихо перестаёт видеть вообще все данные, а cron-промпт может ошибочно трактовать результирующий exit code как штатный «нет новых» (см. проверенный паттерн тихого исключения встречи выше в разделе MoveFromFF).
- **`config.py` — модульные `os.getenv(...)` на верхнем уровне запрещены** — выполняются до `load_dotenv()`, значение из `.env` тихо игнорируется. Только pydantic `Settings`.
- **Реальный путь USERTOOLS для cronjob-ов:** `C:\Users\tkachenkoav\Documents\Cursor_projects\hermes-agent\USERTOOLS\` (на VM — переехало в `~/hermes-agent/USERTOOLS/`). НЕ `WorkVault/USERTOOLS/`. WorkVault — только для данных.
- **Не писать ad-hoc скрипты к API** — только через инструмент MoveFrom*. Если сценарий не поддерживается — сначала доработать инструмент.
- **`fetch_gal()` тихо возвращает 0** — причина: голый `except Exception: pass` глотает UnauthorizedError на каждом паттерне wildcards. Всегда логировать исключения в клиентах API.
- **Субагент на Haiku портит `.env` и `contacts.enc`** — при делегировании диагностики Exchange субагент подставлял тестовые credentials и удалял `contacts.enc`. Явно запрещать в промпте: «не удалять contacts.enc и .env».
- **Проверяй что субагент не написал заглушку** — после делегирования разработки API-клиента: `grep -n "return \[\]" client.py` или читать тело метода перед первым боевым тестом.
- **List-запрос не должен тянуть тяжёлые поля** — cost-limit API молча вернёт пустой массив без ошибки. Паттерн: лёгкий list → fetch полных данных только для новых записей (N+1 по числу реально новых).
- **`execute_code` vs `terminal` для Python на Windows:** `python3`/`python3.11` в терминале могут не работать (uv trampoline, MS Store alias). Для быстрых Python-скриптов — `execute_code`.
- **`Configuration(timeout=...)` → TypeError** в новых exchangelib — убрать.
- **`EXCHANGE_PASSWORD=***`** — плейсхолдер, не пароль. Реальная аутентификация через Kerberos.
- **Батч-переименование через bash ломается на пробелах/кириллице** — использовать `execute_code` + Python `os.rename()`. Детали: `references/clean-install-testing.md`.
- **Fireflies сокращает ФИО до формата «Фамилия И.О.» / «Фамилия И.»** (напр. «Ткаченко А.В.», «Аралов А.») в summary/задачах — любой резолвер контактов, использующий substring-поиск (`query in fio`, как `AnywhereContacts.find_contacts`), даёт 0 кандидатов на такой строке: сокращённая форма с точками физически не является подстрокой полного «Фамилия Имя Отчество» в `contacts.enc`. Баг тихий — не exception, а просто «не резолвится», легко принять за «контакта нет в базе». Найдено 13.07.2026 на боевой публикации (все 9 задач встречи «Синк 1-1 Саша - Саша» остались текстом вместо `<ac:link>` меншенов в ProtocolFromSummary). **Фикс-паттерн (не только для ProtocolFromSummary — для любого инструмента, резолвящего Fireflies-текст против contacts.enc):** отдельным шагом до обычного substring-поиска — regex `^([А-ЯЁ][а-яё]+)\s+((?:[А-ЯЁ]\.){1,2})\s*$` разбирает raw на (фамилия, инициалы); ищем кандидатов по одной фамилии (`find_contacts(surname)`), затем среди них оставляем только тех, у кого второе (и третье) слово `fio` начинается с этих же инициалов по порядку; 0 совпадений после фамилии → падать в обычный путь (substring по всей строке raw); >1 совпадений с одинаковыми инициалами → неоднозначность, оставлять текстом, не гадать. Рабочая реализация с тестами — `USERTOOLS/ProtocolFromSummary/protocolfromsummary/contacts_resolver.py` (`_split_surname_initials`/`_initials_match`).
