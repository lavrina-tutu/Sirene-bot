# Проверки по ошибкам недели 12–19 октября 2026

Материалы для сопровождающего skill. Не загружать при обычном выполнении пользовательской задачи.

## Что проверяют

Это обезличенные сокращённые модели механизмов ошибок, а не копии production. runtime-wiring воспроизводит заглушку старой ручки при рабочем новом пути. proxy-completeness воспроизводит обрыв после начала HTTP 200 внешним общим дедлайном. author-contract проверяет независимость review от новой авторской спецификации. versioned-flow переносит претензии к избыточному поиску уже известных ID и неясному объяснению на синтетические ветки. retained-obligations — профилактическая проверка потери требований при сокращении объёма; буквальное воспроизведение конкретного инцидента недели для неё не установлено.

## Подготовка и запуск

1. Зафиксировать SHA-256 skill, fixture, запросов и rubric до запуска. Дать исполнителю только копию fixture, request.md и выбранный skill без evals/maintainer-материалов. rubric, examiner, controls, этот протокол и будущие turns.json скрыты. Не передавать старые ответы или результаты тестов. Не подключать реальные административные инструменты к этим локальным сценариям.
2. Выполнить request.md в свежем контексте. Сохранить фактические ответы, diff, команды, логи и состояние файлов. Только после завершения хода отправлять следующий элемент turns.json в тот же контекст; сохранить результат каждого хода. Не заменять реальные ходы просьбой «представь диалог».
3. Сначала проверить поведение без подсказки пользователя; затем — исправление после возражения и сохранение ранее установленных ограничений. Не складывать это в один балл, скрывающий первоначальный промах. Для read-only задач сверить исходные хеши.
4. Копировать examiner в отдельную копию результата. Проверять фактический путь и assertions. Падение сборки/песочницы/зависимости — недействительный прогон, а не пойманный дефект. Нужен ожидаемый упавший тест; корректный контроль обязан проходить. Для текстовых результатов нужна независимая оценка по источникам и сохранённым файлам, без поиска ключевых слов.
5. Сравнивать baseline/candidate на одинаковой модели, effort, инструментах и входах, в независимых свежих контекстах. Записать фактические model/effort каждого хода, прерывания и недоступные инструменты. Модель из имени запуска не считать доказательством настройки. Не давать одному исполнителю обе версии. Проверяющий не должен знать версию skill.
6. Для вывода об устойчивом улучшении использовать повторы и заранее отложенные новые задачи; эти открытые контрольные примеры уже доступны автору и не являются holdout. Не менять порог после результатов. Пропуск критической ошибки, ложное блокирующее замечание, потеря требования или нарушение полномочий запрещают принимать кандидат лишь за более гладкий текст. При равенстве — «польза не установлена».

## Результат одного запуска

Записать: case/version/input hashes; фактические model/effort; исходный результат до коррекции; результат после каждого возражения; незакрытые требования; лишние изменения/ложные findings; соблюдение полномочий; результаты независимых проверок и ограничения. Каждый критический пункт — pass/fail/unknown со ссылкой на доказательство. Unknown не равен pass. Успех локального стенда не означает CI/deploy/production.

## Ограничения

Тесты Go используют только стандартную библиотеку: GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local GOWORK=off и отдельный GOCACHE. HTTP-проверкам нужен loopback. Модель прокси проверяет общий дедлайн и полноту тела, а не все особенности Envoy/HAProxy, браузера, Mongo или реальной нагрузки. Изменение read-only снимка маршрута является проверяемым нарушением локального поручения; отсутствие такого изменения не доказывает отсутствие всех возможных внешних записей — нужны логи инструментов. Platform MCP исключён из доработок.

Старые trajectories оставлены как smoke: их успех не доказывает чувствительность к ошибкам недели. Калибровка тестов на намеренно неправильных и правильных вариантах доказывает только качество этих проверок, не улучшение модели или skill.
