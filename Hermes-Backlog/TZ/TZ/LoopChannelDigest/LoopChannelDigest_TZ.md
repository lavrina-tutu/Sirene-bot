# LoopChannelDigest — ТЗ

Автор: архитектор (Cursor CLI, по заданию Саши Ткаченко)

## §1 Цель

По запросу Саши в чате сформировать краткий дайджест «движения по вопросам» в указанном канале Loop (Mattermost ТУТУ, `loop.tutu.ru`) за указанный период — что обсуждалось, какой статус (закрыто/в работе/анонс) и кто участвовал, без пересказа сырых сообщений и без FF-шаблона.

## §2 Место в экосистеме

- Класс: analytical/on-demand-инструмент, **не** член семейства `MoveFrom*` (те — connector/monitoring со state). `LoopChannelDigest` — stateless: окно и канал передаются явно при каждом вызове, watermark/крон не нужны.
- Источник данных: Loop = Mattermost, self-hosted, `https://loop.tutu.ru`, REST API v4.
- Назначение: разовый структурированный дайджест, потребляется текущей LLM-сессией (Сирень/default) для генерации финального markdown — не записывается автоматически ни в `WorkVault/Entities/`, ни в Telegram (в этой итерации).
- Регистрация в `MAIN_TZ_INVENTORY.md` — новый draft-инструмент.

## §3 Scope / Non-goals

**В скоупе:**
- On-demand дайджест по явному запросу («дайджест канала X за 2 недели», «что было в Loop-канале Y с 1 по 15 августа»).
- Параметры вызова — **только** канал и временное окно (`since`/`until`). Всё остальное — константы.
- Анализ **ВСЕХ** подтопиков канала по умолчанию (`--topics all`), если явно не указан список.
- Формат вывода — фиксированный, см. §7. Модель (текущей сессии) сама пишет финальный текст, читая структурированный агрегат.

**Non-goals (явно НЕ входит в эту итерацию):**
- Крон/расписание, авто-доставка в Telegram — не закладывается (решение Q3 брифа).
- Запись дайджеста в `WorkVault/Entities/<slug>/Messages/` — не входит (это зона `MoveFromLoop` §AA-§AI, отдельная функция «архивации», не пересекается с этим инструментом).
- Мониторинг/срочные уведомления — зона `MoveFromLoop` итерация 1, не трогаем и не дублируем.
- FF-шаблон, временные метки, дословные цитаты в выводе — исключены по утверждённому формату (см. §7).
- Bi-directional (ответы в Loop из Telegram), вложения/файлы Mattermost, реакции/редактирования постов — вне скоупа.

## §4 Архитектура — два слоя

```
Саша: "дайджест канала LLM за 2 недели"
        │
        ▼
Скилл loop-channel-digest (тонкий: триггеры + правила извлечения тем + утверждённый формат)
        │  вызывает CLI
        ▼
CLI-инструмент LoopChannelDigest (детерминированный Python, без LLM внутри)
        │  curl+subprocess
        ▼
Loop API v4 (loop.tutu.ru)
        │  возвращает
        ▼
Структурированный JSON (топики → треды → участники, Medium-компактизация)
        │  читает как контекст
        ▼
Модель ТЕКУЩЕЙ сессии пишет финальный markdown по формату §7
```

### §4.1 CLI-инструмент — функциональные блоки

1. **Channel resolver** — `channel_name → channel_id` через `GET /api/v4/teams/{team_id}/channels/name/{name}`. `team_id` — константа с дефолтом ТУТУ (`b1mrmr41dtrhbgk3a9qa7bxhqe`), переопределяемая параметром `--team`. Эндпоинты `/channels/name/{team}/{name}` и `/channels/search` **не использовать** — подтверждено 404/пусто на прототипе.
2. **Topics lister** — `GET /api/v4/channels/{channel_id}/topics` → список подтопиков. Дефолт — обрабатывать ВСЕ подтопики; фильтр `--topics "Codex,Cline"` — опционален.
3. **Posts fetcher** — по каждому топику: `GET /api/v4/channels/{topic_id}/posts?since={since_ms}&per_page=200`, пагинация через `before` до исчерпания окна `[since, until]`. Фильтр на каждый пост: `delete_at == 0`, `type == ""`, `create_at` в границах окна.
4. **Thread clustering** — группировка постов внутри каждого топика по `root_id`: пустой `root_id` → новый корень треда; непустой → ответ, привязывается к своему корню. Результат — список тредов на топик вместо плоского списка постов.
5. **Author resolution** — сбор всех уникальных `user_id`, встретившихся в любом топике/треде окна, **один** батч-вызов `POST /api/v4/users/ids` → карта `id → "Фамилия Имя"` (используется схема ФИО «Фамилия Имя», как в `MoveFromLoop`/`MoveFromZulip`). Fallback при неполном резолве (см. §8, риск 4) — использовать `username`, если ФИО не пришло.
6. **Aggregation/compaction (Medium-уровень)** — на треде: текст корневого поста целиком + тексты ответов с чисткой (свернуть `quote`-блоки, ссылки → `[ссылка]`, схлопнуть повторяющиеся приветствия/подписи), авторы уже резолвлены в ФИО. Cap на длину треда: **20 сообщений** и **~4000 символов суммарно на тред** (решение Q4 брифа, стартовая эвристика); превышение — оставить первые + последние сообщения в пределах лимита с пометкой `[...N сообщений пропущено...]`.
7. **Output** — JSON на stdout: `{channel, since, until, topics: [{name, threads: [{root_author, participants: [...], messages: [...], truncated: bool}]}]}`. Опционально `--format md` — тот же контент, отрендеренный как markdown-дамп для ручного дебага (не путать с финальным дайджестом — это просто читаемый вид агрегата, без LLM-синтезы).

**CLI-интерфейс** (переключаемые параметры — только канал и окно, п.1 брифа):

```bash
python -m loop_channel_digest \
  --channel llm \
  --since 2026-08-13 --until 2026-08-26 \
  [--topics all]                          # дефолт: все подтопики
  [--team b1mrmr41dtrhbgk3a9qa7bxhqe]      # дефолт: константа ТУТУ
  [--format json|md]                       # дефолт: json
```

Формат вывода дайджеста, правила извлечения тем и статусов — константы **скилла**, не параметры CLI.

### §4.2 Скилл `loop-channel-digest` — тонкий

Содержит **только**:
- Триггеры: «дайджест канала X», «что было в Loop-канале Y за период», «покажи новости из #канал» и т.п.
- Правило вызова CLI-инструмента (команда из §4.1, дефолты: все топики, если не указано иное).
- Правила извлечения тем из агрегированных тредов: **1 topic Mattermost ≈ 1 раздел дайджеста**; дробление одного topic на несколько разделов — только если внутри явно присутствуют разные несвязанные обсуждения (несколько независимых `root_id`-тредов без смысловой связи). Объединение нескольких topics в один раздел — не практикуется по умолчанию.
- Утверждённый формат вывода (см. §7) с few-shot примерами (§7.3).
- Явный запрет: без FF-шаблона, без временных меток и дословных цитат-формулировок в тексте дайджеста.

**Не содержит:** HTTP-логику, парсинг полей Mattermost, резолв авторов, кластеризацию тредов — всё это в CLI-инструменте. Разделение даёт экономию токенов: скилл короткий, «сырая» механика сбора не проходит через LLM.

### §4.3 Кто выполняет финальную LLM-синтезу

Финальный дайджест пишет модель **текущей сессии** (профиль default/Сирень), читая JSON-агрегат CLI-инструмента как контекст — без отдельного суб-вызова LLM. Отдельная модель/крон-режим в этой итерации не закладывается (решение Q3 брифа); при появлении потребности в периодическом авто-дайджесте — отдельная будущая итерация с явным выбором модели (см. §9).

## §7 Формат вывода дайджеста (утверждённый Сашей)

### §7.1 Структура

```markdown
## 📰 <Канал> — дайджест <период>

**<Тема 1>** — <суть в одном-двух предложениях>. Статус: <✅ закрыто / 🔄 в работе / 📣 анонс>.
Участники: <Имя1>, <Имя2>, <Имя3>.

**<Тема 2>** — ...
Статус: ...
Участники: ...

---
**Ключевые вкладчики-эксперты:** <Имя1>, <Имя2>, ...
```

Правила:
- Заголовок — ровно `## 📰 <Канал> — дайджест <период>` (период — человекочитаемый диапазон дат, не технический ISO-таймстамп).
- Одна тема = один абзац: суть + статус + участники. Без вложенных списков сообщений, без ссылок на конкретные посты.
- Статус — ровно один из трёх: ✅ закрыто, 🔄 в работе, 📣 анонс. Выбор — по итоговому состоянию треда(ов) на конец окна, не по формальному признаку (например, «есть ответ» ≠ «закрыто»).
- Блок «Ключевые вкладчики-эксперты» — в конце, только имена (без должностей, без счётчиков сообщений).
- **Запрещено:** временные метки (даты/часы отдельных сообщений), дословные цитаты, ссылки на посты Loop, структура FF-протокола (Проблемы/Риски/Решения как отдельные секции — здесь нет такого деления, только «тема+статус+участники»).

### §7.2 Правило извлечения тем

1 topic Mattermost ≈ 1 тема дайджеста. Дробление одного topic на несколько тем — только при явно разных несвязанных обсуждениях внутри (несколько независимых по смыслу `root_id`-тредов). Объединение нескольких topics в одну тему — не практикуется. Topics без активности за окно — не включаются в дайджест (пустой раздел не создаётся).

### §7.3 Few-shot пример

Вход (агрегат, топик «Codex», один тред): корневой пост про баг с MCP-подключением от Иванова, три ответа с обсуждением, финальный ответ Петрова «пофиксили, багфикс выложен».

Ожидаемый вывод:

```markdown
**Codex — баг с MCP-подключением** — обсуждали разрыв MCP-сессии при долгих ответах модели. Статус: ✅ закрыто.
Участники: Иванов, Петров, Сидорова.
```

Пример для 📣 (топик «Объявления», один пост-анонс без ответов):

```markdown
**Объявления — обновление LibreChat** — анонсирована синхронизация групп из AD для назначения прав агентам/скиллам. Статус: 📣 анонс.
Участники: Кузьмина.
```

Пример для 🔄 (топик «LLM Gateway», активный тред без финального решения на конец окна):

```markdown
**LLM Gateway — лимиты на batch-запросы** — обсуждают повышение лимита для batch-эндпоинтов, договорились протестировать на прод-нагрузке, решение не принято. Статус: 🔄 в работе.
Участники: Ларьков, Набиева.
```

## §8 Риски

1. **Токен на объём тредов.** Активный канал за длинное окно (месяц+) может дать историю, не влезающую в разумный контекст даже при Medium-компактизации с cap 20/4000 — нужен явный общий бюджет на весь прогон (если суммарный объём агрегата превышает разумный порог — CLI должен явно предупредить в stderr/логе, а не молча обрезать половину дайджеста без сигнала).
2. **`requests` vs `curl` — решено (Q2), но не отменяет наблюдение.** Прототип показал зависание `requests`/`httpx` на `loop.tutu.ru`; новый клиент — curl-only. Если в будущем всё же понадобится `loop_api.py`-код — расхождение с продакшн-кронами MoveFromLoop (там `requests` работает) остаётся невыясненным фактом, зафиксировать в README нового инструмента как заметку для будущих итераций.
3. **Кластеризация тредов ≠ кластеризация «вопросов».** Правило «как из тредов собрать тему» отдано модели (скилл §4.2/§7.2), не коду. Риск: при большом числе тредов в одном топике модель может либо переусложнить дробление, либо слепить разнородное в одну тему — минимизируется few-shot примерами (§7.3) и явным дефолтом «1 topic = 1 тема».
4. **Резолв авторов батчем `POST /users/ids`** — по опыту `mattermost-loop-api` иногда даёт 502. Fallback: показывать `username` вместо ФИО, не падать (CLI завершается с частичным результатом + warning в stderr, а не exit-ошибкой).
5. **Определение статуса (✅/🔄/📣) — субъективная LLM-оценка**, не детерминированный код; консистентность между прогонами обеспечивается few-shot примерами в скилле (§7.3), но не гарантируется формально.
6. **Cap 20 сообщений/~4000 символов на тред — стартовая эвристика без калибровки на реальных данных**, кроме одного прогона на 68 постах/2 недели/1 канал. Возможна потребность пересмотра порога после первых прогонов на более активных каналах (решение Q4 брифа явно допускает калибровку по факту).

## §10 Связи с экосистемой

- **Читает:** Loop API v4 (`https://loop.tutu.ru/api/v4/teams/{team}/channels/name/{name}`, `/channels/{id}/topics`, `/channels/{id}/posts`, `/users/ids`) — Bearer token из `.env` (`LOOP_TOKEN`, тот же токен, что у `MoveFromLoop`).
- **Не пишет** ни в `contacts.enc`, ни в `WorkVault/Entities/`, ни в Telegram — вывод инструмента (JSON) потребляется текущей LLM-сессией, финальный markdown отдаётся Саше в чат.
- **Независим от:** `MoveFromLoop` (v1 синк контактов, итерация 1 мониторинг, итерация 1.5 архивация), `ExchangeMonitor`. Общий только источник токена (`LOOP_TOKEN`), код и state не пересекаются.
- **Использует паттерн (не код) из:** `~/USERTOOLS/MoveFromLoop/` — структура `pkg/`, `scripts/` (не нужны в этой итерации — CLI одноточечный), `tests/`, `.env.example`, `pyproject.toml`, `venv_linux/`.
- **Скилл-зависимость:** `~/.hermes/skills/mattermost-loop-api/SKILL.md` (v2.0.0, devops, канонический) — справочник по эндпоинтам/pitfalls Loop API, применим и к этому инструменту. Дубликат `~/.hermes/skills/productivity/mattermost-loop-api/SKILL.md` (v1.0.0, содержит хардкод токена) — чистка вне рамок этого ТЗ (решение Q5, см. §6).

## §11 Решения брифа (27.08.2026)

1. **Q1 — Размещение.** Отдельный новый инструмент/ТЗ `TZ/LoopChannelDigest/LoopChannelDigest_TZ.md` (не секция внутри `MoveFromLoop_TZ.md`, несмотря на предусмотренную там «итерацию 2» в §AH). Обоснование: разный жизненный цикл — stateless on-demand vs continuous monitoring/state.
2. **Q2 — HTTP-клиент.** Новый лёгкий клиент на `curl`+`subprocess` в самом инструменте (`client.py`); `~/USERTOOLS/MoveFromLoop/movefromloop/loop_api.py` не трогаем и не расширяем. Дублирование ~50 строк HTTP-обвязки (retry/backoff) — принятая цена за отсутствие риска зависания `requests`.
3. **Q3 — Крон-режим.** Только on-demand по явному запросу в чате в этой итерации. Крон, авто-доставка в Telegram — не закладываются.
4. **Q4 — Порог усечения треда.** Дефолт: **20 сообщений/тред**, **~4000 символов суммарно на тред**. Калибровка — по факту первых реальных прогонов, не строгая константа на все времена.
5. **Q5 — Чистка утечки токена.** Подтверждена находка (открытый текст токена Loop в `~/.hermes/skills/productivity/mattermost-loop-api/SKILL.md` v1.0.0) — почистить, но **отдельной правкой скилла вне рамок этого ТЗ**, исполнитель — сторонний по отношению к `LoopChannelDigest`.

## §12 Критерии успеха

- [ ] `python -m loop_channel_digest --channel <name> --since <date> --until <date>` на живом Loop отрабатывает без исключений, возвращает валидный JSON на stdout.
- [ ] По умолчанию (`--topics` не указан) обрабатываются ВСЕ подтопики канала.
- [ ] Треды внутри каждого топика кластеризуются по `root_id` корректно (корень + все прямые ответы в одном треде).
- [ ] Авторы резолвлены в ФИО через один батч-вызов `POST /users/ids`; при 502/неполном резолве — fallback на `username`, инструмент не падает.
- [ ] Треды длиннее 20 сообщений/4000 символов — усекаются с пометкой `[...N сообщений пропущено...]`, не выбрасываются целиком.
- [ ] Инструмент не создаёт и не изменяет `state/`, `loop_rules.yaml`, `contacts.enc`, файлы `MoveFromLoop`/`ExchangeMonitor`.
- [ ] `movefromloop/loop_api.py` не изменён (git diff пуст на этом файле после реализации).
- [ ] Финальный markdown-дайджест (сгенерированный моделью текущей сессии на основе JSON-агрегата) соответствует формату §7.1: заголовок, темы (суть+статус+участники), блок «Ключевые вкладчики-эксперты», без временных меток/цитат/FF-структуры.

## Контракты экосистемы

### Источник истины
- Владелец сообщений и каналов: Loop / Mattermost (`api_loop`, `https://loop.tutu.ru`)

### Входные контракты
| Поле | Тип | Обязательность | Источник (кто отдаёт) | Формат/enum |
|---|---|---|---|---|
| channel | str | required | LLM-сессия / Пользователь | имя или имя канала Loop |
| since | datetime(iso8601) | required | LLM-сессия / Пользователь | начало временного окна YYYY-MM-DD |
| until | datetime(iso8601) | required | LLM-сессия / Пользователь | конец временного окна YYYY-MM-DD |
| topics | str | optional | LLM-сессия / Пользователь | "all" или список названий топиков через запятую |
| format | enum[json, md] | optional | LLM-сессия / Пользователь | формат CLI-вывода (json по умолчанию) |

| Поле | Тип | Потребитель (кто получает) | Формат/enum |
|---|---|---|---|

| until | datetime(iso8601) | LLM-сессия (Сирень/default) | конец окна |
| topics[*].name | str | LLM-сессия (Сирень/default) | название подтопика Mattermost |
| topics[*].threads[*].root_author | str | LLM-сессия (Сирень/default) | ФИО ("Фамилия Имя") или username автора |
| topics[*].threads[*].participants | str | LLM-сессия (Сирень/default) | список ФИО/username участников треда |
| topics[*].threads[*].truncated | bool | LLM-сессия (Сирень/default) | флаг усечения треда по лимиту сообщений/символов |

### Зависимости
- Получает от: [Loop API v4 (`api_loop`)]
- Отдаёт: [LLM-сессия (default профиль для синтеза в чат)]

### Breaking changes policy
- Изменения CLI-интерфейса `--channel`, `--since`, `--until`, `--format` требуют обновления скилла `loop-channel-digest`.
- Формат JSON-вывода CLI стабилизирован для парсинга текущей сессией.

### Границы («что НЕ трогать»)
- Не пишет в `contacts.enc`, `WorkVault/Entities/`, Telegram или БД.
- Не модифицирует и не вызывает `movefromloop/loop_api.py` (использует собственный curl-клиент).
- Не изменяет настройки каналов и топиков в Loop.
