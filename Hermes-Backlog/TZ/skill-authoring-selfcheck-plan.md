## Часть 1 — Механизм загрузки «при каждой правке»

### Варианты

**A. Расширить `description` скилла триггерами.**
Добавить: «обнови скилл», «добавь в скилл», «патч скилла», «создай скилл», «skill_manage», «напиши скилл», «отредактируй скилл», «skill authoring».
- Плюсы: работает автоматически, не нагружает базовый контекст.
- Минусы: срабатывает только если запрос Саши содержит явное слово-триггер. Если агент правит скилл в рамках более широкой задачи («допили hermes-feature» → правка SKILL.md без слова «скилл» в запросе) — не сработает.
- Риск: description раздувается, приближается к лимиту 1024 символов.

**B. Строка в `~/.hermes/hermes.md`.**
Добавить: «При любом использовании `skill_manage` (create/patch/delete) или правке `SKILL.md` — сначала загрузи скилл `skill-authoring-principles` и применяй его правила write discipline».
- Плюсы: hermes.md автозагружается в каждую сессию → правило видно всегда, независимо от формулировки запроса. Гарантированное срабатывание в момент вызова `skill_manage`.
- Минусы: +1 строка постоянного контекста (незначительно, <200 символов).
- Риск: минимальный.

**C. Комбо A+B.**
- Плюсы: дублирование → максимальная надёжность. Description ловит человеческие формулировки, hermes.md ловит инструментальные вызовы.
- Минусы: небольшое дублирование сигнала.

### Рекомендация: **вариант C (комбо)**

Основную гарантию даёт **B** (hermes.md перехватывает `skill_manage` независимо от текста запроса). **A** — страховка на случай, если агент правит SKILL.md через `patch`/`write_file` в обход `skill_manage`. Стоимость обоих — копеечная, надёжность растёт мультипликативно.

## Часть 2 — Что должен содержать skill-authoring-principles v2.0

Структура — **чеклист агента-автора**, три фазы + два справочных блока.

### A. Pre-flight (перед правкой)

- **Размер сейчас:** `wc -c <SKILL.md>`. Если >15k — сначала compression pass, потом правка. Если >20k — вынос в `references/` обязателен.
- **Дубли:** `grep -i "<ключевое слово>" SKILL.md` + быстрый скан 2–3 смежных скиллов (`related_skills`). Похожий питфолл/правило есть → merge, не append.
- **Правильный owner:** питфолл принадлежит скиллу, где знание будет **применено в следующий раз**, а не где инцидент обнаружен. Спросить: «в каком скилле я буду читать этот питфолл, чтобы не наступить снова?».

### B. При добавлении (write discipline)

- **Merge > Append:** новый питфолл сначала ищется среди существующих, объединяется если есть overlap.
- **≥300 символов добавлено → compression pass:** перечитать соседние параграфы, слить повторы, убрать хеджирующие обороты («стоит отметить», «важно понимать»).
- **Блок >500 символов (worked example, длинная процедура, историческая справка) → `references/<topic>.md`,** в SKILL.md остаётся 1-строчный pointer.
- **Language policy:** English для правил/процедур/чек-листов/таблиц (компактнее на ~2× по токенам, ближе к обучающему корпусу инструкций). Русский — только для прямых цитат Саши, исторических прецедентов с датами и блоков `> Context (RU):`. Названия скиллов — as-is.

### C. Post-flight (после правки)

- **Version bump обязателен.**
  - patch (x.y.**Z**): опечатка, уточнение формулировки, исправленная ссылка.
  - minor (x.**Y**.0): новый раздел / workflow / питфолл / триггер в description.
  - major (**X**.0.0): переименование, сломанные ссылки, смена структуры.
- **Related skills alive:** каждое имя в `related_skills:` резолвится через `skills_list()`.
- **Description ≤1024 символов.**
- **Growth gate:** если файл вырос >10% относительно pre-flight — compression pass **обязателен** перед сохранением.
- **Кеш:** при переименовании/удалении секций — verify в новой сессии.

### D. Типы скиллов (краткий справочник)

| Тип | Содержимое | Границы |
|---|---|---|
| Prompt-only | Только SKILL.md | Правила, workflow, чек-листы |
| С кодом | SKILL.md + `scripts/` | Скрипты ≤200 строк; больше — USERTOOLS |
| MCP | SKILL.md + конфиг сервера в `references/` | Конфиг не в основном файле |

### E. Common Pitfalls (только специфичные для авторства скиллов)

- **Append вместо merge** → скилл раздувается за месяцы незаметно.
- **Питфолл в wrong skill** (owner = место обнаружения, не место применения) → дублирование, расхождение при правках.
- **Description >1024** → скилл не грузится, тихий отказ.
- **`platforms: [all]`** → синтаксис невалиден, скилл не грузится (правильно: явный список).
- **Новый скилл без проверки триггер-конфликтов** → `skills_list` + grep по descriptions перед созданием.
- **Ссылка «см. скилл X» вместо дублирования** — referenced скилл физически не грузится, ссылка бесполезна если оба не в одном `skills=[...]`.

**Итоговый целевой размер v2.0:** 5–7k символов SKILL.md (сейчас v1.1 = ~5.9k). Прирост правил компенсируется переводом на English и выносом worked examples в `references/`.

## Часть 3 — Скорректированный план действий

### Шаг 1 — Доработка `skill-authoring-principles` до v2.0

**Исполнитель:** Sonnet-5 (одноразовый cron по этому плану).
**Что делает:**
1. Reшрайт SKILL.md по структуре Часть 2 (A→B→C→D→E) на English (кроме цитат/дат).
2. Расширяет `description` триггерами варианта A (Часть 1).
3. Bump `version: 2.0.0` (major — смена структуры).
4. Worked examples (если есть) → `references/authoring-examples.md`.
5. Проверка: `wc -c SKILL.md` ≤ 7000, description ≤ 1024, все `related_skills` резолвятся.

### Шаг 2 — Интеграция: гарантированная загрузка при правке

**Исполнитель:** ручная правка Сашей (одна строка) или Sonnet-cron.
1. В `~/.hermes/hermes.md` добавить блок:
   ```
   ## Правка скиллов
   При любом вызове `skill_manage` (create/patch/delete) или прямой правке файла `SKILL.md` — сначала загрузи скилл `skill-authoring-principles` (`skill_view(name='skill-authoring-principles')`) и применяй его чеклист pre-flight → write → post-flight.
   ```
2. Триггеры в description скилла (Шаг 1, п. 2) — уже сделаны.

### Шаг 3 — Тестирование

1. Открыть новую сессию, попросить агента: «добавь в скилл `tz-workflow` питфолл про X». Проверить: `skill-authoring-principles` подгрузился (виден в контексте), чеклист применён (grep на дубль сделан, version bumped, размер проверен).
2. Открыть новую сессию, вызвать `skill_manage` напрямую в задаче без слова «скилл» в запросе (например: «допили hermes-feature: обнови секцию про модели»). Проверить: `skill-authoring-principles` подгружен через hermes.md.
3. `wc -c ~/.hermes/profiles/tz-dev/skills/devops/skill-authoring-principles/SKILL.md` ≤ 7000.
4. `skill_view(name='skill-authoring-principles')` — валидная frontmatter, version 2.0.0.

**Критерии успеха (проверка через 2–4 недели):**
- Все правки скиллов за период содержат version bump.
- Ни одна правка не добавила дубль питфолла (spot check: 3 случайных правки).
- Топ-5 bloat-скиллов **не выросли** (baseline на 23.07.2026 фиксируется отдельно).

## Часть 4 — Язык скиллов: рекомендация

**Не отдельная миграция, а правило v2.0.** В `skill-authoring-principles` v2.0 добавляется Language Policy (Часть 2, раздел B): новый контент пишется на English, русский — только для цитат Саши и исторических блоков `> Context (RU):`. Старый русский контент **не переводится массово** — он естественно вытесняется при следующих правках согласно правилу «pre-flight → compression → merge».

Массовая миграция всех скиллов на English — отдельное ТЗ, не входит в v2.0. Приоритет: сначала работает механизм «делать хорошо сразу», через месяц смотрим — надо ли догонять старьё отдельным проходом.
