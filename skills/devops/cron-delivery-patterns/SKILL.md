# Cron delivery patterns (Hermes)

Класс: выбор `deliver` при создании крон-задач. Ошибка здесь даёт **двойные доставки** в чат и **ежечасный спам** из stdout.

## Главное правило

Прежде чем ставить крон, посмотри, что делает скрипт:
1. **Сам шлёт в Telegram** по HTTP (через Bot API / `send_telegram_message` / curl)? Тогда `deliver='local'` — иначе скрипт отправит сообщение, И крон-ранер доставит stdout ещё раз → дубль.
2. **Печатает в stdout при каждом прогоне** (например, `print(json.dumps(result))` в отчёте)? Тогда даже при тихой работе крон каждый тик будет шлётить вывод в чат, если `deliver='origin'` → спам. Ставь `deliver='local'`, чтобы вывод уходил только в `~/.hermes/cron/output/`.
3. **Молчит при пустой выборке** (пустой stdout → `no_agent` крон не отправляет ничего, паттерн watchdog)? Это нормально; `deliver` почти не важен, но `local` безопасен.

Rule of thumb: **`deliver='origin'` только для agent/LLM-кронов, где stdout/ответ агента и есть сообщение пользователю.** Для `no_agent` script-кронов, у которых скрипт сам управляет доставкой или печатает служебный вывод, — всегда `deliver='local'`.

## Питфоллы

- **Двойная доставка digest-крона**: если скрипт сам шлёт сводку в Errors (channel :11112) через `send_telegram_message`, а крон стоит с `deliver='origin'`, пользователь получит сообщение дважды (сначала скрипт, потом крон-доставка stdout). Решение: `deliver='local'`.
- **Ежечасный JSON-спам**: скрипт reconcile печатает `{"created":0,...}` в stdout на каждый запуск. С `deliver='origin'` отчёт приходит каждый час даже без событий. `deliver='local'` убирает шум, лог остаётся в файле.
- **Не верь названию скрипта** — читай его код перед выбором `deliver`. digest (`--dry-run` печатает текст, без него — сама отправляет, stdout пуст) vs reconcile (всегда печатает JSON).

## Шаги при создании no_agent script-крона

1. Прочитай скрипт (`read_file` / `execute_code`) — определи: шлёт в TG сам? печатает в stdout? молчит при пустом?
2. Выбери `deliver`:
   - скрипт сам шлёт ИЛИ печатает служебный вывод → `deliver='local'`
   - скрипт только выводит в stdout то, что нужно показать юзеру → `deliver='origin'`
3. Создай: `cronjob(action=create, no_agent=true, script=<name>, schedule=..., deliver=<по шагу 2>)`. `script` резолвится в `~/.hermes/scripts/`.
4. Проверь на диске: grep по `~/.hermes/cron/jobs.json` — id, schedule, deliver, enabled.

## Пример из практики (ErrorBus, 26.08.2026)

Из 3 ErrorBus-кронов:
- `error_bus_daily_digest.sh` → `digest.py` без `--dry-run` **сам шлёт сводку** в Errors :11112, stdout пуст → `deliver='local'`.
- `error_bus_reconcile.sh` → `reconcile.py` **печатает JSON каждый запуск** + сам шлёт fail-события → `deliver='local'`.
- `error_bus_retention.sh` → раз в месяц → `deliver='local'`.

Все три `no_agent=true`. При `deliver='origin'` reconcile спамил бы JSON ежечасно.

## Разовая вариация регулярного крона (одна конкретная дата)

Когда нужен **ровно один** прогон крона с особой логикой на конкретную дату (например, план-версия апстрим-чека после стабилизации), а во все остальные дни — обычная штатная работа. Отработано 19.09.2026.

**Правильный приём: НЕ паузить/возобновлять штатный крон.** Пауза на одну дату требует отдельного вспомогательного «расписания возобновления» и легко забывается → штатный крон молчит и дальше, будущие запуски теряются беззвучно.

Вместо этого — комбинация из двух действий:
1. **Отдельный разовый крон** `cronjob(action=create, schedule='<ISO-дата>T<время>', repeat=1)` с вариантным промптом/скриптом. Сам себя удалит после одного запуска.
2. **Временный date-гард в штатном кроне**: `cronjob(action=update)` дописать в конец штатного промпта строку: «Если сегодня <дата> — ответь ровно [SILENT] и ничего больше (в эту дату версию X выдаёт отдельный разовый крон — дублировать нельзя)». В остальные дни штатный ведёт себя как обычно.

Достоинства: будущие штатные запуски (до и после даты) работают автономно, ручной активации не требуется, гард не влияет на другие даты. **После** целевой даты гард из промпта штатного крона стоит убрать (отдельная команда пользователя) — иначе он навсегда остаётся хвостом, ссылающимся на несуществующий разовый крон.

## Полный промпт крона — читать из jobs.json, не из списка

`cronjob(action=list)` возвращает только `prompt_preview` (обрезан). Реальный полный `prompt` лежит в `~/.hermes/cron/jobs.json`:
- структура: dict с ключом `jobs` (список); у каждой джобы поле **`id`** (а не `job_id`), `prompt`, `schedule` (dict с `expr`/`display`), `script`, `skills`, `enabled_toolsets`.
- читать python-скриптом через файл (`write_file /tmp/x.py` + `terminal python3 /tmp/x.py`), а не инлайн `python3 -c` — инлайн блокируется gateway-guard на ВМ.
- точный промпт из jobs.json нужен при доработке существующего крона (например, чтобы не потерять стандартный текст перед добавлением date-гарда).

## Одноразовая верификационная задача после манипуляций с данными (schedule 'in 1m')

Когда после правок (удаление строк/сброс реестров/включение флага в кроне) нужно проверить сквозную боевую цепочку (крон → код → уведомления) — **не запускать команду руками в чате**, а ставить одноразовый крон:
`cronjob_manage(action='create', schedule='in 1m', repeat=1, deliver='origin')` с self-contained промптом, где:
- точная команда (включая env-флаги, например `export PFS_POST_SWITCH=1`);
- явный список ожидаемых сущностей/встреч, чтобы отчёт был сверяемым;
- что проверить в реестрах/файлах после прогона;
- правило тишины: если доставку штатно делает другой крон (например `pfs_notify`) — верификационный крон сам ничего не дублирует.

Так проверка идёт тем же путём, что и боевой крон, а отчёт приходит в чат автоматически.

## Периодический отчёт о ходе работ (progress-report) — «крон каждые N минут»

Когда Саша просит «докладывай каждые N минут о ходе работ» (например, пока dev-графы доезжают до конца) — ставится `cronjob(action=create, schedule='every 10m', deliver=<origin-топик>, repeat='forever')` с agent-промптом, который:

**Шаг 0 — сначала ищи устоявшийся формат того же класса, не изобретай новый промпт.** Перед тем как писать self-contained агентный промпт для периодического отчёта, сделай `cronjob_manage(action='list')` и проверь, нет ли уже крона на ту же тему (канбан-статус, сводка по графам, digest и т.п.). Если есть — у пользователя уже есть любимый формат (часто через готовый `script` в `~/.hermes/scripts/` + короткий описывающий промпт). Возьми его: переиспользуй тот же `script` и/или формулировку через `cronjob_manage(action='update')` на новом кроне, а не изобретай вывод заново. Изобретение нового формата ведёт к правке-переделке по команде Саши «у меня уже был крон, его формат был хороший» (пример: канбан-статус — устоявшийся `kanban_status_report.py` + «дай краткий разбор: что блокер, что зависло, что требует вмешательства Саши»).

1. **Динамически собирает охват по префиксу, а НЕ по захардкоженному списку слагов.** Одна и та же формулировка «отфильтруй все открытые (не done/archived) карточки, чей title начинается с `DEV/`» — тогда любая новая тема попадает в отчёт автоматически. Если захардкодить список из 5 графов — новая тема молча не приходила бы (именно так и было в этой сессии: крон итерировал по жёсткому списку, новый DEV-граф не отображался). Расширению ахруп: при появлении новой пары графов промпт приходится править вручную.
2. **Признак завершения — явно в промпте:** «если все графы done — сообщи *все графы завершены* и стоп». Так крон сам сигналит, что мониторинг больше не нужен, и его можно снимать (или снять по команде Саши).
3. **Deliver — только origin-топик** (и тот, откуда пришёл запрос), без дублей в личный DM. Для этого явно `deliver='telegram:<chat_id>:<thread_id>'` (не полагаться на дефолт, см. раздел про one-shot).
4. **Ничего не изменяет** — только чтение (`hermes kanban list` и фильтр).

Прекращение: `cronjob_manage(action='remove', job_id=...)` по явной команде Саши «останови/отмени крон» или после сигнала «все завершены». Это операторский крон слежения, не часть пайплайна — не переустанавливать автоматически.

## Перевод существующего agent-крона в no_agent (скрипт-крон)

Когда задача экономии/стабильности требует убрать LLM из агентного крона (`no_agent: false → true`, пример: `pfs_batch` hourly `run-pending`):

**Нельзя просто повесить целевую команду raw-скриптом.** Если команда **всегда печатает сводку в stdout** (например `run-pending` печатает `=== process_pending: N … ===` и счётчики даже при 0 файлов), то с `deliver=<чат>` каждый тик уйдёт рутинная сводка — ровно то, что агентный крон молчал из-за системного `[SILENT]`. Raw-скрипт ломает тишину.

**Рабочий паттерн — обёртка-фильтр stdout:**
```bash
OUTPUT=$(cd …/Tool && .venv/bin/python -m tool run-pending)  # точная команда + env-флаги
CODE=$?
[[ $CODE -eq 0 ]] && exit 0    # успех → пустой stdout → тишина
# ненулевой exit (есть error>0) → stdout доходит до deliver и watchdog-алерта
```
Потом flip джобы: `script=<обёртка>`, `no_agent=true`, `prompt=""`, **`deliver` сменить `local` → топик ошибок** (иначе и успех, и ошибка останутся в логе крона, никто не увидит).

Ключевые правила:
1. **Обёртка обязана глотать stdout при exit 0.** Иначе raw-вывод команды заспамит чат каждый тик.
2. **`deliver` = топик ошибок** (`telegram:<chat>:<thread>`), не `local` и не чужой топик. Проверь, куда шлёт отдельный notify-крон, — ошибки batch не смешивать с ним.
3. **Не звать `hermes send` из обёртки** при native `deliver` — получится двойная отправка. Один канал ошибок: watchdog Hermes по ненулевому exit.
4. **Не дублировать ErrorBus** отдельным wrap'ом: если ошибка публикации уже стреляет в ErrorBus из самого инструмента, добавление своего канала уведёт её и в `:11112`, и в топик ошибок одновременно.
5. **Экономия**: 0 токенов на тик, LLM-агент уходит (пример: ~$0.09–0.11/день).
6. **Включение только по явному глаголу Саши «ставь кроны»** (operator-hold класс O): положить скрипт на диск можно, но `jobs.json` не писать заранее.

Приёмка перевода — проверить самому до боевого прогона, без публикации:
- **(a) пустой прогон → тишина:** `OUT=$(обёртка 2>&1); echo "EXIT=$? STDOUT=${#OUT}"`. Ожидание: `EXIT=0 STDOUT=0` — обёртка проглотила stdout при exit 0. Если обёртка имеет dry-run, сначала прогнать целевую команду с `--dry-run` и убедиться, что exit 0 → это и есть «пустой» исход.
- **(b) синтетический ненулевой exit:** bash-сниппет `OUTPUT=$(cmd с выводом) CODE=1; [[ $CODE -eq 0 ]] && exit 0; printf '%s\n' "$OUTPUT"; exit $CODE` — убедиться, что stdout пробрасывается наружу при exit 1 (это и поедет в топик ошибок). Не гонять реальную ошибочную публикацию ради теста.
- **Флип сверить на диске:** python-чтение `~/.hermes/cron/jobs.json` — у переведённой джобы `no_agent=true`, `script=<обёртка>`, `prompt=''`, `deliver=<топик ошибок>`; у соседнего notify-крона реквизиты **не изменились** (bit-identical).

## Массовая пауза/возобновление кронов (по команде «останови кроны»)

Когда Саша просит остановить несколько кронов разом («останови кроны OFC и MFKT и MOFS и все остальные»):
1. **Сначала `cronjob_manage(action='list')`** — никогда не угадывай job_id. Считай точный id каждой цели по имени из списка (в списке поле называется `job_id`, в jobs.json — `id`).
2. **Только один pause на один tool_call.** Локальный отложенный `tool_call` отвергает массив `calls` из нескольких записей для local-инструмента: `"tool_call takes exactly one entry for local tools; you sent N"`. Батчить несколько `pause` в один вызов нельзя — каждый крон паузится отдельным вызовом. Пробовать батч = тратить вызов на отказ.
3. **Уже приостановленные не трогай** — пауза им не нужна, лишний вызов и шум в отчёте.
4. **Перепроверь активные по итогу**: только те, чей `state` после ответа стал `paused`, реально остановлены. Сообщи по именам, какие переключились.
5. Минутные/часовые кроны (`*/3`, `*/5`, doorbell) могут выстрелить между `list` и паузой — это нормально, не ошибка.

Возобновление — зеркально: `resume` по одному job_id на вызов.
