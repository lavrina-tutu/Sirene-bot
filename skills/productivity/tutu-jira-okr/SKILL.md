# TUTU Jira OKR

Работа с целями (Objective) и ключевыми результатами (KR) в Jira ТУТУ, проект **OKRS** (департамент АИД). Авторизация и базовые curl-паттерны — см. `tutu-confluence-jira` (тот же `JIRA_TOKEN`/`JIRA_BASE_URL`), здесь не дублируется.

## Overview

OKR в Jira — не отдельная сущность, а обычные issue двух типов:
- **Objective** — issuetype "Большая задача" (id=6), различаются по `Тип OKR` (customfield_43701): `Functional Annual OKR` (годовая) или `Functional Quarterly OKR` (квартальная)
- **KR** — issuetype **UserStory** (id=12809), связаны с Objective через issuelink **Contains** (не `parent`!)

Период (год/квартал) — по `fixVersion`, НЕ по тексту названия. Маркеры `Q1`/`Q2`/`Q3`/`Q4` в названии почти всегда означают дедлайн метрики, а не период отчёта — не полагаться на них при классификации.

## When to Use

- Выгрузка списка целей АИД (годовых/квартальных) с чекин-полями
- Построение иерархии Objective → KR → квартальные Objective → их KR для отчёта
- Сверка данных: цель↔её KR, годовая цель↔её квартальные цели (расхождения % и текста)
- Подготовка отчёта закрытия квартала/года в формате Obsidian .md
- Создание новых KR/Objective задач в Jira (напр. клонирование Q1-набора KR под Q2 для той же годовой цели)
- Пометка задач на удаление (переименование, без физического удаления из Jira)
- Выборка задач АИД по периоду/статусу (напр. "что ещё не закрыто за Q2")

## Карта полей чекина (customfield ID)

| Поле | customfield ID |
|---|---|
| Тип OKR | `customfield_43701` |
| Подразделение | `customfield_43743` |
| Уровень уверенности | `customfield_43706` |
| Что было сделано | `customfield_43822` |
| Описание риска/проблемы | `customfield_43717` |
| Текущее значение метрики | `customfield_43713` |
| Плановое значение метрики | `customfield_43711` |
| % выполнения (0-100%) | `customfield_43782` |
| Дата обновления % выполнения | `customfield_43715` |

## Правило по умолчанию: только подразделение АИД

**Любая выборка KR/Objective (поиск, чекин-анализ, сверка, отчёт) фильтруется по `cf[43743] = "АИД"` по умолчанию**, даже если запрос не упоминает подразделение явно — задачи других подразделений (Отели, Авиа, ЖД, HR, GR, КАМ и т.д.) не подмешивать в результат, даже если они технически подходят под остальные условия (период, ключевые слова в названии, статус). Это касается и проекта OKRAID — там тоже есть задачи разных подразделений, `cf[43743]` фильтруется одинаково в обоих проектах. Если пользователь явно просит другое подразделение или "все подразделения" — тогда фильтр снимается/меняется, но это исключение, не базовый режим.

## JQL-паттерны

Годовые цели департамента:
```
project = OKRS AND issuetype = 6 AND cf[43743] = "АИД"
  AND cf[43701] = "Functional Annual OKR" AND fixVersion = "2026 ф.г."
```

Квартальные цели (замени fixVersion):
```
project = OKRS AND issuetype = 6 AND cf[43743] = "АИД"
  AND cf[43701] = "Functional Quarterly OKR" AND fixVersion in ("Q1 2026","Q2 2026","Q3 2026","Q4 2026")
```

**KR не выбираются JQL напрямую** — только через `issuelinks` каждой Objective:
```bash
curl -s -H "Authorization: Bearer $JIRA_TOKEN" -H "Content-Type: application/json" -X POST \
  "$JIRA_BASE_URL/rest/api/2/search" \
  -d '{"jql":"key in (OKRS-640,OKRS-654,...)","maxResults":100,
       "fields":["summary","issuelinks","customfield_43701","..."]}'
```
Затем в Python: для каждой Objective пройти `fields.issuelinks`, взять те с `type.name == "Contains"`, `outwardIssue` — это KR/дочерняя квартальная цель. `inwardIssue` — родитель (обратное направление).

Получить дочерние ключи для всех Objective проекта разом — по годовой цели-корню (`customfield_44601` = "Вложенные задачи", строка со списком ключей через запятую) или обходом issuelinks, если нужна многоуровневая иерархия.

## Питфоллы

- **SR-задачи затесались в Contains-цепочку** — issuelink Contains у Objective может случайно указывать на задачу другого проекта (напр. `SR-XXXXX`, Self-Review). Фильтровать KR по `issuetype.name == "UserStory"`, отбрасывать всё остальное.
- **OKRAID-задачи не имеют поля «Тип OKR»** — `customfield_43701` вернётся `None`. Если такая задача попала как KR через Contains, определять период/тип по `fixVersions`, не по типу OKR. Связь OKRS↔OKRAID пока не формализована — фиксировать отдельно, не подмешивать в основную иерархию без явного решения пользователя.
- **`parent` в JQL не работает для иерархии OKR** — реальная связь только через issuelinks Contains. `JQL: parent = OKRS-XXXX` вернёт 0 результатов даже если видна иерархия в интерфейсе Jira.
- **Маркеры Q1-Q4 в названии ≠ период отчёта** — напр. `KR5...не менее 300 за Q4 2026` — это годовой KR с дедлайном в Q4, а не квартальный KR за Q4. Классифицировать строго по `fixVersion`, а не по regex на тексте.
- **Пустые чекин-поля у части KR — это нормально**, не баг выгрузки: годовые KR часто не ведутся детально (чекин заполняется только на уровне Objective), будущие кварталы (ещё не наступившие) естественно пустые.
- **`Что было сделано` может дословно дублироваться** между Objective и её единственным KR (когда цель = один KR) — это ожидаемо, не расхождение.

## Формат сверки данных

Сверка = сопоставление 5 чекин-полей между двумя уровнями иерархии (Objective↔её KR, или годовая цель↔её квартальные цели):
1. Что записано на верхнем уровне (текст + % + метрика)
2. Совокупное описание нижнего уровня (перечислить KR/квартальные цели построчно с их % и текстом)
3. Расчёт среднего % по нижнему уровню, сравнение с % верхнего уровня
4. Комментарий: `ОК` (совпадает) / `⚠️ <кратко суть расхождения>` (текст-заглушка, % расходится, риск не перенесён и т.п.)

**Найденные расхождения только фиксируются в отчёте — не исправлять их самостоятельно** (ни текст, ни %, ни статус) без явного решения Саши.

Для отчёта «актуализация годовой цели по Q1+Q2»: годовая цель уже содержит итоги Q1 — предлагать **объединённый** текст (Q1 + новые факты из Q2-целей), а не переписывать с нуля. Не выдумывать данные вне того, что явно есть в Jira.

## Формат отчёта в Obsidian (.md)

- **Описание файла вверху** — компактный callout `> [!info]`: что за файл, откуда данные, что внутри, какие плагины нужны (обычно никакие — стандартный Obsidian 1.0+ хватает: callouts, wiki-ссылки, таблицы). Держать описание минимальным: только то, что нужно получателю ПРЯМО СЕЙЧАС, чтобы понять и открыть файл. Не добавлять по инерции строки вроде "рядом лежит файл X с полными/резервными данными" — если это не нужно получателю отчёта в моменте, это лишнее и подлежит удалению по первому же замечанию (прецедент: пользователь прямо попросил убрать упоминание бэкап-файла как несущественное). Перед отправкой файла — перечитать callout и вычеркнуть всё, что не отвечает на вопрос "как открыть и что тут лежит".
- **Иерархия:** годовая цель → её KR → её квартальные цели → их KR, каждая годовая цель со всей веткой обёрнута в свой `> [!note]`/`[!tip]`/`[!success]` и т.д. (циклический набор типов) — даёт визуально разный фон на каждую ветку.
- **Ссылки на детальные блоки** — Obsidian wiki-ссылки `[[#Заголовок точного текста|текст ссылки]]`, НЕ markdown `#anchor` (Obsidian их не резолвит) и НЕ HTML `<a name=...>` (ненадёжно, лучше `<a id=...>` но wiki-ссылка проще).
- **⚠️ Экранировать `|` внутри wiki-ссылок как `\|`** — иначе markdown-таблица трактует его как разделитель столбца и вся строка/таблица ломается визуально. Проверка перед отправкой: посчитать неэкранированные `|` в каждой строке таблицы, должно быть одинаковое количество на всех строках.
- **Текст ссылки** — короткий вердикт/выжимка (`ОК` без лишних пояснений, или 1-2 строки сути расхождения), не generic слово вроде «Сверка».
- Полные текстовые описания (5 полей чекина) держать **только на одном уровне иерархии** (напр. только годовые), для остальных — компактная таблица + отдельный раздел сверки, не дублировать полный текст на каждом уровне (иначе файл разрастается до сотен KB без пользы).

## Формат сводной таблицы

Сводная таблица всегда идёт **первой** в файле отчёта (перед иерархией по разделам). Колонка `Что было сделано` (`customfield_43822`) — обязательная, не опускать даже если для части задач она пустая.

Колонки: `Ключ | Obj/KR | Квартал | Название | ФИО | Сверка <период>`.
- `Objective` сокращается до `Obj` (экономия ширины колонки).
- Колонка `Уровень` (Годовая/Квартальная) убрана — не нужна, дублируется через `Квартал`.
- `ФИО` — исполнитель задачи (`assignee.displayName` из Jira), берётся по каждому ключу через один batch-запрос `POST /search` с `jql=key in (...)`, не по одной задаче.

## Создание новых KR/Objective (клонирование по образцу)

Частый сценарий: скопировать набор KR с прошлого квартала (образец, напр. Q1) на новый квартал (Q2) для той же годовой цели, с заменой только квартальных маркеров и fixVersion.

### Порядок действий
1. **Всегда сначала утвердить постановку** — какие поля меняются (обычно: название/description с Q1→Q2, fixVersion), какие остаются идентичными (assignee, reporter, приоритет, Тип OKR, Подразделение, плановое значение метрики), какие обнуляются (все чекин-поля — уверенность/что сделано/риск/текущее значение/% выполнения должны быть **пусто**, не 0). Не начинать создание без явного "делай" от пользователя.
2. Прочитать образец: `GET /issue/{OLD-KR-KEY}?fields=summary,description,assignee,reporter,priority,fixVersions,customfield_43701,customfield_43743,customfield_43739,customfield_43711`.
3. **Создать задачу в 2 шага** — `POST /issue` с МИНИМАЛЬНЫМ набором полей (`project`, `issuetype: UserStory`, `summary`, `description`, `assignee`, `reporter`). Поля `fixVersions`, `priority`, `customfield_43701` (Тип OKR), `customfield_43743` (Подразделение) на этапе создания часто возвращают `400 "Field cannot be set. It is not on the appropriate screen"` — это нормально, не баг конфигурации.
4. **Перевести задачу в рабочий статус** через `POST /issue/{KEY}/transitions` (в проекте OKRS обычно id=101 "Planning"/аналог) — это открывает дополнительные поля на edit-экране.
5. **Дозаполнить оставшиеся поля** через `PUT /issue/{KEY}` после перехода статуса: `fixVersions`, метрика (`customfield_43739`), плановое значение (`customfield_43711` — **числом**, не строкой: `100`, не `"100"`, иначе `400 "Значение операции должно быть числом"`). `Тип OKR`/`Подразделение` могут прописаться автоматически по умолчанию/наследованию при переходе статуса — проверить финальным GET, не считать доработку законченной без верификации.
6. **Установить связь** `Contains`: `POST /issueLink` с `type.name="Contains"`, `inwardIssue` = родительская Objective, `outwardIssue` = новая KR-задача.
7. **Финальная сверка** — GET по новой задаче со всеми изменёнными полями + `issuelinks`, сравнить построчно с образцом (кроме заведомо разных полей).

### Питфоллы создания
- **`PUT`/`POST /issue` на многие customfield сразу после создания даёт `400`** — не значит, что поле нельзя установить вообще; часто оно просто недоступно на текущем статусе/экране. Решение — сменить статус транзицией, затем повторить PUT.
- **Числовые customfield как строка** → `400 "Значение операции должно быть числом"`. Передавать JSON-числом.
- **"Пусто" ≠ "0"** — если пользователь просит оставить чекин-поля пустыми, не передавать их в payload вообще (не отправлять `null` тоже обязательно, но лучше просто не включать поле в запрос), а не подставлять `0`/`""`.
- **Не переводить статус самого SR/OKR дальше, чем требуется** — транзиция используется только чтобы открыть нужные поля редактирования, не как способ "закрыть" или "согласовать" задачу без явной команды пользователя.
- **Разные проекты OKR требуют разные обязательные поля при создании Objective** — `POST /issue` с `issuetype="Большая задача"` в проекте **OKRAID** возвращает `400` с `customfield_10007 "Epic Name обязательно"`, которого нет в OKRS. Перед первым созданием Objective в незнакомом OKR-проекте проверить `GET /issue/createmeta/{PROJECT}/issuetypes/{id}` на обязательные поля, не считать поведение OKRS универсальным. Если Epic Name не указан пользователем явно — заполнить тем же текстом, что и summary (без доп. суффиксов в скобках).
- **OKRAID поддерживает те же issuetype, что и OKRS** (`Большая задача` id=6 для Objective, `UserStory` id=12809 для KR) — создание KR через `Contains` работает идентично между проектами. У KR в OKRAID `Тип OKR` (43701) тоже обычно пустой, как и в OKRS — не пытаться его заполнить, если в образце-KR он пуст.
- **Название/описание KR без квартального маркера** — если пользователь не просит привязку к кварталу (только к цели), префикс `summary`/`description` = `KR{порядковый номер}.O{номер цели}.` без `Qx`, где номер KR — по порядку создания (1, 2, 3...), номер цели — из названия родительской Objective (напр. родитель "O1..." → все KR получают `.O1.`). Этот префикс НЕ добавляется на шаге создания (`POST /issue`) вместе с текстом — сначала создать с телом текста как есть, затем сразу(!) на этапе финальной сверки проверить, что префикс присутствует и в `summary`, и в `description` идентично. Не полагаться на то, что пользователь укажет нужный префикс в первой формулировке текста KR — как правило он даёт только содержательный текст, а нумерацию KR/цели нужно уточнять и добавлять отдельным шагом (`PUT` после создания), если её нет с самого начала явно в постановке.

## Смена исполнителя (переназначение assignee)

Частый запрос: "найти задачи АИД (годовые + Qx) с исполнителем X, переназначить на Y".

### Поиск пользователя по ФИО
- `GET /user/search?username=<строка>` — **строка должна быть URL-кодирована как UTF-8 percent-encoding**, не передавать кириллицу напрямую в query string через `curl` без кодирования — Tomcat вернёт `400 "Invalid character found in the request target"` (кириллица как raw-байты в URL нарушает RFC 7230/3986). В bash проще всего через `--data-urlencode` с `-G`, или собрать URL в Python (`urllib.parse.quote`).
- Результат содержит `name` (логин, напр. `tsyba`) — именно это значение передавать в `assignee.name` при `PUT`, не `displayName`.

### Смена исполнителя
- `PUT /issue/{key}` с `{"fields": {"assignee": {"name": "<логин>"}}}` — простое текстовое поле, работает как обычный PUT (в отличие от многих чекин-customfield).
- Менять **только** явно перечисленные ключи из выборки — переназначение исполнителя **не каскадируется** на связанные задачи через Contains автоматически. Если у Objective есть дочерние KR, но в исходной выборке (напр. по `assignee = X`) присутствовал только сам Objective (а не все его KR) — значит остальные KR были на других исполнителях изначально, и их трогать не нужно, даже если они технически "принадлежат" той же цели.
- **Финальная верификация — одним batch-запросом**, не по одной задаче: `POST /search` с `jql=key in (KEY1,KEY2,...)`, поле `assignee`, сверить `displayName` у каждого ключа со списком.
- Формат для передачи пользователю — plain-text список `URL — Название` без markdown-таблицы, если явно попросили "чтобы было удобно скопировать в другой мессенджер" (таблицы плохо копируются в мессенджеры без потери форматирования).

## Пометка задач на удаление

⚠️ **КРИТИЧНО: переименование summary в "Удалить" может привести к РЕАЛЬНОМУ необратимому удалению задачи из Jira, не только к визуальной пометке.** Подтверждённый прецедент (4 задачи переименованы → позже той же сессии стали возвращать `404`) — полный разбор инцидента: `references/marking-for-deletion-incident.md`.

**Правила на основе этого прецедента:**
- Перед переименованием в "Удалить" — явно предупредить пользователя о риске фактического необратимого удаления, получить подтверждение с учётом риска.
- Не полагаться на немедленный GET после PUT как на доказательство "задача просто переименована и цела" — удаление может произойти асинхронно, позже. Если сохранность данных важна — выгрузить и сохранить поля задачи в WorkVault до переименования.
- Если пользователь позже обращается к ключу, ранее помеченному "Удалить", и получает `404` — это ожидаемый исход операции, не баг выгрузки — сообщить прямо.

**Процедура самого шага переименования:**
- Формат — уточнять у пользователя явно, не предполагать: в прецеденте было "название должно быть **строго** 'Удалить'" (полная замена summary, не префикс/суффикс, не `[Удалить] <старый текст>`).
- Менять **только** запрошенное поле (обычно только `summary`) — не трогать description/статус/связи/чекин-поля, если не попросили отдельно.
- Если задача — Objective с подзадачами через Contains, уточнить область: помечать только саму задачу, или её и все дочерние KR. Не включать вышестоящего родителя (`inwardIssue` Contains) в область по умолчанию — это отдельная цель верхнего уровня, не подзадача.
- Каждая последующая просьба "и ещё вот эту, но только её одну" — самостоятельная область, не расширять её на связанные задачи автоматически.
- `PUT /issue/{key}` с `{"fields": {"summary": "<новое значение>"}}` — простое текстовое поле, PUT принимает запрос (в отличие от чекин-customfield'ов), но см. предупреждение выше о скрытых последствиях.
- Верифицировать GET-ом сразу после каждой пометки — сравнить итоговый summary с запрошенным значением дословно. Этот GET подтверждает только факт переименования в моменте, не гарантирует, что задача останется доступна впредь.

## Задачи типа Dependency (внешние зависимости)

Отдельный issuetype, не Objective и не KR — задача-запрос на ресурс/действие от другой команды, блокирующая выполнение KR (напр. "К техблоку — выделить ресурс Python-разработчика на поддержку ML-сервиса"). Семантика полей:
- `reporter` — постановщик зависимости (обычно сам пользователь/руководитель АИД-направления, который формулирует запрос)
- `assignee` — исполнитель ИЗ ДРУГОЙ команды, который должен закрыть зависимость
- Связь с KR — через issuelink **Contains**, но в **обратном направлении**: Dependency — `inwardIssue` со стороны KR (т.е. `IN Contains` при обходе от KR), не `outwardIssue`. Обходить так же, как обычные KR (см. основной паттерн issuelinks выше), просто не путать направление при построении таблицы "с какой задачей связана".
- Не каждая Dependency обязана иметь связь Contains — если `issuelinks` пуст, зафиксировать это явно в отчёте/таблице ("нет связи Contains"), не считать багом выгрузки и не додумывать связь.

### Таблица со ссылками на Dependency + связанные задачи

Частый запрос: "выведи табличку — наименование (со ссылкой), автор, с какой задачей связана (со ссылкой), исполнитель по связанной задаче". Когда формулировка колонок в запросе пользователя неоднозначна (перечислены вперемешку два варианта состава колонок) — **переспросить точный список колонок одним предложением**, прежде чем строить таблицу, а не гадать какой из двух наборов имелся в виду.

## Экспорт таблиц в Excel (для Confluence/пересылки)

Когда пользователь просит "табличку, чтобы можно было скопировать в Confluence" или "как в Excel" — генерировать реальный `.xlsx` через `openpyxl`, а не полагаться на копирование markdown/TSV из чата (табуляция часто теряется при копировании из чат-интерфейса в буфер обмена). Готовый скрипт-шаблон: `scripts/build_xlsx_table.py` (заголовок жирным на заливке, перенос текста, кликабельные гиперссылки на Jira-ключи в нужных колонках, авто-ширина колонок, рамки). Сохранять в `WorkVault/Projects/<okr-tool|sr-tool>/...` (в личную папку сотрудника, если таблица касается конкретного человека) и делать `rclone sync` как обычно.

## Выборка задач по периоду и статусу

Частый запрос: "какие задачи АИД за период X ещё не в статусе Y" (обычно "не закрыто").

- Базовый JQL: `project in (OKRS, OKRAID) AND fixVersion = "<период>" AND cf[43743] = "АИД"`.
- **Питфол: `AND status != "Закрыта"` в JQL по нескольким проектам может вернуть `400 "Значение 'Закрыта' отсутствует для поля 'status'"`**, даже когда часть задач реально имеет этот статус — это не ошибка данных, а следствие разных workflow-схем статусов в разных проектах/типах задач в рамках одного мульти-проектного поиска. Решение: убрать `status != ...` из JQL, выгрузить все задачи по остальным условиям одним запросом, отфильтровать по `fields.status.name != "Закрыта"` в Python на стороне агента.
- Полезные поля для такой выборки: `summary, status, issuetype, assignee` — этого достаточно, чекин-customfield не нужен, если вопрос только про статус/владельца.
