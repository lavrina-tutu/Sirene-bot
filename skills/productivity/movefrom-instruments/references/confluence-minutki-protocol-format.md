## Как найти такую страницу по проекту

Страница "Минутки" — это **дочерняя** страница root-страницы проекта (`card.md: confluence_id`), не сама root-страница. Искать через:
```bash
source ~/USERTOOLS/ConfluenceSync/.env
curl -s -H "Authorization: Bearer $CONFLUENCE_TOKEN" \
  "https://dom.tutu.ru/rest/api/content/<root_confluence_id>/child/page?limit=50" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); [print(r['id'],'|',r['title']) for r in d.get('results',[])]"
```
Искать в списке заголовок, содержащий "Минутки" / "Задачи и договоренности".

## Два реальных формата таблицы (оба валидны, разные проекты используют разные)

### Формат А (2 колонки) — Trisigma, AI-ready
```html
<table><tr><th>Дата постановки</th><th>Задачи и Договоренности</th></tr>
<tr><td><time datetime="2026-07-07" /></td>
<td>
  <h2>Участники:</h2><ul><li>ФИО текстом (без mention)</li>...</ul>
  <h2>Решения:</h2><ul>...</ul>
  <h2>Блокеры:</h2><ul>...</ul>
  <h2>Задачи:</h2><ac:task-list>...</ac:task-list>
  <h2>Риски:</h2><ul>...</ul>
</td></tr>
</table>
```
Одна строка = один день/встреча. Участники — заголовок `<h2>Участники:</h2>` + `<ul>` внутри той же ячейки, **просто текст ФИО**, без `<ac:link>`/mention.

Trisigma: сортировка "последние сверху" (новая строка вставляется сразу после шапки).
AI-ready: сортировка "снизу-вверх" (новая строка добавляется в конец таблицы, перед строкой `вверх`) — **направление сортировки не универсально, уточнять для каждого проекта отдельно перед первой записью.**

### Формат Б (3 колонки) — AI-аналитик (AI-MAS)
```html
<table><tr><th>Дата</th><th>Участники</th><th>Итоги</th></tr>
<tr>
  <td><time datetime="2026-07-07" /></td>
  <td><ul><li>ФИО текстом</li>...</ul></td>
  <td>
    <h2>Решения:</h2><ul>...</ul>
    <h2>Блокеры:</h2><ul>...</ul>
    <h2>Задачи:</h2><ac:task-list>...</ac:task-list>
  </td>
</tr></table>
```
Участники — отдельная колонка, тоже просто текст ФИО (не mention), Решения/Блокеры/Задачи объединены в колонку "Итоги".

## Формат задачи (`<ac:task>`) — общий для обоих форматов

```xml
<ac:task>
<ac:task-id>101</ac:task-id>
<ac:task-status>incomplete</ac:task-status>  <!-- или complete -->
<ac:task-body>
  <ac:link><ri:user ri:userkey="8a8383b593a26ea60194abdf8d090020" /></ac:link>
  <текст задачи, обычно начинается с "Название проекта. ">
  <time datetime="2026-07-15" />
</ac:task-body>
</ac:task>
```

Ключевые находки:
- **Исполнитель задачи — реальный Confluence `@mention`**: `<ac:link><ri:user ri:userkey="..." /></ac:link>`. `userkey` — это Confluence Server internal user key (не email, не login, не modern `accountId` из Cloud API). Нужен резолв email/ФИО → `userkey` — источник этого маппинга **не найден** в текущей инфраструктуре AnywhereContacts/ExchangeGAL, это отдельный блокер для будущей реализации (вероятно `GET /rest/api/user?username=...` на Confluence Server API, не проверено).
- **"Тег проекта" — НЕ отдельный макрос/легенда.** Это просто вручную напечатанный текстовый префикс в начале текста задачи: `"Trisigma. <текст>"`, `"AI-ready.<текст>"`, `"AI-аналитик.<текст>"`. Никакой парсинг "легенды тегов снизу страницы" не нужен — префикс = название проекта как в `card.md` (или его разговорный вариант), напечатанное человеком руками.
- **Дата задачи — НЕ отдельный `<ac:date>` макрос.** Это inline `<time datetime="YYYY-MM-DD" />` **внутри** `<ac:task-body>`, после текста задачи (не отдельная колонка/поле).
- Участники в колонке "Участники"/блоке "Участники:" — **просто текст ФИО**, без mention/ссылки. Mention используется только внутри задач (кто исполнитель).

## Решено брифом с Сашей (09.07.2026) — стандарт для инструмента "Протокол from Summary"

1. **Формат таблицы — только формат А (2 колонки)**, как в Trisigma/AI-ready. Формат Б (3-колоночный, AI-MAS) — не используется для нового инструмента, остаётся легаси на своей странице.
2. **Новые встречи всегда вставляются сверху** (сразу под строкой заголовка) — единый стандарт для инструмента, независимо от того, что написано в текстовой подсказке конкретной существующей страницы (Trisigma говорит "сверху", AI-ready — "снизу-вверх"; новый инструмент игнорирует легаси-подсказку и всегда пишет сверху).
3. **Тег проекта в тексте задачи — отдельный реестр «как называть проект в тексте», не automatic из `card.md: name`.** Реальные теги в минутках не всегда совпадают со значением `name` (напр. slug `ai-transformaciya` → тег `"AI-ready"`, slug `ai-mas` → тег `"AI-аналитик"`). Реестр нужно собрать вручную по фактическим текстам в существующих минутках всех проектов, не выводить программно.

## Резолв Confluence `userkey` — РЕШЕНО (09.07.2026)

Источник маппинга найден и подтверждён рабочим на реальных данных:

- **По логину:** `GET /rest/api/user?username=<login>` — работает, но **Confluence username часто отличается от корпоративного login** (напр. `isereda`→`sereda`, `dnabiev`→`nabieva`, `kkrivorotov`→`krivorotov`, `azhirov`→`zhirov` — обычно просто фамилия без служебных букв). Нельзя полагаться на корпоративный login напрямую.
- **По ФИО — надёжный способ:** `GET /rest/api/search?cql=user.fullname~"ФИО"` (передавать кириллицу через `--data-urlencode`, не ручной percent-encoding). Возвращает `results[0].user.{username, userKey, displayName}`. Проверено на 24+ реальных сотрудниках — все нашлись с первого совпадения по полному ФИО.
- Оба способа читают из `dom.tutu.ru` (ConfluenceSync `.env`, `CONFLUENCE_TOKEN`), не из `hq.tutu.ru` (JIRA).
- Найденные `confluence_login`/`confluence_userkey` **обязательно сохранять сразу** в `contacts.enc` (см. `anywhere-contacts-architecture.md` — новые CUSTOM_FIELDS), чтобы не резолвить повторно того же человека при следующей встрече.
- Глобального листинга пользователей нет (`/rest/api/user/search` без точного username даёт 404 на этом Confluence Server) — резолв только точечный, по логину или по ФИО.

## Резолв участника, если ФИО в summary не совпадает с `contacts.enc` — РЕШЕНО (09.07.2026)

Базовый резолв участника — substring-match по `login`/`fio`/`email`/`aliases` в `contacts.enc` (`ContactStore.find_contacts`, простой код, не LLM). Если он **не находит** совпадения (участник в summary назван нестандартно — сокращённо, с опечаткой, в другом падеже):

1. **Одна попытка** фаззи-резолва через **Haiku**: передать модели упомянутое в summary имя + список кандидатов из `contacts.enc` (ФИО/aliases), попросить сопоставить.
2. Если Haiku даёт уверенное совпадение — использовать его для текущей задачи/mention. Не считать результат окончательным зафиксированным алиасом автоматически — сохранение найденного соответствия в `aliases` отдельно не решено брифом, уточнить при необходимости.
3. Если Haiku **не даёт уверенного совпадения** — не гадать дальше. Оставить имя как обычный текст без Confluence `@mention`, явно пометить в отчёте/уведомлении, что этого участника нужно проверить руками. **Не блокировать публикацию всей встречи** из-за одного нерезолвленного участника.
4. Только одна попытка — не повторять фаззи-резолв, не эскалировать на более дорогую модель автоматически.

## Резолв переговорных комнат в списке участников — РЕШЕНО (09.07.2026)

Если резолв строки-«участника» находит не человека, а запись из `meeting-rooms.md` (переговорка/зум-комната, залогиненная как отдельный «участник» встречи) — это переговорка, исключить её из списка участников протокола, не пытаться резолвить как человека.

**Задачи, привязанные к такому «участнику»-переговорке** (в исходном summary задача была назначена на переговорку, а не на реального человека) — **не пропускать и не блокировать**: исполнитель по умолчанию = `tkachenkoav` (fallback), Саша сам разбирается и переназначает вручную позже.

## Резолв проекта встречи — РЕШЕНО (09.07.2026)

**Первичный сигнал — название самой встречи**, не содержимое summary/список участников. Резолв проекта начинается с попытки сматчить заголовок встречи на `card.md`/aliases проекта.

**Множественные проекты в одной встрече:** если по названию встречи резолвится несколько проектов сразу — публикуем во все резолвленные протоколы (не выбираем «главный», не спрашиваем каждый раз).

**Общий список задач по всем проектам** — отдельная сущность (ссылку Саша даст отдельно), куда попадают задачи, которые явно не относятся к одному проекту или упомянуты «вообще по всем». Существует независимо от протоколов конкретных проектов.

**Fallback для нерезолвленных встреч:** если встреча не подошла ни в проект, ни в 1:1, ни в мультисинк (все три типа сущностей поддерживаются с самого начала первой итерации, не только «проекты») — не блокировать и не откладывать молча, а класть в тот же общий список задач как временный накопитель. Обязательно предусмотреть **ручной перенос** такой записи в правильный проект по последующей явной команде Саши (не одноразовая операция — устойчивый повторно вызываемый механизм).

## Идемпотентность — РЕШЕНО (09.07.2026)

Локальный реестр обязателен (аналог `_registry.json` паттерна MoveFrom*), но с более широким набором полей, чем просто факт «уже опубликовано»: для каждой обработанной встречи фиксировать **какая страница Confluence** (pageId/URL), **какой проект** (slug) и **дата встречи + timestamp публикации**. При повторном запуске на уже опубликованную встречу — не дублировать молча, предупредить и запросить явное подтверждение.

## Триггер запуска — РЕШЕНО (09.07.2026)

**Автоматический крон**, не только ручная команда — подхватывает каждую новую встречу сам после MoveFromFF (аналог связки `vm_movefromff` → следующий инструмент в конвейере). Это отличается от первоначальной рекомендации Opus (только ручной запуск на первой итерации) — Саша явно выбрал автоматику сразу, с оговоркой что это одновременно с расширением scope на все 3 типа сущностей (см. выше).

## Семантика двух дат — РЕШЕНО (09.07.2026, финальный ответ Саши)

- **Левая колонка таблицы** (`Дата постановки`) = дата встречи = дата возникновения/постановки задачи. Не дублирует inline `<time>` — это другая по смыслу дата.
- **Inline `<time>` внутри `<ac:task-body>`** = дедлайн выполнения задачи. Единственная трактовка, подтверждена дословно.
- **Словесные форматы дат из summary** ("на следующей неделе", "к пятнице" и т.п.) — всегда переводить в конкретную календарную дату перед записью в `<time>`, не оставлять текстом.
- **Fallback, если дедлайн явно не назван в summary:** `текущая_дата + 7 календарных дней`. Логика Саши: синки обычно еженедельные, значит подразумеваемый срок — до следующего синка.
