# TaskRefresh — задачи Саши из Confluence

Механический CLI-цикл: `read`/`mine` → показ → Саша называет номер+действие → `apply` (preview)
→ `confirm` (пишет). ТЗ:
`WorkVault/Hermes-Backlog/TZ/TaskRefresh/TaskRefresh_TZ.md`.

## Дефолт вывода при «поработаем с задачами»

Всегда делать `./tr mine --links` и показывать задачи в трёх группах:
1. **⚠️ Просроченные** — со срочным акцентом
2. **На этой неделе** — дедлайн в пределах 7 дней
3. **Позже** — всё остальное с дедлайном

**Выводить ВСЕ задачи без пропусков** — все 21+ штук если столько есть. Не обрезать список.

**Текст задачи выводить оригинальный** — без сокращений и перефразирований, ровно как хранится в Confluence.

**Источник = все задачи из `https://dom.tutu.ru/display/~tkachenkoav/OpenTasks`** — это Confluence `tasks-report-macro` с `spaces=DPAN,~tkachenkoav`, `assignees=tkachenkoav`, `labels=_aid`. TR сканирует по тому же критерию (`CQL_LABEL="_aid"`) → покрытие полное, без пропусков.

Саша сам называет что делать с каждой — менять дедлайн, текст, закрывать. С v2.1 батч-правка одной задачи — одна `apply` с `;` (см. раздел «Батч-операции» ниже).

⚠️ **Типичная ошибка:** несколько `apply` подряд через `&&`, затем один `confirm` — применяется только последнее `apply`. Правильный паттерн для батча в Python-цикле:
```python
# mine один раз в начале, затем на каждое изменение — apply + confirm
terminal("./tr mine > /dev/null")
for change in changes:
    terminal(f'./tr mine > /dev/null && ./tr apply "{change}" && ./tr confirm')
```
`mine` перед каждым `apply` обязателен — `confirm` не обновляет in-memory сессию.

## Команда (экономия токенов — используй `tr`, не длинный venv-путь)

```bash
cd ~/USERTOOLS/TaskRefresh
./tr mine                          # дефолтный срез "мои задачи" одной командой
./tr mine --links                  # + Confluence-ссылка на каждую задачу
./tr mine --any-deadline           # включая задачи без дедлайна
./tr read --assignee X --project Y --deadline overdue --status any   # произвольный фильтр
./tr apply "#N дедлайн ДД.ММ"      # preview, ещё НЕ пишет
./tr apply "#N закрыть"            # → status=complete
./tr apply "#N открыть"            # → status=incomplete
./tr apply "#N ссылка <URL> [подпись]"  # добавляет гиперссылку: JIRA hq.tutu.ru/browse/KEY → макрос, иной URL → <a href>
./tr apply "#N ссылка <URL1>,<URL2>,..."  # несколько ссылок через запятую без пробелов (§25)
./tr apply '#N закрыть; текст: "..."'   # мульти-поле через ';' (v2.1)
./tr confirm                       # пишет + встроенная верификация (перечитывает страницу)
./tr do "<команда>"                # apply+confirm одним шагом, только для механики (v2.1)
./tr batch "<cmd1>" "<cmd2>" ...   # пакетное применение N изменений, один confirm (v2.2)
./tr batch "<cmd1>" "<cmd2>" --quiet  # только итог, без preview (экономия 30-40x)
./tr batch --from-file cmds.txt       # команды из файла (по одной на строку)
./tr batch --dry-run                  # preview всех изменений без записи
./tr do "<команда>" --quiet          # одна строка вывода вместо полного preview (v2.2)
./tr new "<текст>" [--date YYYY-MM-DD] [--page-id 432316254] [--assignee ФИО] [--deadline YYYY-MM-DD]  # вставка новой задачи (v2.3)
./tr show                          # перепечатать последнюю сессию без нового скана
```

`./tr` — bash-wrapper, сам находит `ProtocolFromSummary/.venv` (TaskRefresh не имеет своего venv).
Если `./tr` недоступен (отсутствует/не exec) — fallback:
`~/USERTOOLS/ProtocolFromSummary/.venv/bin/python3 -m taskrefresh <args>`.

## Батч-операции над одной задачей (с v2.1)

Разделитель `;` в одной команде apply — несколько полей одновременно:

```bash
./tr mine > /dev/null
./tr apply '#N закрыть; текст: "финальный текст"'
./tr confirm
```

Другие комбинации:
- `./tr apply '#N исполнитель Набиева Даяна; дедлайн 05.08; текст: "..."'`
- `./tr apply '#N дедлайн +7д; закрыть'`

Порядок полей в команде роли не играет — инструмент применяет их в безопасном порядке: text → assignee → deadline → status → link.

Символ `;` внутри `текст: "..."` — **не разделитель**: `текст: "финал; готово"` парсится как один текст `финал; готово`.

Пакет задач тоже поддерживается: `#3,#5 закрыть; дедлайн 05.08` — оба поля к обеим задачам.

## Смена исполнителя — через `./tr apply`, НЕ через прямой API

```bash
./tr apply "#N исполнитель Набиева Даяна"
./tr confirm
```

`./tr` резолвит userkey через `contacts_resolver.resolve_assignee` (contacts.enc → CQL user.fullname~ → дозапись в contacts.enc). Если человека нет в contacts.enc — TR добавит через CQL fallback. Если резолв не удался вовсе — TR оставит упоминание plain-текстом без mention (`partial_no_mention`) и предупредит.

**Прямой Confluence API PUT для смены `ri:userkey` — антипаттерн** и запрещён. Единственное исключение — сохранение существующего `<a href>` в task-body при одновременной правке текста (см. отдельный питфолл ниже), но и там `ri:userkey` НЕ трогаем.

## Многошаговая правка одной задачи (текст + ссылка + дедлайн)

С v2.1 — одной командой:

```bash
./tr mine > /dev/null
./tr apply '#N текст: "новый текст"; дедлайн 05.08'
./tr confirm
```

**Исключение** — если в задаче есть кликабельная `<a href>` и её надо сохранить: правка текста уничтожит гиперссылку. Тогда:
- дедлайн — через `./tr apply "#N дедлайн ..."` (не трогает href)
- текст со ссылкой — прямой Python PUT (см. питфолл ниже)

Прежний паттерн «apply → confirm → mine → apply → confirm» на каждое поле остаётся валидным, но избыточным. Использовать только если действительно нужен preview на каждом шаге отдельно.

## `./tr do` — apply+confirm одним шагом (v2.1)

```bash
./tr do "#N закрыть"
./tr do "#N дедлайн 05.08" --no-verify
./tr do "#N закрыть; дедлайн 05.08" --no-mine
```

Семантика:
1. Если сессия пуста/stale — авто-запускает `mine` перед apply.
2. Выполняет `apply` (preview попадает в stdout для аудита).
3. Немедленно выполняет `confirm` с `verify=True` по умолчанию.

Флаги: `--no-verify` (пропустить верификацию), `--no-mine` (не делать авто-mine).

⚠️ **Ограничение:** если задача содержит `<a href>` в теле — `do` выдаёт WARN и останавливается, не применяя изменений. Используй в этом случае `apply` + `confirm` вручную или прямой PUT.

Использовать **только для тривиальных механических действий**: закрыть, открыть, сдвиг дедлайна, смена исполнителя, простая замена текста без кликабельных ссылок. НЕ использовать для сложных сценариев, где нужен ручной review preview.

## Batch-режим (v2.2) — когда использовать

Если нужно применить изменения сразу к 3+ задачам одним диалоговым шагом — не гонять
`mine → apply → confirm` в цикле по одной, а собрать все команды в один `./tr batch`:

```bash
./tr batch "#3 закрыть" "#5 дедлайн 10.08" "#7 текст: \"...\"" --quiet
```

Механика: один авто-`mine` (если сессия пуста/stale) → все команды парсятся и
объединяются в один список specs → один `apply_changes` (группировка по странице,
как обычно) → один `_verify_applied` на всё сразу. Экономия токенов — вместо N
отдельных preview+confirm получается один короткий итог.

Флаги:
- `--dry-run` — показать preview всех изменений, ничего не применять (specs
  попадают в `pending_apply.json`, ждут `./tr confirm`).
- `--quiet` — не печатать построчный preview, только итог вида
  `batch: N команд, M задач, ok` (или `..., K ошибок`).
- `--from-file <path>` — команды построчно из файла вместо аргументов CLI.
- `--no-mine` — использовать текущую сессию без авто-`mine`.

⚠️ Как и `do` — задачи с `<a href>` в тексте, где команда правит текст, будут
пропущены с WARN (гиперссылка не переживёт `apply text`, см. питфолл ниже).
Использовать `batch` только для механических правок (закрыть/открыть/дедлайн/
исполнитель/простой текст без ссылок).

Для одной задачи с несколькими полями — используется прежний мульти-полевой
синтаксис `;` (`./tr do '#N закрыть; текст: "..."'` или `--quiet`), `batch`
нужен именно когда меняется **несколько разных задач** за один диалоговый шаг.

## Правило: один mine на сессию (зафиксировано Сашей 13.08.2026)

**Показываешь бриф → Саша работает с этими номерами → применяешь `apply` из той же сессии,
БЕЗ повторного `mine`.** Никаких пересборов между изменениями.

Проблема, которую это решает: каждый `mine` пересчитывает нумерацию #N, а дефолтный `mine`
(без `--any-deadline`) молча отсеивает задачи без дедлайна — список «съезжает», и #N из брифа
начинает указывать на другую задачу (или падает `IndexError: #N вне диапазона сессии`).

Правильный цикл на N изменений в одной сессии:
```bash
./tr mine --any-deadline        # ОДИН раз, показать бриф Саше
./tr apply "#11 дедлайн 15.08"  # номер из этого брифа
./tr confirm
./tr apply "#12 дедлайн 15.08"  # ВСЁ ЕЩЁ номер из исходного брифа — mine НЕ перезапускать
./tr confirm
```

Анти-паттерн (вызывает сдвиг нумерации): `mine` → `apply` → `confirm` → `mine` → `apply` → `confirm`.
Перезапуск `mine` оправдан ТОЛЬКО если Саша явно попросил свежий бриф, либо был перерыв в
сессии и контекст номеров потерян. `batch` внутри сам делает один `mine` и не пересобирает
список — поэтому для массовых правок предпочтителен.
- **project_tag** — сначала текстовый тег в начале задачи ("Trisigma. ...", "АДМ. ..."), page_id
  страницы — fallback только для задач без тега. Персональные 1-1-страницы (Кирилл 1-1, Аралов 1-1
  и т.д.) — общий контейнер для разных проектов, не единый проект сами по себе.
- **`<time>` (дедлайн) и видимый текст задачи** ищутся на любой глубине вложенности html
  (не только прямой потомок task-body) — не создают дубль на задачах с ручной html-разметкой
  из веб-редактора Confluence (`rebuild_task_block`/`_replace_visible_text` оба используют
  рекурсивный обход, см. §14/§19 ТЗ).
- **Верификация после `confirm`** встроена в пайплайн (`verify=True` по умолчанию) — перечитывает
  изменённые страницы сама, покрывает все три поля (`deadline`/`status`/`text`), печатает
  "Верификация после записи: ок" или явную проблему. **Не нужен отдельный curl/read_file
  проход** — если строка "...ок" есть в выводе `confirm`, результат подтверждён.
- **`--links`** на `read`/`mine` дописывает `https://dom.tutu.ru/pages/viewpage.action?pageId=<id>`
  в конец каждой строки брифа — если Саша попросит "сверюсь с Confluence", сразу используй `--links`
  вместо построчного curl после факта.
- **Мульти-полевой парсер (v2.1)** — `;` как разделитель полей с защитой кавычек. Дублирующееся
  поле → ValueError. Незакрытая кавычка → ValueError. Порядок применения: text→assignee→deadline→status→link.

## Правило «перенести на N вперёд» (зафиксировано Сашей 13.07.2026)

Для ПРОСРОЧЕННОЙ задачи команда «перенеси на N дней/недель вперёд» считается ОТ ТЕКУЩЕЙ
ДАТЫ, а не от старого (просроченного) дедлайна задачи. Пример: сегодня 13.07, дедлайн
задачи 22.06 (просрочен), «перенеси на 2 недели вперёд» → новый дедлайн 27.07 (13.07+14д),
НЕ 06.07 (22.06+14д). Если дедлайн ещё не просрочен — можно уточнить у Саши базу, если
неочевидно из контекста.

## ⚠️ Сохранение гиперссылок при модификации задачи

Если в теле задачи есть `<a href="...">текст</a>` — это кликабельная HTML-ссылка, которую **нельзя потерять при правке текста или дедлайна**.

**Как проверить наличие ссылки перед правкой:** прочитать сырой XML задачи через API (`/rest/api/content/<pageId>?expand=body.storage`) и найти `<a href=` в нужном `<ac:task-body>`. `./tr mine` в бриф-выводе ссылку не показывает — только ссылку на страницу.

**Когда ссылка есть — не использовать `./tr apply "#N текст: ..."`.**  `apply text` заменяет весь видимый текст задачи plain-текстом, что уничтожает HTML-разметку ссылки. Мульти-полевой синтаксис (`;`) через `apply text` унаследует ту же проблему — при наличии `<a href>` использовать прямой PUT.

**Правильный путь — прямая правка через API:**
1. GET страницы (`?expand=body.storage,version`)
2. Найти `<a href="URL">старый текст ссылки</a>` в нужном task-body
3. Заменить только текст внутри `<a>...</a>`, оставив `href` нетронутым
4. Если меняется дедлайн — заменить `datetime="YYYY-MM-DD"` только в этом же task-body
5. PUT с `version + 1`
6. Верифицировать: новый текст ссылки есть, старый ушёл, `href` и `datetime` корректны

**Дедлайн без ссылки** — можно через `./tr apply "#N дедлайн ДД.ММ"` без риска.

## Формат ссылки в задаче — встраивать в слово из текста, не отдельным «(ссылка)»

**Правило (явно подтверждено Сашей 21.07.2026):** ссылку встраивать в осмысленное слово из текста задачи.

✅ `Актуализировать список тем на <a href="URL">страничке</a> за Апрель - Июль`
❌ `Актуализировать список тем на страничке <a href="URL">(ссылка)</a>`

Исключение — если в тексте задачи нет подходящего слова-якоря, тогда `(ссылка)` допустимо.

## Когда Telegram скрыл hyperlink — искать URL на той же странице

Telegram передаёт только plain text, скрытые hyperlink-entities теряются. Если Саша указал «ссылку» в тексте задачи, но URL недоступен:
1. Прочесть body страницы назначения (GET `?expand=body.storage`)
2. Поискать URL в соседних задачах того же блока
3. Если нашли — использовать, сообщив Саше откуда взяли
4. Если нет — попросить URL отдельным текстом

## Добавление ссылки в задачу — ВСЕГДА настоящая гиперссылка

Если Саша просит "добавить ссылку" в конец задачи — это ВСЕГДА кликабельная HTML-ссылка
`<a href="URL">(ссылка)</a>` (Confluence storage format), НЕ голый текст URL. Использовать
`apply "#N ссылка <URL>"` (не `apply "#N текст: ..."` с URL внутри строки — тот вставляет
только plain text, будет виден как обычный текст, не кликабельная ссылка). Подпись по
умолчанию "(ссылка)", можно переопределить: `apply "#N ссылка <URL> подробнее"`.

## Контракт команды «Проект — X» (номер задачи + новый/другой проект)

Задача НЕ переносится на другую страницу — только меняется/добавляется `project_tag`
(классификационная метка для группировки в брифе). Механизм: правка
`WorkVault/Tools/TaskRefresh/project_registry.json` — добавить/поправить slug с `tag` (текстовый
префикс задачи). **Побочный эффект, о котором всегда предупреждать Сашу:** реклассификация идёт по
факту текстового тега во ВСЕХ задачах сразу — не только в той, о которой шла речь. Если нужен
per-task override без этого эффекта — текущий механизм не поддерживает, не изобретать workaround,
сказать Саше, что это отдельная доработка.

## ⚠️ ПИТФОЛЛ: `tr apply текст` уничтожает HTML-гиперссылку в задаче (22.07.2026)

**Симптом:** задача содержит кликабельную ссылку `<a href="...">текст</a>` (созданную вручную в Confluence или через `tr apply ссылка`) **или JIRA-макрос** `ac:name="jira"` (через `tr apply ссылка` с hq.tutu.ru/browse/KEY). Команда `./tr apply "#N текст: ..."` перезаписывает весь visible text как plain text — гиперссылка/макрос теряется. Мульти-полевой синтаксис (`;`) при наличии `<a href>` или JIRA-макроса — унаследует ту же проблему.

**Проверка перед apply:** если `./tr mine` показывает ссылку в тексте задачи или если задача правилась вручную в веб-UI — проверить сырой XML перед изменением текста:
```python
import sys; sys.path.insert(0, '/home/tkachenkoav/USERTOOLS/TaskRefresh')
import taskrefresh.config as c, urllib.request, json
req = urllib.request.Request(
    f"{c.CONFLUENCE_BASE_URL}/rest/api/content/<pageId>?expand=body.storage",
    headers={"Authorization": f"Bearer {c.CONFLUENCE_TOKEN}"}
)
with urllib.request.urlopen(req) as r: data = json.load(r)
# Ищем <a href> вблизи нужного текста задачи
```

**Фикс — прямой Python PUT с сохранением href:**
```python
HREF = "https://..."
```

## JIRA-референсы в теле задачи — через `./tr apply ссылка` (§25, v2.4)

URL вида `https://hq.tutu.ru/browse/<KEY>` внутри `<ac:task-body>` вставляется как **JIRA-макрос** (`ac:structured-macro ac:name="jira"`), не как обычная `<a href>`. Любой иной URL — по-прежнему `<a href>`.

- Preview показывает тип: `ADD-568390 (JIRA)` vs `https://loop... (ссылка)`

**Правило даты постановки — ВСЕГДА сегодняшняя дата:**
- Новые задачи добавляются в строку с датой **сегодня** (`YYYY-MM-DD` = текущая дата), независимо от дедлайна задачи.

**Правило порядка строк: новые даты — ВЫШЕ старых** (таблица идёт от новых к старым сверху вниз).

## Ручное удаление строки таблицы минуток (по явной команде Саши)

6. Подтвердить: повторный GET — маркер/текст удалённой строки отсутствует, version увеличилась ровно на 1.
7. Удалить `/tmp/page.json`, `/tmp/put.json` сразу (PII).
8. Если строку писал инструмент с `_registry.json` (напр. ProtocolFromSummary) — синхронно пометить запись исключённой (флаг `historical_no_reload: true` / `entity: excluded_personal`), не удалять физически — иначе следующий прогон republish-нет удалённую строку заново.

**Когда применять эту ручную технику vs `remove_row_by_anchor()` инструмента:** только если удаляемая строка НЕ относится к штатному потоку данных инструмента (например разовая личная встреча в fallback-контейнере «Встречи неразобранное»).
