# Интервью → матрица ИИ-зации (самодостаточный навык)

Навык проводит весь путь за один проход и **ничего внешнего не требует** — вся
методология встроена в его собственные файлы:

```
транскрипт интервью → проверка по вопросам → описание процесса → матрица ИИ-зации → Excel
```

«Матрица ИИ-зации» — это таблица, которая показывает, какую работу в процессе
можно передать искусственному интеллекту, а какую оставить человеку:

- **строки** — когнитивные виды деятельности (поиск информации, анализ данных, принятие решений и т. д.);
- **столбцы** — стадии (этапы) процесса по порядку;
- **клетки** — что делается на этой стадии в рамках этого вида работы и какой тип ИИ применим.

Навык строит две матрицы: **«как сейчас»** (процесс без ИИ) и **«как будет»**
(процесс с ИИ). Дальше по тексту они называются «как сейчас» и «как будет».

## Файлы навыка (читай по необходимости)

Вся нужная справка лежит рядом, в этой же папке. Внешние навыки не нужны.

- [`questions.md`](questions.md) — список из 40 контрольных вопросов (8 блоков), из них 12 обязательных. По ним проверяется полнота транскрипта.
- [`reference.md`](reference.md) — методология матрицы: легенда из 4 типов ИИ, дерево выбора типа, опорный список видов работы, правила маркировки узких мест, формат клетки, принципы.
- [`templates.md`](templates.md) — все шаблоны вывода: итог проверки, описание процесса (форматы А/Б/В), таблицы матрицы, сводки, схема файла данных `spec.json`.
- [`reproducibility.md`](reproducibility.md) — как получить устойчивый результат: тройной прогон и сведе́ние в согласованную версию.
- `scripts/` — готовые программы: `export_matrix.py` (сборка Excel/CSV), `consensus_matrix.py` (сведе́ние трёх прогонов), `spec_template.json` (образец файла данных).

## Поведение при старте

Если пользователь сразу дал транскрипт — переходи к воркфлоу. Если обратился без
данных («применить навык», «начни») — выведи приветствие:

```text
Привет! Я навык «Интервью → матрица ИИ-зации».
Из транскрипции интервью я:
1. Сверяю процесс с контрольными вопросами и показываю, что раскрыто, а чего не хватает.
2. Собираю описание процесса.
3. Строю матрицу ИИ-зации: что отдать ИИ, а что оставить человеку.
4. Выгружаю результат в Excel с цветовой разметкой.

Что прислать: транскрипт встречи (Zoom / Fireflies / любой текст).
Что выбрать на выходе:
- только матрицу ИИ-зации;
- только описание процесса (форматы А / Б / В);
- и описание, и матрицу (по умолчанию — **формат А** + сводка матрицы в чат + Excel).

Пришли транскрипт и скажи, что нужно на выходе.
```

## Выбор режима вывода

Пользователь выбирает один из трёх режимов (спроси одним вопросом, если он не
указан явно):

```text
Что подготовить по этому интервью?
1. Только матрицу ИИ-зации (в чат: итог проверки + сводка матрицы + `.xlsx`; описание **А/Б/В** — по запросу).
2. Только описание процесса (форматы: **А** — по блокам, **Б** — нарративный регламент, **В** — таблицей; по умолчанию — **А**).
3. И описание процесса, и матрицу.
По умолчанию — 3 в **формате А** (итог проверки + описание по 8 блокам + сводка матрицы в чат + Excel).
```

Что это значит на практике:

- **Только матрица** → в чат **выводим:** итог проверки (блок 1) + сводка матрицы
  (блок 3) + `.xlsx`. **Не выводим** (если пользователь не просил): описание
  процесса — форматы **А** / **Б** / **В**; по запросу можно добавить любой из них.
  Описание всё равно собирается внутри (источник для матрицы). Полные клетки AS IS /
  TO BE — только в Excel.
- **Только описание** → матрицу не строим; выводим **формат А** (итог проверки + 8 блоков).
- **И то, и другое** → итог проверки + **формат А** + сводка матрицы по шаблону из
  [`templates.md`](templates.md); полная матрица клеток — в Excel и `spec.json`.

**Формат А** — основной формат описания в чат (8 блоков). **Формат Б** — **полный**
нарратив по шагам (по запросу): развёрнутые абзацы, детали из интервью, не сжатое
резюме. **Формат В** — таблица этапов (по запросу).

Важный принцип: **описание процесса собирается всегда** — без него матрицу не
построить. Меняется только то, показываем ли мы его в чате.

## Имена участников (обязательно)

В **всех** выходах навыка — итог проверки, уточняющие вопросы, описание процесса
(форматы А / Б / В), матрица, `spec.json`, рекомендации — используй **полные
имена**, а не уменьшительные или разговорные формы из устной речи.

**Правила:**

1. В аналитическом тексте — **полное имя** (официальная форма), не уменьшительное
   и не разговорное из записи.
2. Если в расшифровке есть **фамилия или должность** — указывай **Имя Фамилия**;
   при первом упоминании добавляй роль.
3. **Первое упоминание** — полное имя (и фамилия, если известна). Дальше допустимо
   **только полное имя или фамилия**.
4. **Если полное имя в записи не названо** — не выдумывай; укажи известную форму
   с пометкой «в записи — …» или вынеси в открытые вопросы.
5. **Speaker N** — замени на идентифицированное полное имя, если пользователь или
   расшифровка его дали; иначе оставь Speaker N и отметь в итоге проверки.

Уменьшительные и разговорные формы **допустимы только в прямой цитате** из
расшифровки. То же правило — в полях `owner`, `executor`, `actor` в `spec.json`
и в листе «Контекст» Excel.

## Воркфлоу

Скопируй этот чек-лист и отмечай шаги по мере выполнения:

```
- [ ] Шаг 1.  Принять транскрипт (Zoom / Fireflies / текст)
- [ ] Шаг 2.  Сверить транскрипт с контрольными вопросами → итог проверки
- [ ] Шаг 3.  Проверить полноту (12 обязательных вопросов)
- [ ] Шаг 4.  Выбрать режим вывода (матрица / описание / оба) и форматы
- [ ] Шаг 5.  Собрать описание процесса (всегда, даже если не показываем)
- [ ] Шаг 6.  Разложить процесс на стадии (столбцы матрицы)
- [ ] Шаг 7.  Выделить когнитивные виды деятельности (строки матрицы)
- [ ] Шаг 8.  Заполнить матрицу «как сейчас»
- [ ] Шаг 9.  Заполнить матрицу «как будет» (с ИИ, по легенде)
- [ ] Шаг 10. Пометить узкие места (критические стадии)
- [ ] Шаг 11. Собрать матрицу, сводки и файл данных spec.json
- [ ] Шаг 12. Для финальной матрицы — тройной прогон и согласование
- [ ] Шаг 13. Выгрузить Excel
- [ ] Шаг 14. Выдать результат по выбранному режиму
```

Шаги 6–13 нужны только если строится матрица. В режиме «только описание»
после шага 5 переходи сразу к выдаче.

### Шаг 1. Принять транскрипт

Прими расшифровку встречи: текст прямо в чате или путь к файлу (`.txt`, `.vtt` и
т. п.). Звук навык не обрабатывает — только готовый текст из любого инструмента
расшифровки. Если пользователь указал соответствие Speaker N → человек — зафиксируй
его для шага 2.

### Шаг 2. Сверка транскрипта с контрольными вопросами

Приведи текст в порядок (убери таймкоды и шум, по возможности раздели реплики по
говорящим). **Нормализуй имена** по § «Имена участников» выше. Сверь текст со
**всеми 40 контрольными вопросами** из
[`questions.md`](questions.md). По каждому вопросу поставь один из статусов:

- **раскрыт** — есть достаточный ответ с конкретикой (роли, числа, примеры, артефакты);
- **частично** — тему затронули, но деталей не хватает;
- **не раскрыт** — вопрос относится к процессу, но ответа в записи нет (пробел);
- **не применимо** — вопрос объективно не про этот процесс; ставится только с обоснованием и пробелом не считается.

Выведи **итог проверки** по шаблону из [`templates.md`](templates.md).

- **В чате (по умолчанию)** — **компактный** вариант (таблица + пробелы + рекомендация); выводится **всегда**, до описания процесса.
- **Полный** вариант (что раскрыто / чего не хватает / вопросы владельцу) — только по запросу «развернуть проверку» или для черновика.

Итог проверки показывай **всегда** — он объясняет, на каких данных строится матрица.

### Шаг 3. Проверка полноты

Готовность считается не по «закрыты все 40», а по **12 обязательным вопросам**
(в `questions.md` они помечены О1–О12: название/цель/владелец процесса; запуск/входы/выход/получатель результата; этапы/ответственные/артефакты; ключевые решения; используемые инструменты).

- **Все 12 обязательных закрыты** (раскрыты или обоснованно «не применимо») →
  данных достаточно, переходи дальше.
- **Есть незакрытые обязательные** → данных мало. Сообщи, чего именно не хватает,
  и предложи на выбор: либо донести недостающее (текстом, ответами или новой
  расшифровкой — навык дополнит проверку, не теряя уже собранное), либо собрать
  матрицу как **черновик** с явной пометкой о пробелах. Спроси пользователя, что
  он предпочитает.

Отдельная оговорка про матрицу: длительности стадий и узкие места в обязательные
вопросы не входят (они опциональные). Если их в транскрипте нет — матрица всё
равно собирается, а узкие места помечаются встроенной эвристикой (шаг 10).

### Шаг 4. Выбрать режим вывода

Спроси режим (если не задан) по блоку «Выбор режима вывода». Зафиксируй:

- **режим** (матрица / описание / оба);
- **формат описания в чате:** в режимах «оба» и «только описание» — по умолчанию **А**;
  **Б** или **В** — по запросу. В режиме «только матрица» в чат **выводим** блок 1 +
  блок 3 + `.xlsx`; описание (**А** / **Б** / **В**) **не выводим**, если пользователь
  явно не попросил.

### Шаг 5. Собрать описание процесса

Собери описание процесса — это обязательный внутренний артефакт и мост к матрице.
Форматы и шаблоны — в [`templates.md`](templates.md):

- **Формат А** — по 8 блокам (**основной**, по умолчанию);
- **Формат Б** — **полный** нарративный пошаговый регламент (по запросу или когда
  пользователь явно просит «нарратив / регламент / по шагам»); стандарт полноты —
  в [`templates.md`](templates.md) § «Формат Б»;
- **Формат В** — таблица этапов с типом нагрузки (по запросу).

**Формат Б — обязательная полнота (даже «под капотом» для матрицы).** Нарратив
собирается **развёрнуто**, как регламент для нового сотрудника: не телеграфные
строки и не сжатое резюме для чата. Каждый шаг — **несколько абзацев** (кто, что,
инструменты, решения, артефакт, нюансы из интервью, срок курсивом в конце). После
шагов — ветвления, договорённости, длительность процесса, что остаётся за человеком,
TO BE, открытые вопросы. **Запрещено:** однострочные шаги через `;`, «шпаргалка из
5 строк», урезание деталей «для краткости чата».

**Нарратив — это регламент процесса, а не разбор методологии.** В тексте описания
(формат Б, как и А/В) **запрещено**:

- выводить названия **когнитивных видов деятельности** («Виды деятельности: …»,
  «здесь Анализ данных / Критическое мышление») — это только строки матрицы;
- давать **методологические ремарки и противопоставления** вида «это не анализ
  данных», «это исполнение, а не анализ», «здесь два разных вида» — служебные
  рассуждения остаются в матрице и её обосновании, в нарратив не попадают.

Нарратив описывает, **что человек реально делает** (действия, инструменты, решения,
артефакты), живым языком регламента. Классификация работы по видам — внутренний шаг
для построения матрицы; в самом описании она не упоминается.

Для матрицы из описания критично извлечь:

- **этапы по порядку** (с участниками, длительностью, артефактами, узкими местами) — станут стадиями (столбцами матрицы);
- **действия и тип нагрузки на этапах** — лягут в когнитивные виды деятельности (строки матрицы);
- **что уже автоматизировано и что хотят автоматизировать** — основа для матрицы «как будет»;
- **узкие места** — будущая маркировка критических стадий;
- **что принципиально нельзя отдавать ИИ** — отдельный список.

Если режим — «только описание», описание собрано — переходи к шагу 14 (без построения матрицы).
Иначе переходи к построению матрицы.

### Шаг 6. Разложить процесс на стадии

Разложи процесс на упорядоченную цепочку стадий. Для каждой зафиксируй: название,
длительность, ключевой артефакт на выходе, исполнителей. Стадии становятся
**столбцами** матрицы; порядок слева направо = ход процесса во времени.

**Правило длительности.** Различай два случая:

- **Длительность названа в транскрипте** — записывай как есть («2 ч», «1–3 дня»),
  ничего не помечай.
- **Длительность не упоминалась** — не пиши её молча как факт. Вместо этого:
  1. Сделай расчётную оценку исходя из логики процесса (тип работы, число шагов,
     кол-во участников, аналогичные процессы) и запиши с маркером `~` и пометкой
     `[оценка]`, например: `~2 ч [оценка]`, `~3–5 дней [оценка]`.
  2. Кратко укажи основание оценки в поле «Узкие места / комментарий» или сразу
     после значения: `~2 ч [оценка: ручная сверка ~30 строк, 2 согласования]`.
  3. Добавь стадию в раздел «Открытые вопросы» описания с формулировкой:
     `Уточнить длительность стадии «<название>» у владельца процесса
     (сейчас — расчётная оценка ~X).`

Цель: пользователь видит разницу между тем, что было сказано на встрече, и тем, что
навык рассчитал сам, и знает, что именно стоит уточнить.

В `spec.json` для поля `stages[].duration` используй формат:
`{фрагмент из встречи} | ~X [оценка]` или `не уточнялось | ~X [оценка]`.
Дополнительно заполни `duration_breakdown[]` и `duration_summary` — см.
[`templates.md`](templates.md).

### Шаг 7. Выделить когнитивные виды деятельности

Определи виды интеллектуальной работы **из самого процесса**: разбери каждую
стадию (кто делает, что на входе, что на выходе) и выдели, какая работа там реально
выполняется. Затем сверься с опорным списком из [`reference.md`](reference.md)
(поиск информации, анализ данных, критическое мышление, принятие решений,
генерация гипотез, документирование, исследования, приоритизация) — он нужен для
единообразных названий и страховки от пропусков, а не как меню на выбор. **Список
не исчерпывающий:** финальный `activities[]` строится из процесса и может включать
виды, которых нет в восьми пунктах.

**Как проверить каждый вид через триггеры (обязательно):**
Для каждого выделенного вида убедись, что он проходит проверку триггерами из
`reference.md` § «Критерии-триггеры». Если активность не совпадает с триггерами
стандартного вида — **это новый вид**, дай ему короткое имя по смыслу. Примеры
частых ошибок:
- «запустил скрипт» → это **не «Анализ данных»**; если нет интерпретации — может быть «Создание кода / генерация запросов» или вообще техническая операция без отдельной строки;
- «ревью SQL» или «проверка ноутбука» → это **«Критическое мышление»** или **«Валидация результатов»**, не «Анализ данных»;
- «написание/генерация кода» → это **«Создание кода / генерация запросов»**, даже если итог — данные; не смешивать с аналитикой.

Правила: вид работы из процесса, которого нет в списке, — добавляй; вид из
списка, которого нет ни на одной стадии, — не включай.

**Запрещено:** брать все 8 строк из опорного списка и «раскладывать» процесс по
ним. **Правильно:** вывести виды работ из стадий → проверить по триггерам →
при совпадении использовать каноническое имя → иначе добавить своё. На одной
стадии несколько строк — только если когнитивная работа **разная** (разный глагол,
артефакт, смысл); не дублируй одну работу в «Анализ данных» и «Исследования».

Виды деятельности становятся **строками** матрицы (в spec.json — поле `activities[]`;
ключи в `as_is` / `to_be` должны совпадать с ними **дословно**).

Если какая-то стадия — «чёрный ящик» (непонятно, что внутри), сначала раскопай
скрытую работу: задай уточняющие вопросы по этой стадии (кто, на основании чего,
какой результат), и только потом формулируй виды деятельности. Так матрица не
пропустит неочевидную работу.

### Шаг 8. Заполнить матрицу «как сейчас»

Опиши текущее состояние процесса без ИИ. Каждая клетка — по строгому формату из
[`reference.md`](reference.md): `Вручную: <что и кто делает>. Артефакт: <что
создаётся и где хранится>.` Если вид деятельности на стадии не выполняется —
клетка `Нет`. Формулировок с ИИ на этом шаге быть не должно.

### Шаг 9. Заполнить матрицу «как будет»

Перепиши те клетки, где есть смысл усилить работу искусственным интеллектом.
Каждая такая клетка указывает тип ИИ по легенде, конкретное действие и инструмент,
а также артефакт. Тип ИИ выбирай **строго по дереву выбора** из
[`reference.md`](reference.md); всего типов четыре:

- **Ассистентский ИИ** — рутина: поиск информации, подготовка отчётов, документирование;
- **Агентный ИИ** — сложная аналитика: моделирование, поиск закономерностей, сценарный анализ;
- **Сотрудничество с человеком** — интерактивная работа, где нужно критическое мышление человека;
- **Нет применимости** — креативные и ценностные решения, человеческая интуиция (остаётся за человеком).

**Требования к конкретике в клетке (обязательно):**

1. **Запрещено писать только «частично»** без расшифровки. Каждая клетка с ИИ
   должна явно отвечать: что делает ИИ-агент, что делает человек.
2. **Добавляй сценарий взаимодействия** для каждой клетки с ИИ — по шаблону из
   `reference.md` § «Формат клетки»:
   > Сценарий: агент запрашивает [данные/параметры]; человек предоставляет [что];
   > агент возвращает [артефакт]; человек [финальное действие].
3. **Проверяй реалистичность:** сценарий должен описывать то, что действительно
   можно сделать — не «ИИ делает всё», а конкретный шаг в рамках одной стадии.

Действует принцип «меньше ИИ — лучше»: там, где справляется простое правило или
человек, ИИ не назначаем.

### Шаг 10. Пометить узкие места (критические стадии)

Сначала оцени сложность процесса по 5 критериям из [`reference.md`](reference.md)
(число стадий, ветвления, число ролей, число стадий-кандидатов в узкие места,
разбросанность срывов сроков):

- **выполнен ≤1 критерий — процесс простой** → помечай критические стадии встроенной эвристикой: самые длительные стадии, стадии с наибольшим числом срывов/возвратов, стадии, через которые проходят все задачи;
- **выполнено ≥2 критериев — процесс сложный** → проведи углублённый разбор узких мест по теории ограничений (где работа застревает в очередь, что ограничивает пропускную способность всего процесса) и пометь критические стадии по его итогу.

Критические стадии помечаются маркером ⚠️.

### Шаг 11. Собрать матрицу, сводки и файл данных

Собери по шаблонам из [`templates.md`](templates.md):

- матрицу «как сейчас» и матрицу «как будет»;
- сводку по стадиям с ответственным в состоянии «как будет»: `Человек` / `AI-агент` / `AI + ревью человека`;
- список «что не отдаём ИИ»: стадия / что именно остаётся за человеком / почему;
- **карту пути клиента (CJM)** в `cjm[]` — если у процесса есть клиентский путь:
  по каждому этапу пути — действия клиента, точки контакта, опыт сейчас (AS IS),
  опыт с ИИ (TO BE), эффект; для внутренних процессов без клиента — оставь пустым;
- дисклеймер в шапке: результат — рекомендация, требует обсуждения с владельцем процесса.

Параллельно с Markdown собирай файл данных `spec.json` по схеме
[`scripts/spec_template.json`](scripts/spec_template.json) — это источник правды
для выгрузки в Excel.

### Шаг 12. Тройной прогон (для финальной матрицы)

Модель вероятностна: на одних и тех же данных матрица каждый раз получается чуть
по-разному. Для черновика достаточно одного прогона. **Для финальной матрицы**
(презентация, руководство, продакшен) или по просьбе «сделай устойчиво» применяй
протокол из [`reproducibility.md`](reproducibility.md): зафиксируй оси (стадии и
виды деятельности), собери матрицу три раза, сведи прогоны в согласованную версию
скриптом `consensus_matrix.py`, покажи оценку устойчивости и спорные клетки.

### Шаг 13. Выгрузить Excel

Если строится матрица (режим «только матрица» или «оба»), шаг **обязателен**:
без файла `.xlsx` матрица **не считается выданной**. Markdown-сводка в чат не
заменяет Excel.

Выгрузи `spec.json` в Excel готовой программой (нужна одна зависимость —
`openpyxl`):

```bash
python scripts/export_matrix.py --input <имя>.spec.json --format xlsx --output <имя>.xlsx
```

как будет; Сводка по стадиям; Что не отдаём ИИ) плюс **опциональные** листы, которые
добавляются автоматически только при наличии данных в `spec.json`: «CJM (AS IS → TO
BE)» (если заполнен `cjm[]`) и «Эффект от внедрения» (если заполнены `as_is_short` /

маркировкой критических стадий, **без** листа «Описание процесса», **без**
нарративного текста и **без** дублирования форматов А/Б/В в `.xlsx`. Описание
процесса — только в чате и markdown; `process_description` / `narrative` в
`spec.json` — для markdown, **не** для Excel.

### Шаг 14. Выдать результат

- **Только матрица**: **выводим:** компактный итог проверки (блок 1) + сводка
  матрицы (блок 3: стадии, TO BE, что не отдаём ИИ) + **фактически созданный**
  `.xlsx` (шаг 13). **Не выводим** (если не просили): описание процесса — форматы
  **А** / **Б** / **В**; по запросу — можно. Полные клетки AS IS / TO BE — только в Excel.
- **Только описание**: компактный итог проверки + **формат А** (8 блоков); **Б** / **В** — если пользователь явно выбрал. Матрицу не строим.
- **Оба (по умолчанию)**: компактный итог проверки + **формат А** + сводка матрицы по шаблону из
  [`templates.md`](templates.md) + **фактически созданные** `.xlsx` (шаг 13) и `spec.json` + пути к файлам.

Сохрани артефакты на диск (если пользователь в проекте): `*.spec.json`, `*.xlsx`,
markdown с описанием процесса — по согласованной структуре папки проекта.

## Принципы

- **Строки матрицы — из процесса:** опорный список (8 пунктов) **не исчерпывает**
  `activities[]`; добавляй уникальные виды работы, неиспользованные из списка не
  включай.
- Описание процесса — обязательный мост от транскрипта к матрице; видимость зависит от выбора пользователя, наличие — нет.
- **Excel матрицы:** только листы, которые генерирует `export_matrix.py` (6 базовых
  + опциональные «CJM (AS IS → TO BE)» и «Эффект от внедрения» — по наличию данных);
  **не** добавляй лист «Описание процесса», **не** вкладывай нарратив (формат Б) в `.xlsx`.
- **CJM:** если процесс затрагивает путь клиента (есть точки контакта, ожидания,
  боли) — собери `cjm[]`: для каждого этапа пути зафиксируй действия клиента, точки
  контакта, опыт сейчас (AS IS) и опыт с ИИ (TO BE), эффект. Если процесс чисто
  внутренний и клиентского пути нет — оставь `cjm[]` пустым, лист не появится.
- Не выдумывай данные: пробелы транскрипта отражай в итоге проверки и в открытых вопросах, а не достраивай в матрице молча.
- **Длительность:** из интервью — как есть; не названа — только `~X [оценка]` с рекомендацией уточнить, никогда не выдавай оценку за факт.
- **Нарратив (формат Б):** развёрнутый регламент — назначение, роли, инструменты,
  шаги абзацами с деталями из интервью, ветвления, ограничения, TO BE, открытые
  вопросы; **не** сжимать в телеграф или однострочные шаги (см. `templates.md`).
- Выдача «оба» в чате — **формат А** + сводка матрицы, не полная матрица клеток (она в Excel).
- Только 4 типа ИИ из легенды, без выдуманных промежуточных категорий.
- У каждой клетки «как сейчас» обязателен артефакт.
- Меньше ИИ — лучше: где справляется правило или человек, ИИ не назначаем.
- Матрица и назначения «человек / ИИ / ИИ + ревью» — рекомендация для обсуждения с владельцем, а не директива.
- Итоговый артефакт матрицы — **всегда** файл `.xlsx` (шаг 13) **с цветовой
  разметкой по легенде и пометкой узких мест** (⚠️ на критических стадиях); сводка
  в чат — дополнение, не замена.
