## Типичные находки внешней LLM

По опыту AggregateFromMeetings — что внешняя LLM находит, а Opus-аудит пропускает:

### Класс 1: Конфликт алгоритмов между модулями
Каждый ТЗ верен по отдельности, но два модуля по-разному определяют один enum.
**Пример:** B.Роутер правило 1 «1 алиас → project (любое число участников)» vs H.В1 «3+ участников → всегда multisync».
**Диагностика:** искать все места где один термин (route, enum, тип) упоминается в нескольких ТЗ.
**Решение:** единый владелец алгоритма, остальные только ссылаются.

### Класс 2: Регрессии при правках
Исправление в одном месте файла не распространяется на другое место того же файла.
**Пример:** «H→D нет» на стр. 85, но «H пробрасывает в D» на стр. 72 того же TZ_C.
**Диагностика:** после каждого патча — свип файла на все вхождения исправляемого утверждения.

### Класс 3: Неполная карта state-файлов
Несколько модулей создают похожие файлы без карты.
**Пример:** `state.json`, `aggregate_state.json`, `meetings_index.json`, `unclear_names.jsonl` — непонятно кто главный.
**Решение:** раздел «Хранилища и state» в главном ТЗ с таблицей: путь | владелец | источник истины.

### Класс 4: Два источника истины
**Пример:** алиасы контактов хранятся и в `classification_memory.json` (B.Роутер) и в AC.
**Решение:** явно пометить один deprecated, другой — единственный writable store.

**Вывод:** закладывать 2-3 Opus-прогона + 2 итерации внешней верификации на закрытие всех противоречий.

**Дополнительный вывод (22.06.2026):** каждый крупный бриф (ВОП-блок) добавляет новые противоречия при разнесении по файлам — это норма. После брифа ВОП-1–9 в v1.5 появилось 3 CRITICAL + 7 MAJOR, хотя сами решения были верными. Причина: Opus-агент вносит решения в каждый файл независимо и допускает локальные несоответствия (slug-и, числа, поля MeetingPackage). Один Opus-патч закрывает всё за один прогон (если self-check grep пустой).

## README с дельтой (начиная с v1.5.1)

После нескольких итераций верификации Cursor начинает повторять уже закрытые замечания, если не видит историю. Решение — README_FOR_CURSOR с явным разделом дельты:

```markdown
## Изменения с прошлой верификации (vX.X → vX.X.1)
### CRITICAL (устранены):
- C1 — [что было] → [что стало]
### MAJOR (устранены): ...
### MINOR (устранены): ...
**Self-check grep:** `term1 | term2 | term3` — пустой ✅

## Что НЕ менялось (верифицировано в vX.X–vX.Y, не перепроверять):
- Граф пайплайна A→B→...→G
- AC — единственный writable store алиасов
- ...
```

**Эффект:** верификатор фокусируется на новом и не засоряет отчёт повторными MINOR по стабильным разделам. Сокращает объём отчёта ~вдвое и ускоряет итерацию.

## RUN_IMPLEMENTATION.md — запускающий документ для реализации

После APPROVED ТЗ создать `RUN_IMPLEMENTATION.md` в папке Epic:

**Ключевые разделы:**
- §0 РОЛЬ И ПРАВИЛА — архитектура закрыта, источники истины + их приоритет
- §1 ЧТО СДЕЛАТЬ ПЕРВЫМ — порядок действий при старте
- §2 КРИТЕРИЙ «ЗЕЛЁНОГО» — код + тесты + метрика §8
- §3 BUILD_CHECKLIST.md — разворачивать из IMPLEMENTATION_PLAN §3
- §4 АВТОНОМНЫЙ ЦИКЛ — TDD + pitch, порядок этапов строго
- §5 ТЕСТОВЫЕ ВСТРЕЧИ — фаза T до кода, manifest
- §6 ИЗОЛЯЦИЯ — _sandbox/, не трогать боевые артефакты до H6
- §7 HUMAN-GATES — H0..H8, единственные точки остановки
- §8 ФИНАЛЬНЫЙ ОТЧЁТ
- §9 ГДЕ ИСПОЛЬЗОВАТЬ LLM
- §10 ЗАПРЕТЫ

**HUMAN-GATES (обязательные):**
- H0: подтверждение тестового набора
- H1: diff чужого кода (AC методы)
- H2: B-checkpoint (route precision ≥90%)
- H3: C-checkpoint (PM оценивает decisions/action_items)
- H4: разрешение на платный bootstrap (Opus×15)
- H5: PM размечает unclear-очередь
- H6: финальный ревью + разрешение писать в боевой WorkVault
- H7: обнаружено противоречие в ТЗ
- H8: очистка тестовых артефактов
