# Контракт этапа 02

`MppReader/plan_export.py:export_full()` возвращает `full-export-v2` после одного вызова `read_mpp.read_project_file()` → `UniversalProjectReader.read()`. Observer считает фактические попытки чтения. Экспорт сохраняет исходные ID/UID/WBS, дерево, summary/milestone, даты с исходной точностью, ограничения и режим планирования, actual/remaining, work, splits, baseline 0–10, ресурсы, назначения и календарные привязки. CSV/JSON-контракт `read_project()` и CSV-потребители сохраняются.

Продолжительности и лаги содержат исходную строку и структурированное `quantity`/`lag_value`: десятичный `amount`, enum `units`, исходные `source_units`, `elapsed`. Параллельные связи сохраняются отдельно. Поля с отсутствующим значением имеют `value:null, quality:missing, reason:not_set`; известный ноль — `quality:ok` и нулевое значение. Недоступный getter — `unsupported`, исключение — `missing/getter_failed:...`. Причины не содержат адресов объектов и рабочих путей. Ошибки отдельных getters сохраняются в записи и `quality_issues`; коллекции отражают ошибки как partial/missing/unsupported. `complete` означает полноту доступного извлечения коллекции, а не наличие всех optional-значений или проверку расписания.

Календари содержат семь дней с типом дня и всеми интервалами, исключения с собственными интервалами и повторением, work weeks, parent key/UID и коэффициенты пересчёта. Привязки проекта/задач/ресурсов/назначений сохраняются отдельно; inherited/default-поля остаются явными. Одних weekday-флагов недостаточно для `complete`.

У установленного MPXJ 16.4.0 `Relation` не имеет calendar-getter: это явный `unsupported`; проектный `RelationshipLagCalendar` сохраняется отдельно. `ConstraintFactory` отбрасывает самоссылки и некоторые висячие MPP-записи до выдачи `ProjectFile`. Бинарный `graph-invalid.mpp` доказывает это: из четырёх raw-записей остаются две, образующие цикл. Экспорт всегда содержит `diagnose_graph.raw_relation_enumeration:unsupported` с причиной и не объявляет полную raw-коллекцию связей проверенной. Синтетический JSON дополнительно проверяет диагностику самоссылки, цикла, неизвестного конца и внешней связи, когда эти записи доступны. Восстановление отфильтрованных MPXJ записей из внутренних потоков MPP не реализовано; исходные байты остаются источником истины. Это ограничение не повышается до `schedule:verified`.

Локальные ключи используют UID, затем ID, затем позицию в исходной коллекции с `partial/no_stable_source_id`. Дубли исходных ID получают суффикс позиции и замечание. Такие ключи не доказывают идентичность между файлами. `obj:<адрес>` запрещён.

`PreparedPlan` v1 валидирует schema и semantic SHA-256. Нормализация не угадывает таймзону: неизвестная остаётся null; явный IANA hint сохраняется вместе с fingerprint профиля. Semantic hash включает нормализованные значения, исходный SHA/размер, версии reader/MPXJ/JPype, export и normalization, разрешённую таймзону. Имя поступления, read_at, source/work path, operation ID и телеметрия остаются вне hash. Разные каталоги и имена одинаковых байтов дают одинаковую semantic-сериализацию. Исходные значения для «Итого» сохранены; расчёт summary-v1 и интеграция публичного save/publish относятся к следующим этапам.

`ParseCache`: source SHA + reader/MPXJ/JPype + export version + параметры экспорта. `RepresentationCache`: semantic hash + converter + rules revision + fingerprint профиля плагина + параметры шаблона. Смена правил не инвалидирует parse cache; timezone/normalization меняют semantic hash и представление. Профиль плагина передаётся с fingerprint содержимого, а не только именем. Конвертер в этапе 02 не реализуется.

Кэш записывается через временный файл в той же папке, fsync, atomic replace и fsync каталога. Проверяются namespace/version, material/key, complete, число байтов, SHA payload и обязательные поля. Повреждение даёт cache miss и перестроение из повторно проверенных исходных байтов. Повреждённый источник запрещает и чтение, и повторное использование. Для нового поступления cache hit возвращает его собственные имя/locator. Удаление cache не удаляет ни исходник, ни prepared artifact, ни историю. Кэш не является архивом и не заменяет проверки Confluence.

Бинарные fixtures upstream взяты из [MPXJ](https://github.com/joniles/mpxj/tree/4982974b2594ffc7146cdb9ebdf2ae46186737ca/junit/data); точные URL/SHA и лицензия сохранены в manifests. Два производных бинарных fixtures воспроизводятся функциями `tests/fixtures/synthetic/binary_recipe.py` с использованием POI из установленного MPXJ; XML и mock не засчитываются как MPP-reader проверка. Task-specific binding дополнительно проверяется JSON unit fixture; реальные файлы подтверждают project/resource/effective-task bindings и отсутствие явно заданного task calendar там, где его нет.
