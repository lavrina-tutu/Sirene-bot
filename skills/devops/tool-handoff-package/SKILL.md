# Инструментальный пакет передачи — скилл как инструмент в новый инстанс

Узкий кейс `skill-portability` (передача SKILL.md-скилла) не покрывает ситуацию,
когда скилл — фактически **разработанный инструмент**: CLI + Python-пакет + тесты +
master-ТЗ. Здесь пакет шире, а деперсонализация имеет другой профиль (код, не текст
инструкций). Триггер пользователя: «выгрузи скилл и все нужные для его работы
инструменты в единый архив, без ссылок на нашу чувствительную информацию… с
инструкцией для подключения и работы для Гермес».

## Проверенный состав пакета (11.09.2026, case-collector v0.2.0)

```
<tool-name>/
├── README.md              ← ЗАНОВО, не копия SKILL.md (принимающей стороне нужен setup)
├── SKILL.md               ← манифест; platforms: [linux, macos, windows] если ТЗ требовало
├── scripts/*.py           ← код; без __pycache__/, .pytest_cache/
├── references/            ← LLM-промпты, шаблоны конфигов (user-map с фиктивными примерами)
├── tests/                 ← pytest-набор целиком — это доказательство работоспособности
└── TZ_<Tool>.md           ← master-ТЗ из WorkVault (архитектура/критерии)
```

README-инструкция закрывает: (1) состав и назначение каждого файла; (2) зависимости
(python-версия, pip-пакеты); (3) LLM-бэкенд — встроенный в инстанс vs внешний через
env-переменные (перечислить имена переменных); (4) опциональные конфиги; (5) команды
запуска, включая дешёвый dry-run; (6) команду тестов и ожидаемое число passed;
(7) платформ-адаптацию (Windows); (8) короткий «как это делалось» — контекст
принимающей стороне.

## Деперсонализация: маркеры и ложные срабатывания

Скан-маркеры по коду и текстам: имя пользователя, `/home/<user>`, внутренние домены,
IP/VPN-подсети (10.x), домен компании, @handles ботов, пароли/токены, hostnames.

**Обязательно решать глазами, не чистить вслепую** (реально встреченные ложняки):
1. `token_count`, `max_tokens`, `estimate_tokens` — LLM-токены, не секреты.
2. `api_key = os.environ.get(...)`, `Authorization: Bearer {self.api_key}` — логика
   чтения секрета из env, не сам секрет; удалять нельзя.
3. Тест-гвардии `assert "/home/<user>" not in text` — строка-маркер живёт в тесте,
   но это защита от утечки (инвариант), переносить нужно.

## Порядок

1. Grep-скан по исходникам ДО сборки; повторить по staging-каталогу как финал.
2. Копия в staging через `cp -r`, затем руками убрать `__pycache__/`, `.pytest_cache/`.
3. README писать через write_file (не heredoc — см. питфолл).
4. `tar czf <pkg>.tar.gz <pkg>/`; дать пользователю размер + md5sum вместе с файлом.
5. Финальный grep-скан по staging: все совпадения просмотреть и объяснить, не
   удалять вслепую.

## Питфоллы (реальные кейсы)

- **Длинный heredoc в terminal блокируется shell-hook guard.** `cat <<EOF` с
  большим текстом в одной команде сработал как подозрительный для pre_tool_call.
  Разбивать: файлы — write_file/patch, сборка архива — короткой командой `tar czf`.
- **kanban_attach вне kanban-воркера падает** («task_id is required») — env
  `HERMES_KANBAN_TASK` не проставлен. Для передачи файла пользователю в чат
  использовать `MEDIA:/abs/path` в тексте ответа — нативно и без канбана.
- **MEDIA-путь обязан существовать к моменту отправки**; размер/md5 давать той же
  командой, что и отправку.
- **Скан «token» даёт кучу ложняков** (`token_count`, `max_tokens`) — это LLM-токены.
  Матчить точнее: `api[_-]?key\s*=`, `Bearer `, `secret\s*=`, `password`.
