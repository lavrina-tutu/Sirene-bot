## Суть задачи (от Саши)
Добавить в еженедельный self-check проверку наличия персональных данных (ФЗ-152) в: (1) архиве (~/WorkVault, ~/WorkVault_backup), (2) ВМ (ФС вообще, USERTOOLS, скрипты, конфиги, plaintext), (3) сессиях (~/.hermes/sessions, state.db). При находке — репорт в ErrorBus как **критический инцидент** (`--severity critical`, шлётся в Errors-топик всегда, без тротлинга).

## Правило детекции (развивается с Сашей)
Ключевая идея Саши: **тревожен не единичный факт поля, а комбинация, делающая человека однозначно идентифицируемым и доступным для связи** — «карточка человека»:
- идентификатор (ФИО **или** внутр. логин) + поле связи/атрибут (email **или** телефон **или** messenger-handle **или** должность) — встречены в одном контексте.

То, что под «карточку» подпадает: позиция, способ связи, точное определение человека.

## Открытые развилки (НЕ закрыты — ждать решения Саши)
1. **Severity по месту**: моё предложение — двухслойное:
   - покой-хранилище (WorkVault, бэкапы, USERTOOLS, плоские дампы, конфиги) → комбинация = **critical**;
   - переписка/сессия (`~/.hermes/sessions`, `state.db`) → та же комбинация = **warning** (контекст работы, не немедленный инцидент). Альтернатива — одинаковая строгость везде (сессии тоже critical). Рекомендация на старте: переписка → warning, затем по факту первых прогонов решить про ужесточение.
2. **Спец. категории**: паспортные №, домашние адреса/телефоны, номера карт, личные аккаунты вне рабочего контекста — **critical всегда** (их в рабочей системе не должно быть нигде).
3. **Whitelist**: `contacts.enc` (зашифрован AES-256-GCM) — НЕ трогать, явный skip по пути/binary-детекту. Определить, есть ли другие легитимные места (EntityRegistry/Entities — там ФИО+должности хранятся открыто как рабочая база).
4. **Baseline vs прирост**: первый прогон почти наверняка найдёт десятки старых находок задним числом — репортить как N critical сразу / один сводный «первичный аудит» / только прирост с даты запуска (baseline «уже известно, не инцидент»). Нужна ли мини-БД состояния (напр. `~/.hermes/error_bus/pii_scan_baseline.json`).
5. **Дедуп повторов**: critical не троттлится в ErrorBus → дедуп на уровне скрипта (dedup_key = хеш пути+паттерна), иначе лавина каждую неделю.
6. **LLM или чистый regex**: сама задача про защиту ПДн — анализ через LLM создаёт НОВУЮ точку прохождения ПДн через контекст модели (рекурсивный риск). Рассмотреть детерминированный regex-скрипт без LLM, либо маскировать значения в detail.
7. **Конкурентный доступ к `state.db`** — активно используется гейтвеем; полный еженедельный скан рискован. Рассмотреть только `~/.hermes/sessions/*.jsonl` + выборочно новые записи state.db.
8. **Последовательность с pii-privacy**: скан подключать после завершения pii_impl_plan (иначе скан «стреляет» по ещё не устранённым известным находкам pii-privacy) — или сразу как регресс-тест.
9. **Хардкод креды/токены** (security, не privacy) — включать в охват или вне скоупа (ErrorBus §3.6 разделяет security=риск vs ПДн-факт=проблема).
