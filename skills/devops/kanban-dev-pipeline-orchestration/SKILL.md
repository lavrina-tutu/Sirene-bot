# Оркестрация dev-пайплайна на канбане (TZ:*/HF:*/GATE:*)

Поведение диспетчера канбана и стандартные ловушки при разворачивании и ведении
фаз hermes-feature / tz-workflow. Компаньон скиллов `hermes-feature`,
`tz-workflow`, `kanban-worker`, `kanban-orchestrator` (все user-owned — патч через
Cursor, не напрямую).

## Питфолл 1 — «параллельный диспатч» фазы не по цепочке parents

Создаёшь фазы с `parents=[...]` (например HF:verify → HF:test → HF:docs → ...).
Плоский `kanban list --json` может показать несколько карточек **running
одновременно** и `parent_count=0` у всех — как будто диспетчер запустил их
параллельно, игнорируя зависимости.

**ВАЖНО: это часто НЕ баг.** Плоский список не показывает рёбра родитель/ребёнок.
Диспетчер честно промоутит карточку в ready только когда её parents — done; но
если у нескольких карточек общий уже-done прародитель (напр. GATE:take-into-work),
несколько цепочек могут идти параллельно легитимно.

**Проверка перед тем как резать/чинить:**
1. `kanban_show <card>` → читать поля `parents` и `children` (не `parent_count`).
2. Если у карточки правильный `parents` и она ждёт реальный upstream — это
   нормальное dependency-behaviour, **не трогай**.
3. Патологические дубли-гейты (два `GATE:diagnose-review` под одним parent) →
   заархивируй ручной (`hermes kanban archive <id>`), оставь канонный.

## Питфолл 2 — карточка падает в triage после unblock / auto-pass

После `kanban_unblock` гейт может уйти в **triage** (диспетчер реклассифицирует),
а не завершиться. `hermes kanban promote t_...` работает только для todo/blocked,
**не** для triage. Для triage — `hermes kanban specify t_...` (переводит в todo,
переписывает title/body на дефолт — не теряй контекст, он в коммент-треде).

## Питфолл 3 — воркер канбана крашится при спавне

Признаки: `crashed (worker exited)`, `error: pid ... not alive`, затем
`gave_up (retries exhausted)`, карточка в `blocked`. Это **транзиентный
инфраструктурный сбой спавна**, НЕ проблема логики задачи.

**Порядок действий:**
1. Читай `kanban_show` → `events`/`runs`: зафиксируй `error` и число попыток.
2. Сначала **простой ретрай**: `kanban_unblock` → диспетчер повторит. Часто
   3-й запуск работает.
3. Если снова `gave_up` и задача малая (≤3 файла, план уже одобрен) — **реализуй
   напрямую сам** (как координатор), по одобренному плану, без борьбы с диспетчером.
   **Условие (обязательное, инвариант 8):** сначала вывести граф из диспатча —
   `kanban_comment` корня `dispatch-paused: off-board` + снять/не диспатчить remaining,
   и только при снятом `GATE:plan-approve`. Без `dispatch-paused` прямое impl на живой
   граф — это двойной канал (воркер ещё может спавниться), запрещено.
   **Инвариант 8 / off-board применим к живому графу** (анти-параллельность, двойной канал). Для бага БЕЗ карточки (холодный старт: крон-ошибка, триггер «ошибка/не работает/почини» без слага) действует правило «нет графа — сначала заведи канбан-карточку `BUG:diagnose` (DX)». Прямое `agent -p` на разбор/план/реализацию бага без существующей карточки `BUG:diagnose` запрещено (см. hermes-feature Блок 6В).
   4. **Не оставляй реестр полузакрытым.** При прямом выполнении малого фикса/доработки
      (уже имеющего master-ТЗ) закрой и сопутствующие артефакты ТОЙ ЖЕ ЭПОХОЙ, что и
      карточку: bump `version:` в master-ТЗ (X.Y.Z) и правка строки/`updated:` в
      `MAIN_TZ_INVENTORY.md`, в одном проходе. Иначе карточка done, а инвентарь
      остаётся на старой версии — болтается до следующего ручного аудита.
   5. Не списывай на «баг Cursor / openrouter» — это crash-спавн диспетчера, не
      инструмент.

## Питфолл 3b — системный краш воркера НА ВСЕХ фазах графа (многофазный обход через Cursor)

Если крэш-спавн не единичный, а **каждая** TZ:*/REV:*/HF:-фаза графа падает при
спавне («pid not alive» + в логах `sqlite3 no such table: tasks` / `no such column:
status` + `EmptyStreamError` от custom-провайдера) — это **системный** сбой среды
воркера для данного графа/модели, не транзиент. Простой retry (Питфолл 3) не лечит:
диспетчер бесконечно перепланирует и сыпется. Наблюдалось 08.09 (контур B
chain-enforcement, assignee default, worker вызывался на профильной модели).

**Проверка гипотезы (не чини вслепую):**
1. `kanban_show` на 2-3 упавших фазах: у всех `error: pid not alive` при разных PID.
2. `grep` логов: ищи `spawned=N crashed=N gave_up=N` (кратное совпадение у всех фаз)
   и `EmptyStreamError ... provider=custom ... upstream=[cf-ray=...]` — это
   убедительный признак среды спавна/шлюза, а не конфига карточки. `model_override`
   при этом обычно = модель профиля default (НЕ твоя ошибка корня).
3. Не «чини ядро» (schema/воркер) по первому же краху — сначала проверь, что
   прямой запуск единичной фазы через курсор работает (шаг ниже).

**Подтверждённый рабочий обход для МНОГОФАЗНОЙ работы (выполнено end-to-end):**
Веди весь граф **через Cursor CLI по таблице ролей** (как в контуре A):
- каждый `PREFIX:фаза` = отдельный `agent -p` с ролью-моделью по GLOSSARY §3
  (компрессор = deepseek-v4-flash-0731 без Cursor; исполнитель = composer-2.5; архитектор = cursor-grok-4.6-high,
  ревизор = claude-sonnet-5-medium);
- **один вызов = одна роль**, никогда не склеивай TZ-WRITE в один `agent -p`
  (это и есть интерпретация «делай в 1 проход» = авто-гейты, НЕ склейка фаз);
- после каждого вызова **проверяй факт на диске** (grep/синтаксис/версии), не верь
  самоотчёту (контур A/B: стабилизация→компрессия→patch→REV→impl→test→docs шли
  так, чисто);
- веди журнал фазы в `kanban_comment` на корне, чтобы доска была синхронизирована
  с выполненным (даже если карточки-фазы — nothing real, comment о состоянии).

**После постройки GATE:done preflight-скрипта есть нюанс:** `pipeline_gate_done_
preflight.py --slug <slug>` на off-board-графе корректно вернёт **exit 1 (корень
DEV/<slug> не найден)** — это НЕ баг, а демонстрация, что скрипт нельзя «наговорить»:
done требует канонический DEV-корень. Для фактического закрытия обходной работы:
либо заведи DEV-корень и пометь фазы `done off-board` (comment с session ids) — тогда
preflight вернёт 0, — либо явно зафиксируй off-board-исключение (DKP 0.2.4 «off-board /
retro-graph») и не ставь GATE:done формально.

## Питфолл 4 — пассивная IDEA сама разворачивает чужой DEV-пайплайн

Пассивная IDEA-карточка в triage/blocked (созданная как напоминание БЕЗ команды
Саши «разбери») может быть подхвачена диспетчером, «завершена» её `IDEA:analyze`
run'ом, а затем воркер саможалобно подтверждает «делай в 1 проход» и **разворачивает
полный граф `DEV/<slug>` (TZ:s→HF:*) на постороннюю тему** — жжёт LLM-токены вне
скоупа. Наблюдалось 07.09 (t_c4e7fabb → DEV/exchange-contact-upsert из 16 карточек).

**Правила:**
1. Пассивную идею-напоминание для будущей работы **НЕ клади в канбан** как
   диспатчимую карточку — диспетчер её трогает независимо от `blocked`/`triage`.
   Фиксируй в бэклоге/WorkVault (dialog-backlog.md, appendix ТЗ), вне очереди.
2. Если всё-таки создал IDEA-карточку и увидел `status=running` при том, что это
   пассивное напоминание — убей воркера немедленно (`kill -9 <pid>`), проверь
   `task_links`/`tasks` на развёрнутые дочерние DEV-грани, заархивируй.
3. **Не давай «делай в 1 проход» и не подтверждай авто-проход для чужой/теневой
   темы** — этот режим принадлежит текущей активной задача, не подхватывай его для
   оф-топик карточек по их самоприписанному «одобрено».

## Питфолл 5 — режим «1 проход» и HITL-решения протекают на соседние задачи

Согласования/императивы Саши — контекст текущей задачи (`императив` привязан к
конкретной теме). Движок/скиллы могут «переиспользовать» фразу «берём в работу» /
«делай в 1 проход» / авто-проход для другой карточки того же assignee. Если видишь,
что one-pass/HITL-решение по одному слагу применяется к карточке чужого слага —
останавливай: это несанкционированное распространение, а не допустимый перенос.

## Питфолл 6 — двойной ход «1 проход» + живой граф

Сирень по фразе «делай в 1 проход» запускает **свой** `agent -p` (composer/архитектор) **параллельно** живому графу `DEV/<slug>`, пока воркер диспетчера ещё в `HF:plan`/`HF:impl`. Результат — два активных исполнителя на одной фазе: код ложится на диск до `GATE:plan-approve`, `self-report ≠ факт` (воркер до фазы видел пусто, потом «уже есть»). Наблюдалось 09.09 (DEV/EditPlanConfluence).

**Запрет:** пока граф диспатчится (дети `todo/ready/running`), **координатор не вызывает `agent -p` на фазы графа** (инвариант 8, GLOSSARY §5.2). «1 проход» = авто-гейты, НЕ «второй исполнитель». Триггер — только **путь через диспетчер** (auto-pass гейтов, фазы воркерами).

**Если ручной cursor-cli всё же нужен** (crash-спавн, спешка): сначала `kanban_comment` корня `dispatch-paused: off-board` + снять/не диспатчить remaining, затем свой вызов + retro-create `done off-board, session ids`. Иначе — стоп и ждать очередь.

**Инвариант 8 / off-board применим к живому графу** (анти-параллельность, двойной канал). Для бага БЕЗ карточки (холодный старт: крон-ошибка, триггер «ошибка/не работает/почини» без слага) действует правило «нет графа — сначала заведи канбан-карточку `BUG:diagnose` (DX)». Прямое `agent -p` на разбор/план/реализацию бага без существующей карточки `BUG:diagnose` запрещено (см. hermes-feature Блок 6В).

## Питфолл 7 — REV:tz вердикт CHANGES_REQUIRED: как ловить и гонять перепатч

Вердикт `CHANGES_REQUIRED` от ревизора — НЕ конец и НЕ повод waive. Это протухший
мастер-ТЗ, который надо вернуть в ревью через цикл «patch → снова REV». Наблюдалось
09.09 (DEV/PIIScan-pii-hygiene: 4 внутренних противоречия §-vs-§ + 4 правки не долиты
в норматив).

**Голый unblock REV после `CHANGES_REQUIRED` ЗАПРЕЩЁН** (AC-P05, доработка плана
process-rework): он лишь запускает тот же дефект — ревизор снова заблокирует. Вместо
этого — **rework-ребёнок рабочей фазы** (`TZ:patch` / `HF:plan`), ключ
`devpipe:<slug>:<phase>:rework:<n>:<tz_version>`. Parents = рабочая фаза, **не** REV.
После done rework — новая `REV:*` с ключом версии.

**Порядок (проверенный):**
1. REV-карточка сама себя блокирует (`kanban_block`, вердикт в комментарии) — это
   штатно, не чини.
2. Сверять противоречия §-vs-§ **по факту** (прочитать реальный файл/код), не по
   тексту ТЗ. Пример: «§9/§14 запрещают mask_pii, §16 требует его» — открыть
   `AnywhereContacts/logger.py`, показать `_mask_email` оставляет домен → объяснить,
   почему свои mask_* для стерильного хранения правильней.
3. Обсуждение с Сашей — **поштучно в TG**: каждый пункт одним сообщением, цитата
   строки §, своя рекомендация, ничего не менять до «делаем».
4. Саша одобрил → `kanban_comment` на REV-карточке (аудируемый чеклист всех пунктов)
   → выполнить **новый** `TZ:patch` (архитектор cursor-grok-4.6-high) поверх уже
   прошедшего как rework-ребёнок рабочей фазы. Этого шага нет в шаблонном графе —
   добавляется ситуативно.
5. **Сверять результат на диске самому** (grep изменённых секций), не верить
   self-report архитектора — JSON в Cursor может заявить правки, которых нет.
6. Проверить что «запрещённые к троганию» зоны (§«Что НЕ трогать») не поправлены.
7. `kanban_comment` (чеклист «сделано») → повторная `REV:*` с новым ключом версии →
   ревизор перепроверяет исправленный мастер. **version bump в каждом пате**
   (v1.1.0→v1.2.0), иначе REV не отличит правленный ТЗ от старого.

**Сторож исполняет это сам** (Питфолл 12): REV `CHANGES_REQUIRED`/`REQUEST_CHANGES`
→ создаёт rework-ребёнок рабочей фазы, не голый unblock.

## Питфолл 8 — путь к ТЗ в реестре vs факт лежит вне охваченной зоны

Ревизор поймал: §5 ссылается на `Tools/TaskRefresh/session/` (относительный), а код
лежит в `~/USERTOOLS/TaskRefresh/...`, и зоны `~/USERTOOLS/` нет в §4-таблице. Общее
правило: при правке путей в ТЗ сверять с Реальной структурой на диске (`find`), не
копировать относительные пути из старых строк. (09.09, DEV/PIIScan.)

## Брифование — ТОЛЬКО в Telegram, НЕ через канбан (требование Саши)

Бриф ТЗ (поштучные вопросы Q1..Qn) ведётся в живом чате/топике Telegram, не через
`TZ:architect` `kanban_block(needs_input)` silent-воркером. Silent-воркер не годится
для брифа: повторный block → `block_loop_detected` → triage → принудительный `specify`
(переписывает title/body); дорого (полный контекст архитектора на каждый «1 из N»)
и блокирует работу. Живая процедура H в Telegram дешёвая и нелинейная.

**Правило для графа:** канбан-граф `DEV/<slug>` создаём **после** закрытого брифа
(рекомендуется) либо держим корень `blocked` без воркера, пока Сирень ведёт бриф в TG.
`TZ:architect` — write-only (читает решения из чата/коммента), **запрет** ставить
`kanban_block(needs_input)` на TZ/HF-фазах. Вопрос Саше = сообщение в топик.

## Питфолл 9 — разворот DEV-графа: корень-контейнер и клейм created_cards

Наблюдалось 11.09 (DEV/case-collector), прецедент — VestnikTheme t_a6539ca1.

**Симптом 1 — дети навсегда в `todo`:** фазы создаются с `parents=[корень DEV/<slug>]`; промоушен ребёнка в `ready` требует `done` ВСЕХ parents. Если корень держать открытым/заблокированным «до GATE:done» (буквальное чтение tz-workflow §«Когда создавать граф») — очередь фаз мертва, диспетчер ничего не забирает.

**Рабочий паттерн (root-as-container):** разворот фаз через `kanban_create` с `parents=[...]` → полный бриф/решения — в body корня и `kanban_comment` (аудит-след) → корень немедленно `kanban_complete` как координационная карточка (summary = перечень фаз с id, metadata = решения брифа). Дети промоутятся, дальше граф живёт без корня. Канон tz-workflow («корень живёт до GATE:done») с этой практикой расходится — при следующем Cursor-патче tz-workflow выровнять формулировку под root-as-container.

**Симптом 2 — ложный отказ клейма created_cards:** `kanban_complete(created_cards=[...])` может отклонить часть id, реально созданных тем же ходом тем же профилем («do not exist or were not created by this worker»), при `created_by=worker` у всех — гейт срабатывает по внутреннему порядку создания, не по подделке. Не выдумывать id и не спорить с kernel: один ретрай `kanban_complete` с подмножеством id, прошедших клейм, + `metadata.created_graph_note` (полный перечень); полный список держать в `kanban_comment` корня.

## Питфолл 10 — закрытый бриф трактуется как «ждать сигнала»: старт графа блокируется

Наблюдалось 11.09 (DEV/case-collector): Саша дал полную постановку в 2 сообщениях
(постановка + «Кейсы надо определять по смыслу» = фиксация ключевого требования), и
дал императив «передай архитектору, не запускай пока не закончу ТЗ» на ЭТУ вводную.
Сирень интерпретировала дополнение как «бриф ещё формируется» и ~40 минут ждала
сигнала «готово», затем явно ответила «жду твой сигнал» — старт графа заблокирован,
пока Саша не сказал «делай ТЗ и инструмент по полному циклу».

**Правило:** «бриф закрыт» ≠ «нужно дождаться явного "готово"». Если контекст задачи
уже полный (постановка + ключевые развилки закрыты ответами Саши), бриф закрыт —
разворачивай DEV-граф немедленно. Ответ-фиксация («надо X», «кейсы по смыслу»,
«вот ограничение») — это дополнение постановки, не приглашение к брифованию и не
окно clarify. Императив трактовать максимально широко: «передай архитектору» +
«протестируй» + «сверить с ревизором» = полный цикл, второй сигнал не нужен.

**Анти-паттерн:** «Принято, зафиксировала… жду твой сигнал "готово"» после закрытого
брифа. Это превращает активную постановку в пассивное ожидание — при следующем
сообщении Саши, которое НЕ является императивом, пайплайн не стартует вообще.

## Питфолл 11 — `--model` в карточку: worker-модель ≠ Cursor-модель

При `hermes kanban create ... --model cursor-grok-4.6-medium` / `--model claude-sonnet-5-medium` воркер канбана крашится при спавне: шлюз отвергает «cursor-*»/«claude-sonnet-*» как модель воркера (`openrouter model ... must include upstream provider prefix`, HTTP 400). Cursor-/ревизор-модели живут ТОЛЬКО внутри `agent -p --model ...` (который воркер сам вызывает по таблице ролей), а НЕ как model-override карточки. Ставь карточки БЕЗ `--model` — воркер идёт на профильной модели профиля default и сам поднимает нужную Cursor-модель по фазе. Симптом в логах: `HTTP 400 ... must include upstream provider prefix`.

**Heal D1 = СТОРОЖ (первичный контур, AC-P06), не «эскалация постановщику как
единственный путь».** При `protocol_violation` + Cursor-slug в `model_override` сторож
сам делает `hermes kanban set-model <id> none` на всех минах того слага, затем retry.
Воркер не ждёт постановщика, чтобы граф ожил. Питфолл 12 стыкуется: скрипт снимает
model и перезапускает на одном такте cron.
- Не архивируй/`specify` карточку по одному лишь плоскому `kanban list` —
  сначала `kanban_show` с parents/children.
- Не плоди второй гейт того же назначения вручную, если диспетчер уже создал
  канонный.
- Не превращай транзиентный крэш в договор-константу «диспетчер сломан».
- Не клади пассивные идеи-напоминания в диспатчимый канбан — только бэклог/WorkVault.
- Не переноси one-pass/HITL-решение с одной задачи на другую того же assignee.

## Питфолл 12 — координатор «спит» между гейтами и докладывает «всё в порядке» без проверки

Длительные DEV-графы уходят в рабочие фазы (REV/impl/тесты), которые длятся часы.
Координатор считает «всё идёт по канону» и НЕ проверяет до следующего HITL → воркер
падает/ревизор блокирует `CHANGES_REQUIRED`/гейт уходит в triage, а Саше долго никто
не пишет («6 часов молчал и говоришь что в порядке»). Наблюдалось 27-28.09 (mofs/
tg-topic/topic-origin: 3 ревью-блокировки висели 32-36ч, затронутый unblock без правок).

**Скрипт-сторож = ПЕРВИЧНЫЙ контур** (доработка плана process-rework, канбан слаг
dev-process-rework). Детерминированные правила исполняет `kanban_stuck_monitor.py`
(или sibling) на том же cron — он в репортера в исполнителя:
- `running` без heartbeat >20 мин → reclaim + retry (не wall-clock от `started_at`).
- `protocol_violation` + D1 Cursor-slug → `hermes kanban set-model <id> none` + retry (Питфолл 11).
- REV `CHANGES_REQUIRED` / `REQUEST_CHANGES` → rework-ребёнок рабочей фазы, не голый unblock (AC-P05).
- `running` >4ч при живом heartbeat → notify координатору origin графа; >8ч / 2 ретрая → notify Саше + `kanban_block` корня `review-required: stalled-train`.
- «граф оборван»: узел с обязательными детьми по §5.2 без них / обязательной следующей фазы нет.

**LLM-координатор НЕ имеет права сказать «всё в порядке» / «идёт по канону» без
`kanban list` + `kanban_show` по живым DEV.** Скрипт не освобождает от этой гигиены:
он закрывает дыру «Саша молчит → никто не смотрит», а не заменяет проверку координатора.

**Правило:** активный мониторинг, НЕ пассивное ожидание:
- При КАЖДОМ взаимодействии (`?`, запрос статуса, любая реплика) — до ответа проверь
  статусы всех активных DEV-графов (`kanban list` + `kanban_show` на running/blocked/
  triage). Не отвечать по памяти.
- REV-гейты по Питфоллу 7 сами ставят `blocked`/**не** auto-pass — это норма, но их
  надо замечать в первые минуты и прогонять rework, а не через сутки.
- Разблокировка REV после `CHANGES_REQUIRED` = сначала внести правки (rework-карточка
  как ребёнок рабочей фазы: TZ:patch/HF:plan для topic-origin/tg-topic, НЕ ребёнок REV),
  потом вернуть REV на повторный прогон. Голый `unblock` без правок лишь запускает тот
  же дефект — ревизор снова заблокирует.
- НЕ говорить «всё в порядке» / «идёт по канону», пока не проверил фактические статусы
  и не убедился, что у running-воркеров есть живые запуски (heartbeat/run id).
- После запуска воркера (rework/REV/impl) дай короткий статус с таймингами и подтверди,
  что вернёшься к гейту — не «промежуточно не дёргаю» без следа.

## Питфолл 13 — DEV-граф: сирота BUG-диагноза, архив по канону, ретро-сертификация и выбор кейса (30.09)

### 13a — корень DEV + BUG:diagnose ОДНИМ create-батчем; сирота гасит весь граф

Создание DEV-графа двумя `kanban create` подряд (корень `DEV/<slug>`, затем `BUG:diagnose`
**отдельным** вызовом) оставляет BUG-диагноз сиротой (`parents=[]`). Канон требует запуск
корня + `BUG:diagnose` в **одном** create-батче с ребром (инвариант 9). Симптом: `emit-prompt`
G1.1 «карточка не достижима от корня DEV» → вся W0-цепочка (TZ:* и следом) гасится ДО запуска
воркера, `kanban dispatch`/re-диспатч не помогает (эмит-промт красный). Наблюдалось 30.09
(t_d1df295f → t_ab4ec452 сирота, блокер W0 operator-hold).

**Ремонт (одна операция, не пересоздавать):** `hermes kanban link <root-dev> <bug-diagnose>` +
`kanban comment <blocked> "фикс графа: link корень→BUG"` + `kanban unblock`. После link —
диспетчер сам подхватит. Без этого волна мертва (готовый канон не стартует), ре-диспатч
зацикливается.

### 13b — архив по канону: не путать `done` с реально закрытой работой

Требование Саши (29.09): «карточки реально сделанные и подтверждённые — переносим в Архив,
чтобы не смотреть повторно». Механика:
- Архив = отдельный статус `archived`; `kanban archive <id>` переводит карточку в архив,
  исключая из обычных `kanban list` (архив показывается только c `--archived`).
- **Разовый прогон/массовый перенос**: отфильтровать `status='done' AND completed_at<cutoff`
  (или список id), пройти батчами `kanban archive <id>...` (идемпотентно, каждый `Archived <id>`),
  до/после пересчитать `SELECT count(*) GROUP BY status`.
- НЕ архивировать `done` закрытые ПОЗЖЕ cutoff, если Саша не просил; не путать «архив канбана»
  с «архивом документов» (Rock Bulgout/WorkVault) — разные вещи, команды «покажи архив канбана»/
  «покажи историю» реализуются через `kanban list --archived`, а не через docs.
- Проверять перед архивацией, что карточка **реально** закрыта (функционал на диске), а не
  формально `done` (см. 13c и аудит 30.09: 4 из 54 линий были done без функционала).

### 13c — ретро-сертификация: preflight ужесточился ПОСЛЕ старта графа

Граф, построенный по старому канону (до внедрения G2 context-used / AC-P08 «граф-оборван» /
git-proof), при GATE:done валится НОВЫМ preflight — это **ретро-сертификация**, а не недоделка работы.
Наблюдалось 30.09 (topic-origin: магистраль done, но сторож стал жёстче после старта).

**Правило (решение Саши 29.09, вариант А):** НЕ фальсифицировать (не рисовать лживые
context-used/детей/фазы, не пересобирать граф). Закрывать честно:
- либо чинить сам preflight **отдельным** маленьким графом (дедушкина льгота: карточки до даты
  внедрения без нового маркера ок; «оборван» = только обязательный хребет), затем повторный прогон;
- либо выбрать правильный `--case` (см. 13d) и закрыть по нему;
- либо оставить `blocked` как честный красный и зафиксировать «работы выполнены».

### 13d — выбор кейса CHANGE↔BUGFIX при GATE:done — решение постановщика, не кода

Если preflight в кейсе CHANGE требует фаз `TZ:stabilize`/`TZ:compress`, а в графе их нет —
проверь, как граф **реально собран**: есть `BUG:diagnose`+диагноз и нет компрессии ТЗ = BUGFIX
(граф построен как багфикс); метаданные диагноза «BUGFIX→CHANGE process». Льгота
stabilize/compress-optional в preflight — **только для case DEV** (не CHANGE).

- Граф собран как **BUGFIX** → гоняй `preflight --case BUGFIX`; при PASS закрывай. **Не** рисуй
  фейковые stabilize/compress задним числом (ретро = фейк).
- Граф собран как **CHANGE** → нужны реальные stabilize+compress; если они позади, оформить
  переклассификацию кейса + вопрос Саше. Выбор кейса — **решение постановщика/оркестратора,
  архитектор не решает за Сашу** (выносится в отчёт, канон требует его отмашки).

### 13e — ложные operator-hold: preflight читает ТЕКСТ канона из body карточек

`collect_operator_holds` бьёт по **телу карточек** (корень, показ AC), а не только по ТЗ. Ru-регулярка
`depends:\s*operator:(\S+)` матчит любую цитату «с depends: operator:поднимай» (например описание
критерия AC-D02 в body) → ложный operator-hold AC-000, хотя реальных `depends: operator:` /
`operator-done` / open-questions в графе нет. Наблюдалось 30.09 (GATE:done t_51041aa8: «;» и «поднимай»
как hold'ы).

**Fix:** в preflight — глагол hold-а только из закрытого словаря, якорь только `AC-###` (не AC-D02
внутри бэктиков описания), не матчить в бэктиках/кавычках. Формулировку самого канона НЕ переписывать
(это описание критерия, не тег). Добавить тесты: цитата/описание ≠ hold; живой тег в ТЗ по-прежнему валит.

### 13f — `context-used:` обязателен только для Артифактов с реальным `agent -p`

G2 требует `context-used:`-блок на карточках, где воркер **реально звал** агента (курсор-сессия
в прогоне есть). Фазы координации/классификации (BUG:diagnose без `agent -p`, план лежал на диске)
маркер **не требуют** — ставить ретро-маркер = фейк. В preflight: нет Cursor-сессии → skip; была →
обязателен (сужено по букве DKP п.9). Правило исправлено в preflight 30.09 (архитектор).
