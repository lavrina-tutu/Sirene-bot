# PII / ПДн — защита персональных данных в экосистеме

## Overview

Единый взгляд на то, что считать персональными данными (ПДн, закон ФЗ-152) в рабочей системе Hermes/WorkVault и как защищать: (а) маскирование вывода контактов на экран/в контекст; (б) детекция накопленных/остаточных ПДн в хранилищах и отчёт об инцидентах в ErrorBus.

## Правило «ПДн-инцидент» (согласовано с Сашей)

**Инцидент = «карточка человека»**: идентификатор (ФИО **или** внутр. логин) + атрибут связи (email **или** телефон **или** messenger-handle **или** должность) в одном контексте. Единичный email или ФИО сам по себе — не инцидент.

**Severity по месту нахождения (дифференцировано):**
- 🟢 **Живая переписка** `state.db` — НЕ тревожим (рабочий контекст, это норма).
- 🔴 **Покой-хранилища** — critical: `~/.hermes/sessions/*.jsonl` (файловые архивы сессий), WorkVault, `WorkVault_backup`, логи (`~/.hermes/cron/output`, `~/.hermes/logs`, error_bus).

Креды/токены/пароли — **НЕ** в скоупе ПДн-скана (это security, отдельная категория, см. ErrorBus §3.6 «security = риск, privacy = проблема»).

## Whitelist легитимных хранилищ (не сканировать / не считать утечкой)

- `~/WorkVault/Contacts/contacts.enc` — зашифрован (AES-256-GCM), скан его не читает.
- `~/WorkVault/Entities/<slug>/*` — открытые `card.md` с ФИО+должность/департамент+логин (рабочая база vault, легитимна по дизайну). Пример: `Entities/alekseeva/card.md` = `name: Алексеева Юлия; role: Линейный руководитель; department: АИД; login: yalekseeva`.

Без whitelist скан будет сыпать critical по собственной рабочей базе каждый прогон.

## Параметры скана (согласовано)

- **state.db не сканируется** (исключён и из scope — живая переписка не тревожится).
- **Состояние-файлы сессий** (`~/.hermes/sessions/*.jsonl`) сканируются как покой → critical.
- **Первый прогон = baseline**: найденное в первый раз фиксируется как известное состояние без критики (сводный отчёт); инцидент — только **новые** находки со второго прогона. Иначе шторм critical в первый же запуск (critical в ErrorBus не троттлится).
- **Маскирование значений в отчёте**: в detail только путь + тип + количество + маскированное значение (`tk******@tutu.ru`, «Иванов И.*»). Сам скан не должен плодить второй канал утечки ПДн.
- **Закрытие инцидента**: авто-резолв исчезнувшей находки + нотация «исчезло из скана»; исторический факт бывшей утечки сохраняется в audit-список (не теряется).
- **Последовательность**: ПДн-скан включается ПОСЛЕ завершения `pii_impl_plan.md` (регресс-контроль поверх вычищенной системы, baseline чистый).

## Механика отчёта (паттерн self-check)

По образцу `~/.hermes/scripts/llm_anomaly_scan.sh`: отдельный скрипт-сборщик → read-only анализ → репорт через ErrorBus. Встраивание — отдельным `--tool` (напр. `PDnScan`) в `report_error.sh --severity critical`, одна строка-вызов в промпте крона `vm_selfcheck` (как п.11), регистрация в `~/.hermes/error_bus/instrumentation_registry.json` (Mode A).

## Питфоллы

- Наивные regex на «есть email/ФИО» дают вал ложных critical на штатной переписке/рабочей базе — обязателен признак «карточки» + whitelist + дифференцирование по месту.
- critical в ErrorBus не троттлится — повторные прогоны требуют own-дедупликации по конкретному файлу/строке (не полагаться на шину).
- Сам скан ПДн читает ПДн — значения в detail всегда маскировать, иначе скан сам становится источником утечки.
