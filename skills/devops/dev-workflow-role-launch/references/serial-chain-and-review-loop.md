# Точечная серийная цепочка ролей + цикл REQUEST-CHANGES

Правила для multi-role серийного ведения ролей dev-workflow через `codex exec` (прямой режим, без полного канбана). Действует вместе с `references/invoke.md` и `references/direct-mode.md`.

## Запуск роли фоном
- `terminal` отвергает `notify` без `background=true` — прогон падает ошибкой независимо от того, что команда фоновая. Передавай **оба** флага (`background=true`, `notify=true`) с первой попытки; `persist_on_release=true`; вывод через `tee "$D/evidence/<role>.log"`. Пропущенный флаг = лишний упавший запуск и повтор (дорогие входные токены).
- Модель перед каждым тяжёлым прогоном проверяй дешёвым probe-вызовом того же биндинга — алиас модели валиден, потом гоняй большую роль.

## Серийная цепочка без остановок
- Когда владелец велел «делать всё по очереди чтобы быстрее закрыть»: продолжай между ролями, не переспрашивай после каждого артефакта.
- Переходы по готовности: prep-документы принял/одобрил ревизор → finalize. Но finalize, правящий боевые master/inventory/GLOSSARY, — запись в production и требует явного «делай»; prep/read-only роли запускаются без отдельного подтверждения.
- Prep-роль в промпте и в отчёте внешне помечает «это не доставка/не PASS/не допуск»; ревизор флагает любой текст, выдающий подготовку за выполненный перенос или proof.

## Цикл REQUEST-CHANGES → адресные правки
- Ревизор приходит к REQUEST-CHANGES с нумерованными обязательными R1…Rn (файл/строка/раздел/точная правка) + отдельными неблокирующими M.
- Исполнитель вносит ТОЛЬКО эти правки и выпускает changeset-отчёт «старый адрес → новый адрес» по каждой R, не расширяя содержание; затем повторная **адресная** проверка ревизором по каждой R (PASS/FAIL).
- Технические адресные правки не открывают новый содержательный гейт владельца — продолжай без переспроса.
- Дельта-сущности (напр. nodeids) пересчитываются независимо на каждом шаге (retained + new = total, без missing/extra/duplicate) и подтверждаются в отчёте роли.

## Верификация артефакта роли
- Роль перед «done» выполняет собственную проверку: sha256-эквивалентность точек входа, lint markdown, резолв markdown-ссылок, независимый пересчёт числовых инвариантов; выдаёт её в итоговом сообщении.
- Оркестратор сверяет артефакт глазами (read_file) с заявленным и с числами из отчёта — итогом роли на слово не верить.
- Adressный поиск фактов (инвентаризация каталога по provenance) оркестратор может вести параллельно роли; оформляет результат отдельной короткой evidence-заметкой и передаёт роль (напр. ревизору) как вход.

## Разделение ролей за один проход
- Архитектор НЕ решает содержательно за владельца; подготавливает пакет и честно помечает unknown. Ревизор независимо подтверждает подготовительные документы. Исполнитель finalize применяет только адресные стрелки из trace; при непокрытом противоречии не решает сам, фиксирует открытым.
- Новые семантические изменения (напр. замена rc) — отдельный выбор владельца, не часть механического переноса; не подмешивать молча.
