## C1. PD-033 (Tasks plugin) ↔ TZ_G иммутабельность + TZ_D источник истины + PD-019 дедуп

**Что говорит PD-033:** задачи живут в срезах G; `action_items.md` = Tasks-query-агрегатор; закрытие чекбокса в query правит файл-источник (срез G); Haiku пишет задачи в срез, не в `action_items.md`.

**С чем конфликтует:**
- `TZ_G` §4, §6: срез **иммутабелен** («нет перезаписей, нет алиасов latest»). Если чекбокс задачи правит срез — **срез больше не иммутабелен**.
- `TZ_D`: `action_items.md` — **источник истины**, сквозная нумерация `#N`, дедуп по ключу. PD-033 делает его производным.
- `PD-019` (дедуп: одна задача на N встреч = одна запись) ↔ задача обсуждалась на 3 встречах → 3 среза → **3 чекбокса** в query. Tasks-plugin нативно **не дедуплицирует** одинаковые задачи между файлами.
- `TZ_E`: `commitments.md` — People-аналог `action_items.md`. PD-033 про него молчит.

**Моя рекомендация (вариант, сохраняющий все инварианты):**
- **Источник истины задачи — `action_items.md`** (как в ТЗ): дедуп по ключу, сквозной `#N`, lifecycle.
- В **срез G** встраивать **отфильтрованный Tasks/Dataview-запрос** (read-only view) — «задачи, затронутые на этой встрече». Срез остаётся иммутабельным (в нём query, а не сами задачи).
- **Глобальный список** и **список по проекту** — тоже Tasks-query к `action_items.md` / `People/*/commitments.md`.
- Закрытие чекбокса в любом query правит **`action_items.md`** (Tasks plugin редактирует файл, где физически лежит задача) — единая точка закрытия достигается, как и хотел PM.
- То же для `commitments.md` (People).

**Чем отличается от буквы PD-033:** источник = `action_items.md`, а не срез G. Интент PD-033 (один список, закрыл в одном месте — закрылось везде, без дублей) **сохраняется**, а дедуп/нумерация/иммутабельность срезов — не ломаются.

**Нужно от PM:** подтвердить этот вариант ИЛИ настоять на «задачи физически в срезах» (тогда: срезы перестают быть иммутабельными + нужен механизм дедупа задач по stable-id между срезами — отдельная разработка).

## C2. PD-028 + PD-030 (Haiku везде, итеративный обход) ↔ TZ_C двухшаговая архитектура (Opus)

**Что говорит PD-028/030:** Opus убран везде; bootstrap = поштучный обход встреч от ранней к актуальной, Haiku пополняет decisions+action_items+risks, сравнивая с накопленным инкрементом.

**С чем конфликтует:**
- `TZ_C` «В1 — Модель» и «Архитектура (два шага)»: **Шаг 2 = Opus-агрегация** (×13 проектов, один вызов на проект, агрегирует все summary сразу). Это ядро модуля C.
- `TZ_D` «Bootstrap vs Инкремент»: «Шаг 2 (Opus) агрегирует историю».
- `TZ_C` сам предупреждал: «качество сигналов на инкременте ниже — нет контекста истории». Теперь весь bootstrap идёт инкрементным путём на Haiku.

**Моя рекомендация:**
- **Унифицировать пути:** bootstrap = **хронологический реплей инкремент-пути** (Haiku) по каждой сущности (а не один большой вызов). Один код для bootstrap и инкремента → меньше багов.
- **Шаг 1 (Haiku-разметка/роутинг + резолв людей + флаги наличия сигналов)** — **оставить**, он дёшев и нужен для классификации.
- **Шаг 2** — заменить с «Opus-агрегация всего проекта» на «Haiku-извлечение по одной встрече в порядке дат + накопление в D».
- Резолв конфликтов при реплее — в D (OQ-004, уже в ТЗ).
- **Sonnet** — только для golden-compare (раздел Q5), не в основном цикле.

**Риск (зафиксировать для PM):** Haiku на длинной истории без агрегирующего контекста может терять связи «решение X отменено через 3 встречи». Митигируется тем, что на каждом шаге Haiku видит **накопленный инкремент** (decisions/action_items/risks к этому моменту) как контекст. Это нужно явно прописать в промпте C.

**Нужно от PM:** подтвердить (а) отказ от Opus полностью, (б) bootstrap = реплей инкремента, (в) Шаг-1 Haiku остаётся.
